## 用例质量红线

1. **断言的是 AC 里的可观测断言，不是实现细节**（断言实现细节 = 又变回与实现同源）
2. **三类覆盖齐全**：单点（单次操作）/ **序列**（做 A → 做 B → 切走再切回 → 刷新，断言中间态与最终态）/ 边界（空数据、超长输入、并发编辑、权限不足）
3. 🚨 **断言从未执行 = 假绿**：数据为空 → 循环 0 次 / 分支没走到 → 断言压根没跑，测试照样报绿。
   **前置数据必须是真实业务数据，不是能让断言空跑的空夹具**；断言前先断言「结果非空」，并要求打印实际值。
4. 🚨 **新加的守卫/断言必须做一次证伪实验**：故意破坏它保护的条件，确认它**硬失败**。首次 PASS 证明不了它接上了——**自己写的验证脚本同样适用**（命令写错导致全程空输出，看起来和"全部通过"一模一样）。

## 不稳定失败的处理

**症状是「随机挂一条、每次挂的还不一样、数据看着合理但对不上」→ 先查测试基础设施，再查业务代码。**
高频根因在并发、端口分配、临时目录、共享库、全局状态，不在业务代码。

- ⚠️ 这类症状**两个方向的证据同时失效**：绿可能只是没撞上，红可能是被污染而非真缺陷。**harness 被证明可信之前，测试报告不作为验收证据。**
- 🚫 **禁止以「偶发，重跑一下就好」结案。** 宣称修好要给**重复次数**，且次数与修法性质匹配：结构性修复（失败模式被构造性消除）少量即可；概率性修复按 `p^n` 算 —— 通过率 0.83 时，**跑两次全绿有 69% 是运气**。
- **探活必须验明正身**：只看 HTTP 200 会探到别人的实例，然后把断言打在别人的库上。
