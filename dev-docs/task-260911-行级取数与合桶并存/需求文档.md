## ① 背景与目标

### 为什么做

`repair-260910` 给报价单产品页签加了**行级取数收窄**——视图要按**当前明细行自己的**客户产品编号过滤。
它已交付并验收通过，但代价是**退出了「合桶」**。

**合桶是什么、为什么它会失效**（实查 `ComponentDriverService.eligibleForQuoteBucket` → `viewHasNoRowDimension`）：

> 合桶 = 按**去重后的料号**一次查回全单数据，再分发给各产品卡片。
> 它成立的**充要条件**是「视图结果不依赖行」——方法 javadoc 原话：
> 「与逐行 expand 对无行维度视图**逐位等价（li.id 被视图忽略）**」。

`repair-260910` 让视图开始读 `lineItem.customer_part_no` ⇒ **同一料号的两个明细行要的数据不再相同**
⇒ 那个等式**在定义上**不再成立 ⇒ 只能退出合桶，整单物化从 **1 次 `expandMulti`** 变成
**每明细行 1 次 expand + 1 次反查**。

**用户原话（2026-09-10）**：

> 合桶是必须要保留的，这个是性能和速度的基石。有没有同时体现在取数配置上又保留合桶的方法

### 代价有多大（2026-09-11 实测）

| 项 | 数值 |
|---|---|
| 报价单总数 / 平均明细行 | 127 张 / **31.3 行** |
| 其中 ≤ 15 行的 | **125 张**（多几十条 SQL 无感） |
| **超 50 行的** | **2 张，均 1845 行** ⇒ 约 **3690 条 SQL**（仅该组件） |

1845 行的单正是 `task-260825 大单量导入建单性能` 刚优化过的路径，本次改动与它方向相反。

### 目标

**让"取数口径可以依赖行"与"查询仍然合并"同时成立**，且这件事**表达在取数配置里**，不是写死在 Java 里。

## ④ 依赖与影响面

### 语义图的真实存储（2026-09-11 实查，纠正过一次引用错误）

编译器读的是**两张数据库表**：`semantic_node` / `semantic_node_column`
（`SemanticCompiler.compile(SemanticGraphSnapshot, …)` ← `SemanticGraphLoader`）。

🚫 **不是** `QuoteRegistry.java` 的 `SheetDef`/`SUBDIM` —— 那是 `AbstractDatasetRegistry` 的**数据集导入 sheet 定义**
（与建表迁移 `V405`/`V408` 同源）。`repair-260910` 的 `问题说明 §4.1` 曾引错此处，已于 2026-09-11 更正。

**`roles` 机制是活的且有现成扩展点**（全库实查）：

| roles 值 | 列数 | 节点数 |
|---|---|---|
| `{}` | 236 | 51 |
| `{ROW_KEY}` | 50 | 38 |
| `{PART_NO,ROW_KEY}` | 42 | 42 |
| `{SORT}` | 28 | 28 |
| `{PART_NAME}` | 8 | 8 |
| `{PART_NO}` | 2 | 2 |

编译器在 `SemanticCompiler:746-829` 消费它，**且已有两层覆盖**：
页签视图列级覆盖（`semantic_tab_view_column`）优先于节点级默认（`D-35`，见 `:746` 注释）。

⚠️ **实查 `CUSTOMER_PART` 节点（QUOTE 方言）5 列 `roles` 全为空 `{}`** ——
`customer_product_no` 当前**没有任何角色标记**，这正是编译器不知道它参与行粒度的原因。

**2026-09-10，关于合桶（本任务的立项理由）**：

**2026-09-10，用户对合桶规则的理解（澄清的起点）**：

> 我理解的合桶规则就是一次性把要查的所有料号数据都查出来,然后组装拼会到各个产品卡片上,避免每个产品卡片的每个页签都要计算,是这样吗?

② 省的是**查询**不是**计算**（公式仍逐行求值）。
