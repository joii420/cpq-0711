## 二、🚨 三个 AC 可执行性问题（都是主线写 AC 时的错）

### ① AC-1 的「SQL 执行次数 = 1」与现成正面样本自相矛盾（S3 报）

S3 实测：**可合桶组件（材质元素 `builder_98ee51d1832e`）在同一次物化里也是 2 次** = 1 桶查询 + 1 预取。
⇒ 按 AC-1 字面的「=1」，**这个现成的、本来就合桶的正面样本自己都不满足**。

S3 建议的措辞：**「逐明细行 expand 次数 = 0，桶查询 = 1」**（总计数会是 2）。
S3 原话：「若按字面要求『=1』，材质元素这个现成的正面样本自己都不满足……我不自行解释成一个可测的意思。」

**改动前基线（产品组件 `builder_221dc7668ab6`，4 明细行同料号）**：
```
执行 5 次 = 1 预取(lineItemId=null, rows=4) + 4 逐明细行(rows=1 each)
[quote-bucket] quotation=e166c7d9… eligibleComps=1 totalComps=3 distinctParts=1
   ⇒ comp=221dc766 不在 eligible 列表 ⇒ eligibleForQuoteBucket = false   ← AC-2 基线
```
在 8103（独立源码副本实例）**逐项复现 5/2/1 次** ⇒ 不是 8081 的实例特性。

### ② AC-12 的耗时判据会被共享机噪声吞掉（S3 报）

三轮实测 1200 明细行单：`30.2s / 28.8s / 21.0s`，**抖动 44%**（run2 窗口还混入他人 7 个视图各 4 次执行）。
而 **SQL 次数 `1201`（1 预取 + 1200 逐行）三轮零漂移**。
⇒ S3 建议 AC-12 改以「SQL 次数 1201 → 2」为主判据、耗时为辅。

📌 S3 另证：**造 1200 行没有困难**（`INSERT … SELECT` 复用现有客户料号，<1s），**不需要降级规模**。

### ③ AC-11 的「为什么不变」解释站不住（S1 报，主线已部分核实）

⚠️ **主线核实后的补充（S1 与主线各对一半）**：
- S1 查的 `template_sql_view`（表）确实 0 行；
- 但主线在 `repair-260910` 推的是 **`template.sql_views_snapshot`（`template` 表的列）**，该列**存在**，且 `BuilderRecompileService:39/158` 明写「两层都要推」「缺陷①要救的存量单读的就是它」。

  **DRAFT 单到底读哪一层，尚未定论**，待后端就绪后由实测回答。

✅ **但 AC-11 的断言本身不用改**：S1 已按**更强判据**采基线（直接比对渲染产出逐字节相同），不依赖"哪一层挡着"这个解释。要改的只是 `需求文档 ④` 里那句因果解释。
