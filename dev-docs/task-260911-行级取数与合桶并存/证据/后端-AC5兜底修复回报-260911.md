# 后端 · AC-5 兜底修复回报落盘（2026-09-11）

## 根因：真实 bdv 键带花括号，旧匹配条件恒 false

```
"driverRow":       { ..., "_客户料号_客户产品编号": null }                               ← 清了 ✅
"basicDataValues": { ..., "{$builder_221dc7668ab6._客户料号_客户产品编号}": "RW-A004" }  ← 没清 ❌
"row_data":        { ..., "客户产品编号": "RW-A004" }                                    ← 下游
```

旧代码 `key.endsWith("." + viewColumn)`，而键以 `}` 收尾 ⇒ **永远不匹配**。

**为什么会显示出来**（`FormulaCalculator.resolveRowByFieldName` 对 `INPUT_*` 的瀑布）：
`editValues(空)` → `driverRow["客户产品编号"]`（字段名≠视图列名，取不到）→ `default_source.path`
→ `lookupBdv(basicDataValues, "{...}")` ← **从这里读到别人的值** → `content`

📌 `ExpandDriverResponse.Row` 的 javadoc 本来就写着「key = 字段原始路径**(含花括号)**」—— **契约一直在那儿**。

**修法**：抽 `static boolean bdvKeyTargets(String key, String viewColumn)` —— **先剥两端花括号再按 `.<视图列名>` 结尾匹配**（仍不用 `contains`，避免后缀撞名误清）。

## 🚨 为什么上一轮单测没抓住（主线要求定位，已查到）

| | 旧用例（假绿） | 新用例 |
|---|---|---|
| `basicDataValues` 键 | `"$builder_221dc7668ab6._客户料号_客户产品编号"` | `"{$builder_221dc7668ab6._客户料号_客户产品编号}"` |
| 构造方式 | 手搓 `Map.put` | **`ObjectMapper.readValue` 真实响应 JSON** |
| 对旧代码 | `endsWith(".", vc)` → **true** ⇒ 绿 | → **false** ⇒ 红 |

> 上一轮的「证伪 2」**是真的跑了、也真的变红了**，但它**证伪的是一个真实世界不存在的输入形态**。
> 手搓夹具在简化结构时，顺手把唯一能抓住这个 bug 的那个特征（花括号）也简化掉了。

**结构性防护**：新用例 `LIVE_BUCKET_JSON` 从 S2 原始响应**逐字照抄**，走 Jackson 反序列化进 `ExpandDriverResponse`。
