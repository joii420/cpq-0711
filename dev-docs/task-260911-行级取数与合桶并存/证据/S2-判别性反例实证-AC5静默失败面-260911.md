## 二、这个发现说明了什么（主线分析）

### 机制：集合谓词丢掉了 LEFT JOIN 对"空值"的保底能力

| 方案 | 空客编明细行会怎样 | 为什么 |
|---|---|---|
| **V1 标量**（`repair-260910` 现状） | ✅ **1 行，客编列空** | `customer_product_no = :customerProductNo` 在绑 NULL 时**恒 UNKNOWN** ⇒ 该料号的**所有** `dqcp` 行都不匹配 ⇒ LEFT JOIN **天然产生一行"未匹配"记录**（物料侧有值、客编侧全 NULL）|
| **V2 集合**（本任务方案） | ❌ **0 行** | 集合 `{CP1,CP2,CP3}` **不含 NULL 项**，但该料号的 CP1/CP2/CP3 **会匹配上** ⇒ LEFT JOIN 有匹配 ⇒ **"未匹配那一行"根本不产生** ⇒ 桶里 3 行都不属于空客编的明细行 ⇒ 分发层**挑不到** |

🔑 **关键洞察**：V1 的空值保底**不是显式写的逻辑，是 LEFT JOIN 在"全不匹配"时的副产品**。
换成集合谓词后，只要该料号**还有别的客编在集合里**，这个副产品就消失了。
⇒ **它是被静默拿掉的，不会报错、不会有任何告警**，只表现为那类明细行整页签 0 行。

### 对方案的影响

`backtask.md B-6`（空值兜底）原本被我写成一条"配套守卫"。**这个实证把它的地位改了**：
它不是守卫，而是**方案能否成立的必要条件** —— 不做 B-6，`AC-5` 必红，而且影响面是实测的 **128/3970** 明细行。

### 兜底只能在分发层做（SQL 层无解）

- 🚫 往集合里塞 NULL 哨兵无效：PG 的 `= ANY(array)` 对 NULL 元素同样是 UNKNOWN
- 🚫 加 `OR customer_product_no IS NULL` 是另一回事：那匹配的是 `ds_quote_customer_part` 表里客编为 NULL 的**数据行**，不是"本明细行没有客编"
- 🚫 把"本行客编是否为空"写进谓词 = 行级条件 = **又破坏合桶**，回到原点

✅ **唯一出路：分发层构造。** 桶里挑不到时，取该料号的任意一行、**把作用域列置空**返回。
这在数据上是安全的——桶里这几行的**物料侧列完全相同**（同一个 `dqm` 行 LEFT JOIN 出来的），
差异只在 `dqcp` 侧的列。

## 三、对 `AC-5` 与 `B-6` 的措辞修订建议（待主线确认后同步四处）

`AC-5` 现文只说"仍渲染 1 行、客编列空、物料侧列有值"——**没说清这一行从哪来**。
建议补一句实现约定，使它可验证且不可绕过：

> 桶内无匹配行时，分发层**必须**基于该料号的任一桶内行构造返回行，
> 并将作用域列（及同源于 `dqcp` 的其余列）置空；🚫 不得返回 0 行，🚫 不得回退逐行查询（那会重新破坏合桶）。
