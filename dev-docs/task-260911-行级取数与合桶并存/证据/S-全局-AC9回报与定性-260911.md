# S-全局片 · AC-9 回报落盘 + 主线定性（2026-09-11）

## 一、S-全局的结论：AC-9 **编译产物层面通过**

**选列**：`CUSTOMER_PART(QUOTE).customer_part_name`（未用主线建议的 `customer_drawing_no`）。
**它的理由（比我的建议好，采纳）**：`customer_part_name` 被 **2 个 ACTIVE 视图**的 `builder_config` 真实选中；
而 `customer_drawing_no` 不被任何 `builder_config` 选中，**一旦产物无变化将无法区分「机制不通用」与「该列压根没进编译范围」** —— 会得到不可判别的结果。

**编译产物 diff**（`POST /components/{id}/builder/compile`，不落库）：
```
-  ... AND dqcp.customer_product_no = ANY(:customerProductNos)
+  ... AND dqcp.customer_part_name = ANY(:customerPartNames) AND dqcp.customer_product_no = ANY(:customerProductNos)
---- requiredVariables: customerCode,customerProductNos,total_material_no
+--- requiredVariables: customerCode,customerPartNames,customerProductNos,total_material_no
```
三个产品视图产出同一处增量；`customerPartNames` 在 `LEFT JOIN…ON` **1 次**、在 `WHERE` **0 次**。
参数名推导 `customer_part_name → :customerPartNames` 与既有 `customer_product_no → :customerProductNos` 同一套，**非硬编码映射**。

**`git diff` 证明 Java 零改动**：`git diff --name-only -- "*.java"` 空、`git status --porcelain -- "*.java"` 空。

**证伪回路（两端都做）**：正向控制（投一份删掉 `dimension` 列的 config → 产物跟着少一列 ⇒ 端点是真编译不是回放）· 反向（撤标记后新 JVM 重编 → **逐字节回到 BEFORE**）· 零落库（102 个视图 `sql_template` md5 前后逐行一致）。

**还原已复验**：`ROW_SCOPE` 列数回到 **1**、`PART_NAME` 回到 **8**，与 BEFORE 快照 `diff` 零差异；`updated_by/updated_at` 未被触碰。

## 🚨 二、S-全局报的两条发现

### ① 长驻实例有语义图内存缓存 —— 这是 AC-9 的**假红陷阱**
在 8081（启动早于 UPDATE）上打完标记后重编，产物**毫无变化**；同一时刻、同一份 config、同一个库，**全新 JVM（8107）**编出来就带新谓词。
⇒ **它差点把 AC-9 判成"机制不通用"而误红。**
⇒ **部署含义**：`V441` 这类 `roles` 迁移**上线后必须让实例重载语义图**，否则"只改配置"不落地。
📌 本次交付侥幸没踩到：V441 落库时代码也变了 ⇒ Quarkus 热重启 ⇒ 新 JVM ⇒ 语义图重新加载。**但纯迁移场景不会有这个副作用。**

### ② 标记是**节点级**生效，不限于选中该列的视图
对照组 `builder_221dc7668ab6` 的 `builder_config` **并未选** `customer_part_name`，但它 JOIN 了 `CUSTOMER_PART` 节点，编译产物**同样**多出该谓词。
⇒ 给任一列打标记会波及**所有 JOIN 该节点的视图**（本次 3 个产品视图全中），它们的 `requiredVariables` 都会新增该参数。

## 三、🔑 主线据此实查后的 AC-9 准确定性：**部分达成**

S-全局提出一个它无法验证的风险：「`:customerPartNames` 在运行时**是否有绑定方提供取值**」。**主线查实了**：

**绑值侧是通用的**（`SqlViewExecutor.enrichRowScopeSets:541`）：
```java
for (SemanticNodeColumn col : snap.nodeColumns) {
    if (!col.roles.contains(ROW_SCOPE)) continue;        // 遍历语义图所有 ROW_SCOPE 列
    String param = RowScopeSupport.setParamName(col.dbColumn);   // 参数名按列名推导
    String liCol = RowScopeSupport.lineItemColumnFor(col.dbColumn);
    values = queryRowScopeValues(qid, liCol);            // SELECT DISTINCT <liCol> FROM quotation_line_item
    namedParams.put(param, values);
}
```
⇒ **不是硬编码到 `customer_part_no`。**

**但取值列的映射有边界**（`RowScopeSupport.lineItemColumnFor:106`）：
```java
return LINE_ITEM_COLUMN_ALIAS.getOrDefault(dbColumn, dbColumn);   // 映射不到就用原列名
```
⇒ 若该列在 `quotation_line_item` 上**没有同名列、也没在别名表里登记**，
`queryRowScopeValues` 执行 `SELECT DISTINCT customer_part_name FROM quotation_line_item` 会报错、
**被 catch 返回空集合** ⇒ `= ANY(ARRAY[]::text[])` 恒 FALSE ⇒ JOIN 全不匹配 ⇒ 走 B-6 兜底 ⇒ **1 行 + 该列置空**。

### ⇒ 结论

| AC-9 的两个半句 | 判定 |
|---|---|
| 「只改配置、不改任何 Java 代码，**编译器即生成集合谓词**」 | ✅ **达成**（编译产物 diff + git diff 双证） |
| 「**参与回分**（运行时生效）」 | ⚠️ **有条件达成** —— 要求该列在 `quotation_line_item` 上有**同名列**，或在 `LINE_ITEM_COLUMN_ALIAS` 登记别名。否则**不崩、但收窄恒不生效**（降级为兜底置空） |

🚨 **这条边界必须写进文档**：否则下一个人给某列打 `ROW_SCOPE`，会遇到「**没生效、也没报错**」—— 正是本项目反复栽的那类静默失败。

## 五、S-全局规避掉的坑

1. **8081 缓存导致的 false negative**：差点把 AC-9 判失败，改用全新 JVM 才拿到真结果
2. **无判别力的探针不当证据**：中途用 `PART_NAME` 角色做缓存探针，产物无变化 —— 但查全库发现**没有任何视图产出 `hf_part_name`**，该探针**本身不可判别**，因此**没有**据它下"存在缓存"的结论（后来用新 JVM 才定论）。探针已即刻撤回
3. **端点回放嫌疑**：先用"删一列"正向控制确认 `/compile` 是真编译
4. `pkill` 每次都核对 8081/8091/8097/8099/8103 仍在监听，未误伤他人
5. 临时实例日志里那批 `alter table …` **不是执行的 DDL**：`database.generation=none`，那是 `SchemaManagementIntegrator` 因 `mat_composite_process` 缺表打印的**建议 SQL**（已知既有状态），对共享库零副作用
