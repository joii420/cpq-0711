## 二、方法论纠正：为什么 S2 不采信最初那份 UI 绿

> `MAIN` 单的 `row_data` 写于**改动前**（09:15，V441 落库于 09:23），而 **UI 渲染读 `row_data`**
> ⇒ **MAIN 的 UI 绿不具判别力，机制全坏它也会绿**。

⇒ S2 自建**零残留 FRESH 载体**重跑，要求三层同时成立才判通过。

📌 这与 S3 那条「8097/8103 不能当改动前一侧」是**同一族**：
**载体/实例里残留的旧产物会让判据恒绿**，必须确认每一层数据都是当前代码产出的。

## 三、AC-8：分层判定 + 控制实验归因

改 `so=2` 客编 `CP3 → CP2`：

- **取数/物化层 ✅**：`snapshot_rows` 从 `CP3 → CP2`，其余四行纹丝不动；还原 `CP2 → CP3` 同样跟回
  ⇒ **双向正向控制成立，绑定是活的不是常量**
- **UI 层 ❌**：四个时点（改值后 / 物化后 / 刷新后 / 切走切回后）**始终显示旧值 CP3**，
  因 `row_data`（用户编辑层）钉住旧值，而 `refresh-snapshot` 按设计"保留用户编辑层 row_data"

**归因：非本任务引入（S2 做了控制实验）**：改一个**非 `ROW_SCOPE` 列**（`ds_quote_material.material_name`），
`snapshot_rows` 跟着变、`row_data` 与 UI 同样钉住旧值 ⇒ 钉住是 `row_data` 编辑层的**通用属性**，与行级作用域机制无关。（实验后已还原。）

⚠️ **S2 主动标注的未验证项**：`quotation_line_item.customer_part_no` 在 **UI 上没有编辑入口**
（Step1 实测只有客户信息，无明细行客编字段）。它是用 DB UPDATE 代表"改客编"。
⇒ **该 AC 的用户路径未验证**；若存在它没找到的入口，结论需重跑。
