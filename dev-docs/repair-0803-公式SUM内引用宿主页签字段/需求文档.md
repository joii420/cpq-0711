## 1. 背景与目标

### 1.1 现象

跨页签聚合公式里，`SUM(...)` 的 `targetExpr` 内引用**本页签（宿主）字段**时：

| 被引用字段类型 | 当前行为 |
|---|---|
| `INPUT_NUMBER` / `INPUT_TEXT` / `INPUT` | ✅ 取到值，逐行参与 |
| **`FORMULA`** | ❌ **恒取 0**，静默少算 |

不报错、不提示，只是算少了。现网 `COMP-0157「物料」` 的 `v2-原材料成本公式(银点类)` 正踩着：公式里写的 `(1 + [来料损耗率]/100)` 恒等于 1、`+ [来料加工费]` 恒等于 +0。

### 1.2 根因

`b_field` token 读 `ctx.currentRowRaw`，而 FORMULA 字段的计算结果**只回填 `fieldValues`，从不写回 `currentRowRaw`**。前后端同构：

| 层 | 取值来源 | 回填位置 | 代码位置 |
|---|---|---|---|
| 后端 `b_field` | `ctx.currentRowRaw` | — | `FormulaCalculator.java:195-200` |
| 后端 FORMULA 求值 | — | `ctx.fieldValues.put(name, val)` | `FormulaCalculator.java:884` |
| 后端 INPUT 补值 | — | `currentRowRaw`（**仅 INPUT_\* 类型**） | `FormulaCalculator.java:1861` |
| 前端 `b_field` | `currentRow`（mergedRow） | — | `formulaEngine.ts:415` |
| 前端 FORMULA 求值 | — | `fieldValues[name] = val` | `QuotationStep2.tsx:~696` |

`currentRowRaw` 装的是 driver 行 + 用户编辑值 + INPUT 类型的 default_source 补值，**从来不含公式算出的东西**。

第二层根因：依赖收集器**不递归 `targetExpr`、不认 `b_field`**，两端同样对称：

- 后端 `FormulaCalculator.addExprFieldDeps:1567-1575` — 只扫顶层 `type=="field"`
- 前端 `QuotationStep2.tsx getFormulaDeps:407-413` — 只扫顶层 `type==='field'`

即便让值取得到，**字段级拓扑序也不知道要先算被引用字段** → 结果时对时错，比现在恒 0 更难排查。故两层必须一起修。

### 1.3 目标

让 `targetExpr` 内引用宿主页签的**任意类型字段**（含 FORMULA）都取到正确值，前后端结果一致，且不改变任何现有正确公式的计算结果。

### 1.4 不做会怎样

用户在公式编辑器里能配出这种引用（`CrossTabRefDrawer.tsx:490` 的「本组件字段」下拉**不过滤任何类型**），配出来就静默少算，金额直接错，无任何提示。

## 3. 澄清结论与决策记录

| # | 决策项 | 结论 | 理由 | 被否决的方案及原因 |
|---|---|---|---|---|
| **D-1** | `SUM` 内引用宿主字段的**语义**定为什么 | **逐行广播**：每个匹配行各取一次宿主值，`SUM(aᵢ + D) = Σaᵢ + N·D` | **这不是新语义，是引擎既有语义**——实证：`b_field` 指向 `INPUT_NUMBER` 字段时本来就是逐行广播；`targetExpr` 内嵌套 `cross_tab_ref` 也是逐行广播（N=2 时实测 20.0 = Σaᵢ+2×5）。FORMULA 取 0 才是异类。修复 = 让 FORMULA 与既有行为对齐 | ❌「按提取语义只算一次」：会让 `b_field` 指向 FORMULA 与指向 INPUT 的行为不一致，制造第二种规则；且"只算一次"已有清晰表达方式（写在 SUM 外） |
| **D-2** | 怎么让 `b_field` 取到 FORMULA 值 | **只改取值链**：`currentRowRaw[n] ?? fieldValues[n] ?? 0`，**不碰 `currentRowRaw` 本身** | 影响面精确限定在 `b_field` token 一个分支，其余 token 与流程逐位不变 | ❌「把 FORMULA 结果写回 `currentRowRaw`」：① 会污染内层 KSUM 的 match 键（`targetRowValue:449-454` 的 `mergedCurrentRow` 供 match 的 b 键取值）；② 会绕过单位换算（`convertResolvedRow` 在 `:871` 执行，FORMULA 求值在 `:873-885` 之后，写回的值永远赶不上换算）。现网实测这两条风险各为 0 处，但那是数据恰好，不是结构安全 |
| **D-3** | 依赖收集要不要一起改 | **必须一起改**，且前后端对称 | 只改取值不改依赖 → 拓扑序不保证被引用字段先算 → 结果时对时错，比恒 0 更难查 | ❌「先改取值，依赖后补」：会产出一个不确定性 bug，违背"保证计算正确"的前提 |
| **D-4** | 存量 8 条公式怎么处理 | **逐条人工确认业务意图后改写**，不做无人值守迁移 | 这 8 条当前恒 0（少算），修复后变 N 次（多算）。若本意是"加一次"，必须同步改写成提到 SUM 外，否则从少算变多算 | ❌「修完就算」：会把 8 条公式的错误方向反转，金额变大更难察觉 |
| **D-5** | 要不要禁止 SUM 内引用 FORMULA 字段 | **不禁止**，改为修复 + 配置期提示 | 用户已明确：需要的是"这类公式能正确计算"的方案，不是堵死 | ❌「配置期拦截报错」：堵而不疏，合法需求无法表达 |
| **D-6** | 语义歧义怎么让用户可预期 | 两种意图**各有明确写法**，并在配置期提示 | 引擎无法推断业务意图，只能让表达方式区分开 | — |
| **D-7** | 成环时怎么告知用户 | **弹抽屉**（`Drawer`）列出每个环的完整链路 + 每条边出自哪条公式 | 环是"配置员必须照着逐条改"的信息，需要常驻、可分组、可点击定位；`CLAUDE.md` UI 规范明确弹出式交互一律用 Drawer | ❌「保持现有常驻 notification」：宽 520 的纯文本块，多个环挤在一起无法分组，不能点击跳转，长链路会被挤压换行 ❌「message.error」：换行折叠成一行 + 3s 消失，配置员来不及看（现有代码注释已记载此教训） |
| **D-8** | 链路里用什么标识节点 | **只用组件名称 + 公式名称 + 字段名称**；id 仅作为跳转用的隐藏属性 | 用户诉求明确：ID 无法辨认。现状 `CrossTabComponentOrder:41` 抛的是纯 UUID（`[56c8a517-…, 74c0cede-…]`），正是本次要消灭的形态 | ❌「名称 + ID 并列展示」：ID 对配置员无意义，只增加噪声 |
| **D-9** | 老的 `dfsCycleDetect` 校验怎么办 | **删除**（`ComponentService:1197`） | 它抛「请检查公式间的依赖关系」，零定位信息，能力已被 `describeFormulaCycles` + `cyclicFormulaNodes` 完全覆盖，留着只会让同一个环报出两种不同文案 | ❌「保留做兜底」：兜底已有 `cyclicFormulaNodes`（`:1045-1048`），三重校验徒增分叉 |

### D-6 两种意图的表达方式（写进用户文档）

| 业务意图 | 写法 | 结果 |
|---|---|---|
| 宿主值**整单算一次** | 写在 `SUM(...)` **外面** | `Σaᵢ + D` |
| 宿主值**每个匹配行各算一次** | 写在 `SUM(...)` **里面** | `Σaᵢ + N·D` |

数学补充：乘法因子两种写法等价（`SUM(aᵢ×k) = SUM(aᵢ)×k`，分配律），**加法项不等价**，必须按意图选位置。

## 4. 功能需求

- **FR-1** `targetExpr` 内的 `b_field` 引用宿主页签 `FORMULA` 字段时，取到该字段**本行已计算出的值**（不再恒 0）。
- **FR-2** `targetExpr` 内的 `b_field` 引用宿主页签 `INPUT_*` / `BASIC_DATA` / `DATA_SOURCE` 等非公式字段时，行为**逐位不变**（仍走 `currentRowRaw`）。
- **FR-3** 字段级依赖图把 `targetExpr` 内的 `b_field` / `field` 引用计入依赖边，保证被引用字段先于引用方计算。
- **FR-4** 依赖成环时，按现有机制报「公式存在循环引用」并可定位（复用 `describeFormulaCycles`），不得静默。
- **FR-5** 前端 `computeAllFormulas` 与后端 `FormulaCalculator` 对同一份 `fields / formulas / baseRows / crossTabRows` 输出**逐位一致**。
- **FR-6** 组件公式编辑器（`CrossTabRefDrawer`）在 `targetExpr` 编辑区插入 `b_field` 且目标字段为 `FORMULA` 类型时，显示提示：该值将对每个匹配行各计入一次。
- **FR-7** 提供存量检测清单：列出全库所有「`targetExpr` 内 `b_field` 指向 FORMULA 字段」的公式，供逐条确认。

### 环链路可视化

- **FR-8** 后端环检测返回**结构化载荷**（`errorType` + `cycles[]`，含 `scope` / `nodes` / `edges`），不再只回整段文本；契约见 §5.6.3。
- **FR-9** 载荷中所有面向用户的标识一律为**名称**（组件名称 / 公式名称 / 字段名称），**不得出现 UUID 或字段 id** 于任何展示文案。
- **FR-10** 组件保存检出环 → 前端弹**抽屉**，按环分组展示：每个环一条链路（`A →  B → A`）+ 每条边「出自哪条公式 / 哪条条件规则」；多个环可分别折叠展开。
- **FR-11** 模板发布检出**页签级**环 → 同样走结构化载荷 + 抽屉，链路节点为页签（组件）名称。
- **FR-12** 渲染期（`CrossTabComponentOrder.topoOrder`）检出页签级环时，错误文案中的组件标识由 UUID 改为**组件名称**（此路径不弹抽屉，错误就地显示在卡片上）。

## 5. 数据与规则

### 5.1 取值规则（FR-1 / FR-2）

```
b_field(name) 取值 =
    currentRowRaw[name]        // 命中 → 用之（driver 行 / 编辑值 / INPUT 类 default_source）
 ?? fieldValues[name]          // 未命中 → 回落已算字段值（含 FORMULA 结果）
 ?? 0
```

判空口径沿用现有 `toNumber(...) == null` 语义：`currentRowRaw` 里**显式置空（`""`）视为命中**（尊重用户清空，与 `fillInputDefaultSourceByFieldName:1866` 的"仅键缺失才补"口径对称），不回落。

### 5.2 计算顺序如何约定（FR-3）★

**顺序不由人工配置，由系统按「谁引用谁」自动推导。** 唯一规则：**被引用者先算**。

#### 5.2.1 现行机制（三步，前后端同构，本次不改结构）

| 步 | 做什么 | 后端 | 前端 |
|---|---|---|---|
| ① 收集依赖 | 扫每条公式，找出它引用了本页签哪些 FORMULA 字段 → 建有向边 | `addExprFieldDeps` → `buildFormulaDepEdges` → `dedupeEdges` | `getFormulaDeps` |
| ② 拓扑排序 | Kahn：依赖数为 0 的先入队；算完一个，把依赖它的字段依赖数 −1，归零即入队 | `topoOrder:2249-2271` | `computeAllFormulas` 内 Kahn（`QuotationStep2.tsx:505-527`） |
| ③ 逐行求值 | 每一行**独立**按同一顺序算一遍；算完一个立刻 `fieldValues[name]=val`，后续公式即可取到 | `computeRows:873-885` | 同结构 |

即：顺序是**字段之间**的，不是行之间的；每行都重跑一遍同样的顺序。

#### 5.2.2 本次改动：只改第 ① 步的扫描范围

现状缺陷：`addExprFieldDeps:1567-1575` 与 `getFormulaDeps:407-413` **只扫顶层 token、只认 `type=="field"`**，`SUM( )` 括号内（`targetExpr`）完全不看。所以
`原材料成本 → 依赖 → 来料加工费` 这条边**从未建立**。

改为：在原有「顶层 `field`」基础上，**递归进 `cross_tab_ref.targetExpr`**，把其中 `type=="b_field"` 与 `type=="field"` 且名字命中本组件 FORMULA 字段集的 token 也计为依赖边。

- **递归逐层下探**：`targetExpr` 内还可再嵌 `cross_tab_ref`，须逐层进入
- **自引用不建边**：沿用现有 `-{n}` 处理（自引用另由环检测拦截）
- **去重必须保留**：沿用 `dedupeEdges`。`FormulaCycleDetectionTest` 头注释已锁死这条教训——依赖不去重会让 Kahn 每个前驱只减 1、入度永远归不了零 → **误报**循环引用（2026-07-28 COMP-0112 事故）

#### 5.2.3 一处改动，排序与环检测同时生效

后端 `topoOrder:2253`（求值排序）与 `cyclicFormulaNodes:1634`、`describeFormulaCycles:2152`（环检测）**共用同一个 `buildFormulaDeps`**。故只需改 `addExprFieldDeps` 一处，排序与环检测自动按同一口径，不存在「排序认这条边、检测不认」的分裂。这是本方案成立的结构性前提，实现时**不得**为二者各写一份收集逻辑。

#### 5.2.4 边界：不碰 KSUM 内层

本次放开的是**外层 `cross_tab_ref.targetExpr`** 内的 `b_field`。
**KSUM 子 token（`projectToHostKey=true`）的 inner 白名单一个字不动**——`TokenMappabilityValidator.KSUM_INNER_ALLOWED_TYPES` 明确拒 `b_field`（宿主列）/ 跨页签 `field` / `component_subtotal` / 嵌套 `cross_tab_ref`，双端镜像拒绝（见 `rule-0724/5-公式与Excel列.md §KSUM 硬约束-1`）。

依赖收集递归时**遇到 `projectToHostKey=true` 的子 token 即停止下探**（其内部按白名单本就不可能出现宿主列引用，继续下探无意义且会与硬约束语义冲突）。

#### 5.2.5 成环时的行为（两道防线）

| 防线 | 位置 | 行为 |
|---|---|---|
| **① 配置期拦截**（主） | 组件保存 `ComponentService:1032-1048` | `describeFormulaCycles` 出环路径 → 抛错，**存不进去**（本次升级为结构化 + 抽屉，见 FR-8~FR-12） |
| **② 求值期兜底** | `topoOrder:2270-2271` / 前端同位置 | 环中字段**追加到队尾**继续算，不中止整张卡片（值可能不准，但不崩） |

⚠️ **新增依赖边会让原本不成环的配置有可能成环**。实测：现网 87 个组件按新口径重建依赖图跑拓扑排序，**仍为 0 成环**（§5.3）。但未来用户可配出，故防线①必须与新口径同步生效——因 5.2.3 的共用结构，这一点自动成立，AC-5 负责验证。

#### 5.6.2 目标形态

保存成环时弹**抽屉**（`Drawer`，符合 `CLAUDE.md` UI 规范），逐个环展示链路，**全程用组件名称 + 公式名称，不出现任何 UUID / 字段 ID**：

```
检测到 2 处循环引用

环 1（组件「物料」内）
  「原材料成本」→「来料加工费」→「原材料成本」
   ├ 「原材料成本」的 公式「v2-原材料成本公式(银点类)」 中引用了 [来料加工费]
   └ 「来料加工费」的 公式「来料加工费取值公式」 中引用了 [原材料成本]

环 2（跨页签）
  页签「产品」→ 页签「物料」→ 页签「产品」
   ├ 页签「产品」的 公式「管理费」 中引用了 页签「物料」的 [材料成本]
   └ 页签「物料」的 公式「v2-原材料成本公式(银点类)」 中引用了 页签「产品」的 [税率]
```

#### 5.6.3 结构化载荷契约

**照抄既有先例，不动 `BusinessException` 基类、不改响应体格式。** `GlobalExceptionMapper:24-34` 已有两个同型实现——`RowKeyConflictException` 回 `Map.of("conflicts", …)`、`TreeConflictException` 回 `Map.of("conflictTabs", …)`，均走 `ApiResponse.error(code, message, data)`。本次新增 `FormulaCycleException extends BusinessException`（放 `common/exception/`，因 component 与 template 两侧共用），Mapper 加一个 `instanceof` 分支即可。

响应体（`ApiResponse` 固定三段 `code` / `message` / `data`）：

```json
{
  "code": 400,
  "message": "公式存在循环引用（2 处）",
  "data": {
    "errorType": "FORMULA_CYCLE",
    "cycles": [
      {
        "scope": "FIELD",
```
