### 二、Findings（按严重度排序）

#### F-1 · [阻塞] 核价侧 / 冻结单存在第二条上下文通路，完全绕过 `QuotePendingScope`——AC-10、AC-12、B-16 守的都是错的不变量

- **事实**：`applyPendingRewrite` 的门槛读 `SqlViewRuntimeContext.get().quotationId`（`SqlViewExecutor.java:736`），**不读** `QuotePendingScope`。而该 ThreadLocal 有第二个写入点：`FormulaEvaluateResource.java:122` `prevCtx = SqlViewRuntimeContext.setNestedTemplate(effectiveTemplateId, req.quotationId, req.quotationStatus);` —— **quotationId 与 status 都来自请求体**。
  前端确实在发：`useLinkedExcelRows.ts:289-290` `quotationId: quotationId || null, quotationStatus: quotationStatus || null`。
  而 `QuotationStep2.tsx:4569-4577` 的**核价侧** `<LinkedExcelView ... quotationId={quotationId} side="COSTING" />` —— 传了 `quotationId`，**没传 `quotationStatus`** ⇒ 后端收到 `status=null` ⇒ `isQuotationFrozen()` 返回 false。
- **文档怎么说的**：`需求文档.md` §1.4 表格「可见域 ThreadLocal（内建冻结判定，**核价侧靠「一律不调 `open()`」隔离** + 白名单单测）」；AC-10「机制保障 = 核价侧一律不调 `QuotePendingScope.open()`」；AC-12「机制 = `QuotePendingScope.open` 对冻结态存 null ⇒ 改写不生效」；`backtask.md` B-16「断言核价侧调用链上**零处**调 `QuotePendingScope.open()`」。
- **后果**：① 核价单 Excel 视图的公式求值请求会让 `DsRecordRewriter` 在核价上下文里触发 —— AC-10「逐字节不变」会被打破，而 B-16 的单测（断言零处 `open()`）**永远是绿的**，测不到这条；② `quotationStatus` 由客户端提供且核价侧恒传 null，**冻结判定被结构性绕过** —— 一张 SUBMITTED/APPROVED 的单，只要走这条通路就会被当成非冻结改写，AC-12 的机制保障在这条路径上不成立。今天这两点都无害（见 F-4 的"改写当前零覆盖"），**A 把 13 张 ds 表接进改写器的那一刻它们同时生效**。
- **建议**：门槛与隔离口径必须统一到一处（要么改写器也读 `QuotePendingScope`，要么 `FormulaEvaluateResource` 走同一个 `open()`），并把 B-16 的断言从「零处调 open()」改成「核价上下文下 `DsRecordRewriter` 零次触发」的运行时断言。

### 四、结论
