## ① 现象

用户配好模板后导入建单 `QT-20260914-0865`，打开编辑页：

```
产品      1 行  ✅
其他费用  4 行  ✅
BOM       1 行  ❌ 只有根行 S0001，全部业务列空白
材质元素  0 行  ❌ 整个页签空
```

截图：`inbox/shot_20260914_013201.png`

⇒ **`AC-3`（本单可见）不成立。** 数据进了 `_record` 却读不回来 —— 这是功能的核心承诺。

---

## ② 根因（已定位，实证）

**`BomTreeRenderService.queryRecursive` 是 BOM 树骨架 SQL 的唯一执行点，它完全绕过 `DsRecordRewriter`。**

```java
try (Connection conn = dataSource.getConnection()) {        // ← 自己开连接
    UUID pendingQuotationId = resolvePendingOwner();
    if (pendingQuotationId != null) {
        rw = QuotePendingRewriter.rewrite(expanded, conn, false);  // ← 只调 V6 那套
        withPending = rw.sql;
    }
    ...
    try (PreparedStatement ps = conn.prepareStatement(sql)) {      // ← 裸 JDBC
```

**三条事实**：

| # | 事实 |
|---|---|
| ① | 它自己开 `dataSource.getConnection()` + 裸 `PreparedStatement`，**不经过 `SqlViewExecutor`** |
| ② | 而 `DsRecordRewriter` 的唯一挂接点就是 `SqlViewExecutor.applyPendingRewrite`（`B-12` 挂的） |
| ③ | 它只调 `QuotePendingRewriter`（V6 时代管 `pending_quotation_id` 的那套），**没有 `DsRecordRewriter` 的任何引用** |

⇒ 递归 CTE 永远查主表 ⇒ 主表 0 行 ⇒ 从种子一步都展不开 ⇒ **闭包只剩根料号本身**。

**这完整解释了三个现象**：BOM 只剩根行（闭包=种子）· 材质元素 0 行（它按闭包里的料号取数，闭包里没有子件）· 其他费用正常（平铺取数，走 `SqlViewExecutor`，改写生效）。

### 🔑 反证：改写器本身是通的

| 页签 | 查的表 | 主表行数 | `_record` 本单 | 渲染 |
|---|---|---|---|---|
| 其他费用 | `ds_quote_finished_other_fee` | **0** | 14 | **4 行 ✅** |
| BOM | `ds_quote_material_bom` | **0** | 17 | 1 行（只有根） |
| 材质元素 | `ds_quote_element_bom` | **0** | 13 | **0 行** |

「其他费用」主表 0 行却渲出 4 行 ⇒ 数据只可能来自 `_record` ⇒ **`DsRecordRewriter` 工作正常，缺的是树那条路没接**。

`BomTreeRenderService` 就是其中之一，**而且是最要命的那个**（BOM 树是报价单主体）。当时没逐个证伪，被用户用真实流程撞出来。

🚨 **主线在诊断过程中还犯了一次同型错误**：先据「后端日志里没有改写器的记录」推断「改写器没触发」——
实查 `DsRecordRewriter` 类里**日志语句数 = 0**，它根本不打日志 ⇒ 那个推论**无效**（结论碰巧沾边，推理过程是废的）。

## ④ 🔬 关键可行性已实测（不是推演）

**递归 CTE 的表源能不能换成 UNION 子查询？** —— PostgreSQL 允许。实跑（`cpq_db_0724`，单 `87de9746`）：

```sql
WITH RECURSIVE bom AS (
  SELECT 'S0001'::text AS no, NULL::text AS parent, 0 AS lvl
  UNION ALL
  SELECT b.input_material_no, b.material_no, bom.lvl+1
  FROM ( SELECT r.material_no, r.input_material_no FROM ds_quote_material_bom_record r
          WHERE r.quotation_id = '<本单>'
         UNION ALL
         SELECT m.material_no, m.input_material_no FROM ds_quote_material_bom m
          WHERE NOT EXISTS (...) ) b
  JOIN bom ON b.material_no = bom.no WHERE bom.lvl < 5 )
SELECT * FROM bom;
```

输出：

```
层0  S0001
层1  S0002 ← S0001
层1  S0003 ← S0001
层2  00081 ← S0002      ← 正是「材质元素」页签缺的那些料号
```

⇒ **修法在数据库层面可行**，剩下的是在哪一层接的问题。

## ⑤ 闸门 A0 裁决（2026-09-14 用户裁决）

✅ **甲：在 `queryRecursive` 里并排加一个 `DsRecordRewriter.rewrite()` 调用。**

**三个候选与否决理由**：

| | 做法 | 裁决 |
|---|---|---|
| **甲** | `queryRecursive` 并排加一个 `DsRecordRewriter.rewrite()` —— 它旁边已经有一个同形态的 `QuotePendingRewriter.rewrite(expanded, conn, false)` | ✅ **采纳** |
| 乙 | 改 `costing_bom_tree_config.sql_template`（零 Java 改动） | 🚫 否决：那是**配置不是代码**，改了影响所有走该骨架的页签；而且配置**从未进过迁移**（UI 建的）⇒ 别的库不同步、上线要手工搬。本项目为「UI 配置不进迁移」吃过亏（空库建不起来的根因就是它） |
| 丙 | 树递归整体改走 `SqlViewExecutor` | 🚫 本期否决：`queryRecursive` 有 TREE_PARAM 正则 / 数组参数 / 注释屏蔽等大量特殊处理，搬过去等于重写 ⇒ **修缺陷与重构混在一起，出问题分不清**。<br>📌 **价值主线也认**，建议单独立项（登 BACKLOG） |

**采纳甲的三条理由**：① 旁边**已有一个一模一样的改写调用**，是在既有形态上加平行线、不是发明新东西；② 改动收在一个方法里，易验易回退；③ 乙把 Java 的责任推给一份不会跟着代码走的配置。

### 🚦 实现方必须自己实测的两处（主线未验）

1. **`DsRecordRewriter.enabled(owner, conn)` 要的 `SqlViewRuntimeContext.Snapshot` 从哪来** —— `queryRecursive` 里只有 `QuotePendingScope.pendingOwner()`，没有 `SqlViewRuntimeContext`。是取当前上下文、还是自己构造一个？🚫 不许猜。
2. **`:dsq` 怎么绑进 `TREE_PARAM` 机制** —— 那段代码把 `:xxx` 占位符正则替换成 `?` 并按 `order` 顺序绑值，`:pq` 是特判的（`if ("pq".equals(name))`）。`:dsq` 需要同样的特判。
   🚨 **漏绑的后果是静默的**：`DsRecordRewriter` 的 javadoc 明写「注入了 `:dsq` 却没绑定值 ⇒ 降级成字面量 NULL ⇒ `r.quotation_id = NULL` 恒 false ⇒ 本单 `_record` 整个读不到，**而且不报错**」。
