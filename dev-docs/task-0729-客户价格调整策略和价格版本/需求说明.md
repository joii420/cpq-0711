## 2. 需求背景与目标 ⭐（立项原文）

- **要解决什么问题 / 痛点**：
  - 在报价单已经创建并且审核过后, 因为元素材料价格波动,导致客户的报价单要进行价格调整
- 在调整后还要和核价结果进行比对,确认毛利还是有效的
- **本次要达成的目标**：
  - 可以根据客户进行制定价格调整策略
- 价格调整策略可以选择客户指定的客户料号/所有料号
  - 价格调整策略可以选择客户的调整周期,  每天/每周几/每月几号/每月第几周
  - 价格调整策略可以选择客户的需要调整的元素, 只有这些元素价格浮动需要记录元素价格历史
  - 系统根据客户策略自动计算需要调整的元素价格,记录为元素版本,为待审核状态, 需要财务审核后才生效,并且可以在报价单中切换价格版本
  - 财务审核后需要有一个影响的报价单列表,可以查看审核最新元素报价后,调整后价格是否还符合公司毛利,需要与核价进行比对
  - 财务审核后可以在勾选报价单列表中的报价单进行一键更新价格调整后的最新报价,报价单需要带入最新的元素价格进行重算,并且保留切换历史价格版本的展示功能
  - 报价单中增加历史版本的总报价差异矩阵
- **不做什么（明确边界）**：见 §11.12 明确不做清单

## 4. 功能详述 ⭐

### 4.1 用户场景 / 操作流程

```
① 财务配置客户调价策略（周期 + 执行时刻 + 料号范围 + 参与元素 + 毛利预警线）
   ↓
② 系统到点自动生成「元素价格版本」（调用 task-0722 取价策略算价，全量快照，待处理）
   ↓
③ 系统预算：受影响料号按新价预演重算 → 与该料号核价成本比毛利
   ↓
④ 财务在「价格调整审核」页逐料号审核
   判断依据 = 该料号【最近一张报价单】的调整后报价 vs 该料号核价成本
   ↓
⑤ 通过 → 该料号价格版本指针推进 → 所有活单中该料号的产品卡片按新价重算
   驳回 → 该料号停在原版本，报价保持原样
   ↓
⑥ 报价单内可查看价格版本轨迹、切换历史版本【只读预览】
```

## 11.1 总体模型

- **版本载体**：系统按客户策略周期生成**元素价格版本**（`V` 版本），是一批元素新价的快照，与料号无关。
- **审核与升版单位**：**料号**。每个「客户 × 料号」持有一个**版本指针**，指向它当前采用的元素价格版本。
- **判断依据**：该料号**最近一张报价单**上，按该客户配置的**比对列**算出的报价侧 vs 核价侧差异（默认列 = 产品总价，毛利率由它派生）；任一列跌破阈值即预警。
- **生效方式**：料号通过 → 指针推进到本期版本 → 所有活单中该料号的**报价侧与核价侧卡片都重走公式计算**；驳回 → 指针不动，两侧均保持原样。
- **双侧同源**：版本内同时快照「客户策略价」（报价侧）与「`_GLOBAL_` 成本价」（核价侧）两份元素价，两侧口径各自独立但同源于一个版本（裁决 41）。

### 11.1.1 🔒 明示接受的取舍：单内同一元素可能有多个价

料号级升版意味着：料号 A 已升版（Ag = 5,820）、料号 B 被驳回（Ag = 5,450）时，**同一张报价单里 Ag 会有两个价**。

- 这是料号级审核的**固有结果**，业务上成立：B 的调价被否，它对客户的报价就该维持原样。
- **不是数据不一致**，不得作为 bug 处理。
- 可查证据：报价单「价格版本」抽屉的**料号级价格版本表**逐行显示每个料号当前处在哪一版（屏 7）。
- 澄清过程中业务方曾提出"同一元素不应有多个报价"的关切（§11.14 第二次修正），最终裁决为料号级后本条成为必然后果，特此显式备案。

- 右侧 10 列 = 该客户**最近 10 个价格版本**中该元素的单价（大字）+ 较上一版涨跌幅（小字，涨红跌绿）。

### 11.3.1 版本号规则（补4）

- 格式：`V26080501` = 2026-08-05 当日第 1 版。

- 报价单内的报价价格版本**同规则、换前缀 `R`**（如 `R26080501`）。

### 11.3.2 版本明细内容

- 存该策略约定的**全部元素**当期价（完整快照），逐元素标注较上一版的涨跌。
- 无价元素（取价策略算不出值）在明细中标「无价」，**不可审、不占审核动作**，等价格补齐由下一版重新纳入。

### 11.5.1 比对与毛利计算式（裁决 34 / 43 / 44）

**默认列（产品总价）**：
```
差异         = 调整后报价侧产品卡片总计 − 调整后核价侧产品卡片总计
料号毛利率   = 差异 ÷ 调整后报价侧产品卡片总计
```
- 报价侧总计：从 `quote_card_values` 解析 SUBTOTAL 页签 `subtotal`（复用 `ComparisonViewService` 算法）。
- 核价侧总计：从 `costing_card_values` 同款解析。**同客户同料号核价成本一致**（V6 基础数据按 customer × material 共享），故同一料号的多张单核价侧数值相同。

**自定义列（`kind=TAB_PAIR`）**：
```
差异 = 报价侧(quoteComponentId, quoteMetric) − 核价侧(costingComponentId, costingMetric)
```
- 指标取 `isSubtotal` 字段值或 `__TAB_TOTAL__`（页签合计），与 task-0717 完全同源。
- 着色：`差异 < 0` → 红；`0 ≤ 差异 < threshold` → 橙；否则正常。
- **整行标红条件**：任一列为红（裁决 44）。

### 11.5.2 料号审核抽屉三段结构（屏 4）

对应财务的思考顺序，缺一不可：

1. **为什么变** —— 该料号用到的元素价变动：元素 / 命中规则 / 上版价 / 本版价 / 涨跌 / **该料号用量** / **对单价影响**。合计值须与"调整后报价 − 现报价"对得上（财务复核算式可信度的自检位）。
2. **能不能接受** —— 逐单明细：最近一张单挂 `判断依据` 标签，其余仅作参考。
3. **下钻** —— 每张单直达 task-0717 比对视图；本抽屉**不重复实现**页签级比对。

**（1）三层呈现，各司其职**

| 位置 | 呈现 | 理由 |
|------|------|------|
| 屏 3 列表固定列 | 只出**产品总价**口径（报价侧现→调整后 / 核价侧现→调整后 / 差异 / 毛利率） | 跨客户，各家比对列数与列名都不同，出不了统一表头（裁决 43） |
| 屏 3「比对状态」列 | 汇总标记 `✓ N 列全通过` / `🔴N 🟠M / X列` | 统一列，不随客户配置变化 |
| 屏 4 抽屉「二、比对结果」 | 按该客户配置**逐列完整展开** | **比对项唯一完整体现处** |

**（2）🚨 行标红判定口径（强制）**

```
整行标红  ⟺  该料号存在任一比对列 status = RED
          ⟺  breached_count > 0
```

**不是** `产品总价差异 < 0`。两者**不等价**：产品总价正常（如差异 +4.05 / 毛利率 9.2%）而自定义比对列已卖穿的料号，**整行同样标红**。原型屏 3 第 5 行 `10120240` 镀银铜带即为此样例，**前端实现与验收必须覆盖它**，否则裁决 44「任一列跌破即整行标红」形同虚设。

**（3）比对状态标记格式**

红与橙**分开计数**，不得合并成旧写法「M/N 列跌破」（该写法把"已卖穿"与"没亏但未达预期"混为一谈，而二者在裁决 44 里处置不同）：

| 标记 | 含义 | 整行标红 |
|------|------|---------|
| `✓ N 列全通过` | 全部列 status = NORMAL | 否 |
| `🟠M / X列` | 有橙无红（`0 ≤ 差异 < 阈值`，未达预期但未亏） | **否** |
| `🔴N 🟠M / X列` | 存在红（`差异 < 0`，已卖穿成本） | **是** |

**（4）配置入口唯一性**

比对列配置的**唯一写入口** = 屏 1「定价策略 → 价格调整策略 Tab → 比对列配置」。屏 4 审核抽屉内**只读展示，不提供修改入口**。

> 理由：改比对列 = 改审核的判断标准，且按（5）会触发预算重算。若允许在审核抽屉里顺手改，财务正在看的这一屏数据会**当场变化**，审核依据不可追溯。

**（5）预算落库与配置变更重算**

- 比对列差异值在**预算阶段逐列落库**（`material_price_review_column`，见 §11.10）；**列表与抽屉都是纯读库，不实时算**。
- 理由：① 列表标红需要"任一列是否为红"，实时算 = 跨客户 N 行 × 各自 M 列的 N+1；② 若列表读汇总、抽屉实时算，会出现「列表 `🔴1 🟠1`、抽屉算出 `🔴1`」的自相矛盾，直接破坏裁决 41「预算与实际逐位一致、可复现」。
- **比对列配置保存后**：立即重算该客户全部 **`待处理`** 料号的预算并刷新待办池标色；**`已通过` / `已驳回` 的料号不重算** —— 它们的审核依据必须保持可追溯。

**（6）待办池的抽屉入口 = 料号链接，不是整行点击**

> 需求方曾提出"**点击行**弹出抽屉"。**经评估不采纳**，按 `docs/列表操作规范.md` §4「主入口列规则」实现。

| 交互 | 行为 |
|------|------|
| 点**料号链接**（行内唯一主入口） | 打开料号审核抽屉；实现须 `e.stopPropagation()` |
| 点行内**其他位置** | **切换选中**，不打开抽屉 |

**理由**：屏 3 是 `SelectableTable`，工具栏承载「通过并升版（N）」「驳回」等**批量动作**，行点击必须保留给多选语义 —— 若整行点击改为打开抽屉，批量审核将无法操作。与列表规范「主入口链接点击后能跳转/打开 Drawer，**不会同时切换选中**」一致。

### 11.6.1 执行单位与隔离纪律（强制）

- 执行单位 = 「**报价单 × 本次升版料号**」。
- **硬约束**：**只对被升版的料号行执行重算与 `recompute`，不碰其他行** —— 哪怕输入没变，也**不做**"整单重算一遍"，避免引擎兜底路径造成静默漂移。
- 单据级聚合（`total_amount` / 税额）必然随之变化，属预期。

### 11.6.2 `R` 版本合并规则（裁决 30）

- `R` 版本语义 = **这张单基于某个元素价版本的快照**，与 `V` 版本**一一对应**，轨迹表**一期一行**。
- 同一 `V` 版内多次料号升版 → 合并进同一 `R` 版，只更新「最后更新」时间并向「已升版料号」追加。
- **性能无差异**：每次只重算被通过料号的那一个产品卡片，逐个通过 N 次 = 一次批量通过 N 个，卡片重算总量相同。

### 11.6.3 三种非成功态（裁决 19 / 32）

| 态 | 含义 | 处置 |
|----|------|------|
| **失败** | 数据问题（如行键冲突） | 需人工修数据后重试 |
| **冲突** | 重算期间该单被改动（`updated_at` 变化） | 直接重试即可 |
| 等待 / 进行中 | 排队或执行中 | — |

三者都可**单独重试**，不必整批重来。

### 11.8.1 两侧口径的关系（重要，勿混淆）

| | 报价侧 | 核价侧 |
|---|---|---|
| 取价策略 | 该客户的 `element_price_strategy` | `_GLOBAL_` 的 `element_price_strategy` |

| 来源 | **同一个版本快照的两个字段** | **同上** |

### 11.10.6 存量报价单迁移

## 11.11 验收要点（可测口径）

1. **策略配置**：周期四种形态（每天 / 每周 / 每月某日 / 每月第 N 周+星期几）+ 执行时刻均可配可回读；「每月 31 号」在小月顺延至月末；「第 5 周」不足时按当月最后一个该星期几执行。
2. **料号矩阵**：四个筛选框可组合模糊匹配；勾选跨页保留；客户料号为空的行显示「—」且**可勾**。
3. **元素矩阵**：右侧列 = 最近 10 个版本价格 + 涨跌幅；`—` 与 `无价` 语义可区分；历史不足 10 版按实有出列；**一次查询完成**（F12 Network 确认无 N+1）。
4. **版本生成（定时）**：到周期点 + 执行时刻自动生成待处理版本；服务重启错过时刻能在下次扫描补跑；同一周期点**只生成一次**。
5. **版本生成（手动）**：「立即生成一次」与定时走**完全相同**代码路径；同日再次生成流水递增（`…01` → `…02`）。
6. **期期起版**：本期价格全无变动时**仍生成版本**（裁决 7），但 0 变动料号**不进待办池**（裁决 39）。
7. **版本交替**：新版生成时上一版整体作废、未处理料号失效；**已通过并执行的更新不回滚**。
8. **待办池**：一料号一行，核心列「当前版本 → 目标版本」正确；驳回料号显示"未升版"停在原版。
9. **判断依据**：行上数字取该料号**最近建单日**的活单（含草稿），标出单号与日期；抽屉里其余单标为"仅作参考"。
10. **毛利口径**：料号毛利与 task-0717 比对视图同一料号的 `productTotal` 口径**逐位一致**（可用同一张单交叉验证）。
11. **预警**：料号调整后毛利率跌破客户预警线（默认 0）整行标红；确认弹窗二次提示；**不阻断**通过。
12. **只读审核**：审核界面无任何可改价控件；驳回必填原因；驳回版本保留可查。
13. **通过确认**：弹窗列出 N 个料号 + 版本推进路径 + M 张单按状态分组 + 跌破预警线提示。
14. **隔离性（核心 · 必须双向断言）**：通过料号 A 后 —— ① **正向**：`A.snapshot_rows` 里的元素单价**已变**且等于本版价、`A.li.subtotal` 与行金额**已变**；② **反向**：料号 B 的 `quote_card_values` / `snapshot_rows` / `line_total_amount` / `discountRateApplied` **逐字节不变**；③ 仅 `quotation.total_amount` 及税额随之变化。
    > ⚠️ **只写反向断言是无效测试**：已核实 `CardSnapshotService` **从不写 `snapshot_rows`**，所以"B 的 `snapshot_rows` 不变"天然成立 —— 即使 A 的价格根本没更新，测试也会绿。必须补正向对照（§11.15.2.1）。真正需要盯的 `snapshot_rows` 写路径是 `ConfigureSnapshotService`（`:1373/:1432/:1523`）与 `QuotationTreeService`（`:297`）。
15. **升版原子性**：料号升版后其**全部相关元素**均切到本期价，无"部分元素新价、部分旧价"的中间态；实际重算结果与审核页预算值**逐位一致**。
16. **冲突保护**：更新期间人为改动该单 → 该单标记为**冲突**、未写回、可重试；销售改动**不丢失**。
    > ⚠️ 测试必须覆盖**不走 `saveDraft` 的编辑路径**（单元格编辑 `quote-card-edit` / 删恢复 driver 行 / BOM 树增删叶 / 选配加产品）—— 这些路径**不 bump `quotation.updated_at`**，正是裁决 32 从"乐观时间戳"改判为**行级 `@Version`**（F1）的原因。任何用 `quotation.updated_at` 做断言的测试都是**假绿**。
17. **`R` 版本合并**：同一 `V` 版内分两次通过两个料号 → 该单**只有一个** `R` 版本，「最后更新」时间刷新、「已升版料号」累积为两个。
18. **切版本预览**：切到历史版为**只读**（输入框 / 保存 / 提交 / 导出全部禁用），退出预览恢复；单据当前值**未被修改**。
19. **料号级版本表**：单内每个料号显示各自当前版本；被驳回料号显示停留版本；未参与调价料号显示「未参与调价」。
20. **权限**：`SALES_REP` / `SALES_MANAGER` 登录看不到「价格调整审核」菜单，报价单内可见版本轨迹但只读，无通过 / 驳回 / 触发更新入口。
21. **核价侧联动（核心）**：料号升版后 —— 该料号的 `costing_card_values` **按本版 `_GLOBAL_` 价重算**且数值变化；**核价单 `costing_order` 的 frozen 快照逐字节不变**（裁决 42，须逐字段断言）。
22. **双侧同源可复现**：审核页显示的「调整后核价」与通过后实际重算出的核价卡片值**逐位一致**（证明预算与执行同源于一个版本快照，裁决 41）。
23. **比对列可配置**：给某客户加一列「投料·材料小计 ↔ 材料成本·页签合计」并设阈值 2.00 → 该客户所有待办料号的抽屉都出现该列；差异 <0 显红、0≤差异<2.00 显橙、否则正常；**任一列跌破 → 列表整行标红**（裁决 43 / 44）。
24. **配置隔离**：客户 A 的比对列配置改动**不影响**客户 B；新客户默认只有「产品总价」一列且该列不可删除。
25. **行标红判定（核心 · §11.5.3(2)(3)）**：构造一个料号 —— 产品总价差异**为正**（如 +4.05、毛利率 9.2%）、但某自定义比对列 `差异 < 0` → 待办池**整行必须标红**，「比对状态」显示 `🔴1 🟠1 / 3列`。**反向用例**：全部列均为橙（`0 ≤ 差异 < 阈值`）→ **不得标红**，标记显示 `🟠M / X列`。（对应原型屏 3 第 5 行 `10120240` 镀银铜带；此条专防实现被写成 `产品总价差异 < 0 ? 标红 : 不标红`）
26. **比对列配置变更重算（§11.5.3(4)(5)）**：改动某客户比对列配置并保存 → 该客户全部 `待处理` 料号的预算与待办池标色**立即刷新**；同版本内 `已通过` / `已驳回` 料号的预算明细**逐字节不变**。屏 4 审核抽屉内**无任何可修改比对列的控件**（只读展示）。
27. **列表与抽屉逐位一致（§11.5.3(5)）**：任取一料号，屏 3 汇总标记的红/橙计数与屏 4 抽屉逐列明细的 `status` 分布**完全一致**（两处同读 `material_price_review_column`，均不实时算）。
28. 🔴 **升版不被 saveDraft 回滚（核心 · §11.15.2.1）**：料号 A 升版后 → ① `A` 的 `snapshot_rows` 里元素单价**已等于本版价**；② **再对该单执行一次 `saveDraft`，然后重新打开** → 价格**仍是新价**。
    > 此条专防"只重算 `quote_card_values` 不写 `snapshot_rows`"的实现 —— 那样升版当时看着对，销售存一次草稿就静默退回旧价，是本期最隐蔽的失败模式。
29. 🔴 **手工值按列清除（§11.15.2.2）**：销售在某行手改过**元素单价**与**毛重**两个字段 → 升版后 ① 该行**单价 = 本版价**（手改值被覆盖，兑现裁决 37）；② 该行**毛重仍是手改值**（未被误伤）。
30. **导出走新价（§11.15.2.4）**：料号 A 升版后**不打开报价单**、直接导出 Excel → 导出文件中该料号的元素单价与金额**均为新价**（验证 `quote_excel_values` 已置 NULL 且 fallback 重算生效）。
31. 🔴 **子件吃版本（§11.15.4.2）**：对使用 **BOM 闭包形态** `mc_view` 的客户（如罗克韦尔），父件料号升版后 → **闭包展开出的子件行**其元素单价**同样切到本版价**，无"父件新价、子件旧价"的中间态（守裁决 29 升版原子性）。
    > 此条专防 JOIN 键误写成 `cep.material_no = ebi.material_no` —— 那样子件行 JOIN 不中，失败是**静默**的。

## 11.15 技术方案（2026-07-29 定稿 · 独立架构评审后收敛）

> **本节地位**：需求澄清完成后经**独立架构评审**（无澄清会上下文的架构师，逐条读代码核实），查出 **7 条阻断级技术缺口** —— 核心裁决 **12 / 32 / 37 / 41** 在现有架构上**落不了地**。本节是针对这些缺口的技术方案。
> **与业务裁决的关系**：本节与 §11.1~§11.9 同为权威口径。冲突时**以本节为准** —— 因为它修正的正是那些技术上站不住脚的裁决，逐条在 §11.15.7 列明，不是随意推翻。

### 11.15.1 核心架构：双通道分离

**问题**：审核页要显示"按新版价重算后的报价"（预算），执行时又要真的按新版价重算。若两者取价路径不同，必然分岔 —— 这是裁决 41「预算与实际逐位一致、可复现」的最大威胁。

**评审的建议**是给取价函数加 `override_version_id` 参数、并在 `SqlViewExecutor` 注入 `:priceVersionId`。**本方案不采纳** —— 那会把"版本上下文"以 ThreadLocal 形式渗进整条渲染链路，成为新的漂移源（参照 AP-37 的 cache 维度教训）。

**改为双通道分离**：

```
通道 A · 新建单的初次取价
  mc_view ──JOIN──► f_material_element_price(customer_no, base_date, side)
                      ├─ 按 (客户,料号) 查指针 → 有 → 取该版价
                      └─ 指针为空 → 回落 task-0722 实时算
  ★ 只服务"新单第一次取价"；不需要 version override 参数

通道 B · 升版执行 + 审核预算            ← 同一段代码，只差最后落不落库
  element_price_version_item ──直接读──► 字段级写回 snapshot_rows → 重算
  ★ 完全不走视图 / 不走取价函数 / 不需要任何版本入参
```

**收益（三条，都是结构性的）**：

| 收益 | 说明 |
|------|------|
| **裁决 41 从"靠纪律"变成"结构上不可能违反"** | 预算与执行是同一段代码、同一个数据源（版本明细），只差 `dryRun` 布尔。不存在"一端实时算、一端版本价"的分岔可能 |
| **消除评审缺口 A4** | 预算不再需要"用目标版本价预演"的注入通道 —— 它本来就直接读版本明细 |
| **消除评审缺口 A6 的一半** | 取价函数不需要 `override_version_id`；核价侧也不需要传 `:customerCode` 去解析指针（见 §11.15.4） |

### 11.15.2 通道 B · 升版重算通道（8 步）

单一入口 `MaterialVersionUpgradeService`，**执行单位 =「报价单 × line item」**（与 §11.6.1 一致）：

| # | 步骤 | 内容 | 解决的缺口 |
|---|------|------|-----------|
| **S1** | 读版本价 | 从 `element_price_version_item` 读该版本的**报价侧价 + 核价侧(`_GLOBAL_`)价** → `Map<elementCode, {quotePrice, costingPrice, currency}>`。**不走视图、不走函数** —— 版本明细就是权威快照 | 裁决 41 |
| **S2** | 定位价格字段 | 按 §11.15.3 的推导算法，找出该组件的**价格字段名 + 货币字段名** | — |
| **S3** | **字段级写回 `snapshot_rows`** | 按 rowKey 对齐，**只改价格/货币两个键**；`driverRow` 与**行集合保持不动**（不增行、不删行、不换行） | **A1**（最致命） |
| **S4** | 清该字段的手工值 | 删除 `row_data` / `editRows` 里**价格字段这一个键**；其余手改字段（毛重、损耗率等）**原样保留** | **A2** |
| **S5** | 重算卡片 | 走既有 `buildCardValues`，报价侧 + 核价侧都算 | 裁决 41 |
| **S6** | 写回行金额 | 从新 `quoteCardValues` 提取报价侧 SUBTOTAL → 写 `li.subtotal` → `LineDiscountService.recompute(li)` | **A7** |
| **S7** | 失效导出快照 | `li.quoteExcelValues = null` | **B1** |
| **S8** | 聚合单据 | `quotation.total_amount` + 税额 | 裁决 12 |

**`dryRun=true`** 时执行 S1~S6 全在内存、返回 SUBTOTAL 与各比对列值、**不写库** → **这就是审核页的预算**（§11.5.3(5) 落库的那些值由它算出）。

#### 11.15.2.1 S3 为什么是关键（缺口 A1 详解）

**已核实的架构事实**：
- 元素单价是 `INPUT_NUMBER` + `basic_data_path` → 走 `basicDataValues` 通道 → **冻结在 `quotation_line_component_data.snapshot_rows`**（`V269__quotation_line_component_snapshot.sql:8-10`）
- `CardSnapshotService.buildCardValues` 的 baseRows **来自 `snapshot_rows`，不重跑 driver expand**（`CardSnapshotService.java:1078-1113`）
- **`CardSnapshotService` 全类只读 `snapshot_rows`，从不写**。全后端写它的只有 `ConfigureSnapshotService`（`:1373/:1432/:1523`）与 `QuotationTreeService`（`:297`），语义都是"加产品 / 树增删"，**没有"按新价刷新"的入口**

**若不做 S3 的两种失败**：
1. 走 `ensureCardValues` / `snapshotLineValues` 重算 → 读的还是旧 `snapshot_rows` → **价格纹丝不动**，且不报错
2. 走 `refreshQuoteCardValues(li, force=true)`（唯一会实时重 expand 的路径）→ 价格能更新，但**它不回写 `snapshot_rows`**。之后任何一次 `saveDraft`（`QuotationService.java:461-462` 置 `quoteCardValues=null`）+ `ensureCardValues` 都会从旧 `snapshot_rows` 重建 → **新价被静默回滚**

第 2 种最恶劣：升版当时是对的，销售存一次草稿就退回去了。**故 §11.6.1 隔离纪律追加一条**：

> 🔒 **升版必须写 `snapshot_rows`**。只重算 `quote_card_values` 不写 `snapshot_rows` = 新价会被下一次 saveDraft 静默回滚。验收见 #28。

#### 11.15.2.2 S4 为什么必须做（缺口 A2 详解）

裁决 37 称"手工值直接覆盖"是"系统本就不记录哪些值被手改过"的自然结果 —— **事实相反**：

- 有效行合成口径 `effectiveRow = driverRow ∪ basicDataValues ∪ formulaResults ∪ editRows`，**editRows（用户手改）优先级最高**（`CardEffectiveRows.java:13-15`）
- `refreshQuoteCardValues` 第 2.5 步 `mergeRowDataInputsIntoEdits` 还会**主动把 `row_data` 里 autosave 的 INPUT 值（含单价）合并进 editRows**（`CardSnapshotService.java:2168-2176`）

即：系统**不但记录手改，还让它赢**。不做 S4 的话，销售手改过单价的行升版后**仍用手改值**，裁决 37 完全落空，而 §11.13 的对策"完成通知提示复核"是在补偿一个**不会发生**的行为。

**S4 采用"按列清除"而非"整行清空"** —— 靠 §11.15.3 精确定位到价格字段，只删那一个键，毛重/损耗率等其他手改字段保留。这是三种改法里唯一既兑现裁决 37、又不误伤的。

#### 11.15.2.3 S6 的前置风险（缺口 A7）

`LineDiscountService.recompute(li)` 的 S0 **优先采信 `li.subtotal`**（`:66-75`），引擎重算只是缺失时的兜底；而全后端写 `li.subtotal` 的 3 处（`QuotationService.java:420 / :2135 / :1492`）**全是搬运前端 DTO 或版本克隆，无任何后端重算**。故不做 S6，升版改了卡片值但**行金额与单据总额都不会变**。

⚠️ **已知两处口径差，开工前必须对拍**（见 §11.15.9 前置验证 P3）：
1. 后端 `assembleTabsWithFormulaResults` 求 SUBTOTAL 时 `RowContext.productAttributes` 为空 → `product_attribute` token 恒取 0（`CardSnapshotService.java:1685-1686` vs 前端 `QuotationStep2.tsx:1302-1307`）
2. 后端不登记 `${key}#__amount_total__` 哨兵键 → 含 `[页签(总计)]` token 的公式两端不等值

**对拍不通过就不做 S6**，否则升版会把所有行金额改错。现成工具 `CostingSubtotalUtil.extractUnitSubtotal(String)` 实现里无核价专属逻辑，喂 `quoteCardValues` 即可，只需提可见性 / 改中性命名，**不要新写一份**。

#### 11.15.2.4 S7 的现成解（缺口 B1）

升版后 `quote_excel_values` 不刷新的话，**导出给客户的 Excel 仍是旧价** —— 而"把新价发给客户"正是本期的目的。

**已核实**：`ExcelViewService.exportExcelView`（`:782-786`）已有服务端 fallback —— `quoteExcelValues` 快照为空时**整行走 `getExcelView` 重算**。故 **S7 只需置 NULL**，无需新增重算代码，也无需要求"先打开一次报价单"。
> ⚠️ 实现时需确认 fallback 的取数源是 `quote_card_values`（见 §11.15.9 前置验证 P4）。

### 11.15.3 价格字段的定位（零新增配置）

**S2 / S4 都需要知道"哪个字段是元素单价"。已核实：无需任何新增配置，现有配置里链路是完整的。**

**实证**（`客户组件模板/组件导入-罗克韦尔.json`，`components[2]`）：

```jsonc
// 组件字段
{ "name": "元素单价", "field_type": "INPUT_NUMBER", "is_amount": true,
  "default_source": { "type": "BASIC_DATA", "path": "$mc_view.元素单价" } }

// 同组件 sqlViews[0].sqlTemplate
LEFT JOIN f_customer_element_price(:customerCode, :priceBaseDate) cep   -- 函数别名
  ON cep.element_code = ebi.component_no
...
cep.unit_price AS 元素单价                                              -- 输出列名
```

**推导算法**：

```
① 在组件 sqlTemplate 里正则捕获取价函数后面跟的标识符   → 别名（本例 cep）
② 用该别名找  <别名>.unit_price AS <列名>               → 价格列名（本例「元素单价」）
   同法找     <别名>.currency   AS <列名>               → 货币列名
③ 在组件 fields 里找 default_source.path == "$<viewName>.<列名>"
                                                        → 即为要写回 / 要清手工值的字段
```

**三条实现纪律**：

1. **禁止硬编码别名 `cep`** —— 它只是规则文档配方里的习惯写法，**未被明文强制**，必须按 ① 动态捕获。
2. **列名逐客户不同**（罗克韦尔是「元素单价」，规则文档举例是「单价」），**禁止靠约定列名去猜**。真正被明文规定的是 `dev-docs/rule-0724-组件模板配置/核价侧.md:33`：**「别名 = 字段名逐字、不加 `_`」** —— 这条是整个推导链的地基。
3. **建议在视图迁移时一次性推导并落库**：因 §11.15.4 本来就要重写报价侧视图，可同时在 `component_sql_view` 上写入派生列 `price_column` / `currency_column`，运行期直接读、不再解析 SQL；新增/编辑组件时由同一段逻辑在保存时算好。既不要人工配置，运行期也不依赖 SQL 解析的健壮性。

**免费拿到的漏配检测（解缺口 B11）**：推导链路走不通（sqlTemplate 无取价函数，或无字段的 `default_source.path` 指向该输出列）**本身就是"此组件未接入版本机制"的信号**，直接进告警清单，不必另写扫描器。

### 11.15.4 通道 A · 取价函数与视图迁移

#### 11.15.4.1 函数签名

```sql
f_material_element_price(p_customer_no TEXT, p_base_date DATE, p_side TEXT DEFAULT 'QUOTE')
  RETURNS TABLE(material_no VARCHAR, element_code VARCHAR,
                unit_price NUMERIC, currency VARCHAR, price_unit VARCHAR)
```

- **比 §11.10 原定的 `(customer_no)` 多两个参**：`p_base_date` 是 fallback 必需的（§11.4.1「指针为空 → task-0722 实时算」离不开基准日）；`p_side` 预留双侧口径。
- **不含 `override_version_id`** —— 双通道方案下预算不走此函数（§11.15.1）。
- **必须保留 fallback 分支**：按 `(customer_no, material_no)` 查指针 → 有则取该版明细 → **无则回落旧函数逻辑**。否则视图从旧函数切到新函数的**那一刻**，所有未升版料号的元素价会全部变空。§11.13 原写的"加法式、可回滚"只覆盖了"旧函数保留"，**没覆盖"视图切换后的存量单"**，此处补齐。

#### 11.15.4.2 🔴 JOIN 键铁律（缺口 A5）

裁决 31 原文写 `AND cep.material_no = ebi.material_no`，**在 BOM 闭包形态的视图下是错的**：

| 视图形态 | `hf_part_no` 输出表达式 | `ebi.material_no` 的语义 |
|---------|----------------------|----------------------|
| **平铺**（形态 A） | `ebi.material_no AS hf_part_no` | 本行料号 ✅ |
| **BOM 闭包**（形态 B，task-0726 已对罗克韦尔落地） | `COALESCE(cl.root_no, ebi.material_no) AS hf_part_no` | **归属料号 —— 子件行上就是子件料号** ❌ |

指针按裁决 36 / 40 只挂在**父件（line_item 销售料号）**上 → 闭包出来的子件行 JOIN 不中 → **子件元素价不吃版本**，静默打破裁决 29「升版原子性」与验收 #15。

**铁律**：

> **JOIN 键必须与该视图 `hf_part_no` 的输出表达式逐字一致。**
> ```sql
> ON  cep.element_code = ebi.component_no
> AND cep.material_no  = COALESCE(cl.root_no, ebi.material_no)   -- 闭包形态
> AND cep.material_no  = ebi.material_no                          -- 平铺形态
> ```

**两种形态并存 → 迁移脚本必须逐视图按其 `hf_part_no` 表达式改写，禁止统一字符串替换。** 本条同时写入 `dev-docs/rule-0724-组件模板配置/3-SQL视图.md` 作为新铁律，否则新配的模板仍走回旧路。

#### 11.15.4.3 🟢 迁移范围减半：核价侧视图一个都不用改

**已核实**：`RuntimeContext.toNamedParams()`（`:153-157`）把 `customerId` + `customerCode` 从 quotation **无条件**放进参数，不分侧；`SqlViewExecutor` 两条执行路径（`:285` / `:360`）也都无条件调 `enrichCustomerCode`（`:423-432`）。故核价侧**技术上能拿到** `:customerCode`。

**但这条需求在双通道方案下消失了**：

- 裁决 40 明确**指针仅 QUOTE 侧** → 核价侧压根没有指针可查；
- 核价侧的版本价只在**升版时经通道 B**（直读版本明细的核价侧列）注入；
- **新建单的核价侧仍走 `f_customer_element_price('_GLOBAL_', :priceBaseDate)` 实时算，行为完全不变。**

**结论：只迁移报价侧的 `mc_view`，核价侧保持原样。** 迁移面与回滚风险减半。

> 📌 **需显式备案的语义后果**：版本生成一段时间后新建的单，**报价侧用该版约定价、核价侧用建单日实时成本**，两侧基准日不同。这是裁决 40 的固有结果，业务上成立（**售价按约定调价版本、成本按当前实际**），但必须备案，免得日后被当 bug 报。

#### 11.15.5.1 F4 的时间线论证
