# 方向 3 · 总价单一来源改造 —— 开发计划

> 起因：`QT-20260806-0082` 报「预算失败重算」，根因是**总价被记了两份**（前端算一份存库、后端算一份存快照），调价改价后只更新了后端那份。
> 本计划把总价收敛为单一来源，从结构上消除分叉。
> 制定：2026-08-06 · 技术总监

---

## 一、核心设计：不是「改成派生」，是「先兜底、后覆盖」

⚠️ 最初的方向 3 描述是「总价改为后端从卡片值派生」，直译会引出两个问题：保存瞬间总价为空、读取方要处理 NULL。**本计划采用改良实现，两个问题都不出现**：

```
保存时     ：仍写入前端提交的值      ← 兜底，保证字段永远有值、无空窗期
懒算完成后 ：从 quote_card_values 取总价，覆盖 li.subtotal   ← 最终权威
```

**这样做的四个收益**：

| | 结果 |
|---|---|
| 保存耗时 | **零增量**（不在保存路径上算任何东西） |
| 空窗期 | **不存在**（字段始终有值） |
| 读取方（后端 44 / 前端 257 处） | **全部不用改**（字段名、类型、非空性都不变） |
| 回滚 | **容易**（只需还原覆盖那一步） |

**字段保留，存储不变，只有「最终写入的值来自哪里」变了。**

## 三、需要拍板的三个设计点

### 1. 覆盖时机挂在哪

`quote_card_values` 的懒算入口是 `CardSnapshotService.snapshotNewLinesCardValues`（`:771-777` 的 `IS NULL` 选行）。覆盖动作应挂在**它算完之后、同一事务内**。

🔒 **必须同事务** —— 否则「卡片值已更新、总价还没跟上」的窗口会再次制造本次同款的不一致。

### 2. 从卡片值里取哪个数

产品行总价 = 该行 `quote_card_values` 里 **SUBTOTAL 类型页签**的值。

🔒 **必须复用 `CostingSubtotalUtil.extractUnitSubtotal`**（L3 守卫用的就是它），不得新写一套提取逻辑 —— 否则守卫比较的两边又是「两套口径」，这次的 bug 会以另一种形式回来。

> ⚠️ 已知 `ComparisonViewService#extractSide` 与 `CostingSubtotalUtil#extractUnitSubtotal` 是同算法两份实现（`BL-0121`）。本次**不合并它们**，但要明确本改造用哪一份。

### 3. 🔴 L3 守卫改成什么（最重要的一条）

**现状**：守卫比较「前端交的总价」与「后端重算」，差异 > 阈值就拦截不写回。

**改造后**：两边同源 → 恒等 → **守卫永远不会报警**。

> **「不再误报」的另一面是「不再报警」。这次帮我们发现问题的正是它。**

**建议改造**（需拍板）：守卫**保留但换比较对象** ——

```
比较：前端提交的总价（保存时兜底写入的那个）  vs  后端算出的总价
行为：不拦截、不阻塞用户，但差异 > 阈值时 记 WARN 日志 + 落一条可查记录
```

这样保留了「发现前后端算值分叉」的能力，同时不再阻塞业务。**阈值沿用现有的可配项（`price_adjust_settings.subtotalGuardThreshold`）。**

### T1 实施结果（§4.1）· 最终实现 —— 以本节为准（`49e540c6`，2026-08-06）

> 🔒 本节是**实现的权威描述**，与代码逐条对应。上面的 T1 表是立项时的初稿，已被扩大。

#### A. 收敛点：`CardSnapshotService#assignQuoteCardValues`

`quoteCardValues` 的 **5 条写路径**统一走同一个入口，卡片值与派生小计是**同一个动作**：

| # | 位置 | 场景 | 覆盖 `li.subtotal` / `cd.subtotal` | 重算单头 |
|---|---|---|---|---|
| 1 | `snapshotNewLinesCardValues`（Pass2） | 懒算批量 | ✅ | ✅ |
| 2 | `snapshotQuoteSideOnly` | 加产品 / **导入逐行** | ✅ | ❌ **有意不做**，见 D |
| 3 | `refreshQuoteCardValues` | 刷新基础数据 | ✅ | ✅（在 `refreshDraftQuoteCards` 循环**外**） |
| 4 | `editCardValue` | 单元格失焦（改价主入口） | ✅（延后，见 E） | ✅ |
| 5 | `materializeAndProject` | 树删除重灌 | ✅（延后，见 E） | ✅ |

取数口径唯一：`CostingSubtotalUtil`，与 L3 守卫 S0 / S6 **同一个方法**。新增
`extractUnitSubtotalOrNull`（区分「取不到」与「算出来是 0」）+ `extractTabSubtotalsByComponentId`；
原 `extractUnitSubtotal` 退化为薄包装，**行为逐位不变**。

**三种不覆盖情况**（一律保留兜底值，绝不抹成 0）：失败哨兵（`__cardValueFailed`）/
模板无 SUBTOTAL 页签 / 页签没算出 `subtotal`。

#### B. 🔴 单头两套口径（`recomputeDraftHeaderTotals`）

抽 `QuotationService:2054-2068` 那 6 行，**不复用 `recalculate`**（其余是
`derivedAttributeCalculatorV5` 逐行派生属性重算，另一件事且很贵）。

| 口径 | 公式 | PART 子件 | 写入点 |
|---|---|---|---|
| **草稿** | `Σ li.subtotal × finalDiscountRate/100` | **计入** | `QuotationService:667 / 2064 / 2508` |
| **提交** | `Σ li.lineTotalAmount`（已含行折扣 × 年用量） | **排除** | `QuotationService:858` |

🔒 **只在 `DRAFT` 执行**。`ensureCardValues` 也会被非草稿单触发
（`ComparisonViewService` / `CostingFreezeService#createForSubmission`），那时单头已由 submit 用
**另一套口径**算定 —— 不加这道 status 闸门就会被当场覆写成草稿口径，**那是改已提交单据的金额语义，
比原 bug 更严重**。已实测：把单据改成 `SUBMITTED` 后触发懒算，单头两列逐位不变、行总价仍被覆盖。

#### C. submit 时序（`QuotationService#submit`）

`ensureCardValues(id)` **上提到 `lineDiscountService.recompute` 之前**。

改造前：`recompute(旧值) → totalAmount → createForSubmission →` 其内部第一句才 `ensureCardValues`
→ 9 个行金额字段、整单总额、`frozen_dto` 冻的全是**即将被改掉的旧数**。

本改动等于把 `CostingFreezeService#createForSubmission` 的第一句往前挪几行，**冻结核心一字未动**；
`ensureCardValues` 幂等（`IS NULL` 谓词 + 单飞锁），故 `:861` 那次命中 0 行、**净增量 ≈ 0**。

拿不到单飞锁（返回 `-1`）改抛 **409**：继续 = 用旧值算完并冻结，而**冻结数据是不可逆的历史凭据**。
触发条件是同一张单在 ~0.7s 的 warm 窗口内并发 `ensureCardValues`；最现实的来源是**双击提交**
（用户行为，非系统竞态）→ 已提给前端加防抖。

#### D. 为什么路径 2 有意不算单头

路径 2 被 `ImportExecutionService` 在 **N-行循环里逐行调用**（且 `prefetch` 恒 `null`）。
`recomputeDraftHeaderTotals` 内部要查本单全部行 —— 放进逐行路径就是 **O(N²)**。

链路是通的：导入 / 加产品**本身不写** `total_amount`（已 grep 确认两个模块零引用），
靠随后的 `saveDraft`（写前端口径）+ 懒算批量（路径 1，含单头重算）收敛。
**这不是遗漏**。同理，路径 3 的单头重算放在 `refreshDraftQuoteCards` 的循环**外**。

#### E. 🚨 两个实现期抓到的自引 bug（注释已固化，改这段代码前必读）

**E-1 · `REQUIRES_NEW` 自锁 → JTA 60s 超时 500**

```
覆盖 cd.subtotal → 触发 Hibernate auto-flush → 外层事务锁住 cd 行
                 → materializeWholeLineRowData（REQUIRES_NEW）写同一批行
                 → 外层等内层返回、内层等外层放锁 → 自锁至 JTA 超时
```

`editCardValue` / `materializeAndProject` 两条路径都是这个形态。**代码上看不出有锁**——
锁是 auto-flush 这个隐式动作带来的。修法：这两条改用 `applySubtotalsFromCardValues`，
把覆盖**延后到 `materializeWholeLineRowData` + `em.flush()/clear()` 之后**。

> 诊断留痕：现象是稳定 500 且**耗时恒定 60.11s**。「冷启动」是这里最容易让人停止追查的解释，
> 但**恒定 60.11s 不是冷启动能给出的数，那是 JTA 超时阈值**。排除方式 =
> ①在 master 上跑同一请求得 200（证明是自引回归）→ ②从 dev server stdout
> （`/proc/<pid>/fd/1`）捞到 `TransactionReaper::doCancellations` → ③warm 后重测仍恒定 60.11s。

**E-2 · 游离态实体静默丢写**

`refreshDraftQuoteCards` **没有** `@Transactional`（它逐行 `self.refreshQuoteCardValues` 各开各的事务）。
调用方在事务外 `Quotation.findById()` 拿到的是**游离态**实体，赋值不会被脏检查落库 —— 静默丢写。
症状是「行值对了、单头没动」这种**一半生效一半不生效**，极易被误判为「逻辑漏了个分支」。
修法：`recomputeDraftHeaderTotals(UUID quotationId)` 改为**自己在本事务内 `findById`** 取托管实体。

#### F. 性能实测

- **saveDraft 结构性零增量**：覆盖不在保存路径上（`saveDraft` 不调 `ensureCardValues`，只置 NULL）。
  运行时实证 —— saveDraft 后 `li.subtotal` 仍是前端值 `59.580015`、`cd.subtotal` 全 0、
  `quote_card_values` 为 `NULL`；调 `ensure-card-values` 后才变 `37.330516`。
- **路径 2 闸门**（导入循环，加了一次 cd 索引查询）：单行
  median `575.8 → 559.8ms`、min `472.4 → 469.5ms`、p25 `521.0 → 486.8ms` ——
  三个统计量全部 ≤ 0，增量在噪声底以下。

#### G. ⚠️ 回归面：`cd.subtotal` 的下游是 Excel 列

`cd.subtotal` 被 `ComponentDataEffectiveRows#computeScaled`（`:224`，NORMAL 页签「沿用持久化值」）
读走，喂给 Excel 列的 `[页签(总计)]`（`TabJoinPlanEvaluator:303`）与 `__subtotal__`
（`CardFormulaEvaluator:226`）。

- **不是反馈环**：`cd.subtotal` **不参与** `quoteCardValues` 的生成
  （`assembleTabsWithFormulaResults` 的 `componentSubtotals` 全部由 baseRows/editRows/computeRows
  在内存算出，无一处读 `cd.subtotal`）→ 覆盖不会改变下一轮自己的输入，**结构上不可能自激**。
- **但是单向传播**：沙箱单这 8 个页签的 `cd.subtotal` 原本**全是 0**（前端从没送过真值），
  即这些 token 在报价单渲染路径上**一直返回 0**；覆盖后开始返回真实小计。
  **是修复，但是行为变更** —— Excel 视图 / 导出的断言要写成「值从 0 变为真实小计」的方向性判断。

**规则**：值中性验证一律拿 `li.subtotal`（`numeric(20,6)`）与卡片值 JSON 里的
`tabs[componentType='SUBTOTAL'].subtotal` 做**全精度**比较（SQL 侧用 `numeric` 直接比，
脚本侧用 `Decimal`），**不得采信端点 `diff`**。端点 `diff` 只适合「找显著分叉」，
不适合「证明没变」—— 用它做值中性验证会把 2.5e-5 量级的漂移全部漏掉。

> 这批 2.5e-5 量级差异本身是**落库精度规整**（`PrecisionPolicy.round()` 到 6 位）与
> 卡片值 JSON 里 `double` 全精度之间的正常差，不是缺陷；但它必须被**看见并归类**，
> 而不是被显示精度吃掉。

#### ⚠️ 两种对拍不是一回事，不能互相替代（2026-08-06 实测澄清）

跑下面的 SQL 会得到 `7 / 7 / 23`，而端点是 `6 / 6 / 31` —— **不是矛盾，是两个不同的问题**：

| | 比较对象 | 回答的问题 | 覆盖范围 |
|---|---|---|---|
| **对拍端点** | `li.subtotal` vs **现算**（`buildCardValues` 当场重跑） | 「后端现在算出来是多少？和落库值差多少」= **找双端分叉** | 43 行（含 `quote_card_values IS NULL` 的行，因为它现算） |
| **下面的 SQL** | `li.subtotal` vs **已落库的** `quote_card_values` | 「单一来源不变量有没有被破坏」= **守本次改造的约束** | 37 行（`quote_card_values IS NOT NULL`；全库 45 行中 8 行卡片值为 NULL） |

两个清单只部分重叠，各自能抓到对方抓不到的：

- 只在 SQL 侧出现（`QT-20260726-0008` / `QT-20260726-0016` / `QT-20260731-0037`）
  = 落库的 `li.subtotal` 与**它自己那份卡片值**都对不上 → **不变量已破**，但端点看不出来。
- 只在端点侧出现（`QT-20260726-0003` / `QT-20260803-0056`）
  = `li.subtotal` 与卡片值一致，但**卡片值本身是陈旧的**（现算会得到别的数）。

🔒 **验收 `#D3` 系列请两个都跑**：端点用来确认「故障分叉消失」，SQL 用来确认「单一来源不变量成立」。
上面那 7 条 SQL 侧不一致是**存量**（这些行尚未经过覆盖），会在各自下一次懒算/刷新/编辑时自愈 ——
**复测时应看到它们逐条减少，而不是一次归零**。

**可直接跑的全精度不变量对拍 SQL**（不经端点，`numeric` 直比，按三档分类）：

```sql
SELECT q.quotation_number,
       li.subtotal                                   AS li_subtotal,
       (SELECT (t->>'subtotal')::numeric
          FROM jsonb_array_elements(li.quote_card_values::jsonb->'tabs') t
         WHERE t->>'componentType' = 'SUBTOTAL')     AS card_subtotal,
       abs(li.subtotal - (SELECT (t->>'subtotal')::numeric
          FROM jsonb_array_elements(li.quote_card_values::jsonb->'tabs') t
         WHERE t->>'componentType' = 'SUBTOTAL'))    AS real_diff,
       CASE
         WHEN abs(li.subtotal - (SELECT (t->>'subtotal')::numeric
                FROM jsonb_array_elements(li.quote_card_values::jsonb->'tabs') t
               WHERE t->>'componentType' = 'SUBTOTAL')) > 0.01 THEN '显著不一致'
         WHEN li.subtotal = (SELECT (t->>'subtotal')::numeric
                FROM jsonb_array_elements(li.quote_card_values::jsonb->'tabs') t
               WHERE t->>'componentType' = 'SUBTOTAL')       THEN '逐位相同'
         ELSE '末位舍入'
       END                                           AS bucket
FROM quotation q
JOIN quotation_line_item li ON li.quotation_id = q.id
WHERE li.quote_card_values IS NOT NULL
ORDER BY bucket, q.quotation_number;
```

同款口径查**页签小计**（把 `componentType='SUBTOTAL'` 换成按 `componentId` 配对）：

```sql
SELECT q.quotation_number, cd.tab_name, cd.subtotal AS cd_subtotal,
       (SELECT (t->>'subtotal')::numeric
          FROM jsonb_array_elements(li.quote_card_values::jsonb->'tabs') t
         WHERE t->>'componentId' = cd.component_id::text) AS card_subtotal
FROM quotation q
JOIN quotation_line_item li ON li.quotation_id = q.id
JOIN quotation_line_component_data cd ON cd.line_item_id = li.id
WHERE li.quote_card_values IS NOT NULL AND cd.component_id IS NOT NULL
ORDER BY q.quotation_number, cd.sort_order;
```
