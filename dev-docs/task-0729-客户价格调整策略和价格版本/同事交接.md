## 六、技术方案的核心（§11.15 摘要）

### 6.1 最要命的三个坑

| 坑 | 说明 |
|----|------|
| **A1 · 升版会被静默回滚** | 元素单价冻结在 `snapshot_rows` 里，而**全后端没有任何"按新价刷新它"的写入口**。只重算 `quote_card_values` 的话，销售**存一次草稿就退回旧价** —— 升版当时看着对，过一会儿就错了 |
| **A3 · 裁决 32 的乐观时间戳不成立** | `quotation.updated_at` 不是可靠水位线 —— 销售最常见的编辑路径（单元格编辑、删恢复行、树增删叶、选配加产品）**全都不 bump 它**。原方案下"销售改动不丢失"必然失败，且失败方式是**静默覆盖** |
| **A5 · JOIN 键在 BOM 闭包下是错的** | 裁决 31 写的 `cep.material_no = ebi.material_no`，在闭包视图里 `ebi.material_no` 是**子件料号**不是销售料号 → 子件行 JOIN 不中 → **子件元素价不吃版本**，静默破坏"升版原子性" |

**三个坑的共同点：不报错、不崩溃，只是数据悄悄不对。** 这正是本项目历史上返工成本最高的一类（参见 `docs/反模式.md` AP-31 / AP-37 / AP-53）。

### 6.2 核心架构：双通道分离

```
通道 A · 新建单初次取价
  mc_view ──JOIN──► f_material_element_price(客户, 基准日, 侧别)
                      ├ 料号指针有值 → 取该版价
                      └ 指针为空     → 回落 task-0722 实时算
  ★ 只迁报价侧视图，核价侧一个都不用改

通道 B · 升版执行 + 审核预算       ← 同一段代码，只差 dryRun 布尔
  element_price_version_item ──直接读──► 字段级写回 snapshot_rows → 重算
  ★ 不走视图、不走函数、不需要版本入参
```

**为什么这么设计**：审核页要显示"按新版价重算后的报价"（预算），执行时又要真按新版价重算。**两者共用同一段代码 + 同一个数据源**，"预算与实际逐位一致"就从**靠纪律**变成**结构上不可能违反**。
