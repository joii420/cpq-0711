## 一、本次要解决的问题

**用户报的故障**：`QT-20260806-0082` 在价格调整审核页面显示「**预算失败重算**」。

**根因**：价格调整改价后**不重算行总价**，而 L3 口径守卫会比较「前端交的总价」与「后端重算值」，差异超阈值就拦截。

> **调价机制每改一次价就制造一条脏数据，然后守卫再把它拦下来——两个机制在互相打架。**

**选定方案（方向3）**：总价单一来源——保存时仍写前端提交值（兜底，字段永不空窗），懒算完成后**从卡片值取总价覆盖行总价**（最终权威）。

### 2.2 计划外挖出并修复的三个缺陷 ← **本轮真正的价值**

这三条都不是原计划范围，且**全部是既有缺陷**（改造前后实测逐位相同），但都在本轮被挖出并修掉。

#### ① 提交功能单击必失败（可用性）

```
保存草稿成功 → 前端自动发预热请求 → 1ms 后提交请求发出
               ↑ 预热占锁约 0.5s        ↓
                                    提交被拒 409
重试也没用：重试会再保存一次，又触发预热，又撞一次
```

**发现方式**：前端走完整界面流程实测。此前后端评估「最现实的触发源是双击」是**推断**；测试的用例走接口路径，**不经过保存草稿这一步，所以撞不上**。

**修复**：提交路径跳过重复预热（前端）+ 提交碰到锁时**有界等待 8 秒**（后端，事务外非阻塞轮询）。

#### ② 提交金额静默错值（正确性）

```
提交前显式重建价格 ← 修复
```

原逻辑用「价格为空才重算」判定，而在飞的预热计算会把值填回去，导致提交**静默采用旧数据算出的价格**。4/4 复现。

#### ③ 并发下整行被旧值覆盖（数据完整性）← **最严重**

```sql
update quotation_line_item set 年用量=?, ..., 小计=?, ..., where id=?
                               ↑ 框架默认【更新整行】，与业务代码写不写它无关
```

**受害字段**：`年用量` / `折扣系列` / `行金额` / `小计` —— **全部列**。

**用户视角**：

| | |
|---|---|
| 编辑期间 | **无任何征兆**（界面始终显示用户自己填的数） |
| 第一次能看见 | **提交完成之后**——此时错值已冻结进核价单 |
| 触发条件 | **「改完直接提交」**——最自然的收尾动作 |
| 为何长期未被发现 | 反复保存会自愈；耐心的验证者每次都在悄悄修复它 |

**修复**：实体加 `@DynamicUpdate`（只更新改动过的字段）。对照定量：**哨兵存活 0/8 → 8/8**（即修复前 100% 丢失）。

**代价评估**：死锁率无变化（7/8 vs 8/8）；被数据库中断的**永远是后台计算、从不是用户保存**（0/8、0/16）→ 用户无感且自愈；耗时差异在噪声内。

## 五、方法论沉淀

> 本轮三方共 **8 次「差点得出错误结论」**，**没有一次是靠重新思考解决的，全是靠换一种测法**。这个比例本身就是结论。

### 5.1 最高优先级的一条

> **结论存疑时，先问「我现在用的量具能不能分辨这两种情况」，而不是「我判断得对不对」。**
>
> 「我判断得对不对」是没有出口的自省——想一百遍还是同一副眼镜；「量具能不能分辨」是有答案的检查，而答案往往是「不能」。

### 5.2 量具说谎的五种形态

| 形态 | 实例 |
|---|---|
| 现象撞脸 | 事务超时被读成冷启动 |
| 输入被静默改写 | 阈值 `1e-7` 被字段精度截断成 `0`，验的是相反场景 |
| **被测行为压根没发生** | 10 行下后台计算全死于死锁 → 哨兵「存活」什么都没证明 |
| 真相被压缩 | `string_agg(DISTINCT)` 把 10 行塌缩成 2 个值 |
| **字段分辨不了要分辨的东西** | 用 git 作者字段区分会话，而所有会话共用一个身份 |

### 5.3 「状态可以伪造，副作用不能」

> 真实用户点这个按钮，浏览器一共发几条请求？我的用例发了几条？**条数不等就不是同一条路径。**

配套的边界（可以省的部分）：**被测代码之前的都是输入，可以造；它之后的一步都不能省。**

### 5.4 判据独立性：从「谁会修复它」反推「谁的证据不会被谁污染」

三个修复同时落地时，若判据选错，**一个修复会掩盖另一个的失效**。正确做法是找**其他修复手够不到的字段**。

最终拿到的证据形态：

```
同一条 UPDATE ：一个字段被覆盖  +  另一个字段存活
                ↑ 证明竞态真实发生    ↑ 证明字段集受限
```

**两个结论来自同一次观测且互为前提**——比「跑 8 次都对」有力得多。

### 5.5 现状可能正在挡着更坏的事（本轮出现 4 次）

> **凡是要把一个「快速失败」改成「优雅处理」，先问：这个失败当前挡住了什么？**

| 看似是缺陷 | 实际在挡 |
|---|---|
| 拿不到锁立刻失败 | 事务内等待会成死锁环 |
| 提交 409 | 等待的终点恰好是污染发生的时刻 |
| 死锁 | 后台计算回滚 → 没机会覆盖用户输入 |
| 状态表里的 ✅ | 缺口藏在勾后面（比写 ❌ 更糟，❌ 至少会招来追问） |

### 5.6 文档与实现不符的五种形态

落后 / **超前**（比实现乐观，掩盖缺口）/ 描述错（叫「退避」实为定间隔）/ 口径错（16s 不含 21 次往返）/ **两个各自正确的数字被读者错误关联**。

> 数字旁边必须写清量纲：**谁的、什么的、同步还是异步**。本轮那个 `9-12s` 写下来时是对的，两个人读的时候都错了。

### 5.7 「顺手多看一层」需要弹药

有些缺陷既非问出来、也非断言出来，而是**看了运行时真实产物才发现的**（全列 UPDATE 就是查死锁时顺手看见的，没有任何用例在断言它）。

但这条习惯的前提是**知道产物在哪**：服务端输出、数据库会话与锁、运行参数、落库原文、热重载记录。

> **「顺手多看一层」是动作，产物清单是它的弹药。没有弹药时，人只能回到猜。**

边界：**优先读「已经产生的」产物，慎开「需要新增采集的」开关**——后者在共享环境代价不低，且**采集动作本身会改变被观测的系统**。

### 5.8 派活方式会诱导跳过诊断

> 「加防抖」这个措辞**已经隐含了一个诊断**（并发导致、触发源是手速）。照做的人会写完防抖、测试通过、如实汇报完成——**三条都不算撒谎，而提交功能仍然全坏**。
>
> **给出「怎么修」的任务，比给出「什么坏了」的任务更容易让人跳过诊断。**

### 5.9 多会话共享 git 身份时，提交归属只能靠自报 + 时间线交叉验证

单方面查 git 一定会算错（本轮验收人与后端**各错一次**）。

⚠️ **且必须在自报还有效时就固定归属**——本轮有一条 `c382e664` 双方都认不下来，**证据源已不存在，永久无法恢复**。查错可以纠正，证据消失不能。
