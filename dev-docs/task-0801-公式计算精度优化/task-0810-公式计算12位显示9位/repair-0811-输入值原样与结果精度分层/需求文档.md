# 输入值原样与公式结果精度分层

- 立项日期：2026-08-11
- 类型：repair
- 状态：已交付（2026-08-11，AC-1~AC-12 准入）
- 关联任务：`task-0810-公式计算12位显示9位`
- BACKLOG：`BL-0162`

## 1. 背景与根因

task-0810 将动态 JSON 中的数值 token 普遍视为精度敏感值，保存草稿时由 `DecimalRequestValidator` 递归拒绝 JSON number。实际卡片行同时包含输入字段与公式字段，两者语义不同。

当前 `rowData` 中合法的 `{"项次":1}` 在 `PUT /api/cpq/quotations/{id}/draft` 被拒绝，报错：`lineItems[0].componentData[1].rowData[0].项次 must be a decimal string`。直接原因是结构整数白名单只覆盖 `_项次`，没有覆盖物化后的 `项次`；根本原因则是校验没有读取字段 `field_type`，错误地把所有动态数值当成公式精度值。

## 2. 范围

### 2.1 本期做

1. `INPUT_TEXT`、`INPUT_NUMBER` 和基础数据带入的输入单元格按当前单元格值保存、回显和参与运算，不按公式结果精度统一规整。
2. 输入数值跨浏览器边界使用十进制文本保真；结构整数可保持 JSON number。禁止把输入值先转 JS `number` 或 Java `Double` 再恢复十进制。
3. 公式运算过程和跨公式节点工作值保持 12 位小数、`HALF_UP`。
4. 单元格公式最终结果保留最多 9 位小数、`HALF_UP`、去尾零。
5. 产品卡片小计和报价单总金额分别使用独立精度变量，初始值均为 9；变量旁必须注明未来由系统参数动态覆盖，当前不接数据库参数。
6. 修复前端 `losslessJson.ts` 中 `项次/_项次` 乱码白名单，并补真实保存链路测试。

### 2.2 本期明确不做

- 不新增系统参数表字段，不新增管理页面；动态配置接入后续单独立项。
- 不修改 V385 的 `numeric(26,12)` 容量，不新增 Flyway。
- 不回刷已审批/冻结单据；DRAFT 在下次明确保存或重算时采用新规则。
- 不允许用“把所有动态 number 放行”替代字段语义分类。

## 3. 决策记录

| # | 决策项 | 结论 | 理由 | 否决方案 |
|---|---|---|---|---|
| D-1 | 输入字段精度 | 当前单元格值原样保存和使用 | 用户输入/基础数据不是公式结果 | 所有输入统一 9 位或 12 位，会改变源值 |
| D-2 | 公式过程 | 12 位 `HALF_UP` | 保留保护位并维持前后端一致 | 使用 JS number/Double，会重新引入二进制误差 |
| D-3 | 公式最终结果 | 最多 9 位、去尾零 | 用户确认的最终结果口径 | 持续保存 12 位公式结果，不符合新口径 |
| D-4 | 产品卡片小计 | 独立 `PRODUCT_CARD_SUBTOTAL_SCALE=9` | 为后续系统参数调整预留稳定入口 | 继续隐式复用通用 DISPLAY_SCALE |
| D-5 | 报价单总金额 | 独立 `QUOTATION_TOTAL_SCALE=9` | 小计与总额以后可能独立配置 | 与产品小计共用一个变量 |
| D-6 | 输入值载体 | 十进制文本保真；结构整数允许 number | `1.2300` 只有文本能保留书写精度 | 全部 JSON number 或全部强制结构整数转字符串 |
| D-7 | 动态字段判定 | 依据冻结组件字段元数据的 `field_type` / 字段来源 | 字段名白名单无法覆盖自定义字段 | 只给“项次”加白名单，治标不治本 |
| D-8 | 闸门 A | 2026-08-11 用户确认按本文进入开发 | 用户回复“可以” | 未确认即改业务代码 |

## 4. 功能需求

- FR-1 保存草稿必须接受 `INPUT_NUMBER` 当前值，包含 `项次: 1`、数量 `"1.2300"` 和基础数据带入值。
- FR-2 保存与重开不得将输入文本 `"1.2300"` 改为 `"1.23"`、`"1.230000000"` 或 number。
- FR-3 输入字段参与公式时在运算入口解析为 Decimal/BigDecimal，不改写输入载体。
- FR-4 公式每个结果节点按 12 位工作精度计算，最终单元格结果按 9 位输出。
- FR-5 产品卡片小计在结果边界使用 `PRODUCT_CARD_SUBTOTAL_SCALE`。
- FR-6 报价单 `originalAmount/totalAmount` 及对应报价总额结果边界使用 `QUOTATION_TOTAL_SCALE`。
- FR-7 前后端使用同名或明确映射的精度变量，并在注释中标明未来系统参数覆盖点。
- FR-8 公式字段发送非法 JSON number 仍返回 400；输入字段不得被同一规则误拒绝。
- FR-9 字段元数据缺失或损坏时禁止盲目放行所有 number，应返回可定位错误或按明确的兼容策略处理。

## 5. 数据与精度规则

| 数据类别 | 保存载体 | 计算入口 | 结果边界 |
|---|---|---|---|
| `INPUT_TEXT` | 原字符串 | 非数值不参与；数值语义按配置处理 | 不规整 |
| `INPUT_NUMBER` / 基础数据数值 | 原十进制文本；结构整数可为 number | Decimal/BigDecimal | 不回写规整后的输入值 |
| `FORMULA` / `*_FORMULA` | decimal string | 12 位工作精度 | 最多 9 位 |
| 产品卡片小计 | decimal string | 基于公式结果累加 | `PRODUCT_CARD_SUBTOTAL_SCALE`，初始 9 |
| 报价单总金额 | decimal string + `numeric(26,12)` | 基于行金额累加 | `QUOTATION_TOTAL_SCALE`，初始 9 |

## 6. 验收标准

- AC-1 `rowData=[{"项次":1}]` 保存草稿返回 2xx，保存后仍为整数 1。
- AC-2 `INPUT_NUMBER` 输入 `"1.2300"` 保存、数据库 JSON、GET 重开后文本逐字仍为 `"1.2300"`。
- AC-3 基础数据带入的 12 位输入值不因保存或重开被压到 9 位。
- AC-4 同一输入参与 `1/3` 等公式时，前后端过程值按 12 位一致，公式最终结果最多 9 位。
- AC-5 非输入类公式字段若发送 JSON number，后端仍返回 400 且不产生部分写入。
- AC-6 产品卡片小计调用独立变量，边界值 `1.2345678905` 按 9 位得到 `1.234567891`。
- AC-7 报价总金额调用另一个独立变量，同一边界值按 9 位得到 `1.234567891`。
- AC-8 将两个独立变量在测试中设为不同值时，各自仅影响自己的结果边界，证明没有串用。
- AC-9 前端和后端不存在输入值经 `.toNumber()`、`Double`、`doubleValue()` 的新增精度链。
- AC-10 `losslessJson` 正确识别 `项次`、`_项次`、`序号`，源码无对应乱码字面量。
- AC-11 报价、核价、比较三视图对输入值和公式结果的显示/重开一致。
- AC-12 无数据库结构变化、无新 Flyway，V385 的 21 列仍为 `numeric(26,12)`。

## 7. 影响与风险

- 命中 AP-50、AP-57、AP-58、AP-59：三视图、产品小计、前后端双引擎、Excel/快照必须同步验证。
- 动态字段值与字段定义分属不同载体，后端若逐行查询组件会引入 N+1；必须批量加载冻结字段元数据并复用。
- “原样”是值载体语义，不代表允许 JavaScript 浮点噪声。十进制输入必须在成为 JS number 前拦住。
- 产品小计和报价总额的 9 位是结果边界；数据库列继续允许 12 位容量，避免未来参数扩大时再次迁表。

## 8. 已知坑位

- 只把 `项次`加入白名单会让其他自定义 `INPUT_NUMBER` 继续失败。
- 只在前端把 `1`改成`"1"`会掩盖后端语义错误，并破坏结构整数契约。
- `1.2300` 与 `1.23` 数值相等但原始文本不同，测试必须同时检查数值和序列化文本。
- 已发布模板必须读取冻结字段定义，不能回落活组件定义改变历史单据语义。
