## 1. 背景与目标

原 task-0801 的现行契约是：十进制加减乘、除法 12 位、落库/API/显示/导出统一最多 6 位。当前实现还存在三个问题：

1. 后端单次算术使用 `BigDecimal`，但公式节点、跨页签小计、上一行值等仍大量回落到 `Double`。
2. 前端解析器使用 Decimal.js，但公式函数出口和上下文仍大量回落到 JS `number`。
3. 计算值落库只有 6 位，刷新后下游公式只能使用 6 位值，无法满足“计算期间保留 12 位”。

本任务目标：

- 公式计算节点之间、快照、持久化和重新加载后均保留 12 位小数。
- UI、HTML、PDF、Excel 最终最多显示 9 位小数，`HALF_UP`，去尾零。
- 前后端对同一公式、同一输入逐值一致。
- 后端精度敏感值全链路使用 Java `BigDecimal`，前端使用等价的 Decimal.js `Decimal`；不得经过 Java `Double`/`double` 或 JS `number`。
- 已冻结历史单据保持原值，不做读取时重算或改写。

## 4. 功能需求

- **FR-1 精度策略分层**：前后端分别提供 `CALCULATION_SCALE=12`、`DISPLAY_SCALE=9`、`ROUNDING=HALF_UP` 的单一来源。
- **FR-2 公式算术**：加减乘使用十进制精确运算；除法和公式节点输出按 D-1 规整。
- **FR-3 公式上下文**：字段值、上一行值、跨页签值、列小计、页签合计、产品小计以及折扣/总额/差异不得出现 Java `Double`/`double` 或 JS `number`；后端统一 `BigDecimal`，前端统一 Decimal.js `Decimal`。
- **FR-4 JEXL 一致性**：全部 JEXL 求值点使用 BigDecimal 算术，数字字面量、变量和函数结果不得回落到 Double。
- **FR-5 持久化**：21 个关系型计算列使用 `numeric(26,12)`；计算 JSON/JSONB 使用规范十进制字符串。
- **FR-6 兼容读取**：历史 JSON numeric token 必须按原始十进制字面量无损解析并直接进入 BigDecimal/Decimal，禁止先落为 `Double`/JS `number`；空值、除零、非法公式语义保持不变。
- **FR-7 API**：受影响接口的精度字段请求和响应均使用 decimal string；JSON number 请求按现有 400 类型校验拒绝，后端 DTO 直接绑定 BigDecimal/string，不经过 Double。
- **FR-8 前端计算**：前端精度字段类型只允许 `DecimalString | Decimal`，Decimal 值只在渲染边界格式化为字符串；state、payload、localStorage 草稿和后续公式输入禁止 JS `number`。
- **FR-9 显示**：报价/核价/详情/列表/快照/比较视图统一最多 9 位、去尾零。
- **FR-10 导出**：HTML/PDF/邮件/Excel 与 UI 显示值一致；Excel 的精度敏感计算值全部写文本单元格，禁止经过 `double` NUMERIC API。
- **FR-11 历史状态**：非 DRAFT 单据不重算、不回写；DRAFT 仅在用户显式保存或重算时升级新格式。
- **FR-12 对拍与提交闸门**（**2026-08-13 由 `repair-0812` 改写，见下方 ⚠️**）：对账**按结果精度 `FORMULA_RESULT_SCALE`（现值 9 位）判定** —— 比较前先把两侧值归一到该精度，再以 `10^-12` 容差吸收同尺度末位噪声；判定为不一致时仍阻止提交。
  > ⚠️ **原条款已作废**（原文：「对账阈值按 12 位工作值判定；前后端不一致仍阻止提交，不因显示同为 9 位而放过第 10~12 位差异」）。
  > **作废原因**：该条款**不可执行** —— 后端从不产出 12 位的对比基准。`FormulaCalculator.java:1113/:1244` 落进快照 `formulaResults` 的值被 `PrecisionPolicy.roundFormulaResult` 压到 9 位（这是 task-0810 自己保留的既有契约），而前端 `formulaCache` 是 12 位工作值，两侧尺度天然差 3 位、差值上界 `5e-10`，恒 > `1e-12` 容差 ⇒ **凡第 10~12 位非零的公式列 100% 误报且永不消解**，连带提交闸门 409 卡死。
  > 一个只有单边能满足的判定条件 = 恒不成立。详见 `dev-docs/task-0801-公式计算精度优化/repair-0812-对账阈值与结果尺度不对称致误报/问题说明.md`。
  > **若将来业务确认「第 10~12 位分歧也必须阻断提交」**，须先让后端产出 12 位工作值（该 repair 的方案 C，已评估为影响 4 条快照消费链路，当次未采纳），再恢复本条原意。

## 5. 数据与规则

### 5.1 精度分层

| 层 | 精度 | 表示 |
|---|---:|---|
| 公式内部 `+/-/*` | 不主动截断 | 后端 `BigDecimal` / 前端 Decimal.js `Decimal` |
| 除法 | 12 位 | `HALF_UP` |
| 公式节点、跨节点缓存、快照、关系型落库 | 12 位 | BigDecimal / 规范十进制字符串 |
| API 精度值 | 12 位有效工作值 | JSON string，禁止科学计数法 |
| UI/PDF/HTML/Excel | 最多 9 位 | `HALF_UP`，去尾零 |

### 5.2 关系型迁移范围

原 task-0801 的 12 列：

- `quotation`: `total_amount`, `original_amount`, `tax_amount`
- `quotation_line_item`: `subtotal`, `discount_base_amount`, `line_unit_price`, `line_final_price`, `line_discount_amount`, `line_total_amount`
- `quotation_line_component_data`: `subtotal`
- `costing_order`: `total_amount`, `costing_total_amount`

后续新增的 9 个派生计算列：

- `material_price_review`: `warn_diff`
- `material_price_review_column`: `quote_current`, `quote_adjusted`, `costing_current`, `costing_adjusted`, `diff_current`, `diff_adjusted`
- `quotation_price_revision`: `quote_total_amount`
- `material_price_update_job_item`: `diff_value`

上述列统一从 `numeric(20,6)` 扩为 `numeric(26,12)`；只放大，不重算值。JPA `precision/scale` 同步。

### 5.3 JSON/JSONB 规则

- 计算数值写为规范十进制字符串，例如 `"98765431.123456789012"`。
- 历史数字节点 `98765431.123456` 仍可读，但只能从 JSON 原始字面量直接构造 BigDecimal/Decimal，禁止普通 `JSON.parse` 后再转换。
- 文本、布尔、null 语义不变；不得把 null 变成 `"0"`。
- 基础取数值不按 9 位显示规则压缩；进入公式时从原始十进制文本构造 Decimal。
- 禁止整棵 JSON 无字段语义地递归 round。

### 5.4 标准例子

| 场景 | 12 位工作值 | 9 位显示 |
|---|---|---|
| `1 / 3` | `0.333333333333` | `0.333333333` |
| `10 / 3 * 3` | `9.999999999999` | `10` |
| `1.2345678912345` 节点输出 | `1.234567891235` | `1.234567891` |
| `1.2345678915` | `1.2345678915` | `1.234567892` |
| `0.0000000004` | `0.0000000004` | `0` |
| `0.0000000005` | `0.0000000005` | `0.000000001` |
| `98765431.123456789012` | 原值逐字保留 | `98765431.123456789` |
