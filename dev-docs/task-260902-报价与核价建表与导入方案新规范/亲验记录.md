### AC-5 · 39 张 `_history` 结构

比对方式：`_history` 列集合 == 主表列集合（`id` → `origin_id`）∪ `{archived_at, archived_by, archive_reason}` ∪ `{id}`。

```
history 表数=39   不一致=0        ✅ 39/39 全等
```

⚠️ **判据说明（2026-09-03 补记，如实交代）**：我当时的比对式是
`want = (主表列 - {id}) ∪ {origin_id} ∪ {archived_at, archived_by, archive_reason} ∪ {id}`
—— **末尾那个 `∪ {id}` 是我自己加的**，而 AC-5 原文并没有写 history 表可以自带 `id`。
所以这个「全等」建立在我放宽后的判据上，严格按 AC 字面判会是 39/39 全部**不通过**（多一列 `id`）。

测试代理按字面判、报了这条差异，**它是对的**。经复核：给 history 配自己的主键是合理实现
（同一 `origin_id` 会因多次升版出现多行，不能用它做主键），且 `backtask.md` B-2 原本就这么要求。
⇒ **裁决：改 AC 措辞，不改实现。** AC-5 已于同日补上 `∪ {id}`，本条亲验结论在新措辞下成立。

📌 **这条值得记**：主线亲验时若发现「实现合理但与 AC 字面不符」，**正确动作是停下来改 AC 并留痕**，
而不是在判据里悄悄放宽 —— 后者会让亲验退化成「我认为对就是对」。我当时做的是后者。

### 补充复验 · R-2 免版本表唯一约束（起因：两个代理结论冲突）

后端 #1 报「`uq_ds_*=6`」，测试代理报「6 张表唯一约束只有 `id`」。**主线用实证判定**：

```sql
-- 唯一 INDEX 实查（6 张全有）
uq_ds_quote_material             (material_no)
uq_ds_quote_customer_part        (customer_no, customer_product_no)
uq_ds_quote_plating_scheme       (scheme_no, scheme_version, item_seq)
uq_ds_cost_basic_material        (production_no)
uq_ds_cost_detail_material       (production_no)
uq_ds_cost_detail_plating_scheme (scheme_no, scheme_version, item_seq)

-- 行为实证（事务内插重复后 ROLLBACK）
INSERT ... ('TEST-UQ-PROBE','探针1') → INSERT 0 1
INSERT ... ('TEST-UQ-PROBE','探针2') → ERROR: duplicate key value violates
                                        unique constraint "uq_ds_quote_material" ✅
```

**结论：约束存在且生效，测试代理误报。** 根因是它查 `pg_constraint`（唯一 CONSTRAINT），
而实现用的是 `CREATE UNIQUE INDEX` —— PG 里后者不进 `pg_constraint`，但拦重复的效果完全相同。
⇒ 已要求测试代理把判据改成「唯一 index ∪ 唯一 constraint」，或直接用行为实证。
