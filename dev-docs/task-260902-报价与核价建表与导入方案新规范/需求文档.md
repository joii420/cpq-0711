## ① 背景与目标

### 现状

报价与核价的基础数据今天**共用一批物理表**：

- 报价导入 `Q01~Q19` handler（`QuoteImportService`）、核价导入 `P01~P24` + `PricingSheetRegistry` 的 16 个「版本组」，
  **两条线都落在同一批 V6 表**（`material_master` / `material_bom_item` / `element_bom_item` / `unit_price` / `capacity` / `labor_rate` / `production_energy` / `tooling_cost` …），
  靠 `price_type` / `cost_type` / groupKey 区分归属。
- 这批表被 **107 个组件 SQL 视图** JOIN，是报价单 / 核价单渲染的取数真源。

### 问题

1. **口径纠缠**：报价的轴是「销售料号」、核价的轴是「生产料号」，却挤在同一批表里，字段是两侧需求的并集，改一侧要评估另一侧。
2. **粒度单一**：核价只有一套粒度。业务上存在「基础核价（10 类数据）」与「详细核价（19 类数据）」两种深度，现在只能用同一套表凑。
3. **升版规则散落**：版本组定义写死在 16 个 `PricingSheetDef` 里，与 handler 双写（`PricingSheetRegistry` 类注释自陈「改 handler 必须同步改这里，否则虚假升版 / 匹配错组」），
   而报价侧**根本没有统一的升版规则**。

### 目标

按用户给出的三份 Excel，建立**三套互相独立**的数据集，每套自带完整的建表规范、导入规范与版本化规范：

| 数据集 | 代号 | 来源 Excel | 轴 | 表前缀 | sheet | 主表 | `_history` |
|---|---|---|---|---|---|---|---|
| 报价数据 | `QUOTE` | `报价 - …xlsx` | 销售料号 | `ds_quote_` | 16 | 16 | 13 |
| 基础核价 | `COST_BASIC` | `核价2 - …xlsx` | 生产料号 | `ds_cost_basic_` | 10 | 10 | 9 |
| 详细核价 | `COST_DETAIL` | `核价1 - …xlsx` | 生产料号 | `ds_cost_detail_` | 19 | 19 | 17 |
| **合计** | | | | | **45** | **45** | **39** |

**新增 84 张表。** 三套之间无外键、无共享行、无相互引用。

### 不做会怎样

三份 Excel 是业务已经在用的口径。不落地，则新口径的数据只能继续手工塞进语义不匹配的旧表，
「基础/详细」两种核价深度无处安放，且报价侧的升版需求（用户第 4 条）**完全没有承载**。

## ③ 新规范定义（本任务的交付物本体）

### R-1 建表规则

**每个 sheet → 一张主表。** 表名 = 数据集前缀 + 语义后缀（见 `字段矩阵.md` 每节标题）。

**列的取舍由 Excel 表头底色决定**（闸门 A0 裁决）：

| 底色 | 语义 | 建字段 | 导入校验 |
|---|---|---|---|
| 🔴 红 `FFFF0000` | 必填 | ✅ | 非空 |
| ⚪ 白 / 无填充 `theme0` | 主数据 JOIN 展示列 | ❌ **不建** | — |
| 🟡 其余全部（黄 `FFFFFF00` / 橙 `FFFFC000` / 绿 `FF92D050` / 蓝 `FF00B0F0` / `theme4` / `theme7` / `theme9`） | 选填 | ✅ | 无 |

> ⚠️ **两条凌驾于底色之上的规则**（闸门 A0 裁决）：
> 1. **标了「轴」的列一律必填**，无论底色。年降类 3 张 sheet 与报价电镀方案的首列是橙底，但轴为空就无法归组。
> 2. **免版本表的主键列一律必填**，同理。

**每张主表统一追加系统列**：

```
id            bigserial primary key
source        varchar(16)   not null default 'IMPORT'   -- IMPORT | MANUAL
created_at    timestamptz   not null default now()
created_by    varchar(64)
updated_at    timestamptz
updated_by    varchar(64)
```

**带版本表额外追加**：

```
version_no      integer     not null                    -- 该轴值的当前版本，从 1 起
row_fingerprint char(64)    not null                    -- 见 R-3
```

### R-1.5 三套数据集之间的关联语义（2026-09-03 用户澄清，此前文档缺失）

> 🚩 **本节回答的是「三套表既然互相独立，业务上怎么串起来」** —— 这是设计意图，不是实现细节。

**关联链**：

```
ds_quote_material.material_no（销售料号，轴）
        └─ ds_quote_material.production_no（生产料号，🟡选填）
                 └─→ ds_cost_basic_material.production_no      ┐
                 或                                             ├ 二选一，不是两套都关
                 └─→ ds_cost_detail_material.production_no     ┘
```

**三条业务规则**：

1. **报价侧物料表自带生产料号列** —— 销售料号 → 生产料号的映射**就在 `ds_quote_material.production_no` 里**，
   跨数据集对齐直接用它，🚫 **不需要回头查 `material_master` / `material_customer_map` 等 V6 表**。
2. **用户按需关联基础核价或明细核价其中一套**，不是两套都关联。
   ⇒ 这正是三套表物理独立（D-1）的业务依据：它们不是同一份数据的三个视图，而是三条独立的数据线。
3. 🚩 **`production_no` 选填是设计如此，不是数据不全** ——
   **报价的时候生产料号可能还没确定**，它是后期维护的；且可以根据实际情况**修改关联的生产料号**。
   ⇒ 空值的业务含义是「**尚未关联核价数据**」，不是「数据缺失」。
   🚫 **不得把该列改为必填**，那会挡住「先报价、后定生产料号」这条真实业务流程。

> 📌 **一次被纠正的判断**：主线曾对「取值编辑器」会话说「新体系没有销售↔生产料号映射，必须保留一条通往 V6 的桥」，
> 并进而建议「把生产料号改成红底必填」。**两句都错**：映射本来就在 `ds_quote_material.production_no`；
> 选填是业务要求。根因是把「没有外键约束」错误推成了「没有映射数据」，又顺着对方"要跟核价侧对齐"的假设往下答，
> **没有先回头问「那个映射到底在不在新表里」**。

### R-1.6 料号类型列（D-26，2026-09-03 交付后变更）

> 🚩 **本节是交付后的模型变更**：类型从「BOM 行的属性」改为「料号的属性」。

**变更内容**：

| 数据集 | 移除 | 新增 |
|---|---|---|
| 报价 | `物料BOM` 的「**投入类型**」列（`input_type`） | `物料` sheet 加「**类型**」列（`material_type`） |
| 基础核价 | `物料BOM` 的「**组成类型**」列（`component_type`） | `物料` sheet 加「**类型**」列 |
| 详细核价 | 同基础核价 | 同上 |

**新列取值域**：`零件` / `外购件`

🚩 **这不是「移列」，是换概念** —— 实查确认两者取值域完全不同：

| | 旧列（BOM 行属性） | 新列（料号属性） |
|---|---|---|
| 回答 | 「这一行投入的是什么种类」 | 「这个料号本身是什么」 |
| 实测取值 | 报价 `元素` / `材料`；核价 `料件` / `材质` | `零件` / `外购件` |
| 粒度 | 每个 BOM 行可不同 | 一个料号只有一个 |

**用户裁决（2026-09-03）**：**旧语义确实不要了，直接删**。删除后 BOM 行不再区分「投入的是元素还是材料 / 料件还是材质」。

### 🚩 这一列的真正用途（2026-09-03 用户补充澄清，此前文档缺失）

**`material_type` 承载的是 V6 里 `material_bom_item.characteristic` 那套分类**，用来支撑**选配流程往新表落库**：

```
选配新建的「零件」    → ds_quote_material.material_type = '零件'
选配选的「外购件」    → ds_quote_material.material_type = '外购件'
零件的组成 BOM       → ds_quote_material_bom
```

⇒ **加这一列不只是「把类型换个位置」，而是为选配流程在新体系里落主数据打地基。**

**与 V6 `characteristic` 的对应关系**（用户口径）：

| V6 `material_bom_item.characteristic` | 新体系落点 | 维度 |
|---|---|---|
| `OUTSOURCED` | `ds_quote_material.material_type = '外购件'` | 料号身份 |
| `RECIPE` / `ASSEMBLY` | **`ds_quote_material_bom.output_material_type`**（原样保留，本次不删） | **BOM 行的投影** |

> 🚩 **2026-09-03 更正（由「选配功能」会话实证推翻上一版写法）**：本表原写「`RECIPE`/`ASSEMBLY` → `零件`」，
> **把两个不同维度压成了一个**。实测选配产出的 COMPOSITE 产品，**同一批父子关系会写两遍**——
> 一遍 `ASSEMBLY`（装配结构）、一遍 `RECIPE`（配方展开），服务于不同的组件视图：
> ```
> material_no = 0526-2609000003（COMPOSITE 产品）
>   子件 0526-2609000002 | ASSEMBLY | component_usage_type 空      ← 装配投影
>   子件 0526-2609000002 | RECIPE   | component_usage_type AgNi10  ← 配方投影
> ```
> 全库有 **4 个料号**同时存在 ASSEMBLY 与 RECIPE 两个投影（`3120011203` / `0526-2609000003` /
> `S-2120011658` / `S-3111320636`）。若压成料号级的「零件」，这 4 个各丢一半。
>
> ✅ **信息不丢的原因**：`ds_quote_material_bom.output_material_type` 的取值与 V6 `characteristic`
> **逐字相同**（实测 `out=ASSEMBLY|in=材料|37 行`、`out=RECIPE|in=元素|20 行`），且**它不在 D-26 的删除名单里**。
> 所以删 `input_type` 是安全的 —— 那一列只是 `output_material_type` 的中文同义列（两列在现有 58 行里 100% 共变）。

📌 **粒度发生了变化**：V6 的 `characteristic` 是 **BOM 行**的属性（同一料号在不同 BOM 行里可以是不同 characteristic），
新体系的 `material_type` 是**料号**的属性（一个料号只有一个类型）。这与 D-26「类型是料号的属性」的定位一致。

📌 **主线此前的误判**：我曾对「选配流程重构」会话回答「`characteristic` 在新体系完全不存在」——
那是基于当时的信息（`material_type` 尚未建、也无人说过两者对应）。用户澄清后已更正并通知对方。
**教训**：跨会话回答「新体系有没有 X」时，只能说「当前表结构里没有同名/同义列」，
不能推断成「这个业务概念在新体系里没有位置」—— 后者取决于设计意图，而设计意图在用户那里，不在表结构里。


**三处连带后果**（都已实查）：

1. 🚩 **指纹全部失效** —— 两列**都是比对项**。删列后所有现有行的 `row_fingerprint` 都会变
   ⇒ **下次导入时集体升一版**：`ds_quote_material_bom` 58 行 + `ds_cost_basic` 15 行 + `ds_cost_detail` 14 行。
   这是规范的既定行为（结构变了就该升版），不是缺陷，但要在交付说明里写清。
2. 🚫 **迁移不能改原文件** —— V405~V408 的 checksum **已锁死**（`success=true`，已应用到共享库 `cpq_db_0724`）。
   必须**新建 V409** 做 `ALTER TABLE`，改原文件会让所有人的服务 Flyway validate 失败。
3. **跨会话影响** —— `ds_quote_material` 的列集合变了，「产品管理优化」会话的销售产品列表直接读这张表；
   「取值编辑器」会话的语义图节点定义也要跟着改。**已分别通知**。

⚠️ **产品分类目前不参与模板匹配链路，本次也不接**：`TemplateService.matchCustomerQuoteTemplate(customerId, categoryId)`
的 `categoryId` 由**前端当场传入**（报价向导里用户自选），**不从料号推导**。
「料号分类」与「模板按分类匹配」当前是两条独立的线 —— 要不要打通是后续的独立决策，不在本次范围。

#### 🚩 默认值只能由导入器填，DB 列 `DEFAULT` 在本系统下无效

**这不是选择，是实证结论。** `PlainTableWriter:90-92` 构造的是**全列 INSERT**：

```sql
INSERT INTO ds_quote_material (<persistedColumns 全部> , source, created_by, created_at, ...)
VALUES (:p0_0, :p0_1, ...)              -- 每列显式绑参，空值绑 NULL
ON CONFLICT (material_no) DO UPDATE SET ...
```

每一列都被显式提供了值 ⇒ **PostgreSQL 的列 `DEFAULT` 永远不会触发**，空格子只会写成 `NULL`。

⇒ 「产品默认设置在默认分类中」**必须**实现为：Phase 1 解析时值为空则填 `000000`。
**AC-60 专门验这条**，防止实现者想当然地加 `DEFAULT '000000'` 交差。

#### 解析规则（Phase 1）

### R-3 行指纹

```
row_fingerprint = SHA-256( 各「对比项」列的规范化值，按建表字段顺序，用 0x1F 连接 )  → 64 位小写 hex
```

**规范化**（防虚假升版，这是本规范最容易做错的一处）：

| 类型 | 规范化 |
|---|---|
| NULL / 空串 / 纯空白 | 统一为**空**（三者同值，不区分） |
| 数值 | 转 `BigDecimal` 后 `stripTrailingZeros().toPlainString()` —— `1`、`1.0`、`1.00`、`1.000000` **同指纹** |
| 文本 | `trim()`，**保留大小写** |
| 布尔 | `true` / `false` |

⚠️ 只有标「对比项」的列参与。未标的建字段列（典型是「项次」）**存但不参与指纹** —— 改项次不升版。

### R-4 升版判定（以轴为单位）

对本次 Excel 中出现的**每一个轴值 `A`**：

```
S_db = 库中该表、轴值 = A、且属于当前版本的全部行
S_x  = 本次 Excel 中该表、轴值 = A 的全部行

若 A 在库中不存在                      → CREATED  ：整组以 version_no = 1 插入
若 |S_db| ≠ |S_x|                      → UPGRADED
否则若 指纹多重集(S_db) ≠ 指纹多重集(S_x) → UPGRADED   （多重集 = 不看行先后顺序，但计重复次数）
否则                                    → UNCHANGED：一行不动
```

**UPGRADED 的动作（同一事务内按序）**：

1. `S_db` 全部行整行复制进 `<表>_history`（含原 `version_no`、原 `row_fingerprint`）
2. 从主表删除 `S_db`
3. 以 `version_no = max(库中该轴值曾用过的版本号) + 1` 插入 `S_x` 全部行

> 📌 **版本号作用域 = （表, 轴值）**，不是全表一个号。同一张表里 A 料号可能在第 5 版、B 料号还在第 1 版。

### R-5 `_history` 表

- 结构 = 对应主表**全部列**（含 `id` 改名为 `origin_id`、`version_no`、`row_fingerprint`）+ 3 列归档信息：
  `archived_at timestamptz not null default now()` / `archived_by varchar(64)` / `archive_reason varchar(32)`（`IMPORT_UPGRADE` | `MANUAL_UPGRADE`）
- **只增不改不删**，保留全部历史版本。

### R-6 增量语义

**库里有、本次 Excel 里没出现的轴值：原封不动。** 不升版、不归档、不删除。
⇒ 单个料号补数据不会误伤全库；一份只含 3 个料号的 Excel 不会把另外 97 个料号清空。
