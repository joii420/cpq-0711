## Task 2 · 守卫 1：driver 组件维度审计（先于批量化落地）

**为什么先做**：这是防止 §4 缺陷复发的机制。**先有守卫，再有批量**——反过来就是在没有安全网的情况下改数据路径。

**改动**：新增一个维度解析器（建议 `com.cpq.quotation.service` 或 `priceadjust` 下，由架构评审定位置），输入 = driver 组件集合，输出 = 每个组件的批量安全级别：

| 视图 SQL 含 | 安全级别 | 批量行为 |
|---|---|---|
| 无任何维度占位符 | `GLOBAL` | 可跨全批共享 |
| 仅 `:priceBaseDate` | `PER_PRICE_BASE_DATE` | 按建单日分组 |
| `:quotationId` 或 `:lineItemId` | `PER_LINE_ITEM` | **强制逐项** + WARN 日志 |
| 解析失败 / 读不到视图 | `PER_LINE_ITEM` | **强制逐项** + WARN（保守兜底，绝不猜） |

**验收**：
- 单测覆盖 4 个分支（含"解析失败→逐项"）；
- 对当前库真实数据跑一次，输出必须是：`COMP-0049 → PER_PRICE_BASE_DATE`，其余 16 个 → `GLOBAL`，0 个 `PER_LINE_ITEM`；
- 人为在测试夹具里给某视图塞 `:quotationId` → 该组件必须落 `PER_LINE_ITEM`（门禁 5）。

## Task 3 · 方案 B：按 (模板, 取价基准日) 分组预渲染

**改动**：
1. `CardSnapshotService#refreshCostingCardValuesForLine` **新增重载**接受 `precomputed`；**原方法签名保留不动**（其他调用方零影响）。
2. `PriceAdjustJobExecutionService#executeJob`：循环**前**按 `(costingCardTemplateId, quotation.createdAt.toLocalDate())` 分组预渲染，结果 `Map<UUID, Map<String,ArrayNode>>` 传入各 `executeItem` → `upgrade()` → S5。
3. `MaterialVersionUpgradeService#upgrade` 增加可选 `precomputed` 入参（**默认 null = 现状行为**，dryRun/预算路径不受影响）。

**强制约束**：
- 分组内**断言 customerId 唯一**，不唯一直接抛错（不静默串号）；
- `:priceBaseDate` 的推导必须**与 `SqlViewExecutor#enrichPriceBaseDate` 同源**（`quotation.created_at` 的 `LocalDate`）。**不要另写一份日期口径**——两套口径是本项目反复出事的根因（AP-52 族）；
- 预渲染结果只读传递，不得跨 item 复用可变对象（沿用 2026-06-22 教训：不要把缓存对象按引用交出去）；
- 批次中途被 supersede（item 转 STALE）→ 丢弃对应预渲染结果，不写入。

**验收**：门禁 1 / 2 / 3 / 6 全过（4 个基准 job，含 `c2915208`）。

## Task 4 · 守卫 2：批量失败回退逐项

**改动**：预渲染抛异常时（任一组件 expand 失败），**不让整批 FAILED** —— 回退为逐项渲染，使 FAILED 精确落到出问题的那个 item。

**为什么必须有**：现状是 task-0729 debug（2026-08-03）刻意加的行为——单组件异常必须让该 item 可见地 FAILED，而不是"0 行 + 报 SUCCESS"。批量化不能把它退化成"一个组件挂 → 18 项全挂"。

**验收**：门禁 4 —— 注入一个必然失败的组件，断言只有相关 item FAILED、其余 SUCCESS，且 `costing_card_values` 与逐项路径一致。

## Task 5 · 方案 A：按组件维度分层批量（加强）

**目标**：让 render 成本不随建单日分组数增长。

**改动**：基于 Task 2 的安全级别，把 §④ 的组件展开拆成两层：
- `GLOBAL` 组件：整批跑一次；
- `PER_PRICE_BASE_DATE` 组件：按建单日分组跑；
- `PER_LINE_ITEM` 组件：逐项跑。

三层结果在 §⑤ 装配时按 lineItem 合并。

**风险提示**：这一步动的是 `BomTreeRenderService.renderInternal` 的内部结构（三大核心基线的只读侧）。**若评审认为改动面过大，可只交付 Task 3（方案 B）并把 Task 5 转二期**——B 已能达标且已验证。

**验收**：门禁 1~3 + 6 全过；并记录方案 A vs B 在 `c2915208`（6 组）上的耗时对比。
