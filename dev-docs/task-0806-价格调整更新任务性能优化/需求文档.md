## 1. 背景与目标

### 1.1 为什么做

价格调整审核通过后的「更新任务」逐项串行执行，用户实测感受为"非常慢"。实测四个真实 job：

| job | job_item 行数 | 其中**有核价模板** | 耗时 | 每项 |
|---|---|---|---|---|
| `06b54e9a` | 18 | 18 | 58.0s | 3.22s |
| `1b7208ab` | 17 | 17 | 36.7s | 2.16s |
| `6c0aebc8` | 29 | **22** | 60.6s | 2.09s |
| `c2915208` | 24 | **18** | 23.3s | 0.97s |

🔒 **两个数量口径必须分清**（2026-08-07 测试工程师审阅时发现本文档前一版混用，已更正）：

| 口径 | 含义 | 谁用它 |
|---|---|---|
| **job_item 行数** | `material_price_update_job_item` 的全部行 = 本批要升版的行 | 性能口径（§1.1 耗时按它折算）、job 状态汇总 |
| **有核价模板的行** | 其 `quotation.costing_card_template_id IS NOT NULL` 的子集 | **正确性口径**（§5.5 / `baseline.md` / 渲染批量化只影响这批） |

**差集（无核价模板的行）不进 `render()` 路径** —— `refreshCostingCardValuesForLine` 在 `costingCardTemplateId == null` 时直接 return。但它们**仍然走完整的 upgrade()**（S3 写回 / S5 报价侧 / S6 / S8 / S9），所以**必须断言它们逐字节不受影响**，不能因为"不进渲染路径"就不测（见 AC-3a）。

### 1.2 不做会怎样

更新任务耗时随批次线性增长；批量升版（几十张单）时用户需盯着进度抽屉等一分钟以上。且同一份计算在**预算阶段还要付一遍**（审核前对每个料号跑完整 `upgrade(dryRun=true)`），端到端体感是 2×。

### 1.3 做完达到什么状态

18 项 job **58s → 22~25s**，且**收益不随批次内报价单建单日分散而退化**。

**硬性前提：落库数据逐字节不变。** 本任务是纯性能优化，任何一项落库产物出现差异即判定失败，不接受"差异可解释"。

## 4. 功能需求（逐条编号）

- **FR-1** `PriceAdjustJobExecutionService#executeJob` 在逐项循环**之前**，按 `(costingCardTemplateId, 取价基准日)` 分组调用 `BomTreeRenderService.render()` 预渲染，结果按 `lineItemId` 分发给各 `executeItem` → `upgrade()` → S5。
- **FR-2** `CardSnapshotService#refreshCostingCardValuesForLine` 新增接受 `precomputed` 的重载；**原方法签名与行为保持不变**（其他调用方零影响）。
- **FR-3** `MaterialVersionUpgradeService#upgrade` 增加可选 `precomputed` 入参，**默认 `null` = 现状行为**（dryRun / 预算路径逐位不变）。
- **FR-4**（守卫 1）新增 driver 组件维度审计：扫描 `component_sql_view.sql_template`，按占位符判定批量安全级别，并据此决定该组件的批量粒度。判定表见 §5.2。
- **FR-5**（守卫 2）批量预渲染抛异常时**回退逐项渲染**，使 FAILED 精确落到出问题的单个 item，不得让整批 FAILED。
- **FR-6** 分组内**断言 `customerId` 唯一**，不唯一直接抛错（`render()` 的 `ctxCustomerId` 只取 `lineItems.get(0)`，跨客户会静默串号）。
- **FR-7** 预渲染结果跨 `REQUIRES_NEW` 事务只读传递；批次中途被 supersede（item 转 STALE）时丢弃对应结果，不写入。
- **FR-8**（方案 A）按 §5.2 的安全级别把组件展开分三层调度：`GLOBAL` 整批一次 / `PER_PRICE_BASE_DATE` 按建单日分组 / `PER_LINE_ITEM` 逐项；三层结果在装配阶段按 lineItem 合并。**只做分层调度，不改 render 内部计算算法。**
- **FR-9** S0 L3 口径守卫接入 `price_adjust_settings` 开关，默认关闭，可经 `PUT /price-adjust/settings` 即时生效不重启；**告警代码路径保留不删**。

## 5. 数据与规则

### 5.1 表 / 字段变更

| 表 | 变更 | Flyway |
|---|---|---|
| `price_adjust_settings` | 新增一列：S0 口径守卫开关（布尔，默认 `false`） | `V<下一个可用号>__price_adjust_settings_subtotal_guard_enabled.sql`。⚠️ 版本号在开工时现取（Flyway 历史是**全会话共享的移动靶**，见记忆 `cpq-shared-flyway-history-churn`），**不得提前占号** |

无其他 DDL。不新建表、不改视图。

### 5.2 批量安全级别判定表（守卫 1 的唯一口径）

| 组件视图 SQL 含 | 安全级别 | 批量行为 |
|---|---|---|
| 无任何维度占位符 | `GLOBAL` | 可跨全批共享 |
| 仅 `:priceBaseDate` | `PER_PRICE_BASE_DATE` | 按建单日分组 |
| `:quotationId` 或 `:lineItemId` | `PER_LINE_ITEM` | **强制逐项** + WARN 日志 |
| 解析失败 / 读不到视图 | `PER_LINE_ITEM` | **强制逐项** + WARN（保守兜底，**绝不猜**） |

**当前库实测基线**（守卫必须复现这个结果）：本模板 17 个 driver 组件中，`COMP-0049`（`$wl_ys_bom_view`）= `PER_PRICE_BASE_DATE`，其余 16 个 = `GLOBAL`，**全库 0 个 `PER_LINE_ITEM`**。

### 5.3 取价基准日的口径（唯一实现）

`:priceBaseDate` = `quotation.created_at` 的 `LocalDate`，来源 `SqlViewExecutor#enrichPriceBaseDate`。

🔒 **分组键的日期推导必须与它同源，不得另写一份。** 两套口径是本项目反复出事的根因（见 §8）。

### 5.4 现状耗时构成（优化前基线，实测）

## 6. 验收标准（逐条编号，必须可判定）★

- **AC-1** 四个基准 job 的每个 line item，改造前 vs 改造后 `costing_card_values` 的 **MD5 逐字节相同**，不一致数 = **0**。
- **AC-2** 基准 job 集合**必须包含 `c2915208-4327-4818-a9bf-05fdca905c6a`**（跨 6 个建单日的已知反例）。只跑 `06b54e9a` / `1b7208ab` 视为**未测**（见 §8 第 1 条）。
- **AC-3** 改造前后四项落库产物逐字节比对全等：`costing_card_values` / `quote_card_values` / `quotation_line_item.subtotal` / `quotation_price_revision` 三列快照。
- **AC-3a**（2026-08-07 补）**无核价模板的 item 必须完全不受影响**：`c2915208` 的 6 行、`6c0aebc8` 的 7 行（`quotation.costing_card_template_id IS NULL`）不进 `render()` 路径，但仍走完整 `upgrade()`。断言其 `quote_card_values` / `subtotal` / job_item 状态改造前后逐字节相同。
  > 为什么单列一条：这批行**恰恰因为"不进渲染路径"最容易被漏测**，而分组逻辑若把它们错误地纳入或排除（例如 `costingCardTemplateId` 为 null 时分组键退化成 `(null, 日期)` 把它们并成一组），故障会完全静默 —— 它们的核价侧本来就没有值可比。
- **AC-4** 注入一个必然失败的 driver 组件，断言：**只有相关 item 状态 = FAILED，其余 item = SUCCESS**，且其 `costing_card_values` 与逐项路径逐字节一致。
- **AC-5** 人为给某 driver 视图塞入 `:quotationId`，该组件的安全级别判定 = `PER_LINE_ITEM`，实际按逐项渲染，且产生 WARN 日志。
- **AC-6** 同一 job **连跑两次**，两次的全部 `costing_card_values` MD5 相同（防非确定性）。
- **AC-7** S0 开关：`true` 时行为与改造前**逐位一致**（含 `material_price_update_job_item.warn_code` 落库）；`false` 时不产生 `warn_code` 且单项耗时下降 ≥ 0.3s。
- **AC-8** 守卫 1 对当前库真实数据的判定输出 = §5.2 的实测基线（1 个 `PER_PRICE_BASE_DATE` + 16 个 `GLOBAL` + 0 个 `PER_LINE_ITEM`）。
- **AC-9** 原调用方零影响：`refreshCostingCardValuesForLine` 旧签名、`upgrade()` 的 `precomputed=null` 路径、预算 dryRun 路径三者行为逐位不变（各有一条回归用例）。
- **AC-10** 18 项 job 端到端实测耗时并**如实记录**。**本条不预设必须达标** —— 达不到 25s 就如实报数并说明天花板在哪，不修饰、不追加未验证的优化去凑数。

## 8. 已知坑位

1. 🚨 **「抽样 0 不一致」不是安全证明。**
   job `06b54e9a` 也跨 3 个建单日却 0 不一致 —— 因为那几天没跨过价格版本边界，`f_material_element_price` 返回了相同值。**若只跑它就宣布 PASS，D-3 那个会写坏 5 张单的缺陷会带着"已验证"标签进生产。** 说明问题的是**结构性事实 + 存在性反例**，不是样本通过率。AC-2 就是这条的强制体现。

2. **并行正确性必须用"连跑两次比对 MD5"验证**（2026-06-22 教训）：非确定性竞态单跑 / 单测看不到。AC-6 是这条的体现。

3. **`docs/反模式.md` AP-37**：新字段类型 / 同 componentId 多实例 cache 冲突 —— 缓存/共享结果的 key 必须穷举维度。

4. **`docs/反模式.md` AP-52**：全局变量绑定的"语义错配 + 契约不对齐"—— 同一语义禁止两套推导实现。

5. **记忆 `cpq-expand-layer-not-threadsafe`**：expand / 公式 / 快照求值层非线程安全，`expand()` 返回缓存可变对象引用。本任务传递预渲染结果时**只读传递，不得跨 item 复用可变对象**。

6. **记忆 `cpq-shared-flyway-history-churn`**：已应用到共享库的迁移禁改名改号；版本号是移动靶，开工时现取。

7. **记忆 `cpq-worktree-must-base-on-head-not-fresh`**：建 worktree 必须 `git worktree add <path> -b <branch> HEAD`，不能用默认 `fresh`（本地 master 领先 `origin/master` 近百个提交，fresh 会全丢）。

8. **记忆 `cpq-worktree-maven-test-tree`**：后端测试必须在 **worktree 的 `cpq-backend/`** 下跑，子代理 cd 主仓会测错树报假绿。

9. **探针纪律**：本任务的测量手法（临时只读端点 + MD5 比对 + 分相 SQL 计数）见 `test.md`；**探针一律临时、测后即删，不得进交付**。
