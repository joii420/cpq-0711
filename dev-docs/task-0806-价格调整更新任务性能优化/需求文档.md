## 2. 背景与目标

### 2.1 问题

价格调整审核通过后的「更新任务」逐项串行执行，用户实测感受为"非常慢"。实测：

| job | 项数 | 耗时 | 每项 |
|---|---|---|---|
| `06b54e9a` | 18 | 58.0s | 3.22s |
| `1b7208ab` | 17 | 36.7s | 2.16s |
| `6c0aebc8` | 29 | 60.6s | 2.09s |
| `c2915208` | 24 | 23.3s | 0.97s |

### 2.2 目标

18 项 job **58s → 22~25s**，且**收益不随批次内报价单建单日分散而退化**。

**硬性前提：落库数据逐字节不变。** 本任务是纯性能优化，任何一项落库产物出现差异即判定失败，不接受"差异可解释"。

### 2.3 明确不做（边界）

| 不做 | 理由 |
|---|---|
| **线程池 / 多线程并行** | 2026-06-22 已实证并 revert（`docs/RECORD.md` 警示条目 + 记忆 `cpq-expand-layer-not-threadsafe`）：同款设计（有界池 + 每 worker `@ActivateRequestContext`）速度达标 5.6x，但连跑两次 md5 不一致、**73 行中 9 行算错**。根因是 `ComponentDriverService.expand()` 直接 `return cached`，把进程级 Caffeine 缓存的可变对象按引用交给并发 worker。本链路写的是**价格**且落**不可逆凭据** `quotation_price_revision`，代价高于那次。 |
| 改 `buildCardValues` / `assembleTabsWithFormulaResults` | 属 `docs/三大核心模块基线.md` 锁定范围，风险等级不同。一期做完拿到新数据再评估。 |
| 预算（dryRun）阶段批量化 | 见 §6 二期登记。预算按 material 逐 review 计算，批量边界与 job 不同，需单独设计，收益未测。 |
| 报价侧 `buildCardValues`（0.28s/项，零 SQL） | 纯 CPU/JSON 组装，属上一条范围。 |

## 3. 现状测量基线（全部实测，非估算）

### 3.1 单项 3.22s 的构成

插桩实测（`upgrade()` 各阶段计时，经只读 dryRun 预算路径触发，测后已撤除）：

| 环节 | 占比 | 每项 | 18 项 | 性质 |
|---|---|---|---|---|
| 核价树 `BomTreeRenderService.render()` | **43.5%** | 1.40s | 25.2s | 17 条 `$view` SQL + Java 建树 |
| S0 L3 口径守卫 | **14.3%** | 0.46s | 8.3s | 用旧价重算整卡，纯 CPU |
| `buildCostingCardValues` | 11.3% | 0.36s | 6.5s | 纯 CPU |
| S5 报价侧 `buildCardValues` | 8.6% | 0.28s | 5.0s | 纯 CPU，**零 SQL** |
| S9 `updateCurrentPeriodRevision` | 3.8% | 0.12s | 2.2s | — |
| S1/S2/S3 写回 + 实体加载 + 每项事务 | 17.8% | 0.57s | 10.3s | — |

**结论：73% 在"重算卡片"，"改价格键"本身几乎不花时间。**

### 3.2 「有没有 N+1」——实测否定

在 `SqlViewExecutor.execute/executeAllRows` + `DataLoader.executeQuery` 三个执行点插桩，一次单项升版：

```
总计 17 条 SQL —— 每个 driver 组件恰好 1 条，零重复
最贵：$cpgd_view 272ms / $cpbl_view 140ms / $cn_view 138ms
BNF 老路径 executeQuery：0 次
合计 SQL 时间 1263ms（占 render 的 ~57%，其余 ~0.9s 是 Java 建树/建 JSON）
```

**没有 N+1**：17 个页签 = 17 条不同视图 SQL，SQL 文本各异、合并不了，属「N 个组件 N 条查询」。两道既有防线已挡住逐行查：
- `evaluatePath` 对叶子列已在 driver 行里的字段**短路取值**，不发 SQL；
- `$view` 字段路径在 `DataLoader.resultCache` 按 `path::partNo::customerId::lineItem::owner::quotationId` 去重，**不含 driverRow 维度** → 一个组件的所有行共用一条查询。

### 3.3 真正的浪费：跨 item 层面

`render(templateId, lineItems)` 本就是为整批设计的（§④ 注释：「这条 $view 对整单只跑一次」），但 `refreshCostingCardValuesForLine` 每次只传 `List.of(li)`：

| | SQL 条数 | 耗时 |
|---|---|---|
| 逐项 × 18 | **306** | 10910ms |
| 整批一次 | **17** | 847ms |

冷缓存对照实验（批量先跑）确认这不是缓存假象：批量先跑得 17 条，随后逐项阶段**仍新发 289 条**（= 306 − 17），证明逐项的缓存键确实按 line item 分裂。

## 4. ⚠️ 已实证的陷阱（方案设计的核心约束）

**不能按 job 整批渲染。** 这条是本任务最重要的结论，来自实测反例。

### 4.1 现象

对 job `c2915208`（24 张单，全部同一根料号 `S-3120014539`、同一客户、同一核价模板）做「逐项 vs 整批」的落库产物比对：

```
totalCompared=18  totalMismatch=5   ← 5 项 costing_card_values 不一致
5 项批量侧哈希全部相同(451119da)，逐项侧是两个不同值
```

### 4.2 根因（已定位到具体一行 SQL）

1. 逐项 render **是确定的**（连跑两次 A1==A2，18/18）——不是竞态，是**维度丢失**；
2. 差异只出在**一个组件**：`COMP-0049 物料与元素BOM` / `$wl_ys_bom_view`，其余 16 个组件逐字节相同；
3. 该视图含 `f_material_element_price(:customerCode, :priceBaseDate)`；
4. `SqlViewExecutor#enrichPriceBaseDate` → **`:priceBaseDate` = 报价单 `created_at` 的 LocalDate**；
5. `BomTreeRenderService.render()`（:145）用 **`lineItems.get(0).quotationId`** 设 `QuotationIdContext` → 整批时组长的建单日被套给全批；
6. 该 job 的 24 张单跨 **6 个建单日**（8/4/5/2/2/3）→ 5 张单拿到错误基准日下的元素单价。

> 讽刺但关键：出问题的正是**唯一那个接价格的视图**，而这是个价格调整任务。

### 4.3 全库审计（本模板 17 个 driver 组件）

| 组件 | 视图 | `:priceBaseDate` | `:quotationId` | `:lineItemId` |
|---|---|---|---|---|
| COMP-0049 | `wl_ys_bom_view` | ✅ 有 | ✗ | ✗ |
| 其余 16 个 | — | ✗ | ✗ | ✗ |

**当前全库无任何 driver 视图使用 `:quotationId` / `:lineItemId`。** 这是方案成立的前提，必须由代码守卫持续保证（见 §5.1 守卫 1）。

### 4.4 方法论结论（写进验收，不只这次用）

> **"抽样 0 不一致"不是安全证明。**

job `06b54e9a` 也跨 3 个建单日却 0 不一致——因为那 3 天之间没跨过价格版本边界，`f_material_element_price` 返回了相同值。**若只跑它就宣布 PASS，这个会写坏 5 张单的缺陷会带着"已验证"标签进生产。**

真正说明问题的是：**结构性事实**（`:priceBaseDate` 是真实维度）+ **存在性反例**（`c2915208`），不是样本通过率。

## 5. 优化方案

### 5.1 优化 1 · 核价树渲染批量化（主项）

#### 方案 B（打底，已实测验证）

**分组键 = `(costingCardTemplateId, quotation.createdAt.toLocalDate())`**

在 job 执行循环**之前**按该键分组渲染一次，结果按 `lineItemId` 分发给各 `executeItem` 的 S5。

实测（4 个真实 job，冷缓存，方案 B 先跑）：

| job | 项数 | 分组数 | 方案 B | 逐项 | 提速 | 正确性 |
|---|---|---|---|---|---|---|
| `c2915208` | 18 | **6** | 4495ms | 7579ms | 1.7x | ✅ 逐字节相同 |
| `06b54e9a` | 18 | 3 | 1867ms | 8158ms | 4.4x | ✅ |
| `1b7208ab` | 17 | 3 | 1880ms | 8790ms | 4.7x | ✅ |
| `6c0aebc8` | 22 | **6** | 3519ms | 8669ms | 2.5x | ✅ |

**方案 B 已在已知反例 `c2915208` 上验证通过（0 不一致）。**

> ⚠️ 表中"逐项"列是**热缓存值**（~450ms/项），真实 job 是冷缓存 ~2.1s/项，故表中提速倍数**偏保守**；方案 B 列是冷缓存实测，可信。

#### 方案 A（加强，消除退化）

方案 B 的弱点：收益随建单日分散而退化（6 组时只剩 1.7~2.5x；极端每单一日期则退化为逐项、零收益）。实测 4 个 job 有 2 个是 6 组，**日期分散是常态**。

**方案 A：按组件真实依赖维度分组** —— 16 个与报价单无关的组件整批跑一次，只有 `$wl_ys_bom_view` 按建单日重跑。

| | 每 job 的 SQL 时间 |
|---|---|
| 方案 B（6 组） | 6 × 1263ms ≈ 7.6s |
| 方案 A | 1209 + 6×54 ≈ **1.5s** |

A 的价值不是快 5 倍，而是**render 成本基本恒定，不随分组数增长**。

依据：唯一带日期维度的 `$wl_ys_bom_view` 只花 **54ms**，而贵的 `$cpgd_view`(272ms)/`$cpbl_view`(140ms)/`$cn_view`(138ms) 全部与报价单无关。

#### 两道强制守卫（缺一不可）

**守卫 1 · 维度审计兜底**
扫描本次批次涉及的 driver 组件的 `component_sql_view.sql_template`：
- 出现 `:quotationId` 或 `:lineItemId` → **该组件强制逐项渲染 + WARN 日志**，绝不静默共享；
- 出现 `:priceBaseDate` → 该组件按建单日分组（方案 A）/ 整批按建单日分组（方案 B）；
- **推导不出来就退回逐项**，绝不猜。

理由：正是"没审计维度"造成了 §4 的缺陷。守卫必须让未来新增占位符**自动降级到安全行为**，而不是继续共享。

**守卫 2 · 失败隔离不得退化**
现状：单组件 expand 抛异常 → `render()` 整体失败 → **只有该 item** 标 FAILED，其余照常（这是 task-0729 debug 2026-08-03 刻意加的行为，防"残缺数据冒充成功"）。

改批量后一个组件失败会**打死整批**，是净损失。**要求：批量渲染失败必须回退逐项**，让 FAILED 精确定位回单个 item。

#### 其他实现约束

- 预渲染结果类型 `Map<UUID, Map<String, ArrayNode>>`，纯 JsonNode 无 Hibernate 托管实体 → 跨 `REQUIRES_NEW` 事务传递安全（已确认）；
- `refreshCostingCardValuesForLine` **新增**接受 `precomputed` 的重载，**原单行入口保留不动**（其他调用方零影响）；
- 分组内必须**断言 customerId 唯一**，不唯一即抛错——`render()` 的 `ctxCustomerId` 只取 `lineItems.get(0)`，跨客户会静默串号。现状「一个 job 恒等于一个客户」已核实（`material_price_update_job.customer_no`），但**代码里没有任何东西保证它**；
- 预渲染发生在循环前，若批次中途被 supersede（STALE）需能丢弃，不得把已作废批次的结果写入。

#### 前置验证（已完成，结论记录在此）

**render 的输出不依赖 S3 写回** —— 4 个 line item，每个都确认 S3 真写了行（`snapshot_rows/row_data 共改写 2 行（COMP-0045=2）`，非空跑）：

```
deterministic = true      （同状态连跑两次哈希一致）
independentOfS3 = true    （S3 写回后再 render，哈希逐字节不变）
```

机理：`render()` 只查 `$view`（基础资料 / 元素价），S3 改的是报价单自己的 `snapshot_rows/row_data`，两者的**合并发生在下游 `buildCostingCardValues`**，不在 render 里。这条分界线正是"循环前预渲染"成立的依据。

### 5.2 优化 2 · S0 L3 口径守卫改可配开关

**现状**：每项花 0.46s（14.3%）用旧价重算整卡，只为与 `li.subtotal` 比一个数。

**事实**：
- 实测 **123 个 job item 中只响过 1 次**（0.8%，`warn_code='SUBTOTAL_MISMATCH'`）；
- 按 2026-08-06 那次改动**自己的注释**：方向3 T1 把 `li.subtotal` 收敛为单一来源后，守卫比较的两边"趋于恒等"，"代码还是拦截语义，但它已经拦不到东西了"。

**方案**：接入既有 `price_adjust_settings`（阈值已是同款可配项，`PriceAdjustSettingsService#getSubtotalGuardThreshold` 是现成范式），新增开关：
- 默认**关**；
- 可经 `PUT /price-adjust/settings` 即时打开，不重启服务（对齐验收 #70④ 既有口径）；
- **告警能力保留不删** —— 注释里「一旦它再次响起，就说明出现了新的双端算值分叉」仍成立，只是不再每次都跑。

⚠️ 这是**业务可见行为的变更**（侦测频率从 100% 降到 0%），不是纯技术优化。若评审认为侦测必须常开，本项可改为**抽样**（如每批次首项跑）或直接砍掉，收益相应减少 8.3s。

## 9. 附：本任务测量所用的实证方法（供复跑）

| 目的 | 手法 |
|---|---|
| 定位耗时分布 | `upgrade()` 各阶段 `System.nanoTime()` 插桩 → 写文件；用**只读 dryRun 预算路径** `POST /price-adjust/reviews/{id}/recompute-budget` 触发（事务 rollback-only，DB 无痕迹） |
| 数 SQL 条数 | `SqlViewExecutor.execute/executeAllRows` + `DataLoader.executeQuery` 三点插桩 + 相位 marker |
| 证批量等价性 | 临时只读端点：逐项 render vs 批量 render → 各自喂 `buildCostingCardValues` → 比对落库产物 MD5 |
| 排除缓存假象 | **把批量放在最前面跑**（冷缓存），观察随后逐项阶段是否仍新发查询 |
| 证不依赖 S3 | 同事务内 render → `upgrade(dryRun=true)`（S3 真写、事务内可见）→ 再 render，三次哈希对比；并检查 `rowsChanged>0` 确保 S3 非空跑 |

> 全部探针均为临时代码，测后即删；本任务实施期同样遵守：**探针不进交付**。
