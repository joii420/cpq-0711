## 2. 需求背景与目标 ⭐

**要解决什么问题 / 痛点**

「配置页签连表公式」抽屉（`TabJoinFormulaDrawer.tsx`，width 1100）当前是**纯上下堆叠**布局，从上到下依次为：试算条 → 公式表达式框 → 运算符/函数工具条 → 规则提示 → SUMIF 构造器 → 页签字段矩阵。由此带来四个具体不便：

1. **可选字段在最底部**，而公式框在最上方 —— 用户「看一眼有哪些字段 → 插进公式」要反复上下滚动，页签多时尤其明显。
2. **公式框只有 `min-height: 52px`**（约两行），稍长的公式就要在窄条里滚动，看不全。
3. **括号错配只有一句文字报错**（`checkParenBalance` 返回「缺少 N 个右括号」），看不出是**哪一对**出问题，长公式里定位靠人数。
4. 试算功能占据顶部约 60~200px（含结果表），实际使用价值低于它占的版面。

**本次要达成的目标**

- 抽屉改为**左右分栏**：左侧常驻「页签组件与可选字段」，右侧「公式配置」，两侧各自滚动，插字段不再需要滚动找。
- 公式框高度从 52px 提到 **min 170 / max 340**，并随内容自动增高。
- 括号**配对可视化**：按嵌套深度着色 + 光标处高亮同一对 + 未闭合标红，替代纯文字报错。
- 移除试算功能，腾出版面。
- 🆕 **左栏顶部加搜索框**（澄清 C2）：实测本库 `核价模板1` 有 **35 个页签**、`罗克韦尔模板3` 18 个，组件字段数平均 7 / 最多 19。仅靠左右分栏，左栏自身仍有约 5 屏高，"找页签"的滚动成本没被消除 —— 原型用少量页签演示，看不出此问题。
- 🆕 **抽屉宽度自适应**（澄清 C3）：`1520` 硬值 → `min(1520px, 92vw)`，避免 1366/1440 宽笔记本上溢出（原型只在 <1100px 处降级，1100~1520 是盲区）。
- 🆕 **顺手拆分抽屉文件**（澄清 C6）：`TabJoinFormulaDrawer.tsx` 现 925 行，本次还要加分栏/搜索/着色，就地堆叠易误伤无关逻辑（参照 AP-54 教训）。左右两栏各抽子组件，Drawer 只留状态与布局。

**不做什么（明确边界）**

- ❌ 不改公式语义、不改 token 序列化/反序列化（`formulaSerialize.ts` 的 `parseFormulaSegments` / `tokensToDrawerExpression` 等**只读复用**）。
- ❌ **不改后端（本期后端零代码改动，澄清 C4）**：2 个 dry-run 端点（`POST /components/{id}/dry-run`、`POST /components/{id}/dry-run-token`）**原样保留**，仅前端不再调用。
  > ⚠️ **事实纠正 F2**：原稿把「`TabJoinPlanEvaluator` 及 dry-run 端点」并列为试算配套，属误解。`TabJoinPlanEvaluator` 是 **Excel 视图正式渲染链路**的组件（`ExcelViewService.java:50` 注入，codegraph callers 实证），与试算无关，本来就动不得。真正会变成「无前端调用方」的只有上述 2 个端点。
- ❌ 不改 `[引用]` 块现有的 5 色语义（蓝/黄/绿/紫/红，见 §4.2.4）。
- ❌ 不改 SUMIF 构造器的**内部表单结构**（仅调整它在版面中的位置：右栏底部折叠）。
- ❌ 不引入第三方编辑器库（CodeMirror/Monaco 等）—— 现有 contentEditable 方案已够用。

## 4. 功能详述 ⭐

### 4.1 用户场景 / 操作流程

> ⚠️ **事实纠正 F1（入口）**：原稿写「模板管理 → 页签列 → 配置连表公式」，与代码不符。
> 本抽屉**全工程唯一入口是「组件管理」页** —— `ComponentManagement.tsx:1789` 针对当前选中组件的公式列表点「编辑 / 添加」时打开（文件放在 `pages/template/` 目录仅为历史遗留）。
> 且**同一抽屉服务 3 种组件类型**：`NORMAL`（页签组件）/ `EXCEL` / `SUBTOTAL`（小计组件），其中 EXCEL 类型下**没有** SUMIF 构造器区。**验收须三类各走一遍。**

配置人员在「组件管理 → 选中组件 → 公式列表 → 编辑/添加」打开抽屉，为某个列配置跨页签公式：

1. 打开抽屉 → **左栏**看到本目录所有页签组件及其可选字段（明细 / 小计列 / 页签总计），行键不可比的明细自动置灰；页签多时用左栏顶部搜索框直接过滤；
2. 点左栏字段 chip → token 插入**右栏**公式框光标处（左右并排，无需滚动）；
3. 在右栏用运算符 / 函数 / 条件聚合按钮补全表达式；公式框随内容变高；
4. 输入括号时实时看到配对着色；把光标停在某个括号上，与它配对的另一半同时高亮；漏了右括号则该括号标红波浪线；
5. 括号平衡后「保存」按钮可用 → 保存。

### 4.2 界面与交互（前端）· 逐条规格

> 编号对应用户提的 4 点。所有数值以原型为准。
> 原型路径：`dev-docs/task-0801-页签连表公式配置优化/原型-连表公式抽屉-v1.html`（可交互）

#### 4.2.1 左右分栏 + 加宽（第 1 点）

| 项 | 规格 |
|---|---|
| Drawer 宽度 | `1100` → **`min(1520px, 92vw)`**（澄清 C3；宽屏 ≥1654px 时等于原型的 1520，窄屏自动收到 92vw 永不溢出。antd `Drawer` 的 `width` 支持字符串 CSS 值） |
| 布局 | 抽屉 body 内两栏：**左 42% : 右 58%**（原型 `minmax(430px,42fr) / minmax(520px,58fr)`） |
| 滚动 | 两栏**各自独立滚动**（`overflow:auto`，`max-height` 约 78vh），不再整体滚 |
| 左栏内容 | 页签组件与可选字段（现 `TabFieldMatrix`），含标题「页签组件与可选字段 · 点击插入到右侧公式 · 行键不可比的明细置灰」 |
| 右栏内容 | 公式表达式框 → 图例 → 运算符/函数/条件聚合工具条 → 规则提示（黄）→ SUMIF 折叠区（顺序同原型，自上而下） |
| 分隔 | 左右栏之间 1px 分隔线 |

> ⚠️ **左栏内 `TabFieldMatrix` 需改内部排布**：现状是「左侧 160px 固定宽页签名列 + 右侧 chip 区」的**左右结构**，塞进 42%（≈600px）后 chip 区仅剩约 400px，长字段名会被挤成多行难读。原型改为**上下结构**：卡片头部放「页签名 + 行键徽标」，卡片体放 chip 换行。**这是本次真实改动点，不是纯外层布局调整。**

#### 4.2.2 移除试算（第 2 点）

- EXCEL 单值结果 `试算结果：xxx`

- 配套状态与函数：`sampleLi` / `dryRunValue` / `dryRunRows` / `dryRunErrors` / `dryRunLoading` / `runDryRun()`

**保留不动**：后端 dry-run 端点、`TabJoinPlanEvaluator` 及其测试。
**`SampleCardPicker.tsx`**：全工程仅此一处引用 → 随之成为死代码，**本次一并删除该文件**（避免留悬空组件；后续要恢复试算可从 git 历史取回）。

#### 4.2.3 公式框加高 + 自动扩张（第 3 点）

`FormulaRichInput` 的容器样式：

| 属性 | 现状 | 改为 |
|---|---|---|
| `minHeight` | `52` | **`170`** |
| `maxHeight` | 无 | **`340`** |
| `overflowY` | 无 | **`auto`**（超过 max 才滚） |

#### 4.2.4 括号配对着色（第 4 点）

**先明确不冲突的前提**：`[引用]` 块的底色**已承载合法性语义**，本次**不动**：

| 块颜色 | 含义 | 判定来源 |
|---|---|---|
| 蓝 | 普通跨页签明细引用 | `classifyRefSegment` 默认合法路径 |
| 黄 | 小计列 | 字段 ∈ `subtotalCols` |
| 绿 | 页签总计 `[X(总计)]` | `tab-total` |
| 紫 | 宿主自身字段 | `tabDef.self` |
| 红 | **非法**：页签/字段查不到、行键不可比、KSUM 内引宿主列 | 校验失败 |

**着色只作用于分组圆括号字符本身**，与块底色分属两个视觉通道（块 = 有边框底色方块，括号 = 无背景粗体字符）：

| 规格 | 内容 |
|---|---|
| 深度配色 | `(` `)` 按嵌套深度轮转 4 色并加粗（原型：`#d4820a` / `#7d3ac1` / `#0a9396` / `#c2185b`），第 5 层起循环 |
| 配对高亮 | 光标紧邻某括号（左侧或右侧）时，它与配对的另一半同时加黄底 `#fff3cd` |
| 错误标记 | 未闭合的 `(`、无匹配的 `)` → 红色 `#cf1322` + 波浪下划线 |
| 状态行 | 公式框右上角显示「● 括号匹配 / ● 括号不匹配」 |
| 图例 | 右栏公式框下方两行图例：第一行「块底色 = 引用语义」，第二行「括号字色 = 配对深度」 |

**保存按钮禁用逻辑不变**：仍由 `checkParenBalance` 决定（着色是可视化增强，不改校验口径）。

**🔑 括号可视化的两条通道必须分离（实现约定，AC-13/AC-12 成败所在）**：

| 通道 | 触发时机 | 实现方式 | 为什么必须这样 |
|---|---|---|---|
| **内容驱动**：深度着色 + 未闭合标红 | 表达式内容变化时（`renderInto` 重建 DOM） | 括号包进 `<span class="par pN" data-paren-idx="{raw串中的字符下标}">`，**不设** `contenteditable=false`（R3） | 内容变了才需要重算深度；设了 `contenteditable=false` 用户就删不掉括号 |
| **光标驱动**：配对黄底高亮 | 光标移动时（`selectionchange` / `keyup` / `click` / `focus`） | **绝不重建 DOM**，只 `querySelectorAll('[data-paren-idx]')` 找到配对的两个 span 改 `style.background` | 光标移动若触发 `innerHTML` 重建 → 中文输入法 composition 被打断（AC-13 失败）、光标丢失 |

#### 4.2.5 🆕 左栏字段搜索（澄清 C2 新增，原型未含）

| 项 | 规格 |
|---|---|
| 位置 | 左栏顶部常驻（在页签卡列表之上），`allowClear` 输入框 |
| 匹配范围 | **页签名（`componentName` / `alias`）与字段名同时匹配**，大小写不敏感、去首尾空格 |
| 过滤语义 | ① 命中**页签名** → 该卡**整卡保留**（所有 chip 都在）；② 仅命中**字段名** → 该卡保留、但**只显示命中的 chip**；③ 两者都不命中 → 整卡隐藏 |
| 「页签总计」chip | 情况 ② 下**始终保留**（它是整页签级引用，与字段名无关），避免搜出字段却丢了总计入口 |
| 空结果 | 显示「无匹配页签 / 字段」占位文案，不显示空白 |
| 置灰态 | 搜索**不改变**行键可比判定 —— 命中的不可比明细 chip 仍置灰不可点（AC-4 语义不受搜索影响） |
| 实现约束 | **纯前端 `filter`，不新增任何请求**；不改 `tabDefs` 原数组（只在渲染前过滤副本） |

**但原型有 3 处是「演示级简化」，实现时必须补齐**，否则会出现原型上看不出来的 bug：

| 风险 | 说明 | 必须的处理 |
|---|---|---|
| **R1 光标错位（高·已实证）** | `FormulaRichInput.restoreCaret` 遍历时假设「元素节点 = 引用块（带 `data-raw`）」，用 `getAttribute('data-raw') ?? ''` 计长度。新增的**括号 span 没有 `data-raw` → 长度按 0 计**，光标偏移算错。**原型里同样存在这个简化。**<br><br>**实证**（按现状算法逐节点模拟，公式 `SUM([投料.金额])`，DOM = `文本"SUM"` + `span"("` + `块[投料.金额]` + `span")"`）：<br>`offset=4`（应落在 `(` 之后、引用块之前）→ 现状算法返回 **「`)` 之前」**，即光标被放到整个块的**后面**。用户表现为：在 `(` 后打字，字符跑到块后面去。 | 二选一：① 给括号 span 也加 `data-raw`（值为该括号字符）；② 把 `restoreCaret` 改为**递归**下降到元素内部文本节点（`readBack` 本已递归，两者需对齐）。**推荐 ②**，语义更干净且不与 R3 打架。**AC-12 专门验它。** |
| **R2 括号扫描范围（高）** | 原型的括号扫描只跳过了 `[...]` 块，**没跳过 `{...}` 路径块**。而 `formulaBracketCheck.ts` 注释明确：`(总计)` 后缀总在 `[...]` 内、`{...}` 是路径块，二者内部的圆括号**都不是分组括号**。不跳过会误报错配。 | 着色用的扫描必须与 `checkParenBalance` **同口径**：遇 `[` 跳到 `]`、遇 `{` 跳到 `}`。建议把跳过逻辑从 `formulaBracketCheck.ts` 抽成共享函数，**一处维护、两处使用**（校验 + 着色），避免两套规则漂移。**AC-10 / AC-11 专门验它。** |
| **R3 括号 span 可编辑性（中）** | 引用块是 `contenteditable=false`（原子、不可进入）。括号 span **绝不能**照抄该属性，否则用户无法删除/编辑括号。 | 括号 span 不设 `contenteditable=false`，仅加 class 着色；退格删块的 `handleKeyDown` 需确认只对带 `data-raw` 的块生效（若 R1 选方案①给括号加了 `data-raw`，此处必须额外区分 —— 这正是推荐方案②的原因）。 |
| R4 重渲染性能（低） | 每次 `input` 全量重建 DOM，括号 span 使节点数增加。公式长度量级（百字符内）无实际影响。 | 不处理，观察即可。 |
| R5 窄屏（低） | 1520 在 1366 宽笔记本上会挤压。 | 原型已含 `@media (max-width:1100px)` 单栏降级，实现时保留（或按需改 `90vw`）。 |

### 11.3 技术方案要点（用户 2026-08-01 认可）

1. **括号可视化两通道分离**（内容驱动重建 / 光标驱动只改 style，绝不重建 DOM）—— 见 §4.2.4 表格。这是 AC-12 / AC-13 成败所在。
2. **括号扫描单一口径**：抽 `scanParens(expr)` 纯函数，`checkParenBalance` 与着色**同源消费**，杜绝两套规则漂移（AC-10 / AC-11）。
3. **`restoreCaret` 改递归的精确规则**：遇**有 `data-raw`** 的元素 → 按 raw 长度整体跳过（块是原子，不进入内部）；遇**无 `data-raw`** 的元素（新括号 span）→ 递归进入其文本节点按 `textContent` 长度计。**唯有这样才与 `readBack` 完全对齐**，这是 AC-12 的唯一正确解（R1 备选方案「给括号 span 也加 `data-raw`」已否决 —— 会与退格删块的 `handleKeyDown` 判定冲突，见 R3）。
4. **「清空表达式」按钮从左栏移到右栏**公式框标题行（它是公式区的操作，不属于字段面板）。
