# repair-0814 · 行键复选框写 driver 列名致口径污染（根因修复）

- **归属主任务**：`dev-docs/task-0801-页签连表公式配置优化/`
- **姊妹任务**：同目录 `repair-0814-行键中英口径混存致连表可比判定失真/`（`BL-0169`）—— 那条是**数据清理**（把已污染的 7 个组件洗干净），**本条是根因修复**（让污染不再产生）。两条合起来才闭环。
- **BACKLOG**：`BL-0170`
- **立项日期**：2026-08-14
- **用户裁决原文**：**「我勾选 销售料号 不需要为我写成 material_no，行键遵循规则与字段名称一致」**

---

## ① 问题描述

组件管理「字段配置 → 行键」列的复选框，**读写的是 driver 视图真实列名**（`resolvedColumn`），而 `row_key_fields` 按 `rule-0724/2-组件与字段.md §2.4 C3` 存的是**字段名**。两者命名空间不一致，导致：

1. 按规则配好的行键（如 `["销售料号","料号"]`），在 UI 上**一律显示为未勾选** —— 看起来像"没配"；
2. 一旦点勾（哪怕只是想确认配置正确），就**追加**一份英文列名（`销售料号` → 追加 `parent_no`），同一字段在行键里出现两次；
3. `computeFinalRowKeyFields` 的「锚定列保留」又让中文项**在 UI 上删不掉**。

用户视角即：「我 bundle 里明明只有中文字段名，导入生成的组件却多了 `material_no` / `parent_no` / `component_no`」。

---

## ② 复现 / 发现方式

- **发现人 / 方式**：用户 2026-08-13 首次反馈（`COMP-0232~0234`），2026-08-14 用新目录「核价模板2」导入 `COMP-0241~0244` 后**再次复发**，连续三轮追问「为什么 JSON 里只有中文，导入后多了 material_no」。
- **环境**：`10.177.152.12:5432/cpq_db_0724`；前端 `localhost:5174`；后端 `localhost:8081`。
- **可执行复现（已写成 spec：`cpq-frontend/e2e/rowkey-autopollute-probe.spec.ts`）**：
  1. 建临时目录，导入 `客户组件模板/核价组件/核价组件模板-简易.json`（其 `rowKeyFields` 为纯中文）；
  2. 组件管理打开导入出来的「物料BOM」；
  3. **阴性**：什么都不改直接点「保存」→ PUT 请求体 `rowKeyFields = ["销售料号","料号"]`，落库不变；
  4. **阳性**：点一下「行键」列**第一行（销售料号字段）**的复选框，再保存 → PUT 请求体变成 `["销售料号","料号","parent_no"]`，落库同步被污染。
- **触发条件的一般化描述**：只要组件的 `row_key_fields` 用字段名口径（= 全库 139/139 的现状），**任何人点任何一次行键复选框**都会追加一份列名。与是否导入、导入来源无关。

## ③ 需求结果

- **E-1（用户裁决）**：勾选「销售料号」字段，写入的就是 `"销售料号"`，**不得**替换成 `material_no` / `parent_no` 等 driver 列名。行键内容与**字段名**严格一致。
- **E-2**：已按字段名口径配好的行键，打开组件时复选框必须**正确显示为已勾选**（当前一律显示未勾选，是误导用户去点的直接原因）。
- **E-3**：取消勾选必须能真正取消 —— 不再出现「勾了删不掉」。
- **E-4（反向期望，不许放宽）**：`eligible` 判据**不放宽** —— 仍要求该字段能反查到 driver 列（`row-key-candidates` 端点判定）才允许作行键；无 driver 列支撑的字段仍禁用并给出原因。不能为了"能勾上"而让任意字段都可作行键。
- **E-5（存量兼容）**：库里若残留列名口径的历史项，保存时应被**自然清除**，但**不得误删**真正无字段代表的锚定项（「锚定列保留」机制的原意要守住）。
- **E-6**：不改动 `computeRowKey` / `comparable()` / 任何求值逻辑；行键的**语义与运行时行为零变化**（本次只改"写什么进去"和"怎么显示勾选态"）。
- **E-7**：留下自动化回归用例，防止再退化。

## ④ 问题原因 / 报告

### 4.1 根因

| 位置 | 现状 | 应然 |
|---|---|---|
| `FieldConfigTable.tsx:531-532` | `col = cand?.resolvedColumn`；`checked = rowKeyFields.includes(col)` —— 拿**列名**去**字段名**数组里找，恒 false | 按 `record.name` 判定 |
| `FieldConfigTable.tsx:541` | `onToggleRowKey(col, checked)` —— 写入**列名** | 写入 `record.name` |
| `ComponentManagement.tsx:1039-1049` | `preservedAnchors` = server 项里不在 `resolvedColumn` 集合的项 ⇒ 中文项永远被判为"锚定列"永久保留 | 锚定判据改为「不是当前字段名 **且** 不是任何候选的 `resolvedColumn`」，使历史列名残留可被自然清除 |
| `ComponentService.java:907-909` 注释 | 「rowKeyFields 引用的是 driverRow 的底层列」—— 2026-06-13 口径收敛**之前**的旧文本，与 `rule-0724 §2.4 C3` 相反 | 更正 + 加混用软告警 |

### 4.2 证据链（真实浏览器实测，非代码推断）

`e2e/rowkey-autopollute-probe.spec.ts` 一次运行同时给出阴性与阳性：

```
[PROBE] 导入后（保存前）rowKeyFields = ["销售料号","料号"]
[PROBE] PUT#0 rowKeyFields          = ["销售料号","料号"]      ← 阴性：只点保存，不追加
[PROBE] ✅ 未复现：只点保存不会追加
[PROBE·阳性对照] 勾选了字段: CLICKED（第一行 = 销售料号）
[PROBE·阳性对照] PUT#0 rowKeyFields = ["销售料号","料号","parent_no"]   ← 阳性：点一下就追加列名
[PROBE·阳性对照] 非字段名项 = ["parent_no"]
```

阳性对照证明探针有鉴别力（不是空验证）；阴性证明**导入链路与保存动作本身都是干净的**，污染唯一来自复选框写入口径。

补充排除（都已实测/查证）：
- `ComponentImportService:352-354` 对 `rowKeyFields` 是 `nodeToJson` 纯拷贝；`remapImportedRefsInDirectory` 不碰行键；
- 干净 bundle 导入 → 落库纯中文且 `created_at = updated_at`；
- 后端 `ComponentService.create/update` 纯透传，全工程无第二处写 `row_key_fields`；
- 前端 `setRowKeyFields` 仅 4 个写入点（加载 / 草稿恢复 / **复选框** / 草稿按钮），`FieldConfigTable` 内 `onToggleRowKey` 仅 `:541` 一处调用，无 `useEffect` 自动触发。

### 4.3 影响面

| 面 | 影响 |
|---|---|
| 配置体验 | 已配好的行键显示为未勾选 → 诱导用户去点 → 点了就污染（**这是主害**） |
| 连表公式 | 行键集合虚胖 → 跨页签「可比判定」`isSubset` 失真 → 本该可比的页签对被判不可比、明细置灰（姊妹任务 `BL-0169` 的现象） |
| 运行时求值 | 无 —— `computeRowKey` 4-arg 对两种口径都容错，故只是"脏"，不报错 |
| 波及范围 | 全库 139 个有行键的组件、任何人任何一次勾选；已实际发生 **2 次**（7 个组件） |

### 4.4 为什么测试没拦住

1. 现有单测覆盖的是 `computeFinalRowKeyFields` 的**锚定列保留语义**，不覆盖「写入的是列名还是字段名」；
2. `validateRowKeyConfig` 只校验「非空字符串」，混用两套命名空间完全合法通过；
3. 组件管理页无 E2E 覆盖行键勾选路径；
4. 症状是**静默的**（不报错、值不变、只是集合变脏），只有在跨页签公式置灰时才露头。

## ⑤ 修复方案（用户已裁决）

### 选定：复选框按字段名读写（方案 A）+ 后端软告警（方案 C）

**改动 1 · `FieldConfigTable.tsx`（行键列）**
- `checked` 改按 `record.name` 判定；
- `onToggleRowKey(record.name, checked)` 写字段名；
- `eligible` 判据**不动**（仍由 `row-key-candidates` 的 `resolvedColumn` 是否存在决定，E-4）；
- tooltip 文案改为同时显示字段名与其 driver 列（如「行键字段：销售料号 → driver 列 parent_no」），保留可诊断性；
- prop 名/注释同步（`onToggleRowKey(resolvedColumn…)` → `fieldName`）。

**改动 2 · `ComponentManagement.tsx#computeFinalRowKeyFields`**
- 锚定判据改为：server 项**既不是当前字段名、也不是任何候选的 `resolvedColumn`** 才保留；
- 效果：历史列名残留在下次保存时自然清除（E-5 前半），无字段代表的真锚定项仍保留（E-5 后半）。

**改动 3 · 后端 `ComponentService.validateRowKeyConfig`**
- 更正 `:907-909` 过期注释（改述为「字段名口径，见 rule-0724 §2.4 C3」）；
- 新增软告警（`LOG.warn`，**不阻断**）：同一组件的 `rowKeyFields` 若同时包含「是 fields[].name 的项」与「不是 fields[].name 的项」→ 提示疑似混用两套命名空间。哨兵 `["__seq_no__"]` 豁免。

**改动 4 · 回归用例**
- `e2e/rowkey-autopollute-probe.spec.ts` 转为正式回归：阴性（只保存不变）＋ **阳性反转**（勾选后写入的应是**字段名**，且不得出现任何非字段名项）。

**不做**：不动 `computeRowKey` / `comparable()` / `buildMatch` 等任何求值逻辑（E-6）；不放宽 `eligible`（E-4）；不动 PUBLISHED 冻结快照。

### 为什么选它

用户诉求即「所见即所存」：勾字段就存字段名。该口径与 `rule-0724 §2.4 C3`、与全库 139/139 组件现状完全一致，**存量零迁移**；且顺带修好 E-2（勾选态终于能正确显示），从源头消除"看起来没配→去点→被污染"的循环。

### 已知风险

- 触碰 `FieldConfigTable.tsx` / `ComponentManagement.tsx` 两个热点文件，影响全库 139 个组件的行键编辑 → 需回归（见 ⑥）；
- 存量若有"字段名恰等于 driver 列名"的组件（如英文字段名），行为不变（两种判定同解），无风险。

### 被否方案（各一句）

- **后端归一（收到列名转字段名）**：UI 勾选态显示仍是错的（勾了看不见），治标不治本；
- **保持列名口径、改 `rule-0724` 规则**：与全库 139 个组件、与 `computeRowKey` 二级解析主路径全部冲突，且跨口径集合永远不可比。
