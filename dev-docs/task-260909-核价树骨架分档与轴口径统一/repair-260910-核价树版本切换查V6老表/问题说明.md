## ③ 需求结果

> 🚦 **本节的业务规则由用户在 2026-09-10 立项对话中定死**（原 ①~④ 初稿按「每层切上级版本」写，已被推翻）。
> 用户原话：「**有自己 bom 的都可以切，bom 表 material_no 能查到的料号都是可以切换版本的**」
> 「**每一行都展示自己的版本而不是展示上级的版本**」「**从 _history 表中查所有历史版本 + 主表当前版本就是所有可以使用的版本**」

### 业务模型（先钉死语义，再谈实现）

BOM 表一行的含义是「**父件 X 的第 N 版清单里，包含子件 Y**」，版本号描述的是 **X 那张清单**。
⇒ 一个料号「有没有版本」取决于**它自己有没有一张清单**，与它挂在谁下面无关。

| 规则 | 内容 |
|---|---|
| **显示** | 每行显示**该料号自己那张 BOM** 的当前版本（`is_current=true`），🚫 **不是**上级那张清单的版本 |
| **可切判据** | 该料号在 BOM 表里**作为 `production_no`（老表口径 `material_no`）查得到** → 有自己的清单 → 可切；查不到（叶子）→ 无版本、不渲染下拉 |
| **候选来源** | `_history` 全部历史版本 **+** 主表当前版本；实现上即视图 `v_ds_cost_*_material_bom_all`（该视图定义正是这两张表 `UNION ALL`）中该 `production_no` 的所有 `version_no` |
| **切换效果** | 换该节点自己那张清单 → **它下面的组成整批跟着变** |

📌 **这条模型顺带消灭了一个歧义**：实测 `300015` 同时挂在 `300012`(v1) 和 `300001`(v2) 下。按「查自己作为父件的版本」，它的候选恒为 `[1]`（它自己那张清单只有 1 版），与挂在谁下面无关 ⇒ `repair-0590`「下拉给了料号它没有的版本」那类坑在本模型下不可能发生。

## ④ 问题原因 / 报告

### 一句话根因

`CostingVersionService#listVersionOptions` 的**树组件分支**把查询**硬编码**在 Java 里，仍查 V6 老表 `material_bom_item(system_type='PRICING', customer_no='_GLOBAL_')`；而正泰这批数据早已迁到 `ds_*` 新表，老表里一行都没有 ⇒ 候选集恒空。

### 出问题的代码（`CostingVersionService.java:105-120`）

```java
boolean tree = isTreeComponent(componentId);
String dsCostBase = tree ? null : dsCostBaseTableOf(componentId);   // ← 树被显式短路，拿不到 ds 表名

if (tree) {
    em.createNativeQuery(
        "SELECT bom_version, is_current FROM material_bom_item " +      // ← V6 老表
        "WHERE system_type='PRICING' AND customer_no='_GLOBAL_' AND material_no=:p " +
        "AND bom_version IS NOT NULL")
      .setParameter("p", partNo)...
} else if (dsCostBase != null) {
    // 非树组件：已适配 ds_cost_* 新表（主表 UNION _history），这一支是好的
}
```

### 证据链（可复跑）

**E-1 · 老表里没有这批料号**
```sql
SELECT p, (SELECT count(*) FROM material_bom_item m
           WHERE m.system_type='PRICING' AND m.customer_no='_GLOBAL_'
             AND m.material_no=p AND m.bom_version IS NOT NULL)
FROM unnest(ARRAY['300001','300012','300015','992','300013','991','300014']) p;
-- 实测：7 个料号 全部 0 行
```

**E-2 · 老表里存的是完全另一批数据**
```
customer_no=_GLOBAL_ / system_type=PRICING → 68 行 / 20 个料号
样本：2120011658, 3110520789, TEST0813-P01, VS-FG0 …（无一个 3000xx）
最后写入：2026-09-02 11:54:39
```

**E-3 · 新表里数据是齐的，且语义可直接对应**
```sql
SELECT component_no, production_no, version_no, is_current
FROM v_ds_cost_basic_material_bom_all WHERE component_no IN ('300012','300014');
-- 300012 | 300001 | 1 f / 2 f / 3 t     ⇒ 候选[3,2,1] 当前3
-- 300014 | 300001 | 1 f /     / 3 t     ⇒ 候选[3,1]   当前3（版本2里没有它）
SELECT DISTINCT production_no, version_no, is_current
FROM v_ds_cost_basic_material_bom_all WHERE production_no='300001';
-- 300001 | 1 f / 2 f / 3 t              ⇒ 根节点候选[3,2,1] 当前3
```
与截图显示的当前版本**逐字吻合**。视图 = `ds_cost_basic_material_bom` **UNION ALL** `..._history`，且**自带 `is_current` 列** ⇒ 与老表字段**一一对应，属同构替换**。

**E-4 · 两个数据集的视图都存在**：`v_ds_cost_basic_material_bom_all` / `v_ds_cost_detail_material_bom_all`

**E-5 · 骨架 SQL 已给出标准答案**（主任务 B-9 交付物，注释原文）：
> 递归体：`bom_version` 取【这条边所属 BOM 的版本】= `ch.version_no` …
> 锚点：`(SELECT bv.version_no FROM v_ds_cost_basic_material_bom_all bv WHERE bv.production_no = s.production_no …)`

⇒ **根按 `production_no` 查、非根按 `component_no` 查**，候选列表照抄这两个分支即可与显示值同源。

### 影响面

| 范围 | 判断 |
|---|---|
| **失效** | 所有以 `ds_*` 为源的核价树页签，版本**候选列表**恒空（不限于本单） |
| **未受影响** | ① `switchVersion` 切换动作本身 —— 它走 `bomTreeRenderService.render(...)`，用的是**已修好的骨架 SQL**，不查老表；② 非树组件（`dsCostBase != null` 分支）已适配新表；③ 报价侧 |
| **数据安全** | **零风险** —— 纯读路径，不写库；当前表现是「少给选项」不是「给错数据」 |
| **同类点** | 全工程另有 **9 处**硬编码 `FROM material_bom_item`（`BuilderService:659`、`SemanticCompiler:1640`、`QuotePendingRewriter:461/526`、`MaterialBomItemRepository:63/77`、`MaterialMasterRepository:364/401` 等），**是否同病需单独评估**，是否并入本次由闸门 A0 裁决 |
| **与并发会话** | `task-260909-V6老表退役` 的范围是 `costing_bom_tree_config.sql_template` 与视图定义，**未覆盖本处**（已核）⇒ 不撞车 |

### 为什么测试没拦住

1. **主任务 AC 未覆盖版本切换** —— `task-260909-核价树骨架` 的 22 条 AC 全部围绕「树能不能渲染出来」，**没有一条验版本下拉**（已实查：AC 正文里 `版本` 零命中）。任务范围是「骨架分档与轴口径」，版本候选被当成了不相干的功能。
2. **症状本身具有欺骗性** —— 树渲染正常、当前版本也正确显示，**看起来功能是好的**；只有点开下拉才暴露。任何「看渲染结果」型的验证都抓不到它。
3. **主任务亲验用的是 UI 截图比对**，比的是树结构与单元格值，未展开交互控件。

> 📌 **这条属于「同一根因第 2 次出现」**（`CLAUDE.md §4.3` BUG 判据表命中项）：主任务修的是**配置层**的老表引用，本次是**代码层**的同一件事。
> 教训候选：**「某张表停止接收新数据」这类迁移，必须同时枚举配置层与代码层两处引用面**，只改配置层会留下静默失效点。

## ⑤ 修复方案

> 🚦 **本节只写闸门 A0（2026-09-10）裁决通过的方案**。落地方式用户裁决为**甲**：主线直接改生效配置 + 记还原点。

### 改动 1 · 骨架 SQL 递归体的 `bom_version` 取值（**配置数据**，`costing_bom_tree_config.sql_template`）

递归体现状取 `ch.version_no`（= **父件那张清单**的版本），改成**照抄锚点已有的写法** —— 取「该节点**自己那张清单**的当前版本」：

```sql
-- 递归体，改后
(SELECT sv.version_no::text
   FROM v_ds_cost_basic_material_bom_all sv
  WHERE sv.production_no = ch.component_no
    AND :versionFilter(sv.is_current, sv.version_no::text, sv.production_no)
  LIMIT 1)                                     AS bom_version,
```

- 叶子节点该子查询自然返回 `NULL` ⇒ **E-2「叶子无版本」不需要额外判断**
- 与锚点（根节点）写法**语义统一**，两个分支从此同源
- 🚫 **不动** `WHERE :versionFilter(ch.is_current, ch.version_no::text, ch.production_no)` —— 那是**行过滤**，已按 `production_no` 分档且语义正确（切某料号的版本 = 换它那张清单，下级整批跟着变），本次不碰
- 📌 目标配置：`usage='COST_BASIC'` / `is_active=true` 那一条（`基础核价BOM树-COST_BASIC-v1`，主任务 2026-09-10 00:32 配入）。`COST_DETAIL` 库中**尚无配置**（主任务明示本期不配），将来配置时按本写法配

**落地纪律（方案甲）**：改前把 `sql_template` 原文与 `md5` 备份进 `证据/配置动作-还原点.md`；改后实测树渲染行数/层级/父子关系与改动前逐字一致。

### 改动 2 · `CostingVersionService#listVersionOptions` 树分支（后端）

```java
// 改前：硬编码 V6 老表，且 tree 被短路拿不到数据集
boolean tree = isTreeComponent(componentId);
String dsCostBase = tree ? null : dsCostBaseTableOf(componentId);
if (tree) { "... FROM material_bom_item WHERE system_type='PRICING' AND customer_no='_GLOBAL_' AND material_no=:p ..." }

// 改后：树分支也按数据集解析视图名，查「自己那张清单」的全部版本
//   COST_BASIC → v_ds_cost_basic_material_bom_all
//   COST_DETAIL→ v_ds_cost_detail_material_bom_all
"SELECT version_no::text, is_current FROM <按数据集解析的视图> WHERE production_no = :p AND version_no IS NOT NULL"
```

- 该视图定义本身即 `主表 UNION ALL _history` ⇒ **一条 SQL 拿全「历史版本 + 当前版本」**，符合用户口径，且 N+1 上与版本数/行数无关
- `is_current=true` 那条即 `isCurrentVersion`（override 缺失时的兜底当前版本），与老表 `is_current` 语义**一一对应**

### 改动 3 · 前端：叶子不渲染版本下拉

`ReadonlyProductCard` 渲染版本列时，`bom_version` 为空/`null` ⇒ 渲染占位（`—`），**不渲染 `VersionSelectDropdown`**。

### 改动 4 · `switchVersion` 叶子守卫（后端）

对「作为 `production_no` 查不到记录」的料号发起切换 → **400**，消息说明该料号没有自己的 BOM。防止绕过 UI 直调接口写出无意义的 override 行。

**影响面**：`PENDING` 43 单的版本列显示值会变（实测 7 行里 5 行，属**修正**）；已冻结 49 单（APPROVED/REJECTED/WITHDRAWN）读 `frozenDto` 快照，不受影响（AC 有实证条目）。**非协议级改动**：不新增 `field_type`、不改跨端 DTO 形状（改动 3 消费的是已有的 `bom_version` 字段）。

> **已否决备选**：
> - 「前端多传 `parentNo`，后端按父件查候选」 —— 业务模型改为「查自己那张清单」后**该参数不再需要**，且属跨端契约改动。
> - 「按子件料号（`component_no`）查候选」 —— 实测 `300015` 同挂 `300012`(v1) 与 `300001`(v2) 两个父件，按子件查会给出它自己清单里并不存在的版本，违反 `E-6`（`repair-0590` 前科）。
> - 「复用 `bomTreeRenderService` 跑整树反查父件」 —— 与 `task-260819 B-44④` 明确否决的「复用 LIST 模式」同类（笛卡尔积 + 随 `_history` 线性恶化）。
> - 「骨架 SQL 写成 Flyway 迁移」 —— 本项目配置类数据刻意不进迁移，且会与并发会话 `task-260909-V6老表退役` 争抢迁移版本号。
