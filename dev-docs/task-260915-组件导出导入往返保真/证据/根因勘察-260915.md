## 3. 代码链路（实读）

### 3.1 导出/导入**都正确传递** `tabType`，所以 null 是源库真值

```
ComponentExportService.java:68   item.tabType = c.tabType;
ComponentImportService.java:356  c.tabType = it.tabType;
```

### 3.2 树身份的双判据

`TabSemanticResolver`：

- **分支①**（新模型）：`component_sql_view.builder_config` → 三段坐标 `(tabType, variantKey, dialect)` → `semantic_tab_view` → `semantic == 'TREE'`
- **分支②**（存量回退）：`component.tab_type == 'BOM'`（`isLegacyTreeTabType`，`:141-143`）

`parseCoord`（`:293-315`）只读 `builder_config` 的**三个顶层字符串字段**：`tabType` / `variantKey` / `dialect`。**无任何 UUID 引用** ⇒ 跨库稳定。

### 3.3 判据不对称（本案直接成因）

| 调用点 | 方法 | 判据 |
|---|---|---|
| `ComponentService.java:793`（组件新建） | `assertTreeTokenGatesFor(component.id, …)` | **双判据** |
| `ComponentService.java:914`（组件更新） | `assertTreeTokenGatesFor(component.id, …)` | **双判据** |
| `ComponentImportService.java:477`（**导入**） | `assertTreeTokenGates(c.tabType, …)` | **仅分支②** |

导入端注释原文（`:473-476`）：

> task-260904 B-10/B-18：导入 bundle 不携带 builder_config/builder_version
> （见 ComponentExportBundle.SqlView 字段清单），导入建出的组件恒走分支②，
> 故这里用只按 tab_type 判的重载是**结构上正确**的，也避免在导入循环里逐个查库（N+1）。

⇒ 推理自洽，但它把「包丢数据」当成了既定前提。**根因在包丢数据，不在判据。**

## 5. 结论：根因链

```
源库 COMP-0002
  ├ component.tab_type = NULL                                   （新模型下的正常值）
  └ component_sql_view.builder_config->>'tabType' = 'BOM'        ← 树身份的唯一凭据
        │
        └ 配置期双判据 → isTreeTab=true → tree_ref 公式合法保存
                │
             【导出】ComponentExportBundle.SqlView 无 builderConfig 字段
                │        ⇒ 树身份的唯一凭据被丢弃
                ▼
             【导入】建出的 component_sql_view.builder_config = NULL
                │        ⇒ 分支① 永远不成立
                └ 导入端只用分支②（tab_type=='BOM'）→ NULL ≠ 'BOM' → 判定非树页签
                        │
                        └ 闸② 拦下 tree_ref → 400
```

**这不是特例**：任何「取数配置器建的树页签 + 用了父子取值公式」的组件，导出再导入 **100% 失败**。

**更大的一层**：8 个组件的 `builder_config` 全丢 ⇒ 即使绕过报错，导入后的组件在新库里**不再可用取数配置器编辑**，只剩死 SQL。
