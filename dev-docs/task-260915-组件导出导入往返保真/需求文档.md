## ① 背景与目标

### 起因

用户在另一台电脑上导出了一个组件目录的 JSON 包，在当前服务导入时报错：

> 组件「物料」(COMP-0002) 导入失败：公式「零件材料成本」使用了父子取值（tree_ref/tree_attr），该功能仅支持 tabType="BOM" 的树页签组件，当前组件 tabType=(未配置)。

### 根因（已定位，证据见 §④ 与 `证据/根因勘察-260915.md`）

这条报错只是症状。真实缺陷是：**组件导出包是按一份手工维护的字段清单拼装的，而这份清单漏了 8 个字段。**

导出端（`ComponentExportService`）、导入端（`ComponentImportService`）、契约 DTO（`ComponentExportBundle`）**各维护一份字段清单**，三份必须人工保持同步。给 `component` 表加一列时，漏改任何一处都**不报错、不告警、静默丢数据**。

本案中丢失的 `builder_config` 恰好是「这个页签是不是树」的唯一凭据：

- 取数配置器（builder）建的页签，其 `component.tab_type` 列**天然为 NULL**，树身份记在 `component_sql_view.builder_config` 的 `tabType` 字段里
- 导出包不带 `builder_config` ⇒ 导入后树身份丢失
- 导入端的校验又只认 `component.tab_type == 'BOM'`（单判据），而组件新建/更新走的是双判据（builder 语义 OR `tab_type`）
- 两处判据不一致 ⇒ **在源库合法保存的组件，导出再导入必然被自己的校验拒绝**

这个"手工清单必然漏"的模式**已经复发过**。导入端代码里留着上一次的补丁痕迹：

```java
// 恢复行键（导出端早期遗漏；多行可编辑组件缺行键会导致渲染撞键/editRows 塌缩）
```

`rowKeyFields` 是事后补进去的。本次是同一个故障族的第二轮。

### 目标

1. **补齐存量**：让导出→导入的产物与源目录**逐字段一致**
2. **根治复发**：让"下次给 `component` 加列忘了改导出/导入"这件事**在 CI 里变红**，而不是几个月后在另一台机器上表现为一句看不懂的报错

### 不做会怎样

- 跨机器/跨环境搬运组件配置这条路**不可用**：树页签组件导不进去，接价格策略的组件导进去也会被后端 400 硬拒
- 已经导入过的组件**静默残缺**：取数配置器打开是空的，只剩一段无法再编辑的死 SQL
- 下一次给 `component` 表加列时，**同样的缺陷会第三次发生**

### 🚫 明确不做什么

| 不做 | 去向 |
|---|---|
| **为用户手上这份 1.0 老包做一次性补救通道**（人工指定树身份 / 从 SQL 反推 builder_config） | 已否决 —— 用户确认源库那台电脑可用，修复上线后重新导出即可。做补救通道等于为一次性场景引入永久代码 |
| **导入时按目标库语义图重新编译 SQL** | 已否决（方案丙）—— 与现行「SQL 以包为准、原样搬运」的设计冲突；两库语义图有差异时会**静默改变视图取数结果**，比导入失败隐蔽得多 |

| **跨库语义图差异的自动修复/补种** | 不做 —— 预览如实报出，由用户决定。**已登记 `BL-0291`**（2026-09-15 用户裁决采纳） |
| **已导入组件的存量数据补救**（历史上已丢 `builder_config` 的组件） | 不做，**且不登记 Backlog**（2026-09-15 用户裁决不采纳）—— 当前库 103 个视图里仅 1 个缺 `builder_config`，且那一行 `builder_version` 同样为空（非 builder 产出的历史视图），并非丢失。重新导入即可解决，不需要专门的补救代码 |

### 单点 AC

**AC-1 · `builder_config` / `builder_version` 往返保真**
- 前置：以管理员打开组件管理，对目录 `取值配置器测试` 执行导出

  ```sql
  SELECT src.code FROM (…源目录…) src FULL JOIN (…新目录…) dst USING (code)
  WHERE src.builder_config::text IS DISTINCT FROM dst.builder_config::text
     OR src.builder_version IS DISTINCT FROM dst.builder_version;
  ```

**AC-2 · 元素价格三列往返保真**

**AC-5 · `component_sql_view.status` 往返保真**

**AC-12 · 预览报告新增配置器坐标可解析性**
- 操作：调用导入预览接口

**AC-13 · 导入不引入 N+1**
- 前置：构造两个包，分别含 **5 个**和 **10 个**组件（组件形态相同，只是个数不同）
- 操作：各导入一次，分别统计**树身份判定环节**发出的 SQL 条数
- 断言：两次的条数**完全相等**且 **≤ 2**（`TabSemanticResolver.isTreeTabBatch` 的既有承诺：固定 ≤2 条 SQL，与入参个数无关）
- 反向断言：改动前的实现在这一环节发出的条数为 **0**（旧代码不查库）—— 故本 AC 验的是"新增的查询没有随 N 增长"，不是"总 SQL 数不变"

### 序列 AC

**AC-14 · 二次往返幂等**
- 操作：源目录 → 导出包 A → 导入新目录 → 从新目录再导出包 B
- 断言：包 A 与包 B 的 `components` 数组（忽略 `id` 字段与 `exportedAt`）**逐字段相等**；两包 `checksum` 的计算输入一致
- 说明：这条锁死的是"导入没有悄悄规范化/丢弃某个字段"——单次往返比对源库可能被 DB 默认值掩盖

**AC-15 · 导入后配置器可继续编辑**
- 操作：导入后在取数配置器中打开新目录的某个 builder 组件 → 确认显示的配置与源库一致 → 不改动直接保存 → 再次打开
- 断言：① 打开时显示原有的节点/列/开关配置，**不是**空白或"未配置"；② 保存后 `component_sql_view.sql_template` 仍能正常执行（`EXPLAIN` 不报错）；③ 再次打开配置不丢失

### 边界 AC

**AC-16 · 空目录**
- 操作：导出一个 0 组件的目录，再导入
- 断言：导出包 `components` 为空数组（非 null），导入返回成功且创建 0 个组件，不抛异常

**AC-17 · 目标库语义图缺坐标**

- 断言：① 预览中该组件标记为 `UNRESOLVABLE`；② **导入仍然成功**（不阻断）；③ `builder_config` 原样落库（未被清空或改写）

**AC-18 · RENAME 冲突策略下字段仍保真**
