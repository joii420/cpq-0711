task-260907 · B-4 进度写入次数实测（2026-09-07，worktree 临时端口 8098，无 flyway 绕过参数）

判据：进度写入次数必须与 sheet 数（16）、行数（7381）无关。
     🚫 若是「每 sheet 写一次」，序列里应当出现全部 16 个 sheet 名。

── 方法一：pg_stat_user_tables.n_tup_upd 增量 ────────────────────────────
  拒收路径（Phase 1 就整份拒收，不进 Phase 2）  Δ=2   ← 与模型吻合：1 次「解析与校验中」+ 1 次 finalize
  小文件 5 行 / 16 sheet                        Δ=3, 4, 4
  大文件 7381 行 / 16 sheet                     Δ=3, 3

  ⚠️ 本方法【不可用于精确计数】，已自证伪：
     同一份大文件，方法二直接观测到 ≥3 个 progress 状态 + 1 次 finalize = ≥4 次 UPDATE，
     而 n_tup_upd 只报 3 ⇒ 它在少数。
     排查过「并发会话污染共享计数器」这个假设并【已证伪】：近 10 分钟 import_record
     的 8 条记录全部是本次实测产生的，无第三方写入。
     ⇒ 结论是 PG 的累计统计有刷新节流（PGSTAT_MIN_INTERVAL），8 秒静置仍可能未落账。
     ⇒ n_tup_upd 只能用来判「数量级」，不能用来判「精确条数」。

── 方法二：高频轮询 import_record.metadata，记录 distinct 状态序列（决定性）──
  大文件（7381 行 / 16 sheet）：
    t+0.23s  done=0  解析与校验中        ← Phase 1 前的固定写入
    t+0.65s  done=2  物料                ← 检查点：首个 sheet（index 0，桶号 0）
    t+1.67s  done=6  来料固定加工费      ← 静默超时兜底（index 4，桶号仍是 0，但距上次 >800ms）
    t+1.90s  SUCCESS + summary           ← finalize（metadata 被整体覆盖）

  小文件（5 行 / 16 sheet）：
    t+0.10s  done=2  物料
    t+0.18s  SUCCESS + summary
    （done=0 与末尾检查点因间隔 <100ms 被采样跳过，不代表没写）

── 结论 ────────────────────────────────────────────────────────────────
  ✅ 序列里只出现 3 个 sheet 之内的名字，🚫 没有出现「物料BOM / 物料与元素BOM /
     自制加工费 / …」等其余 13 个 —— 直接排除「每 sheet 写一次」。
  ✅ 双重判据两条分支都实测到真实触发：
       固定检查点  → index 0「物料」
       静默超时兜底 → index 4「来料固定加工费」（这条分支此前从未被证明过真的会跑）
  ✅ 写入次数上界 = 1(解析) + PROGRESS_CHECKPOINT_COUNT(2) + ⌈Phase2耗时/800ms⌉ + 1(finalize)
     —— 是【时间有界】，不是【N 有界】。7381 行时 Phase 2 仅 2.2s ⇒ 兜底最多 2~3 次。

  ⚠️ 仍未取得的：单次导入 progress 写入的【精确条数】。
     两种方法一个不准、一个会漏采样；要精确计数需要在 updateProgress 里加日志埋点，
     属改代码，本轮未做。
