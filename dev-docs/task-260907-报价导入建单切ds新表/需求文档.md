## 1. 背景与目标

### 1.1 现状：两个按钮，功能不对等

报价单管理页现有两个导入入口（`QuotationList.tsx:279` / `:291`）：

| | 「从基础数据导入」 | 「导入报价数据」 |
|---|---|---|
| 组件 | `QuoteBasicDataImportV6Drawer` | `DatasetImportDrawer`（`dataset="quote"`） |
| 端点 | `POST /basic-data-import/v6/quote` + `/quote/create-quotation` | `POST /api/cpq/dataset/quote/import` |
| 服务 | `basicdata/v6/quote/QuoteImportService` | `dataset/importer/DatasetImportService` |
| Excel | **17 sheet** 旧模板 | **16 sheet** 新模板 |
| 写入 | V6 表（`material_bom_item` / `unit_price` / …） | `ds_quote_*` 16 张 |
| 选客户 | ✅ Step 1 先选客户 | ❌ 无 `customerId` 参数 |
| 权限 | `SALES_REP` / `SALES_MANAGER` / `SYSTEM_ADMIN` | `PRICING_MANAGER` / `SYSTEM_ADMIN` |
| **建报价单** | ✅ 导数据 + 建单 + 建明细行 + 物化卡片值 | ❌ **纯灌数据**（该类中 `quotation` 字样 0 次） |

**本任务要补的就是最后一行。**

### 1.2 为什么现在做

- `task-260902` 建成 84 张新表与通用导入器后，报价侧交接说明明写「本期只导入不配维护页」「两条线并行」——**并行状态本就是过渡态**，不是终态
- `task-260819` 取数配置器已合 master，QUOTE 方言的 12 个语义节点全部指向 `ds_quote_*`，**新组件的取数出口已经在新表上**
- `task-260903` 已把选配写入侧切到 `ds_quote_*`，只剩导入这一条还写 V6
- ⇒ 导入是**最后一个仍在写 V6 的报价侧入口**。它不切，V6 就永远下不了线

### 1.3 不做会怎样

两套 Excel 模板、两套导入器、两套主数据表长期并存。新表体系的三个消费方（取数配置器、选配、产品管理页）拿到的数据永远只有选配写的那一小部分，导入的大头仍进 V6 —— **新表体系形同虚设，而维护成本双倍**。

### 1.4 目标（一句话）

**「导入报价数据」具备与「从基础数据导入」完全对等的建单能力，数据落 `ds_quote_*`；报价单在新表体系内完成「导入 → 建单 → 编辑 → 提交 → 核价通过 → 回填升版」全生命周期；旧入口下线。**

### 5.9 规则升级提议（本任务开发期实证，待结案时提交）

**① 「起服务前跑差集」这条规则，拦不住真正发生的那种形态。**

我在本任务里给所有子代理定了安全闸：*worktree 里起服务之前，先跑「master 迁移文件 vs 共享库 flyway 记录」的双向差集，非空就别起。*
后端代理照做了，也确实没起服务。**但它差一点还是把 `V423` 落进了共享库** ——

实际形态是：**服务已经在跑**（更早起的），它只是改了一个注释触发热重载。而 `quarkus.flyway.migrate-at-start=true` 在 dev 模式下重载即迁移。
🚨 **整条链路上没有任何环节会提醒它**：它没有"起服务"这个动作，所以安全闸根本不会被触发。

**为什么没炸是运气不是设计**：Quarkus dev 的热重载是**请求触发**的。它改完注释后只跑了独立进程的 `mvnw compile`，没有任何 HTTP 请求打进去，随即 kill 了服务 ⇒ 重载从未发生。
**只要当时有任何一个请求打进来（包括别人开着的浏览器），它就落库了。**

⇒ **建议把规则从「起服务前检查」改成「新建迁移文件的那一刻检查有没有服务在跑」**。
判据一句话：**危险的不是"起服务"这个动作，是"迁移文件与运行中的服务同时存在"这个状态。** 前者是事件，后者是状态；用事件去守状态必然漏。
落点建议：`docs/rules/git-worktree.md` 迁移纪律 / `docs/rules/backend.md`。

**② 判据落在一个恒成立的维度上时，它不是弱证据，是零证据。**

两个实证，同一天，两条会话各栽一次：
- **我**：给树闭包修法做「存量零回归」验证，全量 QUOTE 料号跑闭包 **35 行 vs 35 行逐行相同**。但缺陷只在"一个料号挂多个客户"时发作，而现网 `max(count DISTINCT customer_no) per material = 1`、**多客户料号 0 个** ⇒ 这个 diff **在现网数据下必然为空**，它证明的是「单客户下等价」，不是「多客户下等价」。
- **并发线**：要我验「89 段组件 SQL 的编译产物改动前后是否逐字节相同」。但那 89 段是按**视图名**文本引用该视图的，**改视图体不改任何 SQL 文本** ⇒ 逐字节相同是结构上保证的，与怎么改毫无关系。

⇒ **提出一条判据时，先问「它有没有可能为假」。答不上来就说明它不是判据。**
落点建议：`docs/rules/task-docs.md`（AC 编写规范）+ `docs/rules/testing.md`。

**③ 聚合函数给了数，但它按哪种序聚的，得先确认。**

`flyway_schema_history.version` 是 `varchar`。`max(version)` 走**字典序**返 `'9'`（因为 `'9' > '86'`），`max(version::numeric)` 才返 `86`。
子代理据此报了「临时库只到 V9」，结论对（V421 不是它落的）、依据错。**这类错最难发现，因为它给出的数字看起来完全正常。**
落点建议：`docs/方案制定前必读.md`。

🚫 **危险点不是冲突，是「没冲突」的那种情况**：
`test.md` 两侧行数都是 168、内容却不同（我的订正是行内 `<br>` 追加，不改行数）。
**只看 `wc -l` 会判成"相同"**；`需求文档.md` 是因为行数差了 36 才暴露。
⇒ 如果两边改的是不同段落，`git merge` 会**自动合并成功、不报任何冲突**，
而此时两份文档谁也不知道对方写过什么，**后续引用哪一份都可能引到半截事实**。

**规则建议**：**任务目录的文档只在一个地方改** —— 要么全在主仓（分支只放代码与证据），
要么全在 worktree（结案时随分支合并回去）。跨两地写同一份文档，迟早会出现
「A 会话在主仓写了裁决、B 会话在分支引用了没有该裁决的版本」。
落点建议：`docs/rules/git-worktree.md` 或 `docs/rules/task-docs.md`。

📌 **自查手法**（比 `wc -l` 可靠）：`diff <(主仓副本) <(worktree副本)`，或对每个文件取 `md5sum` 比对。

**⑤ 🚨 迁移的安全闸必须查 classpath，不能查源码树 —— 本任务实证，且是同一族的第三次。**

**事故经过**：`V423` 与并发线撞号、`D-39` 已裁决作废，用户执行 `rm` 删掉源文件。
我复查安全闸，报告「双空（孤儿 0 / 待落 0）」并据此解除 `-Dquarkus.flyway.migrate-at-start=false` 的权宜手段。
**那份复查是真实的，但它查错了对象** —— 后端代理随后跑 `mvnw test`，
Flyway 从 **`target/classes/db/migration/` 里没被清掉的编译产物**把 `V423` 应用进了共享库（09:31:05）。

实际扫描                  = target/classes/db/migration/

**影响面（实测非预测）**：任何 `target/` 里没有 `V423` 的进程启动即挂 ——

主仓 `target/` 就没有 ⇒ **8081 下次重启必挂**；并发线合他们自己的 `V423` 还会再撞一次 checksum。
另外它在共享库留下了**第二条 PRICE 边**，而 `FieldTreeBuilder`(4 处) / `BuilderService`(9 处) 的 `findFirst`

**规则修正（两条，缺一不可）**：
1. **差集口径改成查 `target/classes/db/migration/`**（Flyway 真正扫描的位置），或在跑之前先 `mvn clean`。
2. **删/改任何迁移文件之后，必须清编译产物** —— `mvn clean` 或 `rm -rf target/classes/db/migration/`。
   **只删源文件等于没删。**

📌 **为什么算同一族的第三次**：
① 我的树闭包「35 行 vs 35 行」—— 判据落在一个恒为 1 的维度上；
② 并发线的「89 段 SQL 编译产物逐字节相同」—— 判据恒真；
③ 本条 —— 查的是源文件在不在，不是 classpath 里有没有。
**三次都是「量具给了结果，但它量的不是你要的那个东西」，每次换一个伪装。**

它已把流程改成「先 `rm -rf target/classes/db/migration/` 再改号再重编」——**靠结构而不是靠记性**。
落点建议：`docs/rules/git-worktree.md` 迁移纪律 + `docs/rules/backend.md`。

**⑥ 同一条规则在同一小时内落空两次，形态完全不同 —— 「补一个洞不会让下一个洞更容易看见」。**

规则原文（`backtask.md`）：**迁移一落共享库，文件必须当即进 master**。今天它落空两次：

| | 形态 | 我当时的修法 | 对下一次是否有效 |
|---|---|---|---|
| **V423** | 文件被删了，**但编译产物还在** classpath 上，服务从残留把它落了库 | 把差集口径从「查源码树」改成「查 `target/classes/`」（§5.9 ⑤） | ❌ **完全无效** |
| **V424** | 文件写了、也落了库，**但没提交进 master** | —— | |

⇒ 并发线的原话，我照抄：**「你刚补完 classpath 那个洞，而这次漏的不是 classpath，是提交动作本身。补上一个洞不会让下一个洞变得更容易看见。」**

🔑 **这条的价值在于它否定了「再加一个检查项」这种修法**。
两次事故的检查项不同（一个是 classpath 差集、一个是 `git ls-tree`），
**逐个补检查项永远落后于形态的变化**，而且检查项越多越没人全跑。

**结构性修法**：把「落库」和「进 git」变成**同一个动作**——
迁移文件**在被任何服务加载之前**就先提交（而不是「落库之后记得提交」）。
落点建议：`docs/rules/git-worktree.md` 迁移纪律。
