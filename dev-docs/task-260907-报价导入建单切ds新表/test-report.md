## 8. 本轮沉淀的两条方法论

1. 🚨 **diff 类断言之前必须先断言 HTTP 200。**
   实证：session 过期时 14 个端点全返 401，`diff` 忠实报出 **14/14 全漂移** ——
   那会是一份「本任务把所有维护端点都搞坏了」的**假红报告**。已写进 `test.md` AC-15 行。
2. 🚨 **契约类断言必须查字段，不能查 body 子串。**
   实证：`errors[].value` 的检查原本写成 `body.contains(值)`。B-15 落地后错误 `reason` 里
   开始回显该值，断言于是**通过了，而 `value` 字段依然不存在** —— 一条完美的假绿。
   改成逐条目检查字段后立刻正确变红（4 条里 0 条带 `value`）。
3. 🚨 **「内容不变」类断言的量具必须排除 `id` 与审计列。**
   第一版指纹用了整行 `t::text`，必红 —— 免版本表走 DELETE+INSERT/UPDATE，`id` 会重排、
   `updated_at` 必然变，而 AC-12② 要的是「**值**必须一样」。
   **这是量具的问题，不是产品缺陷** —— 差一点就报成了 bug。

### 🔬 AC-8 排查全程：两个假设被推翻，根因是我自己的操作错误

**假设一（我的）**：`SqlViewExecutor.PATH_PATTERN` 的列名段是 `[a-z_][a-z0-9_]*`，裸中文列名 `元素单价` 过不了。

📌 佐证：`ComponentDriverService:480` 的既有注释白纸黑字写着「先把 `$view` 整行 merge 进 virtualRow，**绕开 `$view` 单列路径的 ASCII 校验**」——「中文列靠整行短路」是**被写进注释的既有设计约定**。

**假设二（并发线的）**：存量 `COMP-0242/0233/0302` 也用 `$wl_ys_bom_view.元素单价`，所以是既有缺陷。
🚫 **推翻**：那三个组件在**任何报价单里都没有行**（0 行）——**既没成功也没失败，证不出任何东西**。
⚠️ **差一步我就照它报了一个假的交付缺口。** 并发线随后自查，发现它补的「第二形态 `%`」那三个组件同样是 0 行，同一个毛病。

**真根因（后端代理定位，我独立复核）**：
```
COMP-2180  活表 sql_template 含价格列 = t   模板 sql_views_snapshot 含价格列 = f
COMP-0314  快照含价格列 = t   ← 它成功的唯一原因：发布时快照里就有
```
判别维度**不是「builder 视图 vs 命名视图」**，是「**模板发布之后有没有再改过这个视图**」。
