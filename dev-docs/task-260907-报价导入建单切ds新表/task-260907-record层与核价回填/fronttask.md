## 一、确认抽屉

### F-1 · 抽屉骨架与汇总条
**服务的 AC**：AC-5①
**原型**：`原型图/01-核价通过确认抽屉-默认态.html`
- 财务点「核价通过」→ 先调 `GET /{id}/costing-approve/preview`（`api.md` §1），拿到 `previewToken` 与 `dsBackfill`，**渲染抽屉，不直接提交**。
- 头部：标题 + 副标题（单号 / 客户 / 一句话说明确认后会发生什么）。
- 汇总条五项：涉及表 / 涉及料号组 / 将升版 / 无变更 / 无法对齐的行。**最后一项 > 0 时数字标红**。
- 🚫 **不许在打开抽屉之前就调 `costing-approve`** —— 预览是只读的，提交才写。

### F-2 · 逐表逐组比对表格
**服务的 AC**：AC-5②, AC-6, AC-10①
**原型**：`01-…默认态.html`（同版）+ `02-…跨版与无法对齐.html`（跨版）
- 按 `dsBackfill.tables[]` 分组渲染，每组一个小标题（页签中文名 + 表名 mono 灰字）。
- 每行一个「表 × 轴值」组，列固定为：销售料号 / **版本迁移** / 判定 / 整组行数 / 本次覆盖 / 本次不动 / 对不上 / 本次覆盖的列 / 原样保留的列。
- **版本迁移两种形态**（🔑 这是 `D-25` 的核心可见物）：
  - `crossVersion == false` → `v2 → v3` 两段
  - `crossVersion == true` → `快照 v1 → 库中 v2 → v3` **三段**，中间段用金色标签，让财务一眼看见「库里已经被别人改过」
- 表格横向超宽时在**表格自己的容器内**横向滚动（`overflow-x:auto`），🚫 页面主体不得出现横向滚动条。

### F-3 · 「本次不动」「无变更」「仅记录不写回」三处守卫
**服务的 AC**：AC-3①, AC-14①③
**原型**：`01-…默认态.html`、`03-…零变更与空态.html`
- 🚨 **`untouchedRows`（本次不动）列必须渲染，不许省、不许折叠。** 依据 `AP-60`：财务要能看见「这一组有 7 行本次不动」，否则「不写 = 删除」这类后果永远不在她的视野里。
- 🚨 **`result == "UNCHANGED"` 的组仍要列出**（`本次覆盖 = 0`），🚫 不许过滤 —— 否则分不清「这张表没变」和「这张表根本没被算进去」。
- 「仅记录、不写回基础数据的字段」区：渲染 `dsBackfill.extendColumnOnly[]`，逐条说明为什么不写回（公式列 / 自定义列）。
- 全部 `UNCHANGED` 时，顶部出绿色提示条「本单不会改动任何基础数据」，页脚说明文案随之改变。

### F-4 · 「对不上的行」明细区
**服务的 AC**：AC-20③
**原型**：`02-…跨版与无法对齐.html`、`04-…极值与错误态.html`
- `dsBackfill.summary.unanchoredRows > 0` 时：
  1. 顶部出**红色**告警条，写明「确认后这些行按新增写入，库里原有的行不会被删除」；
  2. 单独一个明细表列出每一行（页签 / 销售料号 / 项次 / 投入料号 / 关键值 / 原因），行底色 `#fff2f0`；
  3. **主按钮变红**（`btn-danger`）且文案改为「仍然确认并核价通过」；
  4. 页脚左侧显著提示条数。
- 🚫 **不许折叠进「更多」、不许只在 tooltip 里提**。

### F-5 · 空态与禁用态
**服务的 AC**：AC-15
**原型**：`03-…零变更与空态.html` 下半屏
- `dsBackfill.applicable == false`（老单）→ 渲染空态：图标 + 「本单不涉及新基础数据表的升版」+ 一行说明，🚫 不渲染比对表格区。
- 主按钮禁用时**必须可见 + hover tooltip 说明原因**（`frontend.md §1.2`），🚫 **禁止 `if (...) return null` 把按钮藏掉**。
  已知两种禁用原因文案：`当前登录角色不是财务或管理员，无权核价` / `比对结果已过期，请先点「重新预览」`。

### F-6 · 提交、取消与错误处理
**服务的 AC**：AC-7②, AC-18
**原型**：`04-…极值与错误态.html`
- 「确认并核价通过」→ `POST /{id}/costing-approve`，body 带**预览时拿到的 `previewToken` 原样回传**。
- **409**（`报价数据在预览后发生变化，请重新预览`）→ 抽屉内出红色错误条 + 「重新预览」按钮（重新调 preview 刷新本抽屉），🚫 不关抽屉、🚫 不用全局 `message` 一闪而过。
- **400 / 403** → 同样在抽屉内展示，文案取后端返回的原文。
- 「取消」→ 直接关抽屉，🚫 不发任何写请求（AC-7 断言「一个字节不落库」由此保证）。
- 提交中主按钮 `loading` 且禁用，防重复点击（AC-18 的前端侧防线；服务端仍有状态闸兜底）。

## 二、零改动项（写明「为什么不改」，`task-docs.md` §2 要求）

### F-7 · 报价单保存链路：**不改**
**服务的 AC**：AC-2（回归确认）
- **为什么不改**：`_record` 写入是**服务端内部行为**（`backtask.md` B-5 挂在 `saveDraft` 里），`api.md` §3 已明确 `saveDraft` 的请求 / 响应契约**一字不变**，前端无感知。
- **回归确认清单**（前端须实际点一遍，不是看代码推断）：
  1. 报价单编辑页保存 → 仍走 `added/modified/removed` 三数组 + `baseVersion`；
  2. 并发保存冲突 → 仍返 409 `StaleVersionException`，前端提示不变；
  3. autoSave 频率与耗时无肉眼可见劣化。
- **二期触发条件**：若后端因 `_record` 需要前端额外提供字段（当前判定不需要），则属契约变更，走 `task-docs.md` §4 四步。

### F-8 · 报价单列表页 / 核价工作台列表：**不改**
- **为什么不改**：本段不增删列表列、不增删工具栏动作，只改「核价通过」这个动作**点下去之后**的交互。列表页的 `enabledWhen` 逻辑与现状一致。
- **回归确认**：核价工作台的「核价通过」入口位置、可用条件、权限判定与改动前逐字相同。
