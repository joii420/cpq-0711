## 4 · AC-10 逐条

| 断言 | 结论 | 证据 |
|---|---|---|
| ① 确认界面显示「快照基版 / 库当前 / 将升到」 | ✅ | G単预览 `baseVersionNo=3, currentVersionNo=4, targetVersionNo=5`，财务看得见库里已变过 |
| ② **以主表当前版整组为基底做列级 patch，A 改过而 B 未表征的列在新版里仍是 A 的值** | ⚠️ **本用例证不到** | 见下 |
| ③ 前一版完整进 `_history`，可查回 A 那一版 | ✅ | `_history v4` 6 行齐全，`Ag/00006=55.5` = H単(A) 的值 |
| ④ B 不被拒绝、不报 409 | ✅ | `HTTP 200 / code=200` |

### 🚫 断言② 为什么在本用例上是**空验证**

G単 页签的 `columnScope` 实测：

```
patched:   material_no, material_part_no, item_seq, element_code, content_pct, loss_rate,
           gross_usage, gross_usage_unit, net_usage, net_usage_unit, recovery_discount, recovery_qty   （12 列 = 全部业务列）
preserved: []                                                                                          （0 列）
```

⇒ **「B 未表征的列」在本用例里根本不存在** ⇒ 该断言无论实现对错都成立。
这正是 AC 原文点名的陷阱：「🚫 不能只断言『B 写进去了』—— 后者在 A 的数据被整体覆盖之后照样成立」。

**前置**：需要一个**只暴露主表部分列**的窄页签 —— 与 **AC-13 的前置同源**（AC-13 原文：
「造一个只表征该组**部分行**的页签…且该页签只暴露主表的**部分列**」）。
⇒ AC-10② 与 AC-13 应当**用同一套自造夹具一起走**，不要分两次造。
