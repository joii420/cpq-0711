## ① 背景与目标

### 现状：报价单的数据只活在 JSON 里，回不到主数据

报价单保存时，页签行数据落 `quotation_line_component_data.snapshot_rows` / `row_data`（jsonb）。核价通过时由 `QuoteBackfillService` 把它反写回 V6 老表。这条老路有两个问题：

1. **数据源要换了**。第一段把导入建单整体切到 `ds_quote_*` 新表体系，新建的单不在 `QuotePendingRewriter.WHITELIST_TABLES` 里 ⇒ 老回填对新单**静默降级为 no-op**（第一段 `AC-16` 实证摘要恒 `0/0/0/0`）。**新链路目前没有回填能力。**
2. **从 jsonb 反写是本项目出过重大事故的形状**。`AP-60` / `repair-0727`：核价单 `HJ-20260726-0007` 通过后，`material_bom_item` 一个组从 4 行被"对齐"成 1 行且多列置 NULL，而财务在预览里看到的是「新增 0 / 删除 0 / 改值 0」。根因是把**页签渲染投影**当成了**该组的全部行**。

### 目标

给每张受回填的 `ds_quote_*` 表配一张 **`_record` 关系型表**，让报价单的数据以**与主表同构的形状**落地；核价通过时以「主表整组完整行为基底 + 页签列级 patch」的方式升版回主表，并由**财务人工确认**后才写。

### 不做会怎样

- 第一段交付后，**核价通过→回填升版这个能力在新链路上整体消失**，且**安静地不发生**（no-op 不报错）。实测该能力对存量单是活的：现网 13 单走过 `COSTING_APPROVED`，`unit_price` 26 行 / `material_bom_item` 17 行已由回填转正。
- 这也是 `D-24` 把 S-7 全库清空从第一段挪到本段的原因 —— 清空必须与回填同批上线，否则中间有一段窗口期「旧单没了、新单不回填」。

### 单点 AC

**AC-1（`_record` 表建成，且与主表同构）**
前置：迁移落库后。
断言：① 每张带版本的 `ds_quote_*` 主表都有且仅有一张同名 `_record` 表，判据 SQL 返回 **0 行**：
```sql
SELECT t.table_name FROM information_schema.tables t
WHERE t.table_schema='public' AND t.table_name LIKE 'ds\_quote\_%' AND t.table_name NOT LIKE '%\_history'
  AND t.table_name NOT LIKE '%\_record'
  AND EXISTS(SELECT 1 FROM information_schema.columns c
             WHERE c.table_name=t.table_name AND c.column_name='version_no')
  AND NOT EXISTS(SELECT 1 FROM information_schema.tables r
                 WHERE r.table_name = t.table_name || '_record');
```
② 每张 `_record` 的列 = 主表全部业务列 + `id` + `origin_id` + `quotation_id` + `base_version_no` + `extend_column` + 系统列，逐列**类型与可空性**与主表一致（`origin_id` 可空 —— 报价单里手工新增的行在主表没有对应行）；
③ 免版本三张表**没有** `_record`（同一判据 SQL 的反向：带 `version_no` 才要求有）；
④ 迁移 `success = true`（`flyway_schema_history` 查证）；
⑤ 启动期 `DatasetSchemaSelfCheck` 通过（后端能起来 = 通过，起不来即失败）。

**AC-2（保存时按变更产品增量写 `_record`）**
前置：一张走 `ds_quote_*` 新链路建出的报价单（DRAFT），含 ≥2 个产品卡片。
操作：只修改**第 1 个**产品卡片的物料BOM 页签某一行的一个数值列，保存（走 `added/modified/removed` 三数组协议 + `baseVersion`）。
断言：① 第 1 个产品的销售料号在 `ds_quote_material_bom_record` 中的行被更新；
② **第 2 个产品的 `_record` 行 `updated_at` 逐字未变**（增量语义，不是整单重写）；
③ `_record.base_version_no` = 拍快照时 `ds_quote_material_bom` 该轴值的 `version_no`。

**AC-3（`extend_column` 只留痕，不参与任何写主表的动作）**

② 主表**没有**新增列，也没有任何一列被这些值写入；
③ 这些值**不进 `row_fingerprint`** —— 只改自定义列再保存再通过，该组判定为 `UNCHANGED`，`version_no` 不变。

### 序列 AC（有状态的连续操作）

**AC-10（🔴 本段最重要一条：A、B 同引一个料号，B 后通过）**
前置：报价单 A、B 分别属于**同一客户**，都引用销售料号 `X`，都基于 `ds_quote_material_bom` 的 `v1` 拍了 `_record`。
操作：① A 核价通过并确认（`X` 升到 `v2`）→ ② B 核价通过。
断言：① B 的确认界面显示「快照基版 `v1` / 库当前 `v2` / 将升到 `v3`」——**必须让财务看见库里已经变过**；
② 财务确认后，B 的升版**以主表当前 `v2` 的整组行为基底**做列级 patch（🚫 不是回到 `v1`），⇒ **A 改过而 B 的页签没表征的列，在 `v3` 里仍是 A 的值**；
③ `v2` 完整进 `_history`，可查回 A 的那一版；
④ B 不被拒绝、不报 409。
> 🔑 **本条的判据形态**：断言②必须验「A 改过、B 未表征的列在 v3 里仍是 A 的值」，
> 🚫 **不能只断言「B 写进去了」** —— 后者在 A 的数据被整体覆盖之后**照样成立**
> （判据设计同型采自第一段 `AC-22` 与 `报价侧加客户维度` 的 `AC-2`）。

**AC-11（保存 → 提交 → 驳回 → 改 → 再提交 → 通过）**
操作：保存（写 `_record` v1 内容）→ 提交 → 财务驳回 → 销售改同一行的值 → 再保存 → 再提交 → 财务通过并确认。
断言：① `_record` 是**覆盖式**的，最终只有一份，内容 = 最后一次保存的值（`D-7`：`_record` 做报价单数据，`_history` 做版本记录）；
② 回填写进主表的是**最后一次**的值，不是第一次；
③ 中间态断言：驳回后、再提交前，主表 `version_no` 未变（驳回不触发回填）。

**AC-12（价格调整改价 → `_record.element_price` 与 `snapshot_rows` 不分叉）**
前置：一张含元素价格的报价单，状态取 `MaterialVersionUpgradeService.ACTIVE_STATUSES`（实测 `{DRAFT, SUBMITTED, APPROVED, REJECTED, COSTING_REJECTED}`，`MaterialVersionUpgradeService:124`）中的**每一种**各一张。
操作：跑一次价格调整升版作业。
断言：① 每张单的 `_record.element_price` 与其 `quotation_line_component_data.snapshot_rows` 里对应的元素价格字段**取值相同**；
② 被 `SKIPPED` 的单（状态不在 `ACTIVE_STATUSES`）两者**同时都不变**——不许出现「一个变了一个没变」。

② **行为半边** —— 
对**同一张存量老单**走核价通过，其回填摘要（`versionedGroups`/`addedRows`/`deletedRows`/`changedRows` 四个数字）改动前后相同。⚠️ 必须是**同一张单、同一时刻窗口内**的 A/B，🚫 不许拿历史记录的数字比。

**AC-16（反向 · 核价两套数据集不被波及）**
断言分两层（🚫 不许混成一条 md5）：
① **结构层严格**：两条路径的响应字段集、嵌套结构、HTTP 状态码与错误码，改动前后**逐字相同**；
② **数据层可归因**：落库结果的差异**必须逐条能归因到本次改动之外的原因**（别的会话写库 / 时间戳）。比对范围收窄到本次夹具自己写入的行，🚫 不许整表 md5。
③ **前置**：做任何 diff 之前**先断言 HTTP 状态码**（见本节末）。
> ⚠️ 本条与 `报价侧加客户维度` 的 `AC-6` 是同一个回归面（`VersionedGroupWriter` 三套共用）。已与该会话确认：其 `AC-6` 限定在「导入 + 维护端保存」两条路，**本段新增的核价通过写点不在其比对范围内**，两条 AC 不互相污染。

**AC-17（反向 · 选配链路不被波及）**
前置：一张由选配生成的报价单（`ConfigureProductService` 走 `task-260903` A 阶段的 `ds_quote_*` 写入）。
操作：改动前后各跑一次「选配建产品 → 打开报价单 → 提交 → 核价通过」。
断言：① `ConfigureProductService` / `SelDsQuoteWriter` 写入 `ds_quote_*` 的结果，**在本次夹具自己写入的行范围内**逐行相同（🚫 不许整表 md5）；
② 报价单详情页渲染出的页签数与每页签行数**改动前后相同**（🚫 不写「渲染正常」，写具体计数）；
③ 核价通过后该单状态 = `APPROVED`，且其涉及的料号组版本号增量**与改动前相同**。

**AC-20（边界 · 双锚的三条支路都要走到，且「锚不上」必须可见）**
> 依据闸门 A0-1 裁决（§⑥）。三支路各造一条用例，🚫 不许只验常见路径。
- **同版支路**：`_record.base_version_no` == 主表当前 `version_no` → 断言按 `origin_id` 对位，patch 落在正确的行上（改第 2 行的值，第 1/3 行逐字未变）。
- **跨版支路**：别的单先把该组升过版（`id` 已换）→ 断言改用 `base_row_fingerprint` 重锚成功，patch 仍落在**内容对应的那一行**上。前置须先实证 `id` 确已改变（对比升版前后主表 `id` 集合，交集为空）。
- **锚不上支路**：跨版且该行**同时被别的单改过值**（指纹已变）→ 断言：① 确认界面出现「对不上的行」明细区并列出该行，且**主按钮变红、文案为「仍然确认并核价通过」**（形态与 `原型图/02-核价通过确认抽屉-跨版与无法对齐.html` 一致；🚫 不许折叠进「更多」）；② 财务不确认时一个字节不落库；③ 财务确认后，该行按新增写入且**主表原行未被静默删除**。
> 🔑 断言③必须验「原行还在」，🚫 不能只验「新值写进去了」—— 后者在原行被删之后照样成立（同型判据见 AC-10）。

**AC-18（边界 · 并发两个财务同时点确认）**
操作：同一张报价单，两个财务会话同时点「确认」。
断言：只有一个成功；另一个得到明确错误（状态已不是 `SUBMITTED`），**不产生双份升版**（`version_no` 只 +1，`_history` 只多一份）。

### 🚨 本节所有比对类 AC 的两条共同纪律（2026-09-07 补，来自并发会话实证）

## ⑥ 闸门 A0 裁决结果（2026-09-07 已通过）

> 本节只记**裁决结果**，不记提案过程（`task-docs.md` §5 步骤 4）。

### A0-1 · `_record` 行与主表行的身份匹配 —— 裁决「**双锚：`origin_id` 为主 + 整行指纹兜底**」

`_record` 每行存两个锚：`origin_id`（拍快照时主表那一行的 `id`）+ `base_row_fingerprint`（拍快照时主表那一行的整行指纹）。回填时分三支：

| 情形 | 判据 | 处理 |
|---|---|---|
| **同版**（常见） | `_record.base_version_no` == 主表该组当前 `version_no` | 按 `origin_id` 精确对位，零歧义 |
| **跨版** | 不等（库里被别的单升过版，`id` 已全部失效） | 用 `base_row_fingerprint` 在主表当前组内重锚 |
| **锚不上** | 指纹也匹配不到 | 🚫 **不静默处理**。列入确认界面的「无法对齐」区，由财务整体确认或取消（`D-26`） |

**为什么不用业务键**（实测否决，留痕防后续会话重提）：13 张带版本表**不存在天然唯一的业务行键**。2026-09-07 实测：
- `ds_quote_material_bom` 的 `(material_no, item_seq)` **7 组重复**、`(material_no, input_material_no)` **5 组重复**
- `ds_quote_element_bom` 的 `(material_no, material_part_no, element_code)` **6 组重复**、`(material_no, item_seq)` **14 组重复**
- 存在**完全同键的重复行**：`VS-FG01` `item_seq=1` 的两行连 `input_material_no` 都是 `3120011203`
- `ds_quote_annual_discount` / `ds_quote_plating_fee` **连 `item_seq` 列都没有**

**为什么不用组内行序**：主表读出无 `ORDER BY` 保证，行数一变即整体错位，且错位后无法自我发现 —— 这正是 `AP-54` / `repair-0727` 反复出事的形状（写错行 / 删错行）。

**`origin_id` 为什么必须配兜底**（实测）：`VersionedGroupWriter` 的 UPGRADED 是「归档 → 整组 DELETE → 重新 INSERT」，**主表行 `id` 会变**。实证 `T260907-M1`：`_history` 里 `origin_id` = 3199 / 3200，主表当前行 `id` = 3201，⇒ 跨版后 `origin_id` **一个都对不上**。

### A0-3 · 确认界面的挂载 —— 裁决「**复用现有 `costingApprovePreview` + `previewToken` 机制**」

现有核价通过已是两步（`QuotationResource:602` 预览 → `:614` 带 token 提交，token 失效返 409「报价数据在预览后发生变化」）。新回填的逐表比对**塑进这个既有预览**，财务只看一个弹层、交互习惯不变，且 token 天然拦住「预览完数据又变了」。
🚫 已否决：新起一套独立预览 —— 会让核价通过入口出现两套预览，财务点一次看两个弹层。
