## 二、新提议

### 提议 1 · 「假绿」补两种形态，并归纳出判别它们的共同结构 🔴 推荐

第一段已沉淀三种（验了契约的一侧 / 验了恒真的东西 / 验了恒为空的样本）。本段撞出**两种新形态**：

- **形态④ · 判据对了，但观测对象错了**
  实证：守卫检查的库和被守卫的写入落的库**不是同一个**（`application-test.properties` 有**两个** datasource，只覆盖第一个 ⇒ 写在 laneb、读落 0724）。
  判据本身完全正确，两边各自也都工作正常，**合起来什么都没验**。

- **形态⑤ · 判据没问题，但它赖以成立的现象消失了**
  实证：`AC-17③` 的阳性对照，是靠 `D-45` 那个 bug **存在**才成立的。D-45 一修，对照样本变空 ⇒ 用例从「有效」滑到「恒真」，**而且是绿的**。
  🔑 **这类失效由「修好了一个 bug」触发** —— 没有任何 diff 会碰到那个用例。

**共同结构（这才是提议的核心）**：一次验证由**四**件事组成 ——
> **判据** · **判据所在的层** · **观测对象** · **执行到底跑到哪一步**

四者任一错位，产出的都是**一个看起来完全正常的结果**。
第一段的三种全是「判据」维度，本段的④是「观测对象」、⑤是「判据的前提」，
第二维「**判据所在的层**」由并发会话 `优化组件管理` 补上（2026-09-08，两个实证）：

- 拿带 `dialect='QUOTE'` 过滤的 diff 去证**核价侧**改动的灵敏度 ⇒ **永远空 diff**。判据对、观测对象也对，错在**那一层根本收不到核价侧的改动**
- 拿 `order by ctid` 的存储层错位量具，去验一个「**在 Java 侧加序、不重排堆**」的修法 ⇒ 修完仍是 11 行

🚨 **第二个例子要单独标出来，它比其余几种都贵**：
前面几种假绿的代价是「**漏掉一个真缺陷**」；这一种给出的是「**修复无效**」这个**反向结论** ——
它会让人回头把**对的改动改掉**。

配套两个已实证的推论：
- **证伪实验本身也要验明正身** —— 测试线设计的证伪（换卡片顺序）被守卫 ③ **在到达主断言之前**拦下了 ⇒ 红了，但**不是为了要验的那条红**。「证伪能让它红」不等于「证伪打到了主断言」。
- **判据指向不存在的东西 ⇒ 恒红**，和恒绿一样是零信息，只是伪装成「发现问题了」。

**落点**：`docs/rules/testing.md`（假绿清单）+ `docs/rules/task-docs.md`（AC 编写规范：提出判据时先答「它有没有可能为假」，本段追加「它观测的是不是我要动的那个对象」「它的前提会不会被修复本身抹掉」）。

### 提议 2 · 共享资源要**判身份**，不是**判存活** 🔴 推荐

三处实证，同一个根：

1. **读了一个跑旧代码的实例的数** —— 8099 最后一次热重载 `00:08:44`，早于 D-43 提交 `00:10:03`。症状长得像一个缺陷（「审批返 200 但主表没变」），我差点当缺陷报。
2. **重启了别人正在用的共享 8081** —— 并发线 06:20 起的、正在做他们的闸门 B。我看到端口活着、以为是我自己起的。他们环境没坏是**运气**（我的改动恰好全是加法式的）。
3. **单次采样下结论** —— 我判 8102「已死（000）」，复采三次全是 401，PID 从未重启。`CLAUDE.md` §5 已写「『当前无 X』是瞬时量」。

⇒ **提议**：共享端口/共享库的使用前置从「探活」升级为**三问**：
> ① 它**在跑吗** ② 它跑的是**哪个 commit / 哪个库** ③ 它是**谁**起的

并补一条对称义务（并发线提的，比我的原提议完整）：**起共享端口前也要广播**，不只是重启前。
「我是第一个开门的人」不等于「屋里没人」。

**落点**：`docs/rules/git-worktree.md`（worktree 共享约束）+ `CLAUDE.md` §1 的启动自检段（自检命令旁加一行「同时报出该实例的 commit」）。

### 提议 5 · 文本判据要问「出现在**哪一子句**」，不是「出不出现」 🟡 建议

两次实证，都在同一天、同一条 `BL-0229` 上：

- 我用「SQL 里含不含 `customer_no = :customerCode`」清点 → 得出「4 个已经有了」。**四个全是写在 `LEFT JOIN` 上的**，一个都不算数，且其中 **3 个正是实际出故障的组件**。
  ⚠️ 并发线在几小时前**明确警告过**我这个三态区分，我还把它写进了 `BL-0229` 原文 —— **然后自己踩了一遍**。
- 我用 `FROM\s+(ds_quote_\w+)` 定「外层主表」→ 它先匹到了 `WHERE` 里的 `NARROW` 桥子查询，把 3 个 `COST_BASIC` 视图归错了主表。
  🚨 **这个错判碰巧指对了地方**（那个子查询确实要改）—— 比明显的错更危险，因为它自洽。

⇒ **提议**：对 SQL / 代码做**结构性判断**（「这个谓词在不在主表的 `WHERE` 上」「这个调用在不在事务里」）时，

正则只能用来**缩小候选集**，不能用来**下判断**。

**落点**：`CLAUDE.md` §5（已有「grep 结果为空 ≠ 不存在」三个成因，本条是它的对偶：**grep 结果非空 ≠ 命中了你以为的那个位置**）。

### 提议 8 · 「无 `ORDER BY` 的 `listAll()` + 下游 `findFirst` / `groupingBy`」= 数据一改就静默换语义 🔴 推荐

**来源**：并发会话 `优化组件管理` 2026-09-08 实证，非本任务发现，但形态值得进规则。

三层链：`SemanticGraphLoader:81` 的 `SemanticNodeColumn.listAll()` 无 `ORDER BY`
→ `SemanticGraphSnapshot:65` 的 `groupingBy` 也不排序
→ 下游按 **PG 堆顺序**遍历字段。

⇒ **任何 `UPDATE semantic_node_column` 都会重排该节点的字段顺序**（MVCC 把行的新版本挪到别的页）。
实证：`V433` 只改了 11 行 `roles`，让 11 个核价数据源的字段面板顺序全乱。

🔑 **值得进规则的不是这个 bug，是它的形态**：
> **改的是 A，坏的是 B，中间没有任何报错，而且能被发现纯属侥幸** —— 只因为那个返修任务的 `AC-R1` 恰好在验字段顺序。

它和本段那七个缺陷同族（**没有任何机制会主动告诉你它坏了**），
区别是本段那七个至少还有人在看（主线在逐条亲验），这一个**连看的人都是碰巧**。

⇒ **提议**：写法级硬规则，不依赖业务判断 ——
**「查询结果的顺序会被下游消费」时（`findFirst` / `groupingBy` / 按下标取 / 直接渲染成列表），
查询侧必须显式 `ORDER BY`。** 🚫 不得依赖插入顺序、主键顺序或堆顺序。

**落点**：`docs/rules/backend.md` —— 和那里已有的 **N+1 硬指标**并列。
两者同类：**看写法就能判违规，不需要理解业务**，因而可以进 PR 自检清单。

### 提议 9 · `git checkout -- <path>` 应进 §3.2「历史销毁」清单 🔴 推荐

**实证（2026-09-08，测试代理自查出来并主动上报）**：
做完证伪注入后要还原生产文件，用了 `git checkout -- <测试文件>` ——
**把自己尚未提交的整份实现一起冲掉了**。靠重放脚本 + 与预存绿版本 md5 逐字节核对才复原。

🔑 **一句话**：
> `git checkout -- <path>` 不是「撤销我刚才那次注入」，是「**回到 HEAD**」。
> 在**未提交的工作区**里，这两者差的是**一整份实现**。

**为什么现在的 §3.2 拦不住**：
「历史销毁」列的是 `git reset --hard` / `git push -f` / `git clean -fdx` —— 这些**读起来就危险**。
而 `git checkout -- <单个文件>` **读起来像撤销一处改动**，指向单文件、动词是 checkout，
🚫 三步前置（量化影响面 / 说清可恢复路径 / 用户批准）**一步都不会被触发**。

⚠️ 而它的影响面恰恰**说不出数字** —— 未提交的改动不在任何 `git` 视图里能一眼数清，
`git diff --stat <path>` 给的是「将被删掉多少行」，但那正是**你以为自己只删了注入的那几行**的地方。

⇒ **提议**：§3.2「文件销毁」行补 `git checkout -- <path>` / `git restore <path>` / `git stash`（不带 `--keep-index` 的形态），
并加一条**替代做法**：
> 还原一次注入，用**精确逆替换**（把注入的那段改回原文）或**预存副本 + `md5sum` 核对**，
> 🚫 不用任何「回到某个版本」的命令 —— 那类命令的作用域是**整个文件**，不是你改的那几行。

📌 本段的两次数据清理（`D-45` / `D-48`）已经用了「显式 id 列表 + 事务内硬守卫」这个形态，
本条是它在**文件**上的同构版本：**按你实际动过的东西还原，不按版本还原。**

### 提议 10 · 判「这个实验是不是只读」要按**进程**算，不按**用例**算 🔴 推荐

**实证（2026-09-08，测试代理提议实验时自己写的「只读，不写任何数据」）**：
代理提议在 `lanec`（V429，一个真实的**未迁移**库）上跑一次用例，
证明守卫① 在真实未迁移库上会红 —— 比「改常量指向不存在的列」那种人造证伪强。
它明确写了「**只读，不写任何数据**」，而且**对用例来说是真的**：那条路径一行业务数据都不写。

结果：`application-test.properties:44` 是 `quarkus.flyway.migrate-at-start=true`
⇒ **Quarkus 启动时先把库迁到最新，测试才开始跑。**

```
Current version of schema "public": 429
Migrating … to version "430 …" / "431 …" / "432 …"
Successfully applied 3 migrations, now at version v432
```

**双重后果**：
- `lanec` 被**不可逆地**从 V429 推到 V432（迁移是增量 DDL，没有回退路径；
  且本项目干净库全量重放卡 `V87`（`BL-0220`）⇒ **重建不出 V429 状态**）
- 而实验**结构上根本拿不到想要的证据** —— 守卫① 看到的永远是**已迁移**的库，用例必然 PASS

🔑 **一句话**：
> **「只读」是对用例说的，不是对进程说的。**
> 用例不写业务数据，不代表**跑用例这件事**不写库 —— 框架在你的第一行断言之前就动手了。

**为什么它属于「判据所在的层」那一族**（提议 1 第二维）：
只读性被断言在**用例层**，而写入发生在**框架层**。同一形态今天出现了三次：
`dialect='QUOTE'` 过滤去证核价侧改动 · `order by ctid` 去验 Java 侧加序 · 本条。

⇒ **提议**：跑任何测试/脚本前，判「它会不会写」要看**整个进程**会做什么，至少穷举三项 ——
> ① 框架的启动副作用（Flyway `migrate-at-start` / schema 自动生成 / 缓存预热写盘）
> ② 用例自身的读写
> ③ 收尾/清理路径
>
> 🚫 尤其：**「拿一个旧版本的库当对照」这件事，与「在它上面跑应用」互斥** ——
> 应用一启动就把它迁到最新，对照物当场消失。要留对照库，就只能用 `psql` 直连，不能起应用。

📌 **本次实际损失可控**（已核）：`lanec` 本就在待回收清单上，
且 `custdim2` / `gateb` 仍在 V429、`custdim` 在 V428 ⇒ 未迁移对照并非唯一资源。
**记这条不是为了这次的损失，是为了「提议实验时说的只读，和实际发生的只读，可以不是一回事」。**

**落点**：`docs/rules/testing.md`（测试可信前提）+ `docs/rules/backend.md`（迁移纪律，
它已有「dev 热重载即迁移」一条，本条是同一根因的另一副面孔：**起应用 = 迁移**）。
