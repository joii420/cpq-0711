还原时的五条硬要求

  • 1. 「本次不动」这一列必须渲染，不许省。 它是 AP-60 的守卫 —— 财务要能看见「这一组有 7 行本次不动」， 否则「不写 = 删除」这类后果永远不在她的视野里。repair-0727 的真实事故就是预览显示「0 变更」而执行删了 3 行。
  • 2. 判定为「无变更」的组仍要列出，不许过滤。 否则分不清「这张表没变」和「这张表根本没被算进去」。
  • 3. 「对不上的行」不许折叠进「更多」。 unanchoredRows > 0 时主按钮变红并改文案「仍然确认并核价通过」，页脚左侧显著提示条数。
  • 4. 🆕 BLOCKED 组不许阻断确认，也不许被当成「没事」。 它本次一个字节不写但核价通过照常进行：🚫 不禁用确认按钮、🚫 主按钮不变红、🚫 不用 error 告警条； 同时 🚫 也不许只用灰标签混在「无变更」里 —— 财务必须能一眼看出「这几组我没写，你事后要处理」。 ⇒ 统一橙档：判定标签 本次跳过、行底 #fff7e6、 warning 告警条、汇总条「本次跳过的组」、以及独立的「本次跳过的组」明细表。
    ⚠️ 版本迁移列的终点必须写「不升版」，🚫 不许显示「→ v3」—— 那是本次根本不会发生的迁移。
  • 5. 🆕 recordStale 的告警必须排在最顶端，且不许静默。 它说的不是「会写什么」，而是「下面这些结论可能算错了」—— 排到汇总条之后就退化成「众多提示之一」。 分级：BLOCKED 是橙（warning），本条是红（error）。
    🚫 detail 是异常原文（IllegalStateException: …）， api.md 明写不得当用户文案渲染；财务只看按 reason 映射的中文，未知码带原码兜底。
    ⚠️ 判据取 recordStale.stale 与 summary.recordStale 的并 —— 只信其中一个，遇到另一个出口时告警会整块消失，而漏报的代价是财务照着过期数据确认回填。
    🔴 主按钮与「有 N 行对不上」同档：变红 + 文案「仍然确认并核价通过」。 🚫 但不禁用、不阻断 —— 红条写「请先不要确认」而按钮还是蓝色，等于同一屏给出两个相反的信号； 而硬阻断又会让数据层的可信度问题卡死业务流程。「仍然」两个字承担的正是「你已被警告，这是你的决定」。
