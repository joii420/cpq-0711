## ① 背景与目标

### 现状（2026-09-02 实测，非推断）

| 页面 | 入口 | 现有动作 | 缺什么 |
|---|---|---|---|
| 主数据维护 → **材质** 页签 | `pages/config/MaterialRecipeManagement.tsx` | 刷新 / **导入材质库** / **下载导入模板** / 新建材质 | ❌ 导出 |
| 主数据维护 → **工序** 页签 | `pages/master-data/V6ProcessCrudTab.tsx` | 刷新 / **导入工序** / 新增工序 | ❌ 导出 |
| 系统管理 → **用户管理** | `pages/system/UserManagement.tsx` | 新增用户 | ❌ 导入、❌ 导出、❌ 模板 |

**三张表的数据都只进不出**。量级（2026-09-02 实测，⚠️ 共享开发库有并发写入，数字仅用于判断「要不要异步导出」，**不作为 AC 断言值**）：材质约 260 条 / 含量配置约 260 组 / 材质元素行约 620 行；工序个位数；用户 11 条。

### 解决谁的什么问题

- **材质 / 工序**：管理员要做离线核对、批量改一批含量、把主数据交给客户或同事看，现在只能靠开发连库 `psql` 导。导入模板下得下来但**里面是空的**——想「改现有的 300 条」必须先有一份现有数据。
- **用户**：新员工入职要一个个点「新增用户」，11 个人尚可，一次进 20 个人就是 20 轮抽屉填写。

### 不做会怎样

批量维护继续占用开发的时间（每次都是一条 `psql` + 手工拼 Excel），且开发查库导出的口径与导入模板不一致，导回去经常被拒。

### 目标一句话

**让这三张表的数据能「导出 → 用 Excel 改 → 导回去」形成闭环，且导出动作只对系统管理员开放。**

### 🚫 明确不做什么

| 不做的事 | 去向 / 理由 |
|---|---|
| **元素**页签的导出 | 用户本次只点名材质/工序。→ 建议进 `BACKLOG.md`（待用户采纳） |

## ③ 验收标准（AC）

> 环境统一：前端 `http://localhost:5174`，后端 `8081`，库 `10.177.152.12:5432/cpq_db_0724`。
> 角色账号：管理员 `admin`；非管理员用现有 `SALES_MANAGER` 或 `PRICING_MANAGER` 账号各一个。
> 原型基准：`原型图/` 下同名 html。
>
> 🚨 **本节 AC 一律不写死行数，断言的是「导出结果 ⇄ 同一时刻的库内口径」这个不变量。**
> 理由（2026-09-02 实测）：`cpq_db_0724` 是**多会话共享的开发库**，`mvnw test` 也直接写它。
> 立项当天两次相隔几分钟的同一条 `count(*)` 就已经不同（材质 263→259、含量配置 264→260、工序 4→2）。
> 写死数字的 AC **到验收时必然对不上，且分不清是数据漂移还是功能坏了**。
>
> **基准 SQL（下称「基准查询」，验收时现场跑，与导出同一时刻）**：
> ```sql
> -- ① 材质导出应含的「不同材质名」数
> SELECT count(*) FROM material_recipe WHERE status='ACTIVE';
> -- ② 材质导出应含的「数据行数」
> SELECT count(*) FROM material_recipe_element e
>   JOIN material_recipe_config c ON c.id = e.config_id
>   JOIN material_recipe r ON r.id = c.recipe_id
>  WHERE c.status='ACTIVE' AND r.status='ACTIVE';
> -- ③ 工序 / ④ 用户
> SELECT count(*) FROM process_master;
> SELECT count(*) FROM "user";
> ```

### A 组 · 材质导出（单点）

- **AC-1**（权限·可见）以 `SYSTEM_ADMIN` 登录 → 主数据维护 → 材质页签，工具栏右组按 `原型图/1-材质页签-工具栏.html` 的顺序显示 5 个动作：`刷新 / 导出材质库 / 导入材质库 / 下载导入模板 / 新建材质`，「导出材质库」可点击。
- **AC-2**（权限·隐藏）以 `SALES_MANAGER` 登录同一页签 → 工具栏**只有 4 个动作**，「导出材质库」**整个按钮不渲染**（不是禁用态）。以 `PRICING_MANAGER` 登录同样只有 4 个。
- **AC-3**（权限·后端兜底）以 `SALES_MANAGER` 的会话直接 `GET /api/cpq/material-recipes/export` → HTTP **403**，响应体 `{"code":403,"message":"无权限访问"}`。未登录调用 → HTTP **401**。
- **AC-4**（可回导·表头）管理员点「导出材质库」，下载得到 `.xlsx`。用 Excel 打开，**第 1 行前 4 个单元格逐字为**：`材质`、`组号`、`元素符号`、`含量`（顺序不可换——导入端 `MaterialRecipeImportService.validateHeader` 按**位置**逐列比对，错一位即 400 `IMPORT_HEADER_INVALID`）。
- **AC-5**（可回导·含量口径）**不变量：导出文件里每个「含量」单元格的值 × 100 == 该元素在库中的 `material_recipe_element.default_pct`**，且全表任一含量值满足 `0 < 值 ≤ 1`。
  验证样例（立项当日实测，若该材质已被改动则改取任一含 2 个元素的材质，判据不变）：材质 `301/Cu/301` 在库中 `Cu=84`、`301=16` ⇒ 导出文件对应 2 行的含量列必须是 **0.84** 与 **0.16**，**不是 84 / 16**。
  🚨 这条是「可回导」的命门：导入端 `pctInRange(v, 1)` 只接受 `(0, 1]`，导出若照搬库值，回导时**每一行**都会被判「含量非法」。
- **AC-6**（只读参考列）导出文件**第 5 列起**依次为只读参考列：`材质编号`、`含量配置编号`、`状态`、`含量类型`；断言方式：任取一行，其 `材质编号` / `含量配置编号` 与库中该材质的 `material_recipe.code` / `material_recipe_config.config_no` 逐字相同（立项当日 `301/Cu/301` 实测为 `config_no = 00168-01`）。这些列**回导时被忽略**（由 AC-19 验证）。
- **AC-7**（跟随筛选）材质页签「状态」下拉选「停用」，列表显示 N 条（记下 N 与其中任一材质名 X）→ 点导出 → 文件里出现的**不同材质名个数 = N**，且包含 X，不包含任何 `status=ACTIVE` 的材质。再把「类型」下拉选「含量可调」叠加 → 导出文件的材质集合 = 页面上此刻列表显示的集合。
- **AC-8**（不受分页限制）清空全部筛选，页面分页每页 20 条 → 导出文件的**不同材质名个数 == 基准查询①**、**数据行数 == 基准查询②**（两条 SQL 与导出同一时刻跑）。
  关键否定断言：导出行数**不等于当前页的 20 条**，也不等于 `pageSize`。

### B 组 · 工序导出（单点）

- **AC-9**（权限）以 `SYSTEM_ADMIN` 登录工序页签 → 工具栏按 `原型图/2-工序页签-工具栏.html` 显示 `刷新 / 导出工序 / 导入工序 / 新增工序`；`SALES_MANAGER` 登录时「导出工序」不渲染；其会话直接调 `GET /api/cpq/v6/process-master/export` → **403**。
- **AC-10**（列结构）导出文件第 1 行的 7 个列名逐字为：`工序编号`、`工序名称`、`工序类别`、`是否外协`、`标准币种`、`标准单位`、`默认不良率`（与 `ProcessMasterImportService` 的 `COL_*` 常量同名；工序导入按**列名**匹配，顺序无关）。`是否外协`列的值为 `是` / `否`（不是 `true`/`false`）。
- **AC-11**（跟随筛选 + 全量）不加筛选导出 → 数据行数 **== 基准查询③**，且**等于列表分页控件显示的总条数**（不是当前页条数）。把「是否外协」筛为「外协」后导出 → 行数 == 该筛选下分页控件的总条数，且每行 `是否外协` 均为 `是`。

### C 组 · 用户导出（单点）

- **AC-12**（列结构）管理员在用户管理页点「导出用户」→ 文件第 1 行为：`用户名`、`姓名`、`邮箱`、`角色`、`区域`、`部门`（前 6 列＝导入模板列）＋只读列 `状态`、`创建时间`。`角色`列显示中文（`系统管理员`/`销售经理`/`销售代表`/`财务`），`状态`列显示 `启用`/`停用`。
- **AC-13**（跟随筛选 + 全量）不加筛选导出 → 数据行数 **== 基准查询④**，且等于分页控件显示的总条数。把「角色」筛为「销售代表」→ 导出行数 == 该筛选下的总条数，且每行角色列均为 `销售代表`。

### D 组 · 用户导入（单点）

- **AC-14**（模板）用户管理页点「导入用户」→ 打开抽屉（按 `原型图/4-用户导入抽屉.html`）→ 点「下载导入模板」得到 xlsx，第 1 行为 `用户名`、`姓名`、`邮箱`、`角色`、`区域`、`部门`，含 1 行示例数据，`角色`列单元格带批注说明四个合法取值。
- **AC-15**（新增 + 密码回显）用一份含 3 个全新用户名（`t260902a/b/c`）的文件导入 → 结果页（按 `原型图/5-用户导入结果.html`）显示「**新增 3 条，跳过 0 条**」，并列出 3 行 `用户名 → 初始密码`，每个密码互不相同；**导入前后各跑一次基准查询④，后值 − 前值 == 3**；3 条新记录 `is_first_login = true`、`status='ACTIVE'`。
- **AC-16**（重复跳过）把 AC-15 那份文件**原样再导入一次** → 结果显示「新增 **0** 条，跳过 **3** 条」，跳过原因逐行为「用户名已存在」；**基准查询④ 的值与第二次导入前完全相同（增量 0）**，且 `t260902a` 的 `full_name` / `role` / `email` 与第一次导入后**逐字相同**（未被覆盖）。
- **AC-17**（非法角色）文件中某行角色列填 `财务总监`（非法值）→ 该行跳过，原因为「角色不合法：财务总监」，同文件其余合法行**照常新增**（部分成功，不整单回滚）。
- **AC-18**（区域/部门解析）区域表与部门表当前均为 0 条：文件中区域/部门列**留空** → 该行正常新增，`region_id`/`department_id` 为 `NULL`；填一个不存在的部门名 `不存在的部门` → 该行**仍然新增成功**，`department_id` 为 `NULL`，并在报告的「提示」栏出现「部门未匹配：不存在的部门」（**不因此拒绝整行**）。

### E 组 · 序列 AC（连续操作 + 刷新，断言中间态与最终态）

- **AC-22**（筛选态切换序列）材质页签：先「状态=停用」导出（记行数 N1）→ **切到工序页签再切回材质页签** → 筛选条件保持为「停用」，再导出行数仍为 N1 → 清空筛选 → 导出行数变为**基准查询②**的值（且明显大于 N1）。（验证筛选态与导出参数始终一致，不会因页签切换错位。）

### F 组 · 边界 AC

- **AC-23**（空结果）材质页签搜索框输入 `zzz不存在zzz`，列表显示空态 → 「导出材质库」按钮**按 `原型图/1-材质页签-工具栏.html` 的禁用态渲染**（灰色不可点，hover 显示 tooltip「当前筛选结果为 0 条，无可导出数据」）。同样规则适用于工序页与用户页。

## ④ 依赖与影响面

### 依赖的既有机制（均已实测确认，非推断）

| 依赖 | 实测结论 | 出处 |
|---|---|---|
| **方法级权限覆盖类级** | `RoleFilter` 取注解的逻辑是 `methodAnno != null ? methodAnno : classAnno` ⇒ 在类级放开 4 角色的 `MaterialRecipeResource` 上，给导出方法单标 `@RoleAllowed({"SYSTEM_ADMIN"})` **能收紧**。用的是自研 `com.cpq.common.security.RoleAllowed`，**不是** `jakarta.annotation.security.RolesAllowed` | `cpq-backend/.../common/security/RoleFilter.java:60-64` |
| **材质导入表头按位置严格校验** | 前 4 列必须逐字为 `材质/组号/元素符号/含量`，错一位即 400 ⇒ 只读参考列**只能加在第 5 列及之后** | `MaterialRecipeImportService.java:152-156` |
| **材质含量的两套口径** | 导入模板填 **0–1 小数**（模板示例 `Ag=0.9`），落库 `×100` 存 `default_pct=90` ⇒ **导出必须 ÷100 写回小数**，否则回导时 `pctInRange(v, 1)` 判「含量非法」全行被拒 | `MaterialRecipeImportService.java:373`（`multiply(HUNDRED)`）+ `:187` + `MaterialRecipeRules.pctInRange` |
