## 2. ✅ 原「缺陷 1」已推翻：是 **AC 假设错误**，不是产品缺陷（2026-09-03 结案）

我最初把「切换页签后筛选态重置」报成了真缺陷。**主线亲验推翻了这个结论，AC 已修订，代码不动。**

### 主线亲验补上的关键维度：切回后**筛选框显示什么**

| 时点 | 筛选框 | 列表共 | 导出行数 |

⇒ **筛选框、列表、导出三者完全自洽。** 切回后用户看到的列表就是全量、筛选框明明白白写着「全部」，

🚫 我原报告里写的「用户以为在导筛选结果，实际拿到全量」——**这一句不成立**，

**根因**：壳页 `MasterDataHubPage.tsx:28` 的 `destroyInactiveTabPane`（task-0728 既有架构）——

**要求筛选跨页签保持 = 要求改壳页架构**，既超出本任务范围，也与导出功能无关。

## 3.5 ⚠️ 已知限制：「导出 → 回导」闭环对**同名材质**不成立

主线亲验（筛「启用」导出 **629 行**）原样回导：`recipesCreated=0 / configsCreated=0`
（AC-19 ✅ 通过，库计数 263/264/631 前后逐字相同），但**有 3 行被跳过**：

```
行 99   AgCu      → 材质名对应多条材质记录，请先在材质管理页处理
行 148  AgNi      → 材质名对应多条材质记录，请先在材质管理页处理
行 484  SnO2 组2  → 元素组合与该材质的元素组成不一致
```

**根因**：库里存在**同名材质** —— `AgCu` → AgCu85 / AgCu90，`AgNi` → AgNi90 / AgNi95
（材质名相同、编号不同、都 ACTIVE）。导出的「材质」列写的是**材质名**，两条记录导出成同一个值，
回导时导入端无法区分 ⇒ 跳过。第 3 行是 §3 那个列错位脏数据。

**定性**：
- **不是本任务引入的** —— 同名材质是既有数据状态；
- **不是静默失败** —— 导入报告**逐行报明了原因**，用户看得到；
- ⇒ 属**已知限制**，不属缺陷。若要让闭环对同名材质也成立，需要给导出加上「材质编号」作为回导键，
  那是改导入契约（AC 之外），本任务不做。

### 🔬 我在 T-22 里直接撞上了同一现象（并因此改掉了自己写错的断言）
我最初给 T-22 加了一条自造的「durable」不变量：**导出的不同材质数 == 页面列表条数**。
实测 **261 ≠ 263** 而变红。查清后确认 **是我的不变量写错了**，不是产品问题：
```
material_recipe 总数        = 263
count(DISTINCT symbol)     = 261     ← 导出「材质」列的口径
差 2 = AgCu / AgNi 两对同名材质各塌成一个名字
```
⇒ 已改为「列表条数 == 库材质条数」**且**「导出不同材质名数 == 库 `count(DISTINCT symbol)`」——
两侧各自与库口径对齐，🚫 不把两个数字直接划等号。

## 4. 🚨 我自己抓到的一个**假绿**（必须记下来）

**组件层「非管理员看不到导出按钮」曾经是绿的，但它是空验证。**

- 机制：`renderToStaticMarkup` 走 React 的 **SSR 路径**，zustand 在该路径下取不到
  `useAuthStore.setState()` 写入的值 ⇒ 页面里 `useAuthStore(s => s.user?.role === 'SYSTEM_ADMIN')`
  **对任何角色都返回 false**。
- 于是：
  - 「管理员应看到导出按钮」→ **恒红**（看起来像权限判错的产品缺陷）
  - 「非管理员不该看到导出按钮」→ **恒绿，但不是因为角色判断正确**，而是因为**谁都看不到**
- 危险的是后者：恒红会被追查，**恒绿不会**。这正是 `testing.md §3` 的假绿。
- 处置：把整个「按角色显隐」维度移到 E2E（新增 `T-01/02/09-UI`），用真实浏览器拿到**有分辨力**的证据：
  管理员两页都有导出按钮、非管理员两页都没有、导入/模板按钮都还在。组件层只保留**不含角色门**、
  SSR 能如实验证的用户页用例。🚫 没有保留任何「反正它绿」的空验证。

## 7. 不稳定失败的归因（`testing.md §4`，🚫 未以「重跑一下就好」结案）

E2E 初期出现随机失败。**四类症状全部定位到测试基础设施，无一是产品缺陷**，且**都做了结构性修复**：

| 症状 | 根因 | 结构性修复 | 修复后重复次数 |
|---|---|---|---|
| `locator.fill` 超时（登录页） | vite dev server 在连续整页 goto 下偶发慢，输入框未挂载就 fill。**仓库自带 `global-setup.ts` 在同一次运行里对 alice/bob 撞的是一模一样的报错** ⇒ 与本任务无关 | 先 `toBeVisible` 再 fill + 整体重试一次 | T-21 连续 4 次通过 |
| 「页签点不到」/「用户页没有搜索框」 | 每个用例都是全新 browser context，要把整站模块重新拉一遍，重路由偶发慢到分钟级 | `gotoMasterDataTab` / `gotoUsersPage` 带重试 | 通过 |
| 「搜 zzz 却还有 16 行」 | **竞态**：填搜索词时首屏请求还在飞，其响应回来把已过滤结果覆盖成全量 | 先等首屏数据落地，再搜；未收敛则补一次 | T-23b 连续 4 次通过 |
| 「tooltip 不出现」 | 页面刚渲染完 `mouse.move` 打空 | 移开后重试一次 | 通过 |

另修两处**会造成误判**的选择器错误（都是我的用例错，不是产品缺陷）：
- 工序页空态是**自定义** `.ant-table-placeholder`（"未找到匹配…的工序数据"），不是 antd 的 `.ant-empty`；
- 材质页「状态」下拉**没有「全部」选项**（只有 `启用/停用`，「状态：全部」是前缀+占位符），清空要点 antd 的 clear（×）。

**当时唯一未修复的失败是 T-22（7/7 必现、数值每次一致）**，故判为「确定性」而非「不稳定」——
这个分类是对的；但**定性错了**：它不是产品缺陷，而是 AC 假设错误（§2 已更正）。
📌 教训：**「确定性复现」只能证明「不是 flaky」，不能证明「是缺陷」。**
两者是独立判断 —— 必现的现象也可能只是 AC 写错了。

2026-09-03 按新 AC 重写 T-22 后又修了两处**我自己的**定位/断言错误（都不是产品问题）：
- `selectNear('类型')` 在**选中值之后**失效（下拉邻近文本从「类型：全部」变成「标准锁定」）
  ⇒ 两个筛选下拉必须在**未选中时一次性抓好并全程复用**；
- 自造的「导出不同材质数 == 列表条数」是**错误的不变量**（同名材质会塌成一个名字，实测 261≠263）
  ⇒ 改为两侧各自与库口径对齐（§3.5）。
