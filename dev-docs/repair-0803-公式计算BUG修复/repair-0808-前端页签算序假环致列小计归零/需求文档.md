## 1. 背景与目标

`repair-0803`（2026-08-03）把**后端**的页签依赖建图从「页签粒度」改成「列粒度」，消除了 `component_subtotal`
引用零依赖列（如 `产品·税率` 这种 INPUT 列）造出的**假环**。当时同步登记了 `BL-0101`：**前端建图没跟进**，
并明确警示「不要简单照搬页签粒度——那正是 repair-0803 修掉的假环成因」。

前端的页签粒度建图实际上早在 `40983a52`（2026-06-16，修 QT-1743「管理费=0」）就已存在（内联在
`buildCrossTabRows` 里，不是 `crossTabOrder.ts` 的导出函数，故 BL-0101 当时描述为"前端没有 `extractSubtotalRefs`"
——**这一句已过时，需在 BL-0101 中订正**）。于是形成两端不一致：**后端列粒度（对），前端页签粒度（错）**。

BL-0101 当时判「当前未见报障，可能是现网模板的页签顺序恰好正确」。**2026-08-07 报障已实证发生**，
且症状与 BL-0101 预判的完全一致：「前端显示 0，与后端重算结果不一致（用户看到的和存库的不是一回事）」。

**目标**：让前端页签算序与后端 `CrossTabComponentOrder.buildComponentDeps` **同规则**，消除假环，
使卡片列小计 / 产品小计与后端持久化值逐值一致。

## 4. 功能需求

- **FR-1** 前端 `crossTabOrder.ts` 新增 `buildComponentDeps(tabs)`，输入每个 NORMAL 页签的
  `{ cid, code, tabName, formulas, fields }`，输出 `cid → 依赖 cid[]`。语义逐条镜像后端同名方法：
  - `cross_tab_ref` 的 `source` → **全量建边**（不做列粒度豁免）
  - `component_subtotal` → 解析 `component_code` 优先、`tab_name` 回退为目标 cid；解析不到（卡片外引用）或自引用 → **不建边**
  - 目标列**顺序敏感**才建边：`is_tab_total===true` 或 `value==='__amount_total__'` → 建；否则查目标页签 `fields` 里同名列的 `field_type`，是公式类才建；列名缺失 / fields 不可读 / 查无此列 → **建边（保守）**
- **FR-2** `QuotationStep2.tsx#buildCrossTabRows` 内联的 `deps` 组装改为调用 `FR-1`，删除原页签粒度的 `subRefs` 收集逻辑（`crossRefs` 行为不变）。
- **FR-3** `topoOrderComponents` 抛错的 `catch` 分支：保留 `order = ids`，追加 `console.error('[crossTabOrder] 组件依赖成环，退回声明序，列小计可能不准：', e)`，并把注释里失效的「模板保存层已拦截环」订正为实际情况。
- **FR-4** 补测试（见 `test.md`）：建图规则单测 + 本单据真实数据前后端对拍 + QT-1743 反向门禁。

## 8. 已知坑位

- **AP-18 / 双口径**：本 BUG 的表象「行对、小计错」正是行内读后端快照、小计读前端实时重算所致。修完小计后两者应同值；若仍不同值，说明还有第二处分叉，**不得只改小计去迁就行内**。
- **repair-0803 的教训（父任务）**：拓扑序只解决"谁先算"；一列是否顺序敏感取决于**它是不是公式列**。给非公式列建边收益为零，却会凭空造出反向边。本次前端必须守住同一条判据。
- **`cpq-agent-tests-stale-server-false-positive`**：子代理报的"全绿/全红"都要主线在同环境重跑确认。
- **`cpq-worktree-frontend-selfcheck`**：共享 5174 服务的是**主工作区**，worktree 内的改动 curl 不到；前端自检以 `tsc --noEmit` + `vitest` 为准，页面验证放到合并后。
- **grep 陷阱**：本环境 `grep` 是 ugrep，中文多的大文件会被误判二进制静默返空 → 一律 `/usr/bin/grep -a`。
