## 3. 缺陷清单

### D-01 · `columnSumsByComp.test.ts` QT-1743 老用例与新语义冲突 —— 已修，非缺陷
- **现象**：实现落地后该用例 `expected +0 to be 200` 失败。
- **归因**：该用例**绕过 PASS1**（直接传空 `allComponentSubtotals` 调 `buildCrossTabRows`），靠拓扑边把 `INPUT_NUMBER` 列的值传过去 —— 这正是 AC-5 明确推翻的旧假设。
- **主线取证**（三条对照，全部亲跑）：
  1. 走真实链路（PASS1+PASS2）、被引用列 `INPUT_NUMBER`（本次不再建边）→ `mgmt = 200` ✅
  2. 被引用列 `FORMULA`（仍建边）、引用方排前 → `mgmt = 200` ✅（QT-1743 真形状）
  3. 绕过 PASS1 → `mgmt = 0` ← 失败的唯一来源
  并核实三个生产调用点**都先跑 PASS1**，无空 `acs` 的生产路径。
- **处置**：用例按真实链路改写并拆成两条（INPUT / FORMULA 各一），另补两条 `buildComponentDeps` 的直接断言，把"该不该建边"写进断言而非靠数值间接体现。**严重级：无（测试资产修正）**。

### D-02 · 产品小计尾差 `2.5536e-5` —— **存量缺陷，本次不修**
- **现象**：前端 `137.5310921432503` vs 后端持久化 `137.5310666072503`。
- **根因（主线定位到行）**：后端 `CardSnapshotService.java:4078-4079` 对 `__amount_total__` 哨兵键做 `setScale(4, HALF_UP)`，把「组装加工费」整页签合计 `0.083825536` 截成 `0.0838`；前端 `tabTotalLines.ts#sumAmountFromByCol` 走 `sumDecimal` **精确求和不截断**。差值 `0.083825536 - 0.0838 = 0.000025536`，与实测尾差**逐位相等**。
- **性质**：与本次拓扑修复正交 —— 构成产品小计的 6 个列小计已逐值对齐（AC-3）。且它与 `task-0801`「全链路统一 6 位小数」的既定口径直接冲突（4 位是 BL-0017 / task-0729 B8.1 的残留）。
- **为什么以前没暴露**：修复前「物料」整页签贡献为 0，前后端根本没有可比的非零值。
- **处置**：登记 **`BL-0158`**，本次不修（改后端属另一条口径决策，需产品裁定 4 位还是 6 位）。对拍用例对该项采用「绝对容差 1e-3 + 量级闸（>100）」，**真缺陷（算序/建图）复发时仍会硬失败**。

- **现象**：`tab_name#__amount_total__` 取不到值（`expected=12.34 actual=0`；amt-003 连带 `expected=101.22 actual=88.88`）。
