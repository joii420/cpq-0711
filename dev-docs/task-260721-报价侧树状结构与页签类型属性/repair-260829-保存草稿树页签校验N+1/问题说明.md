## ④ 问题原因 / 报告

### 4.1 一句话根因

`saveDraft` 批量路径的主循环里，**每行每页签**都调一次 `QuotationTreeService.assertCanAddRowsToRestrictedTab`，而它开头的 `loadSingleComponentTabMeta` 每次都重新查两条 SQL 去拿**整单恒定**的模板元数据 —— 1845 行 × 5 页签 = **9,225 次调用 / 18,450 条跨网 SQL 往返**，本应只需 **1 次**。

### 4.2 证据链（可复跑）

在 `processBatchStage1` 插 8 处分段计时、在 `loadSingleComponentTabMeta` 插 2 段拆分（纯 `LOG.infof`，零行为改动），真实点击「保存草稿」触发。原始日志见 `证据/埋点日志摘录.md`。

**第 2 轮（采样间隔 25 行）—— 阶段占比**

| 进度 | elapsed | prep | line | product | cdPersist | flush | **assert** |
|---|---|---|---|---|---|---|---|
| 25 | 6,683 ms | 1,510 | 1 | 0 | 15 | 698 (×25) | **4,457 (×125)** |
| 50 | 11,375 | 1,510 | 2 | 0 | 24 | 1,357 (×50) | **8,478 (×250)** |
| 75 | 16,266 | 1,510 | 4 | 0 | 30 | 2,024 (×75) | **12,696 (×375)** |
| 100 | 21,780 | 1,510 | 5 | 0 | 34 | 2,703 (×100) | **17,524 (×500)** |
| 125 | 27,169 | 1,510 | 6 | 0 | 39 | 3,417 (×125) | **22,193 (×625)** |
| 150 | 32,902 | 1,510 | 7 | 0 | 44 | 4,154 (×150) | **27,182 (×750)** |

- **`assert` 占 82.6%**，`em.flush()`（该校验的前置）占 12.6%，预处理占 4.6%
- **真正写库的部分（行实体 persist + Product 查询 + componentData persist）合计 52 ms = 0.15%**

**线性度已验证**（六个采样点，非单点外推）：`assert` 单次 **34~36 ms 恒定**、`flush` 单次 **27 ms 恒定**，**无 O(n²) 增长** ⇒ 可放心线性外推：

```
assert : 1845 行 × 5 页签 × 35 ms ≈ 325 s
flush  : 1845 次 × 28 ms          ≈  52 s
prep   :                          ≈   2 s
                            合计   ≈ 380 s   vs   事务预算 60 s
```

**第 3 轮（拆开 `assert` 内部）**

```
calls=250 | resolveTemplateId=3718ms(avg 14.9ms) allTabsOf=6337ms(avg 25.3ms)
calls=500 | resolveTemplateId=7243ms(avg 14.5ms) allTabsOf=12145ms(avg 24.3ms)
calls=750 | resolveTemplateId=11012ms(avg 14.7ms) allTabsOf=18386ms(avg 24.5ms)
```

两段合计 **39.2 ms**，而同批 `assert` 实测 29,424 ms / 750 次 = **39.2 ms** ⇒ **`loadSingleComponentTabMeta` 吃掉了 assert 的 100%**；行数据解析与真正的树校验体（`assertCanAddToRestrictedTab` + `buildHitContext`）合计仅 24 ms / 750 次，**几乎为零**。

### 4.3 调用链与两处浪费

```
QuotationService.processBatchStage1(:2541)      ← 主循环内，per line × per componentData
  └ QuotationTreeService.assertCanAddRowsToRestrictedTab(:799)
      └ loadSingleComponentTabMeta(:829)
          ├ resolveCustomerTemplateId(lineItemId)   14.7 ms  ← 1 条 native SQL，查 quotation.customer_template_id
          └ publishedTemplateReader.allTabsOf(tid)  24.5 ms  ← 1 条 list + Template.findById + 解析 10 KB jsonb
```

单次 15 ms 对一条简单 SQL 是**跨网往返的合理值**（DB 在 `10.177.152.12`，非本机）—— **问题不在单次快慢，在于调用了 9,225 次**。

两处叠加浪费：

1. **查的是整单恒定值**。这张单只有一个 `customer_template_id`，`allTabsOf` 的入参因此恒为同一个 `templateId`，返回恒为同样 5 行。9,225 次调用得到 9,225 个相同答案。
2. **80% 的调用连校验都不需要**。5 个页签只有 1 个是 `材质元素`，其余 4 个进方法后在 `if (!"材质元素" && !"外购件") return;` 立刻放行 —— **但两条 SQL 的钱已经付了**（判据在查询之后才做）。

### 4.6 为什么测试没拦住

1. **既有测试只测功能不测规模**：`SaveDraftRestrictedTabValidationTest`（B8 配套）真走 `saveDraft` 落库，但 fixture 是**自建最小 Template/Component/LineItem，规模 1 行** —— 1 行时该 N+1 表现为 5 次调用、约 0.2 秒，与正确结果无异。
2. **等价性测试同样不含规模维度**：`BatchStage1PersistEquivTest` 验的是「逐行路径 vs 批量路径持久化逐位等价」（170 行 / 77 行），**只比对结果不比对耗时**，且 170 行 × 5 = 850 次调用 ≈ 30 秒，在测试里不超时也不报警。
3. **全仓无 saveDraft 的 SQL 条数断言**：`backend.md` 的 N+1 硬指标目前靠人工评审，没有自动闸（对照：`repair-260828` 同族问题也是靠埋点才发现的）。
4. **`PublishedTemplateReader` 的类注释明文警告过这件事** —— 「🚫 禁止新增单条查询方法被调用方放进循环——那就是把 N+1 重新引回来」，但 `loadSingleComponentTabMeta` 恰恰是在循环里逐次调 `allTabsOf`，**注释拦不住调用方**。

### 4.7 修复上限实测（两次证伪实验，决定方案范围）

推断「修好这两处就够了」是不够的 —— 主线做了两次**短路实验**（临时把目标代码旁路掉，直接测出「修好之后还剩多少」），结论**推翻了最初的方案设想**：

| 实验 | 做法 | 结果 |
|---|---|---|
| **实验一**：只修 assert | `assertCanAddRowsToRestrictedTab` 开头硬短路 | assert 归零，但 **`em.flush()` 立刻接棒成为主导**（30.9 ms/行）。1775 行耗时 **59.2 s**，外推 1845 行 ≈ **61.5 s** ⇒ **仍会被 60s reaper 砍**（临界失败） |
| **实验二**：assert + flush 都修 | 再把 per-line `em.flush()` 改为循环外统一一次 | **全量 1845 行跑完**，事务未被砍：`processBatchStage1` **24.565 s**，其中**主循环本身只有 75 ms**（`line=9ms` / `cdPersist=65ms`），**23.251 s 是循环外那一次大 flush** |

**实验二暴露了完整的端到端图景**（`[draft-profile]` 首次成功打印）：

```
[draft-profile] total=40648ms | S1.saveDraft=25956ms  S2.snapshotRows=14114ms  S3.priceReconcile=578ms
```

| 场景 | `processBatchStage1` | 端到端 `PUT /draft` | 事务(60s) | 前端(30s) |
|---|---|---|---|---|
| **现状** | ≈ 400 s（外推） | 从未跑完 | ❌ 被砍 | ❌ |
| **只修 assert** | ≈ 61.5 s（外推，1775 行实测 59.2 s） | — | ❌ 被砍 | ❌ |
| **assert + flush 都修** | **24.6 s（实测）** | **40.6 s（实测）** | ✅ 通过 | ❌ 仍超 30s |

🚨 **两条必须带进 A0 的结论**：

1. **只修 assert 不够** —— 会从「必然超时」变成「临界超时」，等于没修。**flush 必须一起修**。
2. **修完这两处也只到 40.6 s，仍超前端 axios 30s 上限** —— 剩余大头是 S1 里那**一次大 flush（23.3 s）** 与 **S2 `snapshotQuotation`（14.1 s）**。**「端到端 < 30s」不是修这两个 N+1 就能达成的**，范围需用户裁决。
   - 大 flush 的 23.3 s = 9,225 条 `component_data` INSERT + 1,845 条 `line_item` UPDATE 的落库往返。其中 UPDATE 部分**与 `repair-260828` 的 C 根因同源**（`@DynamicUpdate` 使 `statement-batch-size=100` 静默失效 → 逐条往返），该返修已裁决用 detach + 原生批量 UPDATE 绕开，**手法可复用**。

### 4.7.1 第三次实验：1+2+3 组合（推翻了一条推算）

在实验二基础上再加第三条改动（D-1 逐行置 NULL → 循环外一条批量 SQL），**续存场景**（componentData 已有 9,225 行）实测：

```
[stage1-profile] 循环外统一flush=29763ms | D-1批量置NULL=47ms(1845行) | elapsed=37712ms
[stage1-profile] ★总结 total=37714ms | prep=7800 loop=88(line=10 cdPersist=77 flush=29763(x1) assert=0(x0))
```

| 项 | 首存（实验二） | 续存（实验三） | 说明 |
|---|---|---|---|
| prep（含整单 DELETE） | 1,221 ms | **7,800 ms** | 续存要先 DELETE 9,225 行子表 |
| 主循环 | 75 ms | 88 ms | 两次都是**毫秒级** |
| 循环外统一 flush | 23,251 ms | **29,763 ms** | ⬅ **最大剩余项** |
| **D-1 批量置 NULL** | — | **47 ms**（1,845 行） | 一条 SQL |

🚫 **一条推算被证伪**：立项时曾推断「flush 的 23.3 s 主体是 1,845 次 `line_item` UPDATE 被 `@DynamicUpdate` 阻断合批」。实验三把 D-1 的逐行置 NULL 整个拿掉（`line_item` 因此不再被无差别标脏），**flush 不降反升**（23.3 → 29.8 s）⇒ **该推断不成立**。

✅ **修正后的事实**：flush 的主体是 **9,225 条 `quotation_line_component_data` INSERT**。

- 实际写入 **8.8 MB**（`row_data` 1.9 MB + `snapshot_rows` 5.8 MB + 记录骨架）
- 29.8 s ÷ 8.8 MB = **295 KB/s** —— 对局域网 PG 而言过低，**不是数据量瓶颈**
- 29.8 s ÷ 9,225 条 = **3.2 ms/条**；对照本次实测的跨网单次往返 ≈ 15 ms，说明**存在一定批处理但效率远未达标**（若完全不合批应为 9,225 × 15 ms ≈ 138 s；若 batch=100 全生效应为 93 批 × 数十 ms ≈ 2~5 s）
- 配置侧 `statement-batch-size=100` + `hibernate.order_inserts=true` **均已开启**；`QuotationLineComponentData` 无 `@DynamicUpdate`、`@Id @GeneratedValue` 为 UUID（非 IDENTITY，理论不禁用 batch）

⚠️ **根因未查明**：「batch 为何只发挥了部分效力」尚无结论。**判定它只需一次实验**：把 `statement-batch-size` 临时设为 1 跑一遍 —— 若耗时暴涨到 ~138 s，说明现有批处理确实在起作用、29.8 s 已接近该路径下限；若耗时基本不变，说明 batch 实质未生效，存在数量级优化空间。**该实验尚未执行**，故第三项的收益区间未定。

### 4.7.2 判定实验：batch 到底生没生效（第三项定性，已执行）

**做法**：保持实验三的短路状态不变，只把 `quarkus.hibernate-orm.jdbc.statement-batch-size` 从 `100` 临时改为 `1`，同一张单再跑一次。**唯一变量是批大小**。

| batch-size | 主循环 | 循环外 flush | 结局 |
|---|---|---|---|
| **100**（现行） | 88 ms | **29,763 ms** | ✅ 事务内完成 |
| **1**（禁用批） | 90 ms（prep 4,771 ms） | **> 55,000 ms 未完成** | ❌ 60 s 被 reaper 砍（04:09:15 进入 → 04:10:15 强杀） |

✅ **定性结论：批处理确实在生效** —— 关掉它，同一段 flush 从 29.8 s 涨到至少 55 s 且跑不完。

⚠️ **但只快了不到 2 倍，而非理论上的百倍**。若 100 条/批完全生效，9,225 条应压成 93 次往返、总计 2~5 s；实际 29.8 s ⇒ **瓶颈不在往返次数，而在每批的处理成本本身**。指向的是数据形态而非批大小：这 9,225 条要写 **8.8 MB**，其中 **5.8 MB 是 `snapshot_rows` jsonb**，客户端要序列化、服务端要 parse 并落 TOAST。

📌 **对方案的意义**：第三项**不是一个配置项能解决的问题**，要动就得换手法（`COPY`、多值 INSERT、或压缩 `snapshot_rows` 体积），收益不确定、风险中等。**29.8 s 已接近当前架构下该路径的下限** ⇒ 建议转 `BACKLOG`，不进本期。

### B-6 `componentData` 由「全删全建」改为 UPSERT（窄切口增量，A0 第二轮追加）

**动机**：实测续存场景下，`flush` 要写 **8.8 MB**，其中 **5.8 MB 是 `snapshot_rows`** —— 而这一列在保存路径上被 `preservedSnapshots` **原样读出、随行删掉、再原样写回**，是纯粹的无用功；`prep` 段还要为此先 DELETE 9,225 行（5.2 s）。

**做法**：

| 步骤 | 内容 |
|---|---|
| 结构判定 | 主循环前比对「payload 的 `componentId` 集合」vs「库中该 `lineItem` 现有的 `componentId` 集合」 |
| **集合相同** → UPSERT 路径 | 复用现有记录，只 `UPDATE row_data, subtotal, tab_name, sort_order`；🔒 **`snapshot_rows` / `deleted_row_keys` 两列完全不碰** |
| **集合不同**（页签增删 / 模板切换） | **回落现行全删全建**，保证正确性。两条路径产出等价，只是快慢不同 |
| 其余三张子表 | `quotation_line_process` / `quotation_line_composite_process` / `quotation_line_item_snapshot` **行为不变**，仍全删全建（数据量小） |
| 顺带简化 | UPSERT 路径下 `preservedSnapshots` / `preservedTombstones` 的「读出→删除→写回」整套逻辑不再需要 |

**键的依据（实测，非假设）**：`template_component_snapshot` 与 `template_component` 两张表里，**同一模板引用同一组件多次的情况均为 0 组** ⇒ `(line_item_id, component_id)` 语义唯一。**刻意不带 `sort_order`** —— 页签顺序会变，用它做键反而会错配。

**手法**（A0 裁决）：**先用 Hibernate 实体 `UPDATE`**，靠 `statement-batch-size=100` 合批（`QuotationLineComponentData` 无 `@DynamicUpdate`，batch 可用）。实测不够快再考虑原生批量 —— **本期不预先绕过 Hibernate 写路径**（`repair-260828` 正在同类坑上，不叠加风险）。

**预估收益**（续存）：`prep` 5.2 → ~1.2 s；写入量 8.8 → ~1.9 MB；`flush` 11~30 → 3~8 s；端到端 21~35 → **8~15 s**。并消除 flush 那个 **2.7 倍波动**（波动源自 I/O 量）。

### B-8 `buildHitContext` 的第二个 N+1（开工后扩范围，用户裁决 2026-08-29）

🔬 **发现方式**：B-1/B-2/B-6 落地后主线亲验（真实 3.49 MB payload → worktree 临时 8095），主循环从 ≈400 s 降到 **21 ms**（`flush=0(x0)`、`assert=0(x0)`），但请求**仍 60 s 被 reaper 砍**。jstack 六次采样，**请求存活期间的四次全部**停在同一个栈：

### B-7 迁移：清理重复行 + 加唯一约束
