## ① 背景与目标

### 现在发生了什么

用户点「立即生成」出了新价格版本，转到价格调整审核列表**搜要审的料号，搜不到**；要等后台慢慢算到那个料号，它才出现。

**这不是搜索坏了。** 审核列表读的是审核行表 `material_price_review`（`PriceAdjustReviewService.list`，按料号 `like` 搜）。一个料号的审核行要等**后台把它的金额算完、事务提交**之后才写得进去（`PriceAdjustBudgetService.processMaterial`：进池判定、建行、试算全包在同一个 `REQUIRES_NEW` 事务里）。后台又是**单线程、逐个料号串行**（`runBudgetLoop`）。
⇒ **算到第几个，列表里就只有前几个。**

**当天还叠了一层（v2 更正，v1 证据写错了）**：18:00 那一版 `V26092003` 是**定时任务**生成的（正泰策略 `DAILY 18:00`），不是用户生成的。用户手动生成的是 17:46 的 `V26092001`（算到 818 行时被作废）和 17:59:52 的 `V26092002` —— **后者只活了 16 秒**，就被 18:00:08 的定时版作废，定时版又从头开始算。这一层不在本任务范围，已登记为 `BL-0314`（⑥ `D-10`）。

### 要等多久（实测，非估算）

客户正泰 `CUST-0004`，策略范围 **4558 个料号**（ALL 模式）：

| 版本 | 进池行数 | 耗时 | 速率 |
|---|---|---|---|
| `V26091901`（定时） | 4527 | **29.5 分钟**跑完 | ≈154 个/分 |
| `V26092003`（定时，立项采样时**正在跑**） | 1698 / 27.7 分钟 | 未跑完 | ≈61 个/分 |

同一段代码，速率差 2.5 倍，取决于当时的并发负载。大单单次试算按小时统计的均值：**低负载 297 ms（09-19 18 时）/ 高负载 695~737 ms（09-20 17~19 时）**。
⇒ **要审的料号排在队尾时，最坏要等 30~75 分钟。**

### 目标

1. **生成版本后十几秒内，该进池的料号全部出现在审核列表**，可搜可筛，带明确的「未计算」状态
2. **点某个料号，就单独把它算出来**
3. **后台照常把全部料号算完**（用户裁决：保留全量算），并按依据单分组并行提速（⑥ `D-3`）
4. **金额决策的守门不许破**：没算过金额的料号不能被通过，也不能被驳回（⑥ `D-6`）

### 不做会怎样

审核工作**无法开始**：财务打开列表搜要审的料号，得到空结果，分不清是「这个料号不涉及调整」还是「还没轮到它」，只能反复刷新干等半小时以上。

## ② 范围

### 做什么

| # | 交付内容 |
|---|---|
| **R-1** | **进池与试算解耦**：版本生成后，先用**常数条**批量查询一次性判定「哪些料号该进池」，再**一条语句批量建审核行**（`budget_status=QUEUED`），立即可搜可筛；试算从这一步剥离。🔒 判定口径一字不改（只改「数据怎么取」，不改「怎么判」）；靠「曾被驳回」进池、没有依据单的行（反例外）**进池即写 READY + 0 列**，不进试算队列；进池阶段的查询**全部走 Hibernate**，以便计数（见 ④ 测量口径） |
| **R-2** | **列表显示计算状态**：四态可见；未计算行金额显示「—」，🚫 不显示 0；顶部提示「共 N 条，其中 M 条未计算」。🔒 规则：**`budget_status` 只在审核状态为「待处理」时有意义** —— 已通过 / 已驳回 / 已作废的行不显示「未计算 / 计算」、不计入未计算数、不触发轮询 |
| **R-3** | **点击即算**：点未计算的料号，单独触发该条试算并**插队**；结果**写回审核行**。试算请求一律「先受理、再轮询结果」（前端超时与后端事务超时同为 60 秒，同步等会让超时显示成网络错误）。未计算的行点开自动算；计算失败的行不自动重算，抽屉里给「重新计算」；计算中的行等待结果。抽屉**先算、后取详情**，两步不并发 |
| **R-4** | **通过前守门**：勾选的行里含未计算项时，点「通过并升版」先**逐条依次**把它们算出来（显示进度），再弹影响面确认框（**以现网确认框为底**，新增「各料号金额」与「计算失败、不参与本次升版」两块），确认后只提交已算好的行。后端「通过」的既有守门（任何未算完 / 算失败的行整批拒绝）**原样保留** |
| **R-5** | **后台全量试算保留，按依据单分组并行**（⑥ `D-3`）：同一张依据单的料号永远在同一个工作线程上顺序处理，不同依据单之间并行，**料号最多的组先派**；并发度可配置，默认 3、上限 5。循环**退出前重扫**「未计算」行直到为空，保证中途被重新排队的行不会漏掉 |
| **R-6** | **三处状态机重定义**（`repair-260918` 交付物，判定地基被本次抽掉）：续跑判据（有审核行 ≠ 已算过）；作废覆盖未计算行；**启动时的续跑判定查询**把「有未计算 / 计算中行的待处理版本」也纳入，并把残留的「计算中」行重置为未计算 |
| **R-7** | **试算并发安全**（⑥ `D-4` `D-9`）：所有试算入口统一次序：**取锁 → 抢占 → 试算 → 条件完成 → 放锁**。锁 = **按依据单的进程内公平锁**（逐料号取放，公平锁保证点击即算能插进来）；抢占 = 条件更新、独立短事务立即提交，只有一方成功；条件完成 = 写结果时要求该行仍在「计算中」，否则整体回滚（中途被改配置重新排队的行，旧配置的结果不会覆盖上去）。覆盖：后台循环 / 点击即算 / 既有「重算」/ 抽屉详情的元素影响试算 / **正式升版任务**。「改策略 / 改比对列」触发的重算**收编**进后台循环（只标未计算 + 唤起循环，不再逐条派异步任务） |
| **R-8** | **依据单与依据行口径**（⑥ `D-5` `J-3`）：试算时按**进池时记下的依据单 + 料号**重找依据行；该单已不在活单范围内 ⇒ 标「计算失败：判断依据单已不在活单范围内」，留在待办池，**不推进指针**（顺带修掉现存潜伏缺陷：此路径下审核行会永远停在未计算）。同一张单里同一料号有多行时，按确定次序取第一行，进池 / 试算 / 抽屉**同一规则** |
| **R-9** | **驳回守门**（⑥ `D-6` `D-11`）：未算出金额的行（**含计算失败**）不能驳回 —— 前端置灰并按原因给提示，**后端同样拦**（与「通过」同一错误信封）。计算失败的行：超时类可「重新计算」；依据单失效类在下一版生成时按现有规则自动了结 |
