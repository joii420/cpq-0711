- **公平锁的 `tryLock()` 会插队**：`ReentrantLock(true).tryLock()`（无超时）不遵守公平性，会让刚放锁的后台线程重新抢到；`BasisQuotationLocks` 一律用 `tryLock(0, ms)` / `lock()`。
- **`ManagedExecutor` 会传播请求上下文**：并行工作线程若沿用它，请求作用域的 `DataLoader` 会被多个线程共用（expand 层非线程安全，06-22 翻车同源）。改用本类自建普通线程池，每个工作线程 `@ActivateRequestContext` 开独立上下文。
- **条件完成前不改托管实体**：原 `computeBudget` 直接改 `review` 实体字段并 persist；若保留，条件更新 0 行后提交时 Hibernate 仍会把脏实体刷回去，等于「丢弃」失效。改为纯内存结果对象 + 原生条件 UPDATE，0 行时 `setRollbackOnly`。
- **原生 UPDATE 里未出现的参数不能 setParameter**：FAILED 分支不含 warn/series 列，按实际拼出的列逐个绑参数，null 值带类型绑定（`CAST(:x AS uuid)` + `setParameter(name, null, UUID.class)`）。
- **202 返回时行必须已是 COMPUTING**：若 compute-now/recompute 只派发异步，前端/测试随即轮询会读到抢占前的 FAILED/READY 而误判结束（AC-13 R3「等回到 READY 再发下一条」会变成并发）。见 §5①的做法。
- **AC-22 diff 纯度**：正式升版两处取放锁不改原有行缩进，`status` 变量作用域问题靠把 `finally` 放到循环体末尾解决，而不是挪动原有声明。
- **测试写了别的任务的证据文件**：跑 `Ac260918T19…` 覆盖了 repair-260918 的已跟踪文件 `证据/测试/S-BE/AC-19/fingerprint-branch.json`，已用 `git show HEAD:<path> > <path>` 还原（本次运行的副本存在 scratchpad）。
- **`processMaterial` 的存量调用方**：生产代码已不再调用，但 `Rp0918aFixture` / `Decision39Test` 反射或直接调它；保留原签名，内部改为「同一套批量进池 + 统一次序试算」，AC-22 所列类全部保持原计数。
