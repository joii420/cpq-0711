# 追加 · F-7 补丁：轮询定时器必须用最新的 `load`（仍属 AC-30，主线审查发现）

## A. 改了什么
只改 `PAR/PriceAdjustReviewPage.tsx` 一个文件，一次保存：
1. 轮询 effect 的依赖从 `[rows, page, status, notComputedTotal, pageHidden]` 改为 **`[rows, page, status, notComputedTotal, pageHidden, load]`**，并**删掉**了 `// eslint-disable-next-line react-hooks/exhaustive-deps`，换成一段注释写明为什么 `load` 必须在依赖里。
2. 顺手修了**我上一轮 F-7 自己引入的** lint 错误：`onError: (e: any)` 改为 `(e)` + `(e as Error)?.message`（行为不变）。
轮询节奏（`nextListPollDelay`、5 秒 / 30 秒）、`load` 本身、`loadLatest` 都没动。

## B. 为什么选「加进依赖」而不是「ref 持有最新 load」
- `load` 只在 `status` / `keyword` / `breachedOnly` 变化时才换，而这些正是「参数变了、旧定时器就不该再用旧参数发请求」的时刻。加进依赖后，React 会在同一次提交里**先清掉旧定时器、再用新 `load` 重新计时**，旧参数的请求从源头上就发不出去。
- 依赖列表因此变完整，可以去掉 `eslint-disable`，让 `exhaustive-deps` 规则以后能机械地守住这里（见 D 的 X1）。用 ref 的写法仍要保留 disable，下次有人往 effect 里加变量时就没人报警了。
- 代价：边输边查时每敲一个字，轮询计时从头开始。轮询本来就只用来刷新计数，推迟几秒没有影响；节奏参数本身没变。
- 残余时间窗（推理，未实测）：提交之后、effect 执行之前的极短时间里，旧定时器如果恰好触发，发出的旧参数请求**先于**同一次提交里首屏 effect 发出的新请求，序号更小，会被 F-7 的判定丢弃。所以不会出现「旧参数请求覆盖新结果」。

## C. 单测
**未验证（单测层）**：这是 React effect 的依赖接线，本仓库没有 jsdom / testing-library，node 下的 vitest 挂不上 effect，也没有可抽出的纯逻辑（序号判定已由 `reviewLatest.test.ts` 覆盖）。改用 eslint 的 `react-hooks/exhaustive-deps` 规则做**机械证明**（D），浏览器层面的行为请主线在 5295 复现。
