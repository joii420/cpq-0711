## 1. 根因证据（证实主线判断）

⇒ 只要读者首尾交叠，写者就被饿死。3 个工作线程的试算事务（各自 `FOR SHARE` 持到提交）正是首尾交叠的读者流，所以生成请求的 `UPDATE element_price_version SET status='SUPERSEDED'` 要等整轮结束。这与测试员现象吻合：返回比 `budget-compute … ms=4801` 晚约 0.1 秒；A 全部 READY 后才被作废；没有停止日志。

生成入口只有一个：`generateVersionAndEnqueueBudget`（手动 `PriceAdjustVersionResource:48` 与定时 `PriceAdjustScheduledScanService:57` 都走它）。

## 2. 修法（选 ⓐ：按版本的进程内公平读写锁）

新增 `VersionSupersedeGate`（`@ApplicationScoped`，`ConcurrentHashMap<UUID, ReentrantReadWriteLock(true)>`，单实例部署前提写进注释）：
- **读者**（包住每一个会执行 `FOR SHARE` 的事务，在事务开始前取、提交后放）：`computeTx` 的全部调用点、`markFailedIfComputing`、`enqueueScope` / `enqueueMaterials`。
- **写者**：`generateVersionAndEnqueueBudget` 在调用 `generateVersion`（`@Transactional`，经 ArC 自调用拦截，返回即已提交）**之前**，先短事务查出该客户当前 PENDING 版本 id，对它取写锁；`generateVersion` 返回（已提交）或抛异常后在 `finally` 放锁；之后才异步派发新版本的预算。
- 公平模式下写者一旦排队，**新读者全部排在写者之后** ⇒ 生成请求只等**在途的**那几次试算（≤ 后台名额 3 + 点击名额 2 + 进池 1），符合 api.md §2.1。
- 写者提交后，排队的读者进入试算事务，`FOR SHARE` 读到 SUPERSEDED ⇒ `VersionNotPendingException` ⇒ 每个工作线程 STOP ⇒ 打「版本已作废，停止剩余 n 个料号」（文案不动）。剩余行已被生成事务里的 `voidPendingByVersion` 作废带走。
- **生成失败**（抛异常 / 校验不通过）⇒ `finally` 放写锁 ⇒ 读者照常进入、版本仍 PENDING ⇒ 循环继续。循环从来没停过、只是等了一下，所以不需要额外唤起，也不会留下 QUEUED 行没人算（这是相比 ⓑ 的主要理由）。
- **AC-20 语义不变**：点击即算在途 = 持读锁 + 持 `FOR SHARE` 的读者 ⇒ 写者等它提交后才作废 ⇒ ① 生成在该次试算提交后返回；② 行最终 VOIDED；③ 作废后无写入；④ 再点 409。`FOR SHARE` 的位置与级别都不改。

**次序（新锁的位置）**：
- 试算：名额 → 依据单锁 → 抢占（独立短事务，不取版本读锁 —— 它没有 `FOR SHARE`）→ **版本读锁** → 试算事务（`FOR SHARE` … 条件完成）→ 提交 → **放版本读锁** → 放依据单锁 → 还名额。
- 进池：**版本读锁** → 进池事务 → 提交 → 放读锁（进池不取名额 / 依据单锁）。
- 生成：**版本写锁** → 生成事务 → 提交 → 放写锁。写者持锁期间不取名额、不取依据单锁。

**无死锁论证**：
- 读者在等读锁时可能持有名额与依据单锁，但写者从不需要这两样。
- 读者持读锁期间只等 DB，而与它冲突的 DB 写者（生成事务）此刻不可能持写锁在跑，因为读写互斥。
- 写者持写锁期间只等 DB 行锁；同进程的读者都被挡在锁外，不持有 `FOR SHARE`。
- 在主线定义的次序链上，新锁位于「抢占」与「试算事务」之间，读者持有它时不去等任何写者持有的东西。

**已知边界（写进注释）**：
- 单实例前提：多实例时进程内锁挡不住别的实例的读者，会退回 PG 行锁行为（与 repair-260918 D-7 同前提）。
- 两个生成请求同时进同一客户：各自先查 PENDING，后者可能锁的是即将被前者作废的版本。这种情况只会退化为不加速，不会死锁、不会错写。
