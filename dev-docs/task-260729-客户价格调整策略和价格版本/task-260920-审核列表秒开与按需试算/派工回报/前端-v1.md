### F-2（AC-5、AC-7、AC-20、AC-21）点击即算
- 唯一实现 `computeNowAndWait`：`compute` 模式先 POST compute-now（202），然后 **每 1 秒** GET `/row`，直到 `READY/FAILED` 或 `reviewStatus≠PENDING`；**90 秒**未结束 → `TIMEOUT`，提示「计算较慢，可稍后刷新」。`waitOnly` 模式（行已是 COMPUTING）只轮询、不 POST。
- 页面 `computeRow`：三个入口（「计算」链接、抽屉、批量通过）共用；**同一行正在算时，第二次点击直接复用同一个 Promise**（不会重复 POST）；立即把该行本地置为 `COMPUTING`（「计算」链接消失 = 禁止重复点）；结束后用 `/row` 的返回值**就地替换该行**，🚫 `load(page)`。
- FAILED 行内「重算」改走 compute-now（F-2 原文）；工具栏「重算预算」没动。
- 抽屉：`drawerComputeMode` —— QUEUED → 自动算；COMPUTING → 只等；FAILED → **不自动算**，显示原因 Alert +「二」位置换成「计算未完成，暂无法判断是否可接受」+「重新计算」按钮（点了才调 compute-now，结束后重取详情）；READY / 非待处理 → 直接取详情。
- 🔒 **先算后取详情**：计算期间整个抽屉只显示「正在计算该料号的影响…」，**不发** `GET /{id}`；算完才发。
- 失败原因取详情接口新增的 `budgetError`。
- 「已被取代」：compute-now 409 且 **`payload.code === 'REVIEW_NOT_PENDING'`**，或轮询看到 `reviewStatus==='VOIDED'` → 提示「该价格版本已被新版本取代」并静默刷新列表；抽屉内同时显示该文案的 Alert。其它离开待处理的情况提示「该料号已不是待处理状态」。

## 4. 规避掉的坑
1. **409 业务码在 `err.payload.code`，不在 `err.code`**：后端信封是 `ApiResponse{code: 409（整数）, message, data: {code: 'REVIEW_NOT_PENDING', invalidItems}}`，而 `buildApiError` 把顶层整数 409 放进了 `err.code`。照「data.code」的字面去读 `err.code` 会永远走不到「已被取代」分支。已用真实 `buildApiError` 构造信封写成用例 + 还原实验 E2 验证。
2. **没用 `runBatch`**：它默认 `concurrent=true` 会一次全发；另写了 `runSequentialCompute`，并用 `maxInFlight=1` 断言。
3. **抽屉关闭 / 批量取消不中止页面级计算**：服务端受理 compute-now 后已经在算，如果把中止信号传进共享计算，列表行会停在本地的「计算中」，而另一个入口复用同一个 Promise 时也会拿到「已中止」。现在页面级计算始终跑到底并就地替换，抽屉 / 确认框只忽略迟到的结果。
4. **确认框两步用同一个 Modal 元素**：条件渲染两个 `<Modal>` 会在切换时卸载重挂、闪一下。
5. **轮询用一次性 setTimeout + silent**：旧代码 5 秒一次还带表格 loading 闪烁；改后响应慢时请求也不会堆积。
6. **非待处理 + READY 的行保留比对标记**：原型状态 6 说明写的是「非待处理行一律显示『—』」，但它画的只有非 READY 的已作废行；若把已通过行的比对标记也换成「—」，会丢掉现网信息（N-5：既有功能不改）。见 §5 待裁 2。
7. **`tsc -b` 而不是 `tsc -p tsconfig.json`**（后者是空验证）；**grep 一律用 `/usr/bin/grep -a`**。
8. **F-3 的「改动前」数字在改代码之前实测**，没有去用共享 5174（它服务主仓）。

9. **停临时 vite 时 `pkill -f 'vite --port 5120 ...'` 把执行它的这个 shell 也匹配上、一起杀掉了**（exit 144，后续命令没跑）。随后用 `ps` + `curl` 单独确认 vite 已停，再单独补跑 tsc 与 vitest。主线亲验停进程时同样要注意。

## 6. 与原型的偏差（逐屏）

**列表**
1. 「未计算」灰标、「预算失败」红标、「待处理」橙标用的是 AntD `Tag` 的默认 / 预设色 —— 组件库等价实现。
2. 顶部「共 N 条，其中 M 条未计算，正在后台计算…」、按钮旁提示：原型是纯文本 span，实现同为 span（颜色取原型的 `#d46b08` 与 45% 灰）。**一致**。
3. 状态 3 提示条：原型是手写的黄色块，实现为 AntD `Alert type="warning"`（无图标，文案里保留「⚠️」）—— 组件库等价实现。
4. 「计算中」的转圈在截图里出现在文字**右侧**（原型在左侧）。代码里 `Spin` 写在文字前面，与改动前的「预算计算中」同一写法，是 AntD v6 `Spin` 的内联排版造成的 —— 归为组件库所限；**是否要调位置请主线裁决**（换 `LoadingOutlined` 图标可以放到左边）。
5. 已算完的行「🔴1 🟠0 / 1列」在截图里显示成方框：无头 Chrome 缺彩色 emoji 字体，属于截图环境问题；这是既有 `buildComparisonStatusLabel` 的输出，本次没动。
6. 没实现：状态 1 工具栏「已选 0 项」前的转圈；查询 / 重置保留现网的链接而非原型的按钮（见 §5 第 4、5 条）。

**抽屉**
7. 状态 1 转圈用 AntD `Spin size="large"` —— 组件库等价实现。
8. 状态 3 的失败 Alert 只放了原型第一行（「该料号的影响计算失败：<原因>」）；原型 Alert 里后两行是写给开发看的说明（「原因取自详情接口的 budgetError…」），没搬进产品界面。
9. `impl-drawer-state3-failed.png` 里「财务自检…对不上」是模拟数据造成的（元素影响 0 与依据单小计差不一致），是既有逻辑，与本次无关。
10. 状态 4（READY 行直接显示）没有单独截图；vitest 的 `drawerComputeMode('PENDING','READY') === 'none'` 已覆盖。

**确认框**
11. 第 1 步进度条用 AntD `Progress`，逐行结果用 `Tag` / `Spin` —— 组件库等价实现。
12. 「各料号金额」原型用绿色虚线框标「本次新增」，那只是原型的标注，实现里没有画框。
13. 第 3 步失败块：原型最后一行小字（「失败清单来自第 1 步…🚫 不经影响面接口…」）是开发说明，没搬进界面。
