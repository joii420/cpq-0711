## 任务分解

| 编号 | 服务的 AC | 任务内容 |
|---|---|---|
| **F-1** | AC-1, AC-4 | **「未计算」与「计算中」拆成两个状态**。`:140-142` 现在 `QUEUED \|\| COMPUTING` 都渲染「预算计算中 + Spin」。改为：<br>· `QUEUED` → **静态**灰色标签「未计算」+ 一个「计算」链接（触发 F-2），🚫 **不转圈** —— 解耦后它可能要等十几分钟才轮到，转圈会让用户以为马上就好；<br>· `COMPUTING` → 保持 Spin +「计算中」。<br>文案与样式以 `原型图/审核列表-未计算态.html` 为准。 |
| **F-2** | AC-5, AC-7, AC-20, AC-21 | **点击即算**。两个入口走同一个函数：① F-1 的「计算」链接；② 点料号链接打开抽屉时，若该行 `budgetStatus !== 'READY'` 则**先调** `POST /reviews/{id}/compute-now`（`api.md §2`）。<br>要求：① 调用期间该行显示「计算中」并禁用重复点击（`AC-21` 前端侧）；② 响应回来后**就地替换该行**（响应字段形状与列表行一致，`api.md §2` 已保证），🚫 不要 `load(page)` 整页重拉；③ `budgetStatus=FAILED` 时按既有 FAILED 分支渲染 + 原因 Tooltip（`AC-7`）；④ 收到 `409 VERSION_SUPERSEDED` 时提示「该价格版本已被新版本取代」并刷新列表（`AC-20`）。 |
| **F-3** | AC-1 | 🚨 **轮询策略改造（不做即性能回归）**。现状 `:81-89`：只要页面上有一行 `QUEUED`/`COMPUTING` 就每 5 秒 `load(page)` 全量拉列表。解耦后**开局 4500 行全是 `QUEUED`、持续十几分钟** ⇒ 约 180 次全量列表请求，而列表每行还要查客户名/依据单（`PriceAdjustReviewService.toListItem:100-141`，每行 3~6 条 SQL）⇒ **会反过来拖慢正在跑的后台试算**。<br>改为：① 轮询只在**本页存在 `COMPUTING` 行**时启动（真正在算的才值得盯）；② 页面上存在 `QUEUED` 行时改为**低频**（≥30 秒）刷新，且只为更新 §1.1 的 `notComputedTotal` 计数；③ 页面失焦（`document.hidden`）时暂停轮询。<br>具体阈值以原型图与本表为准，实现后在回报里给出「15 分钟内发起的列表请求次数」实测值。 |
| **F-4** | AC-8, AC-9, AC-11 | **「通过并升版」守门改造**。`allPendingReady`（`:174-179`）现在「含非 READY 即禁用」，本次改为：<br>· 含**非 `PENDING`** 审核状态 → 仍禁用（原样保留）；<br>· 含 `QUEUED`/`FAILED` → **不再禁用**，点击后先调 `POST /reviews/compute-batch`（`api.md §3`）并显示进度「正在计算 n/N」（可复用既有 `runBatch` 的进度形态，`:200-206`）；<br>· 批量算完后再调 `impact` 预览、打开 `ApproveImpactModal`。<br>🚫 **仍含 `COMPUTING` 的行不得提交** —— 后端会返 409（`api.md §4`），前端应先等它算完或提示用户稍候。 |
