## ① 背景与目标

### 现在发生了什么

用户点「立即生成」出了一个新价格版本，转到价格调整审核列表**搜自己要审的料号，搜不到**；要等后台慢慢算到那个料号，它才出现。

**这不是搜索坏了。** 审核列表读的是审核行表 `material_price_review`（`PriceAdjustReviewService.java:70-93`，按料号 `like` 搜），而一个料号的审核行要等**后台把它的金额算完、事务提交**之后才写得进去（`PriceAdjustBudgetService.processMaterial:298`，进池判定、建行、试算全包在同一个 `REQUIRES_NEW` 事务里）。后台又是**单线程逐个料号串行**（`runBudgetLoop:88-124`）。

⇒ **算到第几个，列表里就只有前几个。**

### 要等多久（实测，非估算）

客户 `CUST-0004` 策略范围 **4558 个料号**（ALL 模式）：

| 版本 | 进池行数 | 耗时 | 速率 |
|---|---|---|---|
| `V26091901` | 4527 | **29.5 分钟**跑完 | ≈154 个/分 |
| `V26092003`（立项采样时**正在跑**） | 1698 / 27.7 分钟 | 未跑完 | ≈61 个/分 |

同一段代码速率差 2.5 倍，取决于当时并发负载。⇒ **要审的料号排在队尾时，最坏等 30~75 分钟。**

### 目标

1. **生成版本后十几秒内，该进池的料号全部出现在审核列表**，可搜索、可筛选，带一个明确的「未计算」状态
2. **点某个料号就单独把它算出来**（实测单次试算 331~896 ms，这条路本来就够快）
3. **后台照常把全部料号算完**（用户裁决：保留全量算），并把这一轮从 30~75 分钟压下来
4. **金额决策的守门不许破**：没算过金额的料号不能被批准升版

### 不做会怎样

审核工作**无法开始**：财务拿到「今天调价了」的通知，打开列表搜要审的料号，得到空结果，无从判断是「这个料号不涉及调整」还是「还没轮到它」。目前唯一的办法是反复刷新等半小时。

## ② 范围

### 做什么

| # | 交付内容 |
|---|---|
| **R-1** | **进池与试算解耦**：版本生成后，先用批量查询一次性判定「哪些料号该进池」并**批量建审核行**（`budget_status=QUEUED`），使其立即可搜可筛；金额试算从这一步剥离 |
| **R-2** | **列表显示计算状态**：`QUEUED` / `COMPUTING` / `READY` / `FAILED` 四态在列表可见；未计算行的金额列不显示 0 |
| **R-3** | **点击即算**：在审核列表点一个未计算的料号，单独触发该条试算并插队，算完就地更新该行 |
| **R-4** | **通过前守门**：勾选的行里含未计算项时，点「通过并升版」先**批量试算这几条**，把金额与影响面摆出来让用户确认，确认后才真升版 |
| **R-5** | **后台全量试算保留并提速**：继续把范围内全部料号算完；提速方式见「⑥ 待 A0 裁决项」 |
| **R-6** | **三处状态机重新定义**：`repair-260918` 交付的「预算续跑 / 作废即停 / 启动收尾」，其判定地基是「已处理 = 有审核行 ∨ 指针已指向本版本」（`PriceAdjustBudgetService.java:222-225`）。解耦后**有审核行不再等于已算过**，这三处必须改判据，否则 `QUEUED` 的行会被当成已完成、永远不补算 |

## ⑥ 方案（闸门 A0 已裁决 · 2026-09-20）

> 本节只记**裁决结果**。候选与权衡在 A0 的对话里呈报过，按 `docs/rules/task-docs.md §5` 不落文档。

### `D-1` · R-5 提速走**方案甲：先压 SQL 往返，再按依据单分组并行**（用户 2026-09-20 裁决）

**两步，顺序不可颠倒：**

1. **压 SQL 往返（零竞态，先做）** —— 按 `basis_quotation_id` 把料号分组（实测约 23 组，3 组占 99.2%），组内把**单据级不变量**预取一次（目标版本价、冻结页签结构、组件字段、价格承载组件角色、版本号），经 `upgrade()` **已有的** `versionPricesOverride`（`MaterialVersionUpgradeService.java:205-206`）与 `precomputed`（`:186-187`）重载注入 —— 两者**传 `null` 即现状行为**，是既有纪律。
   🚫 **不改 `upgrade()` 的算法本身**，只改「调用它之前先把不变量准备好」。
2. **组间并行、组内严格串行** —— 每个 worker 独立 `@ActivateRequestContext` + 独立事务；**同一张依据单的料号永远在同一个 worker 上顺序处理**。

**裁决依据（实测）**：单次试算 `sql=28~40` 条、远端库单条往返 9~15 ms ⇒ **SQL 往返占试算耗时的 66~94%**，瓶颈是 I/O 次数不是 CPU，先减往返比先加线程对症且无竞态。

**为什么组内必须串行**：2026-06-22 被 revert 的那次（`master 934c463`）正是「同一张单的多行并发」。分组并行把并发边界划在单据之间，避开该形态。

**已否决备选**：
- **丙 · worker pool 任意料号并发** —— 收益最高（配合第 1 步可到 5~7 分钟），但须改 `ComponentDriverService` 的缓存返回方式（防御性拷贝）与 per-worker 缓存隔离，动的是 `docs/三大核心模块基线.md` 的报价单渲染层，且正是历史上翻车的形态。**若方案甲实测到不了 `AC-14` 的 15 分钟，再作为第二轮**（那时已有 `AC-13` 的对拍装置）。
- **乙 · 只压 SQL 不并行** —— 零竞态但推算约 27 分钟，达不到 `AC-14`。

### `D-2` · 性能目标维持 `AC-1` ≤15 秒 / `AC-14` ≤15 分钟（用户 2026-09-20 裁决「就这两个值」）

### 🔒 一票否决项（不随方案变）

`AC-13`（同数据连生两版，全部审核行金额排序后取哈希，**两次必须完全相同**）是并行正确性的**唯一判据**，不依赖「我认为哪些缓存安全」这类判断。
依据：2026-06-22 那次**速度达标但产出非确定**，73 行错 9 行，**单跑与单测都看不出来**。
⚠️ 立项期已实证 `expandCache` 的 key 含 `partNo` 与 `qidTag`（`ComponentDriverService.java:405-408`）⇒ 不同料号条目不共享；但全工程另有 4 个进程级 Caffeine 缓存（`FormulaEvalCache` 为 `static`，另 3 个在 `datapath/cache/`）**未逐个核其值是否可变** —— 所以判据取 `AC-13`，不取该分析。
