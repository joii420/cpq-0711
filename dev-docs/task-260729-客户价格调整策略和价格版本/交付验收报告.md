## 2. 🔴 上线前必读（业务方视角）

### 2.1 成本预警线在生产上不会触发

**现象**：屏 3/屏 4 的红/橙标记，上线后大概率**全绿**。

**原因**：本环境所有已检查的真实报价单，**核价侧总小计恒为 0**（V6 成本数据未导入/未联动）。差异 = 报价侧成本 − 核价侧成本，核价侧恒 0 → 差异恒为正 → **RED 结构上不可达**。

**不是**：功能有 bug（判定逻辑已用构造数据正反双向验证通过）。

**要做什么**：上线前确认 V6 成本数据已导入并与报价单关联，否则预警线形同虚设 —— **全绿不代表没有超支，代表没有可比的核价成本**。

### 2.2 核价卡片内同一元素可能出现两个价

见 `需求说明.md §12.6.4`（业务方 2026-08-04 明示接受）。

**一句话**：某零件若**既是别人的子件、自己又是可独立核价的组件**，它下挂物料的元素价跟随**它自己**的价格版本，而非当前卡片所属成品的版本。

**识别方法**：查 `bom_closure` 该物料的归一根是否等于当前卡片料号（SQL 见 §12.6.4）。

### 2.3 已发出单在屏 7 显示「尚未更新」

见 `需求说明.md §11.7.3`（业务方 2026-08-04 裁定）。

`SENT`/`ACCEPTED` 等单按 §11.6.0 有意排除、不参与自动更新，实际停在旧价。屏 7 显示「尚未更新」而非「已升版」—— **这是刻意的，不是漏更新**。

### 2.4 2026-07-26 前定型的单，切版预览核价侧是空的

**现象**：屏 7 点开这批老单的历史版本预览，**核价侧无内容**。

**原因**：那批单定型（`sealed`）的那一刻，`costing_card_values` 还没被懒算出来，快照里存的就是 `null`。

**这不是加载失败，也不是 bug** —— `#18` 忠实返回了快照里的真实内容。

**为什么不补**（技术总监 2026-08-04 裁定）：

> `R` 快照的语义是「**冻结当时的样子**」。事后回填等于**篡改历史** —— 那批单当时确实没有核价卡片值，回填出来的数据不是它们定型时的状态。

**影响范围**：库里 21 条 `sealed=true` 的初版快照中的一部分（已实证 `QT-20260726-0003` 核价侧为 JSON `null`）。此后新定型的单不受影响。

### 2.5 🔧 「只加锁不解锁」缺陷族（原推迟理由已被证伪，本轮修复其中三条）

> ⚠️ **本节曾写错**：原文称「元素被停用」与「用户改了这行元素」在后端判据相同、必须改数据协议才能区分，据此推迟。
> **该前提已被证伪**（后端 2026-08-05 三重证据）：`customer_price_adjust_element` **无 enabled 列**；`doPutElements` 注释明写「**从不读 `element.status` 做任何过滤/剔除**」；§11.2.1 明写「已勾选的元素后来被停用 → **保留在清单里**并标『已停用』，照常参与调价」。
> **即「停用」走 ∈清单 分支，与「∉清单」零交集** —— 不存在歧义，也不需要改数据协议。

#### 缺陷族全貌（4 个入口，规范都要求「应恢复可编辑」）

| # | 入口 | 现状 | 规范依据 | 本轮 |
|---|---|---|---|---|
| 1 | **元素∈清单但解不出价** | 删值不删锁 → **死格**（值没了、锁还在） | `testcases #47` + §11.4.1「无价元素不死格」 | ✅ **已修** `031a2dfa` |
| 2 | **元素∉清单**（财务取消勾选 / 用户改行） | `continue`，锁保留 → 永久锁死 | 验收 `#58`「确认后该元素出清单、**对应单价列恢复可编辑**」 | ✅ **本轮修** |
| 3 | **料号∉范围** | `continue`，锁保留 | 需求说明 `:585`「移出范围的料号，其单价列可编辑性**随之恢复**」 | ✅ **本轮修** |
| 4 | **策略停用** | `prefetch` 返 null → **整单**不动、锁全保留 | E11 断链 4：只读作用域 = 元素∈清单 ∧ 料号∈范围 ∧ **策略启用** | ⏸️ **未修**（见下） |

#### 🔴 入口 2 的严重性：系统做了承诺却没兑现

`doPutElements:409-412` 在财务取消勾选元素时抛 `ElementUnselectNeedsConfirmException`，携带 `countUnlockedQuotationsForElements(customerNo, removed)` —— **真的去 JOIN `quotation_line_component_data` 数了「将解锁的存量单张数」**，并在二次确认弹窗里明示「N 张存量单该元素单价列将解锁」。

> **系统当面告诉财务「这 N 张单会解锁」，然后一张都没解锁。**

⚠️ 连带影响：验收 `#58` 此前判 PASS，**但它只验了确认弹窗与文案、没验解锁本身** —— 已要求补验。

#### 入口 4 为什么本轮不修

**风险不对称**：`prefetch` 返 null 时「整单不动」是短路结构，改成「还得跑一趟纯撤锁扫描」与现有设计冲突，改动面远大于入口 2/3；且「停用整个策略」是罕见运维操作，不像入口 2/3 是日常业务动作。已记 BACKLOG。

#### 另一处未修（低可达性）

`snapshot_rows` 侧 guard 只对「从未锁过」的行正确：若 driverRow 带**上一轮遗留**的 `__priceLocked=true`、本次又解不出价，guard 只 `continue`、残留锁不撤 → 前端优先读 driverRow → 该格仍死。
**可达性低**：需「先有价被锁 → 后失价」，而 §11.3.2.1「无价沿用上一版价」基本堵死版本通道，残余风险只在「指针为空走实时算」。`#47` 场景②不受影响。

### 2.6 🔴 上线部署当刻会看到一批价格版本涌现（属预期，别当故障）

`#4` 定时补跑修复后，**首次启动时所有「已启用 且 当天执行时刻已过」的策略会立即各生成一次版本**。

这正是「补跑」的定义 —— 修复前这些版本会被永久丢失。**部署当刻看到一批版本涌现是正确行为，不是故障。**

### 🔴 关闭后的两个连带效果（业务方需知）

**① 定时扫描停止**：被关闭的客户不再每日/每月自动生成价格版本。
- **手动生成仍可用**（`generateVersion` 不看 `enabled`）
- **现存 PENDING 版本不会消失**，财务照常审核/通过/驳回；副作用只是它不再被新版本自动 supersede，会一直挂着

**② 已锁定的单价列会解锁 —— 但是惰性的**

撤锁只在该单**下次保存**（`saveDraft`）或走 admin 归位端点时执行。**关闭策略那一刻不会立即解锁。**

## 6. 交付过程中的方法论问题（技术总监自陈）

### 6.1 任务书三次同型遗漏

`api.md` 按**端点**组织、`backtask.md` 按**业务流程**组织、`fronttask.md` 按**屏**组织。屏↔端点对应直观 → **前端一处未漏**；业务流程↔端点无天然对应且**从未交叉核对** → 后端漏三批（R 版本快照 / 策略 CRUD / 4 个端点）。

**加剧因素**：`api.md §7`「契约自检清单（前后端联调前逐条对）」**自始至终无人执行**。前端照契约把屏 7 做全（类型 + 纯函数 + 4 条单测 + Drawer 消费），调的是不存在的端点 —— 本该在联调时 5 分钟暴露，拖到验收末期。

**下次的做法**：任务书产出后、开工前，**机械对账一遍 api.md 端点清单 vs 前后端任务块**，逐个打勾。这是纯机械劳动，成本极低，收益是本次三批遗漏全部可提前避免。

> ⚠️ **对账要 `curl` 不能只 `grep`** —— 本轮 `template-series` 就是 `grep @Path` 打了勾、实际路由 404（详见 §6.3）。正确做法见后端产出的《22 端点可达性表》：逐个真实请求，只看「不是路由 404」，401/400/200 都算可达。

### 6.2 设计闸门有效

三次「先出清单再动手」的要求全部拦住了东西：S6 写回前的对拍清单 / 前端改公式引擎前的影响面清单 / 动共享渲染基础设施前的评估 —— **三次里两次证明若直接批准就是改错东西**。

### 6.3 三类「看起来对，实际不工作」的缺陷（本轮集中暴露）

本轮验收挖出的问题里，有三个**都能躲过编译、单测和 grep**，只在真实运行时暴露。它们值得单列，因为常规自检对它们完全无效：

| 类型 | 实例 | 为什么躲得过 |
|---|---|---|
| **代码对称但数据断供** | `#42③` 详情页徽标 | `ReadonlyProductCard` 与 `QuotationStep2` 对称读 `__priceLocked`，**符合 AP-50**；但角色字段只冻进 `quotation_view_structure`、详情页走模板快照 → 判定恒 false。**代码审查看不出来** |
| **`@Path` 存在但路由不可达** | `template-series` 404 | JAX-RS 两阶段分发：先选最具体的**类级** `@Path`，再在类内找方法，**不回溯**。路径字符串明明在代码里，**grep `@Path` 对账会打勾** |
| **测试绿在错的地方** | `#4` 定时补跑 | `computeSlotIfDue_daily_wrongMinute_notDue` **断言的正是 bug 本身**（`09:00` 策略在 `09:01` → `assertNull`），与 `testcases #4` 补跑要求直接冲突。**10 条全绿，其中一条锁死了错误行为** |
| **注释描述了不存在的功能** | `#4` 类头注释 | 声称"服务重启错过执行点，下次扫描天然补上"—— 而第一行 `if (now.getMinute() != executeTime.getMinute()) return null` 就返回了，**根本走不到 slot 计算** |
| **注释以「已实现，别重复造」的口吻说谎** | `#6` | `PriceAdjustStrategyService:270` 写着「复用 B4 `processMaterial` 的 pool-entry 判定，不重复实现」—— **那个判定从来就不存在**。任何人读到这句都会**停止追查** |
| **键名前缀导致解析恒空** | `#6` 实现期（已避开） | `driverRow` 的键是 `_元素`（带下划线前缀）非 `元素`；读裸键 → 相关元素集合恒空 → 保守兜底恒触发 → **判定永不生效且不抛任何错**。单元夹具（键即字段名）测不出，只有真实数据能兜住 |

**共同教训**：

> **「代码里有」不等于「运行时成立」。** 契约对账要 `curl`（证明请求真能走到方法），不能只 `grep`（只证明路径字符串存在）；渲染一致性要看**生产可见**，不能只看代码对称；测试全绿要问一句**它断言的是不是你想要的行为**。

第三类最危险 —— 前两类至少"没人验过"，第三类是**有人验过、而且验错了方向**，还留下了一条绿色的、看起来很可靠的证据。

**六类的共同点：失败全是静默的。** 不抛异常、不红字、不编译报错，只是让功能"看起来实现了"。常规自检（`tsc` / `mvn compile` / 单测全绿 / grep 打勾）对它们**全部无效**。唯一能兜住的是**真实数据 + 真实运行时**：

- 单元夹具的键就是字段名，测不出 `_元素` 前缀问题
- 代码审查看不出详情页数据断供
- `grep @Path` 查不出 JAX-RS 不回溯
- 单测全绿掩盖了断言方向写反

### 6.3.0 「看起来像数据丢失、实际是设计」族（验收期两次误判）

验收期测试工程师两次把**设计行为**误判为 bug，两次都自己查到设计依据并纠正。这一族值得单列，因为**误判方向都是"以为丢数据了"** —— 而这是最容易让人立刻上报、并让实现方回头去查一个不存在的缺陷的方向。

| 实例 | 表面现象 | 实际设计 | 依据 |
|---|---|---|---|
| **`#29`** 升版后价格"被清空" | `row_data` 里价格字段不见了 | **S4b：非手动行只删不覆盖**，权威值在 `snapshot_rows.driverRow`（核对为 `Cu=171.368` / `Ag=43358.75`，精确等于本版价） | `MaterialVersionUpgradeService:457-465` |
| **`#32②`** 传 `null` 未触发必填校验 | `PUT elementCodeField:null` → 200 且字段未变，疑"校验被绕过" | **部分更新语义：`null`=不动、空串=清空**（与 `dataDriverPath`/`rowKeyFields`/`treeConfig` 同一套约定）。改传空串立即拿到 `400 COMPONENT_ELEMENT_BINDING_REQUIRED` 且未落库 | `ComponentService.java:716` |

> **通则**：系统里存在"看起来像数据丢失、实际是设计"的写入与存储语义。**改字段前先确认该字段的更新约定（`null` 是不是"清空"），查数据前先确认该值的权威存储位置（是不是在你查的那张表/那个键里）。**

⚠️ **验证一个"设计"必须走完两步**：确认它是设计（找到依据）**+ 用正确的输入拿到预期结果**。只做第一步 = 停在"哦这是设计"，那和没验一样 —— `#32②` 是改传空串真拿到 400 才算验完。

### 6.3.1 共享 dev server 的心智模型盲区（本轮事故）

修 `#6` 期间共享 8081 编译失败、挡住所有会话，成因是**先落调用点、方法定义还没写完**，热重载恰好扫到中间态。

> **worktree 隔离了 git 工作区和分支，但没有隔离运行时。** 在共享 dev server 上开发，编辑器里的"半成品状态"是**会被别人看见的** —— 这和在隔离环境里随便改的心智模型完全不同。

**两条纪律**（后端自陈，已验证有效）：

1. ⭐ **重构顺序：先加新方法、再改调用点** —— 让任一中间态都可编译。这条比"改完记得编译"更根本，因为它让错误状态压根不存在
2. 改共享环境的代码前先 `./mvnw -o compile` 自检，比等热重载报错快

### 6.4 纪律与事实是两条独立的记录，不要合成因果链

C4 交付时，后端发现 `COSTING_CARD` 有完全相同的缺口，**按任务书边界没有顺手扩围，而是来问**。事后查明：核价侧从不写 `__priceLocked`，回填是空转 —— 扩围了也没用。

两条结论必须**分开归档**：

| | 内容 | 作用时刻 |
|---|---|---|
| **纪律条**（流程） | 任务书未授权的扩围，即使技术上「顺手」也不做 | 作用在**决定做不做的当下** —— 信息不全，但必须行动 |
| **事实条**（技术） | 核价侧无 `__priceLocked` 写入 → 回填角色字段空转，缺口在上游 | 作用在**下一个人要不要做的将来** —— 信息已全，避免重踩 |

> **合成一条会读成「因为不扩围所以躲过一劫」—— 那是运气叙事。**
> 分开写才是：纪律让人在信息不全时不犯错，事实让下一个人不必重新查。**用后者评价前者是事后偏见** —— 当时若掌握那个事实，根本不需要动用边界纪律。

### 6.5 并发造数撞车（技术总监编排失误）

**经过**：同一时间派后端 seed 四态数据、派测试造 P0 数据，**两条指令都没指定客户**，都默认落在 `CUST-0001`。

**真实损害**（与第一判断相反）：
- 测试**没有**覆盖后端的料号范围 —— 审计表实证该表撞车前就是空的
- **反方向有真损害**：测试的指针（11:58:39）外键指向后端的 `element_price_version`（11:58:36），相隔 3 秒；测试的 approve 流走 `findPending(customerNo)` 抓到了后端那条 PENDING 版本，而**该版本元素价明细是 0 行** → 测试那批 P0 结果不可信，已作废重跑

**两个做对的地方（值得沿用）**：

1. **手工 UUID 用可读模式**（`0729aaaa-0000-4000-8000-0000000000XX`）+ 可辨识料号名（`ZZTEST-0729-*`）。正是它让另一方**一眼认出「这不是我造的」**，而不是当成系统脏数据删掉
2. **发现争用后立刻停手、如实报告已造成的损害、不猜测对方状态硬恢复**。若按常规"顺手清理干净"，会把对方正在用的 fixture 一起抹掉 —— 对方还在写代码，会当成自己实现有 bug 去查

**已定纪律**：各方造数带**可辨识前缀**（后端 `ZZTEST-0729-` / 测试 `QA-0729-`），并按客户号分流独占。

**下次的做法**：派并发 agent 前，**先分配互斥的数据域**（客户号 / 前缀），写进指令里，而不是等撞了再分。
