## 续集：预算/dryRun 路径漏了 `@ActivateRequestContext`（同根因第二次）

**背景**：BL-0108 ①②合入 master 后，测试立即撞到同一根因家族的另一条路径——
`recompute-budget` 两次独立复现 `budget_status=FAILED`，`budget_error` 是与更早那次
（`PriceAdjustJobExecutionService.executeItem`）逐字一致的 `ContextNotActiveException`
（`DataLoader` 的 `RequestScoped` context 不可用），只是这次**没有伪装成 SUCCESS**——BL-0108
② 那道"不再静默吞异常"的纵深防御第一次实战验证：完整堆栈、`FAILED` 而非假成功，从 8 轮
排查缩短到立即定位。

### 根因

`PriceAdjustBudgetService` 内有**两层嵌套** `@Transactional(REQUIRES_NEW)`：
`processMaterial`（外层）→ `computeBudget`（无事务注解，随外层）→ `runDryRunSnapshot`
（内层，挂起外层另开一个 REQUIRES_NEW）→ `materialVersionUpgradeService.upgrade(dryRun=true)`
→ S5 核价渲染 → `DataLoader`。

`@ActivateRequestContext` 原本只挂在**外部调用方**（`onVersionGenerated` /
`recomputeSingleReview`）身上，**两层 REQUIRES_NEW 边界本身都没有**——与
`executeItem` 修复时的教训完全一致：**request context 的可用性跟着"这一层 REQUIRES_NEW
边界"走，不会从外层调用方自动透传进被挂起/新开的事务里**。挂在调用方≠挂在真正touch
DataLoader 的事务边界上。

### 顺带发现：另外两个未在 coordinator 排查表里、但同样绕开保护的入口

排查 `managedExecutor.runAsync` 全工程用法时发现，`PriceAdjustComparisonColumnService`
与 `PriceAdjustStrategyService` 各有一处**直接**
`managedExecutor.runAsync(() -> budgetService.processMaterial(...))`——完全绕开
`onVersionGenerated`/`recomputeSingleReview` 身上挂的 `@ActivateRequestContext`，是另外
两个独立的裸入口。这证明"在各个外部调用方分别补"必然会漏，必须收敛到
`processMaterial`/`runDryRunSnapshot`（唯一必经的 REQUIRES_NEW 边界）本身。

### 排查结果表（对照 coordinator 给的清单）

| 入口 | 结论 |
|---|---|
| `PriceAdjustJobExecutionService.executeItem`（异步升版） | ✅ BL-0108 已修（未受影响） |
| `PriceAdjustBudgetService.processMaterial`（预算/dryRun，外层 REQUIRES_NEW） | ❌→✅ **本次修复**：补 `@ActivateRequestContext` |
| `PriceAdjustBudgetService.runDryRunSnapshot`（预算/dryRun，内层嵌套 REQUIRES_NEW） | ❌→✅ **本次修复**：补 `@ActivateRequestContext`（与外层分开补，两层各自需要） |
| `PriceAdjustScheduledScanService.scanAndGenerate`（`@Scheduled` → 版本生成 → 预算） | ✅ **本次一并覆盖**——调用链 `scanAndGenerate`→`generateVersionAndEnqueueBudget`→异步`onVersionGenerated`→`processMaterial`，修复点在共享核心方法，无需在本类单独补 |
| `PriceAdjustNotificationService`（B11 通知） | ✅ 不涉及 `@RequestScoped`——已核查仅注入 `NotificationService`，无 `MaterialVersionUpgradeService`/`BomTreeRenderService`/`DataLoader` 依赖 |
| `PriceAdjustComparisonColumnService`（未在原排查表，本次新发现） | ✅ **本次一并覆盖**——直接 `runAsync(processMaterial)`，修复点在共享核心方法自动覆盖 |
| `PriceAdjustStrategyService`（未在原排查表，本次新发现） | ✅ **本次一并覆盖**——同上，直接 `runAsync(processMaterial)` |
| `QuoteImportService`/`BasicDataImportV6Resource`（不同 feature area，全工程 `runAsync` 排查时一并核查） | ✅ 已有自己的 `@ActivateRequestContext`，与本 bug 家族无关，未改动 |

### 修法

`processMaterial`（外层 REQUIRES_NEW）与 `runDryRunSnapshot`（内层嵌套 REQUIRES_NEW）**各自**
补 `@ActivateRequestContext`——两层都要补，不能只补一层（内层会挂起外层事务另开一个，
request context 的可用性不会跟着自动透传）。修复点落在这两个共享核心方法本身（而非四个
各自独立的外部调用方），一次性覆盖 `onVersionGenerated`/`recomputeSingleReview`/
`PriceAdjustComparisonColumnService`/`PriceAdjustStrategyService` 全部 4 个入口。

## 3. 澄清结论与决策记录

| # | 决策项 | 结论 | 理由 | 被否决的方案 |
|---|--------|------|------|-------------|
| 1 | job_item 清理方式 | 直接 DELETE，不做软删除/detach | job 明细对已删除报价单无保留价值，重试也无处可试（coordinator 明确指示） | 软删除/置状态 CANCELLED——增加复杂度且无消费方会读这个状态 |
| 2 | 空批次 job 是否一并删除 | **删**——若某 job 名下全部 item 因本次删除清空，一并删除该 job | job 的 `totalCount`/`successCount` 等汇总字段只服务于它名下的 item，item 清零后是"指向不存在明细的孤儿统计"，无查阅价值 | 保留空批次记录——曾考虑"留作历史审计"，但审计对象（item）已不存在，空壳记录本身不提供信息 |
| 3 | 异常捕获方式 | 沿 `getCause()` 链找根 `SQLException`，按 SQLState=23503 判定，不依赖具体包装类型 | 实测已有的 `GlobalExceptionMapper.handleHibernateConstraint`（捕获 `org.hibernate.exception.ConstraintViolationException`）**没有**拦下这次的 500——说明实际抛出的异常包装类型与该 mapper 预期的不同（很可能是 `@Transactional` 拦截器在方法返回后的提交阶段才抛，包装链不同），故本次改为在 `delete()` 内部主动 `em.flush()` 强制同步抛出 + 直接 try/catch，不依赖全局 mapper 猜包装类型 | 只加强 `GlobalExceptionMapper`——风险是仍可能猜不中新的包装类型，且这样定位不到"是报价单删除"这个具体业务场景，提示不够精确 |
| 4 | `costing_order` 是否顺手修 | **不修**，只排查报告 | coordinator 明确要求"不要自作主张给它加级联删除"，处置口径是业务决策 | 顺手一起改——被 coordinator 明确否决 |

## 4. 功能需求

- FR-1：`QuotationService.delete()` 补充清理 `material_price_update_job_item`（按
  `quotation_id` 删除），并在该表名下 job 变空时一并删除 `material_price_update_job`
- FR-2：`delete()` 捕获外键冲突（SQLState 23503），翻译成 `BusinessException(409, ...)`，
  消息含友好的表名/业务对象名；未登记映射的约束名走通用兜底（报约束名本身，不再裸 500）

  改造后这类场景会给用户看到什么提示

## 6. 验收标准

- AC-1：拿一张当前被 `material_price_update_job_item` 阻塞、且所属 job 有其它 item 的
  测试 DRAFT 单，`DELETE /api/cpq/quotations/{id}` 返回 200，quotation 表行确实清除
- AC-2：AC-1 的场景里，该报价单的 `material_price_update_job_item` 行全部清除（0 孤儿），
  同一 job 下其它报价单的 item 行原样保留、数量正确递减
- AC-3：构造一个 job 只有一条 item（对应即将删除的这张单）的场景，删除后该 job 本身也被
  一并删除
- AC-4：构造一个仍被 `costing_order` 阻塞的场景，删除请求返回 **409**（不是 500），响应
  体含明确指出"关联的核价单（costing_order）"的可读提示
- AC-5：AC-4 场景下，`quotation`/`costing_order` 两表数据均**未被误删**（事务正确回滚）

## 7. 影响面与风险

- 改动文件：`cpq-backend/src/main/java/com/cpq/quotation/service/QuotationService.java`
  （`delete()` 方法本体 + 新增 2 个私有方法）
- 不触发 AP-44（无 field_type 变动）；不涉及前端改动；不涉及 Flyway（无 schema 变更）
- 风险：`em.flush()` 强制同步执行 DELETE——理论上会让 FK 检查从"提交时"提前到"方法体内"，
  但语义完全不变（同一事务内，只是检查时机提前），且是标准 JPA 技术，风险低

## 8. 已知坑位

- 本任务发现**已有的 `GlobalExceptionMapper.handleHibernateConstraint`
  （`org.hibernate.exception.ConstraintViolationException`）实测未能拦下这次的 FK
  违反**——说明该全局 mapper 的覆盖面有盲区（Quarkus/Hibernate 对同一类 DB 异常，
  依据抛出时机不同可能包出不同的包装类型）。本次未深挖该 mapper 的盲区根因（超出本次
  修复范围，本次绕开该问题、直接在业务方法内主动 flush+catch），如实记录供后续参考——
  若未来还有其它入口遇到"明明有全局 FK mapper 却仍然裸 500"，先怀疑同一类"包装类型
  与 mapper 预期不符"的问题。
