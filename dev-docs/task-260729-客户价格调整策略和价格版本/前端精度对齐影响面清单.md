## 0. 为什么"改完金额会不会变"能被完整回答，而不需要真的跑遍全部报价单公式引擎

`formulaEngine.ts` 的 `evaluateExpression` 把整条表达式拼成一个 JS 字符串一次性求值（原生 double 浮点，天然有效精度 ~15-17 位），**只在返回前做一次 `.toDecimalPlaces(4)`**——不是像某些逐操作符 BigDecimal 实现那样每一步都四舍五入到 4 位再喂给下一步。这意味着：

- **单个公式字段内部**（哪怕内部就有除法，如 `A/B*C`）：无论对不对齐，中间计算都是原生浮点精度，只有最终返回值的小数位数不同——不影响该字段自身"真值"的准确性，只影响它显示/存储时保留几位小数（且 PRD 既有策略本就要求计算列显示 4 位，见 `cpq-decimal-display-policy`）。
- **真正会被"对齐"影响的，只有一种情况**：公式 A 的结果被四舍五入到 4 位后，作为**另一个独立的 `evaluateExpression()` 调用**（另一字段/另一 Tab/另一行）的输入——即通过 `component_subtotal` / `cross_tab_ref` / `previous_row_subtotal` 这三种"跨字段跨 Tab 引用" token 类型被下游消费。只有这种"先四舍五入、再参与下一轮计算"的链式路径才可能让最终金额产生实质差异（4 位截断的误差被下游放大）。

因此，完整回答"金额会不会变"不需要真的对每张单重放整条渲染流水线，只需要：**①结构性地找出所有"含除法 AND 结果被跨字段/跨 Tab 链式消费"的公式定义**（§1）；**②对命中的公式，用真实持久化数据验证其当前实际取值**（§2）。凡是没命中①的公式，理论上就不可能因精度对齐而改变任何金额（只可能改变展示位数，且展示位数已由既定 4 位策略兜底不受影响）。

## 1. 结构性审计：全库扫描「含除法 且 结果被链式消费」的公式

扫描范围（`cpq_db_0724` 全量，2026-08-02 时点）：
- `component.formulas`（87 个组件，其中 15 个非空）
- `component.fields`（87 个组件的字段定义，判断 `is_subtotal`/`formula_name`/字段间 `field` token 互相引用）
- `template.components_snapshot`（10 份模板快照）
- `quotation_view_structure.structure`（53 份报价单/核价单冻结结构，QUOTE_CARD + COSTING_CARD）

判定「at risk」的条件（任一满足）：
1. 该 FORMULA 字段本身 `is_subtotal=true`（会被同组件的 `subtotalByColumn`/`__amount_total__` 汇总，进而可能被其它组件用 `component_subtotal` 引用）；
2. 该字段被同组件内另一个 FORMULA 字段的 `field`/`b_field`/`datasource_field` token 引用；
3. 该字段自身表达式里就含 `component_subtotal`/`cross_tab_ref`/`previous_row_subtotal` token（说明它本身就是"跨 Tab 汇总"公式，而不是纯本行计算）。

**结果**：全库含除法的 FORMULA 字段共 **2 个**，均命中条件 1 + 3（两者是同一个公式模式的两份拷贝）：

| 组件 | 字段 | 公式名 | is_subtotal | 表达式摘要 |
|---|---|---|---|---|
| `COMP-0160`（产品·报价侧） | 管理费 | 管理费 | true | `SUMIF(其他费用.比例 WHERE 类别='管理费') / 100 * (SUMIF(物料.材料成本 WHERE 产出类型='非银点类') + 组装加工费(__amount_total__) − 物料·回收成本(回收成本))` |
| `COMP-0135`（产品·同款拷贝） | 管理费 | 管理费 | true | 同上（不同 componentId，公式逐字相同） |

其余含除法的公式（单位换算类，`08-unit-conversion.json` 黄金用例覆盖的那类：克转千克、单价元/kg→元/g 等）**均为终端字段，未被任何下游公式引用**，不在本清单风险范围内。

**`COMP-0135` 在全库 0 处被实际使用**（无任何报价单/核价单/模板快照的 `componentId` 匹配它）——配置存在但从未进入过任何真实业务数据，对当前库贡献 0 影响。

**`COMP-0160` 全库仅 2 处真实使用**（均为罗克韦尔客户、料号 `S-3120014539`，同一份报价模板）：

| quotationNumber | status | lineItemId | 「产品」Tab.管理费（当前实际值） |
|---|---|---|---|
| QT-20260802-0050 | DRAFT | `d51e2e44-e466-4503-b072-a15d3aaa33ac` | **0.0** |
| QT-20260802-0051 | DRAFT | `f3f01620-3868-4ec9-925b-c5ef22d8dbe5` | **0.0** |

两条记录的 `管理费` 当前都精确算出 `0.0`。逐层拆解「其他费用」Tab 的真实行数据（`quote_card_values` 原文）：

```
其他费用 Tab 实际行：
  类别="材料管理费"  费用=null
  类别="外购件管理费" 费用=null
  类别="利润"        费用=null
  类别="税率"        费用=null
```

而 `管理费` 公式的 `cross_tab_ref` predicate 写的是 `类别 = '管理费'`（**精确字符串相等**）——真实数据里的类别标签是"**材料管理费**"「**外购件管理费**」，没有一行的类别字面量恰好等于"管理费"三个字，predicate 命中 0 行 → 空集 → 按 I-1 决策静默回落 0（且即便命中，`费用` 列本身也全是 `null`）。这是一个**与本次精度对齐完全无关的既有配置/命名不一致问题**（配置该字段的人把"管理费"当"类别前缀语义"用，但公式 predicate 按"类别全字面量"精确匹配）——**不在本次任务范围内，本清单不建议顺手修，只如实记录**。

**结论**：`0 / 100 = 0`，无论用现行"4 位收敛"还是对齐后的"12 位中间精度"，两种算法在这 2 条真实数据上给出的都是逐位相同的 `0.0000000000`。**当前库因此不存在任何一条会因精度对齐而改变的金额。**

## 3. 潜伏风险提示（非当前影响，供后续留意）

上面的"0 影响"结论建立在**当前真实数据恰好让唯一的风险公式短路为 0** 之上，这是一个**脆弱的巧合**，不是"这个公式模式天生安全"：

- 如果未来「其他费用」Tab 的类别标签改成与 predicate 字面量精确匹配（如运营侧发现"管理费"行永远算不出值、去修正数据或改 predicate），`比例/100` 就会开始参与真实计算——这时如果 `比例` 恰好是一个像 `33.33`（一比三十分之一的近似值）这类需要更多小数位才能精确表示的数，`33.33/100=0.3333` 四位截断 vs 更高精度截断，在乘以一个较大的成本汇总基数后**会产生真实的、非零的金额差异**（放大倍数 = 成本汇总基数；基数越大，被放大的截断误差越显著）。
- 建议：一旦这个"类别标签不匹配"的既有问题被修复（不管是本次任务顺带修还是后续单独排期），**应重新跑一遍本清单的方法论**（§1 结构扫描 + §2 真实数据验证），而不能沿用"当前 0 影响"的结论。
