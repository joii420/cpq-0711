## 1. 背景与目标

用户 2026-08-07 在 `QT-20260807-0140` 上实测报出两组现象：

1. 财务审核抽屉（屏 4）「三、下钻」表里，**「调整后小计」整列恒为 `—`**。
2. 更正任务（`material_price_update_job`）执行成功后：
   - 刷新报价单详情页 → **该元素（Ag）的元素单价与货币都变成 `—`，产品小计从 18.00 掉到 15.109316**；
   - 点「编辑」进编辑页 → 价格与版本徽标**对不上**（价是新版价、徽标停在上一版）；
   - **在编辑页再刷新一次，价格才正确**（3000 / V26080702，小计 18.587137）。

主线已完成根因取证（§3）。核心事实是：**更正任务跑完的那一刻，被调价元素的单价是"丢的"、行小计与单据总额是偏低的**，要等有人打开并保存该单触发 `PriceReconciler` 归位才自愈。DRAFT 单还有人开，SUBMITTED 单没人开就一直挂着错金额。这是数据正确性缺陷，不是显示问题。

**目标**：更正任务执行完毕后，被更新单据的价格、版本徽标、行小计、单据总额**当场即为终态**，不依赖任何后续保存动作自愈；被跳过的单据对财务可见、不再伪装成成功；审核抽屉的三个数值口径正确可判定。

## 3. 根因分析（取证记录）

> 取证时 `QT-20260807-0140` 已被用户删除，故用**同一次 job（`32ced881`，V26080702，2026-08-08 01:13:57Z，32 项全报 SUCCESS）更新的兄弟单**复现同样的库内状态。

### 根因 A：升版链路只改价、不刷版本标记（= BL-0124）

`MaterialVersionUpgradeService.upgradeComponentRows()` S3a（`:563-566`）只写价格与货币两个键，**全类 0 处 `__priceVersion` / `__priceLocked`**；这两个标记的唯一写点是 `PriceReconciler`（8 处），而 `PriceReconciler.reconcileQuotation` 只挂在 `QuotationResource.saveDraft:154`。

实测 `QT-20260807-0127`（更正后未再保存）的 `quotation_line_component_data.snapshot_rows`：

```json
"driverRow": { "元素单价": 3000.000000,        // V26080702 的新价，S3a 写的
               "__priceLocked": true,
               "__priceVersion": "V26080701" }  // 上一版徽标，没人刷
```

`QT-20260807-0129/0130/0135` 更明显：价 3000、徽标 `V26080601`。

⇒ 用户截图 3「价格和价格版本错乱」即此。**"再刷新一次就对了"不是缓存**，是打开编辑页触发 `saveDraft` → `PriceReconciler` 归位，把价与版本一起刷成 `V26080702`。

### 根因 B：S4 只删价格键、不回填新价 → 元素报价丢失、小计塌

`upgradeComponentRows` S4b（`:597-600`）对 `row_data` 非手动行执行 `remove(元素单价)` + `remove(货币)`；`cleanEditRowOverrides`（S4a，`:419-422`）对 `quote_card_values.editRows` 做同样的删除。**两处都只删不写。**

实测 `QT-20260807-0127` 的 `row_data`，5 行里只有 Ag 行少键，且恰好少的就是被删的那两个：

```json
{ "元素":"Ag", "料件":"Ag粉", "料号":"00255", "项次":1,
  "销售料号":"3110520422", "组成含量(%)":100.0 }   // 无 元素单价、无 货币
```

随后 S5 `buildCardValues` 重建卡片时 `editRows` 是**从 `row_data` 回种**的（`seedEditRowsFromRowData`，`buildCardValues` 对 editRows 传 `null`），价格键仍缺 → 该格算不出值。`0127` 侥幸显示 3000 是因为它这一行没有覆盖层、回退到了 `driverRow`；`0140` 有覆盖层就落成了截图 2 的 `元素单价 —` + `货币 —`。

**数值自洽（三方对齐，可确认就是它）**：

| 状态 | 产品小计 | 对照 |
|---|---|---|
| 调价前（Ag=2500） | 18.00 | = 抽屉「报价·现」 |
| **更正任务跑完** | **15.109316** | **Ag 计 0 —— 用户截图 2** |
| 打开编辑页归位后（Ag=3000） | 18.587137 | = 抽屉「报价·调整后 18.59」 |

差额 3.477821 ÷ 3000 = 0.0011593 kg 用量；反推 2500 × 0.0011593 = 2.898 → 15.109 + 2.898 = 18.007 ✓

### 根因 C：缺 `QUOTE_CARD` 冻结结构的单被静默跳过，却计入 SUCCESS

`upgrade()` 靠 `loadFrozenQuoteTabsNative()`（`:995`）读 `quotation_view_structure (view_kind='QUOTE_CARD')` 定位价格承载组件；查不到 → `priceBearing` 为空 → 返回 `SKIPPED`（`:237-242`）。而 `PriceAdjustJobExecutionService.executeItem:336` 把 `SUCCESS, SKIPPED` 一起映射成 `SUCCESS`。

实测 `QT-20260807-0128`（由 `QT-20260806-0120` 复制、复制后没保存过）：

- `quotation_view_structure`：**0 行**（同源复制但被提交过的 0129/0130/0135 有 4 份结构 —— 提交路径补建了）
- `component_data.row_version = 0`、Ag 仍 2500、`__priceVersion` 仍 `V26080601`、`quotation.updated_at` 停在建单时刻 → **一个字节都没改**
- job 汇总：`total=32 success=32 failed=0`

现网规模（取证 SQL 见 test.md）：**33 张活跃 DRAFT 单没有 `QUOTE_CARD` 结构**，任何一次价格更正都会静默跳过它们。

`QuotationResource.copy:550` 是调了 `ensureStructure`，但外面套着 `catch (Exception ignore)`；0128 两个模板 id 都在却没结构 ⇒ 那次补建失败被吞了（根因另立 `BL-0150`，本次在消费侧自愈）。

### 问题 1：`quoteSubtotalAdjusted` 后端零赋值点

`PriceAdjustReviewService.detail():214-222` 只写 `quoteSubtotalCurrent = li.subtotal`，**从未给 `quoteSubtotalAdjusted` 赋值**。全仓该字段 4 处命中：DTO 声明 1、TS 类型 1、前端渲染 2，后端赋值 0。前端 `fmt(null) → '—'`，与数据无关。

连带：`ReviewDetailDrawer.tsx:137-142` 的「财务自检：调整后报价 − 现报价 …对得上 ✓」整段依赖该字段非空，**永不显示**。

`api.md §2.2` 的响应样例明写 `"quoteSubtotalAdjusted": 222.10` ⇒ 是契约漏实现，不是"本期不做"（同方法第一段的 `usageQty` / `unitPriceImpact` 有明确的"本期未做、如实留空"注释，这个字段没有）。

**附带口径错误**：`detail():202` 把 `elementImpactTotal` 取成 `col-default` 的 `diffAdjusted`，语义是「报价·调整后 − 核价·调整后」（截图里 18.59 − 0），**不是**"元素涨价对单价的影响"（本例应 ≈ 0.587）。前端标签写的是「合计对单价影响」，财务会读成"这次调价让单价涨了 18.59 元"。

## 5. 功能需求

### FR-1 升版写价必须同时写锁标记

`upgradeComponentRows` S3a（`snapshot_rows.driverRow`）与 S3b（`row_data` 手动行）写入 `elementPriceField` 的同时，必须写 `__priceLocked=true` 与 `__priceVersion=<目标版本 versionNo>`。版本号取 `ElementPriceVersion.versionNo`，`upgrade()` 已持有 `targetVersionId`，一次查出后透传，不得逐行查库。

### FR-2 升版清值改覆盖，删值必撤锁

**`row_data` 的三分支口径，手动行（S3b）与非手动行（S4b）完全一致**（D-8，2026-08-07 补）：

| 情形 | 动作 |
|---|---|
| 元素 ∉ 本版明细 | **一个字节都不碰**（沿用现状） |
| 元素 ∈ 本版明细且解出价（`ep.price != null`） | 写新价 + 货币 + `__priceLocked` + `__priceVersion`（不再 `remove`） |
| 元素 ∈ 本版明细但解不出价（`ep.price == null`） | 删价格键 + 货币键，**同时删 `__priceLocked` / `__priceVersion`** |

- S4a（`cleanEditRowOverrides`）：同上口径改为覆盖。
- 🚨 **手动行不得例外**：改造前 S3b 只有 `if (ep.price != null) { put… }`、**没有 `else` 分支**，于是本版无价时手动行会原样保留「陈旧手改值 + 陈旧锁标记」——那是 `#47` 死格的另一种形态（值是旧的、格子还锁着，销售既拿不到系统价也改不了）。判据见 D-8。
- 口径与 `PriceReconciler.reconcileRows` 逐条对齐（该方法 javadoc `:204-206` 已写明"清值与撤锁必须同进同出"，本次是把这条纪律补到升版侧）。

### FR-3 缺冻结结构自愈

`upgrade()` 在 `locatePriceBearingComponents` 返回空时：调用 `CardSnapshotService.ensureStructure(quotationId)` → 重新 `loadFrozenQuoteTabsNative` → 重新定位。第二次仍为空才返回 `SKIPPED`，且 `message` 必须区分两种情形（"补建后仍无价格承载组件" vs "补建失败"）。

### FR-4 SKIPPED 成为独立终态

- `MaterialPriceUpdateJobItem` 新增常量 `SKIPPED`，DB `chk_mpuji_status` 放开该值（V384）。
- `executeItem` 的 `switch`：`SUCCESS → SUCCESS`；`SKIPPED → SKIPPED`（不再合并）。
- `MaterialPriceUpdateJob` 新增 `skipped_count` 列并进 `recountFrom`；批次终态判定规则：`SKIPPED` **不算失败**，但只要存在 `SKIPPED` 且无 `FAILED/CONFLICT/STALE`，批次状态为 `PARTIAL` 而非 `SUCCESS`（财务必须看得见"有单没被更新"）。
- 屏 6a（`JobProgressDrawer`）`ITEM_STATUS_TAG` 补 `SKIPPED: { color: 'gold', label: '已跳过' }`；跳过行显示 `errorMessage` 作为原因，不显示「重试」按钮（重试不会有不同结果）。

### FR-5 审核抽屉「调整后小计」

`detail()` 对 `isBasis` 的那一行调用**隔离子事务 dryRun**（复用 `PriceAdjustBudgetService.runDryRunSnapshot` 的既有模式）拿到调整后 `li.subtotal`，写入 `quoteSubtotalAdjusted`；其余行 `quoteSubtotalAdjusted=null` 且新增布尔 `adjustedComputed=false`。前端按 `adjustedComputed` 区分渲染「未试算」与「—」。

### FR-6 元素明细的用量与影响

- `unitPriceImpactTotal`（前端「合计对单价影响」）= 判断依据单 `dryRun 后 subtotal − 现 subtotal`。
- 逐元素 `unitPriceImpact`：`versionItems.size() == 1` → 直接取上面的整体 Δ；`> 1` → 对每个元素跑一次"只有该元素用新价、其余沿用上一版价"的 dryRun，取各自 Δ。
- `usageQty` = `unitPriceImpact ÷ (currentPrice − previousPrice)`；分母为 0 或任一侧为 null → `usageQty = null`（前端显示 `—`），**不得除零、不得填 0**。
- 合计与 Σ 明细差 > 0.01 → `LOG.warn` 记录（D-6），不阻断、不改数。

### FR-7 N+1 批量化

`detail()` 与 `impact()` 中循环内的 `Quotation.findById` / `QuotationLineItem.findById` 改为一次 `IN` 批量查 + 内存 `Map` 分发。硬指标：单次抽屉打开的这两张表各最多 2 条 SQL，与活单数 N 无关。
