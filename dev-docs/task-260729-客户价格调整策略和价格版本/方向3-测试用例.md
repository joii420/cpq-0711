### 0.1 li.subtotal 双端对拍（`GET /api/cpq/admin/quotations/task0729-subtotal-reconcile`，只读）

| 指标 | 实测 |
|---|---|

🔴 **计划 §5.4 写的「44 个 line item 中 6 个不一致 / 其余 38 个逐位不变」与实测对不上，两个原因**：

1. **数据漂移**：编写计划时 44 行，现在 45 行（`QT-20260806-0083` 是后建的），且不一致数已从 6 → 7。**环境是移动靶**（`交付验收报告 §5` 已有此教训），基线必须在开工那一刻重采。
2. 🧭 **口径错**：计划的"6 张"来自对拍端点的 `diff` 字段，而该字段**四舍五入到 4 位**。有 **5 张单的差异在 2.5e-5 量级**，端点报 `diff=0.0000`，但 `li.subtotal` 是 `numeric(20,6)`、后端算值是 `double`，**改造后这 5 张的第 5~6 位必然改变**。若按计划原文"其余 38 个必须逐位不变"判定，**这 5 张会被误判成"改造引入了新问题"**。

**前置数据**：任取一张 §0.1「逐位一致 31 张」中的 DRAFT 单，推荐 `QT-20260728-0023`（`li.subtotal=214.0`，后端算值同为 214.0，且不在调价客户的锁价范围里）。记 `LI_ID` / `Q_ID`。

> 🔒 **这条用例天然会假绿**：该单前后端本来就一致（214=214），**覆盖动作跑没跑，结果都是 214**。所以必须先注入哨兵。

**执行步骤**
1. 记录原值：`SELECT subtotal, row_version FROM quotation_line_item WHERE id=:LI_ID`（记为 `S0`/`V0`）。
2. **注入哨兵**：
   ```sql
   UPDATE quotation_line_item SET subtotal = -12345.678901, quote_card_values = NULL WHERE id=:LI_ID;
   ```
3. 触发懒算：`POST /api/cpq/quotations/{Q_ID}/ensure-card-values`。
4. 跑 **T-B** 比对 SQL。
5. 复原：`UPDATE ... SET subtotal = :S0 WHERE id=:LI_ID`，并再次 `ensure-card-values` 让卡片值回到自洽态。

**断言（机械可判定）**
- 🔒 步骤 3 响应 `200`，且 `data.lineItems[].subtotal` 不为 `-12345.678901`。
- 🔒 步骤 4：`li_sub IS NOT DISTINCT FROM card_sub_r6` 为真，且 `li.subtotal = 214.000000`。
- 🔒 **防空转**：`li.subtotal ≠ -12345.678901` —— 证明它被**真的写过一次**，而不是"碰巧相等"。
- 🔒 **反向判别器**：若实现把兜底值原样保留（覆盖没接上），断言 2 会拿到 `-12345.678901`；若实现覆盖时用错了源（例如取了 NORMAL 页签而非 SUBTOTAL 页签），本单会拿到 `0.000000` 或 `14.000000` 之类**非 214** 的数 —— 三种结果互不相同，可直接定性。
- 🔒 复原后 `T-B` 仍成立（不留脏数据）。

**证据形式**：三次 SQL 输出（注入前 / 触发后 / 复原后）+ `ensure-card-values` 响应 JSON。

### D3-02　🔴 本次故障复现：归位改价后总价 = 后端算值（37.330516，不再是 59.580015）

**前置数据**：`QT-20260806-0082`，`li.id = a31c46f2-fe0e-4e72-8876-3ff139ef5b24`。执行前先跑 §0.3 那组 SQL 确认现场仍是 `59.580015 / 37.33051640854084`（**若已被并发会话改动，改用 `QT-20260806-0083`，它是同值的孪生单**）。

**执行步骤 —— 两条路径都要跑，缺一不可**

**路径 ①（最小复现，钉死数值）**
1. `UPDATE quotation_line_item SET quote_card_values = NULL WHERE id=:LI_ID;`
2. `POST /api/cpq/quotations/{Q_ID}/ensure-card-values`
3. 跑 **T-B**。

**路径 ②（真实链路，钉死时序）**
1. 前端打开 `QT-20260806-0082` → Step2 → 触发一次 `PUT /quotations/{id}/draft`（真实 saveDraft，走 `PriceReconciler` 归位）。
2. **保存刚返回时**立刻查 `li.subtotal` 与 `quote_card_values`。
3. 再 `POST .../ensure-card-values`，复查。

**断言（机械可判定）**
- 🔒 路径 ①：`li.subtotal = 37.330516`（`numeric(20,6)`，`HALF_UP`），**不是** `59.580015`。

**执行步骤**（沿用验收 `#66` 同款方法）

2. 切改造后分支，同样跑法。
3. **回切改造前**再跑一轮控漂移（共享 dev server + 共享库，漂移必须量化）。
4. 每次 saveDraft 期间抓后端日志：`[draft-profile]` 分段耗时 + `[ensure-cardvalues]` 出现次数。

**断言 —— 🔒 三层判据，前两层是结构判据（不依赖计时，比耗时更硬）**

**第 1 层 · 结构判据（决定"是不是走偏"）**
- 🔒 saveDraft 请求期间日志 `[ensure-cardvalues] quotation=` 出现次数 **= 0**（改造前后都必须 0）。
- 🔒 saveDraft 返回后立刻查：`quote_card_values IS NULL` **且** `li.subtotal` = 前端提交值。
  - 这两条成立 = **覆盖动作确实不在保存路径上**，性能增量在结构上就不可能存在。
  - 任一条不成立 = **实现走偏**（把覆盖挂进了保存路径），无论耗时数字多好看，**本闸门判 FAIL**。

**第 2 层 · 规模斜率判据（区分"慢"与"走偏"）**
- 🔒 计算 `Δ(N) = 改造后中位数(N行) − 改造前中位数(N行)`，N ∈ {1,3,5,10}。
- 🔒 通过：`Δ` 与 N **无相关**（`|Δ(10) − Δ(1)| < 50ms`）且 `max(Δ) ≤ 50ms`（落在漂移噪声内，参考 `#66` 实测漂移 51ms、最坏界 87ms）。
- 🔒 **判为"走偏"**（不是"慢"）：`Δ` 随 N **近似线性**且斜率 ≥ 300ms/行 —— 这是误调 `ensureCardValues` 两侧全算入口的指纹（实测该入口单次 **368~396ms**，10 行 ≈ +3.7~4.0s）。**结论写"实现误用了全算入口"，不写"性能超标"**，并要求回到 §三.1 复核挂点。
- 🔒 判为"慢"（非走偏）：`Δ` 与 N 无关但 `50ms < Δ ≤ 300ms` —— 多了固定开销（如一次多余查询/UPDATE）。此时补查 SQL 语句计数定性，不直接判 FAIL，报技术总监。
- 🔒 硬红线兜底：任何情况下 `Δ > 300ms` 判 FAIL（E14-7）。

**第 3 层 · 漂移控制**
- 🔒 步骤 3 回切后的中位数与步骤 1 相差 `< 50ms`，否则本轮数据作废重跑（共享环境被并发污染）。

**证据形式**：4×3 轮的中位数表（含每轮 4 个原始样本）；`[draft-profile]` 日志摘录；`[ensure-cardvalues]` 计数；saveDraft 后的 `quote_card_values IS NULL` SQL 输出。

**约束 1 · 全库零 PART 子件 —— 两套单头口径的差异在现网数据上验不出来**

```sql
SELECT composite_type, count(*) FROM quotation_line_item GROUP BY 1;
-- 实测：44 行全部 composite_type='SIMPLE'，PART = 0 行
```

「草稿口径**含** PART / 提交口径**排除** PART」是 `D3-30`/`D3-31` 的核心判别器，但**现网一条 PART 行都没有** → 两套口径在现存数据上**恒等**，用它们测等于没测。处置：`D3-30` 必须**造一张组合产品单**（SIMPLE 父 + ≥1 PART 子），否则该判别器降级为"环境不可验"并如实标注 —— **不接受用全 SIMPLE 的单跑一遍就说口径对了**。

**约束 2 · 非 DRAFT 单只有 2 张，且它们天然测不出闸门**

```
APPROVED : QT-20260726-0016 (li.subtotal=26.0)
SUBMITTED: QT-20260726-0018 (li.subtotal=14.0)
```

两个坑叠在一起：
1. 这 2 张单的 `li.subtotal` 与后端重算值**本来就一致**（对拍 diff=0）→ 覆盖跑不跑，行总价都不变；
2. 它们的 `quote_card_values` **非 NULL** → `ensureCardValues` 的 `IS NULL` 谓词根本不选中 → **覆盖压根不会执行，闸门从未被考验**。

→ `D3-31` 必须先 `quote_card_values = NULL` **且**注入哨兵，才能真正把闸门放到火上烤。**照原样跑一遍拿到"单头没变"，证明的是"什么都没发生"，不是"闸门生效"。**

**🔒 路径 5 的三个执行契约（2026-08-06 实测踩到，别再猜）**

1. **`mode` 只认 `PRUNE` / `ROW`** —— 传 `NODE` 返 `400 非法 mode: NODE，必须是 PRUNE 或 ROW`。
2. **必须先 `delete-preview` 拿 `previewToken`**，否则 `delete` 返 `409 树结构已变化，请重新预览后再执行删除`。
   ```bash
   POST .../line-items/{lid}/tree/delete-preview  {"componentId":"<树页签>","mode":"PRUNE","nodeId":"<__nodeId>"}
   POST .../line-items/{lid}/tree/delete          {...同上..., "previewToken":"<上一步返回>"}
   ```
   `nodeId` 取自 `quote_card_values.tabs[].baseRows[].__nodeId`（形如 `3120011203/3110520422/00257`），**不是** `rowKey`（该结构里没有 `rowKey` 键）。
3. 🔴 **树删除会级联在其他页签写 row 墓碑** —— `delete-preview` 响应的 `cascadeTabs[]` 会列出受牵连的 `componentId` + `rows[].rowKey`，执行后这些页签的 `quotation_line_component_data.deleted_row_keys` 会多出条目。
   **复原树操作必须两处都还**：`quotation_line_item.deleted_tree_nodes` **和** 各页签的 `cd.deleted_row_keys`。
   ⚠️ `deleted_row_keys` 是 **NOT NULL** 列，清空要写 `'[]'::jsonb`，写 `NULL` 会撞约束。
   ⚠️ 只还前者会让行总价停在"删了一行"的中间值（实测 `0082` 一度停在 `36.436180` 而非 `37.330516`）。

**通用断言（每条路径都要过）**
- 🔒 `888.888888` / `777.777777` 在该路径跑完后**必须消失**（防空转的硬证据）。
- 🔒 后端日志出现 `[subtotal-single-source] quotation=… 覆盖生效：行总价 N 处、页签小计 M 处`，且 `N ≥ 1`、`M ≥ 1`（这行日志是后端自带的计数器，比自己数 SQL 更直接）。
- 🔒 **错实现会产出什么**：
  - 某条路径漏接收敛点 → 该路径跑完 `li` 仍是 `888.888888`（一眼可辨，不会与任何真实值混淆）；

  - 单头漏接 → 前两个清了、`666.666666` 还在（路径 2 除外，它就该留着）。
- 🔒 路径 5 若不可达，**判「环境不可验 + 原因」**，不拿路径 4 的结果代替（两者用的是不同的调用位置，`:3334` vs `:3218`）。

**证据形式**：5 条路径各自的「投毒 → 触发 → 复查」三段 SQL 输出 + `[subtotal-single-source]` 日志摘录。

### D3-29　路径 2（加产品/导入逐行）有意不算单头 —— 正向 + 收敛 + 反向性能

> 后端明示：路径 2 在导入 N 行循环里被逐行调，算单头要查全单 = **O(N²)**，故有意不接，靠随后的 saveDraft + 懒算批量收敛。**这是设计不是遗漏**，用例按此断言。

| 归属 | 测试层级 |
|---|---|
| 后端自测 + 测试复验 | API 测试 + SQL 断言 + 性能对照 |

**前置数据**：一张可重复导入的草稿单 `QA-0806-IMP`（走 V6 批量导入，≥10 行）。

**执行步骤 + 断言**

1. **正向（路径 2 当场生效的部分）**：投毒三件套 → 触发一次加产品/导入 → 断言
   - 🔒 `li.subtotal`、`cd.subtotal` **已归位**（`888.888888` / `777.777777` 消失）；
   - 🔒 `q.total_amount` **仍是 `666.666666`**（有意不算）。
2. **收敛（随后必须自愈）**：`PUT .../draft` 一次 → `POST .../ensure-card-values` → 断言
   - 🔒 `q.original_amount = round(Σ li.subtotal, 6)`、`q.total_amount = round(Σ li.subtotal × rate/100, 6)`；
   - 🔒 **窗口有界**：从导入结束到 saveDraft 之间单头偏差存在，是**已知且有界**的；若 saveDraft + 懒算后仍不收敛 → FAIL。
3. **反向（防"顺手给路径 2 也加上"）**：
   - 🔒 10 行导入的耗时与 1 行导入的**单行均摊耗时**比较，若均摊随行数显著上升（O(N²) 特征）→ 说明有人把单头重算塞进了循环，判 FAIL；
   - 🔒 后端已实测闸门：单行 median `575.8→559.8ms`、min `472.4→469.5ms`（增量在噪声底以下）。复验时以**相同量级**为准，超出一个数量级才判异常（共享环境噪声大，见 `D3-12` 第 3 层）。
   - 🔒 结构判据（优于计时）：`recomputeDraftHeaderTotals` 的**调用点**不得出现在 `snapshotQuoteSideOnly` 里。
     ```bash
     /usr/bin/grep -an "recomputeDraftHeaderTotals(" CardSnapshotService.java \
       | /usr/bin/grep -av "public void\|{@code\|@link\|^\s*\*"
     ```
     🔒 命中行号集合必须是 **`{597, 3122, 3219, 3335}`**（已实测，4 处**全在整单边界**：懒算批量收尾 / `refreshDraftQuoteCards` 循环外 / `editCardValue` / `materializeAndProject`），**不含 `snapshotQuoteSideOnly`（`:804-820`）内的任何行号**。多出一处落在 `:812` 附近 = 有人把单头重算塞进了导入循环 → 判 FAIL。

**证据形式**：三步各自的 SQL 输出 + 导入耗时表 + `grep` 行号集合。

### D3-31　🔴 DRAFT 闸门：两套单头口径不互相污染（正反两向）

> coordinator 点名独立成条。`recomputeDraftHeaderTotals` 首句 `if (!"DRAFT".equals(q.status)) return;` —— 因为 `ensureCardValues` 也会被非草稿单触发（`ComparisonViewService:326` / `CostingFreezeService:82`），那时单头已由 submit 用**另一套口径**算定，误覆盖 = **改已提交单据的金额语义**。

| 归属 | 测试层级 |
|---|---|
| 测试验收（建议技术总监亲验） | SQL 断言 |

**前置数据**（🔒 见 §4.0 约束 2，两个坑必须一起绕开）
- 非 DRAFT 样本：`QT-20260726-0018`（SUBMITTED，`li.subtotal=14.0`）、`QT-20260726-0016`（APPROVED，`26.0`）。
- DRAFT 对照：`QT-20260806-0082`。
- 🔒 **执行前对非 DRAFT 样本做完整备份**（`li` + `cd` + `q` 三张表相关行），它们是真实业务单，测完必须逐字节复原。

**执行步骤（非 DRAFT 侧）**
1. 备份 → 记录 `q.total_amount` / `q.original_amount` 原值（记为 `H0`）。
2. **两个哨兵一起注入**（缺一不可）：
   ```sql
   UPDATE quotation_line_item SET subtotal = 888.888888, quote_card_values = NULL WHERE id = :LI_ID;
   -- quote_card_values 置 NULL 是为了让 ensureCardValues 的 IS NULL 谓词真的选中它，
   -- 否则覆盖压根不执行、闸门从未被考验（§4.0 约束 2）
   ```
3. `POST .../ensure-card-values`。
4. 复查 `li.subtotal` / `cd.subtotal` / `q.total_amount` / `q.original_amount`。
5. 逐字节复原。

**断言（机械可判定）**
- 🔒 **闸门生效（正向）**：`q.total_amount` 与 `q.original_amount` 逐位 = `H0`（**一个字节都不许动**）。
- 🔒 **行仍被覆盖（关键的另一半）**：`li.subtotal` 从 `888.888888` 变为后端算值 —— 证明**懒算与覆盖确实跑了**，闸门只挡住了单头那一步。
  - 🔒 **没有这一半，本用例就是"什么都没发生"的假绿**（§4.0 约束 2 的两个坑正是为此设的）。
- 🔒 **DRAFT 对照组（反向）**：同样两个哨兵注入 `QT-20260806-0082` → 单头**必须变**为 `37.330516`。
  - 🔒 **错实现会产出什么**：闸门写成恒 `return`（把 DRAFT 也挡了）→ DRAFT 组单头停在 `666.666666`；闸门漏写 → SUBMITTED 组 `total_amount` 从提交口径值跳成 `Σ subtotal × rate` 的草稿口径值（`QT-20260726-0018` 会从其提交期值变成 `14.000000 × rate/100`）。
- 🔒 状态覆盖面：至少覆盖 `SUBMITTED` + `APPROVED` 两态；`SENT`/`ACCEPTED`/`CANCELLED` 现网无样本 → 标「环境不可验」并说明，**不改真实单的 status 去凑**（`#46` 曾因此临时改状态，本轮不重复该做法）。
- 🔒 复原验证：测完 `q` / `li` / `cd` 三表相关行与备份逐字节相同。

**证据形式**：非 DRAFT 组与 DRAFT 组各自的四值前后对照 + 备份/复原 md5。

## 5. 方法论条目（本轮沉淀）

### 5.1 🔴 API 验证不能替代 UI 路径验证 —— UI 会带出 API 调用者不会产生的前置调用

**本轮实例**：`D3-32` 用 `SQL 造状态 → POST /submit` 判 PASS；真实 UI 是 `saveDraft → (fire-and-forget warm) → submit`，**单击一次提交 100% 409**。PASS 掩盖了「提交功能全坏」。

**为什么会漏**：我用 SQL 伪造了 `saveDraft` 的**结果状态**（`quote_card_values = NULL`），却没产生它的**副作用**（前端在保存成功后自动发的那条 warm）。**状态可以伪造，副作用不能。**

**通则**：
- 被测功能若由 UI 上一个动作触发，用例的起点就必须是**那个动作**，不是它的中间态。
- 尤其当前端存在 **fire-and-forget / debounce / 自动重试** 这类"用户看不见、API 调用者也不会写"的伴随请求时——它们恰恰是并发缺陷的来源。
- 判据：问自己「真实用户点这个按钮时，浏览器一共发出几条请求？我的用例发了几条？」**条数不等就不是同一条路径。**

### 5.2 「断言过了但没压到被测的那条路」——本轮出现 5 次，三方都犯

| # | 实例 | 假绿长什么样 |
|---|---|---|
| 1 | 值中性用端点 4 位 `diff` 判「逐位不变」 | 5 张末位差被显示成 `0.0000` |
| 2 | 后端用 `restore-driver-rows` 压树删除的 `true` 分支 | 语义不同（`deletedRowKeys` vs `deletedTreeNodes`），什么都没清，「一致=YES」是碰巧 |
| 3 | 我用 `delete-driver-row` 删「材料成本」行验单头跟随 | 该页签小计本来就是 0，删了也不变，`hdr_follows=t` 是碰巧 |
| 4 | 后端阈值写 `1e-7` 验守卫 | `numeric(20,6)` 静默截断成 `0`，实际验的是「阈值=0」，结论恰好反过来 |
| 5 | `D3-32` 走 API 路径 | UI 路径多一条 warm，真实序列 100% 409 |

**共同点**：断言本身没写错，**输入没落在被测的那条路上**。前四次是量具问题，第五次是整条用户路径没被覆盖。

**统一防法**：每条用例问一句「**如果被测逻辑被整个删掉，这条用例会不会仍然绿？**」会 → 判别器无效，重设计。

### D3-35 判别器改版（2026-08-06 · 去文案依赖）

> **改版原因**：原判别器拿 409 的 message 原文区分「锁竞争」与「已存在进行中核价单」。后端加等待逻辑后新增文案
> `系统正在处理该报价单的金额（已等待 %d 毫秒），请稍后重新提交`（旧文案作后备保留），**按文本匹配的断言会漏判**。
> 文案还会再改，判别器不能建在它上面。

**为什么不能靠信封**：`ApiResponse` 只有 `{code:int, message:String, data}`，`BusinessException` 只有 `int code + message`——
**两条 409 在响应结构上完全同构**，没有机器可读的 errorCode。这是判别器退化到匹配中文的根本原因。

#### 两条 409 的运行时差异（源码实证）

| | 锁竞争 409 | 已存在进行中核价单 409 |
|---|---|---|
| 抛出点 | `QuotationResource.awaitWarmBeforeSubmit:359`（**Resource 层，事务外**） | `CostingFreezeService:108/117`（**submit 事务内**） |
| 唯一触发条件 | 等满 `SUBMIT_WARM_WAIT_BUDGET_MS` 仍拿不到单飞锁 | `uq_co_active` 唯一索引冲突 |
| **前置状态** | 另一会话持 advisory 锁 | **该单已有 `status IN ('PENDING','APPROVED')` 的 `costing_order`** |
| 耗时 | **≥ 预算值**（等满才抛） | 无等待，快 |
| 日志 | `[submit-warm-wait] … 拒绝提交` WARN | 无此 tag |

`uq_co_active` 实测定义：
```sql
CREATE UNIQUE INDEX uq_co_active ON costing_order (quotation_id)
  WHERE status = ANY (ARRAY['PENDING','APPROVED']);
```

#### 🔒 改版判别器（主判据 + 两条正向佐证，全部不含文案）

**主判据 · 前置排除（把歧义变成结构上不可能）**
```sql
-- 每档执行【前】断言 = 0；为 0 则核价单 409 结构上不可能发生 → 任何 409 必是锁竞争
SELECT count(*) FROM costing_order
WHERE quotation_id = :Q AND status IN ('PENDING','APPROVED');
```
> 🔒 这条比「事后分辨两个 409」更强：它**消除**歧义而不是**识别**歧义。用全新复制单跑本用例时该值天然为 0，
> 但**必须显式断言**——沙箱里存在残留 active 核价单的情况（后端踩过），不查就会把核价 409 误记成锁竞争 409。

**佐证 1 · 耗时下界**：锁竞争 409 必须等满预算才抛 → `time_total ≥ SUBMIT_WARM_WAIT_BUDGET_MS`。
🔒 **预算值从源码常量读，不要硬编码**（`QuotationResource.SUBMIT_WARM_WAIT_BUDGET_MS`，当前 3000ms）：
```bash
/usr/bin/grep -an "SUBMIT_WARM_WAIT_BUDGET_MS = " cpq-backend/.../QuotationResource.java
```

**佐证 2 · 日志 tag**：`[submit-warm-wait]` 是内部日志前缀、非用户可见文案，比 message 稳定得多。
- 等到锁：`… 等待 Nms（probe K 次）后取得单飞锁，继续提交`（**仅当 `probes>1` 才打印**，后端有意设计成防假绿判据——重试逻辑被删则此行永不出现）
- 等不到：`… 仍未取得单飞锁，拒绝提交`

**允许把 message 记进证据，但不得作为判定依据。**

#### 🔴 档 A / 档 C 的期望值已随等待逻辑改变（重跑前必须改断言）

| | 旧行为（无等待） | 新行为（3s 预算） |
|---|---|---|
| warm 在飞时提交 | 立即 **409** | 等最多 3s；实测 warm 只占 **0.5~1.1s** → **等到锁 → 200** |

→ **档 A / 档 C 的期望从 409 改为 200**，并新增断言：日志出现 `[submit-warm-wait] … 后取得单飞锁` 且 `probes > 1`
（证明**真的等过**，而不是碰巧没撞上——这正是后端埋那行日志的用意）。

**409 仍可达的条件**：warm 耗时 > 预算。按我实测的伸缩曲线 `T(N) ≈ 0.44 + 0.065×N` 反推：

| 行数 N | warm 估时 | 3s 预算 |
|---|---|---|
| 10 | 1.09s | 在预算内 |
| 20 | 1.74s | 在预算内 |
| **39** | **2.97s** | **临界** |
| 50 | 3.68s | **超预算 → 409** |

🔒 **该曲线是乐观下界**（N 行由同一行复制、料号相同、driver 展开缓存命中率偏高；真实异构单每行成本更高），
所以真实触发 409 的行数**低于 40**。新增一档「**档 D · 大单**」：造 ≥50 行单验证超预算路径仍以 409 收场且不留冻结数据。

### 5.3 🔴 写下数字时必须标注量纲 —— 否则它会被正确地写下、错误地读出

**本轮活例**：`QuotationWizard.tsx:569` 的「大单 ensure 可阻塞 ~9-12s」与 `:576` 的「最多 ~16s」。
两个数字**各自都对**，但旁边没写「这是什么的时长」，于是被**两个人**先后读错并串起来：

| 数字 | 真实量纲 | 被误读成 |
|---|---|---|
| 9-12s | **单次 ensure 请求**的阻塞时长 | 大单 warm 的耗时上界 |
| 16s | **前端后台轮询的总预算**（异步，不阻塞用户） | 同类时长，可与 9-12s 互推 |

由此产生两个错误结论：① 「9-12s 反推 130~180 行大单」（拿 A 的数配 B 的模型）；
② 「前端能等 16s，后端凭什么只等 3s」（**异步轮询预算** vs **同步占住 HTTP 请求**，量纲不同，不可类比）。

> **两个数字各自都对，错的是连线。** 这比「数字写错」隐蔽得多——校对数值查不出来，
> 因为每个数单独看都没问题。

**强制写法**：文档/注释里出现时长、数量、阈值时，紧跟一个**量纲短语**，说明「谁的、什么的、同步还是异步」：

```
✅  单次 ensure 请求阻塞 ~9-12s（同步，占住 HTTP 请求）
✅  前端后台轮询总预算 ~16s（异步，不阻塞用户操作）
✅  提交前等 warm 让锁的预算 3000ms（同步，Resource 层事务外）
❌  ~9-12s
❌  最多 ~16s
```

**读数一侧的配套判据**：拿两个数做推理前先问「**这两个数是同一量纲吗？**」——
同步耗时 vs 异步预算、单次 vs 累计、下界 vs 中位数，任一不同就不能互推、不能互相印证、不能类比大小。

> 与 §5.1「状态可以伪造，副作用不能」配成一对：
> §5.1 管**用例有没有走真实路径**（写的人）；本条管**读数的人有没有把两个数错误关联**（读的人）。

### D3-35 档 D 补充：预算是变量，且并发影响面要先界定

**① 预算值是变量，临界行数随它走**（🔒 断言前先读源码常量，不要写死）

| 预算 | 覆盖行数（按 `T(N) ≈ 0.44 + 0.065×N` 反推） | 状态 |
|---|---|---|
| 3000ms | 约 **39** 行 | 共享环境当前值 |
| 8000ms | 约 **116** 行 | 已批准、待落地 |

> 🔒 两个数都是**乐观下界**（N 行由同一行复制、料号相同、driver 展开缓存命中率偏高）。
> 独立佐证：后端另行估算 8s 覆盖「乐观 115 行 / 折算 60~80 行」，与本曲线的 116 行吻合；
> RECORD 记载存在 **77 行首存**的真实单——**落在 3s 之外、8s 之内**。
> 档 D 造多少行取决于落地的预算值，执行时按常量重算，不照抄本表。

**② 并发影响面（跑前必读，实测已界定）**

🔒 **单飞锁按 quotationId 隔离，占锁不会挡到别人的单**：
```
key = ('x'||substr(md5(quotationId),1,16))::bit(64)::bigint
实测 0082 / 0083 / 0100 → 947050492256157304 / -2777477647344093848 / 3621888754131836033（互不相同）
```
→ 在自己的沙箱单上占锁 3.7s，**不会**让其他会话的提交撞 409。**别把这个当风险写进结论。**

**真实风险是资源竞争，不是锁**：
- 50 行冷算 ensure 会真实跑满 driver 展开 + 公式求值，**占用共享 dev server 的 CPU 与 DB 连接 3.7s+**
- 造 50 行会连带产生 50×N 条 `quotation_line_component_data`

**执行协议**：① 单次跑通即可，不做重复采样；② 跑完立即删单（DRAFT 可删）；
③ 收尾断言 `SELECT count(*) FROM pg_locks WHERE locktype='advisory'` 回到基线；
④ 与其他会话的重活错开。

### D3-36　甲 · 提交前 force 重算 → 提交金额可信

| 归属 | 测试层级 |
|---|---|
| 跨端 | API 测试 + SQL 断言 |

**🔒 我的判据（不复用后端的推动手法）：直接压 force 谓词本身**

后端用「`0.05s` 间隔提交 + 加工费 `83.825536→999.999`，期望 `38.246716` 而非 `37.330516`」——那验的是**竞态窗口**。
我另取一个角度验**force 语义**，两者互为补充：

> 造一行 **`quote_card_values` 非 NULL 但内容陈旧、且 `li.subtotal` 与之自洽**的数据。
> 非 force 路径的 `IS NULL` 谓词**选不中它** → 提交时不重算 → 金额停在陈旧值；
> force 路径无谓词 → 必然重算 → 金额被纠正。

**执行步骤**
1. 复制沙箱单，触发一次懒算使其自洽（`li.subtotal == card_r6`）。
2. **人为制造"自洽的陈旧态"**：
   ```sql
   -- 把卡片值里 SUBTOTAL 页签的值与 li.subtotal 同时改成同一个假值
   UPDATE quotation_line_item SET subtotal = 555.555555,
     quote_card_values = jsonb_set(quote_card_values,
       '{tabs,<SUBTOTAL页签下标>,subtotal}', '555.555555'::jsonb)
   WHERE id = :LI;
   ```
   🔒 **两处一起改是关键**：只改 `li.subtotal` 会被 D3-14 口径判成"不变量已破"，
   而这里要造的是"**看起来完全自洽、但相对底层数据已陈旧**"——非 force 路径无从发现。
3. `POST /submit`。

**断言**
- 🔒 提交后 `li.subtotal = 37.330516`（真值），**不是 `555.555555`**。
- 🔒 `quote_card_values` 的 SUBTOTAL 页签同步回真值。
- 🔒 **反向判别**：若 force 未落地，两者都停在 `555.555555` 且提交返回 200 —— **静默错值，无任何报错**。
- 🔒 补跑后端那条窗口判据（`0.05s` 间隔 + `加工费→999.999` → 期望 `38.246716`）作为第二证据。

**证据形式**：三步 SQL 前后对照 + submit 响应。

### D3-37　🔴 乙 · `@DynamicUpdate` → 其他列不再被整行覆盖

> 🔒 **本条的判据必须用「甲治不了的列」**。甲只重算并写 `subtotal` / `cd.subtotal` / 单头三类；
> **`annual_volume` / `discount_*` / `line_total_amount` 它一列都不碰**。
> 所以「这些列在并发下存活」**只可能是乙的功劳** —— 这是本条与甲解耦的全部依据。
>
> ❌ **不得用 `subtotal` 验乙**：乙失效时 `subtotal` 被打回旧值，但甲会立刻把它重算回来 → 结果照样对 → 假绿。

**前置**：沙箱单一张，`annual_volume` 记为 `V0`。

**执行步骤（制造"两个事务改不同列"的竞态）**
1. 让一个慢操作**加载**该 li 并持有内存快照（`annual_volume = V0`）——用 warm（`ensure-card-values`，实测占锁 0.5~1.1s）。
2. **在它 commit 之前**，从另一路径把 `annual_volume` 改成哨兵 `7777` 并提交：
   ```bash
   curl -X POST .../ensure-card-values &          # t0 加载，开始算
   sleep 0.2
   psql -c "UPDATE quotation_line_item SET annual_volume=7777 WHERE id=:LI"   # t1 改别的列并 commit
   wait                                            # t2 warm commit
   ```
3. 查 `annual_volume`。

**断言（机械可判定）**
- 🔒 **乙生效**：`annual_volume = 7777`（哨兵存活）——warm 的 UPDATE 只含它自己改脏的列，不含 `annual_volume`。
- 🔒 **乙失效**：`annual_volume = V0`（哨兵被整行覆盖冲掉）。
- 🔒 **独立性自证**：同一次运行里 `li.subtotal` 无论是否被打回，**都不影响本条判定** ——
  因为甲不写 `annual_volume`，它救不回 `7777`。执行时把 `subtotal` 的前后值一并记录，
  **用于证明"即使 subtotal 被甲修正了，annual_volume 的结论仍独立成立"**。
- 🔒 **补充判据（SQL 形态，best-effort）**：`pg_stat_activity` 采样抓 UPDATE 原文。
  ```sql
  SELECT query FROM pg_stat_activity WHERE query ILIKE 'update quotation_line_item%';
  ```
  有乙 → 列数少、语句短；无乙 → 全列语句（本表列多，会被 `track_activity_query_size=1024` **截断**，截断本身即信号）。
  ⚠️ **仅作佐证**：`pg_stat_statements` **未安装**（`shared_preload_libraries` 为空，装它要重启 PG，共享环境不动），
  服务端 `log_statement=none`，采样有竞态。**判定以哨兵存活为准。**

**证据形式**：`annual_volume` 前后值 + 同期 `subtotal` 前后值（证独立性）+ 采样到的 SQL 原文（若抓到）。
