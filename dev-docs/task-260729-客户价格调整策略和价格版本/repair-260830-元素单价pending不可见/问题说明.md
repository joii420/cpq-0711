## ④ 问题原因 / 报告

### 4.1 根因（一句话）

> **`f_material_element_price` 是数据库函数，`QuotePendingRewriter` 的文本改写够不到它内部；
> 而该函数内部又自己读了一遍 `material_bom_item` / `element_bom_item` 并写死 `is_current = true`，
> 于是同一次查询里同一张表被读了两遍 —— 外层那遍看得见 pending，函数里那遍看不见。**

### 4.2 机制展开

`mc_view` 的两处数据来源待遇完全不同：

| 位置 | 是否被改写 | 结果 |
|---|---|---|
| `FROM element_bom_item ebi` | ✅ 白名单命中（`QuotePendingRewriter:46-49` 的 8 张表），token 被替换为把 `is_current` 重定义成 `(t.is_current OR t.pending_quotation_id = :pq)` 的子查询 | `_元素`/`_料件`/`_毛重`/`_净用量` 等列**全部正常取到** |
| `LEFT JOIN f_material_element_price(:customerCode, :priceBaseDate) cep` | ❌ 这是**函数**不是表名，不在白名单、也不可能在 —— 函数体是编译在库里的对象，正则文本替换够不到 | `元素单价` → `null` |

函数内部的失败点（`V369__task0729_material_element_price_and_views.sql:58-64`）：

```sql
candidate_materials AS (        -- 候选 material_no 全集
    SELECT material_no FROM material_bom_item
     WHERE customer_no IN (p_customer_no, '_GLOBAL_') AND is_current = true   -- ← 看不见 pending
    UNION
    SELECT material_no FROM element_bom_item
     WHERE customer_no IN (p_customer_no, '_GLOBAL_') AND is_current = true   -- ← 看不见 pending
)
```

该 CTE 的作用是把**元素级**的价（白银 = 12345）扩展成**料号 × 元素级**的价，好让视图能用统一的
`(material_no, element_code)` 二维键 JOIN。正泰 1845 个料号一个都不在这份候选清单里
⇒ `LEFT JOIN … ON cep.material_no = COALESCE(cl.root_no, ebi.material_no)` 匹配不上 ⇒ `null`。

**价本身是算得出来的**，不是没价：

```sql
SELECT * FROM f_customer_element_price('CUST-0004','2026-08-30');
-- 白银 | 12345.0000 | CNY | kg   ← 建档、行情、策略三样都在
```

### 4.3 证据链（全部可复跑，均为只读）

**证据 1 — 候选集实测为空**

```sql
SELECT count(DISTINCT material_no) FROM f_material_element_price('CUST-0004','2026-08-30');  -- 16
SELECT * FROM f_material_element_price('CUST-0004','2026-08-30') WHERE material_no='202601010001';  -- 0 rows
```

**证据 2 — A/B 对照，唯一变量 = `is_current` 过滤**

两条查询除 `candidate_materials` 的 `is_current` 过滤外**逐字相同**（同样的 pending 行可见改写、同样的 JOIN 条件、同样的基准日）：

```
实验A  现状取价                →  202601010001 白银 →  (空)
实验B  仅去掉 is_current 过滤   →  202601010001 白银 →  12345.0000
```

**证据 3 — 白银是天然对照组**

白银是 12 个元素里**唯一**建档（`element.element_code='白银'`）、有行情
（`element_daily_price` 1 条，`source_id=6b038405-…`，`price_date=2026-08-30`）、
策略覆盖（`element_price_strategy` CUST-0004 默认策略 `LATEST/factor=1/premium=0/ACTIVE`）三样齐全的元素，
它仍然 **1713 行全空** ⇒ 证明本根因**独立且充分**，与建档缺失无关。

**证据 4 — 数据侧已排除脏数据**

正泰 12 个元素值 `length` 与 `octet_length` 一致、`btrim` 前后相同 ⇒ 无前后空格、无不可见字符。

**证据 5 — 反向验证「只按 pending 判断」会更糟**

```
核价侧 (_GLOBAL_, p_pq=NULL)：只按 pending 判断 → 候选 0     ；现状 is_current → 候选 16
CUST-0002（全正式行）       ：只按 pending 判断 → 候选 0
SQL 三值逻辑：NULL = NULL → NULL，在 WHERE 里等价于 false
```

⇒ `is_current` 与 `pending_quotation_id = p_pq` 两个分支**各管一半，缺一不可**。

## ⑤ 修复方案

> **A0 裁决**：2026-08-30 用户裁决采用**方案乙**。

### 5.1 方案：函数加 pending 参数 + 改写器补参

**核心思路**：根因是「同一张表读两遍，外层被改写器覆盖、函数里那遍没覆盖」，
正解就是**让改写器把第二遍也管起来** —— 而不是放弃 pending 隔离。

**B-1｜迁移（新增 `V###`）**

① 新增**三参重载** `f_material_element_price(text, date, uuid)`：函数体与现两参版逐字相同，
   仅 `candidate_materials` 的两处过滤改为：

```sql
WHERE customer_no IN (p_customer_no, '_GLOBAL_')
  AND (is_current = true OR pending_quotation_id = p_pending_quotation_id)
```

② 旧**两参版**用 `CREATE OR REPLACE`（签名不变）改为委托调用：

```sql
SELECT * FROM f_material_element_price(p_customer_no, p_base_date, NULL::uuid)
```

🔑 **实施细节：用重载而非改签名，完整避开 §3.2「契约销毁」红线** ——
无需 `DROP FUNCTION`，老调用方（8 个用 `f_customer_element_price` 的组件、Java 侧
`PriceReconciler`/`PriceAdjustVersionGenerationService`）**一行不用改**。

已实测重载无歧义（2026-08-30，dev 库 `zz_tmp_probe` 临时探针，验后即删、残留 0）：
两参调用解析到两参版、三参调用解析到三参版，参数个数不同不构成歧义。

🔑 **`p_pq` 为 NULL 时 `pending_quotation_id = p_pq` 恒不成立**（SQL 三值逻辑），
函数自动退化为纯 `is_current` —— 这正是核价侧与冻结态需要的行为，**不需要额外写分支判断**。
这是 E-4/E-5/E-6「零回归」的技术依据。

**B-2｜`QuotePendingRewriter` 扩展**

新增一条改写规则：识别 SQL 中的 `f_material_element_price(<两个参数>)` 调用，补为三参形式
（第三参 = `:pq`）。约束：

- 复用既有的**注释屏蔽**机制（`QuotePendingRewriter:146` 的 `masked`，`task-0725 T1` 引入），
  确保注释里写的函数名不被误改
- 只在**已判定需要 pending 改写**的上下文生效（`SqlViewExecutor:569` 已保证核价侧 / 冻结态直接 return）
- 已是三参调用的**幂等跳过**
- 改写失败沿用既有**安全降级**语义（返回原文，本次渲染看不到 pending 数据，不影响正确性）

**B-3｜单元测试**：补齐 4.7 列出的三类缺口。

**改动文件清单**：

| 文件 | 改动 |
|---|---|
| `cpq-backend/src/main/resources/db/migration/V###__repair260830_*.sql` | 新增（三参重载 + 两参委托） |
| `cpq-backend/src/main/java/com/cpq/datasource/sqlview/QuotePendingRewriter.java` | 新增函数调用改写规则 |
| `cpq-backend/src/test/java/com/cpq/datasource/sqlview/QuotePendingRewriterTest.java` | 新增用例 |
| **15 个组件的视图 SQL** | **零改动**（那里面是客户已配好的生产配置） |
| 前端 | **零改动** |

**是否构成协议级改动**：**是**，但不触发 `AP-44`（字段类型联动）——
本次改的是「pending 可见性协议」的覆盖范围，不涉及 `field_type`、不涉及跨端契约、不改任何 API。
按 `change-protocol.md` 需登记的是：**今后凡在 SQL 视图里新增「内部会读版本化表的数据库函数」，
都必须同步纳入改写器的处理范围** —— 拟结案时提议晋升为规则。

### 5.2 已否决备选

- **已否决备选：方案甲（函数无条件去掉 `is_current` 过滤）** —— 改动最小（1 个迁移、零 Java、零视图），
  实测正常客户候选集逐字不变、性能 22.9ms→37.5ms 可接受，但它把 pending 隔离**从精确约束降级为巧合**
  （A 单渲染时候选集含 B 单的 pending 料号，实测不串价仅因「候选集只是料号白名单、价是元素级的」）。
  一旦将来有人拿这个候选集做别的判断即埋雷。**用户裁决不采用。**
- **已否决备选：方案丙（候选集下沉到视图，函数只返元素级价）** —— 结构上最彻底，
  但要改 15 个组件的生产视图配置，且 `versioned`/`realtime` 优先级要在视图里用 `DISTINCT ON` 重新表达，
  改配置的风险高于收益。**用户裁决不采用。**
- **已否决备选：只用 `pending_quotation_id = p_pq`（去掉 `is_current OR` 半边）** ——
  用户在 A0 阶段主动提出并要求评估，**已实测否决**：核价侧候选 16→0、老客户候选→0、
  本单核价转正后单价再次变空（见证据 5 / E-4 / E-5 / E-8）。

```sql

```
