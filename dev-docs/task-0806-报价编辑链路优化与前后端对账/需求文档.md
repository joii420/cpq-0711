## 1. 背景与目标

### 1.1 起点：BL-0127 修完，值对了，但结构问题还在

用户报 `QT-20260805-0080`「改了材料占比，只有小计变、行内公式列不动」。根因是三段闭环：

1. **行内 FORMULA 单元格优先读后端快照**（`QuotationStep2.tsx:3322-3338`），而**列小计/产品小计一律前端实时重算**（`buildCrossTabRows`，`:2855` 写在 ProductCard 渲染体里、非 `useMemo`）→ **同一列两个引擎**；
2. `saveDraft` 重建行时 `li.quoteCardValues = null`（D-1 失效），`editRows` 随之被抹掉；
3. 懒重建 `buildCardValues` 对 `editRows` **硬编码 null**，只读纯 driver 的 `snapshot_rows`。

实证：**全库 34 行有卡片值、非空 `editRows` = 0 行** —— 这条通道从未通电。已修复合并。

### 1.2 不做会怎样（三个仍在的问题）

| # | 问题 | 证据 |
|---|---|---|
| **P1** | **每编辑一格等 ~900ms** | 实测中位 900ms（附录 A） |
| **P2** | **前后端两套引擎无对账，分歧完全静默** | 历史断过三次：rowKey 对不上（全库 497 行只对上 1 行）/ `saveDraft` 清空 editRows / 重建不读 `row_data`。**每次都靠线上故障发现，没有一次是监控发现的** |
| **P3** | **快照是 4 条链路的数据权威，却零自动化覆盖** | 比对视图（`ComparisonViewService:286,292`）/ 价格升版（`MaterialVersionUpgradeService:263-276`，**重算后写回 `li.subtotal`**）/ 复制单（`QuotationService:1548`）/ 树删除重算（`QuotationTreeService`） |

### 1.3 做完达到什么状态

**把后端从「显示权威」降级为「校验器」**：

- DRAFT 下行内值走前端引擎 → 与列小计天然同源、零等待；
- 后端异步照算，两边**对账** → 不一致亮标记 + **禁止提交**；
- 在此安全网之上再叠异步、懒物化、缓存三级性能优化。

**目标量化**：编辑一格的用户感知 900ms → **0**；后端单次编辑耗时 900ms → **~450ms**（阶段③④后，须在生产态复测）。

### 2.2 本期明确不做

| 不做 | 原因 | 推迟去向 |
|---|---|---|
| 把公式引擎合并成一套 | 全搬后端 = 每格等往返；全搬前端 = 导出/比对/升版无浏览器可用。现实路径是两份实现 + 持续对账 | 不推迟，**永久不做** |
| 后端 `BigDecimal` 降级 `double` 求速度 | 会变快也会与前端更一致，但**金额精度退化**。项目选的是反方向（前端引入 decimal 向后端靠），方向正确 | 不推迟，**永久不做** |
| 缓存 `row_data` / `snapshot_rows` | 每次编辑就变，失效判据写不干净，有踩坑史 | 不推迟，**永久不做** |

| Redis 分布式失效 | D8 裁定先按单实例 | 转多实例部署时再做 |
| AC-3/5/6 三条自动化回归（BL-0127 遗留） | 覆盖对账够不着的入口（比对/升版/导出） | 保留在 `BL-0127` 条目下，本任务 ④ 后接续 |

## 3. 澄清结论与决策记录 ★

| # | 决策项 | 结论 | 理由 | 被否决的方案及原因 |
|---|---|---|---|---|
| **D1** | 对账不一致时怎么办 | **只标记 + 埋点，不自动改数**（用户拍板） | 谁对谁错无法自动判定；本次故障的教训就是「静默」比「错」更危险 | ❌ 自动以后端为准回灌 = 退回今天的行为（慢且会抹掉用户编辑）；❌ 自动采信前端 = 后端白算，对账退化成告警装饰 |
| **D2** | 告警内容 | **必须带两边的输入快照**，不能只报「结果不同」 | 一眼分清是「输入不同」（去查数据流）还是「同输入不同结果」（真引擎分歧）。见 §5.4 | ❌ 只报结果差值：排查仍要人肉挖，等于没减负 |
| **D3** | 异步竞态 | 带请求序号 / `row_version`，**过期响应直接丢** | 异步返回时用户可能已改了几格 | ❌ 后到即覆盖：会用旧快照结果盖掉新编辑（lost update） |
| **D4** | 差异阈值 | 按现行 `DISPLAY_SCALE = 6` 比对，差值 < 阈值视为一致 | 否则浮点末位天天误报，噪音淹没信号 | ❌ 逐字节比对：`BigDecimal` vs IEEE754 必然末位不同，恒报警 |
| **D5** | 对账粒度 | **编辑防抖后整卡对一次**，不是每格一次 | 跨页签公式必须整卡才有意义；每格一次请求量爆炸 | ❌ 每格失焦对一次：与 ② 的防抖合并冲突，且跨页签依赖看不全 |
| **D6** | 冻结单据 | 非 DRAFT **显示快照、前端算只用于对账** | 方向对称，且不破坏「提交即冻结、逐字节不变」语义 | ❌ 一律前端实时算：公式引擎/精度口径任何改动都会让历史单据显示漂移 |
| **D7** | 不一致能否提交 | **禁止提交**，并列出差异清单（用户拍板） | 自相矛盾的单子一旦冻结，比对/升版/导出各读各的，且**不可改** | ❌ 仅警告放行：等于知道有问题还放行，把矛盾永久钉进历史 |
| **D8** | 部署形态 | **先按单实例做**（用户拍板），缓存用本地 evict + TTL | 省掉一整块分布式复杂度；`redis-client` 扩展已装，转多实例时再补广播 | ❌ 一上来就上 Redis pub/sub：当前无多实例需求，为假想需求付复杂度 |
| **D9** | 判谁对的默认倾向 | **默认怀疑后端** | 金额链路（`li.subtotal`、Excel 导出）实际跟的是**前端**，前端错了直接反映在钱上、易被业务发现；后端错了藏得深 | ❌ 默认怀疑前端：与金额实际来源相反，会把排查引向错误方向。**注：本条是经验判断，非定论** |
| **D10** | 阶段① 五件事能否拆开上 | **不能，必须一起上** | 只做分流不做对账 = 把唯一的人肉探针（用户肉眼）也拆了 | ❌ 先分流后补对账：中间窗口期完全裸奔 |
| **D11** | 阶段③ 懒物化的粒度 | **只推迟公式列，INPUT 值即时写** | INPUT 是用户敲的、不需要「算」；贵的只是上千次公式求值。这样 ensure 挂载点少一半 | ❌ 整个 `row_data` 都推迟：行键判重等只看 INPUT 的读取方也被迫挂 ensure |

## 4. 功能需求

### 阶段① · 分流 + 对账 + 提交闸门

- **FR-1** DRAFT 单据的行内 FORMULA 单元格取值改走前端引擎（`computeAllFormulas` / `computeTabFormulasTree`）；非 DRAFT 仍读快照 `formulaResults`。
- **FR-2** `ProductCardProps` 新增 `quotationStatus`，**报价侧 / 核价侧 / `ReadonlyProductCard` 三处调用点全部透传**（AP-41）。
- **FR-3** 保留「快照缺该 rowKey / 该列时本地兜底」现有行为，**不得删除**（新行 / LIST_FORMULA 字符串公式依赖它）。
- **FR-4** 后端异步返回结果后，前端逐格与本地值比对；差异按 D4 阈值判定，超阈值写入 `out.errors` 旁路 → `ComponentCell` 显示 ⚠ + tooltip，tooltip 内容按 D2（两边值 + 两边输入）。
- **FR-5** 差异上报埋点（API-5），含 lineItemId / componentId / rowKey / 字段名 / 两边值 / 两边输入摘要。
- **FR-6** 提交前置校验 `assertLineSettled(lineItemId)`：存在**未落定的对账差异**或**在飞的编辑写**→ 拒绝提交，返回差异清单（API-3 新增错误码）。

### 阶段② · 异步

- **FR-7** 编辑请求改为不阻塞渲染：`handleSnapshotCellEdit` 不再 `await` 后回灌，仅把响应交给对账。
- **FR-8** 防丢更新：同一 `lineItemId` 的编辑请求服务端串行化（或用现有 `row_version` 乐观锁 + 失败重放）。
- **FR-9** 编辑请求防抖合并：连改 N 格合并为 ≤2 次请求（D5 同批做整卡对账）。
- **FR-10** 失败可见：自动重试 N 次，仍失败则在卡片上显示可见失败态（不得静默）。

### 阶段③ · 懒物化

- **FR-11** `row_data` 的**公式列**改为懒物化：编辑期只标脏，不逐组件 `REQUIRES_NEW` 落库；**INPUT 值仍即时写**（D11）。
- **FR-12** 新增 `ensure-row-data` 端点（API-2）；Excel 视图 / 导出 / 折扣基数 / 提交冻结采集 / 回填采集 / 价格归位 / 价格升版**调用前先 ensure**（清单见 §5.3）。
- **FR-13** 脏标记**持久化**（进程重启 / 多实例不得丢）。

### 阶段④ · 缓存

- **FR-14** 缓存冻结结构，key = `quotationId + view_kind`。
- **FR-15** 缓存 `row_key_fields`，key = `componentId`。
- **FR-16** 失效：写入口事务提交后同步 `evict`；配 TTL 兜底与手工清缓存诊断端点（API-4）。
- **FR-17** **禁止 negative caching**：查不到时不缓存 `null`。

## 附录 A · 实测基线（本方案全部依据，非估算）

### A.1 一格编辑 ≈ 900ms（端点），方法内 795ms 分布

| 阶段 | 中位 | 占比 |
|---|---|---|
| 整行物化 `row_data`（**8 次 `REQUIRES_NEW` 独立事务**） | **356 ms** | **45%** |
| 整卡重算 assemble（PASS1+PASS2） | 120 ms | 15% |
| 小计覆盖 + **整单表头重算** | 78 ms | 10% |
| 加载实体 + 冻结结构 + 抽 baseRows/editRows | 53 ms | 7% |
| flush / clear / 重读实体 | 39 ms | 5% |
| 应用编辑 + 查墓碑 | 12 ms | 1.5% |
| 序列化 cardValues | 0.3 ms | ~0 |

> 写的数据量只有 **27 KB**（`quote_card_values` 23KB + 8 组件 `row_data` 3.8KB）。
> **贵在 9 次独立事务提交 × 远程往返，不是数据量。**

### A.2 缓存收益（用现成 `precomputeCardValuesPrefetch` 实测）

```
无缓存（每次重查重解析）  均值 229.5 ms
有缓存（复用预取）        均值  60.0 ms     → 计算段省 74%
建缓存一次性              282.3 ms          → 必须「建一次命中多次」才划算
```

放回全链路：900ms → ~730ms（端到端 19%）。

### A.3 冻结结构体量（决定缓存内存代价）

| 视图侧 | 份数 | 平均 | 最大 | 全库合计 |
|---|---|---|---|---|
| `QUOTE_CARD` | 51 | 22 KB | 38 KB | 1.1 MB |

### A.4 测量环境与可信度

全部数字来自 **dev 模式 + 远程共享库（`10.177.152.12`）**，且测量期间有并发会话在同库活动。生产是打包 jar + 可能同机房 DB，**SQL 往返快很多时缓存与懒物化的收益都会缩水**。

动阶段③④ 之前**必须**用 `target/quarkus-app/quarkus-run.jar` 在生产态复测基线 —— 本项目在性能上栽过这个跟头（优化「首存慢」时，实测发现真正卡点不在当初以为的地方）。
