## 0. 一句话

**把后端从「显示权威」降级为「校验器」**：DRAFT 下行内值走前端引擎（与列小计天然同源、零等待），后端异步照算，两边**对账**——不一致就亮出来并禁止提交。在此安全网之上，再做异步、懒物化、缓存三级性能优化。

## 1. 背景：为什么现在做

### 1.1 已交付的前置（BL-0127）

用户报 `QT-20260805-0080`「改了材料占比，只有小计变、行内公式列不动」。根因是三段闭环：

1. **行内 FORMULA 单元格优先读后端快照**（`QuotationStep2.tsx:3322-3338`），而**列小计/产品小计一律前端实时重算**（`buildCrossTabRows`，`:2855` 写在 ProductCard 渲染体里、非 `useMemo`）→ 同一列两个引擎；
2. `saveDraft` 重建行时 `li.quoteCardValues = null`（D-1 失效），`editRows` 随之被抹掉；
3. 懒重建 `buildCardValues` 对 editRows **硬编码 null**，只读纯 driver 的 `snapshot_rows`。

实证：**全库 34 行有卡片值、非空 `editRows` = 0 行** —— 这条通道从未通电。已修复并合并（回种 + 内容键配对 + 两个既有缺陷）。

### 1.2 但修完只是"值对了"，三个结构性问题仍在

| # | 问题 | 现状 |
|---|---|---|
| **P1** | **每编辑一格等 ~900ms** | 实测中位 900ms（本机 dev + 远程共享库） |
| **P2** | **前后端两套引擎无对账，分歧静默** | 历史上断过三次（rowKey 对不上 / saveDraft 清空 / 重建不读 row_data），每次都靠线上故障发现 |
| **P3** | **快照是 4 条链路的数据权威，却无自动化覆盖** | 比对视图 / 价格升版（**写回 `li.subtotal`**）/ 复制单 / 树删除重算 |

## 2. 实测基线（本方案的全部依据，非估算）

### 2.1 一格编辑 ≈ 900ms（端点），方法内 795ms 分布

| 阶段 | 中位 | 占比 |
|---|---|---|
| ⑤ 整行物化 `row_data`（**8 次 `REQUIRES_NEW` 独立事务**） | **356 ms** | **45%** |
| ③ 整卡重算 assemble（PASS1+PASS2） | 120 ms | 15% |
| ⑦ 小计覆盖 + **整单表头重算** | 78 ms | 10% |
| ① 加载实体 + 冻结结构 + 抽 baseRows/editRows | 53 ms | 7% |
| ⑥ flush / clear / 重读实体 | 39 ms | 5% |
| ② 应用编辑 + 查墓碑 | 12 ms | 1.5% |
| ④ 序列化 cardValues | 0.3 ms | ~0 |

> **写的数据量只有 27 KB**（`quote_card_values` 23KB + 8 组件 `row_data` 合计 3.8KB）。
> **贵在 9 次独立事务提交 × 远程往返，不是数据量。**

### 2.2 缓存收益（用现成 `precomputeCardValuesPrefetch` 实测）

```
无缓存（每次重查重解析）  均值 229.5ms
有缓存（复用预取）        均值  60.0ms      → 省 74%（计算这半段）
建缓存一次性              282.3ms
```

放回全链路：900ms → ~730ms（**端到端 19%**）。写仍是天花板。

### 2.3 冻结结构体量（决定缓存内存代价）

| 视图侧 | 份数 | 平均 | 最大 | 全库合计 |
|---|---|---|---|---|
| `QUOTE_CARD` | 51 | 22 KB | 38 KB | 1.1 MB |
| `COSTING_CARD` | 43 | 47 KB | 48 KB | 2.0 MB |

**全库全缓存原始 JSON 才 3.1 MB** —— 内存不是约束。

## 3. 已裁定决策

| # | 决策 | 裁定 | 理由 |
|---|---|---|---|
| **D1** | 对账不一致时怎么办 | **只标记 + 埋点，不自动改数** | 谁对谁错无法自动判定；自动回灌 = 退回今天的行为；自动采信前端 = 后端白算。**静默改数比显示不一致更危险** |
| **D2** | 告警内容 | **必须带两边的输入快照**，不能只报"结果不同" | 一眼分清是「输入不同」（去查数据流）还是「同输入不同结果」（真引擎分歧）。见 §6 |
| **D3** | 竞态 | 带请求序号 / `row_version`，**过期响应直接丢** | 异步返回时用户可能已改了几格 |
| **D4** | 差异阈值 | 按现行 `DISPLAY_SCALE = 6` 比对，小于阈值视为一致 | 否则浮点末位天天误报 |
| **D5** | 对账粒度 | **编辑防抖后整卡对一次**，不是每格一次 | 跨页签公式必须整卡才有意义 |
| **D6** | 冻结单据 | 非 DRAFT **显示快照、前端算只用于对账** | 方向对称，且不破坏冻结语义 |
| **D7** | 不一致能否提交 | **禁止提交**（列出差异清单） | 自相矛盾的单子一旦冻结，比对/升版/导出各读各的，且不可改 |
| **D8** | 部署形态 | **先按单实例做** | 缓存用本地 evict + TTL，**不上 Redis 广播**（扩展已装，将来需要再加） |
| **D9** | 判谁对的默认倾向 | **默认怀疑后端** | 金额链路（`li.subtotal`、导出）实际跟的是前端，前端错了直接反映在钱上、易被业务发现；后端错了藏得深。**经验判断，非定论** |

## 4. 四阶段方案

> **顺序不可调换**：① 是后面三步的安全网。②③④ 的任何错误最终都表现为"前后端对不上"，而对账正好盯这个。先优化后补网 = 中间裸奔。

### 阶段① · 分流 + 对账 + 差异可见 + 提交闸门

**这五件事必须一起上** —— 只做分流不做对账 = 把唯一的人肉探针也拆了（本次故障正是用户肉眼发现的）。

| # | 改动 |
|---|---|
| **A1** | `ProductCardProps` 加 `quotationStatus`，**三处调用点全传**（报价侧 / 核价侧 / `ReadonlyProductCard`）。⚠️ AP-41：漏一处 = 一个视图对一个视图错 |
| **A2** | 取值分支：`useSnapEdit` 增加 `&& status !== 'DRAFT'`；DRAFT 下直接用 `computeAllFormulas`（**那趟计算本来每次渲染就在跑，边际成本为 0**） |
| **A3** | 保留"快照缺该 rowKey / 该列时本地兜底"（现状已有，**不得删**） |
| **A4** | 后端算完回来做对账，逐格比对；不一致写入 `out.errors` 旁路 → `ComponentCell` 已有 ⚠ + tooltip 通道 |
| **A5** | 提交前置检查 `assertLineSettled(lineItemId)`：**在飞的写 + 未落定的对账差异**一起挡（与阶段②③共用同一个闸门） |

**解决**：P2（分歧静默）+ 显示不同源。

### 阶段② · W1 异步（前端不 await）

| 风险 | 对策 |
|---|---|
| **丢更新**（去掉 await 后并发请求基于旧快照互相覆盖） | 按 `lineItemId` 串行化，或用已有 `row_version` 乐观锁 + 失败重放 |
| 失败静默 | 自动重试 N 次 + 可见失败态 |
| 提交竞态 | 复用 A5 闸门 |
| 对账噪音 | 等该行所有在飞写落定后才比 |

**收益**：用户感知 **900ms → 0**。**解决**：P1。

### 阶段③ · W3 懒物化 `row_data`

抄 `P3 lazy-excel` 现成模式（首存留 NULL → 用时调 `ensure-excel-values` 补算）：编辑期只标脏，`row_data` 推迟到真要用时再物化。

**优化形态**：只推迟**公式列**，INPUT 值即时写 —— INPUT 根本不需要"算"，贵的只是那上千次公式求值。这样挂载点再砍一半。

**收益**：**~356ms / 次（45%）**，单项最大。

**前置调研已完成**，结论见 §5。

| 风险 | 对策 |
|---|---|
| 脏标记必须落库（进程重启/多实例会丢） | 加持久化标记列，或复用 `snapshot_at` / `row_version` |
| 懒算雪崩（多行同时脏，打开 Excel 一次性全算） | **只能缓解不能消除**（成本转移非消失）：分批 / 后台预热 / 进度提示。`ensure-excel-values` 已在承受同款 |
| 双写入源打架（`saveDraft` 前端权威 vs 懒物化后端算） | 必须一次明确裁决谁赢并写进文档 |

### 阶段④ · 缓存（冻结结构 + 行键）

| 缓存 | key | 何时变 | 失效机制 | 失效时间 | 兜底 TTL | 容量 |
|---|---|---|---|---|---|---|
| **冻结结构** `quotation_view_structure` | `quotationId + view_kind` | 仅显式重建结构 | 写入口**事务提交后** `evict(quotationId)` | 同步立即 | **30 分钟** | LRU 200（全库才 51 条） |
| **`row_key_fields`** | `componentId` | 组件保存 | 组件保存**提交后** `evict(componentId)` | 同步立即 | **10 分钟** | 全量常驻（几百个短数组） |

> TTL 的作用**不是**"内容会变"，而是**防某条写路径漏挂 evict** —— 它是保险丝，不是主机制。

**三道防线**（失效点漏挂是本阶段头号风险，且**静默**）：
1. **失效钩子必须放在唯一写入口**。写入口多于一个 → **先收敛入口，再上缓存**（前置条件）
2. TTL 兜底（上表）
3. 留手工清缓存的诊断端点，出事不用重启

**🚨 硬规则：永远不要缓存"查不到"的结果（negative caching）。**
`ImplicitJoinRewriter.tableColumnsCache` 就栽在这儿——视图 `DROP CASCADE` 瞬间缓存了空集，永久残留 → BNF 路径不再注入谓词 → 视图返全表 → UI 出现「首值（共N项）」。CLAUDE.md「任何 schema DDL 后必须重启 Quarkus」那条纪律即由此而来。
落地：**`loadRowKeyFieldsNode` 返 null 时不缓存 null**。

**收益**：计算段 74%，端到端 ~19%。

**D8：单实例部署**，故本阶段**不做 Redis 广播失效**；将来转多实例时，本地 evict 会失效（最长 TTL 窗口不一致），届时再补广播。

## 6. 对账告警的内容要求（D2 展开）

**不能只报"结果不同"**，必须同时带该行两边的输入快照：

```
不一致：物料 / Ag粉 / 材料成本
  前端 6.087758    输入：材料占比=0.25  组成数量=2  元素单价=28892.5
  后端 608.775811  输入：材料占比=25    组成数量=2  元素单价=28892.5
                         ^^^^^^^^^^^^ 输入就不同
```

排查顺序（按本项目真实发生频率）：**① 输入不是同一份 → ② 字段解析口径 → ③ 公式没被解析到 → ④ 行集/行序 → ⑤ 真算术差异**。
⑤ 最罕见：`GoldenCardValuesEquiv` 的 amt-002/003 曾被归因为精度分歧，后有提交专门更正——**真实根因不是精度**。

> **仍存在的分歧面（本任务不修，但对账要能照出来）**：前端主干四则运算已用 decimal.js（task-0801 的 `ArithDecimalParser`）、列小计用 `sumDecimal`，但 **C\* 族聚合与 `cross_tab_ref` 聚合仍是纯 JS number**（`formulaEngine.ts:188` 注释明写）。而本次故障涉及的 `<XTAB SUM>` 恰走这条路。

## 8. 明确不做

| 不做 | 原因 |
|---|---|
| 把公式引擎合并成一套 | 全搬后端 = 每格等往返；全搬前端 = 导出/比对/升版无浏览器可用。现实路径是两份实现 + 持续对账 |
| 后端 `BigDecimal` 降级为 `double` 求速度 | 会变快也会与前端更一致，但**金额精度退化**。项目选的是反方向（前端引入 decimal 向后端靠），方向正确 |
| 缓存 `row_data` / `snapshot_rows` | 每次编辑就变，失效判据写不干净，有踩坑史 |
| 缓存 `template.components_snapshot` | 失效面扇出（一个组件 → N 个模板），且主路径读的是冻结结构。归 `task-0806-模板发布全量冻结` |
| W4 按依赖图增量重算/增量写 | 风险最高（漏算下游 = 静默不一致）。等 ① 对账跑稳后单独评估 |
| Redis 广播失效 | D8 单实例，暂不需要 |
