## 五、本轮修复的缺陷

### BUG-1（阻塞级，已修并验证）— batch-expand 快照旁路无视 `usage` 门控

- **发现**：测试工程师 T5 执行期
- **复现**（验收人亲自）：带 `lineItemId` 时，`usage=COSTING`／非法 `XXX`／不传 **三者均返回含 `__v6_id` 的 pending 数据** → 违反 AC-17
- **根因**：`ComponentResource:301-308`（Phase1 `tryReadSnapshot`）与 `:446`（`expandWithSnapshot` 内部同样先读快照）**都不看 `usage`**。而 `quotation_line_component_data.snapshot_rows` **只由报价侧写**（实测核价侧完全不用该表）——修复前该表内容为空故无害，T3 的 P1 让报价侧在开域态写入后就含 `__v6_id` 了
- **修法**：用已有 `isQuoteUsage()` 门控两处；非 QUOTE 改走不读快照的 9 参 `expand()`（保留完整上下文）
- **验收人复验**：`COSTING`/`XXX`/缺省 **全部不含 `__v6_id`** ✅；`usage=QUOTE` 仍命中快照优化 ✅（未误伤）；逐页签行数不变；86 tests 全绿
- **补上的真正缺口**：新增 `ComponentResourceSnapshotBypassUsageTest`(4)。T4 原 4 个类**结构性覆盖不到**这条路径（用合成 componentId、从不预置 `snapshot_rows` → 快照永远 miss）。新测试**预置**含 `__v6_id` 的快照夹具，并在 `@BeforeEach` 加**前置非空断言**（先确认夹具确实写入，否则会因"快照本来就 miss"而空转通过——正是 T4 漏掉的原因）

### T3 顺带修复的独立缺陷（否则 BOM 树 100% 失败）

P1 生效后递归 CTE **第一次**真正进入 `QuotePendingRewriter.rewrite()`，其「主位表探测」fallback（顶层没有则退化为任意深度第一个 `FROM`）对 `WITH RECURSIVE` + SELECT 列表标量子查询选错主位，把 `__v6_id` 锚点插进只能返单列的标量子查询 → PG `subquery must return only one column`。修法：新增 3-arg `rewrite(sql, conn, injectAnchor)`，树 spine 传 `false`；2-arg 委派 3-arg(`true`)，既有 3 个调用方逐字不变（已核实）。
