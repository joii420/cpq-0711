## 2. 需求背景与目标 ⭐

- **要解决什么问题 / 痛点**：

  导入报价 Excel 建单后，报价单产品卡的**所有页签内容全空**。实测样本 `QT-20260725-0001`（客户罗克韦尔 CUST-0001，主件 S-3120014539，导入源 `docs/table/报价测试数据/v2/报价系统模板0723.xlsx`）：6 个页签中 5 个业务页签 `baseRows` 为空数组，BOM 页签落失败哨兵，第 6 个是 SUBTOTAL 依赖前者故必然为空。

  **导入侧完全正常**：Excel 17 张表的行数与导入日志逐张吻合，`[v6import] QUOTE TOTAL status=SUCCESS sheets=19`，数据已正确落库。**问题 100% 在渲染读取侧**，且由三个互相独立的根因叠加造成：

  | # | 根因 | 影响页签 | 性质 | 状态 |
  |---|------|---------|------|------|
  | 1 | **pending 感知 SQL 改写在驱动展开链路失效**（`quotationId` 全链路未传播 → 改写门槛恒关） | 材料成本 / 外购件成本 / 加工费 / BOM | 代码级缺陷 | **本期修** |
  | 2 | **`rewriteNamedParams` 不屏蔽 SQL 注释**，把注释里的 `:命名参数` 也当占位符 → 参数错位查询直接报错 | 产品 / BOM | 代码级缺陷 | **本期修** |
  | 3 | `costing_bom_tree_config` 表空，缺 `usage=QUOTE` 生效配置 | BOM | 环境缺配置（非代码 bug） | ✅ 2026-07-25 已配置并激活 |

  **根因 1 所属功能**：task-0721「报价数据版本升级」的 **B3 pending 感知改写**。该功能的业务价值是「**报价单私有草稿数据 + 核价通过才转正**」的数据隔离机制——销售在报价阶段导入的基础资料（BOM / 元素 / 加工费 / 电镀等 7 张版本化 V6 表）不应立刻污染全系统正式基础资料（其他报价单、核价单读同一批表），故设计为：

  ```
  导入   → is_current=false + pending_quotation_id=本单   （待生效）
  本单   → 靠 B3 pending 感知改写「本单可见」              ← 断在这里
  他单   → 不可见（数据隔离）
  核价通过 → B5 QuoteBackfillService 升版转正，全系统可见
  ```

  当前断的是「本单可见」这一环，导致销售在 DRAFT 阶段完全看不到自己刚导入的数据，**无法核对即无法决定是否提交核价**——功能核心价值失效。

- **本次要达成的目标**：

  1. 报价单在 **DRAFT（未冻结）** 状态下，产品卡各页签能正确显示本单 pending 数据，与导入 Excel 内容一致（逐页签期望行数见 §8 验收标准）。
  2. 修复后**无需变更任何现有组件 / 模板 / 视图 SQL 配置**即生效（已验证现有 5 个视图 SQL 逻辑均正确）。
  3. 核价侧（`usage=COSTING` / 无 quotationId 上下文 / 已冻结报价单）**零回归**，行为逐位不变。
  4. 注释中书写 `:命名参数` 作为文档说明**不再触发查询失败**（这是正当的配置习惯，框架应当兼容）。

- **不做什么（明确边界）**：

  - **不改任何组件 / 模板 / 视图 SQL 配置**——排查已确认现有配置正确（`jg_view` 的 `price_type='PROCESS'` 经确认是"仅自制加工费"的有意口径，非缺陷）。
  - **不动 B5 升版回填逻辑**（`QuoteBackfillService`）——该环节工作正常，不在本期范围。
  - **不做树 SQL 配置**——根因 3 已于 2026-07-25 完成（见 §9 关联记录）。
  - **不解决「跨客户同成品的根客户推断」**——报价树 SQL 因框架未注入 `:customerCode`，多客户报价同一成品时按 `customer_no` 字母序取根客户。属 task-0721 已登记的 follow-up，本期不扩范围（建议进 Backlog）。

## 4. 功能详述 ⭐

### 4.1 用户场景 / 操作流程

1. 销售进入「报价单导入」，上传客户报价 Excel（如 `报价系统模板0723.xlsx`）。
2. 系统解析 19 个 sheet，把 BOM / 元素 BOM / 各类加工费 / 电镀等写入 7 张版本化 V6 表，落**待生效**状态（`is_current=false` + `pending_quotation_id=本单`）。
3. 系统建报价单（DRAFT）+ 明细行，并**物化产品卡各页签内容**进 `quote_card_values`。
4. 销售打开该报价单 Step2，**期望看到各页签显示自己刚导入的数据**（当前实际：全空）。
5. 销售核对无误后提交核价；核价通过时 B5 把 pending 数据升版转正。

**当前失败点在第 3~4 步**：物化时读不到 pending 数据，空内容被冻结进 `quote_card_values`，第 4 步看到空表。

### 4.2 界面与交互（前端相关）

- 涉及页面 / 入口：报价单向导 Step2（产品卡页签区）、报价单详情页（`ReadonlyProductCard`）
- **有一处前端改动**（2026-07-25 架构评估后修正，原判断「无前端改动」不成立）：前端两侧共用同一个 `useDriverExpansions` hook 且传**同一个 quotationId**（`QuotationStep2.tsx:3362` 报价 / `:3364` 核价），而后端 `BatchExpandDriverRequest.Task` **没有侧别字段** → 实时 batch-expand 路径无法区分报价侧/核价侧，无法决定是否开启 pending 可见域。须新增 `usage` 字段（缺省 `COSTING` = 不开，保证老前端零行为变化）并由前端按视图传值。详见 `fronttask.md` / `api.md`。
- 页签结构 / 列 / 交互本身不变，前端主要是从「渲染空数组」变成「渲染有数据的数组」。
- 需前端配合验证的点：
  - 各页签数据正常显示，**不得出现 "加载中…" 永久占位**（AP-31 族）
  - BOM 页签树结构正确（父子层级 / 同料号多 occurrence 不挂错枝）
  - 不得出现「首值（共 N 项）」错乱（AP-22 族）
- 有无原型 / 截图：无需新原型；以修复前后同一报价单的页签截图作为证据。

### 4.3 业务规则与计算逻辑（后端相关）

#### 根因 1 —— pending 感知改写门槛恒关

**机制**：`QuotePendingRewriter` 把视图 SQL 中 7 张白名单表（`unit_price` / `material_bom` / `material_bom_item` / `element_bom` / `element_bom_item` / `capacity` / `plating_scheme`）替换为等价子查询，并把 `is_current` 列重定义为：

```sql
(t.is_current OR t.pending_quotation_id = :pq) AS is_current
```

用户原写的 `WHERE x.is_current` 一字不改，替换后对本单 pending 行自动成立（零配置）。

**门槛**（`SqlViewExecutor.java:555`，`BomTreeRenderService.resolvePendingOwner()` 同款）：

```java
if (owner.quotationId == null || owner.isQuotationFrozen()) return sqlTemplate;
```

**断点**：填充页签的驱动展开入口一进门就把上下文的 quotationId 擦成 null（`ComponentDriverService.java:341-342`，另一处 `:643` 同样）：

```java
SqlViewRuntimeContext.setNested(componentId, null, null, null);
//                                           ↑templateId ↑quotationId ↑status
```

而 `setNested` 是**整体覆盖**语义（`SqlViewRuntimeContext.java:92-103`，注释原文「先保存旧值，再覆盖」），不继承 `prev` 的 quotationId：

```java
Snapshot prev = CURRENT.get();
CURRENT.set(new Snapshot(OwnerType.COMPONENT, componentId, templateId, quotationId, quotationStatus));
return prev;   // 旧值仅留待 finally 恢复，不参与合并
```

**设计意图与实现矛盾**：`ComponentDriverService:339-340` 的注释留了逃生舱——「渲染期上层可进一步 setNested 补 quotationId+status」。但覆盖语义使该逃生舱**不可达**：上层即便补了，driver 一进来就覆盖成 null，而覆盖窗口正好是需要它的执行期。且实测全工程仅 3 处调用 `SqlViewRuntimeContext.set*`，物化报价卡的 `ConfigureSnapshotService` **完全没设**：

| 调用点 | 传入 quotationId |
|--------|-----------------|
| `ComponentDriverService:342` | `null` |
| `ComponentDriverService:643` | `null` |
| `FormulaEvaluateResource:119` | 有值，但属 Excel 公式求值路径，非报价卡页签 |

**两条独立失败路径（同一根因）**：
1. `applyPendingRewrite` 直接 return 原模板 → 视图仍按原始 `is_current` 过滤 → 0 行
2. `injectPendingParam` 不绑 `:pq`；`rewriteNamedParams` 对未绑定占位符替换为**字面量 NULL** → `pending_quotation_id = NULL` 恒不成立 → 0 行

**修复要求（行为契约，不预设实现）**：
- 报价卡物化 / 渲染期间，SQL 视图执行与 BOM 树递归执行时，上下文必须能取到**当前报价单的 quotationId 与 status**。
- `quotationId` 可从既有入参推导：`expand()` 已接收 `lineItemId`，而一个 lineItem 唯一属于一张报价单。
- 冻结态（`SUBMITTED` / `APPROVED` / `PUBLISHED`）与核价侧必须保持「不改写」语义不变。

**修法：已完成架构评估，采纳方案 D'（2026-07-25）**

原提出的 A / B 两个候选**均被否决**，评估过程另发现 3 个改变方案空间的事实：

| 候选 | 结论 | 否决/采纳理由 |
|------|------|--------------|
| A 给 `setNested` 加继承语义 | ❌ **否决（单独实施是 no-op）** | 全工程除 `FormulaEvaluateResource:119`（Excel 路径）外，**没有任何调用点给 `prev` 塞过 quotationId** → 继承一个恒为 null 的值等于什么都没修。且 `SqlViewRuntimeContext` 结构上无法承载「quotationId 已知、owner 未知」——`setNested(null,…)` 会把整个 Snapshot 吞成 `EMPTY`（`:94-97`），外层根本放不进去 |
| B 显式穿参 | ❌ **否决（性价比最差且未消除判错风险）** | 需改 `expand()` **6 个重载** + `expandUncached`/`expandMulti`/`expandForPartSet`/`expandWithSnapshot` ≈ 20 个签名 + 12 处 callsite + 6 个测试；且**修不到报价树那条路**——`ConfigureSnapshotService:343-345` 构造的 lite line 只有 `id` + `productPartNoSnapshot`，`render()` 无法反查 quotationId，还得再改 `render` 的 4 个重载。更致命的是 `CardSnapshotService:1957`（核价）与 `ConfigureSnapshotService:403`（报价）调**同一个 8-arg `expand`**，两处必须传相反值 → 判错成本最高 |
| **D' pre-gated 窄作用域** | ✅ **采纳** | 新建 `com.cpq.datasource.sqlview.QuotePendingScope` 专用 ThreadLocal，承载**已判定完毕**的 pending 归属，**仅由报价侧渲染入口开启**。0 个签名改动；`SqlViewExecutor` / `SqlViewRuntimeContext` 均不动；现有 `SqlViewExecutorPendingHookTest` / `SqlViewIsolationBoundaryTest` 不改一行仍有效 |

**D' 的两条保障机制（核心价值 —— 把 AC-17/AC-10 从「靠人审查」升级为「靠构造保证」）**：

- **AC-17 核价零回归** = 核价侧任何入口**一律不调用 `open()`**（靠"不调用"而非运行时判断 → grep 一个方法名即可穷举静态审查）
- **AC-10 冻结态** = `open()` **内建冻结判定**：冻结态 ⟹ 存 null ⟹ 下游 `quotationId` 保持 null，与修复前逐位相同

**⚠️ 一个诱人但错误的"2 行修法"（必须避开）**：工程里已有 `com.cpq.formula.dataloader.QuotationIdContext`，在全部 8 个渲染入口都 set 过 quotationId（`ComponentDriverService:363` 已在读它做缓存维度），直接拿它当 pending owner 只需改 2 行。**但它是报价/核价两侧共用的** —— `CardSnapshotService:809`（`precomputeCostingDriverUnion`，纯核价）/ `:1937` / `:492` 都是核价路径，且 `CreateQuotationMaterializer:43` 在 **DRAFT** 状态就会调 `ensureCardValues` → 「DRAFT + 核价渲染 + 非 null quotationId」三条件同时成立 → **核价侧开始 pending 改写，100% 破 AC-17**。

**⚠️ `quotationStatus` 必须恒传 null，不得传真实 status（HIGH 级隐性风险）**：`ComponentSqlViewService:379` 有一条今天恒不可达的休眠分支——

```java
if (ctx.quotationId != null && ctx.isQuotationFrozen()) {
    Optional<ComponentSqlView> fromQuotation = lookupFromQuotationSnapshot(ctx.quotationId, ...);
```

一旦把真实冻结 status 传进 `SqlViewRuntimeContext`，已提交报价单的视图 SQL 来源会从 `component_sql_view` 实时表**静默切换**到 `quotation_component_sql_snapshot` 表 → 已冻结单渲染结果可能漂移。方案 B「显式穿真实 status」最容易踩。D' 靠 pre-gate 天然规避：`pendingOwner()` 已保证「非 null ⟹ 非冻结」，故 status 传 null 时 `isQuotationFrozen()=false`，既让 `SqlViewExecutor:555` 门槛成立，又让 `:379` 保持休眠。**一个值同时满足两个消费者的正确性，是本方案的核心不变量，必须在代码里写下注释锁定。**

**修复行为契约（实现无关）**：
- 报价卡物化 / 渲染期间，SQL 视图执行与 BOM 树递归执行时必须能取到当前报价单的 pending 归属。
- 冻结态（`SUBMITTED` / `APPROVED` / `PUBLISHED`）与核价侧必须保持「不改写」语义逐位不变。
- `BomTreeRenderService.resolvePendingOwner():436-441` 必须改为读 `QuotePendingScope`——它原读 `SqlViewRuntimeContext`，而在 `ConfigureSnapshotService:350` 调 `render()` 那一刻**从未有任何 `setNested` 发生过**（driver 的 setNested 在更内层的 `:216 expandUncached`），故恒返 null。这是报价树侧的独立断点。

#### 🔴 评审补充 1（BLOCKER）——driver 路径上有**两层**缓存，都必须补 pending 维度

2026-07-25 评审发现：只给 `ComponentDriverService.cacheKey` 补维度**不够**，D' 宣称的「AC-17 由构造保证」会不成立。

`com.cpq.formula.dataloader.DataLoader` 是 `@RequestScoped`（`:45-46`），持有实例级 `resultCache`（`:56`），**就在 driver 展开路径上**（`ComponentDriverService:498` / `:581` / `:678` 都调 `dataLoader.loadByPath(...)`），且**只在 `@PreDestroy` 清**（`:379-382`；`clearCache()` 注释明写「仅供测试」，全工程无生产调用方）。其 key（`:189-191`）为：

```
normalizedPath :: partNo :: customerId :: viewLineItemId :: ownerTag :: quotationId
```

**没有「pending 是否可见」维度**。碰撞路径：F4 前提成立时（同组件挂报价+核价两个模板），报价侧与核价侧这 6 个维度**逐字相同**（templateId 两侧都是 null，因 `setNested` 第 2 参恒 null；quotationId 同为本单）；而 `CreateQuotationMaterializer:41/43` 在**同一请求线程**先跑报价再跑核价 → 同一个 DataLoader 实例 → **核价侧直接拿到报价侧已改写、带 `__v6_id`、含 pending 行的结果**。

⚠️ 另注意 `:90` 那个重载的 key **只有 `normalizedPath` 一项**，粒度更粗，须一并评估。

→ **`cacheTag()` 必须同时进 `DataLoader` 三个进缓存的 `loadByPath` 重载（`:90` / `:104` / `:189`）的 key。**

#### 🔴 评审补充 2（HIGH）——batch-expand 的**合桶**会把侧别抹平

`ComponentResource:318-331` 的 bucketKey 为 `componentId | customerId | partVersion | dp | fieldsTag | q=quotationId [| li=lineItemId]`，**没有侧别维度**。`canMerge`（`:342-343`）成立时整桶只跑一次 `expandMulti`，作用域只能按 `pivot`（`:336`）开一次 → 桶内混着报价/核价任务时，其中一侧必然拿到错误的可见性。

**✅ 决策（2026-07-25）：把侧别纳入 bucketKey，报价/核价永不合并**（改动约一行）。这样混合批次也能正确工作，`api.md` §2.3 的混合示例保持有效。

#### 根因 2 —— 命名参数替换未屏蔽 SQL 注释

`SqlViewExecutor.rewriteNamedParams`（`:602`）用正则 `(?<!:):([a-zA-Z_][a-zA-Z0-9_]*)` 扫占位符，仅排除 `::` 强转，**不识别 `--` 行注释 / `/* */` 块注释 / 字符串字面量**。于是注释里的 `:customerCode` 也被替换为 `?` 并追加一个绑定值，而 pgjdbc 解析时会忽略注释内的 `?`，造成 **Java 侧绑定数 > pgjdbc 认到的占位符数**：

```
WARN [SqlViewExecutor] executeAllRows failed path=$cp_view:
     The column index is out of range: 3, number of columns: 2.
```

**已用隔离 JDBC 复现，报错文字逐字一致**（`pgjdbc 认到 2 个，Java 侧绑 3 个 → setObject(3) 抛出`）。
