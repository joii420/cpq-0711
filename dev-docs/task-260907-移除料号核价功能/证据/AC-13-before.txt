采样过程中我自己犯的两个错（记下来，因为它们都差点变成错误结论）
================================================================

【错误 1】用 LIKE 判 JSON 结构 —— 假阴性
  我先跑了这组判据：
    costing_card_values::text LIKE '%basicDataValues":{"%'   → 0
    costing_card_values::text ~ '"subtotal":"[1-9]'          → 0
    costing_card_values::text LIKE '%editRows":[{%'          → 0
    costing_card_values::text LIKE '%resolvedRows":[{%'      → 0
  「整整齐齐全是 0」，差点据此写下"全库核价侧无任何业务数据"。

  实际原因：列是 jsonb，`::text` 输出会被 PG 规范化成 **冒号后带空格**：
    {"tabs": [{"tabName": "物料BOM", "baseRows": [{...
  而我的模式全部假设冒号后无空格 ⇒ 必然 0 命中。

  改用 jsonb 操作符重查后：
    非零 subtotal 的页签 = 9257   ← 不是 0
    非空 basicDataValues 的行 = 0  ← 这个确实是 0（另一回事，见下）
    非空 editRows 的页签 = 0       ← 同上

  📌 教训：**判 JSON 结构要用 jsonb 操作符，不要用字符串 LIKE。**
     「结果整齐得可疑」本身就是重查的理由 —— 真实数据很少这么干净。

【错误 2】看一个样本下全称结论
  我把 API 响应里 **第一个** lineItem 的 costingCardValues 打出来，看到
  4 个页签 baseRows 为 []、subtotal 为 "0"，就判定「这张单核价侧几乎全空、
  不能当夹具」，并准备去换单。

  实际：这张单 1845 个 lineItem 里，**1844 个有非零 subtotal**。
  我抽到的第一个恰好是那唯一的空行。

  📌 教训：判夹具是否够用要**统计全体**（GROUP BY / count），
     不是看第一条。
