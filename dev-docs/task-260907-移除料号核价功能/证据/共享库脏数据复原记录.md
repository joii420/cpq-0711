# 共享库脏数据复原记录（2026-09-07）

## 起因

测试代理执行 `AC-8a` / `AC-8b` 的读写序列时，步骤 8「改回原值」**没有真的生效** —— 用例日志打印了「已复原为 10」，但值没写回去。它在收工核对时查库发现并主动上报（其测试代码原本只打印不回读，已在本轮修掉：现在会回读校验并大声报错）。

## 影响面（只读手段量化，`CLAUDE.md §3.2` 第 1 步）

| 表 | id | 料号 | 版本 | 字段 | 现值 | 应为 |
|---|---|---|---|---|---|---|
| `ds_cost_basic_material_bom` | 6853 | 3120014539 | v8 | `item_seq` | 11 | 10 |

## 可恢复性（§3.2 第 2 步）

**可恢复** —— 原值在历史表完好：`ds_cost_basic_material_bom_history` v7（id=255）与 `ds_cost_detail_material_bom_history` v1 各一行 `item_seq=10`。

## 为什么不能走 UI / API 复原（主线三组实验）

| 实验 | body | 结果 |
|---|---|---|
| 干跑：不改任何值 | 原样回传 | `UNCHANGED`（证明 body 格式正确、零副作用） |
| A：`item_seq` 11→10，**保留**旧 `row_fingerprint` | 改一个字段 | `UNCHANGED` |
| B：`item_seq` 11→10，**删掉** `row_fingerprint` 字段 | 改一个字段 | `UNCHANGED` |

⚠️ 端点：`PUT /api/cpq/dataset/{cost-basic|cost-detail}/parts/3120014539/sheets/MATERIAL_BOM/rows`
⚠️ 乐观锁字段名是 **`baseVersion`** 不是 `versionNo`（用 `versionNo` 会返 409「数据已被他人更新至 v8」）。

## 🚩 根因：这是既定设计，不是缺陷（推翻测试代理的归因）

测试代理报为「**疑似缺陷**：项次 10→11 能存、11→10 被静默丢弃，值得单独立项」。**该归因不成立。**

决定性证据 —— `cpq-backend/src/main/java/com/cpq/dataset/fingerprint/RowFingerprints.java:17-18`：

> `row_fingerprint = SHA-256( 各「对比项」列的规范化值 … )`
> **只有** `compared=true` 的列参与（调用方负责过滤）—— **典型是「项次」建字段但不参与指纹，故改项次不升版（AC-17）**。

⇒ `item_seq` 不参与指纹是 `task-260902` 的**既定设计**（其 `AC-17`）。**任何单独修改 `item_seq` 的保存都会返 `UNCHANGED`，与方向无关。**

**那第一次 10→11 为什么存下来了？** 因为它搭了另一列变化的便车 —— 全列比对 v7(history) vs v8(current)：

```
v7: "source": "IMPORT"  , "item_seq": 10, row_fingerprint = dafdabe5…
v8: "source": "MANUAL"  , "item_seq": 11, row_fingerprint = a70dab6c…
                ↑ 变了两列，不是一列
```

首次手工编辑把 `source` 从 `IMPORT` 翻成 `MANUAL`，**是它驱动了升版**；`item_seq` 只是顺带被写进去了。
复原时 `source` 已是 `MANUAL` 不再变化，只剩不参与指纹的 `item_seq` ⇒ 必然 `UNCHANGED`。

> 📌 **主线自己在这条上也差点下错结论**：第一次只比对了 6 列（`item_seq`/`component_qty`/`base_qty`/`material_loss_rate`/`defect_rate`/`row_fingerprint`），
> 看到「唯一变化是 `item_seq` 而指纹变了」，据此断言「`item_seq` 参与指纹」。
> **全列比对才发现漏了 `source` 列。** —— 与本任务另外两次同型失误（`LIKE` 判 JSON 假阴性、看第一个样本下全称结论）同源：**拿局部观察当全称结论。**

## 处置（§3.2 第 3 步：已获用户明确批准）

用户 2026-09-07 批准「甲：SQL 直改回 10」。

```sql
BEGIN;
SELECT count(*) FROM ds_cost_basic_material_bom  WHERE id=6853 AND item_seq=11;  -- 1
SELECT count(*) FROM ds_cost_detail_material_bom WHERE id=15   AND item_seq=11;  -- 1
UPDATE ds_cost_basic_material_bom  SET item_seq=10 WHERE id=6853 AND item_seq=11;  -- UPDATE 1
UPDATE ds_cost_detail_material_bom SET item_seq=10 WHERE id=15   AND item_seq=11;  -- UPDATE 1
COMMIT;
```

**为什么 SQL 直改在这里不破坏一致性**：`item_seq` 不参与 `row_fingerprint` 计算（见上），
所以改它**不会**造成指纹与内容失配 —— 指纹 `a70dab6c…` 保持原值即是正确状态。
🚫 **未改 `source`**：它记录「本行被手工编辑过」，是真实事件，改回 `IMPORT` 反而是伪造历史。

## 遗留（登记 BACKLOG，非缺陷）

「用户改了项次 → 点保存 → 提示成功 → 实际没存」这个 **UX 缺口**依然存在：设计上不升版是对的，但 UI 不该让用户以为存进去了。
性质是**交互改进**，不是缺陷 —— 🚫 不要按「静默丢数据的 bug」去立项修它，那会改掉 `task-260902 AC-17` 的既定设计。
