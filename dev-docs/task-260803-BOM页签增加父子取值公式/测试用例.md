## 0. 测试环境与自动化边界说明

**已知环境限制**（影响本文档每条用例的可执行方式）：

- 测试库 Flyway 校验挂着，所有 `@QuarkusTest` 起不来 → 后端自动化只能是**纯 JUnit**（不依赖 CDI/DB 的纯函数测试，如树关系解析、单元格拓扑排序、有值判据、边界计算）。
- 后端 REST API 级校验（闸 ②③④、Excel 降级、400 响应）依赖 `ComponentService`/`ComponentImportService` 等 CDI Bean，无法用 `@QuarkusTest` 跑，只能对**本地已在跑的 dev server**（`localhost:8081`，默认 profile，连 `cpq_db_0724`）用 `curl` 半自动验证 → 标注 **[手工-curl]**。
- 前端 UI 交互（FormulaBuilder 分区/抽屉/chip/tooltip）需要真实浏览器，标注 **[手工-UI]**（前端 dev server `localhost:5174`）。
- 双端语义一致性（前端 `formulaEngine.ts` vs 后端 `FormulaCalculator`）理论上应双端各跑一遍同一组用例对比结果；纯函数层面双端各自可自动化，但"两端结果逐位相同"这件事本身仍需人工比对（除非真的落地了共享夹具，本文档不假设该夹具已存在）。
- 端到端验收（AC-27/28，真实报价单/核价单渲染 + `row_data` 落库）→ **[手工]**，需要真实浏览器 + 已在跑的前后端 dev server。

**自动化程度标签**：
- **[自动化]**：可写纯 JUnit（或前端 vitest，若有）验证，不依赖外部服务
- **[手工-curl]**：需要 dev server 在跑，用 curl 验证 REST 层行为
- **[手工-UI]**：需要真实浏览器操作
- **[手工]**：端到端／需要人工判断截图等综合场景

**优先级**：P0 阻断 / P1 重要 / P2 增强

## 11. 🔍 需求缺口清单

> 本节是本次测试设计的核心产出。以下每条都是需求文档本身说不清楚、隐含矛盾、或未覆盖的边界，**不是我在挑刺实现**，而是需求条款本身留白，实现方无论怎么做都有理由。

### G1【高】混合表达式下"公式列恒有值"是否会传染整个 CSUM/CAVG 的有值判定

- **位置**：§4.3.4 判据 2/3/6 三条叠加处
- **问题**：判据 6 规定"被引用列是公式列时恒为有值"。当一个聚合表达式**同时**引用一个取数列（可能为空）和一个公式列（恒有值）时——例如 `CSUM([用量] × [成本])`，`用量` 是取数列且某子行为空，`成本` 是公式列——按判据 3"至少一个 field 取到值→该行整体判定为有值，参与聚合（取不到值的字段按 0 代入）"，因为 `成本` 恒有值，这一行会被判定为"有值"并参与聚合（用量按 0 代入，贡献 0），**而不会**像"CSUM(单独引用用量)"那样被整行剔除。
  这个结论是从判据 2/3/6 组合推导出来的，需求文档没有给出这种"取数列 + 公式列混合"的显式例子，容易让配置者、甚至实现方都理解错（如果实现方误把判据 6 只用于"单列聚合是不是公式列"这种简单场景，混合表达式下可能被写成"任一 field 是取数列且为空就整行排除"的更直觉但与判据 3 字面不符的逻辑）。
- **建议**：请 PM/架构明确写出这个组合案例的期望结果（本文档 TC-VAL-03 已按字面推导给出一版，建议采纳或订正），并在 §4.3.4 加一段专门说明。

### G2【中】成环之后，"下游于环"的单元格是否也带错误标记

- **位置**：§4.3.6 求值架构 第 1 条
- **问题**：原文"成环 → 环上所有 cell 值置 0 + 错误标记，不影响图上其他 cell"。但一个**不在环内、却依赖了环上 cell** 的单元格（例如 `D = A + 1`，其中 `A` 是环上 cell）——`D` 最终会不会也被打上 ⚠ 标记，还是安静地算出 `0+1=1` 且不带任何错误提示？这直接决定用户能不能定位问题根因（分不清"D=1 是正常业务值"还是"D=1 是因为上游算错兜底成 0 之后的连锁反应"）。
- **建议**：明确"错误标记是否沿依赖边向下游传播"，并补一条 AC。若决定不传播，也应在文档里显式写明，避免实现方和测试各自猜测出两种不同的行为。

### G3【中】非 BOM 组件已配 `previous_row_subtotal`，改成 BOM 类型时是否需要拦截

- **位置**：§4.3.8 闸 ③
- **问题**：闸 ③ 只规定了"改离 BOM"方向的拦截（已配父子 token 的 BOM 组件不能改走）。但反方向——一个非 BOM 组件本来就用了 `previous_row_subtotal`（BOM 页签整体禁用该 token），用户把它的 `tabType` 改成 `'BOM'`——需求没规定这个动作要不要拦。如果不拦，组件会先进入"BOM 类型但含被禁用 token"的非法状态，直到下次保存公式才会被闸 ② 发现，中间有个不一致的窗口期。
- **建议**：明确该反向场景（"改入 BOM 且已有 PREV"）是否也要在改 `tabType` 那一刻校验，而不是拖到下次改公式才发现。

### G4【中】批量导入 bundle 部分失败的粒度

- **位置**：§4.3.8 闸 ④ / AC-19
- **问题**：原文"bundle 同 ② 校验，不留绕过口"，没说明当 bundle 内**多个组件**中只有一个违反父子公式规则时，是**仅该组件导入失败**（部分成功）还是**整个 bundle 回滚**（原子操作）。这个粒度直接决定 AC-19 该断言什么——检查"某个具体组件被拒绝且其余成功导入"，还是检查"整个导入请求返回失败、无一入库"。
- **建议**：请架构师明确导入失败粒度（建议与现有导入服务对非法组件的既有处理方式保持一致），并把断言写进 AC-19 的判据里，而不是只写"拒绝"两个字。

### G5【中】悬空父引用（`__parentId` 指向的节点不在当前行集里，非墓碑原因）

- **位置**：§4.3.1 树关系定义
- **问题**：§4.3.1 只定义了"墓碑删除行"这一种"父不存在"的已知情形（父被删 → 子视为无父）。但还有另一种情形：某行的 `__parentId` 指向的节点根本**不在这批 baseRows 里**（既不是墓碑，可能是版本切换、分页截断等原因造成的数据不一致）。这种情形下：
  - `[是否根]` 严格按字面定义"`__parentId` 为空 → 1"，而这里 `__parentId` **非空**（只是指向的行找不到），所以 `[是否根]` 按字面应该显示 **0**——但这具有误导性，因为这一行实际上根本取不到父行的值。
  - `PGET` 在这种行上该返回什么？按"父行不存在"的既有精神应该也是 0（类比墓碑父的处理），但需求没有把这种情形正式纳入 §4.3.1 的定义范围。
- **建议**：把"悬空引用（父行不在当前行集）"显式并入"父不存在"的统一处理条款，并裁决 `[是否根]` 在此情形下是否也应该显示为 1（即"事实上无法取到父值"是否应该等价于"是根"）。

### G6【低】单节点树（只有根、没有任何子行）时 `[是否根]` 与 `[是否叶子]` 是否互斥

- **位置**：§4.3.2 树属性定义
- **问题**：需求从未讨论过这种最简单的边界（T12：只有一个根节点，没有子行）。把 `[是否根]`（`__parentId` 为空→1）和 `[是否叶子]`（`C(r)=∅`→1）两条定义字面组合，这个唯一的根节点会**同时**满足 `[是否根]=1` 且 `[是否叶子]=1`。这不算矛盾（两条定义各自独立成立），但容易让配置公式的用户误以为这是两个互斥状态（类似单选），写出类似"`IF [是否根] THEN X ELSE IF [是否叶子] THEN Y ELSE Z`"这种条件公式时，如果误以为二者不会同时为真，可能漏考虑"根同时也是叶子"该走哪条分支的场景。
- **建议**：在配置文档/UI 提示里显式举出"单节点树，根即叶子"这个例子，避免用户的条件公式漏分支。参见附录夹具 **T12**（只有根、无任何子行）：按字面定义组合，S0 应同时得到 `[是否根]=1` 且 `[是否叶子]=1`；本文档**未将其列为正式 TC**——因为需求本身从未明确规定这一具体组合的期望行为，写成"预期结果"只能是从两条独立定义反推的合理猜测，而非需求条款直接给出的判据，不满足"预期结果必须可判定"的要求，故只作为 gap 佐证材料保留在此处。

### G7【高】AC-29 性能验收缺少量化阈值

- **位置**：§8.4 AC-29
- **问题**：AC-29 只要求"实测最大树的页签级求值耗时，写入交付文档"，没有给出任何"多少行 × 多少公式列必须在多少毫秒内完成"的通过/不通过界限。这导致该 AC 实质上是一条**过程性要求**（有没有测），而不是**结果性验收**（测出来达不达标）。如果实测出来的耗时是秒级甚至更慢，算不算这条 AC 失败，文档没给判据——测试工程师无法在这条上给出"通过/不通过"的结论，只能给出"数字是多少"。
- **建议**：请架构师/PM 至少给一个参考阈值（例如"`COMP-0157` 规模的树，页签级求值应在 Xms 内完成，超过则视为需要优化"），否则 AC-29 永远只能停留在"测过了"层面。

### G8【低】F-2/F-5/F-7 的具体 UI 文案未定稿

- **位置**：§4.2 F-2/F-5/F-7

  2. F-7"行内红字说明"的具体措辞未给出。

### G9【中】"公式列恒有值"是否对所有形态的 FORMULA 都成立，包括纯字段直通赋值

- **位置**：§4.3.4 判据 6
- **问题**：判据 6 断言"公式列总能算出一个数（哪怕是 0）"，这个"恒有值"的保证，前提是"现有引擎的空按 0 口径"对**所有形态**的 FORMULA 都生效。但 §4.3.3 脚注里描述"空按 0"口径时举的例子是**算术运算**场景（`[用量] × [损耗率]` 这类乘除加减）。一个最简单的"纯字段直通赋值"公式（如 `成本 = [取数成本]`，没有任何运算符，只是把另一个字段的值原样透传）在 [取数成本] 为空时，这条"空按 0"口径是否同样适用、还是可能直接透传 `null`——需求文档没有明确说清楚。如果直通赋值场景下公式列结果真的可能是 `null`，判据 6 的"恒有值"这个大前提在这种子情形下就不成立，进而影响 TC-VAL-07/TC-VAL-08 这类依赖判据 6 的用例是否成立。
- **建议**：请架构师明确确认"纯字段直通赋值型 FORMULA"是否 100% 不返回 null（即是否也纳入"空按 0"口径），并把这条正式写入引擎既有口径定义里，而非隐含假设。**本文档的 T10/TC-VAL-07/08 已经默认按"恒不为 null"设计，若该假设不成立，这几条用例的预期值需要重新核定。**
