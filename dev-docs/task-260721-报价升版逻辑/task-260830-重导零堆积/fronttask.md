# fronttask —— 前端任务分解

## 结论：前端零改动

本次改动全部落在后端（`VersionedV6Writer` 的写入分支判定 + 版本号选取 + `QuoteBackfillService` 转正去重 + 5 张表唯一键迁移），**不改任何接口契约、不改任何响应字段、不改任何页面**。

> ⚠️ 2026-08-30 扩范围（S-4~S-6）后，后端改动面变大，但**前端仍为零改动** —— 契约与响应字段一字未变，见 `api.md`。前端的责任从 4 项回归确认增加到 5 项。

### 判定依据

| 判据 | 说明 |
|---|---|
| 无新增/变更接口 | 见 `api.md` —— 导入端点与核价通过端点的方法、路径、入参、响应体、错误码全未变 |
| 无响应字段变化 | 导入结果 `SheetResultDTO.successRows` 等字段语义不变。**重导时后端不写行，但 `successRows` 仍按「本次处理的业务行数」计数**（与改动前一致），前端展示无需调整 |
| 无页面设计改动 | 不新增页面/弹层，不改布局与交互 ⇒ **不触发 `frontend.md §1.3` 的 HTML 原型图要求** |
| 无字段类型变动 | 不改任何 `field_type` ⇒ **不触发 `AP-44`** 的 17 个协议检查点 |

### 需回归确认的清单（前端不改，但要确认没被后端改动带坏）

| 编号 | 服务的 AC | 回归项 |
|---|---|---|
| F-R1 | AC-3 | 「从已有产品添加」列表：未提交单的料号仍不出现（B7 闸门行为不变） |
| F-R2 | AC-1 | 首次导入后打开报价单，页签数据正常渲染（正式行走 `QuotePendingRewriter` 第二分支，不应出现「加载中…」或「—」） |
| F-R3 | AC-4 | 第 2 次导入同一文件后打开报价单，数据与第 1 张单一致且完整 |
| F-R4 | AC-7 | 报价单改值 → 核价通过后，页面显示改后的值 |
| F-R5 | AC-16 | **共用版本号的第二张单核价通过后，其页面数据仍完整显示**。<br>背景：B-14 的去重分支会**删掉该单自己的草稿行**，此后它读的是另一张单转正后的正式行（走 `QuotePendingRewriter` 第二分支）。数据内容逐字相同，理论上无感知，但**必须真机确认不出现空白/「加载中…」/「—」**——这正是 `AP-31` / `AP-38` 的典型触发形状（行没了但渲染层还在等） |

> ⚠️ F-R2 特别说明：`AP-31`「加载中…永久占位族」与 `AP-38`「0 行 driver 鬼魂行」都表现为渲染层症状但根因在后端取数。本次改动改变了数据的 `is_current` / `pending_quotation_id` 取值形态，**必须真机确认渲染无回归**，不能只看后端 SQL。
