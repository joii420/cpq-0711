## 2. 需求背景与目标 ⭐

### 2.1 现状与问题（已实证）

报价导入的三个 Sheet ——「来料年降」「组装加工费年降」「年降系数」—— 业务上是同一件事：同一批列（年降顺序、年降系数、单次固定年降值、货币、计价单位、降价次数），只是**年降挂在谁身上**不同。但当前落在**两张表、三套语义**：

| Sheet | Handler | 目标表 | 写入语义 | 版本化 | pending 隔离 | 客户维度 |
|---|---|---|---|---|---|---|
| 来料年降 | `Q08IncomingAnnualDiscountHandler` | `unit_price`（`price_type=INCOMING_MATERIAL_REDUCTION`） | 组级整组替换 | ✅ | ✅ | ✅ |
| 组装加工费年降 | `Q15AssemblyAnnualDiscountHandler` | `unit_price`（`price_type=COMPONENT_REDUCTION`） | 组级整组替换 | ✅ | ✅ | ✅ |
| 年降系数 | `Q19AnnualDiscountHandler` | `annual_discount` | **行级 upsert（空值不覆盖）** | ❌ | ❌ | ❌ |

由此产生四个问题：

**问题一 · 建模冗余**：同一批列的读取与写入逻辑写了三遍，任何规则变更都要改三处。

**问题二 · 语义不一致**：同一次导入里，前两个 Sheet 是「本次导入的行集即当前状态」，第三个是「空值不覆盖旧值」（`ON CONFLICT DO UPDATE SET col = COALESCE(EXCLUDED.col, existing.col)`，见 `AnnualDiscountRepository.CONFLICT_SET`）。

**问题三 · pending 隔离缺口（缺陷）**：V349 只给 7 张版本化表 + 占号表加了 `pending_quotation_id`，`annual_discount` 不在其中。**「年降系数」在报价单 pending 期就直落正表并立即对所有报价单生效**，破坏 task-0721 建立的他单隔离。

**问题四 · 客户维度缺失（缺陷）**：`uq_annual_discount = (biz_type, material_no, discount_strategy, discount_order)` 不含客户编号。同一销售料号导给 A 客户后再导给 B 客户，**后者静默覆盖前者**。

**同一列语义分裂的旁证**：「来料年降」的投入料号躲在 `unit_price.code`（同一列在别的 `price_type` 下又是元素代码 / 零件号 / 耗材料号），「组装加工费年降」的工序编号躲在 `unit_price.operation_no`，两者在表里根本对不上，无法用一条 SQL 统一取"某料号的全部年降"。

### 2.2 关键前提：三条路径当前均为「只写不读」

2026-08-03 全量勘察（库 `cpq_db_0724`）：

| 读路径 | 结果 |
|---|---|
| `component_sql_view.sql_template` 提到 `annual_discount` / `REDUCTION` / `年降` | **0 条** |
| PG 视图引用（`mc_view` / `tool_view` 命中的是列名 `cep.unit_price`，非表） | **0 个** |
| 组件 `data_driver_path` / 字段 `basicDataPath` 引用 | **0 个** |
| Java 侧读 `annual_discount` 表（`QuoteTableAxis` / `Capacity` 命中的是 `annual_discount_factor` **列**，非本表） | **0 处** |
| 存量数据 | `unit_price`：`COMPONENT_REDUCTION` **1 行**、`INCOMING_MATERIAL_REDUCTION` **0 行**；`annual_discount` **0 行** |

前端 `formatPathValue.ts` / `QuotationStep2.tsx` 中的 `INCOMING_ANNUAL_DOWN` / `ASSEMBLY_ANNUAL_DOWN` / `ANNUAL_REDUCTION_FACTOR` 只是 Sheet 类型的中文显示名，与存储无关。

> ⚠️ **推论（本需求的基石）**：没有下游要改、没有存量要洗，此刻合并的迁移成本接近零。这是动手的最佳窗口 —— 一旦某个客户模板开始配年降页签，改造成本将成倍上升。

### 2.3 本次要达成的目标

1. 三个 Sheet 落到**同一张年降表** `annual_discount`，用 `discount_type` 区分。
2. 写入语义归一：三类统一走 `VersionedV6Writer` 组级版本化 + pending 隔离。
3. 补齐 `customer_no` 客户维度（修问题四）。
4. 补回此前被丢弃的列：`seq_no`（项次）、`discount_times`（降价次数）。
5. 纠正 `docs/table/报价系统Excel导入落库方案.md` §8 / §15 / §19 的落库规则描述，含 3 处已发现的文档漂移。

### 2.4 不做什么（明确边界）

- **不配组件页签 / SQL 视图 / 模板绑定**：年降如何参与报价与核价计算是独立业务需求，需求尚不存在，应单独立项。本次只到"能被读"为止，不做"真的去读"。
- **不动核价侧**：核价导入没有任何年降 Sheet（`docs/table/核价系统Excel导入落库方案.md` 全文无「年降」）。
- **不动 `unit_price` 的 CHECK 约束**：`INCOMING_MATERIAL_REDUCTION` / `COMPONENT_REDUCTION` 两个枚举值退役但保留在 `chk_unit_price_type` 里 —— 动 CHECK 要 DROP/ADD constraint，收益为零。
- **不做历史数据迁移**：`annual_discount` 空表；`unit_price` 存量 1 行且无读者，迁移中直接清除，重导即恢复。
- **不新增 UI / 不改导入结果 DTO / 前端零改动**：新增的校验错误走现有 `failedRows` / `errors` 渲染通道（`QuoteBasicDataImportV6Drawer.tsx` 已具备）。
- **不合并三个 Handler**：编排器按 `sheetName()` 一对一分发，合并要改分发协议（见 §10 Q5）。
- **不触发 AP-44**：本次不改任何 `field_type`，不涉及组件管理 / 模板管理 / 报价渲染三大核心模块。

## 4. 功能详述 ⭐

### 4.0 前提：报价导入是两阶段架构（本需求全部规则以此为准）

`QuoteImportService.importQuote()` 自 task-0709 update-0723 起为两阶段：

| 阶段 | 实现 | 行为 |
|---|---|---|
| **Phase 1** | `QuoteImportValidator.validate()` | 全量只读校验，**零写库**。任一 sheet `failedRows > 0` → 整单 `FAILED`，直接返回、不进 Phase 2 |
| **Phase 2** | `QuoteImportService.writeAll()` | 单一事务（`REQUIRES_NEW`），全部 handler `MANDATORY` join。任一 handler `recordError` → 整单回滚 |

> ⚠️ **推论**：`recordError` ≡ 整单导入失败，不存在「跳过坏行、其余照常落库」。**业务校验的正确落点是 Phase 1，不是 handler。**

### 4.1 用户场景 / 操作流程

**前置**：与 repair-0727 相同 —— 「组装加工费年降」用到的工序须已在 主数据维护 → 工序（`process_master`）中登记。

**主流程**：
1. 报价单管理 → 从基础数据导入 → 选客户 → 上传报价 Excel。
2. **Phase 1** 校验三个年降 Sheet：销售料号 / 投入料号 / **年降顺序** 必填；「组装工序」按 `ProcessNoResolver` 两段匹配解析（保持 repair-0727 现状）。
3. **Phase 2** 三个 handler 各自声明 `discount_type` 与 `target_no` 来源，共用 `AnnualDiscountWriter` 落库到 `annual_discount`。
4. 落库行 `is_current=false` + `pending_quotation_id=本单`（pending 期他单不可见）。
5. 创建报价单 → `V6QuotationCommitService` 把 pending 归属从导入记录过户到报价单。
6. 核价通过回填 → `QuoteBackfillService` 把 pending 行转正（`is_current=true` + `pending_quotation_id=NULL`），老组 `is_current` 切走。
7. 任一必填校验失败 → Phase 1 拦截，整份 Excel 导入失败，数据库零变动。

### 4.2 界面与交互（前端相关）

**本次前端零改动。** 新增的「年降顺序必填」错误走现有导入报告的 `failedRows` / `errors` 渲染通道，无新增 UI、无新增字段、无接口变更。

### 4.3 业务规则与计算逻辑（后端相关）

#### 规则一：表结构 —— 就地改造现有空表 `annual_discount`

不新建表名。`annual_discount` 现有 0 行、0 读者，改造成本等于新建，且省掉"旧表怎么办"的决策。

```sql
-- 判别列：现有 biz_type 的 CHECK 已是 (INCOMING, ASSEMBLY, FINISHED)，语义天然对应三个 Sheet
ALTER TABLE annual_discount RENAME COLUMN biz_type TO discount_type;
-- 重建 CHECK，取值：
--   INCOMING_MATERIAL  ← 来料年降
--   ASSEMBLY_PROCESS   ← 组装加工费年降
--   FINISHED           ← 年降系数（整单级）

-- 新增列
system_type          VARCHAR(10) NOT NULL DEFAULT 'QUOTE'
customer_no          VARCHAR(20)          -- 导入时由系统提供，三类统一
target_no            VARCHAR(30)          -- 语义由 discount_type 决定，见规则二
seq_no               INTEGER              -- 项次
version_no           VARCHAR(20) NOT NULL
is_current           BOOLEAN     NOT NULL DEFAULT true
pending_quotation_id UUID
pending_supersedes   UUID[]

-- 删除列（无写入方、无读取方）
discount_strategy    -- 被 discount_type 取代（原恒写死 '来料年降'）
discount_base        -- 建表至今从未写入

-- 保留列
material_no（销售料号，主轴）/ discount_order / discount_ratio
/ fixed_discount_value / currency / unit / discount_times
```

**唯一键**（与 `uq_unit_price` 同口径：groupKey ∪ 版本列 ∪ 组内行区分列）：

```sql
DROP INDEX uq_annual_discount;
CREATE UNIQUE INDEX uq_annual_discount ON annual_discount(
    system_type, discount_type, material_no,
    COALESCE(customer_no, ''), COALESCE(target_no, ''),
    version_no, COALESCE(discount_order, 0));

CREATE INDEX ix_annual_discount_pending ON annual_discount(pending_quotation_id)
    WHERE pending_quotation_id IS NOT NULL;   -- 对齐 V349 给 7 张表建的那批
```

> 📌 `discount_order` 保持现有 `NOT NULL`（规则四已定三类统一必填）；唯一键仍写 `COALESCE(discount_order, 0)` 纯粹为与 `uq_unit_price` 表达式口径对齐，属防御性写法，不代表该列可空。

#### 规则二：`target_no` 的语义（方案 A · 泛化目标列）

| `discount_type` | `target_no` 存什么 | 示例 |
|---|---|---|
| `INCOMING_MATERIAL` | 材质料号（Excel「投入料号」原样，不 resolve 不铸号） | `AgNi11#-Ⅰ` |
| `ASSEMBLY_PROCESS` | **解析后的真工序编号**（非 Excel 原文，允许为空） | `Z100` |
| `FINISHED` | 恒 `NULL`（整单级年降无挂载目标） | `NULL` |

**名称一律不存**，由视图 JOIN 主数据取（材质名走 `material_recipe`，工序名走 `process_master`）。与现有「名走 `material_recipe` 兜底」惯例一致，避免主数据改名后年降表变陈旧。

> 📌 **为什么用单一泛化列而不是各类一个专用列**：一个视图即可统一取三类年降（业务上年降本来就是一件事）；与 `unit_price.code` 按 `price_type` 变语义的现有惯例一致；加第四种年降只需加枚举值，不动 DDL。代价是 `target_no` 的语义需要配合 `discount_type` 读 —— 已在本文与落库方案文档中固化。

#### 规则三：版本化语义

```
groupKey  = (system_type, customer_no, discount_type, material_no, target_no)
content   = (discount_order, discount_ratio, fixed_discount_value,
             currency, unit, discount_times, seq_no)
versionTriggerColumns = null      -- 任何内容变化即升版，与 Q08/Q15 现状一致
版本列    = version_no（VARCHAR 存数字，首版 "2000"，升版 max+1）
```

⚠️ **「年降系数」的写入语义发生变更**：从行级 upsert（空值不覆盖）改为**组级整组替换**（本次导入的行集即当前状态，留空即为空）。这是三者归一的必然代价，需求方已确认采纳（§10 Q3）。

#### 规则四：年降顺序三类统一必填

`discount_order` 是组内**唯一的行区分维度**，为空则同组多行会撞唯一键。

- 现状：只有 Q19 强制非空（`Q19AnnualDiscountHandler:38-41`），Q08 / Q15 允许为空 —— 属遗漏。
- 改动后：三类统一在 **Phase 1** 校验，为空 → `recordError` → 整单拦截。
- 错误信息须明确指出行号与列名。

#### 规则五：Handler 结构 —— 保留三个，写入逻辑抽共享

保留 `Q08` / `Q15` / `Q19` 三个 `SheetHandler`（编排器按 `sheetName()` 一对一分发），各自退化为"声明差异"；共同的读列、groupKey 组装、写入器调用抽到新的 `AnnualDiscountWriter`。

| Handler | `discount_type` | `target_no` 来源 | Phase 1 必填校验 |
|---|---|---|---|
| Q08 来料年降 | `INCOMING_MATERIAL` | `row.exact("投入料号")` | 投入料号、年降顺序 |
| Q15 组装加工费年降 | `ASSEMBLY_PROCESS` | `ctx.sharedCache["assemblyProcessNo"]` 解析结果 | 年降顺序（工序仍可空） |
| Q19 年降系数 | `FINISHED` | 恒 `NULL` | 销售料号、年降顺序 |

**共享读取器可以一套 key 吃三个 Sheet** —— `SheetRow.getStr` 是 `contains` 匹配，表头差异不需要按 Sheet 分支：

| 字段 | 读取 key | 命中的实际表头 |
|---|---|---|
| `discount_ratio` | `getDecimal("年降系数")` | `年降系数（%）` / `年降系数（%/年）` |
| `fixed_discount_value` | `getDecimal("单次固定年降")` | `单次固定年降值` / `单次固定年降金额` |
| `material_no` | `getStr("销售料号","宏丰料号","成品料号")` | 三 Sheet 均为 `销售料号`（兼容旧模板） |
| `discount_order` / `seq_no` / `discount_times` / `currency` / `unit` | `年降顺序` / `项次` / `降价次数` / `货币` / `计价单位` | 三 Sheet 同名 |

#### 规则六：退役的代码与数据

- `AnnualDiscountRepository`（`upsertOne` / `upsertBatch` / `accDiscount`）**整体删除** —— Q19 改走 `VersionedV6Writer` 后无任何调用方。
- `AnnualDiscountBatchUpsertEquivTest`（上述方法的等价护栏测试）**一并删除**。
- `AnnualDiscount` entity 按新 schema 更新：加 `systemType` / `customerNo` / `targetNo` / `seqNo` / 版本列，删 `discountStrategy` / `discountBase`，`bizType` → `discountType`。
- `unit_price` 中 `price_type IN ('INCOMING_MATERIAL_REDUCTION','COMPONENT_REDUCTION')` 的存量（当前 1 行）在迁移中清除。

### 4.4 ⚠️ 登记点清单（7 处，漏一处静默失效）

`annual_discount` 进入「版本化 + pending」体系后必须登记的位置。**除第 1 项外，漏登记都不会报编译错，只在某条路径上静默失效** —— 这是本次改造真正的风险点。

| # | 登记点 | 漏了会怎样 |
|---|---|---|
| 1 | `VersionedV6Writer.ALLOWED_TABLES` | 写入器抛「表未登记白名单」（唯一会吵的一处） |
| 2 | `VersionedV6Writer.SYSTEM_TYPE_SCOPED` | 护栏失效；将来核价侧接入时跨 QUOTE/PRICING 污染版本号 |
| 3 | `QuotePendingRewriter.WHITELIST_TABLES` | SQL 视图读年降表时 **pending 行完全不可见**，且拿不到 `__v6_id` 锚点 → 该页签无法回填 |
| 4 | `QuoteTableAxis` 新增 `Spec` + 进 `ALL_MANAGED_TABLES` / `SCAN_TABLES` | B5 回填与 pending 转正均由它驱动 → **pending 行永远转不了正** |
| 5 | `V6QuotationCommitService.PENDING_TABLES` | 导入记录 → 报价单的 pending 过户漏这张表 → 行成孤儿 |
| 6 | `QuoteImportService.PENDING_TABLES`（`clearPreviousPending` 用，与 #5 同源但各自一份字面量） | 重导时上一次 pending 残留不清 → 行数翻倍 |
| 7 | `QuotationService.cleanupPendingV6Data` | 删报价单时年降 pending 行残留 |

`QuoteTableAxis.Spec` 登记内容：

```java
new Spec("annual_discount", "version_no",
    List.of("system_type", "customer_no", "discount_type", "material_no", "target_no"),  // axis
    List.of("discount_order", "discount_ratio", "fixed_discount_value",
            "currency", "unit", "discount_times", "seq_no"),                              // content
    null);   // 非主从表
```

## 9. 依赖与风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| **7 个登记点漏登记** | 静默失效（pending 不可见 / 转不了正 / 残留孤儿 / 行数翻倍） | 实现计划中逐点列为独立任务与独立验收项（AC-8~AC-11、AC-15），每项配可执行断言 |
| 「年降系数」写入语义变更 | 若业务真依赖"分多次导入、每次只填部分列"，整组替换会清掉未填列 | 需求方已确认采纳（§10 Q3）；落库方案文档同步说明 |
| 「年降顺序」改必填 | 若真实模板存在空值行会被拒导 | 当前存量 1 行且 `discount_order=1`，风险极低；错误信息须明确指出行号与列名 |
| 共享 Flyway 历史并发 | 迁移编号被其它会话抢占 → 启动 validate 失败 | 动手时重查 `flyway_schema_history` 最大值；不改已应用迁移的号与名 |
| 窗口期收窄 | 一旦客户模板开始配年降页签，改造成本成倍上升 | 本轮迭代内完成 |

**依赖**：无外部依赖。`ProcessNoResolver`（repair-0727 已交付）保持原样复用。
