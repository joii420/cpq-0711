## 2. 需求背景与目标 ⭐

### 2.1 现象（需求方原述）

基于 task-0721 交付，报价侧已可树状展示。在 **BOM 树页签**中，当存在**相同行键的重复行**、需要删除其中一条时：

| # | 现象 | 严重度 |
|---|------|--------|
| **①** | 点删除后提示"已删除该行"，但**页面不实时消失**，必须点「刷新基础数据」按钮才看到效果 | 中（体验 / 信任） |
| **②** | 点「刷新基础数据」后，**两条重复键的行一起被删除**（只想删一条） | 高（数据误删） |
| **③** | 两条重复行都被删掉之后，**提交审批仍报"行键重复，无法提交"** | **P0 阻断**（无自救路径） |

### 2.2 本次要达成的目标

1. 树页签删除一行后**当帧即消失**，不依赖「刷新基础数据」。
2. 重复行**删一条只删一条**，另一条保留（行身份可区分）。
3. 删除后**提交校验与页面所见一致**：页面上不存在的行不参与行键重复判定，不再出现"页面已删干净但提交仍被拦"的死局。
4. 存量已被"连删"的报价单有明确补救口径（见 §6.2）。

### 2.3 不做什么（明确边界，待 §12 裁决后收敛）

- **不改核价侧删除 / 渲染行为**（共用引擎，须零回归）。
- **不做编辑期实时行键预检红点**（那是 `BL-0001` 第二期增强，非本次）。
- **不动 task-0721 已定的树渲染方案 A（物化侧接树）与页签类型属性**。
- **不做墓碑的通用"回收站 / 撤销"UI**（现有"清空墓碑"端点即可满足补救）。

## 4. 功能详述 ⭐

### 4.1 用户场景 / 操作流程（期望态）

1. 销售打开报价单编辑页 → 报价侧 → 某 `tab_type=BOM` 树页签，树上存在两条行键相同的行（同料号在树上出现两次 / 同节点下两条明细）。
2. 在**其中一条**行上点 `×` → 删除确认抽屉列出影响面 → 确认。
3. **期望**：该行**立即从树上消失**（无需刷新），另一条同键行**原样保留**；页签小计 / 公式列随之重算。
4. 用户提交审批 → **期望**：不再因这两行报"行键重复"（页面上已不存在的行不参与判定）。
5. 若树上仍有**真实的、页面可见的**重复行键 → 提交仍应拦截，且「定位」能跳到那两行（现有 `RowKeyConflictDrawer` 行为不变）。

### 4.2 界面与交互（前端相关）

| 交互点 | 现状 | 期望 |
|---|---|---|
| 树页签行 `×` 删除 | 提示"已删除该行"，但行仍在，须点「刷新基础数据」 | 确认后当帧消失（与非树页签 `delete-driver-row` 一致的"服务端权威投影原子重灌"体验） |
| 删除确认抽屉影响面 | 已列出 ①树节点 ②级联页签行 ③保留料号 | 不变；若身份口径调整，抽屉需能区分"同料号的哪一次 occurrence" |
| 「刷新基础数据」按钮 | 现被迫兼任"让删除生效"的补救手段 | 回归本职（拉最新已审核基础数据），不再用于修复删除不生效 |
| 提交失败抽屉 | 列出行键重复明细 + 定位 | 不变；但列出的行必须是**页面上真实可见**的行 |

### 4.3 业务规则与计算逻辑（后端相关）

本次的核心是**统一"一行的身份"口径**。当前同一条树行在系统内有 **4 套身份**，互不等价（详见 §11）：

| 身份 | 计算方式 | 使用场景 | 对重复行是否可区分 |
|---|---|---|---|
| `__effKey` | 行键字段组合 → 撞键加 `#序号` 唯一化 | 渲染 / editRows / formulaResults 键 | ✅ 可区分（`#0`/`#1`） |
| `fp`（内容指纹） | `driverRow` 全字段规范化拼接 | **删除墓碑匹配**（`keepMask`） | ❌ **不可区分**（内容相同即同 fp） |
| `rowKey` | 行键字段组合（**不消歧**） | **提交期行键重复校验** | ❌ 不可区分（判重恰恰依赖它相同） |
| `__nodeId` | BOM 递归 spine 路径 id | 树结构 / 剪枝 / 级联 | ✅ 可区分（结构路径唯一） |

**待裁决的规则口径（§12 Q1 / Q2）**：树页签的行身份是否统一收敛到 `__nodeId (+ 节点内行序)`，以及提交期行键校验对树页签的语义。

### 4.4 数据字段

本次**预计不新增业务字段**；可能涉及的存储结构调整（视 §12 裁决）：

| 字段 | 位置 | 含义 | 是否新增 | 备注 |
|------|------|------|---------|------|
| `deleted_row_keys[].effKey` | `quotation_line_component_data` (jsonb) | 墓碑的键身份 | 存量 | 现仍写入但**匹配时不使用**（2026-07-14 改 fp 单键后成僵尸字段） |
| `deleted_row_keys[].fp` | 同上 | 墓碑的内容指纹 | 存量 | 当前唯一匹配键 → 症状 ② 根源 |
| `deleted_row_keys[].nodeId`（候选） | 同上 | 树行的结构身份 | **可能新增** | 若采纳 Q1(a)，须向后兼容读旧墓碑 |
| `deleted_tree_nodes` | `quotation_line_item` | 剪枝节点墓碑 | 存量 | PRUNE 模式用，本次不改语义 |

## 8. 验收标准 ⭐

> 全部基于「同一 BOM 树页签内存在两条行键相同的行」这一前提数据。

1. **AC-1（症状①）**：在树页签删除其中一条行并确认后，**不点任何刷新按钮**，该行在当前页面即刻消失；页签行数 −1，小计随之重算。
2. **AC-2（症状②）**：AC-1 之后，**另一条同键行仍在**，其各列取值逐字段与删除前一致（无串行、无位移）。
3. **AC-3（症状③）**：AC-1 / AC-2 之后点「提交审批」，**不再**因这两行报"行键重复"；提交成功（若单据其他部分合规）。
4. **AC-4（真重复仍须拦截）**：若页面上确实仍有两条可见的重复行键（未删除），提交仍被拦截，`RowKeyConflictDrawer` 列出的行号可「定位」到那两行。
5. **AC-5（刷新幂等）**：AC-1 后再点「刷新基础数据」并整页重载，删除结果保持（被删的不复活、保留的不消失）；连续刷新 3 次行数稳定（AP-51 行数纪律）。
6. **AC-6（剪枝不回归）**：PRUNE 剪枝 + 跨页签级联删除行为与 task-0721 交付一致（`retainedParts` 仍按"树上无剩余 occurrence 才删"）。
7. **AC-7（核价侧零回归）**：核价侧树渲染 / 删除 / 小计逐字节不变（共用引擎隔离，spec §3.7）。
8. **AC-8（非树页签零回归）**：非树页签 `delete-driver-row` 行为不回归；E2E `quotation-flow.spec.ts` 通过，`'加载中' final count = 0`。
9. **AC-9（存量兼容）**：改动前写入的历史墓碑仍能正确过滤对应行（不出现"老单据行全回来"或"老单据多删行"）。

## 11. 根因勘察（技术总监，2026-07-26，代码级证据链）

> 证据等级：以下 ①②③ 的调用链与代码位置**均已逐行核对源码**；标注「待运行时确认」处尚未在真实单据上复现验证。

### 11.0 一句话总结

**同一条树行在系统里有 4 套互不等价的"身份"**（`__effKey` / `fp` / `rowKey` / `__nodeId`）。
删除按 `fp`（内容指纹）匹配、渲染按 `__effKey`、提交校验按 `rowKey`、树结构按 `__nodeId`。
重复行的内容与行键都相同、**只有 `__nodeId` 不同** —— 而 `__nodeId` 恰恰是删除与校验**都没用上**的那一个。

### 11.1 症状①：删除后不实时消失 —— ✅ **实机确认，且比初判更严重**

> **2026-07-26 实机复现**（管理员会话直调 API，报价单 QT-20260726-0006 / lineItem `dfee1e78`，复现后已复位）。

**实测 1：响应契约确实缺投影**

```
POST /api/cpq/quotations/{qid}/line-items/{lid}/tree/delete  → 200
响应字段 = ['deletedNodeIds', 'cascadeDeletedRowKeys', 'quoteCardValues']   ← 无 componentData
```

前端因此拿不到新墓碑，渲染不变 —— 症状 ① 成立。

**实测 2（新发现 ①-b，初判未覆盖）：树删除不重新物化 `row_data`，且「刷新基础数据」也不补**

| 步骤 | `snapshot_rows` | `row_data` | `deleted_row_keys` |
|---|---|---|---|
| 删除前 | 6 | 5 | 1 |
| ROW 删除后 | 6 | **5（未变，第 5 行仍是被删的 AgNi）** | 2 |
| 再调 `refresh-card-snapshot` | 6 | **5（仍未变）** | 2 |

对照：非树的 `delete-driver-row` 走 `CardSnapshotService.refreshQuoteProjection`，其职责明确包含
**「② 物化 row_data（同墓碑 → N-1，与前端展开同序，两存储恢复对齐）」**；
树端点只调了 `snapshotQuoteSideOnly`（仅重算 `quoteCardValues`），**漏了物化那一步**。

⇒ 后果：渲染按「baseRows 6 − 墓碑 2 = 4 行」显示，而 `row_data` 仍 5 行 → **两存储行数错位**。
这正是 AP-54 / 2026-07-14「删错行、值串行、反复删把 row_data 搅坏」的同一成因。**改动 A 必须连这一步一起补**。

链路（前 → 后 → 前）：

1. `BomTreeDeleteConfirmDrawer.tsx:88-90` — 执行删除后**只取 `data.quoteCardValues`** 回灌。
2. `QuotationStep2.tsx:1768-1771` — `applyTreeQuoteCardValues` **只 patch `item.quoteCardValues`**，不动 `componentData`。
3. 后端 `QuotationTreeService.executeDelete:461-471`（mode=ROW）**只写行墓碑**到
   `quotation_line_component_data.deleted_row_keys`，**不改 `snapshot_rows`**；随后 `:496` 调
   `snapshotQuoteSideOnly` 重算 `quoteCardValues`，`:498-502` 的响应体**没有 `componentData` 投影**。
4. `CardSnapshotService.buildTabNode:1731` — `tabNode.set("baseRows", baseRows)`，这里的 `baseRows`
   **未按行墓碑过滤**（行墓碑只作用于 `buildResolvedRows` / `formulaResults`，见 `:1806-1815`）；
   只有**剪枝**墓碑 `deleted_tree_nodes` 会在 `:1108 filterPrunedTreeRows` 真正剔除 baseRows。
5. 前端渲染行数来自 `QuotationStep2.buildSnapshotExpansions:1483-1496`：
   `baseRows`（来自 quoteCardValues）**×** `comp.deletedRowKeys`（来自 `componentData`）→ `keepRow` 过滤。

**结论**：删除只更新了乘式的**一个因子**（quoteCardValues，且其 baseRows 按设计不过滤），另一因子
`componentData[].deletedRowKeys` **仍是旧值** → 前端过滤器手上没有新墓碑 → 行照旧渲染。
点「刷新基础数据」→ `refreshCardSnapshot` + 整页 `getById` → `enrichComponentData.ts:200-203`
透传 `saved.deletedRowKeys` → 墓碑到位 → 行才消失。

**对照组（证明是契约缺口而非玄学）**：非树页签走 `handleDeleteDriverRow`（`QuotationStep2.tsx:1715-1736`）
→ `delete-driver-row` 端点返回 **`componentData[{rowData, deletedRowKeys, …}]` 权威投影**
（`CardSnapshotService:2366-2375`）→ `applyQuoteProjection:1685-1705` **原子重灌两个存储** → 当帧消失。
**树删除端点缺的正是这块投影。**

> 📌 推论（待运行时确认）：**PRUNE 模式应当是即时生效的**（剪枝走 `deleted_tree_nodes`，后端 baseRows 已剔除），
> 失效的只有 **ROW 模式**。可作为定位验证的对照实验。

### 11.2 症状②：两条重复行被一起删除 —— ⚠️ **初版根因已被真实数据证伪，机制待确认**

> **2026-07-26 技术总监实机核验（`cpq_db_0724`，用户当晚复现单 QT-20260726-0006 / lineItem `dfee1e78`）。**
> 初版判断"两条重复行 fp 相同 → keepMask 连删"**在该数据上不成立**，如实记录如下。

**实测事实**：

| 检查项 | 实测结果 |
|---|---|
| 树页签 `BOM` 快照行 | 6 行；其中 **row4** = 料号 `992`(AgNi11#-Ⅰ) 挂 `S-3120014539`，**row5** = 同料号 `992` 挂 `S-80011`（DAG 重复子件） |
| 两行 `driverRow` 是否同内容 | **否**。`driverRow` 内含 `parent_no` 列，两行分别为 `S-3120014539` / `S-80011` → md5 不同 |
| 墓碑 | 仅 1 条：`fp="∅∅∅AgNi11#-Ⅰ∅∅∅∅992S-3120014539"`, `effKey="S-3120014539/992::4"` |
| fp 手工验算 | 该 fp **仅匹配 row4**（row5 的 fp 尾段是 `992S-80011`，不同） |
| 后端物化结果 `row_data` | **5 行**（主料1 / 投入零件1 / 组成件1 / H65 / **AgNi11#-Ⅰ**）→ **只删掉一条，另一条 AgNi 仍在** |
| 前端过滤仿真（按 `deletedRows.ts` 算法 + 真实 `rowKeyFields=["料件"]` 跑真实 baseRows） | row4 ❌ 过滤、**row5 ✅ 保留** —— 前端也只删一行 |

**结论**：在这份数据上，前后端**都只删了一行**。症状 ② 的机制**尚未确认**，待需求方补充复现细节（§12.2）。

**仍然成立的部分**：`keepMask` 按 fp 单键匹配是**偶然**靠 `driverRow` 里恰好有 `parent_no` 列才区分开两个 occurrence 的。
若某树页签的 driver 视图**不输出父件列**，两个 occurrence 的 `driverRow` 即完全同内容 → fp 相同 → **连删必然发生**。
故 Q1「墓碑加 `nodeId` 维度」的裁决依然正确且必要：把行身份从"碰巧不同的内容"换成"结构上唯一的路径"。

### 11.2-旧 初版分析（保留追溯，结论已被上表修正）

- `DeletedRowKeys.keepMask:114-124` — 自 2026-07-14「删错行 Phase 1」起，墓碑匹配改为
  **`fp` 内容指纹单键**，`effKey` 形参**保留但不参与匹配**（当时真根因是前后端 effKey 口径不一致）。
- `DeletedRowKeys.rowFingerprint:79-95` — fp **只取 `driverRow`**（行键字段按序 + 全字段升序拼接）。
- 树的结构身份系统列 `__nodeId / __parentId / __lvl / __hfPartNo` 由 `BomTreeRenderService` 写在
  **snapshot row 顶层**，**不在 `driverRow` 内**（见 `QuotationTreeService:600-604`、
  `buildSnapshotExpansions:1513` 的 `br.__nodeId` 取法）。
- ⇒ 同一料号的两次 occurrence，`driverRow` 逐字节相同 → **fp 相同** → `keepMask` 一次删两行。

**这不是意外，是被记录在案的已知边界**：`DeletedRowKeys.java:106-107` 原文
「字节级完全重复的两行 fp 相同 → 删一个会连删（此场景身份本就不可区分；Phase 2 的 uniqFp 若引入 #序号再细分）」，
对应 `BL-0055`。当时判定"重复行的唯一来源是 `element_bom_item` 双重登记（脏数据），修数据即可绕过"——
**task-0721 报价侧接树后该前提失效**：BOM 树上同一料号挂多个父是**合法结构**，重复行成为常态。

**同源附带缺陷（本次一并暴露）**：`QuotationTreeService.computeRowFpForNode:537-546` 按 `__nodeId`
找**第一条**匹配行取 fp。同一节点下有多条业务行时，删第 2 行会算出第 1 行的 fp → **删错行**。

### 11.3 症状③：都删了仍报行键重复（P0 阻断）—— ✅ **实机确认，与现象描述逐字吻合**

> **实测**：把两条 AgNi 行都写入墓碑（页面上均已不显示）后调 `POST /api/cpq/quotations/{id}/submit`：

```
HTTP 422
{"code":422,"message":"行键重复，无法提交：\n· 组件「656c9b87…」行键 [AgNi11#-Ⅰ] 在第 5,6 行重复",
 "data":{"conflicts":[{"rowKey":"AgNi11#-Ⅰ","rowIndices":[5,6],…}]}}
```

第 5 / 6 行（1 基）正是 `snapshot_rows` 里那**两条已被墓碑标记删除**的行。
校验器读全集、不消费墓碑 —— **用户在 UI 上已无任何操作可以解除**，P0 阻断成立。

**同时暴露**：这两行的 `rowKeyFields = ["料件"]`，值都是 `AgNi11#-Ⅰ` → 树上同料号两 occurrence
**天然撞键**。故仅"让校验消费墓碑"不足以闭环：用户若不删任何一行、正常报价，照样提交不了 ——
必须同时落 Q2 裁决（树页签按 `__nodeId` 判重）。



- `QuotationService.submitForApproval:719-745` 构造校验输入：
  `CompRows(cd.componentId, cd.snapshotRows, cd.rowData)` —— **只喂 `snapshot_rows` 和 `row_data`**。
- `RowKeyUniquenessService.collectConflicts:52-77` 直接遍历 `snapshotRows` 逐行算 `computeDedupKey`，
  **全程不读 `deleted_row_keys`，也不读 `deleted_tree_nodes`**。
- 而删除是**墓碑软删**（`snapshot_rows` 一行不少）⇒ 校验器看到的永远是**完整集** ⇒ 重复键恒在
  ⇒ 提交永远被拦，**且 UI 上无任何操作可以解除**（用户已经把两行都删了）。

**二级问题（设计层，需产品裁决）**：即便接上墓碑，BOM 树里同一料号挂两个父**本就合法**，其
`rowKey`（行键字段组合，`RowKeyConflictDetector` 不做 `#序号` 消歧）必然相同 ⇒ 平铺表的
「组件内行键不可重复」硬约束与树语义**天然冲突**。这正是 `BL-0004` 记录的
"渲染侧已 `#序号` 消歧、提交侧未消歧"的设计不对称，状态 **BLOCKED（待产品确认）**。

### 11.4 三症状的因果链

```
task-0721 报价侧接 BOM 树
   └→ 树上同料号多 occurrence 成为常态（DAG 重复子件是核心场景）
        ├→ 行内容(driverRow)完全相同 ─→ fp 不可区分 ─→ ② 删一连删（BL-0055 残留被激活）

        └→ 树删除端点响应契约缺 componentData 投影 ─→ ① 前端两存储不同步，须整页重载
```
