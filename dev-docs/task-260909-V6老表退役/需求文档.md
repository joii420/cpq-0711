### 为什么现在能做

**`_record` 机制已就位并接管**（`task-260907` 第二段）：

- `DatasetQuotationCommitService:40` 类注释：「**不做 pending 过户**：`ds_quote_*` **29 张表无一张有 `pending_quotation_id` 列**」——新体系**设计上就不要 pending 这个概念**

## ③ 🚦 开工前置（未闭合则不许进闸门 A）

### P-1 · 09-08 那 12 行 pending 的来源必须查清

**这是 `D-1` 成立与否的唯一悬念，也是 `D-3` 的前提。**

预实验的结构性证明是：pending 非空只有一个源头 `QuoteImportService:97`，而该类不可达（唯一注入点 `BasicDataImportV6Resource:60` **0 处调用**，两个 POST 恒返 410 —— 已实证 `HTTP 410`）。

**但实证撞出一个反例**：410 于 **2026-09-07 06:30** 上线，而 `annual_discount` 有 **12 行 pending 创建于 2026-09-08 01:10:53**。

已查明的形状（全部实测）：

```
12 行同一时刻同一事务 · created_by / updated_by 全 NULL · 全部 is_current = false
料号 S0001 / S0004（夹具形态） · customer_no = CUST-0001
pending_quotation_id = 0c448bad-…  既不是 quotation 也不是 import_record
那一刻：0 张报价单 · 0 个导入批次 · 0 行其它 V6 表   ← 无任何业务伴生对象
```

⇒ 形状上**几乎肯定**是测试或脚本直写（测试确实会 `new ImportContext()` 直调 `handler.handle(...)`，完全绕过 410）。
🚫 **但当前 master 里找不到能产生它的测试** —— 没有任何测试同时用 `S0001/S0004` 与 `annual_discount`。产生它的代码可能在某个分支/worktree 上。

**🚫 说不出它是谁写的，就不能宣告「没有任何路径会产生 pending」。** 查清前不许进闸门 A。

**建议查法**：扫全部 worktree 分支的 test 树；查 `annual_discount` 该时刻前后的 PG 日志；比对各 worktree 的 `AnnualDiscountWriterTest` 变体。

### P-2 · 预实验中「建单臂」是空验证，需重做或显式作废

已跑 3 轮真机建单（1 次幂等复用 + 2 次真新建），pending 计数与指纹全未变。
🚫 **但这不能当证据**：三次建单**对 10 张表的全表行数增量全部为 0**，建出的单 **0 明细行**（根因：所选批次 `batchParts = 0`，全库无一批次带 `batchParts`）。

### 批次 1 · 退役 3 个 `v_compat_*` 兼容视图

**必须先改写下游**（否则 `DROP VIEW` 会级联失败或打挂 composite 视图）：

| 改写对象 | 现状 |

- BOM 侧 **10 行 / 2 行**换成新表版本，**58 行**因 `cust_scope` 解禁

✅ **实测逐值等价**（不只是行数相同）：3 个 `production_no` 中唯一能桥的 `3120014539` 两侧都得 `S-3120014539`；`300013`/`300015` 两侧都桥不到。

🚨 **`CostAllVersionViewSelfCheck` 在 `@Observes StartupEvent` 里双向比对视图与主表列集，多一列即 `IllegalStateException` 应用起不来。** 改视图**必须与守卫同批提交**（`repair-260909` 的原样教训）。
