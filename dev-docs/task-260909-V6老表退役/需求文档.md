## ③ 🚦 开工前置（未闭合则不许进闸门 A）

### P-1 · 09-08 那 12 行 pending 的来源 —— ✅ **已闭合（2026-09-09）**

**这是 `D-1` 成立与否的唯一悬念，也是 `D-3` 的前提。**

预实验的结构性证明是：pending 非空只有一个源头 `QuoteImportService:97`，而该类不可达（唯一注入点 `BasicDataImportV6Resource:60` **0 处调用**，两个 POST 恒返 410 —— 已实证 `HTTP 410`）。

**但实证撞出一个反例**：410 于 **2026-09-07 06:30** 上线，而 `annual_discount` 有 **12 行 pending 创建于 2026-09-08 01:10:53**。

已查明的形状（全部实测）：

```
12 行同一时刻同一事务 · created_by / updated_by 全 NULL · 全部 is_current = false
料号 S0001 / S0004（夹具形态） · customer_no = CUST-0001
pending_quotation_id = 0c448bad-…  既不是 quotation 也不是 import_record
那一刻：0 张报价单 · 0 个导入批次 · 0 行其它 V6 表   ← 无任何业务伴生对象
```

⇒ 形状上**几乎肯定**是测试或脚本直写（测试确实会 `new ImportContext()` 直调 `handler.handle(...)`，完全绕过 410）。
🚫 **但当前 master 里找不到能产生它的测试** —— 没有任何测试同时用 `S0001/S0004` 与 `annual_discount`。产生它的代码可能在某个分支/worktree 上。

**🚫 说不出它是谁写的，就不能宣告「没有任何路径会产生 pending」** —— 这条判据促成了下面的调查。

#### ✅ 调查结论：**这 12 行不可能来自生产路径**

决定性依据是**生产路径对 `pending_quotation_id` 取值的结构约束**：

```java
// QuoteImportService.java:86-97
public void processImport(UUID recordId, String customerNo, ...) {
    ctx.importRecordId    = recordId;
    ctx.pendingQuotationId = recordId;   // ← pending 归属 key = import_record.id
```

⇒ **生产路径下，任一 pending 行的 `pending_quotation_id` 必然是 `import_record.id`（建单前）或
`quotation.id`（`repointPendingOwnership` 过户后），二者必居其一。**

而那 12 行的 `0c448bad-dac8-442f-87f0-7035cf5fb1ae` **两边都不是**（实测）：

| 查询 | 结果 |
|---|---|
| `SELECT count(*) FROM import_record WHERE id='0c448bad-…'` | **0** |
| `SELECT count(*) FROM quotation WHERE id='0c448bad-…'` | **0** |
| 反向证明：`SELECT count(*) FROM import_record` | **50**（表非空，查得着，不是空表假阴性） |

**生产路径在结构上造不出这样的值。** 配合三条同向证据：
① `created_by` 为 NULL（生产路径必写 `importedBy`）
② 那一刻 0 张报价单 / 0 个导入批次 / 0 行其它 V6 表 —— **无任何业务伴生对象**
③ 走的是 `VersionedV6Writer:325-327` 的 **pending 分支且是首版**（`mx == null → "2000"`）

⇒ **结论：进程内直调（测试或脚本）写入，非业务路径。**

⚠️ **仍未点出具体产出方**：各分支 test 树全搜过，无 `S0001` 与 `annual_discount` 共现者；
`QuoteImportAcTestBase`（用 `CUST-0001`）走 RestAssured / HTTP，而 V6 导入端点恒返 410，走不通。
**但 P-1 要证的不是「是谁写的」，而是「新单会不会产生」** —— 这一问已被上述结构约束答死。

#### 📌 调查中的两次自我更正（写下来避免下一个人重走）

1. **「`version_no='2000'` 是测试夹具标记」—— 错。** 它在 3 个**生产**文件里（`VersionedV6Writer` /
   `CostingVersionService` / `QuoteBackfillPreviewService`），且 `unit_price` 有 **100 行**是该版本。
   真相：`VersionedV6Writer:12` 注释「版本列为 VARCHAR 存数字字符串，**起始 `"2000"`**」——
   它是**默认起始版本号**，不是指纹。差一点把一个普通默认值当成测试证据写进立项文档。
2. **「`QuoteImportAcTestBase` 是产出方」—— 错。** 它用 RestAssured 打 HTTP，而目标端点 410。

两次都是「形状像就下结论」，都由下一步查证推翻。

### P-2 · 预实验中「建单臂」是空验证，需重做或显式作废

已跑 3 轮真机建单（1 次幂等复用 + 2 次真新建），pending 计数与指纹全未变。
🚫 **但这不能当证据**：三次建单**对 10 张表的全表行数增量全部为 0**，建出的单 **0 明细行**（根因：所选批次 `batchParts = 0`，全库无一批次带 `batchParts`）。
**什么都没写，「pending 没变」当然成立。**

#### ⛔ 裁决：**显式作废该臂（2026-09-09 用户裁定）**，不重做

**理由（写清楚，不是省事）**：pending 行由**导入**创建、**非建单**创建 ——
`QuoteImportService:97` 是唯一赋值点，建单侧的 `repointPendingOwnership` 只做**过户**
（`UPDATE … WHERE pending_quotation_id = :importRecordId`），不创建。

⇒ 建单臂即使做实，验的也只是**过户**路径；而过户路径已有**独立且更强的证据**：

> 实测：`material_master` / `annual_discount` / `unit_price` / `material_customer_map` 四张表中，
> **挂在「存在的 `import_record`」上的 pending 行数全部为 0** ⇒ `repointPendingOwnership` 当前**命中面为 0**。

造一个带 `batchParts` 的真批次成本远大于它能新增的信息量。
🚫 **本条作废是有条件的**：若 `AC-11`（序列 AC，走完整建单→提交→核价通过）在开工后**发现 pending 计数变化**，
本裁决立即失效，须回来重做该臂并重新评估 `D-1`。
