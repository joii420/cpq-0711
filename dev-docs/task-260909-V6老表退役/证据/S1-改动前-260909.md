## T-14.1 · `AC-14` 改动前：所有「命中 0」断言的量具阳性对照

`AC-14` 要求每个 0 值断言旁附一条**同 pattern 对已知存在对象的命中记录**。逐条落实：

| 待验的 0 值断言 | 同 pattern 的阳性对照 | 实测阳性结果 | 判定 |
|---|---|---|---|
| `AC-2`：`pg_class WHERE relname LIKE 'v_compat_%'` = 0 | 同一查询换 `LIKE 'v_composite_child_%'` / `'v_ds_cost_%'` | **3** / **26** | ✅ 量具够得着 |
| `AC-4`：`sql_template ~* 'v_compat_'` = 0 | 同一谓词打在拼了探针的同列上：`(sql_template \|\| ' v_compat_probe') ~* 'v_compat_'` | **2**（两行都命中） | ✅ 谓词能读到该列 |
| `AC-4`：`sql_template ~* 'FROM\s+material_bom_item'` = 0 | 同上加探针 | **2** | ✅ |
| `AC-9`：3 文件老表名命中 = 0 | 同 pattern 打在已知含老表名的迁移文件上 | `V255`/`V410`/`V234` 等均命中 | ✅ `grep -a` 够得着 |
| `AC-9`：3 文件 `ds_quote_\|ds_cost_` 命中 ≥ 1 | 同 pattern 打在 `V410__task260903_compat_views.sql` | **19 行命中** | ✅ |


### Q-1 🚨 `AC-9` 对 `Q05ElementRecoveryHandler.java:90` 可能自相矛盾

该行文案原文（commit `14f80f40`）：

```java
String.format("未匹配 element_bom_item (material_no=%s, material_part_no=%s, component_no=%s) - 请先导入物料与元素BOM",
```

- 它是**诊断型**：告诉用户「我去 `element_bom_item` 里按这三个键找，没找着」。
- 而本任务**不改 Q05 的写入目标** —— 同文件 `:94` 仍是 `result.recordWrite("element_bom_item", updated)`，
  批次 3 只把 **pending 写点**改 no-op，导入仍写老表。
- ⇒ 若按 `AC-9` 把这句里的 `element_bom_item` 换成 `ds_quote_element_bom`，
  **这条诊断就会指向一张 handler 从未查过的表**，比不改更误导。

📌 与另两处的性质不同：`SqlViewValidator` / `BnfPathLinter` 是**祈使型**（「请改用 X」），
把 X 换成 `ds_` 是对的；Q05 是**陈述型**（「我在 Y 里没找到」），Y 必须是它真的查过的那张表。

**请主线裁决**（三选一，我不替选）：
- (a) Q05 这处**移出 `AC-9` 范围**，本期不改，AC-9 降为 2 处；
- (b) 改成同时点出两张表（如「未匹配 `element_bom_item`（该表将随 V6 退役，新单请走 `ds_quote_element_bom`）」）
  —— 但那样 `AC-9` 的「老表名命中 0」这半条断言不成立，AC 原文要改；
- (c) 连同 Q05 的写入目标一起换表 —— **那是范围扩大**，超出本任务边界（立项文档 §② 未含）。
