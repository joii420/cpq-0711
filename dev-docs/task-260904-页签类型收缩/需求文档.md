## ① 背景与目标

### 1.1 现状

组件有一个「页签类型」属性（`component.tab_type`），值域 6 类：**主件 / 材质元素 / 零件 / 外购件 / 费用类 / BOM 树**。用户在取数配置器里配组件时必须选一项。

它由 `task-0721` 引入，初始动机单一：**报价单 BOM 树上手工加叶子时，判定这个料号该算材质、零件还是外购件**。落地后又长出四个下游契约（见 §4.2）。

### 1.2 问题

**这个选择在取数层面是冗余的。** 实证根源——同一个锚点节点被多个页签声明共用：

| 锚点节点 | 被几个 `semantic_tab_view` 共用 | 页签类型 | 是否重复读法 |
|---|---|---|---|
| `MATERIAL_BOM` | **9**（3 方言 × 3 类） | BOM 树 / 零件 / 外购件 | 🚨 **是** —— 同一张表三种读法 |
| `ELEMENT_BOM` | 3（3 方言 × 1 类） | 材质元素 | 否 |
| `MATERIAL` | 3（3 方言 × 1 类） | 主件 | 否 |
| 其余 21 个锚点 | 6 个各 2 · 15 个各 1 | 费用类等 | 否 —— 跨方言并列，非同表多读法 |

> 📐 **算术核对**（2026-09-04 实测，按 `node_key` 去重共 **25** 个锚点）：`9×1 + 3×3 + 2×6 + 1×15 = 45` 行。
> ⚠️ v1 写「其余 36 个锚点各 1」，`9+3+3+36 = 51 ≠ 45`，算术不成立。**核心结论不受影响**：同方言内一对多的只有 `MATERIAL_BOM`。

`MATERIAL_BOM` 的一对多，正是「选完数据源还得再选页签类型」的唯一根源。`ELEMENT_BOM` / `MATERIAL` 本来就一对一。

**而真正需要额外语义的只有两处**：

- **BOM 树**：要递归展开（`WITH RECURSIVE` + `UNION ALL` 根分支），且走独立渲染管线
- **材质元素**：要接元素价格策略（`FUNC_ELEMENT_PRICE`）+ 固定元素列

其余页签的取数完全由数据源 sheet 决定，不需要额外声明。

### 1.3 第二个问题：料号类型不该靠页签反推

`BomNodeTypeResolver` 现在按「这个料号出现在当前报价单的哪一类页签的已渲染行里」判类型，并把结果写进 `__nodeType`、回填时写成 `content.characteristic`。

**但料号类型本来就是主数据的固有属性**：

- 在**材质表** `material_recipe` → 材质
- 在**物料表** `ds_quote_material` → 看 `material_type`（零件 / 外购件）

实证两表**完全互斥**：物料表 45 行 / 材质表 260 行 / **交集 0**。判定无歧义。

靠页签反推的代价是判据不稳定——同一个料号，A 单配了零件页签就判零件，B 单没配就判不出来。改读主数据后判据是数据事实，跨单一致。

### 1.4 目标

1. 页签类型由**锚点节点推导**，用户不再选，`component.tab_type` 字段删除
2. 加叶子的类型判定改**读主数据**，不再回填类型
3. 加叶子补齐两条准入护栏：料号必须在主数据中存在、不成环

### 1.5 不做会怎样

- 配置器保留一个用户答不出所以然的必选项（现网 223 个组件里 114 个干脆留空）
- 类型判定继续依赖页签配置，跨单不一致，且新配的组件一旦漏配页签类型，加叶子直接 400
- 加叶子至今**没有环检测**，挂出环来无人拦

## ② 范围

### 2.1 做什么

| 编号 | 内容 |
|---|---|
| **S-1** | 页签类型收缩为**两类锚点推导**：锚点 `MATERIAL_BOM` → BOM 树；锚点 `ELEMENT_BOM` → 材质元素 |
| **S-2** | 取数配置器把「**页签类型**」下拉**换成「数据源」下拉** —— 用户直接选具体数据源（如「物料BOM」「自制加工费」），系统据锚点自动认定其语义并只读回显。⚠️ 不是"什么都不用选"：系统猜不出用户要哪张表，这一步省不掉。变化是**费用类由 2 次选择降为 1 次**，其余由"选抽象类型"变为"选表名" |
| **S-3** | 材质元素页签固定：可配元素价格策略、元素列固定绑定；其余锚点不出现价格策略入口 |
| **S-4** | `semantic_tab_view` **停用 6 行**（3 方言 × {零件, 外购件}）—— 它们是 `MATERIAL_BOM` 的重复读法；停用后 `MATERIAL_BOM → BOM 树` 一对一。**39 个数据源入口全部保留 ACTIVE**（A0-2 修正版裁决） |
| **S-5** | 加叶子类型判定改读主数据：在材质表 → 材质；在物料表 → 按 `material_type` 判零件/外购件；**`material_type` 为空默认判「零件」**（A0-1 裁决） |
| **S-6** | 加叶子准入①：料号**必须在物料表或材质表中存在**，否则拒绝 |
| **S-7** | 加叶子准入②：**不成环**，否则拒绝（**新增护栏**，现无此校验） |
| **S-8** | 删除 **`component.tab_type`** 列（**仅此一张表**，A0-3 裁决：`template_component_snapshot.tab_type` 114 行历史值保留、`semantic_tab_view.tab_type` 是唯一约束组成部分不动）—— 🚨 触 `CLAUDE.md` §3.2 不可逆红线，**单独报影响面请用户批准**，不随本次立项批准生效。**两阶段执行**：先改完全部消费点并验证通过，再单独申请删列 |
| **S-9** | 三套方言（`QUOTE` / `COST_BASIC` / `COST_DETAIL`）同步收缩 |
| **S-10** | `semantic_tab_view.tab_type` **降级为内部分组标签** —— 仅用于标记"该数据源是不是 BOM 树 / 是不是材质元素"（即要不要递归展开、能不能配价格策略），**不再作为用户可见概念**。该列本身不删（是 `(tab_type, variant_key, dialect)` 唯一约束的组成部分） |
