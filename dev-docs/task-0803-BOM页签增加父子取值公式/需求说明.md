## 0. 一句话结论

给 **`tabType='BOM'` 的树页签**增加一组**跨行的父子取值公式原语**（`PGET` 子取父、`CSUM/CAVG/CMAX/CMIN/CCOUNT` 父取子）+ 三个树属性 chip（`[层级]/[是否叶子]/[是否根]`），
让「成本自下而上 rollup」「用量自上而下累乘」这类 BOM 业务算法**由用户用公式配出来**，而不是由后台写死；
其余类型页签**一律禁用**这组公式（四道闸拦截）。

代价是求值器要从「逐行单向单遍」下沉到 **「单元格（行 × 列）级拓扑排序」**——这是本任务的核心改造点，不是加 6 个函数那么轻。

## 2. 需求背景与目标 ⭐

### 2.1 要解决什么问题

BOM 是**树**，但公式引擎只会**逐行算**。行与行之间除了「取上一行」（`previous_row_subtotal`，按数组顺序）之外，没有任何跨行取值能力。于是：

- **成本 rollup 做不了**：父件成本 = 各子件成本之和，这是 BOM 最基本的算法，当前公式表达不出来。
- **用量累乘做不了**：子件的整机用量 = 父件整机用量 × 本条边用量，需要自上而下逐层传递。
- 结果是这类需求只能往后台塞——2026-06-05 就出过一次：我把「根→节点 `composition_qty` 路径连乘」硬编码进 `BomClosureService` 闭包 SQL，被用户当场否决，功能暂停。

### 2.2 用户已定的方针（本任务是它的兑现）

> 2026-06-05 用户裁决：**累乘（及类似业务计算）应由公式决定、用户可配，不应在后台写死。**
> 后台只暴露**原语**（边用量、父节点值/路径访问能力、节点层级），让用户用公式自己组合出算法；
> 不要在闭包 SQL / spine / 后台服务里固化具体算法。
> （记忆 `cpq-computed-values-formula-driven-not-hardcoded`）

`PGET` / `CSUM` 族就是当时缺失的那批原语。**本任务补齐原语，不实现任何具体业务算法。**

### 2.3 本次要达成的目标

1. BOM 页签的 FORMULA 列可以引用**直接父行**的值（`PGET`）。
2. BOM 页签的 FORMULA 列可以聚合**直接子行**的值（`CSUM/CAVG/CMAX/CMIN/CCOUNT`）。
3. 提供分流判定所需的只读树属性：`[层级]` / `[是否叶子]` / `[是否根]`。
4. 两个方向**可在同一页签共存**（不同列各走各的方向）。
5. **非 BOM 页签禁止使用**，且禁止绕过（UI + 配置期正向 + 配置期反向 + 导入 + 求值期，五道拦截）。
6. 报价侧与核价侧**两侧都生效**。

### 2.4 不做什么（明确边界）

| 不做 | 原因 |
|---|---|
| 不实现任何具体业务算法（累乘用量列、成本 rollup 列） | 归业务公式配置，后台只给原语（§2.2 方针） |
| 不做跨页签的父子取值（BOM 页签取别的页签的父子值） | 树结构只在 BOM 页签内成立；跨页签取数已有 `cross_tab_ref` |
| 不做「后代」跨层聚合（整棵子树求和） | 已裁决为**仅直接子行**（§11.1）；跨层由逐层 rollup 自然涌现 → **已记 `BL-0104`** |
| 不做 Excel 列模型（`TabJoinPlanEvaluator`）的支持 | 该模型无行/树概念，照 KSUM 先例**显式抛错降级**（§4.3.7）→ **已记 `BL-0103`** |
| 不做「往上跳 N 层取祖先」 | 「取根节点值」用一列自引用即可（`IF [是否根] → 本行值 ELSE PGET([本列])`）；精确跳 N 层在 BOM 中罕见。**用户裁决：不做也不记**（§11.3） |
| 不做父子公式的配置期试算/预览端点 | **用户裁决：不做也不记**（§11.3）；验证走单据实跑 |
| 不改任何非 BOM 页签的求值路径 | 零回归门禁（§4.3.4） |
| 不做 DB schema / 迁移 | token 存 JSONB，无落库结构变化 |

## 4. 功能详述 ⭐

### 4.1 用户场景 / 操作流程

**场景 A：父件成本 = 子件成本汇总（自下而上）**

1. 用户在组件管理打开一个 `tabType=BOM` 的树页签组件。
2. 新建 FORMULA 字段「成本」，进入公式编辑器。
3. 因为该组件是 BOM 页签，公式编辑器里的「父子取值」区**可用**（非 BOM 组件此区置灰）。
4. 配成条件公式：
   ```
   当 [是否叶子] = 1  →  [取数成本]      // 叶子行取自己 SQL 拉到的成本
   否则               →  CSUM([成本])    // 非叶子行汇总直接子行的成本
   ```
5. 保存 → 报价单/核价单渲染该页签时，树自底向上逐层滚算出每层成本。

**场景 B：整机累计用量（自上而下）**

```
当 [是否根] = 1  →  1
否则             →  PGET([累计用量]) × [边用量]
```

**场景 C：两者共存于同一页签**——「成本」列走场景 A（bottom-up），「累计用量」列走场景 B（top-down），互不干扰。这是本任务允许双向混用的核心价值。

**反向场景 D：用户在非 BOM 页签想用**
- 公式编辑器里父子函数区**置灰**，hover tooltip 说明「仅 BOM 类型页签可用，当前页签类型为 XX」。
- 若绕过 UI 直接调接口写入 → 后端 400。

**反向场景 E：组件已配父子公式，用户想把 `tabType` 从 BOM 改成「零件」**
- 后端 400，提示「该组件的公式 X 使用了父子取值函数，请先删除后再变更页签类型」。

### 4.3 业务规则与计算逻辑（后端相关）

#### 4.3.1 树关系的定义（数据基础）

BOM 页签的每一行都携带系统列（后端 `BomTreeRenderService.treeRowNode` 写入；前端 `QuotationStep2` 已解析为 `__sys.{nodeId,parentId,lvl}`）：

`__nodeId` / `__parentId` / `__lvl` / `__hfPartNo` / `__parentNo` / `__bomVersion`

对本页签的行集合，定义：

- **直接父行** `p(r)` = 满足 `p.__nodeId == r.__parentId` 的那一行；`r.__parentId` 为 null/空 → `p(r)` 不存在（r 是根）。
- **直接子行集合** `C(r)` = `{ c | c.__parentId == r.__nodeId }`，**排除墓碑删除行**（见 §4.3.4 判据 1）。
  → 推论：一个节点的子行若被全部删除，它就变成叶子（`[是否叶子]=1`），这是期望行为。

> 🚨 **铁律：父子边一律按 `__nodeId` / `__parentId` 认，禁止按料号认。**
> BOM 是 DAG，同一料号会挂在多个父件下（现网实例 `3110520789` 同挂 `2120011658` / `2120011659` 两个父件）。按料号认边必然串号，把两个父件的子树混成一坨。`__nodeId` 是节点唯一身份，天然消歧。

#### 4.3.2 函数集与语义

| 函数 | 方向 | 语义 | 参数 |
|---|---|---|---|
| `PGET(expr)` | 子 → 父 | 在**直接父行** `p(r)` 的行上下文求 `expr` | 表达式 |
| `CSUM(expr)` | 父 → 子 | 对每个**直接子行** `c ∈ C(r)` 求 `expr`，取**有值项**求和 | 表达式 |
| `CAVG(expr)` | 父 → 子 | 有值项之和 ÷ **有值项个数** | 表达式 |
| `CMAX(expr)` | 父 → 子 | 有值项的最大值 | 表达式 |
| `CMIN(expr)` | 父 → 子 | 有值项的最小值 | 表达式 |
| `CCOUNT(expr)` | 父 → 子 | **有值项个数**（口径 = `CAVG` 的分母） | 表达式 |

树属性（只读标量，本页签任意公式与条件公式均可用）：

| chip | 取值 |
|---|---|
| `[层级]` | `r.__lvl` —— 🚨 **根为 1，不是 0**（系统既有约定，见 `CostingTreeGrouping:38` 硬编码 `nd.lvl = 1`，子孙按 `node_path` 的 `/` 数递增）。2026-08-03 端到端实测订正：原文档误写「根为 0」，照此写 `IF [层级] = 0` 判根将永远不匹配 |
| `[是否叶子]` | `C(r) == ∅` → 1，否则 0 |
| `[是否根]` | **取不到父行** → 1，否则 0（见 §11.5 G5：含 `__parentId` 为空、指向墓碑行、指向不存在节点三种情形） |

> ⚠️ **单节点树：`[是否根]` 与 `[是否叶子]` 会同时为 1**（根同时是叶子）。两条定义各自独立成立，非缺陷；写 `IF [是否根] … ELSE IF [是否叶子] …` 时须想清楚单节点树走哪支（§11.5 G6）。
>
> ⚠️ **`CCOUNT` 与 `[是否叶子]` 口径不同，不可互相替代**：
> `[是否叶子]` 按**树结构**判（含核价侧 spine 补位的空节点——看得见子节点就不是叶子）；
> `CCOUNT(expr)` 数的是**该表达式有值的子行数**（≤ `|C(r)|`）。
> **叶子判定一律用 `[是否叶子]`**，用 `CCOUNT(...)=0` 判会把「有子节点但子节点该列全空」误判成叶子——这正是澄清第三轮被否掉的口径（§11.3）。

#### 4.3.3 边界口径总表（全部返 0，无例外）

| 情形 | 结果 |
|---|---|
| `PGET` 在**根行**（无父） | **0** |
| `CSUM/CAVG/CMAX/CMIN/CCOUNT` 在**叶子行**（`C(r)=∅`） | **0** |
| `C(r)` 非空但**全部子行无值** | **0** |
| `PGET` 的父行存在但表达式无值 | 0（沿用现有引擎「空按 0」口径） |

> 🚨 **叶子/根返 0 的必然后果（配置者必须知道）**：
> 直接写 `成本 = CSUM([成本])` 会把**叶子行自己从 SQL 取到的成本清成 0**（叶子无子 → CSUM=0 → 覆盖掉取数值）。
> 这是 BOM rollup 的经典陷阱。正确写法是**条件公式分流**（§4.1 场景 A）：叶子取自身取数值，非叶子才取 CSUM。
> 引擎**不做隐式兜底**（不会「无子时自动回退到本行同名列」）——那种魔法在跨列聚合（`父.成本 = CSUM(单价)`）时语义不可解释。此为澄清第一轮定案（§11.1）。

> 🚨 **父子取值当除数时会怎样（2026-08-03 用户提问，已用共享夹具实测钉死）**：
> 因为上表「全部返 0，无例外」，`2 / PGET([X])` 在 **①根行无父 ②父行该列为空 ③父行该列真的是 0** 三种情形下
> 一律变成 `2 / 0`。两端引擎的除零语义是 **整式返 0，不抛异常、不产生 `Infinity`/`NaN`**
> （后端 `PrecisionPolicy.divide:54` `signum()==0 → ZERO`；前端 `precision.ts` `ArithDecimalParser.term:175`
> `r.isZero() → Decimal(0)`；口径见 `api.md` G-9）。
>
> **所以是「除以 0」，不是「除以 1」，结果恒为 0。** 引擎**不会**把缺失的除数悄悄换成 1 —— 那属于隐式兜底，
> 与上一条「引擎不做隐式兜底」的既定方针一致。
>
> ⚠️ **两个配置者必须知道的后果**：
> 1. **算不出「0」和「没值」的区别** —— 父行真的是 0、父行为空、本行是根，三者结果都是 0，事后无法区分。
>    要区分只能另配一列 `[是否根]` 或 `PGET([X])` 本身当标记列看。
> 2. **当前语言写不出保护** —— 组件公式的算术解析器（`precision.ts` `ArithDecimalParser`）只支持
>    `+ - * /`、括号和一元正负，**没有 `IF`、没有比较运算符、没有三元**（`SUMIF` 族的条件只作用于跨页签聚合的
>    过滤，不能当通用条件表达式用）。因此 `IF(PGET([X])=0, 1, PGET([X]))` 这类写法**目前不可用**。
>    若业务确实需要「缺值退化为 1」，属于语言能力扩展，见 [[BL-0109]]。
>
> 实测证据：共享夹具 `fixtures/tree-formula-parity-cases.json` 第 17 条
> 「用户问题-除零 2/PGET(...) 三种取不到值的情形」，含对照组（父列=4 → `2/4=0.5`，证明公式确实执行、
> 那几个 0 不是「公式没跑」的假绿），两端各 17/17 逐位一致。

#### 4.3.4 「有值」的可执行判据（本任务最容易做错的一处）

「空值不参与聚合」必须有可执行判据，否则核价侧 spine 补位空行会把 `CAVG` 分母稀释、把 `CMIN` 恒拉成 0。

**判据（按顺序）**：

1. 该子行是**墓碑删除行**（报价侧 `deleted_tree_nodes` 命中）→ **无值，不参与，也不计入 `C(r)`**。
2. `expr` 中引用的 `field` token，在该子行**全部取不到值**（null / undefined / 空字符串）→ **无值，跳过该子行**。
3. **至少有一个** `field` 取到值 → **有值**，参与聚合；其中取不到值的那些 field 按现有引擎口径当 0 参与表达式运算。
4. **数值 `0` 是有值**。判据是「引用的列取不到值」，**不是「结果等于 0」**——否则单价为 0 的子件会被踢出 `CMIN`。
5. `expr` **不含任何 `field` token**（纯常量 / 纯树属性，如 `CSUM(1)`）→ 判据 2 无从触发，**所有未删除子行均视为有值**（此时 `CSUM(1)` = `CCOUNT(1)` = `|C(r)|`，即子行个数）。
6. **被引用的列是「公式列」时恒为有值**（2026-08-03 用户裁决补充）。公式列总能算出一个数（哪怕是 0），
   因此判据 2「取不到值」对它天然不成立。

> 🔒 **明示接受的取舍（用户 2026-08-03 裁决）**：判据 6 的直接后果是 ——
> **当聚合的列是公式列时，核价侧 spine 的「补位空行」仍会参与聚合**（它的公式列算出 0）。
> 也就是说「空值不参与」这条规则**只对取数列/输入列生效**。
>
> | 场景 | 是否被空行影响 |
> |---|---|
> | `CMIN([单价])`（单价是取数列） | ❌ 不受影响 —— 空行该列无值，被排除，最小值不会被拉成 0 |
> | `CAVG([成本])`（成本是公式列） | ✅ 会受影响 —— 空行成本算出 0，计入分母，均值被稀释 |
>
> **为什么接受**：判据 6 的替代方案是「先判整行是不是空行」，但那会让规则从「看引用列」变成
> 「看整行」，两套判据并存更难解释；且成本 rollup（`父.成本 = CSUM(子.成本)`）本身就依赖
> 「公式列恒有值」才能逐层滚上去。**用户已知悉并接受此代价。**
> 若日后发现均值被稀释影响业务，解法是在公式里用 `[是否叶子]` / 条件公式显式排除，而非改判据。

> 说明：判据 2 用「全部取不到」而不是「任一取不到」，是为了避免 `[用量] × [损耗率]` 里损耗率没配就把整行踢出聚合。
> 单列情形（`CSUM([成本])`）自动退化为「该列在子行非空即有值」。

**手工加叶子（add-leaf）行**：照常参与聚合，与 driver 展开行无差别。

#### 4.3.5 内层表达式白名单（双端镜像拒绝）

`PGET` / `C*` 的 `targetExpr` 内**只允许**：

`field`（**本页签**列）、`operator`、`number`、`bracket_open`/`bracket_close`、`global_variable`、`tree_attr`

**明确拒绝**：

| 被拒 token | 原因 |
|---|---|
| 嵌套 `tree_ref`（`CSUM(PGET(x))`） | 语义退化（子行的父 = 本行自己），且让 cell 依赖图跨两跳 |
| `cross_tab_ref` / `component_subtotal` | 跨页签取数与树遍历混合，依赖图不可判定 |
| `b_field` | 该 token 只在 `cross_tab_ref.targetExpr` 内有意义 |
| `previous_row_subtotal` | BOM 页签整体禁用（§4.3.7） |

拒绝点**双端镜像**：前端序列化期（`formulaSerialize`）+ 后端 `TokenMappabilityValidator`，照 KSUM 硬约束的既有做法。

> ⚠️ **注意区分**：禁的是**语法嵌套**，不是**列间依赖**。
> `CSUM([成本])` 里引用的「成本」列**本身可以是一个 PGET 列**——这完全合法，也正是双向混用的价值所在。
> 列怎么算是单元格拓扑的事，与内层白名单无关。

#### 4.3.6 求值架构：从「逐行」下沉到「单元格级拓扑」（核心改造）

**现状**：
- 后端 `FormulaCalculator#computeRows`：`for 每行 { for 列的拓扑序 }`——单向单遍。
- 前端 `QuotationStep2#computeAllFormulas(comp, row, ...)`：**逐行调用**，8 个调用点跨 2 个文件。

**问题**：`PGET` 需要父先算（自上而下），`C*` 需要子先算（自下而上），方向相反，单遍不可能同时满足。

**改造**：BOM 页签走**新的页签级求值入口**，求值单元从「行」下沉到 **`(nodeId, 列名)`**，全量建图后 Kahn BFS 拓扑求值。

依赖边定义：

| 边 | 来源 |
|---|---|
| `(r, A) → (r, B)` | 现有 `field` 同行列引用 |
| `(r, A) → (p(r), targetExpr 涉及的各列)` | `PGET` |
| `(r, A) → (每个 c ∈ C(r), targetExpr 涉及的各列)` | `C*` 族 |

规则：

1. **成环** → 环上 cell **及其下游 cell**（拓扑上无法求值的）一并置 0；**与环无依赖关系的 cell 照常求值**（不是整页签炸）。环检测在求值期做，配置期不做（配置期无法知道运行时树形）。
   错误标记（`out.errors`）**本期仅前端出**——后端 `RowResult` 无错误通道，属已知限制。详见 §11.5 G2。
2. **非 BOM 页签一行不改**，仍走原逐行入口 → 零回归门禁。
3. 前端需**新增页签级入口**（如 `computeTabFormulasTree(comp, rows[], ...)`），返回 `行 → 列 → 值`，由渲染层按行取用；原 `computeAllFormulas(comp, row, ...)` **保留**给非 BOM 页签。这是前端最大的一处结构改动（8 个调用点需按页签类型分流）。
4. **与 `cross_tab_ref` 的次序**：组件级拓扑（`CrossTabComponentOrder.topoOrder`）不变。BOM 页签被算到时，其内部 cell 拓扑**整体跑完**，之后其他页签的 `cross_tab_ref` 才会读到它的行——次序天然正确，无需额外协调。
5. **规模与性能**：cell 数 = 行数 × 公式列数。实施时须实测现网最大树（含 `COMP-0157` 8 个 FORMULA 列的报价单）并给出耗时；纯内存拓扑，无额外 DB 往返。

#### 4.3.7 与既有能力的关系

| 能力 | 处置 |
|---|---|
| `previous_row_subtotal`（取上一行） | **BOM 页签禁用**。树上「上一行」是树展开后的数组顺序，可能是父/兄弟/叔叔的孙子，语义模糊，配了必是误用。**实探已证零破坏**：全库 0 个组件使用该 token（§11.4）。禁用点同 §4.3.5 白名单 + 页签级校验。 |

## 10. 补充说明

### 10.1 本任务不引入的「魔法」

设计上刻意拒绝了三处隐式兜底，全部要求用户显式用条件公式表达：

1. `CSUM` 无子行时**不**自动回退到本行同名列取数值。
2. `PGET` 无父行时**不**自动回退到本行同名列取数值。
3. 叶子/根的分流**不**由引擎猜，由 `[是否叶子]` / `[是否根]` 显式判定。

理由：跨列聚合（`父.成本 = CSUM([单价])`）下「回退取谁」不可解释；隐式兜底会造成算错了还看不出来。

## 11. 澄清记录（2026-08-03，三轮 + 实探）

### 11.1 第一轮 —— 聚合语义

| 问题 | 裁决 | 备注 |
|---|---|---|
| `C*` 的「子行」范围 | **仅直接子行** | 自底向上逐层滚算，孙辈的值已先滚进子辈；避免「被聚合列本身也是聚合列」时层层重复计数 |
| 叶子行 `CSUM` 返回什么 | **返回 0，靠条件公式分流** | 否决了「无子时自动回退本行同名列」（有魔法、跨列时语义不清）与「返 null + 标错」（叶子整列不可用） |
| `PGET` 与 `C*` 能否同页签混用 | **允许，不同列各走各的方向** | 明示接受代价：求值器改为单元格级拓扑，成环报错标红 |

### 11.2 第二轮 —— 边界与原语

| 问题 | 裁决 |

### 11.5.1 G1 补例：混合表达式的有值判定

树：父 R，两个直接子 A、B。列 `用量` 是取数列，列 `成本` 是公式列。

| 子行 | 用量（取数） | 成本（公式列，恒有值） | `CSUM([用量]×[成本])` 是否计入 |
|---|---|---|---|
| A | 2 | 10 | ✅ 计入，贡献 20 |
| B | *(空)* | 0 | ✅ **计入**，贡献 0（用量按 0 代入） |

→ `CSUM = 20`；`CCOUNT = 2`（**不是 1**）；`CAVG = 10`。

> 若期望 B 被剔除，**不能**靠改判据，应在表达式里显式排除（例如用条件公式按 `[是否叶子]` 或业务标志位分流）。

### 11.5.2 ⏳ G7 待定：性能阈值

AC-29 当前只要求「实测并写入交付文档」，缺通过/不通过界限，测试只能给出数字、给不出结论。
