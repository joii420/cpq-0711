## ① 背景与目标

`task-261028` 已把**报价侧**产品卡片底部改成「首行税前金额 / 次行 `(VAT)` 含税金额」，并明确不动核价侧。用户检查核价侧后提出 4 个问题，核对代码后全部属实：

1. **没有核价数据时显示了报价侧的金额**：详情页「核价单」视图里，这张单没有核价结构（卡片显示「暂无组件数据」）时，卡片底部仍显示一个金额 —— 它是报价侧的产品小计（每个报价行只有一个 `subtotal` 字段，存的是报价侧小计；核价组件为空时计算函数退回读它）。外币小计同样是这个报价金额除以汇率。用户会把报价金额误当成核价金额。
   > 📌 **2026-10-30 开工后实测更正**：测试夹具在 master 上的证伪用例（CAL-2）显示，「无核价结构」确实显示报价小计（`产品小计 ¥ 888.123456789 外币小计 124.676903837 USD`）；但「核价数据生成失败」显示的是 `产品小计 ¥ 0 外币小计 0 USD`（有核价结构、算出 0），**不是**报价金额 —— 立项时这一半是读代码推断，写错了。两者都会让用户误读成「核价金额」，AC-4 统一显示 `-` 的结论不变。
2. 核价侧仍显示「产品小计」「外币小计」字样，与报价侧已移除字样的口径不一致。
3. 报价币种本身就是 CNY 时，仍多出一行与第一行完全相同的「外币小计」。
4. 核价侧金额的币种写法不统一：详情页是 `¥ 1234`，编辑页是 `CNY 1234`（币种在前），外币小计是 `170 USD`（币种在后）。

澄清阶段用户另外定稿：核价侧金额区改为**左右分币种、上下分含税** —— 左列 CNY、右列报价币种；每列第一行税前、第二行 `(VAT)` 含税。

**目标**：核价卡片底部只显示核价自己的金额，拿不到就明说没有；去掉字样；币种统一用缩写放在金额后面；按币种左右排、按含税上下排；报价币种为 CNY 时只留一列。不改任何计算、保存值和后端。

## ② 范围

### 本期做什么

- **核价侧金额区**（编辑页「核价单 · 产品卡片」、详情页「核价单 · 产品卡片」，以及复用详情组件的核价管理页面）：
  - 去掉「产品小计」「外币小计」字样。
  - 改为两列：左列 CNY、右列报价币种；每列第一行为税前金额，第二行为 `(VAT) 含税金额`。
  - 报价币种为 CNY（含币种为空、按现行规则视作 CNY）时只显示 CNY 一列。
  - 所有金额写成「金额 币种缩写」，如 `1717.135540717 CNY`、`241.055611185 USD`；不出现 `¥` / `￥`。
  - 金额文字（含 `(VAT)` 前缀与无数据时的 `-`）字色统一为白色，与报价侧金额区一致；外币列不再用现行的蓝色。`(VAT)` 行沿用报价侧的透明度层级（前缀 0.82、金额 0.94）。
  - 含税金额 = 核价小计 ×（1 + 该报价行冻结的 VAT 比例）；外币列 = 对应 CNY 金额 ÷ 报价单汇率。税率取值规则与报价侧完全一致：`vatRateRatio` 优先，仅缺失时用 `vatRate ÷ 100`；缺失 / 非数字 / 小于 0 / 大于 1 时含税行显示 `(VAT) -`。
  - 宽度放不下两列并排时（窄屏或超长金额），第二列整列换到下一行，CNY 列在上。
- **没有核价数据时**：卡片主体显示「加载组件结构...」「暂无组件数据」或「核价数据生成失败…」时，金额区只显示一列：第一行 `-`、第二行 `(VAT) -`，不显示任何金额、任何币种。
- 计算与显示口径延续现行：Decimal 12 位工作值，`HALF_UP`、去尾零；最终显示销售代表/销售经理最多 4 位，定价经理/系统管理员最多 9 位。
- **（开工后扩范围，用户 2026-10-30 裁决纳入）编辑页保存后不丢币种与汇率**：编辑页保存草稿（手动或自动保存）后，报价单的币种、汇率及汇率元数据（日期 / 来源 / 采集时间）沿用保存前的值，不再被重置成 `CNY` / `1`。这是既有缺陷（`task-260901` 把保存响应瘦身为 `SaveDraftResponse` 后不再含这几个字段，前端合并时整体覆盖）；保存请求本身不含这几个字段，保存不可能改变它们，故沿用旧值不会掩盖真实变化。

- **（开工后扩范围，用户 2026-10-30 裁决「AC-9 保持为 0，顺手修掉」）消除本任务三个页面上的既有控制台报错**：编辑页、报价详情页、核价管理页在 master 上已有 5 类 error 级输出 —— antd `Drawer` 的 `width`、`Alert` 的 `message`、`Space` 的 `direction`、`Spin` 的 `tip` 四种废弃写法，以及编辑页「`<form>` 嵌套在 `<form>` 内」。只改这三个页面实际渲染并触发它们的组件，视觉与交互不变。
- **（开工后扩范围，用户 2026-10-30 裁决方案 A）第 6 类：保存时静态 `message` 报「Static function can not consume context like dynamic theme」**：在应用根组件配一次 `ConfigProvider.config({ holderRender })`，让 antd 静态方法也拿到应用主题（antd 6.3.5 仅在未配 `holderRender` 时告警，`message/index.js:200-201`）。副作用（用户已知悉并接受）：全应用的静态提示 / 通知 / 确认框改为跟随主题主色与暗色模式。

## ③ 验收标准
