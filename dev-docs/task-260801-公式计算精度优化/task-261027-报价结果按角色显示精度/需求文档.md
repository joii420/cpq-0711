## ① 背景与目标

现行报价精度契约将公式计算过程与展示边界分层：计算工作值保留 12 位小数，报价的计算结果最多显示 9 位小数。现需按当前登录用户角色限制报价计算结果的呈现精度：

- 销售代表（`SALES_REP`）、销售经理（`SALES_MANAGER`）：最多显示 4 位小数。
- 定价经理（`PRICING_MANAGER`）、系统管理员（`SYSTEM_ADMIN`）：继续最多显示 9 位小数。

目标是只改变页面与对外输出中的数字文本，不改变计算、保存、快照、对账、接口精度或历史报价事实。同一张报价单由不同角色查看时，底层值完全一致，仅显示位数不同。

## ② 范围

### 本期做什么

- 报价单列表、编辑向导、产品卡片、报价详情、Excel 视图与比对视图中的计算结果按当前角色限制最大显示位数。
- 计算结果包括：公式单元格、列/页签/组件小计、产品小计、行金额、报价原价/折扣结果/未税及含税总额等派生金额。
- HTML、PDF、报价 Excel、Excel 视图导出、比对 Excel 及邮件附件，按发起该次输出操作的当前用户角色生成 4/9 位文本。
- 保留 `HALF_UP` 与去尾零语义；字段显式配置的位数小于角色上限时，仍按较小的显式配置显示。
- 新建与历史报价单使用同一角色显示规则，不回算、不回写。

### 本期明确不做什么

- 不修改 12 位计算过程、除法精度、公式算序或舍入方式。
- 不修改 API decimal string、关系型字段/JSONB 快照、草稿保存值、提交对账值或历史冻结值。
- 不将角色上限用于原始输入或基础属性，例如用户输入数字、汇率、税率、利润快照、基础资料取数值；它们继续遵守各自现有显示契约。
- 不扩展到报价单之外的价格管理、主数据、选配实例或独立核价页面。
- 不新增系统参数、页面或交互；因此不需要 HTML 原型。
- 不自动生成部署包；只有用户后续明确要求打包或部署时才更新 `deploy/`。

## ③ 验收标准（AC）

- **AC-1 · 角色单点**：以销售代表和销售经理分别查看含计算值 `1.2345678915` 的同一张报价单，公式单元格、产品小计和报价总额均显示 `1.2346`；页面状态和 GET 响应中的原值不被改写。
- **AC-2 · 其他角色**：以定价经理和系统管理员查看 AC-1 的同一张单，对应计算结果显示 `1.234567892`。
- **AC-3 · 显式配置**：计算列显式配置 2 位时，四个角色均显示 `1.23`；显式配置 6 位时，销售两角色显示 `1.2346`，其他两角色显示 `1.234568`。
- **AC-4 · 页面全入口**：报价列表、编辑步骤、产品卡片、详情卡片、Excel 视图与比对视图对同一计算值使用一致的角色上限，且所有页面“加载中”计数最终为 0。
- **AC-5 · 对外输出**：分别以销售经理和系统管理员生成 HTML、PDF、报价 Excel、Excel 视图导出、比对 Excel 及邮件附件；前者计算结果最多 4 位，后者最多 9 位，两者的未舍入原值与报价单保存值均不变。
- **AC-6 · 去尾零与边界**：销售角色下，`12.500000000000` 显示 `12.5`，`1.23444` 显示 `1.2344`，`1.23445` 显示 `1.2345`，负数同样按 `HALF_UP`。
- **AC-7 · 保存不变**：销售经理打开草稿、编辑一个与目标计算值无关的文本字段并保存，刷新后后端响应、关系型列及快照中该计算值仍与保存前逐字相等，不得将页面上的 4 位文本回写。
- **AC-8 · 连续角色切换**：先以销售代表查看报价并记录 4 位文本，退出后以系统管理员重新打开同一张单，同一结果恢复为最多 9 位；再切回销售代表恢复为最多 4 位，期间报价的修改时间、快照和金额字段均不变。
- **AC-9 · 非计算数值边界**：在 AC-1 的销售角色下，用户输入数字、汇率、税率、利润快照和基础资料取数值与改造前显示文本一致，不被统一压到 4 位。
- **AC-10 · 权限边界**：未登录请求仍按现有鉴权返回 401；角色显示规则不扩大任何报价查看、导出或发送权限。
- **AC-11 · 无回归**：前端类型检查、单测、生产构建及 Playwright 报价主链全绿；后端精度/导出定向测试全绿，且同轮基线无新增失败。

## ④ 依赖与影响面

- 依赖现有角色枚举与会话角色：`SALES_REP` / `SALES_MANAGER` / `PRICING_MANAGER` / `SYSTEM_ADMIN`。
- 依赖 `PrecisionPolicy`、前端 `precision.ts` / `formatNumber.ts` 的 12/9 位基线与 `HALF_UP` 规则。
- 影响报价列表、编辑、详情、产品卡片、比对、Excel 视图、HTML/PDF/Excel/邮件导出；属于“改一处、多处可能静默漏改”的强联动展示契约。
- 不改数据库 schema，不需要 Flyway 迁移；不新增业务端点。
- 本任务不修改字段类型，不触发 AP-44 十七处传播；但会修改报价渲染主链和导出契约，必须按 `change-protocol.md` 完成列表/编辑/详情/导出全入口检查与 E2E。
- 本任务不破坏 `docs/三大核心模块基线.md` 的数据源、模板冻结、页签树或驱动展开基线；仅在现有最终呈现边界增加角色上限。

### 方案裁决（A0）

- **D-1 · 已选择方案甲**：建立报价专用的角色显示精度解析器；前端从认证状态订阅原始角色值并把 4/9 位上限显式传给报价渲染函数，后端由 Resource 从当前会话读取角色并把上限显式传给导出服务。通用格式化函数只增加可选上限参数，省略参数时仍按现有最多 9 位行为。
- 不采用“让通用格式化器直接读取全局登录态/请求上下文”：这会让主数据、价格管理、选配等非报价页面产生隐藏角色依赖，也使纯函数和导出单测难以隔离。
- 不采用“在 API 返回或保存时预先舍入”：这会破坏用户已确认的“保存不变、只影响显示”，并让同一报价无法按不同查看角色恢复 4/9 位文本。
- 前端遵循 React 派生状态原则：直接订阅 `user?.role` 这一原始值并同步计算上限，不使用 effect 把角色复制到本地 state，也不在通用工具中隐藏订阅。
