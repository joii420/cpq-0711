## 1. 背景：问题是什么

### 1.1 一句话

模板发布（PUBLISHED）之后，**页签内部的字段定义、组件公式、驱动路径这些「内容层」仍然是活的** —— 在「组件管理」里保存一次组件，所有引用该组件的已发布模板快照会被**自动、静默、无提示**地改写，连带改变在途报价单的渲染结果。

### 1.2 这是代码漂移，不是既定设计

`docs/三大核心模块基线.md:178` 写明了 snapshot 的存在理由：

> 为什么需要 snapshot：组件管理改字段后，老模板的历史报价单**不能反向受影响**（否则历史报价改写）。

同文档 `:182` 定的契约是「组件管理改字段 **+ 调 H1 端点时**同步刷新所有 PUBLISHED 模板 snapshot（**但只在用户明确触发时**）」。
同文档 §10.2 第 4 条：「模板新版本通过 `createNewDraft` 创建，**不直接动 PUBLISHED**」。

而代码实现：`ComponentService.update:733` **每次保存组件就无条件自动调用** `refreshSnapshotsByComponent`。「只在用户明确触发时」这个限定词在实现里根本不存在，§10.2 第 4 条也被同一条路径绕过。

`TemplateService.refreshSnapshotsByComponent:333-334` 的注释坦承了这一点：

> 语义说明: 这刻意破坏 PUBLISHED 模板的 "版本快照不可变" 约定，因为配置层变更必须对所有视图同步生效

**本任务不是推翻架构，是把实现拉回它自己写明的基线。**

### 1.3 三类活穿透（本次要全部堵死）

| # | 活穿透形态 | 位置 |

| ① | `refreshSnapshotsByComponent` 改写已发布模板 `components_snapshot` | `TemplateService:340-414`，4 个调用点 |

### 1.4 ② 从未被冻结的 8 个字段

`rowKeyFields`、`sortField`、`elementCodeField`、`elementPriceField`、`elementCurrencyField`、`columnCount`、`status`、`directoryId`。

**字段账（口径统一，全文以此为准）**：`Component` 实体共 **23** 个字段 = `id` + `createdAt` / `updatedAt`（3 个非配置）+ **18 个渲染配置字段** + `status` / `directoryId`（2 个刻意不冻，见 §4.1.3）。18 个需冻字段中，**旧 snapshot 只冻了 12 个**，本次补齐剩余 **6 个**（上列前 6 个）。

上列 8 个中，前 5 个直接改变渲染结果：

- `rowKeyFields` —— driver 行的业务标识；改了会让已发布模板的快照**命中不了**（历史坑参见行键唯一化消歧）
- `sortField` —— 「快照组装层按该字段对 driver 行做数字感知升序排列」，直接决定行序
- `element*Field` —— 决定元素单价是否接价格策略（task-0729 B7）

**根因**：这三类都是「组件级角色字段」。`Component.java:120` 的注释自己写着 ——

> 组件级角色字段，**不进 `fields` 的 config JSON（绕开 AP-44 17 点联动）**

它们当初为了绕开 AP-44 那 17 处协议传播的成本被挂在 `component` 表列上，而 snapshot 冻的恰恰只有 `fields`。**绕开 AP-44 的同时顺带绕开了冻结** —— 这是无意的副作用，不是有意的设计。

## 2. 目标与非目标

### 2.1 目标

模板发布后，**其渲染所依赖的全部配置冻结成一份不可变快照**。此后：

- 改任何组件配置，**已发布模板与其报价单的渲染结果一字节不变**
- 想让新配置生效，**只能** `createNewDraft` → 改 → `publish` 出新版本
- 快照读不到时**显式报错**，绝不静默回落活表

## 3. 已核实的现状与文档纠错（本期不改代码，只固化 / 纠正文档）

### 3.0 D5 的现状核实

用户定的 status 语义**当前代码已经做到**，本期只做「固化 + 文档化」，不改代码：

- **后端渲染链路零处读 `component.status`**（全量 grep：命中的 `status='ACTIVE'` 全在别的表 —— `comparison_tag` / `MaterialRecipe` / `DerivedAttribute` / SQL 视图 / 元素等；`component` 表唯一命中是 `TemplateService:804` 的 admin 端点，不在渲染路径）
- **组件选择器已过滤**：`ComponentPalette.tsx:106`、`TemplateConfiguration.tsx:129` 均 `filter(c.status === 'ACTIVE')`
- **实测硬证据**：库中 121 个组件里 **51 个已 `DISABLED`**，其中 **12 个 tc 行分布在 2 个已发布模板上，且仍在正常渲染**

> 值域是 `ACTIVE` / `DISABLED`（`ComponentService.toggleStatus:846-850`），**不是** `INACTIVE`。

**交付物**：把这条写成带实测证据的不变量，写入 `docs/三大核心模块基线.md`，防止将来有人「顺手」在渲染层加 `status='ACTIVE'` 过滤把它破坏掉。

### 3.1 附带发现：基线 §3.4「老版本自动归档」是错的（D6）

立项勘察中发现的**第二处文档与代码不一致**，与主线问题独立，但在严格版本化下会咬人：

| 出处 | 说法 |
|---|---|
| `docs/三大核心模块基线.md:218` | 「发布为新 PUBLISHED → 老 PUBLISHED **自动 ARCHIVED**（同 series 版本）」 |
| `TemplateService.publish:313-314` | 「同 series 升级时，旧 PUBLISHED **保持原状态**，由用户后续主动归档。V62 已撤销 V28 partial unique index，同 (customer_id, category_id) 允许多个 PUBLISHED 共存」 |

**实测：代码是对的，文档是错的。** 6 个 series 中 **4 个存在多 PUBLISHED 版本共存**，最多一个 series 挂着 6 个已发布版本（v1.0~v1.5）。

## 4. 设计

### 4.1 数据模型

#### 4.1.1 新表 `template_component_snapshot`

一行 = 一个已发布模板的一个页签的**完整生效配置**。发布时写一次，此后只读。

```
主键 / 溯源
  id, template_id (FK → template ON DELETE CASCADE), sort_order
  template_component_id, component_id     -- 仅溯源，不建 FK
  frozen_at

来自 template_component（模板级，现已冻结）
  tab_name, preset_rows(jsonb), formula_assignments(jsonb)

来自 component（内容层，本次要冻的主体）
  component_name, component_code, component_type, column_count
  fields(jsonb), formulas(jsonb), excel_columns(jsonb)
  data_driver_path(text), tree_config(jsonb), bom_recursive_expand(bool)
  tab_type, part_no_field, part_name_field
  row_key_fields(jsonb)   ← ② 新补
  sort_field              ← ② 新补
  element_code_field      ← ② 新补
  element_price_field     ← ② 新补
  element_currency_field  ← ② 新补
```

**索引**（按 §1.5 那 6 处 SQL 的谓词开）：

- `(template_id)`
- `(template_id, tab_type)`
- `(template_id) WHERE data_driver_path IS NOT NULL`
- `(component_id)` —— 供 §4.4.3 版本差异视图使用

**唯一约束 `(template_id, sort_order)`** —— 正好把 AP-40 那个「同 componentId 多实例必须按 sortOrder 精确匹配」的历史坑从 schema 层面变成不可能。

**不建 FK 到 `component` / `template_component` 是刻意的**：快照的全部意义就是与活表脱钩，组件被停用或被删都不该动摇已发布模板。

#### 4.1.2 三条冻结边界

| 边界 | 规则 | 依据 |
|---|---|---|
| **DRAFT 模板不写快照** | 草稿期一律走活表 | 现状即如此：`create:130` 不设、`createNewDraft:468` 显式 NULL、`publish:256` 才写 |
| **ARCHIVED 模板同样冻死** | `archive()` 只改 status 不动快照，新表同理 | 历史报价单仍在读它们 |
| **`sql_views_snapshot` / `template_sql_views_snapshot` 不动** | 本来就在 publish 冻结且 refresh 不碰 | 但有 fallback 缺口，见 §4.3.4 |

#### 4.1.3 不冻的字段

- `status` —— 见 §3（不进快照也不进渲染路径）
- `directory_id` —— 纯组织维度，不影响渲染

### 4.2 写入路径

#### 4.2.1 唯一写入点：`TemplateService.publish()`

发布事务里一次性落三样，全部同事务：

1. `template_component_snapshot` —— N 行（每个 tc 一行）【新增】
2. `template.components_snapshot` jsonb —— **改为从 ① 派生**，不再各自拼装
3. `sql_views_snapshot` / `template_sql_views_snapshot` —— 维持现状

**派生而非并行拼装是关键**：两份数据同源同事务生成、之后都不再变，结构上不可能不一致。

**前端契约不变**：`components_snapshot` 的字段形状保持一致，`BulkImportPartsDrawer.tsx:123`、`QuotationStep2.tsx:3844`、`ExcelViewConfigTab`、`enrichComponentData` 路径全部无感。

#### 4.2.2 `refreshSnapshotsByComponent` 整体退役

DRAFT 模板恒无快照 → 该方法的作用面**从来只有 PUBLISHED + ARCHIVED** → 冻结之后它没有任何合法用途。**不是限制它只刷 DRAFT，是整个下线。**

| 调用点 | 处置 |
|---|---|
| `ComponentService.update:733` | **删除**（灾难源头：保存组件即改写已发布模板） |
| `ComponentService.setDriverView:792` | **删除** |
| `ComponentResource:145` `POST /components/{id}/refresh-template-snapshots` | **直接删路由**（D11） |
| `ConfigCenterResource:128` 批量刷新 | **保留**（admin 后门），改造见 §4.2.3 |

#### 4.2.3 保留的 admin 后门：从「静默改写」变「留痕改写」

适用端点：`ConfigCenterResource:128`、`TemplateResource:170`（delete-tcs）、`TemplateResource:205`（promote-override-to-component）。三者统一加：

1. **前置影响面预览** —— 先返回「将改动 N 个模板 / M 张在途报价单」，二次确认才执行（对齐 `docs/列表操作规范.md` 危险动作二次确认）
2. **写审计**（D9）—— 目标表 **`operation_log`**：
   - 现有列 `operator_id / operation_type / target_type / target_id / summary / created_at` 语义完全匹配「谁在什么时候动了哪个对象」，且 `CustomerService` 已是真实写入方
   - **加法式新增 `details jsonb` 列**存结构化 diff（改前改后），可空，不影响现有写入方
   - `operation_type` 取值示例：`TEMPLATE_SNAPSHOT_FORCE_REFRESH` / `TEMPLATE_TC_DELETE` / `TEMPLATE_OVERRIDE_PROMOTE`；`target_type = 'TEMPLATE'`
   - ❌ **不用** `basic_data_change_log`：那张表语义是「基础资料变更」，模板快照不是基础资料，为复用而扭曲语义会污染 `BL-0100` 的设计意图
3. **日志告警** —— `LOG.warn` 明确标注「已破坏模板不可变性」

`TemplateResource:143` `migrate-to-unified-view` 是一次性历史迁移（基线 §3.5 标注「已跑过」）→ **直接删除**。

#### 4.2.4 CI 级约束

Flyway 迁移不得再直接 `UPDATE template SET components_snapshot = ...`。写入 `docs/方案制定前必读.md` §改动 5（该节现有内容是老契约「必须同时改 3 个层」，需一并改写）。

### 4.3 读取路径

#### 4.3.1 收口到 `PublishedTemplateReader`

10 处各写各的 SQL 是本 bug 潜伏至今的原因之一。新增读取服务，渲染期一切「这个模板有哪些页签、每个页签什么配置」的问题都问它。

接口按现有调用形态给**批量**方法（`driverCompsOf(templateId)` / `treeTabsOf(templateId)` / `hasRecursiveExpand(templateId)` / `allTabsOf(templateId)` …），一次一个模板返全集 —— 把 CLAUDE.md 「单个业务操作 SQL 条数与 N 无关」的铁律焊在接口形状里。

#### 4.3.2 6 处 native SQL：只换表，谓词不动

```sql
-- 改前
JOIN component c ON c.id = tc.component_id  WHERE tc.template_id = :tid AND c.tab_type = 'BOM'
-- 改后
FROM template_component_snapshot s          WHERE s.template_id = :tid AND s.tab_type = 'BOM'
```

**有益副作用**：改完后 `template_component` 活表也退出渲染路径 —— `delete-tcs` 后门连渲染都影响不到了。

`ExcelViewService` 那 4 处需注意 `:435` 的性能守卫注释（「避免对每行做无谓的 `Component.findById`」）：换成按 templateId 一次性预载 Map，比现状更快。

#### 4.3.3 快照缺失 = 显式报错，绝不回落活表

PUBLISHED / ARCHIVED 模板读不到快照行 → 抛错，带 `templateId` + 缺失的 `sortOrder`。

**绝不能写成「没有就查活表兜底」** —— 那是活穿透原地复辟，而且是静默的。

渲染只发生在报价单上，而报价单绑定已被 task-0729 强制要求 PUBLISHED，故渲染期不存在 DRAFT 分支，无需兜底路径。

#### 4.3.4 堵上 SQL 视图 fallback 缺口

`ComponentSqlViewService.lookupForResolver:400` 第 3 步「兜底实时读 `component_sql_view`」是 `sql_views_snapshot` 线上唯一的活穿透口，性质与主线问题相同。

改为同 §4.3.3 口径（miss 即报错）。**但不得盲改** —— `snapshotForComponents` 冻的是「含 GLOBAL scope 闭包」的视图集，若闭包算法本有漏算、现靠 fallback 悄悄兜着，一改成报错会把原本能跑的模板打挂。

**前置门槛（D13，本期唯一浮动项）**：§4.4.2 体检 B 跑完看数据再定边界 ——

| 体检 B 结果 | 处置 |
|---|---|
| 零 miss | 直接切报错，本节完成 |
| miss 少（闭包算法小漏，可定点补） | 补闭包算法 + 回填存量 snapshot → 再切报错，仍在本期 |
| miss 多（翻出闭包算法的历史欠账） | **本节整体拆出单独立项**，主线先上；此时 SQL 视图那条线暂时保留 fallback，并在 spec / BACKLOG 显式记为已知缺口（**不得默默留着当没事**） |

体检 B 跑完须把数据给用户过目再定，不由实现者自行决断。

### 4.4 存量对齐与可观测

#### 4.4.1 一次性对齐 = 一条 Flyway 迁移

       tc.preset_rows, tc.formula_assignments,

#### 4.4.2 迁移前两份体检，迁移后一份铁证

| 项 | 内容 | 门槛 |
|---|---|---|
| **前置体检 A** | 「现 `components_snapshot` vs 当前活配置」逐字段 diff，**存档留证** | 理论应近乎为零；非零处 = 历史某次传导失败留下的疤，冻死前须人工看一眼 |

| **迁移后铁证** | **值中性验证**：迁移前后对同一批报价单纯读渲染，卡片值**逐位对比** | **必须逐位一致**。本次改的是「数据从哪读」不是「读出什么值」，任一位不同即 bug。沿用 `GoldenCardValuesEquiv` 背靠背纯读手法 |

#### 4.4.3 版本差异视图（不是告警器）

`GET /api/cpq/templates/{id}/frozen-drift`（`SYSTEM_ADMIN`）：对比该已发布模板快照 vs 当前活组件配置，输出逐字段差异。

**D10：本期只做 API，不做前端 UI**（UI 登 BACKLOG）。管理员先用 curl / DB 查。

**语义定位很重要**：迁移当天应全零；随组件继续迭代，差异会自然增长 —— **这不是故障，正是严格发版模型下的正常状态**。它回答的是「这个已发布模板比当前组件配置落后多少，值不值得发新版」，是发版决策依据。同时天然兼任 admin 后门的安全网：谁偷改了快照，一眼可见。

#### 4.4.4 回滚

新表可直接 `DROP`；`components_snapshot` jsonb 形状向后兼容，代码回滚即恢复旧行为。

### 4.5 换模板护栏（D8）—— 本期唯一的前端改动

**背景**：严格版本化（D1）落地后，「想用上新配置」的唯一路径变成「发新版 → 已有报价单换模板」。而这条路径**当前是坏的**（`BL-0129`）：`QuotationService:1670` 换模板时**显式清空 `snapshot_rows`**（既有设计语义「留空待重建」），结果是产品行无数据、总价恒 0，且实测三条恢复路径（重算 / 刷新卡片快照 / force 重建）**均无法纠正**。

**本期不修 `BL-0129`**（根因在另一条链路），但必须让用户知情 —— 因为现有文案在骗人：
