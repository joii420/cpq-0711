## ① 问题描述

在「组件管理」里把一个已有组件的**页签类型改为 `BOM`（树页签）**时，保存被拒，HTTP 400，前端弹出：

```
该组件已被 1 处核价(COSTING)模板引用，不能设为 BOM 树页签——会把这些核价模板
一并改成树渲染，破坏核价侧零回归。报价侧树页签请新建专用组件。
```

> 用户未提供截图，本段为错误文案原文（与代码字符串逐字一致，见 §④ 证据 A）。

这段文案里的因果陈述——「会把这些核价模板一并改成树渲染」——**在 task-0806 交付之后已经不成立**：已发布/已归档的核价模板从冻结快照读渲染配置，改活表组件影响不到它们。护栏因此从「有效防线」退化为「纯误拦」。

> 📌 **E-7 / E-8 的形态（2026-08-14 用户纠正，重要）**：这两条都是**对当前状态的不变量断言**，**不是**「与上一版快照做 diff 找出 `tab_type` 从非 BOM 变成 BOM 的页签」。
> 用 delta 做判据两头都错 —— **假阳性**：A 页签 非BOM→BOM 同时 B 页签 BOM→非BOM，净结果仍是 1 个树页签、完全合法，delta 却会报警；
> **假阴性**：上一版本来就有 2 个树页签（`validateAtMostOneTreeTab` 自己写明「存量模板若已违反该约束不回补校验」），本次谁都没动 → delta=0 放行，而这恰是最该拦的。
> 因此判据是「**本次要冻的这批快照行**里 `bom_recursive_expand=true` 的数量」，与上一版无关，不需要 diff、不需要二次确认交互。
>
> 由此，「重新发布会把当时的活配置重新冻进去」这一风险的正确拆解是：
> ① 会产生**非法状态**（2 个树页签 → 渲染器 `for…break` 静默取第一个）→ E-7 硬拦；
> ② 会产生**配置错误**（缺 `parent_no` → 满屏空行）→ E-8 检出；
> ③ 行主轴 / 行结构变化 → **用户主动改 `tabType` 的预期后果，不需要任何处置**（原先设想的"发布期提示/二次确认"落在这一档，已判定为噪音，不做）。

## ④ 问题原因 / 报告

### 根因（分层）

**第 1 层 · 判定条件写死、缺 status 维度。**
`ComponentService.assertNotReferencedByCostingTemplate` 的 SQL 只按 `template_kind='COSTING'` 计数，**没有任何 `t.status` 过滤，也不看 `template_component_snapshot` 是否已有冻结行**。

**第 2 层 · 护栏的前提被 task-0806 抽掉了，但护栏没被复审。**
护栏 2026-07-21 写下时，已发布模板的渲染配置确实实时读活表 `component`，所以「改组件 → 核价模板跟着变树」是真的。task-0806 把权威源改成 `template_component_snapshot`（`tab_type` / `bom_recursive_expand` **都在冻结列清单里**），读取收口到 `PublishedTemplateReader`，并把 `refreshSnapshotsByComponent`（H1 自动推送）**整体退役**。前提没了，结论就不再成立。

**第 3 层 · 这道护栏是单向的，本来就拦不住它想拦的事。**
组件侧拦「改成 BOM」，但**模板绑定侧不拦**：`TemplateComponentService.addComponent` 只有 `validateAtMostOneTreeTab`（一个核价模板最多一个树页签），对「把一个 BOM 组件绑进核价模板」放行；且新建组件路径 `componentId == null` 直接 return（`ComponentService.java:411`）。所以「新建一个 BOM 组件 → 绑进核价模板」这条路一直畅通——`COMP-0232`「物料BOM」（`tab_type=BOM`、被核价模板-简易引用）就是活证据。护栏挡住的只是「先有引用、后改类型」这一个方向。

### 证据链（可复跑）

**证据 A —— 护栏代码原文**（`cpq-backend/src/main/java/com/cpq/component/service/ComponentService.java:410-423`）：

```java
private void assertNotReferencedByCostingTemplate(UUID componentId) {
    if (componentId == null) return;            // 新建流程豁免 → 单向护栏的缺口之一
    Number count = (Number) em.createNativeQuery(
            "SELECT count(*) FROM template_component tc " +
            "JOIN template t ON t.id = tc.template_id " +
            "WHERE tc.component_id = :cid AND t.template_kind = 'COSTING'")   // ← 无 status 过滤
        .setParameter("cid", componentId)
        .getSingleResult();
    if (count != null && count.longValue() > 0) {
        throw new BusinessException(400, "该组件已被 " + count.longValue() + " 处核价(COSTING)模板引用，…");
    }
}
```

调用点 `ComponentService.java:105-107`，仅在 `requestedTabType` 归一后等于 `BOM` 时触发：

### 影响面

- **功能面**：22 个组件无法转为 BOM 树页签，且**无任何合法绕过路径**（除非解绑核价模板——而 PUBLISHED 模板本就不允许改 `template_component`，`addComponent` 要求 `DRAFT`）。用户唯一出路是「新建一个一模一样的组件」，凭空制造重复组件与后续维护负担。
- **数据面**：**零污染**。护栏是纯拒绝，不写库，不改渲染，误拦不产生脏数据。
- **架构面**：这是 task-0806「冻结改造」的**收尾遗漏**——凡「以活表配置会外溢到已发布模板」为前提写下的旧校验，都该在 0806 里被重新审一遍。本条是已发现的第一个，**同类还可能有**（见 §⑥ AC-7）。

### 已知限定（不夸大）

护栏并非完全无价值，以下两条**残余真风险**在改动中必须保留处置：

1. **DRAFT 核价模板仍读活表**（`BomTreeRenderService.java:236-241`）。现网 COSTING 侧 DRAFT 恰好 0 张，但机制上一旦新建一张 DRAFT 核价模板绑了该组件，改 `tabType` 就会真串。
2. **重新发布会重新冻结当时的活配置**。已发布核价模板下次 `publish()` 时，`tab_type='BOM'` + `bom_recursive_expand=true` 会被正式冻进新版快照并真实生效。这是 publish 的**正常语义**（用户显式动作、且是严格版本化的题中之义），但 task-0721 当初的顾虑包含这一层，不能装作不存在 → 对应 E-7。

### 为什么测试没拦住

`ComponentServiceTabTypeGuardTest.componentReferencedByCostingTemplate_cannotBecomeBomTab` 是存在的，而且是绿的——但它构造的 COSTING 模板是 **`status = "DRAFT"`**：

```java

```

于是：

- 该测试**永远不会**因为本缺陷变红——它测的是残余真风险那一档，不是误拦那一档；
- 「**已冻结的 PUBLISHED 模板引用 → 应放行**」这条语义**从来没有测试覆盖**（0806 时也没补）；
- 更根本的是，task-0806 的验收清单里没有「复审所有以『活表配置外溢』为前提的旧校验」这一项，属规格级遗漏，非测试执行不力。

## ⑤ 修复方案

✅ **已裁决（2026-08-14）：方案 D 修订版，且原定二期的 `BL-0172` 并入本期一起做。**

### 选定方案（三件事，全部纯后端）

**D-1 · 护栏判定收窄到「未冻结的引用」**（对应 E-1 / E-2 / E-3）

`assertNotReferencedByCostingTemplate` 的计数加上冻结维度：**只统计还会读活表的那些 COSTING 引用**，即
`status ∉ {PUBLISHED, ARCHIVED}`（DRAFT 等）**或** `status ∈ {PUBLISHED, ARCHIVED}` 但 `template_component_snapshot` 零行（D17「未冻结」过渡态）。
计数 > 0 才拒绝，并在文案里点名**具体模板 + 状态**。

> ⚠️ **口径必须同源**（AP-52 教训）：不在护栏里自己再写一遍「什么叫已冻结」。
> `PublishedTemplateReader` 已有 `isFrozen(UUID)`（`:80`），但它是**单张**的，护栏里循环调 = N+1 违规。
> 因此在 `PublishedTemplateReader` 增加一个**批量**判定方法，护栏调它，判定逻辑保持唯一。

**D-2 · `publish()` 补树页签不变量断言**（对应 E-7）

在 `TemplateService.publish()` 落 `persistSnapshotRows` **之前**，对**本次要冻的那批行**断言：
`templateKind='COSTING'` 时 `count(bom_recursive_expand = true) ≤ 1`，违反则 400。
**不与上一版 diff、不做二次确认交互**（理由见 §③ E-7/E-8 下的说明框）。

同一条业务约束今天只存在于 `TemplateComponentService.addComponent:38` 的 `validateAtMostOneTreeTab`，
publish 路径是漏的 —— 本次是把既有约束补到另一个入口，不是新立规则。

**D-3 · 树页签 `$view` 缺 `parent_no` 的显式检出**（对应 E-8，原 `BL-0172`，用户裁决并入本期）

现状 `BomTreeRenderService.java:349-354` 只有一行 `LOG.warnf`，用户侧零提示、表现为满屏空行。改为显式检出。

### 为什么选它

1. **止血面 100%**：D-1 一步解开现网全部 22 个被误拦的组件（含用户手上的 `COMP-0233`）；
2. **判据与 0806 架构同源**：「这条引用是否还会读活表」正是冻结改造的核心语义，不是打补丁；
3. **不碰 publish 的写入主体**：D-2 是在 `persistSnapshotRows` 前加断言，不改冻结写入逻辑本身，与 0806 刚交付的核心路径解耦；
4. **回归面极小**：`ComponentServiceTabTypeGuardTest` 现有用例**一条都不用改语义** —— 它的核心护栏用例造的恰是 `status="DRAFT"` 的 COSTING 模板，正是「至今仍该拦」那一档，天然仍绿；
5. **存量安全已实测**：`cpq_db_0724` 的 5 张 COSTING 模板（活表侧 + 快照侧）**均恰好 1 个树页签，零违规**，D-2 硬拦不会把任何既有模板锁死在「改点别的就再也发不出去」。
