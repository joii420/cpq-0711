## 真正的根因

核价 Excel 的四列都是 `TAB_JOIN_FORMULA`（`[材质元素(总计)]` / `[BOM(总计)]` / `[加工费(总计)]` / `[核价小计1(总计)]`），四个 `tabKey` 与本模板组件**逐一对得上**（已核）。

但求值路径是：

```
ExcelViewService:453  buildTabJoinEffectiveRows(componentDataList, templateId)
  → ComponentDataEffectiveRows.computeScaled(...)
      Pass1: rows = parseRows(cd.rowData); colSums = columnSums(rows)   ← 只从 cd.row_data 求和
```

⇒ **TAB_JOIN 的数据源是 `quotation_line_component_data.row_data`，不是 `costing_card_values`。**

而实查：

```sql
select cd.component_id, c.code, c.name, c.component_type, jsonb_array_length(cd.row_data) 行数
from quotation_line_component_data cd left join component c on c.id=cd.component_id
where cd.line_item_id='b7066093-ebc9-4a78-b1e4-4ca47298b73e';
```

| code | name | type | 行数 |
|---|---|---|---|
| COMP-0010 | 产品 | NORMAL | 1 |
| COMP-0011 | BOM | NORMAL | 4 |
| COMP-0012 | 加工费 | NORMAL | 1 |
| COMP-0013 | 材质元素 | NORMAL | 2 |
| COMP-0014 | 小计 | SUBTOTAL | 1 |

**全是报价侧组件（报价模板『施耐德1』）。核价侧四个组件（`COMP-0016/0017/0018/0019`）一条记录都没有。**

⇒ Excel 列的 `tabKey`（核价组件 id）在 `cdList` 里**一个都命中不了** ⇒ `tabJoinProvider` 空 ⇒ 四列全部取不到 ⇒ 恒 `0`。

**这与核价侧的既有架构一致**：核价侧是**自渲染**（数据落 `costing_card_values`），报价侧才落 `component_data`（见 `task-0712` 的「报价侧 `buildCardValues` 纯读 snapshot_rows vs 核价侧自渲染 = 根因不对称」）。**Excel 的 TAB_JOIN 求值只认后者。**

## 判决性对照（这才是能定性的证据）

| | 有 `component_data` 吗 | Excel 非零单元格 |
|---|---|---|
| **报价侧** Excel（`quote_excel_values`） | ✅ 有（5 条） | 本单 4 行**各 3 个非零** |
| **核价侧** Excel（`costing_excel_values`） | ❌ **0 条** | **全库 11 行 / 5 张单 / 3 个不同核价模板，全部 0** |

⇒ **核价 Excel 视图在这个库里从来没有算出过任何非 0 值**，跨模板、跨单据、跨时间。

## 定性

**独立的既有结构性缺陷，不是 `repair-260911` 的回归，也不是它的遗漏。**

- 不是回归：本次改的是 `evalCrossTab` 的匹配取值，Excel 这条路**根本不经过它**（它只做 `columnSums` 求和，不求值公式）
- 不是遗漏：即使本次一并刷新 Excel 值，数据源对不上，刷了还是 0（**已实测**）
- 修它要动的是「核价 Excel 的取数源」，属架构层面，应单独立项

## 修法方向（初判，未深查，不构成方案）

让核价 Excel 的 TAB_JOIN 从 `costing_card_values`（核价侧的权威渲染结果）取数，而不是从 `component_data`。需要评估：`ComponentDataEffectiveRows` 是报价/核价共用的纯计算器，改它会同时影响报价侧；可能需要在 `ExcelViewService` 按 `viewKind` 分流。
