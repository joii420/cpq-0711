### 4. 过程中规避掉的坑

1. **差点让 AC-4 变红。** 最初的诊断条件是「宿主行取不到值就报」。查 `ComponentCell.tsx:305-310` 发现 `err` 会**直接用 ⚠ 替换数值**，于是 BOM 根行（各列全空）会渲染成 ⚠ 而不是 `0` —— 直接违反 AC-4「根行仍为 0」。改成只在「键整个不存在」时报，并让 `buildHostMatchRow` 给声明过的字段一律建键，把这两种情况分开。
2. **第一版「显式清空」用例是空验证。** 我原本按 AC-6③ 的字面（`INPUT_*`）写，跑实验 B 时**它没变红** —— 因为 `buildResolvedRow` 的 INPUT 分支本来就是 `== null`，`respectExplicitBlank` 只作用于 BASIC_DATA/DATA_SOURCE 分支。追回问题说明 ⑤ 那张表点名的 `buildResolvedRow:1345`，逐行数确认那是 **BASIC_DATA 分支**，才补了真正有鉴别力的断言（实验 B 现在能跑红）。**没做这个实验的话，AC-6 会以「用例全绿」的形态交付一条永远不会失败的守卫。**
3. **没把 `mergedRow` 换成匹配视图。** 它喂的是 `b_field`，A0 明确「不动 b_field 取值链」；换了会外溢且不报错。
4. **递归下传时 `matchRow` 未传就保持 `undefined`**（而不是顺手传 `mergedMatchRow`）—— 否则老调用点的内层 KSUM 匹配键全集会凭空变大，AC-7 的「逐位不变」就不成立了。
5. **`buildHostMatchRow` 的 `formulaCache` 传 `{}`** —— 对齐后端 `resolveRowByFieldName(..., null)`；传 `formulaCache` 会让匹配键吃到本行公式列的算出值，两端立刻分叉。
6. **没有拿 5174 / 5090 验证**（它们服务主仓代码，看不到 worktree 改动 = 假绿）；临时端口用 5092，5091/8093/5090/8091 一个没碰，用完立刻 kill 并确认 5090/5174 仍 200。
