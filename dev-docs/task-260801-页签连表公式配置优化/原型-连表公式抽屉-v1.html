第 4 点「一对一对加色彩区分」· 可行性评估

先说结论：可以做，且成本低（现有 FormulaRichInput 已是 contentEditable + 自绘 DOM，不需要引入编辑器库）。 但有一个必须先避开的冲突。

⚠️ 冲突：颜色这个"通道"已经被占满了

公式里的 [引用] 块现在就是彩色的，而且 5 种颜色都已承载「这个引用合不合法」的语义 （见 formulaSerialize.ts · classifyRefSegment）：

现有颜色含义触发条件
蓝普通跨页签明细引用默认合法路径
黄小计列字段 ∈ subtotalCols
绿页签总计[X(总计)]
紫宿主自身字段tabDef.self
红非法：页签/字段查不到、行键不可比、KSUM 内引宿主列校验失败

所以不能再把「配对关系」也画到块底色上 —— 否则用户看到红色，分不清是"引用非法"还是"某一对的配色"。

✅ 建议方案：只给括号字符上色，不动块底色

维度做法
着色对象只作用于 ( ) 这些文本字符（加粗 + 字色按嵌套深度轮转），块引用仍是底色方块
为什么不撞车两者视觉通道不同：块 = 有边框的底色方块，括号 = 无背景的粗体字符。上方原型里可以直接对照看
光标联动光标停在某个括号旁 → 它和配对的另一半同时加黄底，一眼看出配到哪
错误提示未闭合 / 多余的括号 → 红色 + 波浪线，替代现在那句干巴巴的「括号不平衡」文字
实现成本低。renderInto 里对非块文本节点扫一遍括号即可；已有 formulaBracketCheck.ts 的平衡校验可复用其判定
风险中低。改的是渲染层，不碰 token 序列化，公式语义与保存结果不受影响；但要保证重渲染不打断光标（该组件已有 caretOffset/restoreCaret 机制，沿用即可）

另一种可能的理解（如果我理解错了请指出）

「一对一对」如果指的是把同一个页签的多个引用染成同一色（例如所有 [投料.*] 都是橙色）， 那就与现有语义直接冲突 —— 它会覆盖掉"红=非法"这条最重要的提示。 真要做，得先把合法性提示改走别的通道（如块右上角小图标 / 下划线波浪），代价明显变大。 我按前一种理解（括号配对）做了上面的原型，你定稿时说一声即可。

需要你定稿的点

  1. 左右比例：目前 42% : 58%（左字段 / 右公式）。字段名长的客户可能要 45:55，可调。
  2. 抽屉宽度：1520px。如果常在 1366 宽屏笔记本上用，建议改 90vw 自适应。
  3. 规则提示那块黄色说明：现在常驻右栏底部，占约 100px。是否改成默认折叠、点「?」再展开？
  4. SUMIF 构造器：仍留右栏底部折叠（展开后较高，会把公式框顶上去）。是否改为独立弹层？
  5. 第 4 点：确认是「括号配对着色」还是别的含义。
  6. 试算移除：确认整条移除（含样本卡选择器与逐行结果表），后端 dry-run 端点保留不动。
