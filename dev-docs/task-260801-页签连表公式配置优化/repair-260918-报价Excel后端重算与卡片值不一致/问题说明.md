## ④ 问题原因

### 4.1 根因：同一张单，后端有两个取数源

报价侧 `getExcelView` 调 `buildRowData` 时**不传有效行**（`ExcelViewService.java:162-172`：`costingSide=false ⇒ eff=null`）→ 走 `buildTabJoinEffectiveRows`（`:573-619`）→ `ComponentDataEffectiveRows.compute`，对**组件原始行数据 `quotation_line_component_data.row_data`（下称「草稿纸」）各列直接求和**（`ComponentDataEffectiveRows.java:189-190, 284-294`），SUBTOTAL 页签再拿这些列和代入公式。

而同一系统里另外两条算 Excel 值的路 —— 系统自动生成 Excel 存值（`CardSnapshotService.buildExcelValues` → `buildLineRowData(…, quoteCardValues)`，生产调用点 `:1171`、`:1399` 均传卡片值）与核价侧（`repair-260912` 已改）—— 读的是**正式账 `quote_card_values`**，经 `CardEffectiveRows.parse`（带公式结果与单位换算，`CardEffectiveRows.java:100-105`）。

草稿纸对不上正式账，有两个**独立**缺口叠加：

| 缺口 | 现象（0881 实测） | 出处 |
|---|---|---|
| **(a) 草稿纸里的公式值不对** | 物料 6 行「材料成本」草稿纸 vs 正式账：`0.000066807` vs `0.059191597`；`0` vs `0.463735546`（00144）；`0` vs `1.437983994`（00255）；`0.000802284` vs `0.015491845`（00256）；`0.002538082` = `0.002538082`（00257）；根行 `0` = `0`。6 行中 4 行不同。「回收成本」草稿纸 6 行全 0，正式账合计 `0.317766357` | 即 `BL-0298`（已登记，本任务不修） |
| **(b) 列求和不做单位换算** | 组装加工费「加工费」配了 `unit_source_field=计价单位`，值 KPCS ⇒ 正式账列小计 ×0.001 = `0.03954034733`；草稿纸路径直接加原值 `39.54034733`。`ConfigureSnapshotService.java:1674-1678` 注释写明草稿纸存原值、换算由读方负责，而 `ComponentDataEffectiveRows.columnSums` 没换 | 本任务根因的一部分 |

**三个数逐位推得出**（输出见 `证据/输出/0881-复现-260918-2012.txt` §4~§6）：

- `col_1` = 草稿纸材料成本列和 = `0.000066807 + 0.000802284 + 0.002538082` = **`0.003407173`**
- `col_2` = 草稿纸回收成本列和 = **`0`**
- `col_3` = 产品小计公式（`物料·材料成本 + 物料·材料损耗成本 − 物料·回收成本 + 其他费用(总计) + 产品·管理费 + 组装加工费(总计)`）代入草稿纸列和 = `0.003407173 + 0 − 0 + 0 + 0.003954035 + 39.54034733` = **`39.547708538`**；同一公式代入正式账 = `1.978941064 + 0.085323417 − 0.317766357 + 0 + 0.018550954 + 0.03954034733` = `1.80458942533` → **`1.804589425`**

**(a) 的机制（属 `BL-0298`，仅作背景，未做实验区分）**：建单物化草稿纸时，累计跨页签列小计的 `ConfigureSnapshotService.accumulateColumnSubtotals`（`:1759`）只累加 `instanceof Number`，而物化行里「产品·税率」存为字符串 `"1.13"`（0881 实测 JSON 类型 `string`），未配单位列不会被 `UnitConversion.convertObjectRow` 转成数字 ⇒ `COMP-0001#税率` 在累计表里必然缺席；H85 的公式含「加工费小计 / 税率小计」，其物化值恰为 0，与此吻合。`BL-0298` 原推测的「单趟拓扑序」也可能同时成立。

**为什么只有施耐德模板出错**：它的 Excel 列引用「物料·材料成本 / 回收成本」这类**依赖别的页签小计的公式列**（撞缺口 a），产品小计公式里又含**带 KPCS 换算**的组装加工费（撞缺口 b）；另两个 Excel 组件引用的列不依赖这两种情形，草稿纸值恰好等于正式账。

## ⑤ 修复方案（`D-1` 甲 + `D-2` 返回空白）

**一句话**：报价侧所有「后端算 Excel 列值」的入口，改为按**该行自己的正式账（`quote_card_values`）**解析有效行后求值；正式账不可用的行，这类列返回空，且不写入存值。**不改求值规则、不改前端、不改数据、无迁移。**

| 改动点 | 做法 |
|---|---|
| `ExcelViewService.getExcelView`（报价侧分支） | 与核价侧同法：按行所用模板解析一次模板上下文（`loadEffRowsCtx`，同一请求内按模板复用），逐行 `parseEffectiveRows(li.quoteCardValues, ctx)` 传入 `buildRowData`。正式账不可用 → 该行 `TAB_JOIN_FORMULA` / `CARD_FORMULA` 列置 `null`，其他类型列（产品属性 / 组件字段 / 变量 / 固定值 / 公式 / Excel 公式）按原逻辑。**核价侧分支逐字不变** |
| `ExcelViewService.dryRun`（`/excel-view/dry-run`） | 同上 |
| `ExcelViewService.dryRunTabFormula`（模板级与组件级试算共用） | 未传 `cardValuesJson` 时改用该行 `quote_card_values`；不可用 → `value=null`，`errors` 含固定文案（见 `api.md`）。不再构造 `CardDataProvider(cdList)` |
| `ExcelViewService.exportExcelView` | 无需单独改 —— 兜底行来自 `getExcelView` |
| `CardSnapshotService` 报价侧两处补算（`:1169-1171`、`:1392-1400`） | 该行正式账不可用 → **跳过，不赋值**（保持 `quote_excel_values` 为 NULL）；可用 → 原逻辑。**核价侧（`costingExcelValues`）两处不动** |
| 查询条数 | `getExcelView` / `dryRun` 的逐行查组件数据改为整单一次批量取（复用既有 `ExcelCompDataContext` 预取机制）；模板上下文、模板公式每请求只取一次 |

- **正式账「不可用」的判定**（全部入口同一口径，抽成一个方法）：值为 NULL 或空白 / JSON 解析失败 / 含 `"__cardValueFailed": true` / `tabs` 缺失或为空数组。
