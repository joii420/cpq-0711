## 2. 根因（一句话）

`v_compat_material_master` 把 `ds_quote_material` 映射成老 V6 `material_master` 的形状，
而 **`material_master` 根本没有客户列**（`information_schema` 实查 0 行）。
V425 之后 `ds_quote_material` 的轴是 `(customer_no, material_no)` ⇒ 复合轴被压回单轴，
两个客户的行在视图层合不掉，且 `id = md5('dqm:' || material_no)` 让它们连主键都撞在一起。

## 4. 证伪实验：证明「减少的是重复行，不是掉数据」

用**改前定义内联重建** old 视图，与现视图做双向 `EXCEPT`：

```
old_rows | old_distinct_rows | new_rows | invented_rows | lost_material_no | dropped_distinct_rows
    2731 |              2731 |     2715 |             0 |                0 |                    16
```

- `invented_rows = 0` —— 新视图没有凭空造出任何行
- `lost_material_no = 0` —— 没有丢失任何料号
- `dropped_distinct_rows = 16` —— 恰好等于 16 个跨客户重号

被丢弃的那 16 行**逐个核对**：

```
material_no | n_customers | distinct_physical | distinct_created | distinct_updated
S0001..S0014, T260907-M1, T260907-M2  |  2  |  1  |  2  |  2      （16 行全同此形）
```

⇒ **物理属性 7 列（品名/规格/尺寸/旧料号/类型/单重/生产料号）跨客户完全一致**，
唯一差异是 `created_at` / `updated_at`（各自的导入时刻）。

### ⚠️ 已知且已评估的降级：时间戳

去重后 `created_at` / `updated_at` 取 `min(customer_no)` 那一份。
2026-09-09 全工程扫确认 **8 个 Java 消费点与 3 个依赖视图没有任何一个投影这两列**
⇒ 实际影响为零。哪天有人开始消费它们，这里就是该被重新审的地方（同一段话已写进守卫测试注释）。

## 5. 🔍 排除分析：`v_composite_child_elements` 的 2 组真重复 **不属于 C-1**

第一轮勘察（旧数据，视图 4543 行）在 `v_composite_child_elements` 上按
`(hf_part_no, child_hf_part_no, customer_id, element_name)` 分组发现 7 组疑似重复。
**逐个排除的过程**（结论：其中 5 组是我分组太粗造成的假阳性，剩 2 组是真重复但另有根因）：

### 假阳性 5 组（`S0013` / `0526-2609000002`）
分组键**漏了 `material_part_no`**。该视图输出 `material_part_no`，
`S0013` 的 `Ag` 在 `material_part_no = 00017` 与 `992` 下各有一行 —— 是两条合法的不同数据。
补上 `material_part_no / seq_no / composition_pct` 重新分组后，这 5 组全部消失。
> 🚩 教训：**在有多维度输出的视图上判重，分组键必须取全键**，否则「重复」是自己造的。

### 真重复 2 组（`0526-2609000006` 的 `Ag`(00006, seq 1, 90%) 与 `Ni`(00006, seq 2, 10%)）
全键（含 `material_part_no / seq_no / composition_pct`）完全相同，各 2 行。
**三个候选成因逐个实测排除**：

| 候选成因 | 排除依据（实测） |
|---|---|
| ① `v_compat_material_master` 对该料号扇出 | `SELECT count(*) FROM v_compat_material_master WHERE material_no='0526-2609000006'` → **1 行**。mm 侧无扇出 |
| ② `customer` 表 `code` 重复导致 `LEFT JOIN customer` 扇出 | `SELECT code, count(*) FROM customer GROUP BY 1 HAVING count(*)>1` → **0 行** |
| ③ `v_compat_element_bom_item` 自身重复 | 该视图 **29529 行 / 29529 去重 id** ⇒ 自身零重复 |

⇒ 三个都不是。**根因在别处，不在 C-1 的血缘上。**
⇒ 建议单独登 BACKLOG，🚫 不要挂到 C-1 名下（挂错会让下一个人以为修了 C-1 就好了）。

### 反向确认：C-1 与 elements 视图确实无关
第一轮实测 `SELECT ... FROM v_composite_child_elements WHERE hf_part_no IN (那 6 个料号)` → **0 行**。

## 6. 📌 隐性依赖备案：`ExistingProductService` 的 `DISTINCT ON` 缺 tie-break

`ExistingProductService.java:140 / :157` 两处 `LEFT JOIN v_compat_material_master`
**都没有客户条件**，扇出靠外层 `DISTINCT ON (u.material_no)` 吸收。

实测（改前，新数据）：`ds_quote_customer_part` CUST-0004 侧 4511 行
→ `LEFT JOIN` 后 **4518**（+7 扇出）→ `DISTINCT ON` 收敛 **4509**。

⚠️ 但代表行的选取是
`ORDER BY u.material_no, u.src_created_at, u.customer_product_no` ——
**在扇出行之间没有任何 tie-break**，`product_name` / `spec` 取哪个客户的由 PG 任意决定。

⇒ 修完 C-1 后扇出消失、问题随之消失，**但这条正确性是靠「上游视图没有重复行」才成立的**，
是一条**隐性依赖**，不是这段代码自身的性质。
🚩 谁将来再让 `v_compat_material_master` 出现重号（比如给它加客户维度而忘了改这两处 JOIN），
这里会**第一个静默出错**：不报错、不多行，只是名字和规格串到另一个客户去。

### `id = md5(...)` 未被持久化（三重证据）
1. 对 `public` schema **每一个 `uuid` 类型列**跑
   `WHERE col IN (SELECT md5('dqm:'||material_no)::uuid FROM ds_quote_material)` → **0 命中**
2. 8 个 Java 消费点的投影列里都没有 `id`
3. 3 个依赖视图 `pg_views.definition ~ 'mm\.id'` → **全为 `f`**

⇒ 所以 V435 **刻意不动 id 算法**：改它零收益、有风险。

| `v_compat_material_master-改动前定义.sql` | `pg_get_viewdef` 输出，**只有视图体** | 🚫 **不能** —— 没有 `CREATE OR REPLACE VIEW ... AS` 头 |

⚠️ 这条差别值得单独记一笔：`pg_get_viewdef` 默认**不带** `CREATE` 头。
只备份它的输出，会得到一份**看起来完整、实际跑不了**的「备份」——
而这件事只有在真要还原的那一刻才会发现，那正是最不该出意外的时刻。

`还原-可执行.sql` 已做语法自检：在 `BEGIN; ... ROLLBACK;` 里实跑过一次，
返回 `CREATE VIEW` 成功，回滚后视图仍是 V435 版（2715 / 2715 去重）。
