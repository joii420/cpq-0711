## (a) 为什么不发生 —— 机制已坐实，不是猜的

`ConfigureSnapshotService.snapshotLines(..., skipRowsWithSnapshot=true)`（saveDraft 走这条）
的契约原文：**「复用行已有完整 `snapshot_rows` 时整行跳过 expand + materialize」**。
0625 的产品页签正好 6 行 `snapshot_rows` 齐全 ⇒ **整行跳过** ⇒ 不重算。
这是首存性能优化（`cpq-import-firstsave-perf-bottlenecks`）的既有行为，**不是本次改动引入**。

## 🔴 由此暴露的真问题：`D-3` 写的自愈路径**不存在**

`D-3` 裁决「第③层 55 张报价单不批量刷新，**靠用户下次「刷新基础数据」自愈**」。
但两条路都已实测不成立：

| 路径 | 实测 | 出处 |
|---|---|---|
| 「刷新基础数据」(`refresh-snapshot`) | **不重建报价侧卡片值** | `D-20` |
| 「保存草稿」(`saveDraft`) | **整行跳过**，不重算 | 本条，2026-09-09 |

⇒ **存量单的第③层（已物化 `snapshot_rows` / `row_data`）目前没有任何自愈路径。**
用户 2026-09-08 已裁决「存量单不管了，新建单测试和正确就行」⇒ **不是交付阻塞**，
但 `D-3` 那句「靠下次刷新自愈」**是错的，必须改口**，否则下一个人会按它做规划。

## (c) 为什么「0」不算证据

`filterEditRowsToNewBaseRows` 第一行守卫就是
`if (editRowsByComp == null || editRowsByComp.isEmpty()) return;`，
而 saveDraft 先把卡片值置 NULL ⇒ **按构造走不到记录点**。
再查：`[edit-rows 失配]` 这条 `LOG.warnf` 在**全部历史日志里从未响过一次**。
⇒ 它的沉默既可能是「确实没失配」，也可能是「它从来不响」，两者无法分辨。
🚫 **不许把它记成通过**。AC-18 的实际保护力全部来自 **(b)**。
