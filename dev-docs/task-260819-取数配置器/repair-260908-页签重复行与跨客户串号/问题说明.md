## ① 问题描述

**用户原话（2026-09-08）**：

> 报价单查询到的产品卡片的各个页签的重复行越来越多：QT-20260908-0624 - 草稿，分析这张报价单的 SQL 执行是缺少了什么条件导致的，会不会与客户编号有关。
> 并且 物料组件 不需要 ANY(:total_material_no)，只需要当前产品卡片的销售料号的一行数据就可以。

**客观现象**：报价单产品卡片的各页签出现本不该出现的行，且**单子里产品越多、BOM 越深，多出来的行越多**。

⚠️ **这不是显示问题，是数据正确性问题**：另一个客户的行**静默**混进卡片，用户从界面上看不出这一行属于别人。
`BL-0229` 原文记录的爆发形态是「提交返 **422** 行键重复」，但那是**运气好被提交守卫拦住**了 ——
带版本的表（`ds_quote_element_bom` / `ds_quote_material_bom`）不一定有这道守卫。

## ④ 问题原因 / 报告

### 根因（两个独立缺陷，实测贡献可分离）

```
闭包料号数 14  →  「产品」页签现状返回 28 行（应为 1 行）
                  ├ 加 customer_no 谓词后  14 行   ← 缺陷①去掉的那一半
                  └ 只取当前卡片料号       1 行   ← 缺陷②去掉的那一半
```

#### 缺陷① · 取数视图主表 `WHERE` 无客户谓词

`SemanticCompiler.applyFullScope()`（`cpq-backend/src/main/java/com/cpq/builder/compiler/SemanticCompiler.java:896`）
只发两类谓词：核价侧的 `is_current` / `:versionFilter`，以及 `<别名>.<轴列> = ANY(:total_material_no)`。
**客户维度一条都没有。**

以「产品」页签冻结快照原文为例：

```sql
FROM ds_quote_material dqm
  LEFT JOIN ds_quote_customer_part dqcp
         ON dqcp.material_no = dqm.material_no AND dqcp.customer_no = :customerCode
WHERE dqm.material_no = ANY(:total_material_no)     -- 🚫 主表一行都不过滤
```

`:customerCode` **只用在 LEFT JOIN 客户料号上**。实测 `S0001` / `S0004` / `S0008` / `S0012`
**100% 跨 `CUST-0001` 与 `CUST-0004` 双客户存在**（例：`S0001` 在 `ds_quote_material` 里
`CUST-0004 铆钉` + `CUST-0001 铆钉` 两行）⇒ **每个料号必然翻倍**。

#### 缺陷② · 「主件」页签不该用整单 BOM 闭包

`:total_material_no` 是整单闭包（4 成品 + 10 直接子件 = 14）。
渲染时 `ComponentDriverService` 会把 outer `hfPartNos` **加宽到「这张卡片自己的 BOM 闭包」**
（单卡路径 `_widenedHfPartNos = materialsByRoot.get(partNo)`，`ComponentDriverService.java:426`；
合桶路径 `widenedPartNos = partNos ∪ totalMaterialNo` + `rootsByMaterial` 回分，`:744`）。
该加宽是 `task-260819` D-58 有意为之 —— 因为多数页签**确实需要子件行**。

但「主件」页签描述的是**卡片自己那个成品**，加宽让它多出了后代料号的行。

### 🔑 关键结构事实：`material_no` 在两族表里不是同一个东西

（2026-09-08 逐表查 `information_schema.columns` 实测，非推断）

| 族 | 页签（QUOTE 方言 16 个） | 锚点表 | 表里的 `material_no` 是 | 子件维度在哪一列 |
|---|---|---|---|---|
| **A** | **主件**（1 个） | `ds_quote_material` | **卡片自己的成品料号** | 无（成品自身维度） |
| **B** | BOM树 / 外购件 / 零件 | `ds_quote_material_bom` | **父件**（多级 BOM 里就是子件自己） | `input_material_no` |
| **B** | 材质元素 | `ds_quote_element_bom` | 被分析的那个料号 | `material_part_no` |
| **B** | 费用类 ×11 | 各费用表 | 成品料号 | `input_material_no` / `sub_component_no` / 无 |

⇒ **B 族必须保留闭包**：多级 BOM 里 `C1 → C2` 这条边的 `material_no` 是 `C1` 不是成品，
收窄到成品会把树砍成只剩第一层；材质元素同理（成品自己通常没有材质构成，有构成的是投入料）。
⇒ **半成品自己的费用行仍要上卡**（用户 2026-09-08 裁决，见 `D-1`）。

## ⑤ 修复方案

> 本节只写**闸门 A0 裁决通过的那一个方案**。裁决台账见文末 `D-1`~`D-5`。

### 总览：两个缺陷都收口在「编译产物 → 落盘 → 驱动层消费」这一条链上

```
SemanticCompiler  ──①客户谓词──►  sql_template  ──►  builder_config / sql_views_snapshot
                  ──②axisScope─►      （元数据）  ──►  ComponentDriverService 两处加宽点
SqlViewExecutor   ──②'硬阻断──►  :customerCode 未绑定即 400
```

### B-1 · 编译器补客户谓词（缺陷①）

在 `SemanticCompiler.applyFullScope()` 内新增：

```java
if (cols.contains("customer_no")) {
    where.add(alias + ".customer_no = :customerCode");
    c.requiredVars.add("customerCode");
}
```

- 该方法有 **3 个调用点**，写在方法内即全覆盖：
  锚点 `WHERE`（`:344`）· SUB 相关子查询（`:780`，局部 `where`）· GRAIN 目标（`:815`，INNER JOIN 后进 `anchorWhere`）
- **按列存在性触发**，天然只对 `ds_quote_*` 生效 ⇒ 核价两方言零改动（`ds_cost_*` 45 张表无此列）
- 🚫 **刻意不碰 `ensureLeftJoin()`（`:751`）** —— LOOKUP 边的客户维度走 `fixedPredicate` 与列对列连接键
  （客户维度形态③），加进 `WHERE` 会把 `LEFT JOIN` 收成 `INNER`、静默丢行

#### B-1b · `NARROW` 桥的子查询同样要加（2026-09-08 呈报期补，**只改 `applyFullScope` 覆盖不到**）

`SemanticCompiler:585-587` 把料号桥**直接拼进 `anchorWhere`**，不走 `applyFullScope`：

```sql
WHERE dcbm.production_no IN (
        SELECT dqm.production_no FROM ds_quote_material dqm
        WHERE dqm.material_no = ANY(:total_material_no))    -- 🚫 内层 ds_quote_material 无客户过滤
```

内层这张表**有 `customer_no` 且没被过滤**。同款判据（桥的 target 物理表含 `customer_no` ⇒ 子查询 `WHERE` 追加
`AND <sub>.customer_no = :customerCode`）。

⚠️ **实测当前 0 行影响**（`AC-16` 因此必须写成**结构断言**，不能写成数据断言）：
`ds_quote_material` 里 16 个料号跨客户，但 `count(distinct production_no) > 1` 的组数 = **0**；
且 `x IN (SELECT ...)` 是**集合成员判定**，子查询里多出重复值不会让外层翻倍。
⇒ **结构隐患不是活故障。拿数据验它会得到一个恒绿的判据**（`task-260907` 的「验了恒为空的样本」同型）。

### B-2 · `:customerCode` 未绑定硬阻断（B-1 的必要配套）

`SqlViewExecutor.rewriteNamedParams()`（`:626-652`）现行约定是**未绑定的占位符替换成字面量 `NULL`**。
加了 `customer_no = :customerCode` 之后，任何没提供 `customerCode` 的执行路径会让
`customer_no = NULL` 恒为 false ⇒ **整个页签返 0 行**。

改为与 `:total_material_no` 同款硬阻断（该分支就在同一方法 `:637-646`，注释原话
「避免 `x = ANY(NULL)` 静默返回 0 行伪装成"无数据"」）：`customerCode` 未绑定即抛 400。

🔎 **已核实不受影响的三条路径**（它们各自做字面量替换，不经 `rewriteNamedParams` 的未绑定分支）：
`BuilderService.bindLiterals():384`（`/preview`）· `QuoteViewValidationService:194` · `CostingTreeSqlValidator:62`。
**仍需实测确认**（`AC-5` 的反向断言）。

### B-3 · 编译产物带 `axisScope`（缺陷②）

- `CompileResult` 新增字段 `axisScope`，取值 `SELF` / `CLOSURE`
- `SemanticCompiler`：`tabType` 等于 `ROOT_SOURCE_TAB_TYPE`（`"主件"`，`:148`）⇒ `SELF`；其余 ⇒ `CLOSURE`
- **三个方言都产出该声明**（口径统一、未来可用），但**只有报价侧驱动层消费它**（见 `D-2`）

### B-4 · `axisScope` 落盘与读回

- 写：`BuilderService.save()` 把 `axisScope` 并进 `component_sql_view.builder_config` jsonb（`:820-826` 附近）
- 写：`ComponentSqlViewService` 冻结快照时把 `axis_scope` 写进快照条目（与 `scope` / `required_variables` 同级）
- 读：`ComponentSqlViewService.lookup*`（`:361` / `:393` / `:479`）把 `axis_scope` 带出给调用方
- 🔑 **无 DDL** —— 两处都是既有 jsonb 列加键
- 🔑 **缺键 ⇒ 按 `CLOSURE`**（= 现状），存量零回归

### B-5 · 驱动层按 `axisScope` 决定要不要加宽

`ComponentDriverService` 两处加宽点各加一个分支，`SELF` 时不加宽：

| 位置 | 现状 | `SELF` 时 |
|---|---|---|
| 单卡路径 `_widenedHfPartNos`（`:426`） | `materialsByRoot.get(partNo)`（该卡闭包） | `null` ⇒ 下游退化为 `List.of(partNo)` |
| 合桶路径 `widenedPartNos`（`:744`） | `partNos ∪ totalMaterialNo` | `partNos`（本桶根料号集合，`rootsByMaterial` 回分照常正确） |

### B-6 · 存量重编译 + 快照对齐（第①②层）

**不新增接口** —— 扩展**已有的** `POST /api/cpq/config-center/refresh-all-snapshots`
（`ConfigCenterResource:126`，`SYSTEM_ADMIN`，已自带 `confirm=false` 预览零写入 / `confirm=true` 执行 + `operation_log` 审计）：

1. 新增可选 body 字段 `recompile`（缺省 `false`，**行为逐位不变**）
2. `recompile=true` 时，先按各视图的 `builder_config` 重放 `SemanticCompiler`，
   写回 `component_sql_view.sql_template` + `builder_version`
3. 再走既有 `TemplateService.forceRealignSnapshots(...)` 把实时视图推进 5 个 `PUBLISHED` 模板的冻结快照

🚨 **B-6 的执行属 `CLAUDE.md §3.2`「契约销毁」边缘**（改写已应用到共享库的 28 个视图 + 5 个模板快照）：
