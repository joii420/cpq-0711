## 1. 背景与目标

### 1.1 要解决什么问题（承接自前身 §2.1，事实未变）

组件的取数视图（`component_sql_view.sql_template`）**是裸 SQL 文本**，在「组件管理 → SQL 视图」抽屉的一个 TextArea 里手敲，保存时只跑 dry-run（EXPLAIN）。实际全部由 Agent 按 `dev-docs/rule-260724-组件模板配置/AGENT-配置入口.md` 手写。

四个痛点：

1. **业务/实施人员完全无法自助** —— 配一个客户模板必须找 Agent 或开发，客户模板一改就要重新排期。现网 **157 个组件 / 13 个客户目录**，且随客户持续增长。
2. **隐性铁律极多，写错不报错只出错数** —— `hf_part_no` 驱动键别名、业务列 `_` 前缀、tabType→V6 表映射、版本化表禁进带 `is_current` 的 `LEFT JOIN ON`（写错 → 运行期列索引越界，dry-run 查不出）、BOM 闭包三铁律（漏去重 → 页签小计翻倍且静默）、价格策略必 `LEFT JOIN` 且禁 `COALESCE(...,0)`。
3. **视图列名 ↔ 字段 `default_source.path` 要逐字对齐**，差一个全半角就取不到值，**后端不强校验**（仅软告警）—— 当前最高频的静默故障源。
4. **dry-run 只能查语法与禁表**，查不出「语法对但运行期返 0 行」—— 而这正是页签空白的主要成因。配完无法自证正确，必须建一张报价单才能验。

### 1.2 目标（承接自前身 §2.2，待本轮复核）

- 实施顾问（**不写 SQL**）能在界面上通过拖拽独立配出报价侧页签的取数，并**当场用真实数据验证**，全程不接触表 / JOIN / 别名 / SQL 概念。
- 配置器产出的组件与现网 Agent 手写版**渲染结果逐行等值**（golden 用例把关）。
- 铁律由生成器保证：用户**无法**配出违反铁律的视图。
- 「视图列 ↔ 组件字段 ↔ 绑定路径」三者永不失配（同一次保存原子产出）。

### 1.3 不做会怎样

配组件的能力永久绑定在 Agent 身上；客户模板的交付节奏受排期约束；上述四类静默故障持续按现有频率发生（`RECORD.md` 里已有多起「配完页签空白 / 小计翻倍 / 价格静默按实时价」的返修记录）。

### 3.1 编译产物正确性

**AC-1（单点）材质元素基础配方 + 价格策略**
前置：新建组件，页签类型选「材质元素」。
操作：拖入 材质名称 / 元素名称 / 组成含量 / 损耗率 / 毛用量 / 元素单价 六列，勾「材质名称」为行键 → 查看生成的 SQL。
断言：SQL 同时满足 ——
① 含 `AS hf_part_no`，其表达式为 `ebi.material_no`；
② 业务列别名均形如 `_<来源简称>_<原列名>`；
③ 元素单价与货币两列别名为 `元素单价` / `货币`，**不带 `_` 前缀**；
④ 含 `LEFT JOIN f_material_element_price(:customerCode, :priceBaseDate) cep`（**不是** `f_customer_element_price`），别名逐字为 `cep`；
⑤ JOIN 条件为**双条件** `cep.element_code = ebi.component_no AND cep.material_no = ebi.material_no`，其中 `cep.material_no` 与 `hf_part_no` 表达式**逐字一致**；
⑥ 全文**不含** `COALESCE(` + `,0)` 形式的价格兜底；
⑦ `ebi.is_current` / `ebi.system_type` 出现在顶层 `WHERE`，**不在任何 `JOIN ... ON` 内**。

**AC-2（单点）三件套由同一次保存原子产出**
> 🔄 **③ 已修正（D-41，2026-08-21）**：原断言 `row_key_fields = ["材质名称"]`（单项）**写错了**。
> 按 D-20 实测口径，材质元素页签的行键是「材质名称 + 元素名称」**两项**（元素名称在图里节点级默认即带 `ROW_KEY`）。
> 角色纯图派生（AC-47/48）与单项断言不可兼得 —— 以图派生为准，本条断言改为**两项**。
前置：AC-1 的配置。
操作：点保存 → 查库 `component` 与 `component_sql_view`。
断言：① `fields[]` 恰好 7 项（6 列 + 价格策略带出的元素列）；② 每项 `default_source.path` 等于 `$<视图名>.<该列的视图列名>`，**逐字相等，0 处失配**；③ `row_key_fields = ["材质名称"]`；④ `data_driver_path = $<视图名>`；⑤ `component_sql_view.builder_config` 非空、`builder_version` 有值。

**AC-3（单点）子件闭包的三条铁律**
前置：AC-1 的配置。操作：勾「子件数据也要」→ 查看 SQL。
断言：① 含 `WITH RECURSIVE`；② 递归项用 `UNION` 而**非** `UNION ALL`；③ 含按 `(root_no, node_no)` 二次去重的 CTE（`GROUP BY root_no, node_no`）；④ 主查询用 `LEFT JOIN` 接闭包且 `hf_part_no` 表达式变为 `COALESCE(cl.root_no, ebi.material_no)`；⑤ 顶层 `FROM` 仍是裸表 `element_bom_item`；⑥ 价格策略的 `cep.material_no` **同步**变为 `COALESCE(cl.root_no, ebi.material_no)`。

**AC-4（单点）查名连线自动生成，界面不出现 JOIN 字样**
前置：材质元素页签。
操作：依次拖入「材质料号 ▸ 材质名称」「元素 ▸ 元素名称」；再切到零件页签拖「工序号 ▸ 工序名」。
断言：① 材质名称列表达式为 `COALESCE(mr.name, mm2.material_name)`，且 SQL 自动出现 `LEFT JOIN material_recipe` 与 `LEFT JOIN material_master`；② 元素名称自动接 `LEFT JOIN element el ON el.element_code = ebi.component_no`；③ 工序名自动接 `LEFT JOIN process_master`；④ 同一维表被两个码列展开时，SQL 中该表**只出现一次**或使用互不冲突的别名，**无重复 JOIN、无别名冲突**；⑤ 配置器界面（含字段面板、已选列、体检区）全文**不出现「JOIN」四个字母**。

**AC-5（单点）附属源编译为相关标量子查询，行数不翻倍**
前置：材质元素页签，已拖入 3 列，预览行数记为 N。
操作：拖入「物料BOM（材质边）」组的「组成数量」→ 预览。

> 🚫 **不按原始 key 逐字比**（D-44）：`driverRow` 的 key 是视图列别名，而 D-13 裁决配置器列名一律带来源前缀，两边 key 天生不同。

```sql
-- ① 节点：17 张导入 Sheet + 5 张查名维表 + 1 个表函数
CREATE TABLE semantic_node (
    id               UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    node_key         VARCHAR(80)  NOT NULL,          -- ELEMENT_BOM_ITEM
    display_name     VARCHAR(200) NOT NULL,          -- 物料与元素BOM
    node_kind        VARCHAR(20)  NOT NULL,          -- SHEET | LOOKUP | FUNCTION
    physical_table   VARCHAR(120),                   -- element_bom_item（FUNCTION 为空）

    anchor_expr      VARCHAR(200),                   -- ebi.material_no  → hf_part_no
    grain_columns    TEXT[]       NOT NULL DEFAULT '{}',    -- {material_part_no, component_no}
    fixed_predicate  TEXT,                           -- customer_no = :customerCode（查名维表用）
    func_signature   TEXT,                           -- f_material_element_price(:customerCode, :priceBaseDate)
    dialect          VARCHAR(20)  NOT NULL DEFAULT 'QUOTE',  -- QUOTE | COSTING | BOTH ← D-19，二期填核价侧靠它
    -- ↓ 2026-08-21 补：api.md §1.1 已声明但草案漏列，后端实现时补齐
    short_name       VARCHAR(40),                    -- Sheet 简称，视图列名 _<简称>_<列名> 的构成部分（D-13）
    discriminator    TEXT,                           -- 判别式 price_type='...'，AC-43 要求展示
    source_handler   VARCHAR(80),                    -- 对应的 Q*Handler，AC-36 双向对账用
    note             TEXT,
    UNIQUE (node_key, dialect)
);

-- ② 节点的列
CREATE TABLE semantic_node_column (
    id            UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    node_id       UUID NOT NULL REFERENCES semantic_node(id) ON DELETE CASCADE,
    db_column     VARCHAR(120) NOT NULL,             -- component_no
    display_name  VARCHAR(200) NOT NULL,             -- 元素
    data_type     VARCHAR(20)  NOT NULL,             -- TEXT | NUMBER | DECIMAL
    is_code       BOOLEAN NOT NULL DEFAULT false,    -- .asCode()
    roles         TEXT[]  NOT NULL DEFAULT '{}',     -- {PART_NO,PART_NAME,ROW_KEY,SORT} ← D-25
    sort_order    INT NOT NULL DEFAULT 0,
    UNIQUE (node_id, db_column)
);

-- ③ 边
CREATE TABLE semantic_edge (
    id             UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    from_node_id   UUID NOT NULL REFERENCES semantic_node(id),   -- 故意 RESTRICT：AC-54
    to_node_id     UUID NOT NULL REFERENCES semantic_node(id),
    edge_kind      VARCHAR(20) NOT NULL,             -- GRAIN | SUB | JOIN | LOOKUP | PRICE
    cardinality    VARCHAR(20) NOT NULL,             -- MANY_TO_ONE | ONE_TO_MANY
    fallback_order INT,                              -- 多源 COALESCE 顺序（唯一性范围见下方索引）
    coalesce_group VARCHAR(40),                      -- 同组 = 一条逻辑边（边数按此合并计数 = 19）
    -- ↓ 2026-08-21 补：D-32 的 THIN 判据落库，避免每次 GET 现查触发 O(边数) 次探测
    assert_status      VARCHAR(10),                  -- PASS | FAIL | THIN | NA
    assert_sample_rows INT,                          -- 样本行数，< 30 判 THIN
    note           TEXT,
    UNIQUE (from_node_id, to_node_id, edge_kind),
    CONSTRAINT chk_card CHECK (cardinality IN ('MANY_TO_ONE','ONE_TO_MANY'))
);
-- ⚠️ 2026-08-21 修正（草案原写 (from_node_id, fallback_order)，**错了**）：
--    实测 E06(→材质库) 与 E08(→元素库) 同属 from=物料与元素BOM 且 fallback_order 都是 0，
--    但分属**两个不同的 COALESCE 组**（材质名 / 元素名），按原范围会互相打架、种子灌不进去。
CREATE UNIQUE INDEX uq_edge_fallback ON semantic_edge(from_node_id, coalesce_group, fallback_order)
    WHERE fallback_order IS NOT NULL AND status = 'ACTIVE';

-- ④ 边的连接键（支持 .and() 多组）
CREATE TABLE semantic_edge_key (
    id            UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    edge_id       UUID NOT NULL REFERENCES semantic_edge(id) ON DELETE CASCADE,
    left_column   VARCHAR(120) NOT NULL,             -- material_no
    right_column  VARCHAR(120) NOT NULL,             -- finished_material_no
    seq           INT NOT NULL DEFAULT 0,
    UNIQUE (edge_id, seq)
);

-- ⑤ 页签视图（6 类页签 → 7 行：费用类占 2，见 D-34）
CREATE TABLE semantic_tab_view (
    id             UUID PRIMARY KEY DEFAULT gen_random_uuid(),

    switches       TEXT[] NOT NULL DEFAULT '{}',     -- {CLOSURE}
    dialect        VARCHAR(20) NOT NULL DEFAULT 'QUOTE',
    UNIQUE (tab_type, variant_key, dialect)          -- ← 原为 (tab_type, dialect)，D-34 放宽
);

-- ⑥ 视图可用节点（主源 / 附属源）

    add_dims    TEXT[] NOT NULL DEFAULT '{}',        -- ← D-26 必须挂这里，见下

-- ⑦ 页签级的列角色覆盖（D-35 实测新增）

CREATE TABLE semantic_tab_view_column (
    id           UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    view_id      UUID NOT NULL REFERENCES semantic_tab_view(id) ON DELETE CASCADE,
    column_id    UUID NOT NULL REFERENCES semantic_node_column(id) ON DELETE CASCADE,
    roles        TEXT[] NOT NULL DEFAULT '{}',   -- 覆盖 semantic_node_column.roles
    sort_order   INT NOT NULL DEFAULT 0,
    UNIQUE (view_id, column_id)

```

**三个建模判据（都不是风格问题，写错就是 bug）**

| 判据 | 为什么 |
|---|---|
| `add_dims` 挂 `semantic_tab_view_node`，**不挂**节点或边 | D-26 那个真 bug 的根因正是「附属源照抄了 Sheet 自身维度」。它表达的是「该附属源**在这个页签里**相对主源额外增加的维度」= (页签 × 节点) 的属性。挂错表 = 把已修掉的 bug 固化进 schema，且 CI 发现不了。<br>已知实数：零件页签的电镀费用 `{费用类型}`、外购件页签的组成件其他费用 `{要素}`，其余为空 |
| `semantic_edge.from/to` 用 **RESTRICT** 外键（不是 CASCADE） | AC-54 要求「删掉仍被引用的节点必须在**库层**崩」。CASCADE 会静默连带删边 —— 那正是最坏情况 |
| `dialect` 现在就建，不等二期 | D-19 已定二期填核价侧 17 页签声明。留了这列，二期是**插行**；不留，二期是**改表 + 迁移存量** |
| `roles` 是**两层**：节点级默认 + 页签级覆盖（第 ⑦ 张表） | D-35 实测：同一字段在不同页签担任的角色**确实不同**，且是真实语义差异 —— 主件页签的行身份**就是**销售料号（`PART_NO`），其他页签的行身份是子件/元素/工序，销售料号只是归属维度（`ROW_KEY`）。<br>定稿原型本来就是两层：`SHEETS.cols` 的第 4 个元素 = 节点级默认（如 `项次→SORT`），`TABDEF.codeCols/extra` 的 `r:[...]` = 页签级（如主件的 `销售料号→PART_NO+ROW_KEY`）。表结构照此 1:1 落地即可 |
| `variant_key` 让「一个页签类型 → 多个视图声明」，**而不是新增页签类型** | D-34 费用类分立。走新增 `tab_type` 的话要动后端 `VALID_TAB_TYPES`（6→7）与 `BomNodeTypeResolver` 的节点类型判定 —— 那是**报价单树的渲染契约**，代价远大于此。页签类型仍是 6 类不变。<br>附带好处：`onlyVariant` 这类「某列只属于某个数据来源」的条件字段**不需要了** —— 每个 variant 是独立一行，列集合各挂各的 |

**与原型声明的映射对照**（验收 AC-51 时逐项比对用）

| 原型里的写法 | 落到哪 |
|---|---|
| `node("物料与元素BOM").table("element_bom_item")` | `semantic_node.display_name` / `.physical_table` |
| `.scope(FULL)` | `semantic_node.scope` |
| `.grain("material_part_no","component_no")` | `semantic_node.grain_columns` |
| `.anchor("ebi.material_no")` | `semantic_node.anchor_expr` |
| `.col("component_no","元素",TEXT).asCode()` | `semantic_node_column` 一行（`is_code=true`） |
| `edge(A).to(B).on(x,y).cardinality(MANY_TO_ONE).fallbackOrder(0)` | `semantic_edge` 一行 + `semantic_edge_key` 一行 |
| `.and("material_part_no","code")` | `semantic_edge_key` **第二行**（`seq=1`） |
