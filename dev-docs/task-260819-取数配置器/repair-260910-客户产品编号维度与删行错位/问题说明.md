## ④ 问题原因 / 报告

### 4.1 根因（两个症状同源，一条链）

**根因：取数视图的 JOIN 谓词没有覆盖对端表的真实行粒度。**

`ds_quote_customer_part` 的行粒度是 **`(customer_no, customer_product_no)`**，而「产品」组件视图 `builder_221dc7668ab6` 生成的 JOIN 只给了 `(material_no, customer_no)`：

```sql
LEFT JOIN ds_quote_customer_part dqcp
  ON dqcp.material_no = dqm.material_no AND dqcp.customer_no = :customerCode
```

⇒ 少一个维度，左表一行被放大成右表 N 行。

**为什么编译器没生成这个谓词**：语义图**知道**这张表的粒度 —— `QuoteRegistry.java:89-96` 里

```java
SheetDef.unversioned("CUSTOMER_PART", "客户料号", "ds_quote_customer_part", 2,
        List.of("customer_no", "customer_product_no"), …)
//                ↑ groupKey 两列都声明了
col("customer_product_no", "客户产品编号", "SUBDIM", …)   // 是 SUBDIM
```

`customer_no` 这个 SUBDIM 有运行时变量 `:customerCode` 可绑（`RuntimeContext.toNamedParams():156`），
而 **`customer_product_no` 这个 SUBDIM 在整个运行时上下文里没有任何变量可绑** ——
`RuntimeContext` 的占位符白名单只有 `customerId / customerCode / customerCategory / productCategoryId / quotationId / userId / userRole / lineItemId / compositeType / partVersion`。
⇒ 编译器**无从收窄**，只能生成一个不完整的 JOIN。

📌 该视图是配置器产物（`builder_version = 1`，`builder_config` 仅 `{dialect: QUOTE, tabType: 主件, axisScope: SELF}`），
**JOIN 完全由语义图求解器推导**，不是人手写的 ⇒ 手改 `sql_template` 会在下次重新生成时被覆盖。

### 4.2 症状 2（删错行）—— 🚨 **根因尚未定位（2026-09-10 主线自我更正）**

> 🚨 **本节曾写过一版错误的根因，已作废。作废的内容与作废的理由都保留在下面，因为「为什么会写错」比「写错了什么」更值得下一个人看。**

#### ❌ 已作废的机制（v1，写于 2026-09-10 立项时）

原文断言：`rowFingerprint` 只取 `row_key_fields` 的列 ⇒ 放大出的 4 行 `fp` 逐字节相同 ⇒
身份只能靠 `effKey` 的 `#N` 按**数组位置**消歧 ⇒ 视图排序不稳定 ⇒ 墓碑指向别的行 ⇒ 删错行。

**作废依据（实查，三条互相独立）**：

| # | 实查事实 | 出处 |
|---|---|---|
| ① | `rowFingerprint` 是**两段拼接**：`rowKeyFieldNames` 段 + **driverRow 全部键按升序**段 ⇒ 它是**整行内容指纹**，不是只取行键字段 | 前端 `deletedRows.ts:31-46` · 后端 `DeletedRowKeys.java:102-117`（两侧同构） |
| ② | **2026-07-14 的删错行修复已把匹配改成「按 fp 单键」**，`effKey` **不再参与匹配** —— 前后端注释均明写「effKeys 参数保留仅为签名兼容」 | `DeletedRowKeys.keepMask` javadoc · `deletedRows.ts` `keepRow` 注释 |
| ③ | 库里**真实存量墓碑**的三条 `fp` **各不相同**：`∅B17-DUP-0910-1…` / `∅B17-DUP-0910-2…` / `∅B18-BIND-0910B…`（客户产品编号已进 fp），而它们的 `effKey` 才是 `S0004#0/#1/#2` | `quotation_line_component_data.deleted_row_keys` 实查 |

⇒ 这几行的 driverRow 内容**本就互不相同**，`fp` **能**区分它们；排序不稳定也**不会**通过 `effKey` 造成删错行。
**建立在 v1 之上的「行身份 A+B+C 三层」方案随之失去依据。**

#### 🔍 当前的工作假设（v2，⚠️ **未证实，不许据此写代码**）

排序不稳定可能**仍是**元凶，但机制在**显示层**而非匹配层：
删除后重新查询时堆物理序变化 ⇒ 剩余行的**渲染顺序**跟着变 ⇒
用户看到「我点的第 2 行还在（内容已换人）、第 4 行没了」⇒ 判断为删错行，而**数据层可能删对了**。

若 v2 成立，修法收敛为 **只做确定性排序**，`__row_uid` 与行键补维度都不需要 ——
改动面从「19 个主文件的协议级改动」降到「编译器一处」。

🚫 **v2 是假设，不是结论。** 已派 S3 测试员在**改动前**如实复现：
记录点击的是哪一行、消失的是哪一行、墓碑实际写入的 `fp` 与 `effKey`、以及每行 driverRow 的全量键值。
**拿到实测再重走闸门 A0。**

#### 📌 v1 为什么会写错（与 §4.5 是同一个病）

`rowFingerprint(rkf, driverRow)` 的**函数签名**看起来就是「按 rkf 算指纹」，
⇒ 主线**按签名推断了语义**，没有打开函数体，也没有打开任何一条真实墓碑数据看一眼。
**三条证伪材料（函数体 / javadoc / 库里的真实 fp）任意一条都能在 30 秒内拦下这个错误**，而当时一条都没查。

## ⑤ 修复方案（闸门 A0 用户裁决，2026-09-10）

> 本节只记**裁决通过**的方案。候选对比过程按规则不入档。

### 5.1 取数维度 —— 新增运行时占位符 `:customerProductNo`

**思路**：`customer_product_no` 是语义图已声明的 SUBDIM，缺的只是"绑什么值"。
仿照 `SqlViewExecutor` 里**现成的** `enrichCustomerCode` / `enrichPriceBaseDate` 同款模式——
从 `namedParams` 里**已有的** `:lineItemId` 反查 `quotation_line_item.customer_part_no` 并补全。

⇒ 🚫 **不需要改 `RuntimeContext` 的 7 个构造点**（`toNamedParams()` 已经放了 `lineItemId`）。

**改动点**：

| # | 文件 | 改什么 |
|---|---|---|
| B-1 | `SqlViewExecutor.java` | 新增 `enrichCustomerProductNo(namedParams)`，在 `:349/:350` 与 `:424/:425` 两处调用点与既有两个 enrich 并列 |
| B-2 | `SemanticCompiler.java` | CUSTOMER_PART 参与 JOIN 时，在 **`LEFT JOIN … ON`** 上追加 `AND <别名>.customer_product_no = :customerProductNo` |
| B-3 | `BuilderService.bindLiterals()` | `/preview` 走字面量替换、不经 enrich ⇒ 补绑该占位符 |
| B-4 | `QuoteViewValidationService` · `CostingTreeSqlValidator` · `SqlViewValidator.bindWithNullPlaceholders` | 另三条**不经 enrich** 的旁路（`SqlViewExecutor:118-121` 已列名），逐条补绑 |
| B-5 | 视图重生成 | 走 `ComponentSqlViewService.snapshotForComponents()` 重生成组件 `221dc766` 的视图 |

🚨 **谓词必须写在 `LEFT JOIN … ON`，🚫 绝不许写进 `WHERE`**：
`customer_part_no` 实测 **112/3949** 行为空，写进 `WHERE` 会让这些卡片整个页签 **0 行且不报错** ——
正是 `repair-260908` B-2 记录过的静默失败形态（`SqlViewExecutor:111-122`）。
挂在 `ON` 上时该谓词恒 UNKNOWN ⇒ JOIN 不匹配 ⇒ **左表行仍在、只是客编列为空**，正好满足 `E-5`。

### ~~5.2 行身份 —— A + B + C 三层同时做~~（已冻结，见上）

| 层 | 做什么 |
|---|---|
| **A · 确定性排序** | 编译器生成的 `ORDER BY` 末尾追加 tie-breaker（锚点表及参与 JOIN 各表的主键 `id`），消除堆物理序漂移 |
