## 0. 🚨 先说一件必须澄清的事：主线要求的「把 B-2 的谓词改回去」这个做法在本案**是零证据**
══════════════════════════════════════════════════════════════
B-2 改的是 SemanticCompiler（编译期），渲染读的是**已落库的 component_sql_view.sql_template**。
⇒ 只回滚 Java 而不重新编译视图，渲染行为**根本不会变**，实验必然「不变红」，
   按 §3④ 的字面判据会被读成「白测」—— 那是**错误结论**（testing.md §5.5 形态②「验了一个恒真的东西」）。

这不是推断，是本片**已经实测到的**事实（证据 05）：
  · 19:53 视图重生成**之前**，8123 上已经跑着含 B-1~B-5 全部 Java 改动的代码，
    产品页签仍是 4 行 / 7 行 / 4 行，与 master 逐字节相同（见 05-UI用例-改动后-视图未重生成.txt、06-AC5-AB对照.txt）
  · 19:53 视图重生成**之后**，同样的代码、同样的库，变成 1 行（见 07/10）
  ⇒ **是「已落库的 sql_template」这一个变量决定了行为**，不是 Java 的实时产出。

而真正意义上的「把谓词改回去」= 把共享库里的 sql_template 改回旧版 = 全局配置写入，
**不在 S2 片的写入面内，我没有批准权** ⇒ 未执行。
替代方案：下面三个实验，全部在本片私有写入面内完成，合起来的判别力强于一次代码回滚。

## 3. 实验 E2 · ON/WHERE 判别：客编填一个客户料号表里不存在的值
══════════════════════════════════════════════════════════════
新建 R0910S2-F2-无匹配客编：明细行客编填 **R0910S2-NOMATCH**
三种实现的预期结果互不相同 ⇒ 本实验有判别力：
   · 谓词在 ON 且绑定生效  → 1 行，客编列空   ← 期望
   · 谓词误写进 WHERE      → 0 行（静默失败）
   · 谓词没生效/没绑上      → 4 行

### E1 / E2 实测（服务端物化 quote_card_values）
单据|明细行客编|渲染行数|渲染行客编|品名
R0910S2-F1-正向控制|B17-DUP-0910-1|1|B17-DUP-0910-1|触桥组件A
R0910S2-F2-无匹配客编|R0910S2-NOMATCH|1|(空)|触桥组件A
(2 rows)

### E1/E2 运行时 batch-expand 实测（非物化快照）
  F1-正向控制(客编=B17-DUP-0910-1): rowCount=1  rows=[('S0004', 'B17-DUP-0910-1')]
  F2-无匹配客编(客编=R0910S2-NOMATCH): rowCount=1  rows=[('S0004', None)]

判定：
  E1 正向控制 —— 渲染行客编跟着明细行客编走（B17-DUP-0910-1），⇒ 「1 行」不是常量，绑定是活的 ✅
  E2 ON/WHERE —— 1 行 + 客编空（不是 0 行、不是 4 行）⇒ 谓词确在 ON 且绑定生效，E-5 不回退 ✅
