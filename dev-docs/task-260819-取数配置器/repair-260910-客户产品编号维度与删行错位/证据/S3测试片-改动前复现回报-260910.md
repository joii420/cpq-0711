## 三、🔑 决定性实测：前端算对了、墓碑存对了、**消失的却是另一行**

| | 第 1 轮 | 第 2 轮 |
|---|---|---|
| 点击 | 屏幕**第 2 行** `CP2` | 屏幕**第 1 行** `CP1` |
| 发出/落库 `effKey` | `R0910S3-M1#1` ✅ | `R0910S3-M1#0` ✅ |
| 发出/落库 `fp` | 含 **CP2** ✅ | 含 **CP1** ✅ |
| 最终渲染 | `CP1, CP2, CP3` | `CP1, CP2, CP3` |
| 结果 | **被点的 CP2 还在**，CP4 没了 | **被点的 CP1 还在** |

> 两轮删的是不同的行，**最终输出逐字节相同**。整页刷新后依旧（**不是渲染抖动**）；`snapshot_rows` 仍是完整 4 行。

**服务端投影三段实录**（代理原话：**纯 API，不经浏览器**）：

```
deletedRowKeys = []                     ← 墓碑空的，完全不涉及删除机制
baseRows     = [CP1, CP2, CP3, CP4]     ✅ 驱动展开对
editRows     = [CP1, CP2, CP3, CP3]     ❌
resolvedRows = [CP1, CP2, CP3, CP3]     ❌ 最终渲染源
rowData      = [CP1, CP2, CP3, CP3]     ❌
```

⇒ ① **错配在服务端投影**，不是浏览器；② **`rowData` 覆盖 `baseRows`**（`baseRows[3]=CP4` 而页面显示 CP3）。

**代理给出的三条「站得住的结论」**（逐字抄）：

> 1. 行身份（`effKey`/`fp`）算得对、存得对 —— **身份体系不是故障点**；
> 2. 被点的那一行**没有消失**；
> 3. **行↔值的对应关系在投影层是坏的**，且**零墓碑时也坏**。

**代理的自我修正**（值得保留，示范了正确的自我纠错）：

> 我一度想写「消失的永远是末行」，但「哪一行消失」是我按屏幕上客编值判定的，而这一列的值本身就会错配
> （`restore` 后无任何删除就已是 `CP1,CP2,CP3,CP3`），所以那个说法**我收回**，只保留上面三条。

**代理的推测（明确标注未验证，🚫 不作结论）**：

> `editRows` 里值重复 + 整体错位一位，形态像 `AP-54`「过滤后下标当原数组下标」；
> `resolvedRows` 行数对、内容是前 N-1 行，形态像既有教训里的 `slice(0, N-1)`。
> 证实/证伪需读投影侧实现，**超出本片可读范围**。
