## 观察 7 · ⚠️ 对观察 5 的自我修正：渲染出的「客户产品编号」列本身就会错位/重复

`41-P2-UI实录.txt`（P2 轮 UI 实录原文）：

```
restore-driver-rows → 200
恢复后 deleted_row_keys = []
恢复后渲染 = ["R0910S3-CP1","R0910S3-CP2","R0910S3-CP3","R0910S3-CP3"]   ← ⚠️ 4 行，但 CP3 出现两次、CP4 不见了
点【第 1 行】(R0910S3-CP1) 后当场渲染 = ["R0910S3-CP1","R0910S3-CP2","R0910S3-CP3"]
落库 deleted_row_keys = [{"fp":"…CP1…","effKey":"R0910S3-M1#0"}]
刷新后渲染 = ["R0910S3-CP1","R0910S3-CP2","R0910S3-CP3"]
```

⇒ **`restore` 之后、一次删除都还没做的时候，渲染的客编列就已经是 `CP1,CP2,CP3,CP3`** ——
行数对（4 行），值错（少 CP4、多一个 CP3）。

**因此观察 5 的「消失的永远是末行」这个说法要收窄**：
「哪一行消失」是我**按屏幕上的客编值**判定的，而这一列的值本身就可能与底层行错配。
可以稳稳站住的只有下面三条：

| # | 站得住的结论 | 依据 |
|---|---|---|
| ① | **前端算出并落库的行身份是对的** —— 两轮 `effKey`/`fp` 都精确指向被点的那一行 | 观察 3、观察 6、`41-P2-UI实录.txt` |
| ② | **被点的那一行没有消失** —— 两轮点完之后它都还在屏幕上 | 观察 3（点 CP2，CP2 仍在）、P2（点 CP1，CP1 仍在） |
| ③ | **渲染层的行↔值对应关系本身是坏的**，且在没有任何删除动作时也坏（restore 后即 `CP1,CP2,CP3,CP3`） | 观察 7 |

🚫 我**没有**验证的：这个错位究竟发生在编辑行(`editRows`)构造、投影(`resolvedRows`)、还是前端渲染 ——
判定它需要读投影/渲染侧实现，**超出本片可读范围**。

## 观察 8 · 🔑 错配发生在**服务端投影**，且与墓碑机制无关（`42-服务端投影实录-零墓碑态.txt`）

纯 API（不经浏览器）：`restore-driver-rows` 清空墓碑后立刻读 `GET /api/cpq/quotations/{id}`：

```
deletedRowKeys = []                                      ← 墓碑空的，完全不涉及删除机制
baseRows     = [CP1, CP2, CP3, CP4]   ✅ 驱动展开对
editRows     = [CP1, CP2, CP3, CP3]   ❌
resolvedRows = [CP1, CP2, CP3, CP3]   ❌ 最终渲染源
rowData      = [CP1, CP2, CP3, CP3]   ❌ 落库的编辑行
```

⇒ 两点确定：
1. **不是浏览器渲染问题**，服务端返回的投影本身就是错的；
2. **`rowData` 覆盖 `baseRows`** —— `baseRows[3]=CP4` 而页面显示 CP3，说明显示值取自 `rowData` 这一层。

⚠️ 但**刚加完卡片、从未删过时（观察 1）投影是对的**（CP1..CP4）。
⇒ 这份错配是**「删除 → 行集合变化」之后被引入并持久化的**，不是一开始就错。
