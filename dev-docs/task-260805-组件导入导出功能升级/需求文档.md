> 本文是本任务的**唯一权威需求口径**。实现计划 / 测试用例见同目录后续文档。

## 0. 一句话

把「公式绑定完整性」的暴露点从**导入提交**前移到**导出**与**导入预览**，
让业务用户能在**源环境的 UI 里**修，而不是去手改 JSON；
同时把**旧版 bundle 的兼容导入**和**新版导出↔导入往返一致**钉成可验收的硬指标。

---

## 1. 问题

### 1.1 三个环节，只有最后一个拦

| 环节 | 现状 |
|---|---|
| 导出 `GET /component-directories/{id}/export` | **零校验**，`ComponentExportService.exportDirectory` 直接读库拼 bundle |
| 导入预览 `POST /{id}/import`（dry-run，返回 `blockers`/`canCommit`） | **不查公式绑定**，只查依赖缺失 / code 冲突 / checksum（`ComponentImportService:149/:153/:157`） |
| 导入提交 `POST /{id}/import/commit` | ✅ `validateExplicitBinding`（`:348`）400 拒绝 |

最难受的是中间那行：**preview 是专门给用户"提交前看清楚"的**，却唯独不报绑定问题 —— 用户看到一片绿，点提交才 400。**先给了个安全的假象。**

### 1.2 报错文案在导入时不可执行

```
以下公式字段未绑定公式，请在字段配置中显式选择：XXX（BL-0098：系统不再按位置自动匹配公式）
```

「在字段配置中显式选择」只有在**源环境**才做得到。导入时用户手上只有一个 JSON，就算硬改也得自己从 `formulas` 数组里翻出对应那条的 UUID 填进 `field.formula_id`——**这个动作实际上做不了**。

### 1.3 成因（非设计失误，是演进顺序）

preview/commit 这套是更早的 P3 导入功能；`validateExplicitBinding` 是 [[BL-0098]]（2026-08-03）加的，只接进了 commit 的第三遍循环，没回头补 preview 和 export。

## 3. 设计

### 3.1 导出端（R1）

`exportDirectory` 对每个组件跑一遍**只读**解析（`ensureFormulaIds` + `bindFormulaIdsToFields` 的解析口径，**在内存副本上，不写库、不改 bundle 内容**），产出 `bindingReport`：

```
bindingReport: {
  unboundCount: int,
  items: [{ componentCode, componentName, fieldName,
            resolvedFormulaId, resolvedFormulaName,
            status: "BOUND" | "RESOLVED_BY_NAME" | "RESOLVED_BY_POSITION" | "UNRESOLVABLE" }]
}
```

**只警告不阻断**：备份、跨环境迁移、出故障时导一份现场数据，都是正当场景，堵死反而添乱。
UI 在导出成功后若 `unboundCount > 0` 给出提示，并可直接跳转到固化抽屉（§3.4）。

> **为什么导出不自动固化到源库**：导出是只读操作，产生写库副作用会很意外；且「固化」会把**按位置猜出来的绑定永久钉死**，猜错就把错误固定下来。必须是显式动作 + 可先预览。

### 3.2 导入预览端（R2）

`preview()` 在**内存副本**上跑同款解析（preview 本就"绝不写库"），扩充 `ImportPreviewResult`：

- 每个 `ComponentPlan` 增加 `formulaBinding` 段：逐 FORMULA 字段列出 `fieldName / resolvedFormulaName / status`
- `UNRESOLVABLE` 的进 `blockers`，点名「组件 X 的字段 Y」
- `canCommit` 随之反映

> 🔑 **必须展示"绑到哪条"，而不只是"能不能绑"。**
> 老 bundle 的绑定是靠名字/位置**推导**出来的（§4 实测：31 条公式 **0 条**带 id）。
> 用户需要看见推导结果对不对 —— 只告诉他"能过"，等于把 BL-0098 的静默错绑换个地方重演。

### 3.3 导入提交端（R3）

- 默认行为不变（`validateExplicitBinding` 抛 400，单事务整体回滚，不留半截脏数据）
- 新增 `@QueryParam("ignoreUnboundFormulas") @DefaultValue("false")`，显式 `true` 时降级为警告放行
- 放行后该组件在组件管理中标记「待绑定」，引导用户去固化

> 形状与既有 `ignoreMissingDeps=false` 完全一致，不引入新范式。

### 3.4 一键固化（R4）

现有 `POST /api/cpq/admin/formula-binding/consolidate` 已具备：`dryRun` 默认 `true`、逐字段清单（`CONSOLIDATED`/`UNRESOLVABLE`/`ERROR`）、`@RoleAllowed(SYSTEM_ADMIN)`。**缺的是作用域与入口**：

- 端点加可选 `directoryId` / `componentIds`（**不传 = 全库，向后兼容**）
- 组件管理加抽屉：先 `dryRun` 出清单（哪个字段会绑到哪条公式、哪些 `UNRESOLVABLE`）→ 用户核对 → 确认写库
- 与导出同为**目录级**，场景贴合

### 3.5 三类标识的正确落库（R5）

导入时三类标识各有各的处理，**必须全部正确**：

| 标识 | 处理方式 | 代码位置 |
|---|---|---|
| **组件 id** | 导入**新生成** UUID，`idMap: 旧id → 新id`；`cross_tab_ref.source` 经 `FormulaRefRemapper` 重映射 | `:269` `c.persist()` / `:273` `idMap.put` / `:323` `remap` |
| **组件 code** | `SKIP`/`RENAME` 策略决定终值，`codeMap: 旧code → 新code`；`component_subtotal.component_code` 经同一 remapper 重映射 | `:279` `codeMap.put` |
| **公式 id** | `ensureFormulaIds` 补 UUID（已有原样保留）→ `bindFormulaIdsToFields` 绑字段 → 条件公式固化内部 `rules[].formula_id` / `default_formula_id` | `:346-348` |

**已知缺口（本任务必须处理）**：`ComponentImportService:312-316` 的 `hasNullId` 分支 ——
老 bundle 若 `Item.id` 为 `null`，`idMap` 建不起来 → **`cross_tab_ref.source` 不重映射，仍指向源环境的组件 UUID → 跨组件引用断链**。
当前只打一行后端 `LOG.warnf`，**用户完全看不见**。

**要求**：该情形必须在 **preview 中显式暴露**（`blockers` 或高优先级 warning，点名受影响的组件与引用），不能只落日志。

### 3.6 往返保真（R6）

定义「完全一致」：**导出 A → 导入到空目录 → 再导出得 A″**，则 A″ 与 A 在下列字段上**逐字段相等**：

- `components[].code`（SKIP/无冲突时）、`name`、`componentType`、`status`、`dataDriverPath`
- `tabType` / `partNoField` / `partNameField` / `sortField` / `rowKeyFields` / `columnCount`
- `fields`（含 `formula_id`、`conditional_formula` 内部引用）
- `formulas`（**含 `id`** —— 已有 id 原样保留，往返不得重新生成）
- `excelColumns` / `sqlViews`（视图名与模板正文）
- `dependencies`

**允许且必须不同**的：`components[].id`（新 UUID）、`exportedAt`、`checksum`、`source`（目录信息），以及 `RENAME` 策略下的 `code`。

> 这条把「导入有没有丢字段」变成一个**可自动化的对拍**，比逐项人工核对可靠得多 ——
> repair-0805 的根因正是「白名单搬运漏了一个键」，往返对拍是这类缺陷的天然门禁。

#### 📌 3.6 澄清（2026-08-05 技术总监补，**待用户复核**）

实现期推演发现上文「逐字段相等」的字面表述有两处**在数学上无法满足**，若照字面执行会得到「正确的代码反而失败」的倒挂结果。现澄清如下，**立意不变**（仍是「导入有没有丢字段」的自动化门禁），只修正判定方法：

**① 起点 A 必须是「已规范化」的 bundle（两阶段构造）**

真实历史 bundle 的 FORMULA 字段普遍没有 `formula_id`（§4 实测 0/19），而 `commit()` 的**既有**逻辑落库时会自动补全。直接拿原始历史 bundle 当 A，则 A″ 必然比 A 多出一批 `formula_id` —— 这不是缺陷，只是 A 本身不是稳定态。
故 A 的取法为：先把夹具导入一次（让绑定固化）→ 导出所得即 A → 再用 A 走一轮导入导出得 A″。

**② `cross_tab_ref.source` / `component_subtotal.component_code` 按「拓扑等价」比较，不比字面值**

每次 `commit()` 都为组件生成全新 UUID，`FormulaRefRemapper` 会把跨组件引用重映射到本批次的新 id —— 这正是 AC-6 ③ 要求的**正确行为**。因此 A 的 `source` 指向 dir1 里的副本、A″ 的指向 dir2 里的副本，**两者必然不同**。
若按字面比较：**remap 正常工作 → 对拍失败；remap 被删除 → 引用原样透传 → 对拍反而通过**。方向完全反了。
故这两类跨组件引用一律按「**是否指向同一个逻辑组件**」判定（A 的 source == A 内某组件 id ⟺ A″ 的 source == A″ 内**对应**组件 id），不要求 UUID / code 字面相等。

**③ 不受影响、仍要求字面相等的**：`formulas[].id`（已有 id 原样保留，是 §3.6 点名的硬指标）、`fields[].formula_id`、以及上文列出的其余全部标量字段。

> **连带修正**：本澄清同时作废实现计划 §5 第 11 条原定的两条反向门禁挂载点（「注释掉 `bindFormulaIdsToFields` / `FormulaRefRemapper.remap` → 往返对拍必须失败」）——
> 往返对拍比较的是**同一份代码连续处理两次**的产物，某步骤被整体删除时两侧「一致地错」，字面相等反而成立，**检不出**这类回归。
> 两条门禁改挂到 **AC-6 的单次导入断言**（拿原始 bundle 的已知值与落库后的值做单次比较），实测可正确检出。详见 `测试用例.md` §6。

## 4. 旧版 bundle 兼容矩阵（实测）

工作区 `客户组件模板/` 下有 **18 份真实历史 bundle**（2026-07-26 ~ 08-03 导出，全部 `bundleVersion 1.0`），共 **93 个组件**。实测形态：

| 项 | 实测 |
|---|---|
| 公式总数 / 带 `id` | 31 / **0** ← 全部需 `ensureFormulaIds` 补 |
| FORMULA 字段 / 带 `formula_id` | 19 / **0** |
| 其中带 `formula_name`（可按名字确定性解析） | **17** |
| 条件公式字段（内部按公式名引用） | **2** |
| **依赖位置回退猜测的** | **0** ✅ |
| 缺 `Item.id`（会导致跨组件引用断链） | **0 / 93** ✅ |
| `cross_tab_ref` 引用 | 30 处，集中在 2 份文件 |
| 可选字段缺失（正常降级） | `partNoField` 53/93、`sortField` 39/93、`tabType` 33/93、`rowKeyFields` 2/93 |

### 🔑 兼容性的真正含义

**不是「能不能导进来」——全部能**（17 个按名字 + 2 个条件公式按内部名字，零位置猜测）。
**而是「导进来的绑定对不对」。** 所以 R5 的验收判据是**绑定结果正确**，不是「导入不报错」。

这也是 R2 要求 preview **展示绑定去向**的根本原因。
