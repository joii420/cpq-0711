## 0. 三条铁律（违反即打回）

1. **只读就是只读**：导出与 preview 的绑定解析必须跑在**深拷贝**上。原 `fields`/`formulas` 对象一个字节都不许改，更不许写库。判据 = 导出前后 `component.fields/formulas` 的 md5 不变。

3. **保存路径行为逐字节不变**：`ComponentService` 保存链路共用 `FormulaIdBinder`，本任务对它只做**加法**（新增方法），既有方法的签名与行为不动。护栏 = `FormulaIdBinderTest` / `FormulaBindByIdTest` / `FormulaNameResolutionTest` 全绿。

## 1. 一处需要澄清的设计（已决，照此实施）

### 1.1 `bindingReport` 放在 bundle 顶层，不进 checksum

导出端点返回的是**文件下载**（`Content-Disposition: attachment`），没有旁路可以塞报告。决定：作为 bundle 的**顶层可选字段** `bindingReport`。

- `computeChecksum` 现只覆盖 `source + components + dependencies` —— 加顶层字段**天然不影响 checksum**。⚠️ 必须补一条测试把这个性质钉死（老 bundle 的 checksum 在新代码下仍 `checksumValid=true`）。
- 不往 `Item` 里加任何字段（一加就改 checksum，全部存量 bundle 的校验会集体翻红）。
- 往返对拍（§3.6）不比较 `bindingReport`（它与 `exportedAt`/`checksum` 同属元信息）。
- 前端从下载的 blob 文本里 `JSON.parse` 读它，**不额外发一次请求**。

### 1.2 `warnings` 与 `blockers` 分家

现状：checksum 不一致的提示被塞进 `blockers`，但 `canCommit` 仍为 `true` —— 而前端 `ComponentImportDrawer` 只在 `!canCommit` 时渲染 blockers。**结果这条警告用户永远看不到**（既有缺陷，本任务顺手修）。

新口径：

| 字段 | 语义 | 影响 canCommit |
|---|---|---|
| `blockers` | 真阻断 | ✅ 是（有值即 false） |
| `warnings` | 高优先级但不阻断 | ❌ 否 |

- checksum 不一致 → 移到 `warnings`
- 跨组件引用无法重映射（§3.5 `hasNullId`）→ `warnings`
- `RESOLVED_BY_POSITION` 的绑定 → `warnings`（按位置猜出来的，用户必须核对）
- `UNRESOLVABLE` 的字段 → `blockers` + `canCommit=false`

前端**必须无条件渲染 `warnings`**（不论 canCommit 真假）。

### 1.3 「跨组件引用不可重映射」判 warning 不判 blocker

需求 §3.5 给的是「`blockers` 或高优先级 warning」二选一。**选 warning**，理由：commit 侧没有对应的 override 开关，判成 blocker 等于把这类 bundle 堵死且无解；而 §4 实测 `Item.id` 缺失 **0/93**，真实场景不触发。AC-7 的判据是「**显式暴露**、不再只落日志」，warning 满足。

### 1.4 「待绑定」标记用**派生**，不加列不做迁移

`ignoreUnboundFormulas=true` 放行后要在组件管理标记「待绑定」。判据本身是纯函数：**存在 `field_type=FORMULA` 且无 `conditional_formula` 且无 `formula_id` 的字段**。因此在 DTO 层派生一个布尔 `hasUnboundFormula`，不加数据库列、不写 Flyway。附带好处：BL-0098 之前遗留的坏配置也一并被标出来。

### 1.5 夹具原样入库，只做文件名中性化

需求 §6 写「脱敏后入库」。**实施时只把文件名换成 `bundle-01.json`…`bundle-18.json`，内容原样**，理由两条：① 改 `name` 有实质风险 —— 那 19 个 FORMULA 字段里 17 个是**靠公式名**确定性解析的，改名可能改变本任务要验的解析结果，夹具就不再是真实历史产物；② 本仓库私有且 `docs/` 已遍布真实客户名，重命名不产生额外保护。**此点在交付报告中如实标注，供用户复核。**

## 2. API 契约（冻结口径 · 前后端共同依据）

### 2.1 `GET /api/cpq/component-directories/{id}/export`

响应 body（bundle）新增顶层字段：

```jsonc
{
  "bundleVersion": "1.0",
  "exportedAt": "...", "source": {...}, "components": [...], "dependencies": {...},
  "checksum": "sha256:...",          // 口径不变，不含 bindingReport
  "bindingReport": {                  // 🆕 R1；无 FORMULA 字段时 items=[] 且 unboundCount=0
    "unboundCount": 2,                // = items 中 status==UNRESOLVABLE 的条数
    "totalFormulaRefs": 19,           // 扫描到的绑定点总数（普通 FORMULA 字段 + 条件公式内部引用）
    "items": [
      {
        "componentCode": "COMP-0157",
        "componentName": "物料",
        "fieldName": "材料成本",        // 条件公式内部引用写成「材料成本 › 规则1」/「材料成本 › 默认」
        "resolvedFormulaId": "8f3e-...",   // 解析不到为 null
        "resolvedFormulaName": "银点材料成本公式",
        "status": "BOUND",             // BOUND | RESOLVED_BY_NAME | RESOLVED_BY_POSITION | UNRESOLVABLE
        "message": null                 // UNRESOLVABLE 时给人话原因，其余为 null
      }
    ]
  }
}
```

**status 判定表**（唯一口径，前后端与测试都按它）：

| 字段现状 | 解析结果 | status | message |
|---|---|---|---|
| 有 `formula_id` 且能在本组件 `formulas` 查到 | 命中 | `BOUND` | null |
| 有 `formula_id` 但查不到 | — | `UNRESOLVABLE` | 「绑定的公式已不存在（id=…）」 |
| 无 `formula_id`，靠 `formula_name` 或「字段名==公式名」命中 | 命中 | `RESOLVED_BY_NAME` | null |
| 无 `formula_id`，靠**位置**命中 | 命中 | `RESOLVED_BY_POSITION` | null |
| 都解析不到 | — | `UNRESOLVABLE` | 「未绑定公式，且无法按名称/位置推导」 |

> 导出**永不阻断**：`unboundCount > 0` 也照常 200 + 完整 bundle。

### 2.2 `POST /api/cpq/component-directories/{id}/import`（preview）

`ImportPreviewResult` 新增：

```jsonc
{
  "...": "既有字段全部保持不变",
  "warnings": ["⚠ checksum 校验不一致…", "⚠ 2 处跨组件引用无法重映射…"],   // 🆕 §1.2
  "bindingSummary": {                                    // 🆕 全 bundle 汇总
    "totalFormulaRefs": 19, "bound": 0, "resolvedByName": 17,
    "resolvedByPosition": 0, "unresolvable": 2
  },
  "crossRefIssues": [                                    // 🆕 R5 / AC-7
    { "componentCode": "COMP-0031", "refType": "UUID", "ref": "a1b2-…",
      "reason": "BUNDLE_MISSING_ITEM_ID" }               // BUNDLE_MISSING_ITEM_ID | REF_NOT_IN_BUNDLE
  ],
  "components": [
    { "code": "...", "name": "...", "action": "CREATE", "newCode": null,
      "conflict": false, "sqlViewCount": 1,
      "formulaBinding": [ /* 与 §2.1 items 同结构，去掉 componentCode/componentName */ ]   // 🆕 R2
    }
  ]
}
```

规则：
- `action=SKIP` 的组件**照常出 `formulaBinding`**（供核对），但它的 `UNRESOLVABLE` **不进 blockers**（这个组件根本不会被导入）。
- 会真正落库的组件（CREATE / RENAME）中若有 `UNRESOLVABLE` → `blockers` 加一条**点名到「组件 X 的字段 Y」**的文案，`canCommit=false`。
- 存在 `RESOLVED_BY_POSITION` → `warnings` 加一条。
- preview 的解析必须**复现 commit 的处理顺序**：`ensureFormulaIds` → `bindFormulaIdsToFields` → 判定，全程在内存副本上。

### 2.3 `POST /api/cpq/component-directories/{id}/import/commit`

新增 query 参数（形状照抄既有 `ignoreMissingDeps`）：

```
?conflictPolicy=RENAME&ignoreMissingDeps=false&ignoreUnboundFormulas=false
```

- 默认 `false`：行为逐字节不变（`validateExplicitBinding` 抛 → 400 → 单事务整体回滚）。
- `true`：跳过阻断，`ImportCommitResult` 新增 `unboundWarnings: [{componentCode, fieldName}]` 与 `unboundCount`。
- ⚠️ **不许用 `try { validate } catch (IllegalArgumentException e) { ignore }`** —— 那会把同一循环里其它来源的 IAE 一并吞掉。正确做法：给 `FormulaIdBinder` 加 `listUnboundFormulaFields(fields): List<String>`，让 `validateExplicitBinding` 内部**复用它**（一份口径），commit 按开关决定「抛」还是「记」。

### 2.4 `POST /api/cpq/admin/formula-binding/consolidate`（R4）

```
?dryRun=true&directoryId=<uuid>&componentIds=<uuid>,<uuid>
```

- 两个新参数都可选；**都不传 = 全库，SQL 与行为与今天逐字节相同**（加 WHERE 子句只在传参时拼接）。
- 两个都传：取交集（`directoryId` 内 ∩ `componentIds`）。
- 响应结构不变（`dryRun` / `componentsUpdated` / `itemCount` / `items[]`）。
- 鉴权保持 `@RoleAllowed({"SYSTEM_ADMIN"})` 不动 —— 它能改写全库公式绑定。⚠️ 组件管理页的角色是 `SALES_MANAGER + SYSTEM_ADMIN`，故**非管理员点固化会拿到 403**，前端须给出可读提示而不是白屏。


### B2 细则

```java
public final class FormulaBindingInspector {
    public static Report inspect(String componentCode, String componentName,
                                 JsonNode fields, JsonNode formulas);   // 单组件
    public static Report merge(List<Report> reports);                    // 汇总
}
```
- **入口第一件事就是深拷贝**（`fields.deepCopy()` / `formulas.deepCopy()`），之后随便折腾。
- 内部按 `FormulaIdBinder.ensureFormulaIds` + `bindFormulaIdsToFields` 的**同一口径**推导；来源标签取自 B1。
- 条件公式字段：**逐个内部引用**出一条 item，`fieldName` 格式 `字段名 › 规则N` / `字段名 › 默认`。已有 `formula_id` 且查得到 → `BOUND`；否则按 `formula`/`default` 名字查 → `RESOLVED_BY_NAME`；查不到 → `UNRESOLVABLE`。
- 无 `formulas`（空数组）而有 FORMULA 字段 → 全部 `UNRESOLVABLE`（对应遗留的 `COMP-0049` 形态）。
