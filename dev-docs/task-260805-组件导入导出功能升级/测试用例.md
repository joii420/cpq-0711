### 关键发现①：18 份真实 bundle 里天然 **0 例** UNRESOLVABLE / RESOLVED_BY_POSITION

逐条重放 `resolveFormula` 的判定链后发现：17 个非条件 FORMULA 字段**全部**带显式 `formula_name` 且均能在同组件 `formulas` 里按名找到；2 个条件公式字段的 `rules[].formula` / `default` 引用也全部按名解析成功。由于 `resolveFormula` 在**显式 `formula_name` 命中/不命中**两种情况下都不会继续往下走（命中→返回；不命中→直接 `null`，不 fallback 到位置），**这 19 个字段结构上不可能触发 `RESOLVED_BY_POSITION`**。

**推论（很重要）**：18 份真实 bundle 只能给 AC-1/AC-2 的 status 判定表提供 `RESOLVED_BY_NAME` 这一种阳性样本；`BOUND`（显式 `formula_id`）、`RESOLVED_BY_POSITION`、两种 `UNRESOLVABLE` 必须靠**自造夹具**覆盖（见 §4.2）。这也印证了 RECORD.md 里 2026-08-03 的纠偏结论：`COMP-0032`「材料成本」的「银点材料成本公式」绑定，走的是**条件公式默认分支按名**解析，不是位置回退——本次复核在 bundle 层面独立证实了这一点。

### 关键发现②：`COMP-0031`「报价」是 `SUBTOTAL` 类型组件，`fields=[]` 但 `formulas` 非空

`bug2-重算.json` 里 `COMP-0031`（`componentType=SUBTOTAL`）有 1 条公式「公式1」（5 个 `component_subtotal` token 相加），但 `fields` 数组为空——它不通过任何 FORMULA 字段引用这条公式。B2（`FormulaBindingInspector.inspect`）按 §B2 细则只扫 `fields[].field_type=='FORMULA'`，因此**这条公式永远不会出现在 `bindingReport`/`formulaBinding` 里**。这是设计上的合理范围外（SUBTOTAL 组件的小计公式不是"字段级绑定"问题），但需要一条用例把这个边界钉住，防止日后有人"顺手"改成也扫 SUBTOTAL 从而引入未预期的行为变化。已列入 U-B2-09，并在 §7 公开问题里请架构确认这是否是预期范围。

### 关键发现③：18 份 bundle 的 `dependencies`（全局变量/数据源）全部为空

18 份 bundle 的 `dependencies.globalVariables` / `datasources` 均为 `[]`。这意味着 AC-6 端到端导入时 `ignoreMissingDeps` 参数不影响这批夹具的可导入性（`missing` 恒为 0），简化了 AC-6 用例设计（不需要额外构造全局变量/数据源来满足依赖检查）。

### 4.3 AC-7 专用夹具：抹掉 `Item.id`

**做法**：以 `bundle-01.json`（`bug2-重算.json`）为底本，程序化克隆一份，把其中 `code=COMP-0033` 的组件项 `id` 字段整个删除（置为 `null` 或从 JSON 里去掉该键，两种写法在 Jackson 反序列化后效果相同，均为 `Item.id=null`）。

**为什么选 `COMP-0033`**：`bug2-重算.json` 里 `COMP-0032`「物料」的 `formulas` 含两条 `cross_tab_ref`，`source="6206da55-5a6e-42f1-ac59-6f04a007d4d6"`，该 UUID **正是** `COMP-0033` 的 `Item.id`（已用 Python 核实，见 §0）。抹掉 `COMP-0033.id` 后，`COMP-0032` 对它的引用就变成"bundle 内确实存在这个 code/名字对应的组件，但 id 缺失、无法建 idMap"的**真实语义**场景，而不是随手编造一个不存在的 UUID（那样测的是另一件事——纯粹的悬空引用，AC-7 要测的是"同批次内因 id 缺失导致的断链"）。

## 6. 反向门禁：与实现计划 §5 第 11 条的分歧（**已裁决 · 采纳本方案**）

> **2026-08-05 技术总监裁决**：本节论证成立，采纳。技术总监复核补充了一个更强的论点（见下方"裁决补充"），进一步确认往返对拍在方向上对这两条门禁不适用（不只是"测不出"，`cross_tab_ref` 场景下正确代码反而会字面失败、改坏的代码反而字面通过——**方向是反的**，不只是灵敏度不够）。G-GATE-01/02/03 均按 §6 原设计挂载到 AC-6 单次导入断言，执行。

实现计划 §5 第 11 条要求至少两条反向门禁：
① 注释掉 `bindFormulaIdsToFields` 调用 → 往返对拍必须失败
② 注释掉 `FormulaRefRemapper.remap` 调用 → AC-6 的③必须失败

**逐条推演后发现①无法通过 AC-8 往返对拍检出**，理由：

往返对拍比较的是 **A vs A″**，而 A 与 A″ 是**同一份代码对结构相同的输入连续处理两次**的产物。如果 `bindFormulaIdsToFields` 被整体注释掉，这个"缺陷"在两次 `commit()` 里是**一致缺失**的——A（第一次 commit 产物）就已经没有 `formula_id`，A″（第二次 commit 产物）在同样被注释掉的代码下**同样**没有 `formula_id`。两边"一致地错"，字面比对反而相等，往返对拍**测不出来**。

同理，②注释掉 `FormulaRefRemapper.remap`：A 的 `cross_tab_ref.source` 会保留 bundle 原始的（源环境）UUID，这个 UUID 不属于 A 自身任何组件的 id（因为 remap 没跑，A 的组件 id 是新生成的，原始 UUID 对不上）——但这个"错误的悬空值"在没有 remap 的情况下，**从 A 到 A″ 也是原样透传**（A″ 的 idMap 是从 A 的 `Item.id` 建的，A 里那个残留的原始 UUID 根本不在这个 idMap 的 key 集合里，找不到就跳过、原样保留）。同样是"一致地错"，往返对拍依然测不出来。

**结论**：往返对拍能检出的是"两次处理行为不一致"（非幂等）类回归，检不出"从第一次就统一地没做某件事"类回归。这是往返测试这种设计天然的盲区，不是本文档设计得不够细。

**改用方案**：把这两条反向门禁挂到 **AC-6 的单次导入断言**上（这两条断言本身就是"拿原始 bundle 里已知的引用值，跟落库后的值做单次比较"，不是"处理结果 vs 处理结果"，所以能真正检出"根本没处理"这类问题）：

| 编号 | 改坏的代码 | 断言必须失败的用例 | 失败原因 |
|---|---|---|---|
| G-GATE-01 | 注释掉 `ComponentImportService.commit()` 第三遍循环里的 `FormulaIdBinder.bindFormulaIdsToFields(fieldList, formulaList)` 调用 | E-IMP-01 断言②（`field.formula_id` 反查名称 == preview 报的 `resolvedFormulaName`） | `field.formula_id` 保持 `null`（因为原本靠 `formula_name` 隐式绑定的字段永远不会被固化），反查名称这一步直接拿不到值，与 preview 侧非空的 `resolvedFormulaName` 不相等 |
| G-GATE-02 | 注释掉 `ComponentImportService.commit()` 第二遍循环里的 `FormulaRefRemapper.remap(...)` 调用 | E-IMP-01 断言③（`cross_tab_ref.source` 属于本批次新 id 集合、不等于任何原始 `Item.id`） | `source` 原样保留 bundle 里的原始 UUID（如 bundle-01 的 `6206da55-...`），既不在"本批次新 id 集合"里，又**等于**原 bundle 的某个 `Item.id`，两个子断言都会失败 |
| G-GATE-03（加固，非计划要求，建议顺手加） | 注释掉第三遍循环里的 `FormulaIdBinder.ensureFormulaIds(formulaList)` 调用 | E-IMP-01 断言①（每条公式 `id` 非空） | 老 bundle 的 `formulas[].id` 本就是 `null`（§0 已证实 31/31 无 id），不补的话落库后仍是 `null`，断言①直接失败 |

**执行方式**：这三条门禁是**一次性人工验证**（改一行代码 → 跑对应用例 → 确认变红 → 改回来），不是要长期留在 CI 里的用例（CI 里留的是 E-IMP-01 本身；G-GATE 系列是证明 E-IMP-01 这条断言"真的在检查东西、不是摆设"的元验证，实现阶段跑一次、把"改坏后失败"的日志/截图存进交付记录即可）。

**裁决补充（技术总监，2026-08-05）**：`FormulaRefRemapper.remap` 正常工作时，`cross_tab_ref.source` 在 A 与 A″ 之间**必然不同**（每次 `commit()` 都生成全新组件 UUID，A 的 source 指向 dir1 副本、A″ 的 source 指向 dir2 副本）。这意味着**字面对拍下，正确的代码会字面失败、改坏的代码（原样透传旧 UUID）反而字面通过**——不是"灵敏度不够测不出来"，是**方向相反**。这进一步坐实了往返对拍不适合承载这两条反向门禁，拓扑等价比较（§5.8 I-RT-02）不是防御性设计选择，是**唯一可行**的比法。

**裁决**：①②两条门禁的挂载点从"AC-8 往返对拍"改为"AC-6 单次导入断言"，**按 §6 原设计执行，不再需要重新设计对拍算法**。

## 7. 公开问题（**已裁决**，按原重要性排序留存，供实现阶段查阅）

**Q1（固化前/后视角）—— 裁决：固化后视角**。技术总监已读过后端实现：`commit()` 里顺序是 `ensureFormulaIds` → `bindFormulaIdsToFields` → 再走 `listUnboundFormulaFields`/`validateExplicitBinding`，两个分支都在固化之后。**U-FIB-01 按原设计执行，不用改**（先跑 `bindFormulaIdsToFields` 再断言 `listUnboundFormulaFields` 恰好返回 `["字段C"]`），不会有误报。

原文（供留存）：`FormulaIdBinder.listUnboundFormulaFields(fields)` 的判定口径是"字段当前是否已有 `formula_id`"（固化前视角），还是"字段固化后是否仍然没有 `formula_id`"？两者对"未显式绑定但可按名称解析"的字段会给出不同答案。

**Q2（`crossRefIssues[].reason` 判定规则）—— 裁决：与推演规则逐字吻合**。**bundle 内存在任一 `Item.id` 为空 → 全部悬空引用判 `BUNDLE_MISSING_ITEM_ID`；否则判 `REF_NOT_IN_BUNDLE`**（bundle 级判定，非逐 ref 级）。**I-AC7-01 收紧为断言具体值 `"BUNDLE_MISSING_ITEM_ID"`**（§4.3 夹具确实抹了 `COMP-0033.id`，命中"存在任一 Item.id 为空"）。

**Q3（AC-8 起点与比法）—— 裁决：采纳"两阶段构造起点 + 拓扑等价比较"解读**。与需求 §3.6 立意（"把『导入有没有丢字段』变成可自动化对拍"）一致，字面逐字节 diff 在数学上不可满足（见 §6 裁决补充：`cross_tab_ref.source` 场景下正确代码必然字面失败）。技术总监会把这条澄清回写进需求文档并向用户报备；本文 §4.4/§5.8 按此设计执行，不改。

**Q4（§4.4 步骤 3，删 dir1 组件腾 code 空间）—— 裁决：无需决策，处理合理**。按原设计执行。

**Q5（SUBTOTAL 范围外）—— 裁决：确认是范围外，判断正确**。理由（技术总监补充，记入文档）：`validateExplicitBinding` 只看 `fields`，`commit()` 也只对**字段级**绑定阻断——`bindingReport`/`formulaBinding` 的覆盖面**恰好等于 commit 实际强制的范围**，这是自洽的（SUBTOTAL 组件的小计公式不受 `ignoreUnboundFormulas` 开关约束，本就不该出现在同一份报告里造成"能看见但管不着"的困惑）。U-B2-09 作为边界钉子保留，不升级为阻断项。
