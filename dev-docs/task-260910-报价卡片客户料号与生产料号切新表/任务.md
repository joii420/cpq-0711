## ① 背景与目标

用户在报价单编辑页（`QT-20260909-0799` / 正泰 CUST-0004 / 销售料号 `S0001`）提出三个问题，
排查后确认是**同一条病灶的三张脸**：卡片头部这一圈 UI 全部还挂在旧数据源上，而实际数据早已迁到
取数配置器的 `ds_*` 数据集表。

| 用户看到的现象 | 根因（已实证） |
|---|---|
| 卡片上没有客户料号 | ① 头部**根本没有渲染客户料号的位置**（`QuotationStep2.tsx:3085` 只有「客户产品编号」/「料号」二选一）<br>② 连客户产品编号也是空的：后端 `QuotationService.java:3524-3537` 查 `material_customer_map`，实测正泰 14 行**全是 pending 占号影子行**（`material_no=0028-26090000xx`，其余列全空），没有 S0001 |
| 「生产料号」浮层全是「—」 | 后端 `QuotationService.java:3560-3592` 用**销售料号**去查 `internal_material`（全表 **0 行**）→ 兜底 `material_master`（48 行，**无 S0001**）⇒ `hfPartInfo=null` ⇒ 前端 `QuotationStep2.tsx:3116` 回退成 `productPartNo`，于是标题写「生产料号」值却是销售料号 `S0001` |
| 卡片边框是红的 | `QuotationStep2.tsx:2257-2281` 拿 `customerPartNo` 调 `/material-mappings/match`，后端查 `customer_material_mapping`（全表 **0 行**）⇒ 恒 `NO_MATCH` ⇒ 恒红。**只要行上有客户料号就一定是红框**，该信号已完全失效 |

**目标**：把这三处读侧全部切到 `ds_*` 新体系；删掉已失效的红框信号；卡片头部按用户指定的布局重排。

**不做会怎样**：卡片头部持续显示空值与恒红边框，用户无法从卡片上识别客户料号与生产料号；
旧表引用继续拖住 `task-260909-V6老表退役` 的收尾。

**AC-5 · 后端 SQL 按客户维度隔离**
断言：`ds_quote_material` 与 `ds_quote_customer_part` 的查询 `WHERE` 中**必须含 `customer_no = :customerCode`**。
验证方式：测试侧自造前缀化数据 —— 插入 `(T260910-C1, T260910-M1, production_no=T260910-P-AAA)` 与
`(T260910-C2, T260910-M1, production_no=T260910-P-BBB)` 两行，用 `T260910-C1` 的报价单打开，浮层料号必须是 `T260910-P-AAA`。

**AC-6 · 一料号对多客户产品编号时按 line_item 精确消歧**
断言：客户料号查询**优先**用 `quotation_line_item.customer_part_no` 精确匹配 `customer_product_no`；
仅当该列为空时才回退按 `material_no` 取一条，且回退路径**必须有确定性排序**（不得依赖堆表顺序）。
> 事实来源：`ds_quote_customer_part` 实测存在同 `(customer_no, material_no)` 对应 **2 条**不同客户产品编号的情况
> （`CUST-0001 / 0526-2609000006` → `T260907R-SEL-D40B` 与 `T260907R-SEL-D40`；`CUST-0004 / T260907-M1` 同）。

**AC-7 · N+1 守恒**
断言：打开一张含 N 个产品行的报价单，本次新增的三类查询（客户料号 / ds_quote_material / 核价 union）

验证：后端日志 `quarkus.hibernate-orm.log.sql=true` 下计数，N=1 与 N=5 两次的条数**相同**。
