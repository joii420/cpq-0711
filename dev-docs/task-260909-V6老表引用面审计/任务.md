## ① 背景与目标

### 为什么现在做

报价侧数据已整体迁到 `ds_quote_*` 新表体系，但 V6 老表**没有随之退役**，形成一个所有人都以为已经死掉、实际还在供数的中间层。
2026-09-09 的退役评估（`INDEX.md §6` 有完整结论）暴露了三个**被广泛相信但实测不成立**的前提：

## ③ 已知量具陷阱（必须先解决，否则整份清单的数字全是废的）

这一节是本任务与「再 grep 一遍」的区别所在。**四个陷阱全部已实测复现**，AC 逐个钉死。

### T-1 表名与列名同名 → 数字虚高 30 倍

`unit_price` 既是表名，也是 `production_energy` 的列名，还是大量 Java 字段/DTO 名。

```
/usr/bin/grep -rlaE "\bunit_price\b" main      → 59 个文件
/usr/bin/grep -rlaE "(FROM|JOIN|INTO|UPDATE)[[:space:]]+unit_price\b" main → 2 个文件
```

⇒ **裸 `\b` 计数不可作为引用面**。清单必须区分「作表名」与「同名列/同名字段」，且必须显式写出被排除的同名情况。
实测：10 张表里只有 `unit_price` 存在同名列（`pg_attribute` 全库扫描确认，其余 9 张 0 命中）。

### T-2 本环境 `grep` 是 `ugrep -I`，中文多的大文件被静默判为二进制返空

已有记录在案的事故（`docs/反模式.md` / 记忆）。**空结果不等于不存在**。
⇒ 全部检索必须用 `/usr/bin/grep -a`，并做一次对照实验留证（AC-12）。

### T-3 空结果不许直接当结论

评估阶段实测过一个真实例子：`component_sql_view` 对三张老表 **0 命中**，看起来像「配置层已经干净」——
但真实原因是那 135 段已被 V411 改写 + 取数配置器接管，现存于备份表 `component_sql_view_backup_260903`。
**「0」背后可能是「已迁走」，也可能是「pattern 写错了」，两者数字一模一样。**
⇒ 任一维度为 0 时，必须拿一个**已知存在**的引用点用同一 pattern 反查证明量具够得着（AC-13）。

### T-4 引用点是移动靶

`task-260909-已有产品抽屉数据源收敛`（并发会话，闸门 A 待放行）的 `B-1` 会：
- **删掉** `ExistingProductService` 读 `material_customer_map` 的那一支
- **保留** `LEFT JOIN v_compat_material_master`（其 `D-3` 已写死硬约束，不许直连 `ds_quote_material`）

⇒ 这两个引用点必须标「在途」并注明归属；对方已承诺合并后主动通知，届时刷新（AC-10）。
