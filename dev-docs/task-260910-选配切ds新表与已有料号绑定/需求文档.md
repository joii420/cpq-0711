## ① 背景与目标

### 1.1 为什么做：选配现在写的数据，在报价卡片上看不见

**实测的核心事实** —— 选配建的 14 个报价行，卡片上 15 个组件里**只有 3 个有数据**：

| 组件 | 有快照数据 | 数据来自 |
|---|---|---|
| `T260907-物料` | 14 / 14 | `ds_quote_material` |
| `T260907-物料BOM` | 14 / 14 | `ds_quote_material_bom` |
| `T260907-物料与元素BOM` | 14 / 14 | `ds_quote_element_bom` |
| **`T260907-自制加工费`** | **0 / 14** | 🔴 **选配写 `unit_price`，组件读 `ds_quote_self_process_fee`** |
| `T260907-组装加工费` / `-组装加工费年降` / `-年降系数` / `-成品其他费用` / `-来料固定加工费` / `-来料其他费用` / `-来料回收折扣` / `-来料年降` / `-电镀费用` / `-组成件其他费用` | 0 / 14 | 选配不写这些表 |

⇒ **用户在选配抽屉里选的工序，从来没在报价卡片上显示过。** 这不是推断，是直接证据。

**根因是写读两侧分家**：

| | 选配**写**哪张表 | 渲染侧**读**哪张表 |
|---|---|---|
| 自制工序 | `unit_price`（V6 老表，`cost_type='自制加工费'`） | `ds_quote_self_process_fee`（**10 段**组件 SQL） |
| 组装工艺 | `capacity`（V6 老表，`resource_group_no='QUOTE_ASSEMBLY'`） | `ds_quote_assembly_fee`（**2 段**组件 SQL） |

实测 `component_sql_view` 全库 **98 段**，对 `unit_price` / `capacity` 的表名位引用是 **0 段**。
`capacity` 更极端：**全库零渲染消费方**（Java 表名位只有 `ConfigureProductService` 自己、组件 SQL 0 段、`pg_depend` 视图依赖 0 个）。

### 1.2 第二个问题：「已有零件」搜索搜不到料号

`search-parts` 读 V6 老表 `material_master`：

| 候选源 | 行数 |
|---|---|
| `material_master`（**当前读的**） | **48** |
| `ds_quote_material` | **2727** |

**真实料号验证**：`T260907M-AC17ANCHOR` 走该端点的实际 SQL 命中 **0** 条，走 `v_compat_material_master` 命中 **1** 条。
⇒ **漏掉约 98% 的料号。**

同时 `material_master.material_recipe_id`（老 SQL 靠它带出材质信息）实测 **48 行只有 1 行非空（2%）** ⇒ 材质三列对 47/48 行全靠 `COALESCE(…, mm.material_type)` 兜底成料号类型字符串。**材质信息几乎从来就没有过。**

### 1.3 目标

1. **选配写入侧切到 `ds_quote_*`**，让选配填的工序真正显示在卡片上；
2. **选配读取侧切到 `ds_quote_material`** 并按客户过滤，让「已有零件 / 外购件」能搜到全部料号、且不串客户；
3. **带版本数据改走 `_record` + 核价通过回填**（D-7），把「新料号进主数据库」纳入核价审核闸门；
4. **补上「客户产品编号不存在但销售料号用已有的」这个功能缺口**（D-12）。

**不做会怎样**：选配功能的工序采集形同虚设（用户填了看不见）；「已有零件」路径实际不可用；新料号绕过核价审核直接进主数据库。

📌 **存量数据不迁的后果实测为 0**（D-13）：在 `unit_price` 但不在 `ds_quote_self_process_fee` 的缺口 = **27 个客户×料号组合**，被 **21 张单**（12 `APPROVED` + 9 `DRAFT`）的 23 个明细行引用；但查这些单的工序页签当前状态 —— `T260907-自制加工费` / `自制加工费` / `加工费` / `T260907-组装加工费` **全部 0 行有数据**。⇒ **那些页签现在就是空的，不迁移不会让任何一张单变差。**
