## ① 根因（一句话）

**后端两条通道对同一组 BOM 行给出的行序不同，而前端 `comp.rows`（可编辑行数据）与展开 `exp.rows` 是纯下标配对，没有任何身份校正；`warmCardValues` 把通道从实时翻到快照的那一刻，行序变了、`comp.rows` 没人重排 ⇒ 整列错开一格。**

| 通道 | 行序 | 证据 |
|---|---|---|
| 实时 `batch-expand`（跑组件 `sql_template`） | `[00005, 00006, 根]` —— 根**排最后** | `component_sql_view.sql_template` 末行 `ORDER BY parent_no, material_no, "_物料BOM_项次"`；根分支 `parent_no` 恒 NULL，PG `ASC` 默认 **NULLS LAST**。已按真实客户+料号闭包**实跑复现** |
| 快照 `quote_card_values.baseRows` | `[根, 00005, 00006]` —— 根**排最先**（spine DFS） | DB dump，`__lvl=1` 根在 `ord=1` |
| 服务端 `row_data`（刷新后 `comp.rows` 的来源） | `[根, 00005, 00006]` —— 与快照同序 | DB dump `[{"row_index":0},{…00005…},{…00006…}]` |

### 精确到文件:行的机理

1. **配对是下标**：`QuotationStep2.tsx:3330` → `rowAt(i, activeComponent, renderSplit)`（`manualRows.ts:41`）把 `comp.rows[i]` 与 `activeDriverExpansion.rows[i]` 硬配对。
   INPUT 单元格的值 **只读 `row[key]` = `comp.rows[i][key]`**（`QuotationStep2.tsx:2660-2661` 注释明写「INPUT 受控值仍读 comp.rows，不叠加 editRows」；`ComponentCell.tsx:613`）。
2. **`comp.rows` 是实时期 bake 出来的**：`QuotationStep2.tsx:2500-2560` 的 bake effect 按 `exp.rows[ri].basicDataValues` 写 `comp.rows[ri]`，守卫 `bakedRef` 的 key 是 **`${componentId}-${ri}-${key}`——只有下标，没有行身份**。
3. **通道翻转时没人重排**：`QuotationWizard.tsx:929-955` 的 `syncLineItemsFromResponse` 只 patch `id / partVersionLocked / 四份值快照`，**一个字都没碰 `componentData[].rows`**。
4. **为什么最后一行反而是对的**：实时期 `ri=2` 是根行、`basicDataValues` 全 null ⇒ `resolveInputDefaultForBake` 返 `undefined` ⇒ `if (v == null) continue;`（`:2542`）**发生在 `bakedRef.add` 之前** ⇒ 守卫没登记 ⇒ 翻到快照后 `ri=2` 变成 00006，被重新烘一次 ⇒ 正确。

⇒ **这解释了「错开一格」而不是别的错法，也解释了「偏偏第 3 行对」这个反直觉细节。**

### ❌ 判否：F-2 的 AP-31/AP-38 推测（path cache 缺行维度）

- BASIC_DATA 的 `globalPathCache` 在本页签**根本没参与**：9 个字段全是 `INPUT_TEXT`/`INPUT_NUMBER`（`default_source.type=BASIC_DATA`），走 bake 写 `row[key]`，不走 path cache 渲染分支。
- 若真是「path 级缓存取到最后一个值」，3 行应当**全部**显示 00006 的值；实测是 `00005 / 00006 / 00006` 的**平移**，不是重复。
- ⇒ 不是缓存维度问题，是**行序 + 下标配对**问题。

### 🚨 顺带发现：这是一个**先于 F-2 存在的结构性缺陷**，不是 F-2 引入的

同一个下标错配在「刷新打开一张 `quote_card_values` 仍为 NULL 的单」时**同样成立**（`comp.rows` 来自服务端 spine 序，`exp.rows` 来自实时 SQL 序）。
本模板 9 列全是 INPUT（只读 `comp.rows`）⇒ 肉眼看不出；**但 BASIC_DATA / FORMULA 列读的是 `exp.rows[i].basicDataValues`**，在这类模板上会直接错行。
📌 **此推论未真机验证**，据代码路径推得，列在这里供主线定范围。

### ⚠️ 附带风险（只报不动）

misalign 窗口内若触发 `autoSaveDraft`，`comp.rows` 会按错位顺序落 `row_data` ⇒ **真数据错行**。
本次样本单 `75edd250` 的 DB `row_data` 实测**是正确的**（没被污染），但这是时序侥幸，不是机制保证。

## ② 🚦 修法有 2 种，按 `CLAUDE.md` 闸门 A0 **不许我自己选**

### X1 · 通道翻转时把服务端权威行灌回 `comp.rows`（**我的推荐**）

在 `QuotationWizard.tsx` 的 `syncLineItemsFromResponse` 里，当响应行带 `componentData[].rowData` 时，一并重灌 `comp.rows` —— 与刷新路径（`enrichComponentData.ts:89` 解析 `saved.rowData`）逐字同源。

| 维度 | 说明 |
|---|---|
| **改动面** | `QuotationWizard.tsx` 1 处、约 10 行；`tryParseSnapshotJsonLossless` **已在该文件导入**（`:57`）。零新文件、零新函数、不碰渲染主链路、不碰后端 |
| **为什么天然安全** | `ensure-card-values` 返回的是 `quotationService.getById(id)` 整份 `QuotationDTO`（`QuotationResource.java:283`），**含** `componentData[].rowData`（`QuotationDTO.java:307`）；而 `saveDraft` 的瘦身响应 `SaveDraftResponse` **结构上根本没有 componentData**（`:100` 注释原文「不含 componentData」）⇒ 一句 `Array.isArray(r.componentData)` 守卫即可把重灌**只**限定在 warm 这条路径，autoSave 路径逐字节不变 |
| **有直接先例** | `QuotationStep2.tsx:2356` 的 `applyQuoteProjection` 做的就是同一件事，注释原文：「前端整段替换两存储 → **comp.rows 与 buildSnapshotExpansions 展开恢复同序对齐**」。本次等于把删除路径已有的不变量补到 warm 路径 |
| **对 AC-R6 的效果** | 重灌后 `comp.rows` **就是**刷新后那一份 ⇒ 断言 ④「刷新后与不刷新逐字节一致」按构造成立；断言 ①（根行全空）由 `{"row_index":0}` 直接满足 |
| **风险** | warm 轮询最长 16s，窗口内用户手打的单元格会被服务端值覆盖。⚠️ 但同一次响应里 `quoteCardValues` 本来就在覆盖，成对覆盖反而比现在半新半旧一致 |
| **不解决** | 上面那条「刷新 + cardValues 仍 NULL」的潜在错行（实时通道单独存在时） |

### X2 · 给 `comp.rows` 做身份重排（结构性修法）

在 ProductCard 里为每个组件记住上一轮展开的行身份（`driverRow` 归一化指纹，两条通道同源于同一段 SQL ⇒ 可跨通道比对），展开换序时按身份重排 `comp.rows`，而不是按下标。

| 维度 | 说明 |
|---|---|
| **改动面** | `QuotationStep2.tsx` 新增一个 effect + 一个 ref，约 40~60 行，**落在渲染主链路** |
| **优点** | 连「刷新 + cardValues NULL」那条潜在错行一起治；保住用户在实时窗口里的手工输入（重排而非覆盖） |
| **风险** | ① 指纹要跨通道稳定：快照侧数值经 lossless 解析成 DecimalString（`"1"`），实时侧是裸 number（`1`），必须归一化比对，比错了会**静默重排错行**；② 身份戳只能放 ref（放进 row 会被持久化进 `row_data` 造成污染）⇒ 刷新后 ref 清零，只能覆盖「同一挂载周期内的换序」；③ 影响**所有** driver 组件，不只树页签 —— 回归面远大于 X1 |

### X3 · 改 SQL `ORDER BY parent_no NULLS FIRST`（**我判否，列出仅为排除**）

那是**每个组件的 `component_sql_view.sql_template` 配置数据**（不是代码），且多层树的 spine 序是 DFS，平铺 `ORDER BY` 根本复现不了。治标且不通用。

## ③ 我的推荐与理由

**推荐 X1。** 三条理由：
1. 它把**已经存在的不变量**（`applyQuoteProjection` 那句注释）补到唯一漏掉的那条路径上，不是发明新机制；
