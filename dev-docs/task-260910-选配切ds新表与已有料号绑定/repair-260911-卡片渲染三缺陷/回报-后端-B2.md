### 1.4 🔴 诊断 §2「时序实证（决定性）」站不住 —— 用户那一刻 DB 里**是有**卡片值的

诊断据「截图 07:39:32 UTC，`quote_values_at`=08:43:09 UTC，晚 64 分钟 ⇒ 那一刻快照没算出来」下的结论。
**`quote_values_at` 是 last-write-wins 的一列**（诊断自己在 U2 提过，但判为「影响小」而略过）。主仓 8081 dev server 日志（`…/54527263-…/scratchpad/quarkus-restart.log`，时间为本地 PDT = UTC−7）显示：

`ConfigureProductResource:78-88` 的顺序是 `ensureStructure` → per-line `snapshotLineValues`，而 `snapshotLineValues` → `snapshotQuoteSideOnly`（写 `quote_card_values`）→ `snapshotCostingSideOnly`（上面那 4 条 expand 日志）。

同一日志里 **全程没有 `12a5cee8` 的 `savedraft-invalidate`、也没有 `ensure-cardvalues-batch`** ⇒ 用户那 32 秒里既没保存草稿、也没触发 warm，纯粹是「选配完 → 直接看卡片」。

### 1.5 🐞 顺带挖出一个**没人报过**的后端缺陷（只定位，未改）

用户截图前 31 秒，日志里连刷 4 条：

```
00:39:01.519 WARN [ComponentDriverService] [snapshot-read] line=96ff4a3a… comp=7f9a5bbf…
  读快照失败,回退实时: Unrecognized field "__lvl" (class ExpandDriverResponse$Row),
  not marked as ignorable (2 known properties: "driverRow", "basicDataValues")
```

`ComponentDriverService.tryReadSnapshot`（`:275-307`）把 `snapshot_rows` 反序列化成 `ExpandDriverResponse.Row`，而 `Row` 只有 `driverRow` / `basicDataValues` 两个属性、**没开 `ignoreUnknown`** ⇒ **任何树页签的快照都必然抛异常、必然降级实时**。
⇒ batch-expand 的「快照快路径」对树页签**恒定失效**（性能上也是白干一次 IO + 一次实时展开）。
🚫 **本次没动它**（属 `R-4` 判否的 C1 邻域，且要不要让实时通道带 spine 是裁决事项）。**建议登记 BACKLOG**。

## 2. 两个落点的调研结论（按主线要的四项逐条答）

### 落点甲 · 建单收尾同步 `ensureCardValues`

| 项 | 结论 |
|---|---|
| **改动面** | `ConfigureProductResource.configureProduct` 末尾加一句 `cardSnapshotService.ensureCardValues(quotationId)` |
| **墙钟代价（实测）** | 值已就绪时 `POST /{id}/ensure-card-values` = **0.200s**；把本行两列置 NULL 后冷算 1 行 = **0.451s**。<br>⇒ 加上去约 **+0.2s**（configure 本身 1.0s）。📌 backtask 引的「1845 行 9~12s」是整单大单口径，**单个选配产品差两个数量级** |
| **风险** | 与 `snapshotLines` / `syncRecordsForFlow` 的顺序不打架（`D-21` 裁的是 `syncRecordsForFlow` 必须在两段物化**之后**；ensure 插在它之前即可）。但—— |
| **对 AC-R4 的影响** | 无。`ensureCardValues` 的 missing 谓词只选 `IS NULL` 或带 `__cardValueFailed` 的行；合法空卡片 `{"tabs":[]}` 非 NULL、无标记 ⇒ 不重算、不阻塞 |
| 🔴 **致命问题** | **它解决不了本缺陷。** 卡片值本来就已经算好了（§1.1），ensure 会选中 0 行、立刻返回。前端内存态照样没有 `quoteCardValues` ⇒ 照样平铺。**改了也不会变绿。** |

### 落点乙 · 渲染侧闸门（`useSnapQuote=false` → Spin 到 warm 完成）

| 项 | 结论 |
|---|---|
| **改动面** | 纯前端。`CardValuesWarmBoundary.tsx` + `cardValuesWarm.ts` 已就位，`QuotationWizard.tsx:2347` 已经把 `warming={cardValuesWarming}` 接上了 —— **壳子是现成的，缺的是「谁去触发」** |
| **墙钟代价（实测）** | 一个选配产品 = ensure 一次 **0.20~0.45s**。大单（如 `5f641c55` 1200 行全 NULL）才会到 9~12s 量级，但那条路径是「打开报价单」，`loadQuotation:748` **今天已经是同步 await + 轮询**了，本次不改它 ⇒ **大单转多久 = 今天转多久，无增量** |
| **风险** | `CardValuesWarmBoundary` 用的是 antd `Spin spinning`（遮罩 + children 仍在 DOM），**不是整块隐藏** ⇒ 砍不掉「实时兜底」，只是把它盖住；降级路径仍在 |

## 3. 🚦 我的推荐：落点乙的一个**最小变体**（记为「丙」），请主线裁决

**动作**：`QuotationWizard.tsx` 的 `onConfigureConfirm`（`:1809`）末尾补一句已有的
`warmCardValues(quotationId, basicItems)`。

**为什么是它**：

1. **它正对根因** —— 缺的就是「新加的这一行没人去把已算好的卡片值取回来」。`warmCardValues`（`:962`）内部正好干这三件事：`shouldWarmCardValues` 判定 → `ensureCardValues` → `syncLineItemsFromResponse` 回灌 `quoteCardValues`。回灌后 `useSnapQuote` 翻 true ⇒ **无需刷新就变成树**。
2. **零新代码路径** —— 函数、闸门、Spin 壳、超时上界、失败提示全是现成的，`saveDraft` 那条路径已经这么用了（`:1035`）。
3. **代价 0.2~0.45s**，且 `cardValuesWarmGateRef` 会自动把 Spin 打开，用户看到的是「转一下就出树」而不是「先平铺后跳变」。
4. **AC-R4 天然满足**（§2 乙那行）。

**⚠️ 但它是前端改动 ⇒ 按 `F-2` 的约定，这条要回流给前端工程师。** 后端侧本条 **无代码可改**。
