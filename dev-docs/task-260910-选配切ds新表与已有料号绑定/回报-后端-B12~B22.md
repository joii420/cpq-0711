## 4. 规避掉的坑（12 条，逐字要点）

1. **没有改 `resolvePart` 的签名** —— 那几行正是 B-1/B-3/B-10 在改的地方，改签名等于互相打掉。改用 `SelQuotationScope`（本仓惯用的作用域对象）。

6. **patch 层加了「合成根行不追加」** —— `ds_quote_material_bom_record` 全库 9636 行里 **9235 行**是非轴列全空的树渲染构件，无脑追加就是一片空白行。

### ① B-16「投影侧补 `material_ratio`」—— **在投影层做不到，D-10 的落点应改写**
> 实测根因（不是漏写，是**数据不在卡片里**）：全库对 `ds_quote_material_bom` 建绑定的 4 个组件里，**只有 1 个有「材料占比（%）」字段**：
>
> | 组件 | 有 `material_ratio` 列? |
> |---|---|
> | `T260907-物料BOM` (f6d51727) | ✅ `builder_config` 里有 `sourceColumn: material_ratio` |
> | `BOM` (7f9a5bbf) / `BOM` (452bbdbe) / `BOM` (eb834021) | ❌ 三个都没有 |
>
> `DsRecordProjector` 只能产出**页签表征的列**（`binding.fieldToColumn()`）⇒ 页签没这个字段，投影层拿不到值，「补」无从下手。**这正是 12.2% 填充率的来源**：填上的 49 行全部来自那个有该字段的组件。
> ⇒ **把 B-16 落在了 B-12 的直写路径上**（已实测 `_record` 与主表都是 `100.000000000000`）。
>
> ⚠️ **残留风险**：如果客户模板用的是那 3 个**没有占比字段**的 BOM 组件，提交时 `syncRecords` 的覆盖式重写会把直写进去的 `material_ratio` **抹成 NULL** ⇒ AC-14②/AC-12 在那种模板下会红。
> **可选修法（需裁决）**：在 `syncRecords` 里加「页签没表征的列，从被替换的那条既有 `_record` 行**继承**」（= 把 `DsBackfillCollector.preservedColumns` 那条列级 patch 纪律用在 `_record` 重写上）。对导入侧是 no-op ⇒ AC-15 仍逐字一致，但**它动的是 `syncRecords` 这条导入 + saveDraft + submit 三路共用的写入面**，属跨任务改动 ⇒ **停手报主线**。

### ② B-17 的根因判定与任务书不一致，且「已修好」的证据指向别人的提交
> 任务书写「同单同料号多 line item ⇒ 同内容行出现两份」。**逐行核了复现单，不是这个形状：**
> ```
> 单 08c99680 · 卡片 f69cad35（S0001）的 snapshot_rows = 8 行，是 4 组两两完全相同的行：
>   [1]=[2] __nodeId=S0001            (合成根行)
>   [3]=[4] __nodeId=S0001/S0003
>   [5]=[6] __nodeId=S0001/S0002
>   [7]=[8] __nodeId=S0001/S0002/992
> 另一张卡片 cb2ce85c（同料号）也是同样的 8 行。
> ```
> ⇒ **重复发生在单张卡片内部**（`snapshot_rows` 本身把每个 spine 节点渲染了两遍，**用户在卡片上看到的也是双份行**），不是跨卡片投影。跨卡片那部分 D-43 的 `dedupe` 是好的 —— 它按 `occurrenceKey` **刻意含 `lineItemId`**，结构上就不许收敛同卡片内部的行（AP-60 纪律）。这也解释了两条 `_record` 行为何逐字节相同、只差 `origin_id`。
>
> **更关键：这个形状在今天的 HEAD 上复现不出来。** 造了完全同型的数据（单 `2d45b3e8`：同一张单、同一料号 `S0004`、两个 line item、且 `S0004` 同挂两客户）→ 每张卡片 `BOM|6`（不是 12），`_record` **0 组重复、`unanchored=0`**。

>
> **做了什么**：仍加了 `dropAnchorShadows` 作为 `_record` 侧止血（同卡片 + 同为 DRIVER + 逐列相同 + 一条锚上一条没锚上 才丢），零误伤已实测；但**它是否真能修掉那个形状，未验证**。

### ③ 「按列 COALESCE 覆盖」在渲染层不可实现（`api.md §4` 同一条）
> `_record patch` 的关联键契约写的是 `_record.origin_id → 主表.id`。但渲染层拿到的 `driverRow` 是**视图输出行**，身上**没有主表 `id`**（组件 SQL 不 select 它，且 D-8 要求 SQL 一段不改）⇒ **这条关联在那一层建不起来**。
> 实现改成：**只追加 `origin_id IS NULL` 的行 + 按内容去重**，不做同行的列级覆盖。理由：`origin_id` 非空意味着主表已有那一行、组件 SQL 已经读出来了；用户对它的编辑走 `row_data` 覆盖层。**D-9 的列级覆盖在回填侧已经有了**（`DsBackfillCollector.buildGroup` 的 `patchedColumns`），没重写它。
> ⇒ 需确认此偏差是否接受；若接受，**`api.md §4` 的「`_record` patch 合并」应改写成「渲染侧=追加+内容去重 / 回填侧=按列 COALESCE」两段**。

### ④ AC-15 的前置事实不成立
> AC-15 写「`ds_quote_material_bom_record` 现有 `source='IMPORT'` 的存量行」。实测**一行都没有**：
> ```
> SELECT source, count(*) FROM ds_quote_material_bom_record GROUP BY 1
> → QUOTE_DRAFT|9636      （只有这一种 source）

> `_record` 唯一的 source 常量是 `DsQuoteRecordService.SOURCE_QUOTE_DRAFT`；导入建单也走同一投影、同样写 `QUOTE_DRAFT`。⇒ **AC-15 断言应改成「导入建单产生的 `_record` 行（`source=QUOTE_DRAFT`）行为逐字一致」**，否则测试员会去找一组不存在的行。

### ⑤ 「同一(单,料号)多个树根行」按交代**没有动**
