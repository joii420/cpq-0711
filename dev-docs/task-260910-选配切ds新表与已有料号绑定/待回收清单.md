## 5. 🚦 回收前必须先量化 FK（本任务的教训）

删报价单**不能只删 `quotation` + `quotation_line_item`**。实测 **9 张表**指向 `quotation`：

| 删除行为 | 表 |
|---|---|
| **CASCADE 自动级联** | `quotation_line_item` · `quotation_view_structure` · `quotation_component_sql_snapshot` · `quotation_price_revision` |
| **NO ACTION 必须先删子行** | `costing_order` · **`import_record`** · `quotation_approval` · `quotation_withdraw_request` · `material_price_update_job_item` |

📌 **主线在删那 2 张哨兵单时第一次量化就漏了 `import_record`，靠事务整体回滚才没出事。**
⇒ 回收时请让执行方**先跑 `pg_constraint WHERE confrelid='quotation'::regclass` 查全 FK 图**，再按依赖顺序删，🚫 不要逐张试。

**建议的回收顺序**：`costing_order` / `import_record` / `quotation_approval` 等 NO ACTION 子表 → `quotation`（CASCADE 带走 4 张）→ `sel_part_signature` → `ds_quote_*` 业务行 → `ds_quote_material`（**必须最后**，B-23 报告明确「先删单再删料号」）

**可恢复性**：🚫 **不可恢复**（无备份、不能由迁移重建 —— 都是运行时业务数据）。但**可重新造**（跑一遍选配即可重建同型数据）。
📌 例外：主线删那 2 张哨兵单前导出过 CSV，存在本次会话 scratchpad（会话结束即失效）。
