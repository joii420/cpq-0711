## 一、为什么要做（已实证的逻辑缺口）

**前端校验是唯一的守门人，服务层没有对应的不变量。**

`QuotationCreateForm.tsx:227` 的 `isValid` 挡住了正常用户（没选模板则「下一步」禁用），但服务层对模板绑定的校验强度层层递减：

| 入口 | 现状校验 |
|---|---|
| `QuotationService:239` create 的 `customerTemplateId` | **无任何校验**（靠外键兜，写不存在的 id → 500） |
| `QuotationService:272` create 的 `costingCardTemplateId` | 只校验**存在性**（查不到则 `LOG.warnf` + 静默忽略），不校验状态/类型 |
| `QuotationService:343/344` saveDraft 两个字段 | **连存在性都不校验** |
| `QuotationService:1465` copy 换模板的 `customerTemplateId` | **不校验**（端点直接收 body 里的任意 id） |

后果链（已核实每一环）：
1. 绕过 UI 的调用（脚本 / E2E / 直接打 API）可把报价单绑到 **DRAFT** 模板；
2. `TemplateService:181` 允许删除 DRAFT 模板（删除入口全仓唯一，就这一处）；
3. 于是 `quotation_costing_card_template_fk` 的 `ON DELETE SET NULL` 被激活 → 报价单核价侧关联**静默置空**（症状=核价单视图空白，且无任何记录可溯源）；报价侧 `customer_template_id` 是 `NO ACTION`，表现为删除报 500（可见但形态差）。
4. 同源问题：`customer_template_id` 为空的那 8 张 DRAFT 单，全部由程序化路径创建——正是"服务层无不变量"的产物。

> 已排除的担心：正常路径下 `SET NULL` 走不通（能绑的是 PUBLISHED、能删的是 DRAFT，两集合不相交；`template.status="DRAFT"` 全仓只有 `TemplateService:128` 新建初值与 `:463` 复制为新草稿两处，**无 PUBLISHED→DRAFT 原地降级**）。`material_master.material_recipe_id` 的 SET NULL 也走不通（删除端点走 `deleteSoft`，从不物理删）。**本任务补的是"绕过 UI"这条路。**

## 二、不变量定义（**语义已裁定，逐字实现**）

新增一个私有校验方法，三个入口共用。语义：

```
校验(templateId, expectedKind, currentValue):
  1. templateId == null            → 直接返回（保持既有"null 不覆盖"语义，不是绑定动作）
  2. 模板不存在                     → 400
  3. 模板类型 != expectedKind       → 400
  4. templateId == currentValue     → 放行（维持原绑定，不是新绑定 —— 见 §2.2 回归防护）
  5. 模板 status != 'PUBLISHED'     → 400
```

### 2.1 类型校验（本次新增的第二个不变量，别漏）

- `customer_template_id` 只能绑 `template_kind = 'QUOTATION'`
- `costing_card_template_id` 只能绑 `template_kind = 'COSTING'`
- **现状完全没有类型校验** —— 可以把核价模板绑到报价字段上，那是比状态错更严重的错配（下游整套渲染都会错）
- `template_kind` 为 `null`/空白时按 **`QUOTATION`** 兜底，与 `TemplateService:124-128` 的默认值口径一致
- 库内实测值域：`QUOTATION`(5) / `COSTING`(2)，全部 `PUBLISHED`

### 2.2 状态校验必须豁免"值未变化"（**最关键的一条，防回归**）

`status` 值域 = `DRAFT` / `PUBLISHED` / `ARCHIVED`（`chk_template_status`）。

如果无条件要求 `PUBLISHED`，会引入一个**新的回归**：模板被归档（ARCHIVED）后，所有引用它的**历史草稿单再也无法 saveDraft**（前端每次保存都会把同一个 templateId 回传）→ 用户被彻底锁死在编辑页。

所以规则是：**新绑定必须 PUBLISHED；维持原值一律放行**（不管目标模板此刻是 PUBLISHED 还是 ARCHIVED）。

### 2.3 各入口的 `currentValue` 取值（逐个确定，不要凭感觉）

| 入口 | expectedKind | currentValue | 效果 |
|---|---|---|---|
| `create`（`:239` customerTemplateId） | QUOTATION | **null** | 新建无原值 ⇒ 一律严格要求 PUBLISHED |
| `create`（`:261-272` costingTemplateId） | COSTING | **null** | 同上 |
| `saveDraft`（`:343` customerTemplateId） | QUOTATION | `q.customerTemplateId`（库内现值） | 值未变则豁免 |
| `saveDraft`（`:344` costingCardTemplateId） | COSTING | `q.costingCardTemplateId` | 同上 |
| `copy`（`:1465`，`newTemplateId`） | QUOTATION | `source.customerTemplateId` | 同模板复制（含 `templateId==null`）⇒ 相等 ⇒ 豁免；换模板 ⇒ 严格 PUBLISHED |
| `copy`（`:1466` costingCardTemplateId） | — | — | **不校验**：`= source.costingCardTemplateId` 是延续既有绑定，不是新绑定 |

`copy` 那行的自洽性已推演过：`newTemplateId = (templateId != null) ? templateId : source.customerTemplateId`，三种情况（换模板 / 显式传同一个 / 传 null）都落到正确分支。

### 2.4 行为变更声明（有意收紧，需在报告中确认）

`create` 的 costingTemplateId 现状是「查不到 → warn + 静默忽略」，本次改为 **400**。这是有意的：静默忽略会让用户以为绑上了，实际没有。若某条既有调用依赖这个宽容行为，测试会暴露出来——**暴露即修调用方，不要为了让测试过而放宽不变量**。

### 2.5 错误信息必须可定位

每种失败都要带上 `templateId`、以及期望/实际值（kind 或 status）。禁止只抛「模板无效」。

1. 新增私有方法（建议签名，名字可微调但语义不可变）：
   ```java
   private void validateTemplateBinding(UUID templateId, String expectedKind, UUID currentValue)
   ```
   按 §二 的 5 步语义实现，抛 `BusinessException(400, ...)`。
2. 在 §2.3 表格列出的 **5 个调用点**前插入校验（`:1466` 不加）。

4. 不要改动 `V6QuotationCommitService`——它透传给 `create`，自动受新校验保护（`:59` 已确认）。
