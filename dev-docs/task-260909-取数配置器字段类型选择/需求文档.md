## ① 背景与目标

### 起点

用户在 `task-260909-核价树骨架分档与轴口径统一` 交付后配置核价模板亲测，提出两条业务规则：

> 1. 核价侧数据是**只读**的，在报价单中不可以切换版本
> 2. 核价侧数据在**核价单**中打开可以切换版本

主线核对现状：规则 2 ✅ 已实现；规则 1 的「不可切版本」✅ 已满足（编辑页版本列是 `disabled` 的 `<select>`）；
**规则 1 的「数据只读」❌ 未满足** —— `QuotationStep2.tsx:3749` 无条件传 `readonly={false}`，核价页签的单元格是可编辑 `<input>`。

用户随即指出更根本的一层：**「字段设置是否应该直接设置为基础数据类型而不是输入框类型？」** —— 主线核实后确认这是对的。

### 根因：配置器产出的字段类型与其语义不符

```
BuilderService.java:880   String fieldType = "TEXT".equals(col.resolvedDataType) ? "INPUT_TEXT" : "INPUT_NUMBER";
BuilderService.java:881   String effectiveFieldType = col.fieldType != null ? col.fieldType : fieldType;
sqlViewBuilderService.ts:17  「不传 viewColumn/fieldType」
```

- 后端**支持** `BASIC_DATA`（`:890` 有分支，写顶层 `basic_data_path`），`ConfigGuideDrawer` 也明确推荐它
- 但**前端配置器不发 `fieldType`，界面上也没有选择器** ⇒ 恒落到按数据类型推的 `INPUT_*`
- 而这些字段的语义是「从 SQL 视图取的展示值」，**不是用户输入**

### 渲染层的后果（这才是它值得修的原因）

`ComponentCell` 的分支：
```
field_type === 'BASIC_DATA'  → 走统一 fallback 链，纯展示，不产生 <input>，与 readonly 无关
field_type === 'INPUT_*'     → readonly=false 时是 <input>
```

⇒ 核价页签今天是 **「看起来能改、改完存不住」**：
- 增量写路径 `quote-card-edit` 是**报价侧专有**（`useSnapEdit = cardSide === 'QUOTE'`，`QuotationStep2.tsx:2684`）
- **整单 `saveDraft` 也不触发保存**（**用户 2026-09-09 亲测**）
- 佐证：`quotation_line_component_data` 里核价模板组件 **0 行**（该单 09-09 建、渲染过多次）

用户打字 → 失焦 → 刷新 → 没了，**全程不报错**。正是 `task-260909-核价树骨架` 一路在消灭的那类静默丢失。

### ⚠️ 开工后发现：`F-3` 单独做会引入全面回归（2026-09-09 并入范围）

后端子代理在 §0 检查点 #4 报出一条契约缝，主线核实后确认**比它描述的更严重**：

```
存量 4 个 COST_BASIC 组件：builder_config.columns[].fieldType 全为 null（6/6 · 12/12 · 8/8 · 7/7）
                          而 component.fields[].field_type 真实为 INPUT_NUMBER / INPUT_TEXT
QUOTE 侧 38 个组件同理（builder_config 从来没存过 fieldType）
⇒ 影响面 42 个存量组件 / 344 个字段
```

链条：
1. **今天**前端不发 `fieldType` → 保存时后端按规则重推 → 结果与原值相同，**无害**
2. **`F-3` 让前端开始发** → 发的是**回填值**，而回填拿到 `null` → 兜底（`SqlViewBuilderTab.tsx:263` 现为 `bc.fieldType || 'INPUT_TEXT'`）
3. 用户打开存量组件、**什么都不改直接保存** → 兜底值被写进 `field_type`

**两种兜底都坏事**：兜 `INPUT_TEXT` → NUMBER 列降级为文本；兜方言默认 `BASIC_DATA` → 存量被静默改类型。
🔑 **根子是「界面显示的 ≠ 实际生效的」** ⇒ 修法方向唯一：**让回填显示真实值**（交付项 7）。

📌 **这不算扩范围** —— `F-3` 不带上它就是交付一个回归。

### 目标

1. 让配置器**能表达**「这个字段是只读展示」这个语义
2. 核价两套数据集（`COST_BASIC` / `COST_DETAIL`）**默认**就是 `BASIC_DATA` —— 把用户的规则 1 落到配置层
3. 报价侧维持现状（那边用户确实要填数）
4. 堵住后端 `fieldType` 零校验这个静默故障面

### 不做会怎样

用户「重新配模板」拿到的仍是 `INPUT_*`，核价页签继续出现可编辑输入框、继续存不住 —— 问题原样重现。

## ③ 验收标准（AC）

> 统一环境：dev server + 默认 profile 库 `cpq_db_0724`；配置器入口 = 组件管理 → SQL 视图配置。

### 一、选择器本体

**AC-1（单点）** 在配置器的列配置区，每一列出现「**字段类型**」选择器，展开后**恰好 3 个**选项：`基础数据(BASIC_DATA)` / `文本输入(INPUT_TEXT)` / `数字输入(INPUT_NUMBER)`。🚫 不出现 `FORMULA` / `DATA_SOURCE` / `FIXED_VALUE`。

**AC-2（单点）** 列配置区提供「**整列批量设为…**」入口，点击后所选值应用到当前所有列，逐列选择器同步变更。

### 二、按方言的默认值

**AC-3（单点·核心）** 新建一个 **`COST_BASIC`** 数据集的页签、选若干列、**不动任何字段类型选择器**直接保存：
落库后 `component.fields[]` 的 `field_type` **全部为 `BASIC_DATA`**，且每个字段写的是**顶层 `basic_data_path`**（形如 `$builder_xxxx.<列名>`），**不含 `default_source`**。

**AC-4（单点·核心）** 同样操作但数据集选 **`COST_DETAIL`**：结果同 AC-3（`field_type` 全 `BASIC_DATA`）。

**AC-5（单点·零回归）** 同样操作但数据集选 **`QUOTE`**：`field_type` 按列的数据类型推为 `INPUT_TEXT` / `INPUT_NUMBER`，且写的是 **`default_source.path`**（嵌套对象），**与改动前逐位一致**。

### 三、🔑 渲染等价（本任务风险最高的一条）

> ⚠️ **全部在自建的 DRAFT 产物上验，🚫 不碰 `核价模板1` / `QT-20260909-0661`**（那是 `task-260909-核价树骨架` 刚交付的东西）。
> 理由有二：① 已发布模板改字段要重编译 + 快照对齐，属 `CLAUDE.md §3.2` 边缘，不该为跑测试去碰；
> ② DRAFT 模板**读活表、不吃冻结快照**（`BomTreeRenderService` 的 `_bt18Status` 分支 + `lookupForResolver:412`），测起来更直接。
> 造数一律带前缀 `T260909FT-`。

**AC-6（单点·核心）** 用配置器在 **同一个 `COST_BASIC` 数据源**上建两个组件（同样的列、同样的字段名）：
`T260909FT-BASIC`（字段全配 `BASIC_DATA`）与 `T260909FT-INPUT`（字段全配 `INPUT_TEXT`/`INPUT_NUMBER`）。
把两者放进同一张 **DRAFT 核价模板** `T260909FT-模板`，绑到一张自建报价单并渲染：
**两个页签逐列显示的值逐字相同**（行数相同、每行每列的可见文本相同）。

> 🔑 **为什么这条风险最高**：`BASIC_DATA` 渲染读 `basicDataValues`，键是 **`{$view.column}`（带花括号）**，
> 而 `basic_data_path` 存的是 **`$view.column`（不带）**，中间隔着 `bnfDriverLookupKey()` 的键格式转换。
> 数据面已实测就位（`basicDataValues` 里 `{$builder_32ab8212df6c.component_qty}: 1`、`{…material_name}: "零件12"` 都在），
> **但转换对不对得上必须实测**。另：全库 `field_type='BASIC_DATA'` 的字段实测**只有 1 个**
> ⇒ 这条渲染分支几乎没有生产验证，🚫 不许假定它是对的。
> 📌 **同源双组件对照**是本条的关键设计：两边跑同一个 `$view`、同样的列，**唯一变量就是 `field_type`** ——
> 值不一致时能直接归因到本次改动，而不是"数据本来就没有"。

**AC-7（单点）** 在编辑报价单的核价页签打开 `T260909FT-BASIC` 页签：
其字段渲染为**纯文本**，页面上**不存在**承载它们的 `<input>` 元素；
同一张卡片的 `T260909FT-INPUT` 页签**仍是 `<input>`**（阳性对照，证明"没有 input"不是因为整页没渲染）。

### 四、边界

**AC-8（边界·非法值）** 直接调保存接口传 `fieldType: "FORMULA"` → **400**，消息列出 3 个合法值；传垃圾值 `"XXX"` → **400**；库中该组件字段**不发生变更**。

**AC-9（边界·向后兼容）** 保存请求**不传** `fieldType`（模拟旧客户端）→ 维持按数据类型推导的现状行为，**不报错**。

**AC-10（边界·行身份）** 把某页签的**料号列**配成 `BASIC_DATA` 后保存并渲染：该页签的行仍能正确归属到卡片（行数与改配前相同），`part_no_field` 仍指向该字段名。
> 依据：料号列/名称列/行键是按**字段名**推导的，与 `field_type` 无关 —— 本条验证该假设成立。

### 五、序列

**AC-11（序列）** 选某列为 `BASIC_DATA` → 保存 → **刷新页面重新打开配置器** → 该列选择器**回填为 `BASIC_DATA`**（与 `AC-39` 同款回填契约）→ 改回 `INPUT_TEXT` → 保存 → 再刷新 → 回填为 `INPUT_TEXT`。

**AC-12（序列）** 在 `T260909FT-BASIC` 上：把某列由 `BASIC_DATA` 改回 `INPUT_TEXT` → 保存 → 重新渲染 → 该列仍显示相同的值、但变回 `<input>`；再改回 `BASIC_DATA` → 保存 → 渲染 → 变回纯文本且值不变。
> 🚫 全程在自建 DRAFT 产物上，不碰任何已交付对象。

### 五点五、回填一致性（开工后并入）

**AC-15（边界·存量保护·核心）** 打开存量组件 `COMP-2299`（`builder_config` 里 `fieldType` 12/12 全为 null，库里真实为 `INPUT_TEXT`/`INPUT_NUMBER`）：
配置器各列的「字段类型」显示的是**库里的真实值** —— NUMBER 列显示「数字输入」、TEXT 列显示「文本输入」，
🚫 **不是**统一的兜底值；随后**什么都不改直接保存** → `component.fields[].field_type` **逐字不变**（12 个字段全部）。

> 🔑 这条是 `F-3` 的**回归门禁**。不过它，本任务就是在 42 个存量组件上埋一个「打开即损坏」的雷。

**AC-16（契约）** 任意一次 `save()` 之后，`builder_config.columns[].fieldType` **不再为 null**，
且其值与实际落库的 `component.fields[].field_type` **同名字段逐字相同**。

### 六、无副作用

**AC-13（无副作用）** 本次交付前后，**存量组件的 `field_type` 一个都不变**：
`COST_BASIC` 33 字段 / 4 组件、`QUOTE` 311 字段 / 38 组件的分布逐位相同（改动前实测基线见 §④）。

**AC-14（无副作用）** 报价侧编辑页仍**可编辑可保存**：用自建的 `QUOTE` 方言组件（`T260909FT-QUOTE`）验证 —— 其 `INPUT_*` 字段仍渲染为 `<input>`，改值失焦后 `quote-card-edit` 正常写入并可读回。
> 🚫 不在既有报价单上改数据。
