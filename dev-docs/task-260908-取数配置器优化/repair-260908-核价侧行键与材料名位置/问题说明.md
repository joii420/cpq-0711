## ④ 问题原因

### P-1 根因：查名字段是「追加」而非「插入」

`FieldTreeBuilder.java:387-389`
```java
if (isMain) {
    fields.addAll(syntheticLookupFields(snap, dialect, anchor, nodesWithOwnGroup));
}
```
`addAll` 追加到 `fields` 末尾，而此时 `fields` 已装完锚点全部物理列 ⇒ 材料名必然排最后。

**引入时间线**：本次新增 46 条查名边之前，`syntheticLookupFields` 在现网**产出 0 个字段**（`BL-0213` 缺口 G-A 原话：「当前数据下 39 个数据源产出合计 0 个」）⇒ **这段追加逻辑此前不可达，位置问题从未显现**。本次让它有了产出，位置问题随之暴露。

**为什么测试没拦住**：`AC-7` 断言的是「所在分组 `groupKind === 'MAIN'` + 不存在独立查名分组」—— **只验归属，没验顺序**。主线亲验照同一条 AC 核对，同样没看位置。**AC 写漏了，不是实现跑偏。**

### P-3~P-7 根因：语义图种子按「物理唯一性」推行键，而非「业务行身份」

`ROW_KEY` 标记是 `task-260819` 建图时按表的物理唯一约束推的，两者在核价侧不重合：
- 物料BOM 多标「工序编号 / 使用特性」—— 那是**行的属性**不是**行的身份**
- 电镀成本多标「电镀方案编号 / 版本编号」—— 同上
- 费用类少标「要素名称」—— 同一料号下有多条不同要素的费用，不带它**区分不开**

### 🔑 为什么现在才痛（这条决定了它算谁的范围）

| | 本次 F-2 之前 | F-2 之后 |
|---|---|---|
| 行键列怎么来 | 用户自己从字段面板拖 | **自动带出** |
| 配错了怎么办 | 可以不拖它、或拖别的 | **✕ 禁用，不可移除** |

⇒ 本次把「行键配置」从**用户可自选**变成**系统强制**，配置错误的后果被放大到每个新配的组件。
**这就是用户在验收本次交付时报出它的原因** —— 数据错误是既有的，但**是本次让它必然发生**。

**为什么测试没拦住**：`AC-14` 断言「不用拖拽就自动带出该源全部带 `ROW_KEY` 角色的列」—— 验的是**机制**，没验语义图里那些行键**配得对不对**。
📌 **判据落在机制层，缺陷在数据层。** 这类断言在数据错误时**恒绿**，因为它忠实地带出了「配置里写的那些列」。

## ⑤ 修复方案

> ⚠️ 只写 A0 裁决通过的方案。**本次范围 = P-1 + P-3~P-7，🚫 P-2 拆出不做。**

### R-1 · 材料名紧跟料号列（服务 E-1）

**文件**：`cpq-backend/src/main/java/com/cpq/builder/compiler/FieldTreeBuilder.java:387-389`

「追加到末尾」改为「**插到最后一个带 `PART_NO` 角色的列之后**」：
- 锚点组内存在 `PART_NO` 列 → 插在它后面
- 不存在 → 维持追加到末尾（行为不变）

🚫 **不许改 `syntheticLookupFields` 自身的返回内容与顺序** —— 它的 `coalesceGroup` 去重与 `AC-7` 的「不另起分组」都依赖现状。本次**只改插入位置**。

### R-2 · 核价侧行键修正（服务 E-2~E-6）

一个 Flyway 迁移，只 `UPDATE semantic_node_column.roles`，七类改动（表见 ③）。

🚫 **三条硬约束**：
1. `WHERE` 同时限定 `dialect IN ('COST_BASIC','COST_DETAIL')` 与 `node_key` —— **报价方言一行都不许动**
2. 只增删 `ROW_KEY` 这一个角色，**不得动同行其他角色**（`PART_NO`/`SORT`）。用数组增删而非整体覆盖
3. 🚫 **不动 `component.row_key_fields`**（裁决 `A0-3`）

**幂等**：`UPDATE` 用「先判断再改」写法，可重复执行。
**迁移号**：2026-09-08 四方核对 = 共享库 432 / master 432 / `target/classes` 432（本次已补齐 V431/V432）⇒ 拟用 **V433**，🚨 **写文件前必须重新四方核对**。

## ⑦ AC 订正记录（开工后）

> 两条都是**主线写错的量具**，由后端代理在执行中发现并纠正。**两次同一个形状。**

### `A0-5` · `AC-R5` 的量具灵敏度实验设计倒挂

**主线原写**：采**报价方言**（`dialect='QUOTE'`）快照 → 故意改一个**核价侧**角色 → 确认 diff 有输出，以此证明量具会动。
**问题**：`AC-R5` 的 SQL 带 `dialect='QUOTE'` 过滤，改核价侧角色**本来就不该让它动** ⇒ 那个实验**永远是空 diff**，拿它「证明量具会动」会得出**完全反向**的结论。
**订正**：用**同方言内**的改动证灵敏度（给某个 QUOTE 列加 `ROW_KEY` → diff 有输出），再把「核价侧改动 → QUOTE 快照零变化」当作**空白对照**。

### `A0-6` · `AC-R9` 的量具选错了层

**主线原写**：用 `order by ctid` 的错位量具重跑 → 错位列数**全部为 0**。
**问题**：那条 SQL 量的是**数据库堆顺序**；修法 A 是**Java 侧加 `ORDER BY`**，它让应用**不再依赖**堆顺序，但**不会去重排堆**。修完再跑仍是 11 行 —— 实测确认。
⇒ **按字面执行会得出「修复无效」的反向结论。**
**订正**：断言改到**改动真正生效的那一层**：
> 对每个数据源的 MAIN 组，**剥掉查名字段后的字段序列，必须逐项等于该节点 `sort_order` 升序**。

修复前会红（15 组不一致，`MATERIAL_BOM` 在 BOM/外购件/零件三个页签视图各出现一次）、修复后全绿（49 组零例外）—— **量具会动**。

### 🔑 两次的共同形状（值得升级成规则）

> **量具所在的层，和改动生效的层，不是同一层。**

- `A0-5`：判据带了一个把「变化源」过滤掉的条件 ⇒ 恒不动
- `A0-6`：判据量的是底层存储状态，而改动发生在读取层 ⇒ 恒不变

两者都属 `RECORD.md` 2026-09-07 那条的变体：**提出判据时先问「它有没有可能为假」**。这里要多问一句：**「它测的是不是我改的那一层」**。
