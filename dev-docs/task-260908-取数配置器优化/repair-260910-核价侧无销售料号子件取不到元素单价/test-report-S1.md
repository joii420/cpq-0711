## 3. AC-8 · `正泰模板` 未被误升版 ✅ 通过

**AC 原文**：`正泰模板` 的 `version` 仍为 `v1.0`、`updated_at` 与改动前相同、`status` 仍 `PUBLISHED`。

### 3.1 前置守卫先过（🚨 不过则本条判「不成立」而非「通过」）

`AC-8` 是一条「**什么都不该变**」的断言 —— `B-3` 若根本没执行，它会毫不费力地通过，那时它证明的是「什么都没发生」，不是「没误伤」。

```
| item                                | pass | version | updated_at                 | series_rows | series_detail                                               | snap_md5                         | 快照md5已变 | 快照含新函数(期望t) | 快照仍含双键(期望f) |
| 前置守卫·核价模板确已升版并重新冻结 | t    | v1.3    | 2026-09-11 06:25:39.215990 |           4 | v1.0/PUBLISHED,v1.1/PUBLISHED,v1.2/PUBLISHED,v1.3/PUBLISHED | b55f134c1fc5a3027bd2a5c812c4628b | t           | t                   | f                   |
```

⇒ `核价模板` 最新 `PUBLISHED` 版为 **v1.3**，快照已换成单键新函数（含 `f_customer_element_price`、不含 `cep.material_no`）。**守卫通过，`AC-8` 的「没变」不是空跑。**

> 📌 守卫的两处设计在本次实战中都兑现了：
> ① **不锁死行 id、按 `template_series_id` 取最新 `PUBLISHED` 行** —— series 现有 **4 个 PUBLISHED 版本**（v1.0/v1.1/v1.2/v1.3），锁死 id 会取到 v1.0 而恒判 `f`；
> ② **故意不看 `updated_at`** —— 实测该字段会被 realign 类操作单独 bump 而 `sql_views_snapshot` 纹丝不动，只看它的守卫会被骗过去。

### 3.2 判定本体（三条原文断言）

```
| item          | name     | AC8_version仍v1_0 | AC8_updated_at未变 | AC8_status仍PUBLISHED | version | updated_at                 | status    |
| AC-8 正泰模板 | 正泰模板 | t                 | t                  | t                     | v1.0    | 2026-09-11 01:01:02.608232 | PUBLISHED |
```

对照基线（`S1-baseline-20260910.txt`，改动前取）：`version=v1.0` · `updated_at=2026-09-11 01:01:02.608232` · `status=PUBLISHED` ⇒ **逐项相同**。

### 3.3 补强断言（AC-8 原文没写，不加就漏）

**为什么必须加**：`new-draft` + `publish` 会**新插一行**，老 `v1.0` 行可以纹丝不动 —— 那时三条原文断言全绿，**但模板确实被升版了**。

### 7.1 🚨 AC 覆盖缺口：`QUOTE` 侧语义图无人认领（**已上报用户，等裁决**）

**现象**：`QUOTE` 侧的 `semantic_node.func_signature` 与 `semantic_edge_key`（2 条键）**没有任何 AC 断言它未被改动**。

**为什么 `AC-4` 接不住**：`AC-4` 断的是报价侧**编译产物的 `md5`** 与 `正泰模板.sql_views_snapshot` 的 `md5`；但本次**不重编译报价侧组件** ⇒ 即使 `B-1` 的迁移误删了 `QUOTE` 边的 `seq=1` 键，报价侧产物的 `md5` **一个字节都不会变**，`AC-4` 照样全绿。缺陷会**静默**到下一次有人重编译报价侧为止，届时症状是「报价侧元素单价忽然按单键取价」，与本次改动相隔很久、极难归因。
