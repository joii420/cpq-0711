## ④ 问题原因 / 报告

### 一句话根因

**核价方言的语义图里没有 `FUNC_ELEMENT_PRICE` 节点，也没有 `ELEMENT_BOM --PRICE--> FUNC_ELEMENT_PRICE` 边**；
`FieldTreeBuilder.java:394` 的 `if (priceEdge != null)` 因此不成立，PRICE 组根本不产出。
**下游全部就绪** —— 前端闸门、组渲染、拖入带元素列，都已被报价侧跑通。

### 证据链（可复跑）

**证据 1 · 节点只挂了 QUOTE**

```sql
select dialect, node_key, node_kind, func_signature from semantic_node where node_key='FUNC_ELEMENT_PRICE';
--  QUOTE | FUNC_ELEMENT_PRICE | FUNCTION | f_material_element_price(:customerCode, :priceBaseDate)
--  (1 row)   ← 核价两方言各 0 行
```

**证据 2 · 边只有报价侧一条（双键）**

```sql
select fn.dialect, fn.node_key, e.edge_kind, k.seq, k.left_column, k.right_column
from semantic_edge e join semantic_node fn on fn.id=e.from_node_id
join semantic_node tn on tn.id=e.to_node_id
left join semantic_edge_key k on k.edge_id=e.id
where tn.node_key='FUNC_ELEMENT_PRICE';
--  QUOTE | ELEMENT_BOM | PRICE | 0 | element_code | element_code
--  QUOTE | ELEMENT_BOM | PRICE | 1 | material_no  | material_no
```

**证据 3 · 前端闸门核价侧已开**（⇒ 前端**没有**任务）

```sql
select dialect, tab_type from semantic_tab_view where tab_type='材质元素';
--  COST_BASIC / COST_DETAIL / QUOTE  三行齐全
```
`TabSemanticResolver.semanticOfGraphTabType('材质元素')` → `MATERIAL_ELEMENT`，
接口实测三方言的 `ELEMENT_BOM.semantic` 均为 `MATERIAL_ELEMENT`（见 ②）。
⇒ `SqlViewBuilderTab.tsx:1117` 的过滤条件 `semantic !== 'MATERIAL_ELEMENT'` **核价侧不成立**，
组一旦被后端产出就会被渲染出来。

### 引入时间线 —— **这不是遗漏，是一条被写下来的决定**

```
semantic_node.created_by = 'seed'，created_at = 2026-09-03 23:12:25（task-260904 建图时）
note = 「别名固定为 cep（AC-1 铁律）；不是 f_customer_element_price。
        只挂 QUOTE 方言：函数按**销售料号**取价，核价侧锚点是生产料号，语义对不上，不硬接」
```

🚨 **所以本条不是回归，是当初显式划下的边界。** 按 `repair-0804` 的教训
（「技术约束注释可能是业务契约」），**不能当成漏配直接补上**。
但这条 note 的理由**已被后续证据部分推翻**，见下。

### 那条 note 现在还成立多少（逐条核）

| note 的说法 | 核实结果 |
|---|---|
| 「函数按销售料号取价」 | ✅ **成立**。`f_material_element_price('CUST-0001', current_date)` 实得 `material_no` 形如 `S-3120014539`（`S-` 前缀的销售料号） |
| 「核价侧锚点是生产料号」 | ✅ **成立**。`COST_BASIC/COST_DETAIL` 的 `ELEMENT_BOM.anchor_expr = production_no`；物理视图 `v_ds_cost_*_element_bom_all` 的列是 `production_no / material_part_no / element_code / …`，**没有 `material_no` 这一列** |
| 「语义对不上」 | ⚠️ **说过头了**。真实情况是**连接键不在视图里**，不是语义冲突 —— 实测 `S-3120014539`（销售料号）与核价侧 `3120014539`（生产料号）**是同一个物料**，`material_master` 就是桥 |
| 「不硬接」 | ✅ 这个结论本身仍站得住，但理由要换：不是接不上，是**接法有分歧**（见下三条路） |

**而且函数体自己写着它覆盖核价侧**：

```sql
candidate_materials AS (   -- 覆盖真实客户（报价侧 BOM/元素挂真实 customer_no）与 '_GLOBAL_'
                           -- （**核价侧** BOM/元素主档全局共享，客户维度只体现在元素价格策略上，
                           --   不体现在 BOM 结构上）
    SELECT material_no FROM material_bom_item WHERE customer_no IN (p_customer_no, '_GLOBAL_') …
```

⇒ 数据侧当初就是按「也要服务核价」设计的。**note 与函数注释互相矛盾，这个矛盾必须由用户裁决，不能由我挑一边。**

### 接价的三个技术事实（A0 的输入，不是方案）

**事实 A · 桥接可行，但有基数风险**

```sql
select cnt as 对应销售料号数, count(*) as 生产料号个数 from (
  select production_no, count(distinct material_no) cnt from material_master
   where production_no is not null and production_no<>'' group by 1) t group by 1;
--  1 → 21 个     2 → 1 个
```
⇒ **22 个生产料号里有 1 个对应 2 个销售料号**。走桥接就会在这一个上**行翻倍**（元素价出两行）。

**事实 B · 桥接覆盖率当前有缺口**

| 数据源 | 生产料号数 | `material_master` 桥不到 |
|---|---|---|
| COST_BASIC / 元素BOM | 3 | **2** |
| COST_BASIC / 物料BOM | 9 | **4** |
| COST_DETAIL / 元素BOM | 1 | 0 |
| COST_DETAIL / 物料BOM | 4 | 0 |

⚠️ 这是**当前测试数据**的分布，不等于生产环境。但它说明「桥接后必然有一批取不到价」，
⇒ 若选桥接方案，`E-3` 的 AC 必须写成「能桥到的取到价、桥不到的显示空而不是报错」，
🚫 不能写成「所有行都有价」——那条 AC 在现有数据上恒红。

**事实 C · 存在一个无料号维度的取价函数**

```
f_customer_element_price(p_customer_no text, p_base_date date)
  → TABLE(element_code, unit_price, currency, price_unit)
```
**完全没有 material 维度**，只按 (客户, 元素) 给价。它正是 `f_material_element_price` 内部
`realtime` 分支调的那个函数，也正对应函数注释里「客户维度只体现在元素价格策略上，不体现在 BOM 结构上」。
实测 `f_customer_element_price('CUST-0001', current_date)` 返回 1 行（`Cu` = 171.3680 CNY/kg）；
核价侧用到 4 个元素代码，其中 **3 个该客户无价** —— 那是数据缺口，不是结构问题。

### 影响面

| 面 | 判定 |
|---|---|
| **报价侧** | 🚫 **不得有任何变化**（E-R1/E-R2）。新增的是核价方言的节点与边，报价侧的 `priceEdge` 查询按 dialect 过滤 |
| **前端** | **零改动**（证据 3）。这不是「免派前端」，是**前端没有任务** |
| **存量组件** | 已保存的 `component_sql_view.sql_template` 不变（新边只在重新编译时参与，同 `AC-9`） |
| **渲染链路** | 本次不动。⚠️ 但若选了需要 `customerCode` 的方案，需确认核价侧能绑上该参数 —— 实测 `SqlViewExecutor.enrichCustomerCode()` **与方言无关**（只看 `namedParams` 里有没有 `customerId`），⇒ 能绑，不需要改渲染链路 |
| **`Sec31CompileCorrectnessTest` 墓碑哨兵** | ⚠️ **必须检查**。`V430` 加查名节点时打红过它两条断言。本次加 FUNCTION 节点与 PRICE 边，需确认 `lookupOrAuxEdgeIds` 的白名单口径不被误触 |

### 为什么测试没拦住

**因为它不是回归，是既有设计边界** —— 没有任何一条 AC 声称核价侧应当有价格策略组。
`task-260904` 的 `AC-2③/AC-3③` 写的是「价格策略组**只在** `semantic==='MATERIAL_ELEMENT'` 时出现」，
这条在核价侧**恒真地成立**（组根本没产出，自然也没错误出现）。
⇒ 📌 **「不应该出现的没出现」和「应该出现的也没出现」在这条 AC 下读数完全相同。**
这类缺口只能靠需求侧发现，测试拦不住 —— 本次确实也是**用户在闸门 B 发现的**。
