### ⚠️ S1 解锁条件的订正（2026-09-08 开工后）

原计划写「S1 是后端层的片，B 完成即开跑，不等前端」（`subagents.md §1④` 的按片解锁）。**实际不成立**：S1 的用例按 AC 原文走 UI（「打开取数配置 Tab → 拖入」），而 **F-2 会改变已选输出列的初始状态**（行键列自动带出）—— 用例的拖拽流程建立在这个初始态上。

⇒ **S1 改为等 `F-2` 完成**。这不是分片判据错了，而是**测试层级的选择**（E2E 而非 API 层）带来的依赖：同一条 AC 用 API 层验则不依赖前端，用 UI 层验就依赖。
📌 **留给下次的判据**：排解锁顺序时，要问的不是「这条 AC 属于前端还是后端」，而是「**这条用例会经过哪些层**」。

### 为什么 AC-9 必须进 S-全局

AC-9 要采**全库** `component_sql_view.sql_template` 的 md5 快照做前后比对。
而 S2 会新建组件并保存取数配置 ⇒ 直接改变这个全局集合 ⇒ **AC-9 会被 S2 打红，且红得像「迁移改了存量视图」这种严重回归**。这正是 `testing.md §4.5` 说的「共库并行真正的杀手：全局计数断言」。

### 为什么 AC-8 必须进 S-全局

它要提交一张真实报价单，写 `ds_quote_material_bom_record` 等 13 张表，且依赖模板发布态。属「公共基础数据 + 配置发布态」，按 §4.5「拿不准一律归 S-全局」。

### S2 的三条隔离约束（缺一不可）

1. 造的每个组件名以 `T260908-S2-` 开头
2. 只断言自己造的那批（🚫 不许写「组件列表共 N 条」这类全局计数）
3. `finally` 里清理自己造的组件 + 其 `component_sql_view` 行
