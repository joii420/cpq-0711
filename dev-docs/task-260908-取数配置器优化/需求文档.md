## ① 背景与目标

用户 2026-09-07 起真机连续使用取数配置器（`task-260819` 交付、`task-260904` 收缩页签类型、`task-260907` 补齐）配置报价/核价组件模板，暴露 6 项使用层面的缺口。它们分两类：

**第一类：配出来的视图缺业务必需的列（需求 1/2/3）**

料号是编码，人看不懂。当前配置器配出的任何数据源，**只能拖出料号列，拖不出对应的名称列** —— 实测全语义图带 `PART_NAME` 角色的列只有 2 个，且都在已被 `B-50` 摘除的 `QUOTE_MATERIAL_BRIDGE` 上（已登记缺口 `BL-0213`：配置器路径「名称列」实际不可达，那道「料号列或名称列至少配一个」的闸等于「料号列必填」）。

后果：实施人员配出来的报价单/核价单，用户看到的是一列 `S-3110520789`，要知道它是什么得另开一个页面查。

**第二类：配置界面把不相关的配置项摊给用户（需求 4/5/6）**

- 组件绑定区固定显示 5 个下拉（料号列 / 名称列 / 元素列 / 元素单价列 / 货币列），但**元素列与元素单价列只对「物料与元素BOM」数据源有意义**，其余 40 个数据源的用户看到的是 3 个永远该留空的框；货币列实测 38 个组件里只有 1 个在用。
- 行键列决定行身份（删行、回填、墓碑匹配全靠它），**配漏了会导致删错行/回填错位**，但当前要靠用户自己记得去拖。
- 料号列拖出后默认名是各表的物理语义名（「投入料号」「组成料号」「材质料号」），同一个概念在不同页签叫不同名字，模板做出来不一致。

**不做会怎样**：第一类使 `BL-0213` 继续挂着，实施人员配的每个模板都缺名称列；第二类使配置器的误配率维持在当前水平（`task-260904` 已因料号列校验有两个执行点、只改下游而返工过一次）。

**AC-1 · 报价侧普通数据源的材料名（连物料表，带客户维度）**
以 admin 打开组件 `04375490-927f-4802-bcc7-4156df4fc27d`（「T260907-来料其他费用」）的「取数配置」Tab（数据集=报价、数据源=来料其他费用）→ 左侧「可用字段」面板中存在字段 **「材料名」**，带 `lookupLib` 徽标 → 拖入「已选输出列」→ 右侧「生成的 SQL」中出现 `LEFT JOIN ds_quote_material` 且 `ON` 子句**同时含两个条件**：`.input_material_no = <别名>.material_no` 与 `.customer_no = <别名>.customer_no`（`D-11`）。

**AC-2 · 报价 BOM 的材料名是双表 COALESCE**
打开组件 `f6d51727-bd1e-4cc3-a839-94208cc12f41`（「T260907-物料BOM」）→ 拖入「材料名」→ 生成的 SQL 中该列表达式形如 `COALESCE(<物料表别名>.material_name, <材质表别名>.symbol)`，且 `FROM` 段同时出现 `LEFT JOIN ds_quote_material` 与 `LEFT JOIN material_recipe` 两条。
**两层断言，口径不同，🚫 不要混**（`D-13` 订正，见下方「AC 订正记录」）：

**① 预览层（验功能通）** —— 执行预览 → `rowCount > 0`，材料名列**至少一行非空**，无「加载中…」、无 `null` 字面量、`diagnostics` 无该列 ERROR。
⚠️ **预览按 `:total_material_no`（该单 BOM 闭包）收窄，返回的是个位数**，🚫 **不要拿它去对全表数字**。

**② 覆盖率层（验 COALESCE 两路都真的通）** —— 直连 SQL 重采：
```sql
select count(*) 总行,
  count(*) filter (where m.material_no is not null) 命中物料,
  count(*) filter (where r.code is not null)        命中材质,
  count(*) filter (where m.material_no is not null and r.code is not null) 交集
from ds_quote_material_bom b
left join ds_quote_material m on m.material_no=b.input_material_no and m.customer_no=b.customer_no
left join material_recipe   r on r.code=b.input_material_no;
```
**断言写成不变量，不写成数字**：`交集 = 0`（用户「不重号」假设，`D-11` 的前提）· `命中物料 > 0` **且** `命中材质 > 0`（两路都通，缺一路 COALESCE 就退化成单源）。
📌 实测记录（**仅供漂移对照，不是断言**）：立项 2026-09-08 早 `97/61/23/0`，同日 1 小时后 `103/67/23/0` —— **共享库在被并发写入，数字必漂**。

**AC-3 · 报价 BOM 的生产料号走独立 JOIN（不被别名缓存吞掉）**
在 AC-2 的基础上再拖入「生产料号」→ 生成的 SQL 中 `ds_quote_material` 出现 **2 次且别名不同**：一条 `ON .input_material_no = ...`（材料名用）、一条 `ON .material_no = ...`（生产料号用，`D-2`）。
🚫 反向断言：**不允许**两列共用同一个别名 —— 那正是 `SemanticCompiler.ensureLeftJoin` 按 `target.id` 缓存别名会造成的静默失效形态（第二条边的连接键被吞、值取错且不报错）。

**AC-4 · 物料与元素BOM 只连材质表**
打开组件 `dc3297cc-e9a3-4184-8bc8-bb61db2a07d2`（「材质元素」）→ 拖入「材料名」→ 生成的 SQL **含 `LEFT JOIN material_recipe`、不含 `ds_quote_material`**（后者用标识符边界匹配，见下方⚠️）。

**同 AC-2 的两层口径**（`D-13`）：
**① 预览层** —— `rowCount > 0` 且材料名至少一行非空。
**② 覆盖率层** —— `select count(*) 总行, count(r.code) 命中材质 from ds_quote_element_bom b left join material_recipe r on r.code=b.material_part_no`。断言 `命中材质 > 0`（材质这一路通）。
📌 漂移记录（不是断言）：立项 `107/58` → 同日 `112/63`。

⚠️ **「不含 `ds_quote_material`」必须按标识符边界匹配**：`ds_quote_material` 是 `ds_quote_material_bom` 的前缀，裸 substring 计数会让本条恒红、让 AC-5「只出现 1 次」恒红、让 AC-3「出现 2 次」恒绿 —— **三条同时错**。用 `(?<![A-Za-z0-9_])ds_quote_material(?![A-Za-z0-9_])`。

**实证**：预览按 `:total_material_no`（该单 BOM 闭包）收窄 —— 后端代理实测 AC-2 预览 `rowCount=2`，而 `ds_quote_material_bom` 全表是 103 行（`CUST-0001` 93 + `CUST-0004` 10）。**两个口径差两个数量级**，照原文写的用例必然红，且会红成「功能坏了」。

**订正**：拆成两层 —— **预览层**只验「功能通」（`rowCount>0` + 至少一行非空 + 无「加载中…」），**覆盖率层**用直连 SQL 按全表口径验。

### `D-15` · 所有行数类断言一律改为「不变量」而非「具体数字」

**触发**：共享库在被并发写入 —— 同一天内 `ds_quote_material_bom` 97→103、`ds_quote_element_bom` 107→112。写死数字的 AC 会**被合法的数据变化误触发**。

### `D-16` · AC 里的三处「不含某表名」必须按标识符边界匹配

`ds_quote_material` 是 `ds_quote_material_bom` 的**前缀**。裸 substring 计数会让 **AC-4「不含」恒红 · AC-5「恰 1 次」恒红 · AC-3「恰 2 次」恒绿 —— 三条同时错，且两个方向都错**。

### `D-17` · 核价侧 AC（AC-6 / AC-24）走「切数据集」入口 —— **批准**
