## 1. 背景

### 1.1 用户观察到的现象

用户报告：导入的 Excel 里「物料BOM → 材料净重」是 **12 位小数**，导入系统后精度变短。

### 1.2 代码勘察结论（已实证）

以「材料净重」为样本，逐层追下来：

| 环节 | 位置 | 精度 |
|---|---|---|
| Excel 表头 | 「材料净重」/「净重」 | 12 位 |
| 解析 | `v6/parser/SheetRow.java:134` `getDecimal` | **不截断**，`new BigDecimal(str)` 全精度 |
| 组装 | `v6/quote/MaterialBomMergeHandler.java:168` | **不截断**，无 `setScale` |
| 落库 | `material_bom_item.net_weight` = `numeric(20,6)` | ← **精度在这里被 PG 静默 HALF_UP 掉，只剩 6 位** |
| 显示 | `DISPLAY_SCALE = 9` | 只是上限；底层只有 6 位，所以看到 6 位 |

**库内实测佐证**（`cpq_db_0724`，68 行有值记录）：

```
net_weight | rough_weight | net_decimals
 91.768628 |              |            6
377.298754 |     2.365000 |            6
 43.492768 |              |            6
107.452720 |              |            6
```

小数位数 **全部恰好 = 6**，且 `91.768628` / `43.492768` 末位非零——是被 HALF_UP 截到 6 位的典型痕迹。

**结论：精度丢在存储层，不是显示层。**

### 1.3 这是 task-0810 的另一半

`task-0810`（已交付）确立的契约是：**计算 12 位 / 显示最多 9 位 / 权威计算列存 `numeric(26,12)`**。

但它的 DDL 范围（`V385__task0810_formula_scale12.sql`）只覆盖了 **21 个「权威或派生计算金额列」**——`quotation.*`、`quotation_line_item.*`、`costing_order.*`、`material_price_review*`。**基础资料侧一列没动**，形成断层：

| 侧 | 现状 |
|---|---|
| 计算 / 金额列（0810 已扩） | `numeric(26,12)` ✅ |
| 基础资料导入列（重量 / 价格 / 含量 / 用量） | 仍是 `numeric(18,6)` / `(20,6)` / `(10,4)` / `(18,4)` ❌ |

而 task-0810 需求文档第 119 行明确写着：

> 基础取数值不按 9 位显示规则压缩；进入公式时从原始十进制文本构造 Decimal。

**这条契约当前是落空的**——基础取数值确实没被显示规则压，但它们在**落库那一步就已经只剩 4~6 位**了。本任务补齐的正是这个断层，因此收益不只是"看得到更多位"，而是**公式的输入基数本身更准**。

## 2. 目标 / 非目标

### 2.1 目标

- **G-1** 重量 / 含量·占比 / 单价·价格·费用 / 用量·数量·工时 四族基础资料数值列，落库精度统一扩到 **12 位小数**。
- **G-2** 扩容**端到端生效**：不只是 DDL，导入与维护页两条写路径上的 scale 归一常量必须同步，否则扩列无效（见 §4 的四个同步点）。
- **G-3** 整数容量**不缩水**：每列目标 `precision = 原 precision − 原 scale + 12`。
- **G-4** 顺带修掉 `MaterialBomMergeHandler` 缺 scale 归一导致的**重导虚假升版**缺陷（见 §6.1）。
- **G-5** 顺带对齐已存在的**实体 ↔ DB 漂移**（见 §6.2）。

### 2.2 非目标（明确不做）

| 不做的事 | 理由 |
|---|---|
| **改显示位数** | 用户已裁决：维持 task-0810 的「显示最多 9 位」。改显示会推翻 0810 的 D-2 / FR-9，涟漪覆盖报价编辑·详情·核价·列表·快照·HTML/PDF/Excel 全部视图 |
| **回填 / 重算存量数据** | 用户已裁决：不处理。扩列只做 `ALTER TYPE`，历史值原样保留（尾部补零）。**已被截断的原始精度无法找回**，只能靠重导 Excel 恢复——本期不做 |
| **改销售折扣率 / 税率的业务位数** | 0810 已定「输入契约不变」。这些列有业务契约，不属"重量/价格/含量" |
| **动前端 / API** | 精度字段本就走 decimal string 传输，扩列对前端与接口是透明的（判定依据见 `fronttask.md` / `api.md`） |

## 4. 核心难点：四个同步点，漏一处静默失效

**本任务的工作量不在 DDL，在这里。** scale 常量在代码里有多份独立副本，分别服务不同写路径：

| # | 同步点 | 位置 | 规模 | 漏改后果 |
|---|---|---|---|---|
| **1** | **DB 列类型** | 新建 `V386__task0813_basicdata_scale12.sql` | 85 条 `ALTER COLUMN TYPE` | 列容量不够，写入即截断 |
| **2** | **JPA 实体** | `v6/entity/*.java` 的 `@Column(precision, scale)` | 约 86 处 | Hibernate 侧元数据失真；`PricingMaintenanceService` 若反射取值会拿到旧 scale |
| **3** | **导入 handler 硬编码 scale** | `v6/pricing/P*.java`、`v6/quote/*.java` 的 `DecimalScale.at(x, 6)` / `setScale(6)` | **约 28 处**（`P01/P02/P08/P09/P10/P11/P12/P13/P14/P15/P18/P22/P23`、`FinishedOtherMergeHandler`、`IncomingOtherMergeHandler`） | **导入路径先 setScale(6) 再写库 → 扩列完全无效** |
| **4** | **`PricingSheetRegistry` 声明式镜像** | `v6/maintenance/PricingSheetRegistry.java` 的 `.scale(col, N)` | **16 处** | **维护页手工保存路径仍按旧 scale 归一**（`PricingMaintenanceService:569` / `:843` 消费它） |

同步点 3 与 4 是**同一个 scale 的两份副本**，分别管「Excel 导入」与「维护页手工保存」两条写路径。任一漏改，那条路径就仍然截断——**而且是静默的**，不报错、不失败，只是精度没了。

> 这正是历史记忆 `v6-handler-registry-mirror-trap` 记录的陷阱的又一个面：
> 「改 handler 必须同步改 `PricingSheetRegistry` 声明式镜像，否则静默失效」。

## 5. 风险与处置

### 5.1 R-1 视图依赖阻塞 ALTER（已探明，面很窄）

PG 中 `ALTER COLUMN TYPE` 若该列被视图引用，会直接报
`ERROR: cannot alter type of a column used by a view or rule`。

**已用 `pg_depend` 全库扫过**，结论：

- 只有 **3 个视图**依赖目标表：`v_composite_child_elements` / `v_composite_child_materials` / `v_composite_child_processes`
- 其中**只有 `element_bom_item.content` 一个目标列**被引用（`v_composite_child_elements`）
- 其余被引用的全是非数值列（`characteristic` / `component_no` / `customer_no` / `material_no` / `seq_no` / `system_type` / `material_name` / `material_type` / `specification` / `cost_type` / `finished_material_no` / `operation_no`）

**处置**：迁移里对 `content` 单独走 `DROP VIEW v_composite_child_elements` → `ALTER` → 按原定义重建。

⚠️ **这三个视图是 V202 智能视图，属 `docs/三大核心模块基线.md` §5.1 锁定范围**，重建必须逐字节比对原定义。

⚠️ **DDL 后必须重启 Quarkus**（`CLAUDE.md`「视图 DROP CASCADE / 重建后必须重启」）：
`ImplicitJoinRewriter.tableColumnsCache` 等进程级缓存会在视图消失的瞬间缓存空集，导致 BNF 路径谓词不注入 → UI 出现「首值（共 N 项）」错乱。

#### 🔴 5.1.1 实施期修正：上述扫描**不完整**——根因是两库 schema 漂移（技术总监疏漏）

**发现经过**：2026-08-13 实施期，T6 反射测试在**测试库**跑 Flyway 时 V386 直接失败：

```
ERROR: cannot alter type of a column used by a view or rule
Detail: rule _RETURN on view v_q_part_info_merged_drop depends on column "rate"
```

**根因**：上面那次 `pg_depend` 扫描**只扫了 dev 库 `cpq_db_0724`**，没有交叉核对测试库 `cpq_db`。两库带的历史遗留对象不同：

| 库 | `_drop` 后缀遗留视图 |
|---|---|
| dev `cpq_db_0724`（2026-07 新建，用 `deploy/cpq-init` 建） | **0 个** |
| 测试 `cpq_db`（老库，Flyway 逐版本演进至今） | **7 个** |

其中 **2 个**依赖本任务目标列（其余 5 个不依赖，已用 `pg_depend` 精确确认）：

| 视图 | 依赖的目标列 |
|---|---|
| `v_q_part_info_merged_drop` | `exchange_rate.rate` |
| `v_costing_summary_full_drop` | `plating_fee.{defect_rate, plating_material_fee, plating_process_fee}` |

**处置**：
1. 两个视图是 `V360__task0723_stage5_deprecate_costing_views.sql` 主动改名加 `_drop` 后缀标记的**待废弃对象**，全工程 grep 确认**无任何业务代码引用**（只有 V360/V361 改名迁移本身命中）→ 已在测试库 `DROP VIEW`（定义先备份）。
2. **V386 文件不改** —— 它已在 dev 库 applied，改文件会触发 checksum mismatch，波及所有共享该库的会话（项目有过教训，见记忆 `cpq-shared-flyway-history-churn`）。
3. `deploy/0813-dbupdate.sql` 在 ALTER 之前加 `DROP VIEW IF EXISTS` 防御 —— 内网升级走手工增量脚本而非 Flyway 重放，在这里防御即可覆盖「有历史包袱的库」这条路径。

**教训（值得写进反模式）**：
> **DDL 影响面勘察必须在「结构最脏」的库上做，而不是最干净的那个。**
> 本项目 dev 库是新建的（无历史包袱），测试库是老库（带完整演进痕迹）。只扫 dev 库得出的「影响面很窄」结论，对老库和生产库都不成立。
> 同类风险：`docs/方案制定前必读.md` 已记过 `mat_*` 废弃表族的类似形态——**"已废弃但还在库里"的对象是 DDL 的隐形地雷**。
> 正确做法：`ALTER TYPE` / `DROP` 类 DDL 的依赖扫描，**至少要在 dev + test 两个库各跑一遍并取并集**。

### 5.2 R-2 扩列后重导触发版本升级

导入侧 `VersionedV6Writer.tally()` 靠比对「新解析值」与「库内 existing」判断是否升版。扩列改变了 existing 的 scale，**首次重导可能被判定为内容变化而升版**。

**分析**：`norm()` 用 `stripTrailingZeros()`，`91.768628000000` 与 `91.768628` 归一后相等 → **不会误判**。
**但仍须在测试里实证**（见 `test.md` T-4），不能只靠推理。

### 5.3 R-3 表重写耗时

`ALTER COLUMN TYPE` 会重写表。目标表实测行数：`material_recipe_element` 621 / `unit_price` 377 / `material_bom_item` 256 / `element_bom_item` 192 / 其余 < 100。
**开发库无压力**；生产库需在 `deploy/0813-dbupdate.sql` 里标注锁表提示。

### 5.4 R-4 精度扩大后公式结果发生位移

## 6. 顺带修复的两个既有缺陷

### 6.1 D-1 `MaterialBomMergeHandler` 缺 scale 归一 → 重导虚假升版

`v6/quote/MaterialBomMergeHandler.java:167-168` 直接把 `row.getDecimal(...)` 的**全精度值**塞进 `CHILD_CONTENT`（`net_weight` / `rough_weight` 都在第 63 行的内容列清单里），**没有 `DecimalScale.at`**。

按 `VersionedV6Writer.java:940-960` 自己的注释：

> 若某数值列的 Excel 来源值精度超过其 DB 列 scale，则"本次新解析值(全精度)"与"重导时从库 load 出来的 existing(已截断)"在比较字符串上不相等 → **同一份文件重导会被误判"内容变化"而错误升版**（违反「重导不升版」不变量）。

`P09` / `P10` / `P12` 已按此模式修过，**`MaterialBomMergeHandler` 没修**。

**当前后果**：用户这份 12 位小数的 Excel，**每重导一次就给物料BOM错误升一个版**。

**本任务处置**：补 `DecimalScale.at(v, 12)`。注意扩到 12 位只是把阈值抬高，**Excel 若有 13 位仍会复发**——归一动作本身不能省。

#### 🔴 6.1.1 交付期更正：上述「当前后果」的因果归错了（技术总监）

**发现经过**：2026-08-13 测试执行 TC-BD.1b 时，PRICING 侧 5 张表连导两次版本恒为 `2000`（归一生效 ✅），但 QUOTE 侧 `2000 → 2001` 必升版。追查后确认**升版与精度归一无关**。

**实测证据**（`cpq_db_0724`）：

| system_type | `is_current=true` | `is_current=false` | pending_id 数 |
|---|---|---|---|
| PRICING | 38 | 16 | **0** |
| QUOTE | **2** | 206 | **45** |

**真实根因**：QUOTE 侧导入走 `task-0721 B2` 的 **pending 草稿模式**——`QuoteImportService` 每次导入生成新 `pendingQuotationId`，`VersionedV6Writer` 的 pending 分支**故意不 flip 现有 `is_current`**，落库行恒为 `is_current=false`（他单隔离）。而版本比对取 existing 的条件是 `WHERE ... AND is_current = TRUE`（`VersionedV6Writer:416`）——**基线几乎不存在** → 每次导入都被当作新增 → 必然升版。

**结论修正**：
- ❌ 原表述「12 位 Excel 每重导一次就错误升一版」把因果归给了**精度归一缺失** —— **不准确**。QUOTE 侧升版是 pending 架构的**结构性行为**，与本任务无关，也非本任务引入。
- ✅ 归一的价值**已被 PRICING 侧独立证实**：同样含 13 位超容量输入，5 张表连导两次版本恒定不变。PRICING 侧不走 pending 模式（`pending_id = 0`），有真实 `is_current=true` 基线可比，因此能真正检验归一是否到位。
- ✅ 给 QUOTE 侧 BOM 四件套补归一**仍然正确且应保留**：它是防御性的——一旦未来 pending 行被转正、或有调用方走非 pending 分支，基线存在时归一就是必需的。**只是它不是当前"升版"现象的解药。**

**遗留**：D-1 描述的「用户可感知的虚假升版」在当前架构下，**通过公开导入接口已无法复现**。若用户确实观察到过该现象，需另行确认其操作路径（可能早于 pending 模型引入，或走了别的调用方）。**不阻塞本任务交付**——本任务的核心目标是精度，已由 AC-5 全项 PASS 独立证明。
