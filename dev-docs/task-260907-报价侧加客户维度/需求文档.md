## ① 背景与目标

BOM 树的递归 SQL（`costing_bom_tree_config`，**全系统共用一份**）要从 V6 老表 `material_bom_item` 改读新表 `ds_quote_material_bom`。而那份递归**靠 `customer_no` 做客户隔离**：

```sql
FROM material_bom_item ch JOIN bom b
  ON ch.material_no = b.material_no AND ch.customer_no = b._cust
```

新表体系没有这一列。用户的解法不是丢掉这个维度，而是**把它补进整个报价侧新表体系**。

**不做会怎样**：递归换表时只能丢掉客户隔离。实测当前数据下不会串（见 §③ AC-1 注），但那是「现网恰好没有」而非「设计上安全」—— 本项目**出过跨客户串号故障**（森萨塔，占号表 `material_customer_map` 全局唯一）。

#### 💡 B-7 的一条近路（由 `报价数据导入切ds新表` 会话提出，主线复核属实）

**也许不必「递归改读 `ds_quote_material_bom`」，换成兼容视图可能就够。**

```

⇒ 症结不是「新表料号在任何地方都捞不到」，而是**那两条递归还在读 V6 裸表**。
而 `v_compat_material_bom_item` 正是 `task-260903` B 阶段为这件事建的（`V6表 UNION ALL ds_quote_*`，V6 优先 + 反连接去重），

🚨 **三条必须先排除的风险**（对方一并给出，不是只报好消息）：

1. **`costing_bom_tree_config` 是报价 + 核价共用**（`usage` = `QUOTE` / `COSTING`）⇒ 改它同时影响两条线。

3. 兼容视图的新表侧 **`pending_quotation_id` 恒 `NULL`、`is_current` 恒 `true`** ⇒ 若递归里有 pending 或版本相关谓词，**语义会变**。

📌 **这是一条待验证的方向，不是结论。** B-7 立项时先做这三条排除，再决定走近路还是走大改。

### 单点 AC

**AC-1（客户隔离真正生效，且能被证伪）**
前置：`costing_bom_tree_config` 的 QUOTE 递归接上客户隔离后。
🚧 **现网数据验不出阳性**：实测 V6 老表 QUOTE + `is_current` 中，**跨多客户的料号 0 个**、**子件集合因客户而异的料号 0 个**
⇒ 「隔离有没有生效」在当前数据下**无法证伪**，断言会以「通过」的形态空跑。
操作：**用例自造前缀化夹具** —— 同一料号 `T260907-X` 挂在两个客户下，各自子件不同。
断言：① 客户 A 的报价单只展开出 A 的子件；② 客户 B 的只展开出 B 的；③ 两者互不出现对方的子件。

**AC-2（🔴 整组删除不得跨客户误删 —— 本任务最重要的一条）**
前置：轴模型改复合后。
操作：以 `CUST-0004` 导入料号 `X` → **再以 `CUST-0001` 导入同一料号 `X`**。
断言：① **本次导入所写入的每一张表**，其 `customer_no` 全 = 本次所选客户，`NULL` 行数 = **0**（🚫 不锁「15 张」这个数字，同 AC-3 记账）；
② 🚨 **`ds_quote_material_bom` 中该料号两个客户的行并存，第一次导入的行未被删除**。

> 🔑 **为什么断言必须写成「两个客户并存」而不是「本次写入成功」**：
> 只断言①**抓不住静默删除** —— ① 在删除发生后**照样成立**。
> （判据设计来自 `task-260907-报价导入建单切ds新表` 会话的 AC-22，本任务同型采用。）
>
> 🚨 **失败形态是静默删数据，不是撞键报错**（主线曾判反，已实测更正）：
> ```
> ds_quote_* 的 UNIQUE 约束(contype='u') = 0 个
> 13 张带版本表：只有 PRIMARY KEY (id)，无任何业务唯一索引
> SheetDef.java:30               public final String axisColumn;   // 单列
> VersionedGroupWriter.java:206  "DELETE FROM " + table + " WHERE " + axisCol + " IN (:axes)"
> ```
> 隔离**根本不靠 DB 约束**，靠整组删除 + 重插。只加列不扩轴 ⇒ 客户 A 导入会**静默删掉**客户 B 的同料号数据，不报错、不撞键、不留痕。

**AC-3（报价侧全表 DDL 落地）**
断言（**不变量口径，🚫 不锁行数**）：
① **所有 `ds_quote_*` 业务表及其镜像表**（`_history`、以及后续新增的 `_record` 等同范式表）**全部**有 `customer_no`，
   判据 SQL：`SELECT table_name FROM information_schema.tables t WHERE t.table_name LIKE 'ds_quote_%'
   AND NOT EXISTS(SELECT 1 FROM information_schema.columns c WHERE c.table_name=t.table_name AND c.column_name='customer_no')`
   → **返回 0 行**；
② 每张镜像表与其主表的 `customer_no` **列定义一致**（类型 / 可空性 / 默认值逐项相同）；
③ 迁移 `success = true`（`flyway_schema_history` 查证）。

> 🚫 **本条曾写成「29 张全部有」「14 对 `_history`」**，由 `核价回填` 会话指出并已改：
> 该会话的 **S-2 要新建 13 张 `_record`**（照 `_history` 范式）⇒ 合并后 `ds_quote_%` 会变 **42** 张，
> 照原文验会得到**假红 —— 红的是数字过期，不是隔离坏了**。
> 🔑 依据 `RECORD.md` 2026-09-06 规则升级提议①「AC 判据不许写具体数字」，
> 实证是 `task-260819` 的 `AC-113`/`AC-122` **同一条 AC 上栽了三次**。
>
> 📌 采集时点数字仅作**参考基线**（2026-09-07 实测：29 张 = 13 带版本 + 3 免版本 + 13 `_history`，已有 `customer_no` 的 1 张），

**AC-8（元素价格策略闭环：配置器能直接接到客户级价格函数）** 🆕 *用户 2026-09-07 裁决「加上，让元素价格策略闭环」*

**背景（实测）**：现有唯一的价格节点 `FUNC_ELEMENT_PRICE` 绑的是 `f_material_element_price`，
而**它对 `ds_quote_*` 新导入料号恒返 0 行** —— 实测该函数返 21 个料号，其中 V6 里没有的 = **0**。
那 19 个能出价只因它们同时存在于 V6。⇒ 配置器配的「物料与元素BOM」页签**配不出对新料号有效的元素单价列**。

**为什么 `f_customer_element_price` 是正确口径**（主线实查函数体）：
```
f_customer_element_price(客户, 基准日) → (element_code, unit_price, currency, price_unit)   ← 无 material_no
  读 element_price_strategy（客户级默认 + 客户×元素级专属，专属优先）
  → 按 method(LATEST/AVG/MAX/MIN) + 时间窗从 element_daily_price 取行情
  → unit_price = ROUND(raw × factor + premium, 4)
  料号从头到尾不进运算
```
⇒ 与用户业务规则一致：「**一张报价单中的元素价格是统一的**」，不会出现同客户同元素不同料号价格不同。

断言：
① 语义图新增节点 `FUNC_CUSTOMER_ELEMENT_PRICE`（`node_kind=FUNCTION`，`dialect=QUOTE`）；
② 声明 **3 列**：`unit_price`「元素单价」· `currency`「货币」· `price_unit`「计价单位」
   —— 🚨 **`price_unit` 必须声明**：现有 `FUNC_ELEMENT_PRICE` 只声明了前两列，但函数实际返回 4 列且 `price_unit` **有值**（实测 `kg`）；
③ 配置器「物料与元素BOM」数据源下，用新节点配出的元素单价列**对 `ds_` 独有料号也能取到价**；
④ **验收必须挑实际能算出价的元素** —— 实测 `CUST-0004` 下只有 **5 个**：`Ag / Cu / Ni / Zn / 白银`（全 CNY/kg）。
   🚧 其余元素返回空**不是缺陷**：该函数有三层数据依赖（`element` ACTIVE + 该客户有 `element_price_strategy` + `element_daily_price` 有行情），缺任一层该元素整行不出现。

> 🔴 **本条最大的实现风险：可能重现刚修掉的「两个价格策略组」缺陷。**
> `ELEMENT_BOM → FUNC_ELEMENT_PRICE` **已有一条 `PRICE` 边**。若新节点再加一条 `PRICE` 边，
> `FieldTreeBuilder` 的 `priceEdge` 专用块**只取一条**，两条 PRICE 边的行为**未定义**——
> 极可能重现 `task-260907-取数配置器补齐` 的 `AC-30`（QUOTE 材质元素返回两个价格策略组，
> 两块 `viewColumn`/`isCore` 不同，用户无从分辨该拖哪个）。
> ⇒ 🚦 **实现前必须先确定「同一锚点两条 PRICE 边」的行为**，并在回报里说明选了哪种：
> (a) 取代现有边（现有节点保留但不再挂 PRICE） · (b) 两条边共存且面板出两组（**需要能区分**）· (c) 其它。
> 🚫 **不许默认「加上去就行」** —— 那正是 AC-30 的成因。

> 📌 **一条要知情的取舍**：`f_material_element_price` 的 `versioned` 分支（价格版本冻结）在新路径下会丢。
> 实测 `material_price_version_ref` 全库仅 **4 行 / 4 客户 / 4 料号**，`CUST-0004` 为 **0** ⇒ **现网零损失**，但这是已知取舍。

### 序列 AC

**AC-5（导入 → 维护端编辑 → 再导入，三步都不串客户）**

### 🚦 合并前置（硬时序，不可跳）

| 项 | 内容 |
|---|---|
| **等对方验完 AC-15** | `报价导入切ds新表` 会话的 `AC-15`（「基础资料维护页签读写行为与改动前逐字一致」）的验收窗口在**本任务落地之前**。⚠️ 因为本任务的 DDL 与轴模型**必须同一批合并**（见下），不存在「先合 DDL 让你慢慢验」的缓冲 ⇒ **合并前必须先同步对方、等其验完**。 |

### 🚫 DDL 与轴模型必须同一批合并

**不允许「先加列、轴模型下一轮再改」。** 中间那个状态最危险：列已经在、值也在填，而删除仍按单列轴走 ——
**看起来一切正常，实际每次导入都在删别的客户的数据。**
> 这是**结构上不让那个状态出现**，强于「发现轴还是单列就停下」那种事后检测 —— 后者依赖有人去看，而该中间态恰恰"看起来正常"。

### 波及面

- `VersionedGroupWriter` **三套数据集共用** ⇒ 改它波及核价两套（AC-6）
- 维护端 8 个端点 `GET /dataset/{dataset}/parts/{axisValue}/...` —— `{axisValue}` 是**单个路径段**，装不下复合轴
- `QuoteRegistry` 16 个 sheet 定义
- 16 个 sheet 里**只有「客户料号」有客户编号列**，其余 15 张的值只能来自**导入时选定的客户**

### 🔴 `customer_no` **不能声明成 `ColumnDef`** —— 否则 B-1 落地当天存量 Excel 全部导不进去

由 `核价回填` 会话交底，**主线四条逐字复核属实**（2026-09-07）：

| # | 约束 | 源码 | 后果 |
|---|---|---|---|
| ① | 列集**双向**比对，多一列即启动失败 | `DatasetSchemaSelfCheck.java:112-118`<br>`for (String col : act.keySet()) if (!exp.contains(col)) problems.add(table + " 多出未声明的列: " + col);` | `ALTER TABLE` 加了列、Registry 不同步声明 ⇒ **后端 `onStartup` 抛 `IllegalStateException`，起不来** |
| ② | 🚨 **但不能声明成 `ColumnDef`** | `DatasetSheetParser.java:72-77`<br>`for (ColumnDef c : spec.persistedColumns()) { ... if (idx == null) out.missingHeaders.add(c.label); }`<br>`if (!out.missingHeaders.isEmpty()) return out;` | `persistedColumns()` 每列**必须在 Excel 表头出现**。而 `customer_no` 的值来自**导入时选客户的下拉，不来自 Excel**（16 个 sheet 里只有「客户料号」有该列）⇒ 其余 15 张 sheet 表头校验全报「缺列」，**整份 Excel 拒收** |
| ③ | 出路：走**静态系统列** | `SheetDef.java:20-27` 的 `SYSTEM_COLUMNS` / `VERSION_COLUMNS` / `ARCHIVE_COLUMNS`；`expectedTableColumns():106-113` 把它们并入期望列集 | 静态系统列**进自检、不进 `persistedColumns()`** ⇒ 自检认、表头校验不认，**正是所需形状** |
| ④ | 写入点要显式加 | `VersionedGroupWriter.java:264-267`（`insertAll` 只写 `persistedColumns + INSERT_SYS_COLUMNS`）· `:244-245`（`archive` 只复制 `persistedColumns + ARCHIVE_SYS_COLUMNS`） | 走系统列这条路 ⇒ **这两处必须显式加上 `customer_no`**，否则**列建了、值永远 NULL** |

**⇒ B-1 的实现形状（不是「加个字段」那么简单）**：
1. `SheetDef` 加第四组静态常量（如 `CUSTOMER_COLUMNS`）
2. 🚨 **必须只对报价侧生效** —— `SheetDef` 是**三套数据集共用**的，无条件追加会让**核价两套的自检也要求这一列 ⇒ 核价侧当场起不来**
3. `expectedTableColumns()` / `expectedHistoryColumns()` 按报价侧条件追加
4. `insertAll` 与 `archive` 两处显式带上它

> ⚠️ **④ 的失败形态特别值得记**：列建好了、自检过了、导入也不报错，**只是值恒为 NULL**。
> 届时 `AC-2①`「`NULL` 行数 = 0」会红 —— **红得对，但排查方向极易跑偏到 DDL 上**（「列不是加了吗？」），
> 而真因在两个写入点的列清单里。

> 🔑 **形状对齐**：`核价回填` 会话的 `D-28`（给主表加「来源报价单 id」）撞的是同一堵墙，已按同形状定案（新增 `RECORD_COLUMNS` + `expectedRecordColumns()`）。
> 两边都走静态常量 ⇒ 其 `_record` 照主表建时不会打架。
