### FT-3b 详记（2026-09-02 补做）

**先补了一条往返用例 `T-E-12c`**：原来的 AC-30 用例只「读」不「存」，
去零函数即便真改了值也落不到库里 ⇒ **那条 SQL 断言永远是绿的，从没被证明接上过**。
新用例：建一条 12 位小数配置 → UI 打开其编辑抽屉 → 读出去零值 → **一个字不改直接保存** → 回查库。

| 杠杆 | 结果 |
|---|---|
| **A（原定）** `Number(s).toString()` | 🚩 **无效杠杆**。含量值域是 0~100 带 12 位小数（≤15 位有效数字），double 能精确表示 ⇒ 输出与正确实现**逐字相同**：`90.000000000000→90`、`12.345678901200→12.3456789012`、`0.150000000000→0.15`。**它根本不改值**，验不出任何东西 |
| **B（改用）** `parseFloat(s).toFixed(9)` | ✅ 真改值：`12.345678901200 → 12.345678901`（正是预期的「尾数被吃掉」） |

**第一次跑杠杆 B 仍没验到 SQL 断言** —— 它红在**显示断言**上，把后面的存储断言挡住了。
⇒ 调序（存储断言先验、显示断言后验，两条都保留），再跑：

```
未破坏：  输入框 [12.3456789012, 87.6543210988]  库内 [Ag=12.345678901200, Ni=87.654321098800]  ✅绿
杠杆 B：  输入框 [12.345678901,   87.654321099]   库内 [Ag=12.345678901000, Ni=87.654321099000] ❌红
          失败点 = 「原样保存后库内必须逐字不变」——**正是那条 SQL 断言**
还原后：  ✅ 复跑回绿；precision.ts sha256 与备份逐字节相同
```

⇒ **那条 SQL 断言确实查了库、确实接上了。**
📌 两条可复用的教训：①「只读不写」的用例验不了「写入不变式」；②**判据排序会决定哪条断言永远跑不到** ——
把最可能被遮蔽的那条排前面（与 AC-31 的「后端 409 先于 tooltip」同一手法）。

**FT-3 的自然佐证**：`tI28` 首跑在测试中途抛异常，`@AfterEach` 照样把 dev 库清回基线 —— 这正是「不许用跑完手工清代替 finally」的实证。
