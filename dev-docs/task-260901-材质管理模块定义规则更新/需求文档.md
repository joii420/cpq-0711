## ① 背景与目标

### 1.1 现状（全部为 `cpq_db_0724` 实测，非推断）

| 事实 | 数据 |
|---|---|
| `material_recipe` | **258 条**，`code` UNIQUE（材质编号 = 材质料号），`symbol`（材质名/化学式）无唯一约束但实测 258 个名互不重复 |
| `material_recipe_element` | **621 行**，`recipe_id → element_code + default_pct`。`default_pct` 存 **100 制**（AgNi10 存 `Ag=90.000000000000`），列 `numeric(16,12)` |
| **一个材质只能有一组含量** | `uq_recipe_element UNIQUE (recipe_id, element_code)` —— 同一材质同一元素只能有一行 |
| 元素组合的重合度 | 258 个材质里只有 **82 种不同元素组合**、**223 种不同含量配比** |
| `element` 主表 | 38 行，`element_no` 数字段 `10001`~`10095`，混一行脏数据 `element_no='白银'` |
| 导入模板 | 两 sheet：`材质编号`（材质/材质编号）+ `材质对应元素`（材质/材质编号/元素名称/含量/元素编号），**材质编号与元素编号都要业务方手填** |
| `recipe_type` 三态 | CHECK 允许 `locked`/`editable`/`partial`，但 **258 条全是 `locked`**、621 行元素全 `is_locked=true` —— 该能力从未启用 |
| `material_master.material_recipe_id` | 1890 行**全 NULL** |
| `material_master.config_fingerprint` | 1890 行**全 NULL** |

### 1.2 问题

**问题 1 · 材质与含量档次绑死，材质库按档次膨胀。**
同一材质的不同含量档次现在各占一个材质编号。实测 `{Ag, Ni}` 这一个元素组合下就挂了 10 个材质编号：

| 材质编号 | 材质名 | 含量 |
|---|---|---|
| 00006 | AgNi10 | Ag 90% / Ni 10% |
| 00018 | AgNi(0.15) | Ni 0.15% / Ag 99.85% |
| 00019 | AgNi0.15 | Ni 0.15% / Ag 99.85% |
| 00020 | AgNi15 | Ag 85% / Ni 15% |
| 00021 | AgNi20 | Ag 80% / Ni 20% |
| 00022 | AgNi30 | Ni 30% / Ag 70% |
| 00026 | AgNi40 | Ni 40% / Ag 60% |
| 00083 | AgNi25 | Ag 75% / Ni 25% |
| 00094 | Ag/Ni | Ag 6.6107% / Ni 93.3893% |
| 00197 | AgNi10/Ag15CuP | Ag 90% / Ni 10% |

**问题 2 · 同名材质多编号被静默合并**（原 `repair-260901`，根因已定位）。
`MaterialRecipeImportService:99-107` 用 `codeByMaterial.putIfAbsent(mat, code)` 建「材质名 → 编号」单值反查表，元素行的**材质编号列（B 列）从头到尾没被读过**（`:113-117`）。同名材质的第 2 个及以后编号被静默丢弃，所有同名行归进同一组：符号重叠 → **含量被后一个编号覆盖、`skipped=0` 报告全绿**；符号不重叠 → 含量累加 Σ=2.00 → 报 `含量合计≠1`，**归因误导到「含量填错」**。

**问题 3 · 导入要求手填两种编号，填串列已实际发生。**
实测 `material_recipe_element` 里材质 `00262 / Sn02` 的 `element_code` 填的是 `10004` —— 那是 Sn 的**元素编号**，业务把编号填进了符号列。`task-260812` 已把材质编辑抽屉的元素列改成字典下拉，但**导入这条路仍是自由文本**。

**问题 4 · 选配无法按含量档次取材质，也没有「是否允许自定义含量」的开关。**
`ConfigureProductService:526-546` 已按 `is_locked` / `min_pct`~`max_pct` 校验选配输入的元素含量，但 258 条材质全 `locked`、元素全 `is_locked=true` ⇒ 任何自定义含量都会被拒（`元素已锁定,不可修改`）。业务侧没有开关可开。

### 1.3 目标

把材质模型从「**材质 = 一组元素 + 一组固定含量**」改成「**材质 = 一组元素，下挂多组含量配置**」，并把导入简化为**单表 4 列、两种编号全自动**。

### 1.4 不做会怎样

材质库继续按含量档次碎片化增长；同名多编号的静默覆盖继续发生且报告全绿；业务每次导入仍要手工维护两套编号；选配拿不到含量档次，「自定义含量」能力永远开不了。

| # | 交付项 |

**六条派生规则**（这些不是实现细节，是可被 AC 断言的语义，`backtask.md` 不得自行改动）：

| # | 规则 |
|---|---|
| **M-0** | **元素组成是材质的显式属性，不是从配置派生的。** 权威源是 `material_recipe_composition`；每条含量配置的元素集合**必须与它逐个相等**（集合相等，不是子集）。配置矩阵的列 = 元素组成、列顺序 = `sort_order`。⇒ 0 条配置的材质**照样有明确的元素组成**，列表与抽屉都能正常显示。→ 服务 AC-10 / AC-13 / AC-17 |
| **M-0a** | **元素组成的三个来源，规则同源**：① **UI 新建材质** —— 用户直接建若干张「配方卡片」，每卡片自己填元素与含量；保存时校验**各卡片的元素种类集合相同**，一致则该集合即为材质的元素组成（`sort_order` 按第 1 张卡片内的元素顺序）。② **导入** —— 同一材质在文件内的各组互相比对，全一致才建（M-5b）。③ **编辑既有材质且无 ACTIVE 配置** —— 在元素组成区直接增删改。<br>⇒ ①②**是同一条规则的两个入口**，判据、错误文案与「不一致就整体拒绝」的处置必须一致，🚫 不许两边各写一套。 → 服务 AC-33 / AC-34 |
| **M-0b** | **元素组成的可改性 = 与「材质编号只读」同款的两段式**：该材质**无任何 ACTIVE 配置**时可自由增删改（改的是笔误）；**一旦有 ACTIVE 配置就转为只读**。理由直接来自新规则第 1 条 —— **同一组元素才是同一个材质，换了元素集合就已经不是这个材质了**，该走「新建材质」而不是「改这个材质」。要改只能先删光该材质的全部配置。→ 服务 AC-31 |
| **M-1** | **配置编号发号**：`config_no = <材质编号> + '-' + String.format("%02d", seq)`，`seq = max(该材质所有配置的 seq，含 INACTIVE) + 1`。`%02d` 在 `seq ≥ 100` 时自然给出三位（`100` → `"100"`），**不得用 PG 的 `lpad(x,2,'0')`**（它会把 `'100'` 截成 `'10'`）。→ 服务 AC-14 / AC-15 / AC-26 |
| **M-2** | **删除 = 软删**：`status → INACTIVE`，物理行保留，`seq` 水位不释放 ⇒ **编号永不回收**。列表与选配下拉默认只列 `ACTIVE`。→ 服务 AC-15 / AC-17 |
| **M-3** | **导入的内容比对只看 `ACTIVE` 配置**。匹配不到就新建（发新号），**不复活已停用的配置** —— 停用是人的显式动作，导入不撤销它。可观测后果：停用 `00006-02` 后重导原文件会得到内容相同的 `00006-04`，这是预期行为不是缺陷。→ 服务 AC-7 / AC-20 |
| **M-4** | **配置的相等判据** = 元素集合相同 **且** 每个元素的含量 `BigDecimal.compareTo == 0`（值相等，忽略 scale 差异）。**不套用 Σ 的 0.02 容差** —— 容差只用于「Σ 是不是 1」，不用于「两个配置是不是同一个」。→ 服务 AC-7 / AC-20 |
| **M-5** | **`allow_custom_content` 优先于元素级锁**：`false` → 选配直接拒绝任何自定义含量，不进元素级校验；`true` → `is_locked` 不再单独生效，只校验 `min_pct`/`max_pct`（若有）+ Σ=1。新建材质（含导入自动创建的）**一律默认 `false`**。→ 服务 AC-16 / AC-18 / AC-19 |
| **M-5b** | **导入新建材质时的元素组成来源（顺序无关）**：先把该材质在**同一份文件里的所有配置组**互相比对元素集合 —— **全部一致才建材质**，并以该集合写入元素组成（`sort_order` 按元素在文件中首次出现的顺序）；**任一组不一致则整个材质跳过**，不建材质、不发号、不入任何配置。⇒ 同样的数据换个行序，入库结果完全相同。→ 服务 AC-32 |
| **M-6** | **导入按材质名匹配材质时的防御分支**：若同一 `symbol` 查到 **≥2 条** `ACTIVE` 材质，跳过该材质并报告「材质名对应多条材质记录，请先在材质管理页处理」。当前 258 个材质名互不重复、该分支不会触发，但 `symbol` 无 DB 唯一约束（§2.2 明确不加），必须防着。→ 服务边界 AC |

🚨 **红线提示**：③ 里的 `DROP CONSTRAINT uq_recipe_element` 与 `DROP COLUMN recipe_id` 属 `CLAUDE.md §3.2`「契约销毁 / 数据销毁」范畴。
执行前主线必须按红线三步走：**先量化影响面**（`SELECT count(*) FROM material_recipe_element WHERE config_id IS NULL` 必须 = 0 才允许 DROP）→ **说清可恢复性**（`recipe_id` 可由 `config_id → material_recipe_config.recipe_id` 完整重建，信息零丢失）→ **单独报请用户批准**。

| **X-5** | **「有 ACTIVE 配置后元素组成只读」这条严格度**（M-0b / AC-31） | 你只裁决了「元素组成显式存一份」，**没说它能不能改**。我按新规则第 1 条推的：同一组元素才是同一个材质，换了元素集合就不是这个材质了 ⇒ 该走新建材质。但这意味着「AgNi 配方升级加微量 Ce」只能新建一个材质，**旧材质的历史配置与新材质不连续** | 若你要的是「能加元素、已有配置连带调整」，本条要推翻重写（那是个大得多的交互：加元素后每条配置的含量都要重新给，且 Σ 必须重新配平） |
