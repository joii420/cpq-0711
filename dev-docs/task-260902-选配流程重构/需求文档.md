## ① 背景与目标

### 现状：选配的「配件」直接等于一个材质料号

现行模型只有两层 —— **产品 → 配件**，而「配件」在实现里就是**一个材质料号**：

| 证据 | 位置 |
|---|---|
| `PartRequest.recipeCode` 是**单值** | `cpq-backend/.../dto/PartRequest.java` |
| 前端提示语「请至少新增一个材质料号」 | `ConfigureProductDrawer.tsx:271` |
| 落库只写 **1 行**「自指物料行」= 选中的材质 | `ConfigureProductService.insertMaterialBomItemV6` |
| 指纹只认 `MAT=材质编号` + `ELE=元素码:含量` + `PRC=工序码` | `SalesFingerprintCalculator.renderToken` |

⇒ 一个零件**只能有一种材质**，没有「零件」这一层实体，也没有外购件的概念。

### 问题：真实产品结构装不进这个模型

1. **一个零件常常用多种材质**（触点部位用银基材料、基体用铜基材料），现模型只能拆成两个「配件」，丢失了「它们同属一个零件」这一事实。
2. **外购件无处安放** —— `material_bom_item.characteristic` 枚举里有 `OUTSOURCED`，组件页签类型里有「外购件」，但 **dev 库实测 `OUTSOURCED` 零行**（全表 RECIPE 11095 / ASSEMBLY 49；`is_current=true` 口径 ASSEMBLY 37 / RECIPE 21 —— **两种口径下 OUTSOURCED 都是 0**，取数 2026-09-02）。这是从未落地的能力，不是「已有但没接」。
3. **零件没有品名 / 规格 / 尺寸** —— `PartRequest` 只有 `name`（"配件 1"）和 `unitWeightGrams`。
4. **客户产品编号来得太晚** —— 代码注释写明「选配阶段没有 `customer_product_no`（客户产品号在数据导入后才存在）」。后果是选配生成的料号在 `material_customer_map` 里 `customer_product_no` 为空，「从已有产品添加」列表**找不回它**，现在靠一句 `OR EXISTS (SELECT 1 FROM sel_part_signature …)` 兜着。
5. **指纹维度不足** —— 零件重量**不进指纹**，今天两个配置相同但一个 10g、一个 20g 的零件会**共用同一个销售料号**，而重量直接决定材料成本。

### 目标

把选配从两层模型升到三层，让它能表达真实的产品结构：

```
产品（客户产品编号）
└── 配件 1..N
     ├── 零件（新建 / 已有）
     │    ├── 品名 / 规格 / 尺寸 / 总重
     │    ├── 材质 1..N（每个带占比，Σ=100%）
     │    │    └── 含量配置（选标准配方，或自定义含量）
     │    └── 工序
     └── 外购件（从现有料号库选）
          └── 工序
└── 组合工序
```

### 不做会怎样

多材质零件只能被拆成互不相关的配件、外购件永远配不出来、重量不同的零件共用料号导致成本错算、选配产品在产品库列表里持续「找不回」。

## ② 范围

### 做什么

| 编号 | 范围项 |
|---|---|
| **S-1** | **客户产品编号前置**：选配第一步输入客户产品编号；已存在则**阻止继续**并提示改走「从产品库添加」入口 |
| **S-2** | **配件类型分流**：添加配件时先选「零件」或「外购件」 |
| **S-3** | **零件层实体化**：新建零件可填品名 / 规格 / 尺寸 / 总重；已有零件从产品列表选 |
| **S-4** | **零件挂多材质**：一个零件可添加 1~N 个材质，每个材质填**占比**，占比合计校验 = 100% |
| **S-5** | **每个材质选含量配置**：接 `task-260901` 的配方层；材质支持自定义含量时可自定义（依赖其 `allow_custom_content`） |
| **S-6** | **外购件**：从现有料号库选（`material_master.material_type = '外购件'`），再选工序 |
| **S-7** | **指纹维度扩展**：新增**材质占比**、**零件总重**、**品名/规格/尺寸**三个维度；**配方编号不进指纹**（按含量内容判同） |
| **S-8** | **落库对齐**：多材质落 `material_bom_item` N 行（占比落 `material_ratio`）、元素含量按材质分组落 `element_bom_item`、客户产品编号落 `material_customer_map` |

### 🚫 明确不做什么

| 不做项 | 去向 / 理由 |
|---|---|
| **材质用量（克重）逐材质填** | 用户裁决：**材质填占比、零件填总重**，各材质克重 = 总重 × 占比，不单独录入 |
| **新建外购件主数据模块**（编号/供应商/价格的 CRUD + 导入） | 用户裁决：本期**从现有料号库选**，不建新主数据。若将来需要集中维护外购件价格，另立任务 |
| **配方编号进指纹** | 用户裁决：含量相同即同一种材料，按含量内容判同。配方维度的可追溯性本期不保证 |
| **同材质下禁止含量重复的配置** | 属 `task-260901` 的材质库范畴，不在本任务。本任务只保证「含量相同 → 复用同一料号」这一行为是**有意为之**而非巧合 |
| **`material_type` 语义冲突的全局治理** | 见 §④「必须先裁决的架构冲突」。本期只收敛**选配写入侧**，不动导入侧与既有存量 |
| **选配自定义含量回流材质库** | `task-260901` 已裁决：材质库只放标准配置，自定义不回流 |
| **`mat_*` 系列表的清理** | dev 库实测 `mat_` 开头的表**一张都不剩**，但代码里仍有实体映射 `mat_composite_process`（启动时报 Hibernate schema validation ERROR，不阻止启动）。属既有技术债，另行处理 |
| **`flyway_schema_history` 中 375/376 重复记录** | 同一迁移各被记三遍，历史遗留，不影响启动，登记不处理 |

### 4.4 ✅ 已裁决：工序进指纹，但**顺序不进**（按编号排序生成）

**用户裁决（2026-09-02）**：工序作为维度参与指纹；**指纹按工序编号排序生成**；「焊接→铆接」与「铆接→焊接」**算同一个产品**。

⇒ **`SalesFingerprintCalculator` 的 `PRC=` 分支保持现状 `sorted().join(",")`，本任务不改这行代码。** 全类（`MAT`/`ELE`/`PRC`/`COMBO`/`CPROC`）顺序无关的统一口径继续成立，不为工艺路线破例。

**两条必须写进 AC 的推论（后者容易被误解成"重复也被抹平"）**：

| 维度 | 是否进指纹 | 实测依据 |
|---|---|---|
| **工序顺序** | ❌ 不进 | `["Z100","Z101"].sort()` 与 `["Z101","Z100"].sort()` 均得 `Z100,Z101` ⇒ 同一料号 |
| **工序重复次数** | ✅ **仍进** | `["Z100","Z101","Z100"].sort()` 得 `Z100,Z100,Z101` ≠ `Z100,Z101` ⇒ **「焊两次」与「焊一次」是不同料号**（`sort` 不去重） |

**UI 侧的调序功能保留**，但需在实现与验收时明确它的作用域：调序影响**工序在报价单里的显示顺序**与落 `unit_price` 时的 `seq_no`，**不影响料号复用判定**。🚫 不得因为"顺序不进指纹"就把 UI 的 ↑↓ 去掉——那是两件事。

📌 **裁决前评估过的历史同型事故**（`RECORD.md` 选配 Plan 3b · T5）：`COMBO` 原本只含子件报价料号，code review 发现「同客户同子件集但 qty/工序不同会误命中同一父指纹 → **静默丢弃新 qty/工序 → 错价**」，于是升级为「子料号:qty」对并新增 `CPROC=`。**「指纹漏维度 → 静默命中 → 错价」在本系统真实发生过一次**，且没有任何报错外观。本次裁决为"顺序不进"是**业务判断**（同样几道工序换个次序仍是同一个产品），而非遗漏——但正因如此，AC 必须把上表两行**都**断言死，尤其是"重复次数仍进"这条，防止实现者顺手加 `distinct()` 把它一起抹平。
