## 0. 一页总览

选配 = **4 步向导 + 1 次提交**。前 4 步**一行库都不写**（只读候选、只查占用），全部写入集中在最后那一次 `POST`，且在**同一个事务**里。

| 步 | 界面 | 读哪些表 | 写哪些表 |
|---|---|---|---|
| — | 打开抽屉 | `material_recipe` · `process_master` · `sel_template*` | 无 |
| 1 | 客户产品编号 | `ds_quote_customer_part` ∪ `sel_product_no` ∪ `material_customer_map` | 无 |
| 2 | 添加配件 | `material_recipe` / `material_recipe_config` / `material_recipe_element` / `material_recipe_composition` · `material_master`(+`material_recipe`) · `v_compat_material_master` | 无 |
| 3 | 组合工序 | `process_master`（`process_category ∈ {ASSEMBLY,组装}`） | 无 |
| 4a | 指纹预览 | `sel_part_signature` · `v_compat_material_master` · `unit_price` · `capacity` | 无 |
| 4b | **提交** | 上述全部 + `quotation` / `customer` | **13 张表**（见 §6） |

**提交写入的 13 张表**（按写入顺序）：

```
发号        quote_customer_code → quote_material_no_seq → material_customer_map
指纹        sel_part_signature
基础资料层  ds_quote_material → ds_quote_material_bom → ds_quote_element_bom

映射        ds_quote_customer_part
────────── 以上同一事务，以下事务提交之后、尽力而为 ──────────
渲染快照    quotation_line_component_data · quotation_view_structure
回填留痕    ds_quote_*_record（13 张）
```

## 1. 入口与前置

**前端**：`cpq-frontend/src/pages/quotation/ConfigureProductDrawer.tsx`
**后端**：
- `ConfigureProductResource`（`/api/cpq/configure-product`）—— 预览与提交
- `ConfigureSearchResource`（`/api/cpq/quotations/configure`）—— 搜索、占用校验、外购件候选
- `ConfigureProductService`（2186 行）—— 全部业务逻辑
- `SelDsQuoteWriter` —— **选配写入侧唯一与 `ds_quote_*` 打交道的类**

**打开抽屉时一次性拉三份候选**（`ConfigureProductDrawer.tsx:123-163`），三者**互不阻断**，任一失败只让对应选择器进错误态：

| 候选 | 端点 | 数据来源（实查底层 SQL） | 备注 |
|---|---|---|---|
| 材质库 | `GET /material-recipes` | `MaterialRecipeService.list()` → `FROM material_recipe mr` + 标量子查询 `material_recipe_composition` / `material_recipe_config` / `element` | 客户端再过滤 `status='ACTIVE'` |
| 工序 | `GET /sel-param-types/PROCESS/candidates` | `SelParamCandidateService`（按 `sel_param_type.data_source_key` 分发）→ `ProcessMasterReadService` → 实体 `ProcessMaster` `@Table(name="process_master")`，取前 200 条 | 返回**信封** `{code,data}` |
| 有效模板 | `GET /sel-templates/effective/{customerNo}` | 见下方「模板解析的真实链路」——**5 张表**，不是 3 张 | **只用来收窄候选，不再有门禁** |

**模板解析的真实链路**（`EffectiveTemplateService.getEffective()` 逐行读出，🚫 不是按客户直接匹配模板）：

```
customer.code = :customerNo
      ↓ 取 customer.product_category_id                                    ← 表 ① customer
selTemplateService.getByCategory(categoryId)
      ↓ SelTemplate.find("productCategoryId", …).firstResult()             ← 表 ② sel_template
   命中？ ── 否 ──→ ProductCategory.requireDefaultId()                      ← 表 ③ product_category
                        ↓ 再按默认分类找一次（out.usedDefault = true）
                     仍无 ──→ hasTemplate = false，全放行
      ↓ 命中
SelTemplateItem.find("templateId = ?1 ORDER BY sortOrder")                  ← 表 ④ sel_template_item
      ↓ 逐个 enabled 的 item
SelParamType.findById(item.paramTypeCode)                                   ← 表 ⑤ sel_param_type
      ↓
candidateService.candidates(pt.code)   ← ⚠️ 每个 enabled 参数类型再查一次候选（材质库/工序库）
      ↓
effectiveValues = candidates ∩ item.allowedValues（allowedValues 为空则全放行）
```

三条实测要点：

1. **模板是挂在「产品分类」上的，不是挂在客户上**（`sel_template.product_category_id`）—— 这是 `task-260712-update071501`「三模板统一产品分类轴」的产物。客户没配产品分类 ⇒ 直接走默认分类模板。
2. **有默认分类回落**：客户分类找不到模板会再按 `ProductCategory.requireDefaultId()` 找一次，`usedDefault=true`。两次都找不到才 `hasTemplate=false`。
3. ⚠️ **`candidates()` 在循环体内被调用**（每个 enabled 参数类型一次）—— 材质候选那一支会再跑一次 `material_recipe` 全量查询。当前 `sel_param_type` 只有 3 行，量级可控，但形态上是 N+1。

### 🚩 为什么这三个候选**不读** `ds_quote_*`（常见疑问）

**`ds_quote_*` 里根本没有材质库 / 元素库 / 工序库。** 实测该体系共 16 张业务表：

```
ds_quote_material · _customer_part · _material_bom · _element_bom
ds_quote_self_process_fee · _assembly_fee · _assembly_fee_annual · _plating_fee · _plating_scheme
ds_quote_incoming_fixed_fee · _incoming_other_fee · _incoming_recovery · _incoming_annual
ds_quote_finished_other_fee · _sub_component_fee · _annual_discount
```

没有一张是主数据。材质库是 `material_recipe`(+`_composition`/`_config`/`_element`)、元素库是 `element`、工序库是 `process_master` —— **它们都没有 `ds_` 对应物**。

**两者是引用关系，不是替代关系**，`QuoteRegistry` 的列定义里写得很明确：

```java
col("material_part_no", "材质料号", …).master("recipe", "material_part_no_name")   // 值域主表 = 材质库
col("element_code",     "元素",     …).master("element", null)                      // 值域主表 = 元素库
nameCol("input_material_no_name", "投入料号名称", "input_material_no",
        "material_recipe", "code", "name")                                          // 名字靠 JOIN 材质库现算
```

即 `ds_quote_element_bom.material_part_no` 的**值域来自** `material_recipe.code` —— `ds_quote_*` 依赖主数据，反过来不成立。

**证伪实验**（2026-09-09 实测）—— 假如把候选改读 `ds_quote_*`：

| 候选 | 读主数据表（现状） | 若改读 `ds_quote_*` | 后果 |
|---|---|---|---|
| 材质 | `material_recipe` ACTIVE **263** 条 | `SELECT DISTINCT material_part_no FROM ds_quote_element_bom` = **18** 种 | **丢 93% 候选** |
| 工序 | `process_master` **9** 条 | `SELECT DISTINCT operation_no FROM ds_quote_self_process_fee` = **5** 种 | 丢 4 个 |

> 🔑 一句话：`ds_quote_*` 存的是「**哪些报价料号用过哪些材质/工序**」（结果），抽屉要的是「**库里有哪些材质/工序可选**」（候选）。读结果表 = 从没被用过的材质永远选不到，新材质建好后第一次也用不了。

> ⚠️ 两个端点包装格式不同：`/material-recipes` 返**裸数组**，`/sel-param-types/.../candidates` 返**信封**。
> ⚠️ 选配模板本期已下线（task-260902 F-13）：`sel_template_item_value` 现网 0 行 ⇒ 实际等于「不限」，无模板的客户也能正常走完全流程。

## 3. 步骤 2 · 添加配件

**组件**：`configure/PartCardList.tsx` + 全屏子面板 `configure/AddPartSubDrawer.tsx`

配件有**三条互斥路径**，进子面板先选类型，再选来源：

```
配件
├─ 零件 (PART)
│   ├─ 新建 (partMode='new')     → NewPartPanel.tsx     ← 唯一会铸新料号的路径
│   └─ 已有 (partMode='existing') → ExistingPartPanel.tsx
└─ 外购件 (OUTSOURCED)            → OutsourcedPartPanel.tsx
```

### 3.1 路径 A · 新建零件

**采集**：品名 / 规格 / 尺寸 / **零件总重（克）** + 材质 1..N（各带占比，Σ=100%）+ 工序 0..N（有序、可重复）

| 采集项 | 数据来源 | 表 |
|---|---|---|
| 材质下拉 | 抽屉打开时已拉的候选 | `material_recipe`（`status='ACTIVE'`） |
| 材质的含量配置 / 元素明细 / 可选元素集 | `GET /material-recipes/{id}?includeInactiveConfigs=` → `MaterialRecipeService.getDetail()`（`MaterialPicker.tsx:96` / `NewPartPanel.tsx:121,159` 按需拉） | 一次调用**固定 4 条 SQL**：`material_recipe` / `material_recipe_composition` / `material_recipe_config` / `material_recipe_element` |
| 工序下拉 | 抽屉打开时已拉的候选 | `process_master` |

`getDetail` 返回三块（实读源码，非推断）：

| 字段 | 来源表 | 用途 |
|---|---|---|
| `configs[]` | `material_recipe_config`（默认只 ACTIVE，按 `seq`）+ 内嵌各配置的 `material_recipe_element`（按 `sort_order`） | 「标准配置」下拉的选项 + 选中后展示的元素含量 |
| `composition[]` | `material_recipe_composition` | **自定义含量矩阵列的权威来源**（M-0）；后端 `resolveMaterial` 校验「元素是否在材质中定义」用的也是它 |
| `compositionEditable` | 派生：无 ACTIVE 配置时 `true`，有配置即 `false`（M-0b） | 元素组成是否还能改 |

> ⚠️ `composition[]` 与 `configs[]` 是**两个不同的东西**：前者是「这个材质由哪些元素构成」（值域），后者是「这些元素的几套含量档次」（取值）。自定义含量走 `composition` 校验、标准配置走 `configs` 物化。

**每个材质二选一**（互斥，两个都给或都不给 → 400 `MATERIAL_SOURCE_AMBIGUOUS`）：
- **标准配置**：给 `configNo`（如 `00006-01`）
- **自定义含量**：给 `elements[]`，要求该材质 `allow_custom_content=true`，否则 403

**前端校验**（`ratioRules.ts` / `partTextRules.ts`）：占比 Σ=100、同零件内材质不可重复、品名/规格/尺寸 ≤100 字符且不含 `| = , : ∅`。

### 3.2 路径 B · 已有零件

`GET /api/cpq/quotations/configure/search-parts?q=&size=50`（`ConfigureSearchResource:67`）：

```sql

       'Y' AS status_code, mm.material_recipe_id,
       mr.code, COALESCE(mr.symbol, mm.material_type), COALESCE(mr.name, mm.material_type),
       COALESCE(mr.spec_label, mm.specification), COALESCE(mr.recipe_type, mm.material_type)

LEFT JOIN material_recipe mr ON mr.id = mm.material_recipe_id
```

- **不做子件排除**（2026-05-31 用户裁决彻底移除）：组合产品要挑的正是这类中间装配子件。
- 选中后只带走料号，**不解析材质**（沿用它自己已有的）。

### 3.3 路径 C · 外购件

`GET /api/cpq/quotations/configure/outsourced-parts?keyword=&page=&size=`

```sql
SELECT ... FROM v_compat_material_master WHERE material_type = '外购件'
  [AND (material_no ILIKE :kw OR COALESCE(material_name,'') ILIKE :kw)]
```

- **判据是 `material_type='外购件'`**（闸门 A0 裁决）。这条判据成立的前提是 B-9 已把选配写入侧的 `material_type` 归位为「料号类型」，不再往里写材质名。

## 5. 步骤 4 · 确认并添加

### 5.1 指纹预览（只读，不写库）

进到第 4 步、防抖 500ms 后调 `POST /api/cpq/configure-product/lookup-fingerprint`。

**它与提交端共用同一套解析**（`prepareParts`），保证「预览命中 = 提交命中」。**唯一区别**：预览端跳过 `PART_WEIGHT_REQUIRED` 校验（用户可能还没填总重），代价是没填重量时按 `WEIGHT=0` 算 ⇒ **可能预览未命中而提交命中**（偏保守，不会造成错误复用）。

**指纹规范串格式**（`SalesFingerprintCalculator`，`STRUCTURE_VERSION = "v2"`）：

```
SIMPLE:    v2|CUST=<客户码>|PART=<len>:<品名><len>:<规格><len>:<尺寸>|WEIGHT=<总重>|MAT=<材质:占比(元素:含量,…)>|PRC=<工序码排序后>
COMPOSITE: v2|CUST=<客户码>|COMBO=<子件料号:用量 配对排序>|CPROC=<组合工艺码排序后>
```

**库内实证**（`sel_part_signature`，料号 `0028-2609000013`）：

```
v2|CUST=CUST-0004|PART=2:A13:2343:234|WEIGHT=11|MAT=AgCu90:100(Ag:90,Cu:10)|PRC=Z008
```

存的是这串的 `sha256`（`config_fingerprint`，`char(64)`）+ 原文（`config_signature_text`，便于审计）。

四条不变量：
1. **`PART=` 用长度前缀而不是 `/` 分隔** —— 本业务文本带 `/` 是常态（`AgZnO12/Cu`），用 `/` 分隔会让「品名 A/B + 规格 C」与「品名 A + 规格 B/C」撞成同一料号 → 静默错价。
2. **`configNo` 不进指纹** —— 按含量内容判同：含量逐字相同的两条配置（乃至标准配方 vs 自定义含量）必须复用同一料号。
3. **工序进指纹时排序、落库时不排序** —— 换序复用同一料号，但显示顺序沿用第一次写入的那次。**重复次数仍是指纹维度**（「焊两次」≠「焊一次」）。
4. **码值不得含 `| = , : ∅`** —— 否则规范串产生歧义，fail-fast。

**预览查表**：

| 查什么 | 表 | 干什么用 |
|---|---|---|
| 指纹是否已登记 | `sel_part_signature`（`customer_no`+`structure_version`+`config_fingerprint` 唯一） | 判定「这次配置是新建还是复用」 |
| 命中后拉快照 `buildSnapshot()` ① | `unit_price`（`cost_type='自制加工费' AND is_current`，`DISTINCT ON (seq_no)`） | ✅ **确认页显示「已有产品的真实工序顺序」** |
| 命中后拉快照 `buildSnapshot()` ② | `v_compat_material_master.unit_weight` | ❌ 前端无消费方，查完丢弃 |
| 命中后拉快照 `buildSnapshot()` ③ | `capacity`（`resource_group_no='QUOTE_ASSEMBLY' AND is_current`） | ❌ 前端无消费方，查完丢弃 |

**这段功能的业务含义**（一句话）：指纹侧对工序**排序后**比较、落库侧按**原始顺序**写 —— 所以用户选 `Z101→Z100` 会命中当初按 `Z100→Z101` 落库的料号，而命中即早退、落库侧一个字节都不重写。`buildSnapshot().processes` 就是去把那个料号的**真实工序顺序**捞回来告诉用户，否则他以为自己选的顺序生效了。

📖 **完整推导 + 三个字段的消费方实测 + 对切表的含义 → §11.3**

> 📌 **交接文档说的就是这里**：选配的「工序单价」拆在两张 V6 老表 —— 自制工序在 `unit_price`、组装工序在 `capacity`，活读点都是 `ConfigureProductService`。
> ⚠️ **新规则**：两张表读写全部切新表（用户裁决），且②③ 因无消费方**可直接删不必迁** —— 见 **§11.4 C-5**。

**COMPOSITE 预览必须无副作用**：逐子件**只查不铸**；任一子件未命中 ⇒ 提交时必新建 ⇒ 组合体必新建 ⇒ 直接早退 `matched=false`，不再算父指纹。

## 8. 两套版本化写入器

选配同时用了两套，语义不同，改动时不要混：

| | `VersionedGroupWriter`（新） | `VersionedV6Writer`（老） |
|---|---|---|
| 目标 | `ds_quote_material_bom` / `ds_quote_element_bom` | `unit_price` / `capacity` |
| 版本列（**实查列类型**） | `version_no` **`integer`** | `unit_price.version_no` **`varchar(20)`** · `capacity.calc_version` **`varchar(20)`** |
| 起始版本 | **1** | **`"2000"`**（字符串）；`max+1` 时**忽略非数字版本值**（如导入的 `'V_DEFAULT'`） |
| 判定 | `CREATED` / `UPGRADED` / `UNCHANGED`（按行指纹**多重集**比较：不看行序，计重复次数） | 内容相同复用 / 不同 `max+1` 升版 |
| 旧版本去向 | 整行归档进 `<表>_history`，主表 DELETE | `is_current` 翻转为 false，行保留 |
| 升版号 | `max(当前版本, _history 最大版本) + 1` | `max + 1` |
| 增量语义 | **只碰入参里出现的轴值**；库里有、本次没出现的轴值一行不动 | 同左 |

> ⚠️ **选配阶段永远走 `CREATED`**（新料号库里不存在）⇒ `version_no` 恒 1。升版时机由用户裁决移到**核价审批通过后**（该链路当前尚不存在）。

### 11.3 回答第 3 条：`buildSnapshot()` 在选配里到底干什么

**触发时机**：用户走到步骤 4「确认并添加」，前端防抖 500ms 调 `POST /lookup-fingerprint`；**指纹命中**时后端才调 `buildSnapshot(命中的料号)`。

**业务含义 —— 它解决的是「换序命中」造成的认知错位**：

指纹侧对工序是**排序后**比较（`PRC=` 排序拼接），落库侧按**原始顺序**写 `seq_no`，两侧**有意不对称**。后果是：

```
用户这次选：  Z101 → Z100
已有料号当初：Z100 → Z101
指纹相同 ⇒ 命中复用 ⇒ resolvePart 在任何落库之前 return（§6.3(c) 第 2 步）
        ⇒ 落库侧一个字节都不会重写
        ⇒ 最终生效的仍然是 Z100 → Z101
```

⇒ 如果不告诉用户，他会以为自己选的 `Z101 → Z100` 生效了。
`buildSnapshot()` 的 `processes` 就是去把**那个已有料号的真实工序顺序**捞回来，前端在确认页渲染成 `（Z100 → Z101）`（`ConfigureProductDrawer.tsx:185-189` → `ConfirmStep.tsx:243-244`，即 AC-19④，证据截图 `证据/e2e/02-AC-19-4-换序命中复用提示.png`）。

**🔴 实测：三个字段里只有 `processes` 有消费方**

| `Snapshot` 字段 | 后端查什么 | 前端消费点 |
|---|---|---|
| `processes` | `unit_price`（`cost_type='自制加工费' AND is_current`，`DISTINCT ON (seq_no)`） | ✅ `ConfigureProductDrawer.tsx:186` → `reusedProcesses` → 确认页 |
| `unitWeightGrams` | `v_compat_material_master.unit_weight` | ❌ **无消费方**（确认页显示的 `p.unitWeightGrams` 是本次输入的配件总重，来自 `parts`，不是 snapshot） |
| `compositeProcesses` | `capacity`（`resource_group_no='QUOTE_ASSEMBLY' AND is_current`） | ❌ **无消费方**（全前端 grep 无一处读 `snapshot.compositeProcesses`） |

**这对第 6 条切表的直接含义**：
- `capacity` 在选配里的**唯一读点**就是这里，而**返回值被丢弃** ⇒ 切表时这段查询**可以直接删掉，不需要迁移**。
- `v_compat_material_master.unit_weight` 那次查询同理，**可直接删**（顺带消掉一个对已废弃视图的依赖）。
- 只有 `processes` 那段必须迁到 `ds_quote_self_process_fee`（读 `operation_no` + `operation_item_seq`，按项次升序）。

### 11.5 C-1 的材质来源方案（用户 2026-09-09 裁定）

> **用户原话**：「老 SQL 靠 `mm.material_recipe_id` 带出材质信息 本来就是错误的，一个料号可能有多个材质组成，不是一个 id 可以解决的，应该查 `ds_quote_material_bom` 的 `input_material_no` 关联 `material_recipe` 的材质编号，带出料号的材质」

**数据印证（两条，都支持这个裁定）**：

① **多材质是常态，一个外键装不下** —— `ds_quote_material_bom` 按 `(customer_no, material_no)` 统计 `RECIPE` 行数：

| 材质行数 | 料号数 |
|---|---|
| 1 | 19 |
| **2** | **7** |
| **4** | **2** |

⇒ 有 RECIPE 行的 28 个料号里 **9 个是多材质（32%）**。`material_master.material_recipe_id` 是单值外键，结构上就装不下。

② **而且这个字段实际上早就空了** —— `material_master` 全表 **48 行，`material_recipe_id` 非空的只有 1 行（2%）**。
⇒ 老 SQL 的 `LEFT JOIN material_recipe mr ON mr.id = mm.material_recipe_id` 对 **47/48 行返回全 NULL**，`recipe_code` / `recipe_symbol` / `recipe_name` 三列全靠 `COALESCE(…, mm.material_type)` 兜底成料号类型字符串。
**所以现状不是「多材质显示不全」，是「材质信息几乎从来就没有过」。**

**改造方向**：

```sql
-- 料号 → 材质（一对多）
-- 🚫 判据不是 output_material_type，是「input_material_no 能不能在材质表里找到」
FROM ds_quote_material m
LEFT JOIN ds_quote_material_bom b
       ON b.customer_no = m.customer_no
      AND b.material_no  = m.material_no
JOIN      material_recipe mr                    -- ← 能 JOIN 上 = 是材质；JOIN 不上 = 不是
       ON mr.code = b.input_material_no
WHERE m.customer_no = :customerNo               -- ← 必带客户，见下方裁定②
```

⚠️ 四个必须一起想清楚的点：

1. 🔴 **判据是 JOIN 命中，不是 `output_material_type`**（用户裁定①，见 §11.9）。
2. **返回形状变了**：一个料号对应 N 个材质 ⇒ `SearchPartResult` 的 `recipeCode`/`recipeSymbol`/`recipeName`/`recipeSpec`/`recipeType` 五个**单值字段**要么改成数组、要么 `string_agg` 成展示串。**这是跨端契约变更**（前端 `ExistingPartPanel.tsx` 在渲染它们）。
3. **JOIN 键是 `code` 不是 `id`**：`ds_quote_material_bom.input_material_no` 存的是 `material_recipe.code`（Registry 里 `nameCol(… "material_recipe","code","name")` 已是这个口径）。
4. **料号本身要 LEFT**：外购件、组合父料号没有材质行，用 `LEFT JOIN ds_quote_material_bom` 保住料号本身不被吞；材质那一跳才是 INNER（判据）。

### 11.6 C-2 的两个连带问题（回答「`(keyword,page,size)` 的作用是什么」）

**这三个参数的实际作用 —— 实读 `OutsourcedPartPanel.tsx`**：

| 参数 | 后端 | 前端实际怎么传 |
|---|---|---|
| `keyword` | `material_no ILIKE :kw OR material_name ILIKE :kw` | ✅ **真在用**：输入框 + 回车/「搜索」按钮触发 `load(keyword)` |
| `page` | `OFFSET (page-1)*size` | 🔴 **恒为 `1`**（`load()` 里硬编码 `page: 1`），永不改变 |
| `size` | `LIMIT size`（上限 200） | 🔴 **恒为 `PAGE_SIZE = 20`** 常量 |
| 返回的 `total` | `SELECT COUNT(*)` | ⚠️ 只用来显示「共 N 条」这行文字 |

而表格是 `<Table … pagination={false}>`（加载态和正式态**两处都是**）。

🔴 **⇒ 后端的分页能力前端从未接上**：外购件候选超过 20 个时，**第 21 个及以后在界面上永远选不到**，页面只会显示「共 35 条」而列表只有 20 行、没有任何翻页控件。用户唯一的出路是靠关键词缩小范围。

📌 **为什么至今没暴露**：候选条数一直没过 20（实测 `v_compat_material_master` 侧 **6** 条）。这是个**被数据量掩盖的 bug**，不是已解决的问题。

**第二个连带问题 —— 切表后会出现跨客户重号**：

| 口径 | 条数 |
|---|---|
| `v_compat_material_master WHERE material_type='外购件'`（现读） | **6** |
| `ds_quote_material WHERE material_type='外购件'`（应读） | **10** |
| ↑ 去重 `material_no` 后 | **5** |

新表唯一键是 `(customer_no, material_no)` ⇒ **同一个外购件料号挂在几个客户下就出现几行**（实测重复率 2 倍）。兼容视图已经用 `DISTINCT ON` 收敛过（所以是 6 条），直连新表就得自己收敛。

⇒ **切表时必须同时决定**：① 端点加 `customerNo` 参数按客户过滤（推荐，与写入侧口径一致）；还是 ② 跨客户 `DISTINCT ON (material_no)` 保持现有「跨客户搜索」语义。
📌 同型问题在 `repair-260908 C-1` 已经处理过一次（V435 给 `v_compat_material_master` 加 `DISTINCT ON`），**直连新表等于把那次修复绕过去了**。

### E-2：不是「UNION」，是「patch 覆盖」—— 关联键是 `origin_id`

> 🔴 **本节首版把问题问错了**（用户 2026-09-10 指出「UNION 是用来关联什么的」）。
> 实测后确认：`_record` 与主表**不是两批平行数据求并集**，而是**「基底 + 覆盖层」**，关联键是 `_record.origin_id → 主表.id`。

**实测证据**（选配单 `257820e9-49d0-406a-a83a-68568ebbf689`）：

| `_record` 行 | | 主表行 |
|---|---|---|
| `material_no=0028-2609000013` `input=AgCu90` `origin_id=16590` `base_version_no=1` | ⟷ | `id=16590` `output_material_type='RECIPE'` `material_ratio=100` `version_no=1` |
| `material_no=S0001` `input=S0002` `origin_id=16582` `base_version_no=4` | ⟷ | `id=16582` `output_material_type='产出类型1'` `version_no=4` |
| `material_no=0028-2609000014` `input=00006` **`origin_id=NULL`** `item_seq=NULL` | ⟶ | （主表无对应行 = 本单新增） |

⇒ 三类行，处置完全不同：

| `_record` 行的形态 | 含义 | 渲染时怎么办 |
|---|---|---|
| `origin_id` 非空 | 本单对主表某一行的**投影/改动** | 用 `_record` 的值**覆盖**主表那一行 |
| `origin_id` 为 NULL | 本单**新增**的行（主表没有） | **追加** |
| 主表有、本单 `_record` 没有 | 本单没碰过 | 原样用主表的值 |

**这三条正是 `DsQuoteBackfillService` 的 "patch 语义"**（类注释原文：「按 patch 语义把 `_record` 回填升版到 `ds_quote_*` 主表」）。
⇒ **方案 ② 的渲染期取数，就是把回填时的 patch 逻辑提前到渲染期跑一遍**（只读、不落库）。

### E-2 的两个落点（推荐：甲）

**现状 SQL**（`T260907-物料BOM`，本身已含一个 `UNION ALL`：BOM 边 + 树根分支）：

```sql
FROM ds_quote_material_bom dqmb
WHERE dqmb.input_material_no = ANY(:total_material_no) AND dqmb.customer_no = :customerCode
UNION ALL
-- 根分支：本单闭包里无父边的成品自身
FROM ds_quote_material dqm WHERE … AND NOT EXISTS (…)
```

| | 落点 | 改动 | 代价 |
|---|---|---|---|
| **甲（推荐）** | **在 `ComponentDriverService` 的 Java 层做 patch 合并** | 组件 SQL **一段不改**；expand 拿到主表结果后，用 `_record`（按 `:quotationId` 过滤）按 `origin_id` 覆盖/追加 | 合并逻辑从声明式变命令式；但**与 `DsQuoteBackfillService` 的 patch 逻辑可共用同一套代码**，两处不会漂移 |
| **乙** | 改那 12 段生产组件 SQL | 各自加 `LEFT JOIN … ON r.origin_id = dqmb.id` + `UNION ALL` 追加 `origin_id IS NULL` 的行 | 12 处各写一遍 patch SQL（覆盖 + 追加 + 排除），**每段都要处理 `:quotationId` 为 null 的老调用者**；未来新建组件必漏 |

**推荐甲的三条理由**：
1. **patch 语义已经有一份实现**（`DsQuoteBackfillService` + `DsBackfillCollector`）。走 Java 层可以复用它，符合本项目「🚫 严禁两套实现，必然漂移」的既有纪律（`VersionedGroupWriter` 类注释原话）。
2. **12 段 SQL 各写一遍 = 12 份会漂移的实现**，而且取数配置器（`$builder_*`）是生成式的，手改的 SQL 下次重建配置就没了（§9.1 实测：组件 `data_driver_path` 全部是 `$builder_*`）。
3. 乙的每一段都要额外处理「`:quotationId` 为 null（详情页老协议）时不要 patch」，12 段 × 边界分支 = 高漏改概率。

#### E-4：需要补的**只有两列**，且只在物料BOM侧

| 列 | 主表填充率 | `_record` 填充率 | 停写主表后的后果 |
|---|---|---|---|
| `output_material_type`（卡片「产出料号类型」） | 99.9% | **24.4%** | 该列在卡片上变空 |
| `material_ratio`（卡片「材料占比（%）」） | 96.9% | **12.2%** | 该列在卡片上变空 |
| `item_seq` / `component_qty` | ~100% | ~99% | ✅ 不受影响 |
| 元素侧全部列 | — | 100% | ✅ **不需要补** |

**做法**：在 `DsQuoteRecordService` 的投影里把这两列纳入。
⚠️ **范围建议只限选配新铸料号**，不动导入侧投影 —— 导入侧现在靠主表有完整值，改投影会波及 30 张单的既有 `_record`，属独立评估。

#### E-3：🔴 答案是「**按列覆盖**」，不是「整行覆盖」

**决定性实证**：库里**找不到一行**是「用户改动导致 `_record` ≠ 主表」的。
所有 `_record` 与主表的差异，形态**完全一致**：

```
rec_input == main_input   （相同）
rec_qty   == main_qty     （相同）
rec_ratio = (空)  vs  main_ratio = 100.000000000000   ← 差异全部来自这里
```

⇒ 现存差异 **100% 来自投影残缺（E-4），不是业务改动**。

**所以「整行覆盖」是危险的**：

```
若按「_record 整行覆盖主表」：
  主表 material_ratio = 100  →  被 _record 的 NULL 覆盖  →  卡片显示空
  ⇒ 不是"用本单的值"，是"用没投影上的空值把真实值抹掉"
```

✅ **推荐：按列覆盖（COALESCE 语义）** —— `_record` 该列**有值**才覆盖，为 NULL 则保留主表值：

```
effective_col = COALESCE(record.col, main.col)
```

三条理由：
1. **对 E-4 免疫**：即使投影暂时没补全，卡片也不会变空 ⇒ **E-4 从「阻塞项」降级为「优化项」**，可以分批做。
2. **与 patch 回填语义一致**：`DsQuoteBackfillService` 回填时也不会用 NULL 去抹主表值（那样每次核价都会丢数据）。
3. **可证伪**：实施后只要出现「某列在卡片上从有值变空」，就说明退回了整行覆盖 —— 判据明确。

⚠️ **一个例外要显式约定**：按列覆盖之后，「用户主动把某个值**清空**」这个动作无法表达（清空 = NULL = 保留主表旧值）。
📌 现状下这个场景不存在（用户编辑走 `quotation_line_component_data.row_data`，不进 `_record`），但若日后要支持"本单显式清空某列"，需要在 `_record` 里加一个显式的 tombstone 标记，🚫 不能靠 NULL 表达。

#### 两条的依赖关系

```
E-3 选「整行覆盖」 ⇒ E-4 必须先做完，否则卡片两列变空（阻塞）
E-3 选「按列覆盖」 ⇒ E-4 可以后做，卡片始终不会变差（推荐）
```

### ⚠️ 连带：`snapshot_rows` 的冻结时机不变，但取数源变了

②**不改**渲染期（§12.5b 的第②段一个字节不动），只改冻结期的取数。
⇒ 冻结仍发生在选配提交后那一刻，此时 `_record` 已由 `syncRecordsForFlow` 写入（`ConfigureProductResource:103`，事务提交之后）。
🚨 **时序必须复核**：`snapshotLines`（`:72`）跑在 `syncRecordsForFlow`（`:103`）**之前** ⇒ 按现有顺序，冻结那一刻 `_record` **还没写**。
⇒ **实施 ② 时必须调换这两段的顺序**，否则冻结依然读不到数据，卡片照样空。

## 14. 选配的业务定位（用户 2026-09-10 澄清）

> **用户原话**：「选配新增 → 这个场景是客户的产品编号在我们客户料号表中不存在，所以需要选配新增。此时可以选择一个已有的销售料号进行直接绑定，这样子最简单，直接不用零件选配，直接带入已有的销售物料号的数据信息即可（**直接绑定已有零件的功能还没有做，本期可以一并加上**）。第二种情况就是销售没有找到可以直接绑定的销售料号，需要选配新增一个销售料号来绑定客户料号，此时这个选配新增的料号在各个 `ds_quote_*` 表中一定是不存在的……新建零件选择材质和工序后，产生的数据（那两列是空），**核价后覆盖也不会产生问题，因为本来就没有这组 BOM**。」

### 14.1 选配的触发条件与两条分支

**触发条件**：客户产品编号在 `ds_quote_customer_part` 中**不存在**（这正是 §2 那个占用校验的反面）。

```

├─ 情况 1：能找到可直接绑定的已有销售料号
│    ⇒ 直接绑定，不走零件选配，带入该销售料号的既有数据
│    🆕 【功能缺口，用户裁定本期一并加上】
└─ 情况 2：找不到 ⇒ 新铸一个销售料号
     ⇒ 新铸料号在各 ds_quote_* 表中【一定不存在】
     └─ 配件层：新建零件（选材质+工序）/ 已有零件（直接带入）/ 外购件
```

### 14.2 🆕 情况 1 是真实功能缺口（实测确认）

| 现有入口 | 能不能满足情况 1 | 实测依据 |
|---|---|---|
| 「添加产品 ▾ → **从已有产品添加**」 | ❌ **不能** | `ExistingProductService` **只读** `ds_quote_customer_part`（全类无 `insertCustomerPart` / 无 INSERT）⇒ 它是「挑一个**已有绑定**加进报价单」，不创建新绑定 |

⇒ **「客户产品编号不存在，但销售料号用已有的」这个组合，当前两个入口都覆盖不到。**

### 14.3 用户关于「两列空」的判断：数据安全上**成立**

✅ **回填不会抹掉任何真实值** —— 新铸料号在主表没有这组 BOM，回填走 `VersionedGroupWriter` 的 `CREATED` 分支（首次创建，`version_no=1`），不存在"用空值覆盖真实值"。§12.7 E-3 里那个「整行覆盖会抹掉主表值」的风险，**对情况 2 的新铸料号不成立**。

### 14.4 🔴 但有一个**实质数据丢失**，与"覆盖"无关

**`material_ratio`（材料占比 %）是用户在选配抽屉里亲手填的**，后端还强制 Σ=100%（填错直接 400 `MATERIAL_RATIO_SUM_INVALID`）。而 `_record` 的投影**没带这一列**。

**实证链条**（已核价通过的 `0526-2609000006`）：

| 位置 | `material_ratio` |
|---|---|
| `ds_quote_material_bom_record` | **0 行**（覆盖式，回填后已被后续操作重写，查不到当时那份） |
| `ds_quote_material_bom`（主表 v2，`source=QUOTE_BACKFILL`） | **100.000000000000** |
| `ds_quote_material_bom_history`（v1） | **100.000000000000** |

🔑 **v1 的 100 是选配「直写主表」写进去的**（现状双写）；回填时 patch 走 COALESCE 语义，`_record` 的空值不覆盖 ⇒ v2 保住了 100。
⇒ **双写是当前 `material_ratio` 不丢的唯一原因。**

⚠️ **推论（非实测，依据 patch 的 COALESCE 语义）**：停写主表后 —— 主表无 v1 基底 ⇒ `COALESCE(record.material_ratio=NULL, 无基底)` = **NULL** ⇒ **核价通过后主表的 `material_ratio` 也是空**。
⇒ 用户填的 70%/30% 在「选配抽屉 → `_record`」这一跳就永久丢了，不是显示问题，是**数据没落库**。

### 14.5 ⇒ E-4 更正：只补一列，理由也换了

| 列 | 补不补 | 理由 |
|---|---|---|
| **`material_ratio`** | ✅ **必须补** | 用户亲手填的业务数据，不补则永久丢失（§14.4）。多材质场景实测占 32%（9/28 料号），单材质恒 100% 影响小 |

| 元素侧全部列 | ✅ 已完整 | `element_code` / `content_pct` 实测 100% 填充 |

🔄 **E-4 的定性从「覆盖会抹数据」更正为「用户输入会丢失」** —— 前者被用户的业务澄清推翻（本来没数据可抹），后者是新的、更硬的理由。

⇒ **D-43 落地后，D-40 那个选配挂点在「让核价有东西可回填」这个目标上已经是冗余的** —— 因为选配建的单最终一定要走 `submit`，那时 `_record` 就写了。

### 15.4 ⚠️ 但在方案 ② 下，选配挂点从「冗余」变回「必需」

| | 现状（双写） | 方案 ②（带版本表只写 `_record`） |
|---|---|---|

⇒ §12.7 那条「`snapshotLines`(`:72`) 与 `syncRecordsForFlow`(`:103`) 必须调换顺序」的修正，正是这个道理的直接后果。

### 15.5 由此引出一个需要重新确认的点

方案 ② 把 `_record` 从「**提交/保存时的用户改动留痕**」变成了「**建单那一刻的渲染数据源**」——
这两个角色对**写入时机**的要求不同：

| 角色 | 何时必须有 `_record` |
|---|---|
| 原角色：核价回填的数据来源 | 提交之前即可（submit 挂点足够） |
| 方案 ② 新角色：卡片渲染的数据源 | **建单那一刻** |

⇒ 方案 ② 不只是「换个表写」，它**改变了 `_record` 的角色定位**。
🚦 这一点建议在立项文档里显式写清，否则后来人只看到"选配写 `_record`"，会以为它和 saveDraft/submit 那两个挂点是同一回事、可以合并或删掉。

**这正是 `D-43` 描述的形态**：「把 N 张卡片的投影拼起来 ⇒ `usedBase` 只让第一份认领到 `origin_id`，其余 `origin_id=NULL` ⇒ 回填按新增追加 ⇒ 整组 ×N」。
⇒ **`DsRecordCardDeduper` 在「同一张单里同一料号有多个 line item」这个场景下没有生效。**
