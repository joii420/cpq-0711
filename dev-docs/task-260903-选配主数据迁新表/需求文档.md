## 1. 为什么做

`task-260902` 把选配升到三层模型后，选配产出的主数据仍写在 **V6 旧表**（`material_master` / `material_bom` / `material_bom_item` / `element_bom` / `element_bom_item`）。

而「新料号数据规则」那条线已建成 `ds_quote_*` 报价侧新表体系（16 张，带 `version_no` + `row_fingerprint` + `_history` 版本化）。**用户裁决：选配改往新表落库，不再写 V6，且不做双写。**

不双写意味着**没有过渡期** —— 停写 V6 的那一刻，读 V6 的渲染链路就断。所以本任务必须同时做两件事，且**顺序不能反**。

---

## 2. 两阶段（B 先行，A 后到）

| 阶段 | 内容 | 为什么这个顺序 |
|---|---|---|
| **B · 渲染读取侧** | 建兼容视图；135 个组件 SQL + 3 个 PG 视图改读它 | 先让渲染层「两边都能读」，此时 V6 仍在写，**系统行为零变化**，可安全验证 |
| **A · 选配写入侧** | 选配改写 4 张新表；停写 V6 五表；退役 `sel_product_no` | B 落地后才切写入，切换瞬间渲染不断 |

🚫 **A 先于 B 上线 = 选配产品在报价单里渲染为空。** 这是本任务最重要的顺序约束。

## 5. 本期明确不做

1. **存量 V6 数据迁移到新表** —— 实测有 2 个料号存在真正的跨客户 BOM 差异（`3120011203` 在 `CUST-0002` 下是 `3110520422+00144`、在 `_GLOBAL_` 下是 `VS-RM01/02/05`，组成完全不同），而新表无 `customer_no` 只能存一份。归「新料号数据规则」那条线处理。
2. **「审批通过后回写基础数据并升版」** —— 实查核价审批 5 个类（`CostingOrderResource` / `CostingFreezeService` 等）回写调用 **0 处**，整条链路不存在。它还要回答「回写哪些字段 / 多张报价单引用同一料号时谁的编辑生效 / 回写失败算不算审批通过」，是独立任务。
3. **工序侧迁移** —— `quotation_line_process` / `unit_price` / `capacity` 仍走 V6。新体系的 `ds_quote_self_process_fee` 是「按料号导入的基础费率」，与「报价单行的工序单价」语义不同，硬套会错位。
4. **报价单单据层迁移** —— `quotation_line_item` 等新体系没有对应表。
5. **核价侧（`ds_cost_*`）** —— 本任务只动报价侧。
