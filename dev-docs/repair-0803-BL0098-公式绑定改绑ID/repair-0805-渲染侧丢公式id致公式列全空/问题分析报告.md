## 0. 一句话结论

**不是公式算错，是前端渲染层根本没去算。**

`BL-0098「公式绑定改绑稳定 ID」`（repair-0803 的一部分）把「字段 → 公式」的解析主键从**公式名**换成了**公式 id**，
但**报价渲染侧的 `enrichComponentData` 两条组装路径在把公式搬进渲染模型时把 `id` 丢了**
（`ComponentFormula` 接口压根没声明 `id` 字段）。

于是渲染层 `resolveFormula` 拿 `field.formula_id` 去 `comp.formulas` 里找 —— **每一条公式的 `id` 都是 `undefined`，永远找不到**；
而该分支**刻意不回落**到按名字/按位置匹配（这是 BL-0098 的正确设计），于是这些 FORMULA 字段
**整个不进计算列表** → 渲染取值 `formulaCache[列名] === undefined` → 单元格显示 `—`。

后端算得完全正确（快照里 11 列全是正确数值），**只有前端画不出来**。

## 3. 根因 A（主因）：BL-0098 的 id 在渲染侧被丢弃

### 3.1 断链点

`cpq-frontend/src/pages/quotation/QuotationStep2.tsx:131-135` —— 渲染侧的公式类型**没有 `id`**：

```ts
export interface ComponentFormula {
  name: string;
  expression: any[];
  result_type?: string;
}                      // ← 没有 id
```

`cpq-frontend/src/pages/quotation/enrichComponentData.ts` 两条组装路径都按这个类型逐键搬运，
于是 `id` 在这里**被结构化地丢掉**：

```ts
// :166-170  enrichComponentData（走模板快照）
const formulas: ComponentFormula[] = (snapshotComp.formulas || []).map((fm: any) => ({
  name: fm.name || '', expression: ..., result_type: fm.result_type,   // ← 没搬 id
}));

// :297-301  buildComponentDataFromStructure（走报价单冻结结构）
const formulas: ComponentFormula[] = (tab.formulas || []).map((fm: any) => ({
  name: fm.name || '', expression: ..., result_type: fm.result_type,   // ← 没搬 id
}));
```

**数据源本身是好的** —— 冻结结构 `quote_card_structure` 里每条公式都带 `id`
（实测 `structure formula[0] keys = ['expression','id','name','result_type']`，
且与字段的 `formulaId` 逐字对得上）。是**前端搬运时丢的**。

### 3.2 失败放大

丢了 `id` 之后，三处 id 解析全部空转：

| 位置 | 代码 | 后果 |
|---|---|---|
| `QuotationStep2.tsx:380-382` | `resolveFormula` 的 `formula_id` 最高优先级分支 | 返 `undefined` 且**刻意不回落** → 字段**整个不进 `formulaFields`** → 结果 map 里**连 key 都没有** |
| `QuotationStep2.tsx:494-501` | `computeAllFormulas` 条件公式 `byRef` | `rules` 被 `.filter` 全清空、`default` 为 `undefined` → 求值时 `expr === undefined` → **返 `null`** |
| `QuotationStep2.tsx:797-806` | `collectFormulaDefs`（task-0803 BOM 树求值入口） | 同上，树页签路径同样中招 |

渲染层 `ComponentCell.tsx:297-299`：

```ts
const val = formulaCache[field.name];                                    // undefined 或 null
const text = formatNumber(val, {...}) ?? '—';                            // → '—'
```

**两种字段模式的表现略有差别**（截图里都能看到）：

| 字段模式 | 解析结果 | 单元格 | 列小计 |
|---|---|---|---|
| 单一公式 + `formula_id`（10 个） | key 不存在（`undefined`） | `—` | **保留 `row_data` 里的旧值**（见 §4.3） |
| 条件公式 + `formula_id`/`default_formula_id`（材料成本） | key 存在但值 `null` | `—` | `0` |

实测「材料成本」字段配置：
```json
"conditional_formula": {
  "rules":  [{ "formula": "非银点类材料成本公式", "formula_id": "cb3ea05c-…" }],
  "default": "银点材料成本公式", "default_formula_id": "c9213b82-…"
}
```
两个 id 都查不到 → 规则全丢、默认也丢 → `expr = undefined` → `null` → 小计 `¥ 0`。✅ 与截图一致。

### 3.3 为什么 tsc 没拦住

三处查找全都写成 `comp.formulas.find(x => (x as any).id === …)` —— **`as any` 把类型缺失强行绕过去了**。
如果 `ComponentFormula` 声明了 `id?: string`，或者查找处不写 `as any`，
TypeScript 会在**编译期**指出这个字段在渲染模型里并不存在。

讽刺的是，组件**配置侧**的同名类型（`src/pages/component/types.ts:199-211`）不但有 `id`，
还写了一段警告：

> 🚨 加载时必须原样保留、保存时必须原样送回 —— **丢了会让所有字段绑定失配、那些列静默不出值**。

**这条警告说中了**，只是没有覆盖到渲染侧这条路径。

## 4. 根因 B（前置条件 / 放大器）：前后端 rowKey 口径不一致

### 4.1 机制

`useCardSnapshots.ts:110-135` 的 `computeRowKey` 按 `f.defaultSource`（**camelCase**）解析行键字段；
但渲染模型里的字段是 `enrichComponentData.ts:286` 写出的 `default_source`（**snake_case**）：

```ts
default_source: f.defaultSource,     // 结构快照 camelCase → 内部 snake_case
```

调用点 `QuotationStep2.tsx:2081` 又用 `as any` 抹掉了类型差异：

```ts
buildUniqueRowKeys(comp.fields as any, rkfForSide, baseRows, true)
```

于是 `fd?.defaultSource === undefined` → 走不到「按 `$bom_view._料件` 取值」那一级 →
`driverRow['料件']` 又是 `null`（driverRow 的键是 `_料件`）→ **全空 → 退化成行号**。

后端 `FormulaCalculator.computeRowKey` 有完整字段定义，解析出内容键 `AgNi10/Cu触点`。**两边永久对不上。**

### 4.2 这不是新问题

`cpq-frontend/src/pages/quotation/deletedRows.ts:56-59` 早有记载（2026-07-14 删错行修复时写的）：

> effKey 由 computeRowKey 算，**前后端对同一行可不一致**（前端 `driverRow['料件']=null` → 索引兜底 `"0"`，
> 服务端经字段定义解析成内容 `"AgNi11#-Ⅰ"`）→ 双命中因 effKey 对不上而漏删。

当时的处置是**绕开**（删除改用内容指纹 `fp` 单键匹配），**根因没修**。

### 4.3 它的真实危害是「拆掉了安全网」

根因 B 单独存在时**用户无感** —— 快照查不到就走本地 `computeAllFormulas` 兜底，值照样出来
（这正是代码注释里写的「缺时 computeAllFormulas 兜底(防漂移)」）。

**根因 A 单独存在时用户也大概率无感** —— 本地引擎虽废了，但快照能命中，照样显示后端算好的值。

**两个凑一起才炸**：快照命中不了 → 落到本地引擎 → 本地引擎被 A 打废 → 满屏 `—`。

### 4.4 列小计为什么还有数（最危险的一点）

`buildResolvedRow`（`QuotationStep2.tsx:1300-1310`）：

```ts
if (key in formulaCache) out[key] = formulaCache[key];
// 否则保留 driverRow / row 里的原值
```

单一模式字段因为**连 key 都没有**，`key in formulaCache` 为 `false`
→ `resolvedRows` **回落到 `row_data` 里后端上次物化的旧值**
→ 列小计（读 `columnSumsByComp`，源自 `resolvedRows`）**照样显示 `27.614071`**。

**即：明细列全空，小计却是「上一次算对的数」。** 这是典型的静默不一致——
如果这次故障没有把明细也打空、只打空了一部分列，很可能被当成「显示问题」放过去，
而实际参与提交/导出的数就已经是混着新旧口径的了。

## 6. 为什么两个任务之后才暴露

| 时间 | 事件 |
|---|---|
| ~2026-08-02 | `resolveFormula` 只按 name/位置解析，enrich 丢 `id` **无害**（没人用 id） |
| 2026-08-03 `cf07dc5b` | 前端 `resolveFormula` 插入 `formula_id` 最高优先级、**查不到不回落** |
| 2026-08-03 `1062c41c` | 后端补齐结构快照的 `formulaId`；`FormulaIdBinder` 开始给保存的组件写 `formula_id` |

**BACKLOG 的 BL-0098 条目第 114 行其实已经预言了这个失败模式**：

> 绑了名字找不到 → 该字段**整个不进计算列表** → 那一列**静默不出值、不报错**；条件公式同理（静默丢规则）

只是当时讨论的是「按名字绑」的风险，没想到「按 id 绑」会因为**渲染侧丢 id** 而踩进同一个坑。

## 7. 修复建议

### 7.1 必修（根因 A）

1. **`ComponentFormula` 接口补 `id?: string`**（`QuotationStep2.tsx:131`），
   同时把三处查找的 `as any` 去掉 —— 让类型系统守住这条协议。
2. **`enrichComponentData.ts:166` 与 `:297` 两条搬运路径补 `id: fm.id`**。
   两处必须一起改（漏一处 = 一条链路好、另一条静默坏，正是 AP-41 那类「一个视图正常一个失效」）。
3. **回归门禁**：加一条断言「`comp.formulas` 每条都有 `id`，且字段 `formula_id` 在其中能查到」，
   直接把这条协议钉成测试，防止下次白名单再漏。

### 7.2 建议同修（根因 B，否则安全网永远是坏的）

4. `useCardSnapshots.computeRowKey` 同时兼容 `defaultSource` / `default_source` 两种写法
   （或在调用点做一次归一），**并补一条前后端 rowKey 对拍测试**
   （用本单据的 6 行做夹具，前端算出的键必须逐字等于后端 `formulaResults[].rowKey`）。
   —— 这条 2026-07-14 就被记录、被绕开、至今仍在的分歧，是本次故障能炸出来的前提。

### 7.3 建议评估（可观测性）

5. **「绑了公式却解析不到」必须可见**。当前失败是完全静默的：不报错、不告警、单元格只是变成 `—`，
   而且列小计还残留旧值伪装成正常。建议在 `resolveFormula` / `byRef` 解析失败时
   走已有的错误旁路（`out.errors` → `ComponentCell` 的 `⚠` + tooltip），
   与 repair-0803 B1「让错误可见」同一思路。

### 7.4 存量单据

修完前端后，**已有单据无需数据修复** —— 后端快照里的值本来就是对的；
rowKey 修好后快照直接命中，本地引擎修好后兜底也正确。
但建议对 §5.1 表里 10 个组件涉及的在途单据做一次抽查确认。

**「解析主键换代」= 键的两端必须同时迁移，且中间每一层搬运都是断点。**

本次断的是「值的一端」：字段侧 `formula_id` 透传了（`cf07dc5b` 明确写了「enrich 两条路径都透传 formula_id」），

三个可复用的检查动作：
1. 换解析键时，列出该键**两端**的全部承载点与全部搬运层（白名单式 `.map()` 是高危点），逐个勾。
2. **`as any` 是协议断点的高发地**——凡是在 `find(x => (x as any).xxx === …)` 里出现的属性，
   说明类型系统已经不认识它了，必须回头确认那个属性在这条链路上真的存在。
3. **「不回落」的设计（正确）必须配「失败可见」（缺失）**。BL-0098 刻意不回落是对的，
