## 0. 一句话

BL-0098 把「字段 → 公式」的解析主键从**公式名**换成**公式 id**，
但**报价渲染侧的 `enrichComponentData` 两条组装路径没把公式的 `id` 搬过去**
（`ComponentFormula` 接口根本没声明 `id`），
导致渲染层按 id 查找恒不命中 → 那些 FORMULA 字段**整个不进计算列表** → 单元格显示 `—`。

**只搬了钥匙，没搬锁。** 后端不受影响（算得完全正确），故障纯在前端渲染层。

## 1. 缺陷定义

### 1.1 用户可见现象

报价单编辑页 / 详情页的产品卡片里，**绑定了公式的计算列整列显示 `—`**（或 `0`），
但**列小计仍显示旧值**，形成「明细全空、小计有数」的静默不一致。

线上样本：`QT-20260804-0068` →「物料」页签 11 个公式列全空；
列小计 `材料成本 = ¥ 0`（应为 `623.597504`）、`材料损耗成本 = ¥ 27.614071`（旧值残留）。

### 1.2 根因 A（主因，必修）

| # | 位置 | 事实 |
|---|---|---|
| A1 | `QuotationStep2.tsx:131-135` | 渲染侧 `ComponentFormula` 接口**没有 `id` 字段** |
| A2 | `enrichComponentData.ts:166-170`（模板快照路径） | 白名单式 `.map()` 只搬 `name/expression/result_type`，**漏搬 `id`** |
| A3 | `enrichComponentData.ts:297-301`（冻结结构路径） | 同上，**漏搬 `id`** |
| A4 | `QuotationStep2.tsx:381` `resolveFormula` | 按 `field.formula_id` 查 → 恒 `undefined` → **刻意不回落** → 字段整个不进 `formulaFields` → 结果 map 连 key 都没有 |
| A5 | `QuotationStep2.tsx:495` 条件公式 `byRef` | `rules` 被 `.filter` 清空、`default` 为 `undefined` → 求值 `expr === undefined` → 返 `null` |
| A6 | `QuotationStep2.tsx:799` `collectFormulaDefs`（BOM 树求值入口） | 同 A5，树页签路径同样中招（task-0803 复制的第三处） |
| A7 | `ComponentCell.tsx:297-299` | `formatNumber(undefined \| null) ?? '—'` → 单元格 `—` |
| A8 | `QuotationStep2.tsx:1300-1310` `buildResolvedRow` | `if (key in formulaCache)` 为假时**保留 `row_data` 旧值** → 列小计伪装成正常 |

**数据源本身是好的**：冻结结构 `quote_card_structure` 里每条公式都带 `id`，
与字段 `formulaId` 逐字对得上（实测）。是**前端搬运时丢的**。

**为什么 tsc 没拦住**：A4/A5/A6 三处都写成 `comp.formulas.find(x => (x as any).id === …)`，
`as any` 把「这个属性在本类型里不存在」这件事强行绕过去了。

> 讽刺的是，组件**配置侧**的同名类型 `src/pages/component/types.ts:199-211` 不但有 `id`，
> 还写了警告：「🚨 加载时必须原样保留、保存时必须原样送回 —— 丢了会让所有字段绑定失配、那些列静默不出值。」
> **这条警告说中了**，只是没覆盖到渲染侧这条路径。

### 1.3 根因 B（前置条件 / 安全网失效，建议同修但需存量兼容设计）

`useCardSnapshots.ts:110-135` 的 `computeRowKey` 按 `f.defaultSource`（**camelCase**）解析行键；
但渲染模型里的字段是 `enrichComponentData.ts:286` 写出的 `default_source`（**snake_case**），
调用点 `QuotationStep2.tsx:2081` / `:3130` / `ReadonlyProductCard.tsx:660` 又用 `as any` 抹掉了类型差异
→ 解析恒落空 → **rowKey 退化成行号**，与后端的内容键永久对不上：

```
后端 3120011203/3110520422::AgNi10/Cu触点    前端 3120011203/3110520422::1   ❌
后端 3120011203::0                           前端 3120011203::0              ✅ 偶然撞上
```

这条分歧 `deletedRows.ts:56-59` 早在 2026-07-14 就记载过，当时**绕开**了（删除改用内容指纹 `fp`），根因未修。

**它单独存在无害**（查不到快照就走本地兜底），**但它拆掉了根因 A 的安全网**：
本来快照能命中就看不出 A 的问题，正因为命中不了才落到被 A 打废的本地引擎。

## 6. 沉淀（建议登记进 `docs/反模式.md`）

**「解析主键换代」= 键的两端必须同时迁移，中间每一层白名单搬运都是断点。**

三个可复用的检查动作：

1. 换解析键时，列出该键**两端**（引用方 / 被引用方）的全部承载点与全部搬运层，
   **白名单式 `.map()` 是高危点**，逐个勾掉。本次字段侧 `formula_id` 搬了、公式侧 `id` 没搬。
2. **`as any` 是协议断点的高发地**。凡是写成 `find(x => (x as any).xxx === …)` 的地方，
   都说明类型系统已经不认识这个属性了 —— 必须回头确认它在这条链路上真的存在。
3. **「不回落」的设计（正确）必须配「失败可见」（本次缺失）**，否则静默故障更难排查。

**第四条（元教训）**：同一个错误的两个副本，只修了一个。
`1062c41c` 已经发现并修复了**后端**白名单漏搬 `formulaId`，
提交说明还写了「漏搬 → 求值永久退回按名字/位置猜」——
但没有回头检查**前端同构的白名单**。**发现一处白名单漏搬时，应立即穷举同构的其它搬运层。**
