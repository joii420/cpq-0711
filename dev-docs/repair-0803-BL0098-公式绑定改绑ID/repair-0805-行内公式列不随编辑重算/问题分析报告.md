## 0. 一句话结论

**同一列的「行内值」和「列小计」现在来自两个不同的引擎，而快照那一路永远拿不到用户的编辑。**

- 行内 FORMULA 单元格：**优先读后端快照** `quote_card_values.formulaResults[rowKey]`（`QuotationStep2.tsx:3322-3338`）
- 列小计 / 页签合计 / 产品小计：**一律本地实时重算** `buildCrossTabRows → computeAllFormulas`（`QuotationStep2.tsx:1533 / 1584 / 3637`）

用户在卡片里改了 INPUT 列 → 本地引擎立刻响应（小计变了）；
而后端快照在 `saveDraft` 之后被置 NULL、再由 `ensureCardValues` **用 driver 默认值重建、`editRows` 恒空**
（`CardSnapshotService.java:1298` 硬编码 `editRowsByComp = null`）→ 行内公式列回到「用户没改过」的口径，纹丝不动。

**注意严重性判断的方向**：不是"改了没生效"。用户的改动**已经生效**（落进 `row_data`、进了小计、进了 `li.subtotal` / `total_amount`），
**只有行内明细在骗人**。用户若照行内明细核对，会认为系统没重算。

## 3. 根因

### 3.1 根因 A（渲染层）：同一列的「行内」和「小计」走两个引擎

| 消费点 | 取值来源 | 代码 |
|---|---|---|
| 行内 FORMULA 单元格 | **快照优先**：`formulaResults[rowKey]` 命中即用，不命中才 `computeAllFormulas` 兜底 | `QuotationStep2.tsx:3322-3338` |
| 列小计 / 页签合计 | `columnSumsByComp` ← `buildCrossTabRows.computeRows` → **纯本地** `computeAllFormulas` / `computeTabFormulasTree`，**全程不看快照** | `:1533` `:1512` `:1584` `:3637` |
| 产品小计 | `computeProductSubtotal(precomputedSubtotals)` ← 同一份本地 PASS1+PASS2 | `:1982-1999` |
| 详情页（只读） | 同样"快照优先 + 本地兜底"，小计同样本地算 | `ReadonlyProductCard.tsx:689-702` |

**只要快照与本地引擎的输入不同（哪怕值本身都"没算错"），行内与小计就必然分叉，且完全静默。**

### 3.2 根因 B（数据层）：快照里永远不会有用户的编辑

三段拼起来构成一个闭环：

1. **编辑 → 快照**只有一条通道：`handleSnapshotCellEdit` → `editQuoteCardValue` → 后端 `CardSnapshotService.editCardValue`
   写 `editRows` 并重算 `formulaResults`（`CardSnapshotService.java:2595-2669`）。
2. **`saveDraft` 会把整份快照抹掉**：行子表重建后 `li.quoteCardValues = null`
   （`QuotationService.java:505` / `:2332`，注释「D-1 失效(lazy-cardvalues)」）——**`editRows` 随之一起没了**。
3. **懒重建不认用户编辑**：`ensureCardValues` → `snapshotNewLinesCardValues` → `buildCardValues`，
   而 `buildCardValues` 在 `CardSnapshotService.java:1298` **硬编码** `editRowsByComp = null`
   （注释原文：「Task 3: 填 formulaResults，**加产品时 editRows 恒空**」）——
   它只读 `quotation_line_component_data.snapshot_rows` 里的 driver 行，`row_data` 里的用户输入**一格都不读**。

> 即：**编辑写进快照 → 保存把快照连同编辑一起删掉 → 重建时按"没人编辑过"重算**。
> 这就是 §2.3「全库 `editRows` = 0」的真正原因，也是行内值永远停在 driver 默认口径的原因。

### 3.3 根因 C（触发开关）：repair-0805 阶段二让快照那一路从"空转"变成"生效"

A 和 B 都不是这周才有的。让它们第一次被用户看见的，是本目录的**阶段二 F5/F6**：

- `feb287b8`（2026-06-01，Phase4 Task3）引入"行内 FORMULA 读 `formulaResults`"，
  但前端 `rowKey` 与后端口径不一致 → **全库 1/497 命中** → 这个分支长期空转，
  行内实际一直走 `computeAllFormulas` 本地兜底 → **与小计同源、天然一致，看不出任何问题**。
- `1463ee12`（2026-08-05 08:42，repair-0805 阶段二 F5/F6）把 `rowKey` 归一到后端口径 → **497/497 逐字命中** →
  行内从此真的读快照 → 根因 A 的分叉、根因 B 的陈旧，**同时变成用户可见故障**。
- `e704a17f`（同日 10:19，阶段三）把 `saveDraft` 的 `snapshotRows` 接上完整口径 →
  `row_data` 从此写的是**本地引擎的新值**（本次 `6.087758…` 就是这么来的）→
  两套存储的差异第一次被完整、成对地落库，分叉幅度也随之放大。

**本目录 `需求文档.md` §3.2 其实已经写下了这个交易，只是没把它读完：**

> 「不做 F5/F6 的后果（可接受，但要知情）：快照永远命中不了 → 每次渲染都走本地重算。
> **值是对的（本地引擎与后端同构）**，但失去『真零计算』的性能收益……」

做了 F5/F6，等于把"值的权威"从**本地引擎**换成了**后端快照**。
换权威之前必须先确认新权威是最新的——而它不是：它按设计就不含用户编辑。

1. **触发条件**：在报价单卡片里编辑任意 INPUT 列（组成数量 / 材料占比 / 损耗率 / 加工费…），随后保存或重开。

```sql
-- ① 用户编辑（string 类型 = 手敲）

FROM quotation_line_component_data d JOIN component c ON c.id=d.component_id,
     jsonb_array_elements(d.row_data) r

-- ② 后端快照仍是 driver 默认口径 + editRows 空
SELECT jsonb_pretty(t->'formulaResults'), jsonb_pretty(t->'editRows')
FROM quotation_line_item li, jsonb_array_elements(li.quote_card_values->'tabs') t
WHERE li.id='6caffef0-47f8-447c-8b19-d1165b53270f' AND t->>'tabName'='物料';

-- ③ 分叉清单（同行同列对拍，按数组序 ↔ row_index 对齐）
WITH snap AS (
  SELECT ord-1 AS ri, k AS col, (fr->'values'->>k) AS v
  FROM quotation_line_item li, jsonb_array_elements(li.quote_card_values->'tabs') t,
       jsonb_array_elements(t->'formulaResults') WITH ORDINALITY AS x(fr, ord),
       jsonb_object_keys(fr->'values') k
  WHERE li.id='6caffef0-47f8-447c-8b19-d1165b53270f' AND t->>'tabName'='物料'
), rd AS (
  SELECT (r->>'row_index')::int AS ri, k AS col, (r->>k) AS v
  FROM quotation_line_component_data d JOIN component c ON c.id=d.component_id,
       jsonb_array_elements(d.row_data) r, jsonb_object_keys(r) k
  WHERE d.line_item_id='6caffef0-47f8-447c-8b19-d1165b53270f' AND c.name='物料'
)
SELECT s.col, count(*) FILTER (WHERE round(s.v::numeric,6) IS DISTINCT FROM round(rd.v::numeric,6)) AS diverged, count(*) AS cmp
FROM snap s JOIN rd ON rd.ri=s.ri AND rd.col=s.col GROUP BY s.col ORDER BY 2 DESC;
```

## 8. 沉淀（建议登记为反模式）

**「换权威」必须先证明新权威是最新的。**

`repair-0805` 阶段二做的事，本质是把行内值的权威从"每次渲染都算一遍的本地引擎"换成"后端落库的快照"。
换权威的验收只问了「新旧两个权威在**同一份输入**下是否一致」（AC-7 全库 497/497 对拍），
**没问「新权威会不会过期」**——而它按设计就会：`saveDraft` 抹掉它，重建路径又不认用户编辑。

三条可复用的检查动作：

1. **凡是把某个消费点从"实时算"改成"读缓存/读快照"**，必须回答：这份缓存**什么时候失效、由谁重建、重建时的输入齐不齐**。
   本次三个答案分别是：`saveDraft` 置 NULL / `ensureCardValues` / **不齐（`editRows` 恒 null）**。
2. **同一个数值在页面上有两个消费点（明细格 + 小计行）时，两者必须同源。** 不同源就一定会分叉，
   而且分叉时**小计往往是对的、明细是错的**——这比两边都错更难被发现（本目录 `问题分析报告.md` §4.4 记的是同一族，方向相反）。
3. **"某张表/某个字段全库为 0 条"不能直接读作"没人用"**，先排除"写进去活不过下一步"。
   本次 `editRows` 全库 0 条被读成了"无存量要迁"，实际含义是"这条通道从来没成功过"。
