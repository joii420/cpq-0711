## 0. 一句话

用户在报价卡片里改了 INPUT 列，**只有小计跟着变，行内公式列纹丝不动** ——
因为行内读的是后端快照 `formulaResults`，而**快照的重建路径按设计就不含用户编辑**
（`CardSnapshotService.java:1298` 硬编码 `editRowsByComp = null`，且 `saveDraft` 已把整份快照置 NULL）。

**这不只是显示问题**：该快照同时是**比对视图 / 价格升版写回行金额 / 复制报价单 / 树删除重算**四条链路的数据权威，
它们今天读到的全是「用户没编辑过」的口径。

## 2. 三条路的完整比较

> 三条路都能让**截图上的症状**消失。差别在于**修的是哪一层**、**下游四条链路救不救得回来**、**代价多大**。

### 2.1 甲 · 让快照重建带上用户编辑（补输入，不改引擎）

**做法**：`buildCardValues` 组装 `editRowsByComp` 时，从 `quotation_line_component_data.row_data`
提取该行各组件的**可编辑输入列**值，按**内容行键**对齐生成 `editRows`，喂给既有的
`assembleTabsWithFormulaResults`。引擎侧零改动 —— `FormulaCalculator` 早就实现了
「editRows 按 rowKey 覆盖」（`FormulaCalculator.java:726` 注释 + `:27` 字段值收集口径）。

| | 内容 |
|---|---|
| ✅ **唯一同时修好显示与数据的方案** | 快照是四条下游链路的数据权威，见 §2.4；只有甲能让它们一并恢复正确 |
| ✅ **改动点单一** | `buildCardValues` 是**全部**重建路径的唯一入口（`ensureCardValues` / `QuotationTreeService` / `MaterialVersionUpgradeService` / 加产品）——正是 §1-B 那个闭环的收口处，改一处全线受益 |
| ✅ **让既有设计第一次成立** | `editRows` 通道、task-0729 S4a「清销售手改的价格覆盖」、Phase4 Task3「真零计算」三者都建立在"快照含编辑"这个前提上；甲是把缺的前提补上，不是再加一层绕过 |
| ✅ **引擎零改动** | 覆盖语义（rowKey 对齐、AP-54）已实现且被后端测试覆盖，本次只补输入 |
| ⚠️ **风险 1 · 行对齐** | `row_data` 只有 `row_index`，**不能**用下标对齐（墓碑删除 / 手动行 / 树剪枝 / 过滤子集都会错位 —— AP-54 + repair-0727 整族教训）。必须用后端 `computeRowKey`/`resolveRowByFieldName` 算内容键 |
| ⚠️ **风险 2 · 回种范围** | 只回种 `INPUT`/`INPUT_TEXT`/`INPUT_NUMBER` 且 `editable` 的字段。**FORMULA/BASIC_DATA/DATA_SOURCE 一律不回种**，否则后端不再算 = 架构反转成前端权威 |
| ⚠️ **风险 3 · 价格锁** | task-0729 归位写的 `__priceLocked` 列/行必须跳过，否则升版归位的新价被旧编辑值顶回去 —— 那正是 S4a（`MaterialVersionUpgradeService.java:256-259`）想清掉的东西 |
| ⚠️ **风险 4 · 烘焙默认值** | 前端 bake 会把 `default_source` 解析值写进 `row_data`，回种后它们等价于"用户编辑"→「刷新基础数据」将不再覆盖 INPUT 列。**这与 `2026-08-03 row-data-snapshot-authority` 的 D2 裁决（"刷新一律不动 INPUT 列"）同向**，属可接受、但必须写进验收 |
| 📏 **规模** | M（3-5 天，含 A/B 值中性验证） |

### 2.2 乙 · 行内去掉「快照优先」，统一走本地引擎

**做法**：`QuotationStep2` / `ReadonlyProductCard` 两处把 `snapFormula` 从"优先"降为"兜底"（或按状态分流：DRAFT 走本地、非 DRAFT 走快照）。

| | 内容 |
|---|---|
| ✅ **改动最小** | 前端 2 处，当天可交付 |
| ✅ **性能代价 ≈ 0（实测推翻了直觉）** | 「真零计算」是幻觉：`buildCrossTabRows` 就写在 `ProductCard` 渲染体里（`:2855`，**不在 useMemo 内**），每次渲染都对**所有组件所有行**跑一遍 `computeAllFormulas` 来算 `columnSumsByComp`/`crossTabRows`。快照只省了单元格那一次取值，**不省任何计算** |
| ✅ **回到已被长期验证的行为** | 8-05 之前行内本来就走本地引擎（快照命中率 1/497），且落库的 `li.subtotal` 也一直是本地引擎口径 → 行内、小计、落库金额三者同源 |
| ❌ **只治显示、不治数据（致命）** | 比对视图 / 价格升版 / 复制单 / 树删除重算读的仍是缺编辑的快照。用户在 UI 上看对了，**升版一跑金额被改回"没编辑过"的值**（`MaterialVersionUpgradeService:274-276` 直接写 `li.subtotal` + `recompute`）→ 故障从"可见的显示不一致"退化成"不可见的金额被改" |
| ❌ **动摇冻结语义** | 非 DRAFT 单据本应逐字节读冻结快照；无脑改本地重算会让已提交单据随配置/基础数据漂移。要保语义就得按状态分流，复杂度回升 |
| 📏 **规模** | S（1-2 天） |

### 2.3 丙 · `row_data` 定为唯一权威，快照降级为纯缓存

**做法**：沿 `docs/superpowers/specs/2026-08-03-row-data-snapshot-authority-design.md` 的方向，
把"行数据即快照"推到底：快照由 `row_data` 派生，`saveDraft` 后同步失效并按 `row_data` 重算。

| | 内容 |
|---|---|
| ✅ **唯一能根除"三处口径"的方案** | 行内 / 小计 / 落库 / 比对 / 升版全部同源 |
| ❌ **等于宣布前端引擎是唯一真值源** | 与后端 `FormulaCalculator`、核价侧渲染、Excel、比对视图的既有架构直接冲突；核价侧根本没有前端 `row_data` 这一层 |
| ❌ **触碰三大核心模块基线** | 需走 `cpq-architect` 评估 + 独立立项，周期以周计 |
| ❌ **救不了眼前的火** | 本期故障是 P0，等不到丙落地 |
| 📏 **规模** | L（1 周以上，实为独立项目） |

### 2.4 决定性事实：快照不是"渲染缓存"，是四条链路的数据权威

这一条把天平从乙压向甲：

| 消费方 | 读什么 | 现状后果 |
|---|---|---|
| **比对视图（live 侧）** `ComparisonViewService:286,292` | `ensureCardValues` 后读 `quoteCardValues` 的 `subtotal`/`subtotalByColumn` | 报价侧对比数字 = 630.21（应为 6.45），比对结论直接错 |
| **价格升版（task-0729）** `MaterialVersionUpgradeService:263-276` | `buildCardValues` 重算 → **写回 `li.subtotal` + `LineDiscountService.recompute`** | 升版会把用户编辑**静默抹掉并改写行金额** —— 数据损坏，非显示问题 |
| **复制报价单** `QuotationService:1548` | 直接复制 `quoteCardValues` | 复制出的新单继承缺编辑的口径 |
| **树删除重算** `QuotationTreeService` | 从 `snapshot_rows` 重建 `quoteCardValues` | 删一个 BOM 节点 = 顺手把该行所有编辑回退 |

> 另有一处反证 B 的存在性：task-0729 的 **S4a**（`:256-259`）专门写了「清 `quote_card_values.editRows` 里
> 销售手改过的陈旧价格覆盖值」——**它假定 `editRows` 里有东西**。而实测全库 `editRows = 0`，
> 这段清理**恒为 no-op**。既有功能已经在依赖一条从未通电的线路。

## 3. 结论：推荐 **甲**（并把乙的一半作为可观测性保险一起做）

### 3.1 选甲的四条理由

1. **只有甲能同时修好显示和数据。** 乙修完，UI 对了，比对视图仍错、升版仍会改写金额 —— 把"用户看得见的不一致"换成"用户看不见的数据损坏"，是更坏的交易。
2. **甲的改动点比乙更收敛。** 乙要改前端 2 处渲染分支 + 处理冻结语义分流；甲只改后端一个函数的入参组装，而那个函数是四条重建链路的唯一入口。
3. **甲补的是既有设计缺的那块，不是新增一层。** `editRows` 覆盖语义、rowKey 对齐、S4a 清理逻辑都已存在且已被测试覆盖 —— 本次只是让它们第一次有输入。
4. **乙唯一的卖点（性能）经实测不成立。** `buildCrossTabRows` 在渲染体内无条件全量跑，本地引擎每次渲染都已经算完了所有行；"快照优先"省的只是一次 Map 取值。**所以乙既不省钱，也不解决数据问题。**

### 3.2 同时要做的保险（属甲的范围，不是替代方案）

| # | 内容 | 理由 |
|---|---|---|
| **S1** | 行内单元格保留"快照缺该 rowKey / 该列时本地兜底"（现状已有，**不得删**） | 新行 / LIST_FORMULA / 快照未及重算时不至于空白 |
| **S2** | **同一格快照值与本地值不一致时给出可见标记**（⚠ + tooltip 显示两个值），复用 `out.errors` 旁路 | 今天这类分叉 100% 静默；呼应兄弟任务 §7.3 与 repair-0803 B1「让错误可见」。**没有它，下一次同族故障还是只能靠用户截图发现** |

### 3.3 否决说明

- **乙**：否决作为"主方案"，但其 S1/S2 两条保险纳入甲。若用户认为 P0 需要**当天止血**，可先发乙的前端改动作为**临时缓解**（把行内拉回与小计同源），再按甲修数据层 —— 需明确这是两步走，不是二选一。
- **丙**：否决在本期做，转 [[BL-0128]]（P2）。它是正确的长期方向，但需 `cpq-architect` 评估 + 独立立项，且救不了眼前的 P0。
