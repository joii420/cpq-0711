## 2. 需求背景与目标 ⭐

### 2.1 现象与根因（已定位并实证）

**现象**：报价数据导入后，「组装加工费」的工序落库到了错误语义的字段 —— 工序编号列里存的是**工序名称**。

**实测证据**（库 `cpq_db_0724`，2026-07-27 复核仍然成立）：

```
SELECT process_no, process_name, count(*) FROM capacity
 WHERE resource_group_no='QUOTE_ASSEMBLY' GROUP BY 1,2;
 process_no | process_name | count
------------+--------------+-------
 铆接       | (null)       |    10
 焊接       | (null)       |    10
```

**根因**：Excel「组装加工费」sheet 的模板列只有「组装工序」一列（列头 = `销售料号 | 项次 | 组装工序 | 组装加工费 | 货币 | 计价单位 | 拒收率/不良率（%）`），业务在该列填的是**工序名称**（`焊接`/`铆接`），而 `Q14AssemblyProcessFeeHandler.java:53` 直接 `row.getStr("组装工序", "工序编号")` **原样写入** `capacity.process_no`，既不做编号解析，也从不写 `capacity.process_name`（该列不在 handler 的 `CONTENT` 白名单里，恒为 NULL）。

文档 `docs/table/报价系统Excel导入落库方案.md` §14 写的是「组装工序 → `process_no` ✅ 工序编号（**取工序编号对应值**）」——**文档要求解析、代码从未实现**。

**同族第二处**：`Q15AssemblyAnnualDiscountHandler.java:51` 的 `row.getStr("组装工序")` → `unit_price.operation_no`，**同一偏差**（该 sheet 当前测试数据为空，库内尚无脏数据）。

**旁证**：`unit_price` 表里其余所有 `price_type` 的 `operation_no` **全部是真 Z 码**（`Z002` / `Z008` / `Z053` / `Z380` / `Z381` / `Z490` / `Z611`），只有 Q15 这条路径会写中文名称，确属异类。

**当前 UI 显示正常属于两个偏差互相抵消**：组装页签视图 `zz_view` 取值为 `COALESCE(NULLIF(c.process_name,''), c.process_no)` —— `process_name` 恒 NULL 于是兜底到 `process_no`，而 `process_no` 里存的正好是名称，所以页面显示「焊接」看着是对的。**一旦有人按规范在该列填真编号，组装页签立刻变成显示编号而非工序名。**

### 2.2 排除项（已核实，本次不涉及）

| 核价侧 P08（capacity） | `row.getStr("工序编号")` → `process_no`，实测值 `Z008`/`Z053`/`Z490`，**语义正确**，且已有 fail-fast 必填校验 | **不动** |

### 2.3 本次要达成的目标

1. 「组装加工费」「组装加工费年降」两处的工序，落库到 `process_no` / `operation_no` 的必须是**真工序编号**，来源为「主数据维护 → 工序」（`process_master`）。
2. Excel 填名称时，由系统按名称到 `process_master` 反查编号后落库；**反查不到即 Phase 1 拦截、整单导入失败**，不允许把名称写进编号列。

4. 纠正 `docs/table/报价系统Excel导入落库方案.md` §14 / §15 的落库规则描述。

## 4. 功能详述 ⭐

### 4.0 前提：报价导入是两阶段架构（第四轮核查确立，本需求全部规则以此为准）

`QuoteImportService.importQuote()` 自 task-0709 update-0723（B7/B8）起为**两阶段**：

| 阶段 | 实现 | 行为 |
|---|---|---|
| **Phase 1** | `QuoteImportValidator.validate()` | 全量只读校验，**零写库**。任一 sheet `failedRows > 0` → 整单 `FAILED`，**直接返回、不进 Phase 2、一行都不写** |
| **Phase 2** | `QuoteImportService.writeAll()` | 单一事务（`REQUIRES_NEW`），全部 handler `MANDATORY` join。任一 handler `recordError` → 抛 `QuoteImportWriteFailedException` → **整单回滚** |

代码依据：`QuoteImportService.java:123-133`（Phase 1 拦截）、`:233-239`（Phase 2 兜底回滚）、`:186-188`（架构注释）。

> ⚠️ **推论（本需求的基石）**：在此架构下 **`recordError` ≡ 整单导入失败**，不存在「跳过坏行、其余照常落库」这回事。前三轮定稿的 §4.3 规则三与 AC-5 基于错误前提，第四轮已推翻并重写，见 §13.1。

Phase 2 handler 的注释也印证了这一点：`QuoteImportService.java:234` —— 「Phase 1 理论上已全量拦截；仍出现说明是竞态/DB 层意外」。**所以业务校验的正确落点是 Phase 1，不是 handler。**

### 4.1 用户场景 / 操作流程

**前置（本次改动引入的新前置条件，必须先做）**：
主数据维护 → 工序 → 导入工序（或手工新增），把工序表录入 `process_master`，至少覆盖报价 Excel 里用到的工序（当前测试数据为 `焊接`、`铆接`）。

**主流程**：
1. 报价单管理 → 从基础数据导入 → 选客户 → 上传报价 Excel。
2. **Phase 1** 逐行解析「组装工序」列：填 `焊接` → 反查 `process_master` 得到编号（如 `Z100`）。
3. **Phase 2** 落库：`capacity.process_no = 'Z100'`、`capacity.process_name = '焊接'`。
4. 若该列填的已经是编号 `Z100` → 两段匹配第一段即命中，同样落 `Z100` + 主数据里的规范名。
5. 若填的工序在主数据里查不到 → **Phase 1 拦截，整份 Excel 导入失败**，导入报告按料号列出全部缺失工序，数据库零变动。
6. 报价单渲染 → 组装页签「工序」列显示 `焊接`（经 `zz_view` 取 `process_master.process_name`）。

### 4.2 界面与交互（前端相关）

**本次前端零改动。** 导入失败明细走现有导入报告的 `failedRows` 渲染通道（`QuoteBasicDataImportV6Drawer.tsx` 已具备展开显示 `errors` 的能力，展开条件 `failedRows > 0` 恰好命中本次的失败场景），无新增 UI、无新增字段。

### 4.3 业务规则与计算逻辑（后端相关）

#### 规则一：新增 `ProcessNoResolver`（工序解析器）

定位类比现有 `MaterialNoResolver`（同包 `basicdata/v6/service/`）：把 Excel「组装工序」列的原始值解析为 `(process_no, process_name)` 二元组，解析不了则返回可记录的失败原因。

**批内缓存**：一次导入把 `process_master` 全量载入内存（小表），构建 `no → row`、`name → List<row>` 两个 map，放入 `ImportContext.sharedCache`（与既有 `partTypeIndex` / `selfProcessOperationNo` / `materialNoBatchState` 同一模式），避免逐行查库。

**解析顺序（两段匹配）**：

| # | 规则 | 结果 |
|---|---|---|
| 1 | 原始值 trim 后按 **`process_no` 精确匹配** | 命中 → 直接采用该行的 `(process_no, process_name)` |
| 2 | 再按 **`process_name` 精确匹配（trim）** | 唯一命中 → 采用该行的 `(process_no, process_name)` |
| 3 | 按名称命中**多条** | **按 `process_no` 升序取第一条** + `Log.warn` 记录被选中的编号与全部候选（第四轮 N3 改定） |
| 4 | 两段都不命中 | **Phase 1 拦截**：「工序『焊接』未在工序主数据中登记，请先在 主数据维护 → 工序 中录入或导入」 |

> 📌 **为什么要两段匹配**：列名「组装工序」语义模糊，业务既可能填名称也可能改填编号；先按编号匹配的成本为零，却让两种填法都能正确落库，且业务从填名称迁移到填编号时无需改代码。
>
> 📌 **同名多条为什么取第一条而不是拒绝**：需求方裁决（第四轮 N3）。业务真实工序表可能存在重名，拒绝会造成成片导入失败。代价是可能静默绑错工序，故必须 `Log.warn` 留痕；排序键固定为 `process_no` 升序以保证**结果可复现**（不依赖数据库返回顺序）。

#### 规则二：Phase 1 / Phase 2 职责划分（第四轮 N4 确立）

| 阶段 | 做什么 |
|---|---|
| **Phase 1**（`QuoteImportValidator`） | ① 载入 `process_master` 索引；② 逐行解析「组装加工费」「组装加工费年降」的「组装工序」列；③ 解析失败 → `recordError`（**按料号聚合**，见规则三）；④ 解析成功 → 结果收进 `Outcome.assemblyProcessNo`，供 Phase 2 消费 |
| **Phase 2**（Q14 / Q15 handler） | 直接从 `ctx.sharedCache` 取 Phase 1 已解析好的 `(process_no, process_name)` 落库，**不再重复解析、不再重复查库** |

**照抄的现成范式**：`QuoteImportValidator.validateSelfProcessFee()`（`:130-150`）已经是「Phase 1 校验 + 把 `selfProcessOperationNo` 收进 `Outcome` → `QuoteImportService:135` 放 `sharedCache` → `MaterialBomMergeHandler:86` 消费」的完整链路，本次逐字照搬其结构。

> 📌 `QuoteImportValidator.java:78` 的注释明确记载「其余 sheet（成品其他费用/**组装加工费**/电镀方案/电镀费用/年降类…）：仅做基础检查」—— 即组装加工费目前在 Phase 1 **没有专项校验**，本次要新增。

#### 规则三：错误粒度 —— 按料号聚合（第四轮 N1）

Phase 1 发现某销售料号下有任一道工序解析失败时：

- **该料号的全部组装工序行一并计入失败**，`recordError` 的消息按料号聚合上报（形如「销售料号 `10110002` 的组装工序 `点胶` 未在工序主数据中登记」），而不是逐行散报。
- **不变量**：绝不允许出现「该料号在 `capacity` 里的工序数量静默变少」的结果。

> 📌 **为什么粒度是料号**：`Q14` 是**料号级整组升版**（`groupKey = (material_no, resource_group_no=QUOTE_ASSEMBLY)`，同料号多道工序汇总成一组，`writeVersionedGroup` 整组替换）。若允许「坏行跳过、好行照常整组写入」，该料号的新版本会比老版本少一道工序，且老版本 `is_current` 被切走 → **工序凭空消失**，属 `docs/反模式.md` AP-60「页签投影当整组权威致抹数据」同族。
>
> 在 Phase 1 拦截（整单失败、零写库）的前提下，这个不变量天然成立；按料号聚合报错是为了让业务**一眼看到是哪个料号出问题**，而非在几十条散错里翻找。

#### 规则四：落库映射（改动后）

| Handler | 目标字段 | 值 | 备注 |
|---|---|---|---|
| Q14 组装加工费 | `capacity.process_no` | 解析出的**真工序编号** | 原为 Excel 原文 |
| Q14 组装加工费 | `capacity.process_name` | **`process_master` 的规范名称** | 原恒 NULL；取主数据规范名而非 Excel 原文，保证名称口径单一权威 |
| Q15 组装加工费年降 | `unit_price.operation_no` | 解析出的**真工序编号** | 原为 Excel 原文 |
| Q15 组装加工费年降 | — | **不写名称** | `unit_price` 无工序名称列，且 `COMPONENT_REDUCTION` 当前无任何 SQL 视图消费（实测查询为空），不为此加列 |

#### 规则五：版本化列的归属

`capacity` 的 `CONTENT` 列表新增 `process_name`，但**不加入 `VERSION_TRIGGER`**：

- `VERSION_TRIGGER` 保持 `("process_no", "seq_no")` —— 工序编号或项次变化才升版。
- `process_name` 属内容列，名称变化走**原地更新**（同版本号覆盖），不产生新版本。理由：工序改名是主数据侧的展示性变更，不构成产能口径变化。

> ⚠️ **Q14 一次性升版是预期行为，不是 bug**：改动上线后首次重导，`process_no` 从 `焊接` 变为 `Z100`，命中 `VERSION_TRIGGER` → `capacity` 会升一个版本，老版本 `is_current` 正常切走。这是语义纠偏的必然结果。

#### 规则六：⚠️ Q15 的 `operation_no` 在 groupKey 里 —— 双 current 时序约束（第四轮新发现）

**Q15 与 Q14 的版本化语义不同，必须分别对待**：

| | Q14 `capacity` | Q15 `unit_price` |
|---|---|---|
| `groupKey` | `(material_no, resource_group_no)` | `(system_type, customer_no, price_type, cost_type, code, finished_material_no, **operation_no**)` |
| 工序列的位置 | `process_no` ∈ `CONTENT` + `VERSION_TRIGGER` | `operation_no` ∈ **groupKey** |
| 改了取值的后果 | 同组升版，**老版本 `is_current` 正常切走** ✅ | **被当成全新组**，建 `version_no=1` 新行，**老组 `is_current` 不会被切走** → **双 current 静默残留** ❌ |

代码依据：`Q15AssemblyAnnualDiscountHandler.java:52`（`key = (code, finishedMaterialNo, operationNo)`）、`:61`（`g.put("operation_no", operationNo)`）。属历史踩过的「V6 导入器双 current（静默）」同型坑。

**当前状态与时序约束**：

- 实测 `unit_price` 中 `price_type='COMPONENT_REDUCTION'` **为 0 行** —— 库里没有任何老组，**此刻改动是零迁移成本的最佳窗口**。
- **约束**：本改动必须在 `COMPONENT_REDUCTION` 产生数据**之前**上线。若在上线前业务已导入过一次组装加工费年降（`operation_no` 为中文名），则上线后重导会产生双 current，**必须先清理老组**（`UPDATE unit_price SET is_current=false WHERE price_type='COMPONENT_REDUCTION' AND operation_no !~ '^[A-Z]'`）。
- 验收时须实测确认（见 AC-6b）。

#### 规则七：渲染视图对齐

`zz_view`（组装页签）改为：

```sql
LEFT JOIN process_master pm ON pm.process_no = c.process_no
...
COALESCE(pm.process_name, c.process_name, c.process_no) AS _工序
```

与自制加工费 `jg_view` 的既有口径统一（`COALESCE(pm.process_name, up.operation_no)`）：**主数据优先 → 库内冗余名次之 → 编号兜底**。

> 📌 **主数据优先不破坏报价单冻结语义**：`zz_view` 只服务编辑期取数；报价单提交后的值由 `snapshot_rows` 物化冻结，不再走视图。故工序在主数据里改名不会篡改已提交报价单。

## 13.7 第五轮（2026-07-27 验收阶段）：pending 架构揭示的三处验收标准失效

> 与 §13.1~13.6 同源问题：**需求文档基于对既有架构的不完整理解，写下了不可达成或无证伪能力的验收判据**。这三处都不是交付缺陷，是标准本身写错。

**根因（task-0721 B2 pending 架构，已合并、与本次改动无关）**：
`QuoteImportService.java:97` 无条件 `ctx.pendingQuotationId = recordId`，故报价 V6 导入写入 `capacity` / `unit_price` 等 7 张版本化表时**恒为 `is_current=false` + 带 `pending_quotation_id`**。数据只有经 `POST /quote/create-quotation` 才把 pending 过户为 quotationId（仍不改 `is_current`）；真正让用户看到数据的是运行时 `QuotePendingRewriter` 动态改写 `WHERE`，把"本单 pending 行"与"全局 `is_current=true` 行"按 `:pq` UNION。**脱离具体 quotationId 上下文直接 `SELECT ... WHERE is_current`，永远看不到任何新导入的数据。**

| # | 失效的判据 | 实证反驳 | 处置 |
|---|---|---|---|
| 1 | **AC-8 断言②**「再导一次版本号不再增长」 | 改动**前** `process_no` 恒为「焊接」从未变化，却产生 2000~2008 共 **9 个版本**（7/27 01:06~06:19）；改动后 2010~2026 同样每导一次升一版。**升版与 `VERSION_TRIGGER` 无关，是每次导入产生新 pending 组所致** | 判据废止，AC-8 只保留断言① |
| 2 | **AC-6b** 双 current 断言 | 筛选条件 `AND is_current` 的结果集恒为空 → `HAVING count(*)>1` 必返 0 行，**无论代码对错都通过** | 标注为"真空通过"；Q15 双 current 的真实防线是 §4.3 规则六的**上线时序约束** |
| 3 | **AC-7** 组装页签 UI 验证 | `zz_view` 所属「组装加工费」组件实测绑定 **0 个模板**（`jg_view` 绑 2 个已发布），UI 上不存在该页签 | 退化为 SQL 层三级 `COALESCE` 验证（三场景已实证）；UI 缺口如实登记 |

**唯一 `is_current=true` 的例外**：`capacity` 中 `calc_version=2009`（7/27 06:22 创建、无 pending）的 2 行老脏数据（`process_no='焊接'`、`process_name` NULL）。它是改动前经完整建单流程转正的产物，也解释了为何改动后 `zz_view` 在**脱离报价单上下文**查询时仍会看到旧值 —— 这不是本次改动失效，而是新数据尚未走建单流程转正。

**衍生待办**：版本号一天内从 2000 涨到 2026（27 个版本、56 行），说明 pending 架构下重复导入会**无界累积版本行**。已登记 BACKLOG 另行评估。
