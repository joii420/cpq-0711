# 执行条件与取价窗口统一方案

## 1. 先解决“重复”的根因

截图中的两个下拉框实际上表达的是两件不同的事：

| 配置位置 | 真正问题 | 应该回答的问题 |
|---|---|---|
| 执行条件 | 判断这条策略什么时候生效 | “报价单基准日属于什么日历范围时，命中这条规则？” |
| 取值窗口 | 生成要查询哪些历史价格日期 | “命中规则后，去哪些日期找元素价格并聚合？” |

它们可以共用同一套日历语义，但不能共用同一组面向用户的选项文案，更不能各自维护一套枚举。

例如：

- 执行条件使用 **“月内日号介于 1～10 日”**；
- 取价日期使用 **“周期采样 → 月周期 → 每月第 15 日”**。

两者都涉及“月”，但一个是布尔判断，一个是日期集合生成，不再出现两个“每月几号”的并列下拉选项。

## 2. 统一模型：一个规则，两个时间表达式

每条默认规则或元素例外都使用同一个结构：

```json
{
  "scope": {"type": "CUSTOMER_DEFAULT"},
  "priority": 10,
  "match": {
    "all": [
      {"field": "dayOfMonth", "op": "BETWEEN", "value": [1, 10]}
    ]
  },
  "price": {
    "sourceId": "...",
    "dateSelector": {
      "type": "PERIOD_POINT",
      "period": "WEEK",
      "count": 3,
      "anchor": {"type": "WEEKDAY", "value": 2},
      "includeCurrentPeriod": false,
      "shortPeriod": "SKIP",
      "emptyResult": "MISSING"
    },
    "aggregation": "AVG",
    "factor": "1.000000",
    "premium": "0.000000"
  }
}
```

- `match` 只负责“是否命中”。
- `price.dateSelector` 只负责“生成价格日期集合”。
- `price.aggregation` 只负责“对日期集合中的价格做什么聚合”。
- 默认规则和元素例外只通过 `scope` 区分，例外仍然是完整规则行，不做字段级继承。

后端只保留一份 `CalendarExpression` 校验器和解析器；报价单创建、元素增量取价、策略试算共用它。

## 3. 执行条件：只保留“日期谓词”

执行条件不再出现“每月 X 号”“每周 X”这种像取价动作的描述，只提供对报价单基准日的判断。

### 3.1 顶层选项

| 选项 | 含义 |
|---|---|
| 无条件 | 所有日期命中，作为兜底规则 |
| 日历匹配 | 按星期、月内日号、月份或年内月日判断 |
| 指定日期 | 只在某一天或日期区间命中 |
| 组合条件 | 使用 ALL / ANY / NOT 组合多个日期谓词 |

### 3.2 日历匹配字段

| 字段名称 | 示例 | 覆盖场景 |
|---|---|---|
| 星期 | 星期属于 `[1,2,3]` | 今天是周 X；每周 X～Y |
| 月内日号 | 日号介于 `[X,Y]` | 每月 X 日～Y 日执行策略 |
| 月份 | 月份属于 `[1,3,6]` | 某几个月使用不同策略 |
| 年内月日 | 月日属于 `[03-01,03-15]` | 每年某段日期执行策略 |
| 指定日期区间 | `2026-10-01`～`2026-10-15` | 一次性活动或临时策略 |

运算符统一为：`属于`、`介于`、`不属于`。多个条件通过 `ALL/ANY/NOT` 组合。

### 3.3 三个需求示例

```text
今天是周 X 执行 A
→ match: weekday IN [X]

每月 X 日～Y 日执行 A，其余 B
→ A: dayOfMonth BETWEEN [X,Y]
→ B: 无条件兜底

每周 X～Y 执行 A，每周 M 执行 B，其余 C
→ A: weekday BETWEEN [X,Y], priority=10
→ B: weekday IN [M], priority=20
→ C: 无条件兜底, priority=99
```

如果条件重叠，保存前给出重叠提示；最终仍由优先级决定命中顺序。没有兜底规则时阻止启用策略。

### 3.4 严格选择器与字段语义

执行条件的值不允许自由输入，必须由字段类型驱动选择器；`介于`显示前后两个值，`属于/不属于`使用去重多选。至少选择一项，数组内按 OR 匹配。

| 字段 | `介于` | `属于/不属于` | 语义与校验 |
|---|---|---|---|
| 月内日号 | 两个 1～31 日选择器 | 1～31 的多选器 | 只判断每月的日号，不涉及月份和年份 |
| 月份 | 两个 1～12 月选择器 | 月份多选器 | 只判断月份 |
| 星期 | 两个周一～周日选择器 | 星期多选器 | 按 ISO 周一至周日判断 |
| 年内月日 | 两组“月份 + 日号”选择器 | 多组“月份 + 日号”选择器 | 不带年份，每年重复匹配；日号受月份天数约束，闰日单独提示 |
| 日期区间 | 两个带年份的日期选择器 | 日期多选器 | 一次性绝对日期，适合活动或临时策略；连续范围应使用“介于” |

“日期区间”和“年内月日”不是重复配置：前者包含年份，例如 `2026-10-01～2026-10-15`，只影响指定年份；后者不包含年份，例如 `03-01～03-15`，每年都会匹配。系统校验所有范围的结束值不得早于开始值，并阻止非法日期保存。

## 4. 取价日期：统一为五种日期生成器

取值窗口的下拉框只选择“日期生成方式”，不再混合聚合方式。AVG/MAX/MIN/LATEST 单独放在“聚合方式”字段。

### 4.1 最新一条 `LATEST`

```text
查询边界 = [baseDate-maxLookbackDays, baseDate]
结果     = 直接查找边界内 MAX(price_date <= baseDate) 的一条有效价格
```

对应现有“最新一条”，但必须配置最大回溯天数，避免把“基准日之前所有日期”解释成无界候选集。价格修订明细只保存实际命中来源日和价格行，不枚举每一个日历日。

### 4.2 相对区间 `RANGE`

统一配置：`范围口径 + 数量 + 单位 + 是否包含基准日`。

| 范围口径 | 示例 | 日期含义 |
|---|---|---|
| 前 | 前 7 天 | `[base-7, base-1]`，不含基准日 |
| 近 | 近 7 天 | `[base-6, base]`，包含基准日 |
| 滚动 | 滚动 3 个月 | 从基准日向前推 3 个自然月形成闭区间 |
| 前完整周期 | 前 3 个完整周 | 不含当前周，只取已经结束的 3 个周 |

因此“前 X 天”和“近 X 天”不再是两个容易混淆的特殊枚举，而是同一个范围生成器的两个口径。

### 4.2.1 相对锚点区间 `RELATIVE_ANCHORED_RANGE`

用于表达“上月 15 日～本月 15 日”“上周三～本周三”“去年 3 月 8 日～今年 3 月 8 日”等跨自然周期区间。开始和结束各由“相对周期 + 周期内位置”组成：

| 区间类型 | 开始锚点 | 结束锚点 |
|---|---|---|
| 跨自然周 | 上一个/上上个/当前自然周 + 周一～周日 | 上一个/当前自然周 + 周一～周日 |
| 跨自然月 | 上一个/上上个/当前自然月 + 1～31 日 | 上一个/当前自然月 + 1～31 日 |
| 跨自然年 | 上一个/上上个/当前自然年 + 月日 | 上一个/当前自然年 + 月日 |

```json
{
  "type": "RELATIVE_ANCHORED_RANGE",
  "start": {"period": "MONTH", "offset": -1, "dayOfMonth": 15},
  "end": {"period": "MONTH", "offset": 0, "dayOfMonth": 15},
  "inclusive": true,
  "futureDatePolicy": "CAP_AT_BASE_DATE"
}
```

相对周期始终基于报价单 `priceBaseDate` 计算，不使用浏览器或服务器当前日期。ISO 周以周一为第一天。如果结束锚点晚于基准日，必须按 `futureDatePolicy` 截止到基准日、阻止取价或等待后续执行，不能静默查询未来价格。

起止锚点还必须各自配置 `shortPeriodPolicy=REJECT/CLAMP_TO_PERIOD_END`。例如“上月 31 日”落在 2 月时，选择拒绝则当次规则无法执行，选择调整到周期末则取 2 月最后一日。自然语言没有明确这一点时，AI 必须返回 `NEEDS_CONFIRMATION`。

### 4.2.2 日期排除规则 `EXCLUSIONS`

自然语言可以在取价范围后继续表达周期性排除，例如：

```text
取上月15号到本月15号的价格平均值，排除每周六、周日和每月6号
```

解析结构：

```json
{
  "dateSelector": {
    "type": "RELATIVE_ANCHORED_RANGE",
    "start": {"period": "MONTH", "offset": -1, "dayOfMonth": 15},
    "end": {"period": "MONTH", "offset": 0, "dayOfMonth": 15},
    "inclusive": true
  },
  "exclusions": {
    "weekdays": [6, 7],
    "daysOfMonth": [6]
  },
  "aggregation": "AVG"
}
```

第一期支持两类周期性排除：`weekdays` 使用 ISO 周一=1～周日=7；`daysOfMonth` 只能选择 1～31。同一数组内以及两类排除之间均按 `ANY/OR` 处理，日期命中任意一项即剔除；“每月 6 日并且恰逢周六才排除”这种交集条件不在第一期范围。计算顺序固定为：生成日期范围 → 按基准日截断 → 执行日期排除 → 对剩余日期识别节假日/无报价 → 应用无报价策略 → 聚合。

被排除日期即使存在价格也不参与取价；不得作为 `CARRY_FORWARD` 或 `LATEST_IN_WINDOW` 的替代价格来源。日期同时命中“排除”和“节假日”时，排除优先。若起止锚点被排除，锚点仍用于定义范围，但该日期不进入价格样本，日历需要显示“排”；所有候选日期均被排除时返回 `MISSING` 并阻止自动取价。

### 4.3 周期采样 `PERIOD_POINT`

统一配置：`周期 + 采样点 + 取几个周期 + 是否包含当前周期`。

| 周期 | 采样点 | 示例 |
|---|---|---|
| 周 | 周内第几天 | 前 3 周的周二；近 4 周每周周五 |
| 月 | 月内第几日 | 最近一个月的第 15 日；近 6 个月每月第 15 日 |
| 年 | 年内月日 | 最近 2 年每年 3 月 8 日 |

固定规则：

- ISO 周一=1，周日=7；
- 当前周期是否参与由 `includeCurrentPeriod` 控制；
- 月份没有指定日号时不自动取月末；
- 月内没有该日号时按 `shortPeriod=SKIP` 跳过，不把 31 日改成 28/29/30 日；
- 未命中价格不向更早日期无限补取，最终返回 `MISSING`。

### 4.4 固定日期 `FIXED`

```text
指定日期：2026-10-15
指定日期区间：2026-10-01 ～ 2026-10-15
```

适合临时锁价、活动价或一次性客户协议。日期区间可与 AVG/MAX/MIN 组合。

### 4.5 节假日与无报价日处理

节假日不触发策略切换。报价单仍按当前基准日命中的规则版本执行，节假日只影响该规则生成的价格日期如何解析。有效日期但没有价格时，也使用同一套“无报价日”策略；已有价格的节假日仍作为直接取价日，不执行替代取价。

#### 日历来源

默认继承价格源交易日历，也可以明确选择中国法定节假日或客户自定义工作日历。策略保存日历选择方式和日历 ID，执行时选择一个已发布且完整覆盖“目标日期集 + 最大回溯区间”的日历版本；覆盖不足时必须阻止执行，不得把未配置日期默认为开市日。实际选中的日历版本和 digest 需要写入价格修订明细，避免日后日历调整导致历史报价无法解释。规则若显式固定某一日历版本，则只允许使用该版本，覆盖不足直接失败。

#### 日历维护闭环

交易日历不是写死在日期执行器中的节假日数组。本任务新增“定价管理 → 交易日历”：维护 MARKET/COUNTRY/CUSTOMER 主档、IANA 时区、不可变版本、覆盖区间以及每天的 OPEN/CLOSED 和原因；支持从上一版本生成草稿、Excel 导入导出、完整性检查、发布和版本 diff。发布时必须物化覆盖区间内每一天，未配置日期不能默认开市。

价格源管理增加默认日历绑定。运行时严格按“策略固定版本 → 策略固定日历的最新完整发布版 → 价格源默认日历的最新完整发布版”解析，任一路径失败都返回 `CALENDAR_NOT_AVAILABLE`，不隐式回退到周末推断或某个国家日历。维护字段、权限和接口见 `配置管理模块补充设计.md`。

#### 无报价日处理方式

| UI 文案 | DSL 值 | 语义 | 适用提示 |
|---|---|---|---|
| 跳过无报价日，按有效日期计算 | `SKIP` | 不计入 AVG/MAX/MIN 的样本集合 | 平均值默认推荐 |
| 沿用目标日期之前最近一次有效报价 | `CARRY_FORWARD` | 向目标日期之前查找最近有效价，不使用未来价格 | 可设置最大回溯天数 |
| 使用本次区间内最新一次有效报价 | `LATEST_IN_WINDOW` | 将窗口中最后一条有效价的日期作为缺价目标日的实际价格来源日 | 可能使用目标日期之后的价格，必须明确确认 |
| 无报价时暂停并确认 | `REQUIRE_CONFIRMATION` | 不自动替代取价，试算和报价单创建时标记待处理 | 高风险或临时协议 |

策略结构示例：

```json
{
  "calendar": {"type": "PRICE_SOURCE_DEFAULT", "version": "2026-10"},
  "missingPricePolicy": {
    "mode": "CARRY_FORWARD",
    "maxLookbackDays": 7,
    "onExhausted": "MISSING"
  }
}
```

自然语言输入未说明节假日处理时，AI 返回 `NEEDS_CONFIRMATION`，不能只凭置信度自动保存。界面必须展示“目标取价日 → 实际价格来源日”的试算映射，并在保存前要求用户选择处理方式。“补价后日期”不再作为界面术语：目标日本身不改变，只是它所使用的价格来源日发生了替代。

`missingPricePolicy` 是整条客户价格规则的统一配置，不是每个日期的子配置。用户只选择一次，系统将其批量应用到当前规则生成的所有节假日和无报价目标日。日历下方的逐日映射只是只读计算结果，不提供逐日编辑或覆盖；未选择统一处理方式时，不展开逐日结果，只提示需要统一处理的日期数量。`REQUIRE_CONFIRMATION` 在报价单执行时也按本次命中的整批日期确认，第一期不支持逐日选择不同方式。人工确认只能在报价单元素价格表内完成；未确认元素的价格不得按空值或 `0` 参与金额计算，且报价单禁止提交。

需要与两类日期问题分开：2 月没有 30 日属于 `shortPeriod` 的非法/短月处理，不属于节假日；报价单创建日本身是节假日时，执行条件仍按实际 `priceBaseDate` 判断，不自动改成前一工作日。本期固定 `executionDateAdjustment=NONE` 且不提供配置入口；未来若要把执行日调整到工作日，必须另立需求，不能在实现中暗加参数。

### 4.6 面向用户的参数填写方式

`X`、`Y` 只用于方案中的抽象示例，不出现在用户界面，也不要求用户输入类似 `X=2，Y=3` 的字符串。界面把日期生成器拆成“先选方式、再填字段”，并实时生成自然语言预览。

#### 周期采样

“周期采样”先选择采样方式：

| 用户看到的选项 | 需要填写的字段 |
|---|---|
| 前几个完整周的指定星期 | 回溯完整周数、每周取哪一天、当前周是否参与 |
| 最近几周，每周取指定星期 | 回溯周数、每周取哪一天（周几）、是否包含当前周、无价格时如何处理 |
| 最近几个月，每月取一个日期 | 回溯月数、每月取第几日、短月没有该日期时的处理 |
| 最近几年，每年取一个日期 | 回溯年数、每年取哪个月份、每年取该月第几日 |

例如，用户在表单中选择“前几个完整周的指定星期”，填写：

```text
回溯完整周数：3
每周取哪一天：周二
当前周是否参与：不包含当前周，只取已结束的完整周
```

系统自动显示：

```text
回溯 3 个完整周，每周取周二；系统会自动生成 3 个历史日期。
```

#### 相对区间

相对区间也不使用“参数 X”文案，改为：

```text
区间口径：近几天（包含报价单创建日）
数量：5
```

或：

```text
区间口径：滚动几个月
数量：3
```

输入框使用数字类型并限制最小值、最大值；数量旁边直接展示单位和示例，避免用户猜测参数含义。

#### 统一可读预览

所有日期生成器保存前都生成一句业务语言：

```text
报价单创建日命中规则后，回溯 3 个完整周，每周取周二，生成 3 个历史日期；遇到无价格日期时跳过。
```

JSON/DSL 中仍使用 `count`、`weekday`、`dayOfMonth` 等结构化字段，但这些字段不直接暴露给普通用户。

#### AI 快速配置视图

自然语言配置场景默认不展开完整的执行条件、取价日期和价格源表单，先展示 AI 解析摘要：

```text
执行条件：未指定                         [编辑]
取价日期：上一个自然月 · 15 日～30 日     [编辑]
聚合方式：AVG · 平均值
```

下方保持“节假日 / 无报价日处理”展开，并要求用户确认。用户点击“展开结构化配置”后，才显示原有字段编辑器。这样减少首次配置的视觉复杂度，但不隐藏核心字段，也不影响条件重叠、日期合法性、短月和无报价校验。

#### 最终取价日历

AI 解析后以只读日历直接展示基于 `priceBaseDate` 计算出的最终取价结果，普通用户不需要先理解相对周期、偏移量等结构化参数：

- 浅紫色：规则计算得到的目标取价范围；
- 深紫色：开始锚点和结束锚点；
- 灰色删除线和“排”：自然语言规则明确排除的日期；
- 绿色点：目标日当天有报价，直接进入最终样本；
- 未选择处理方式或选择人工确认时，橙色表示节假日 / 休市待处理，红色表示有效交易日无报价待处理；
- 选择跳过时，灰色“跳”表示该目标日不进入最终样本；
- 选择替代取价时，蓝色“代”表示无报价的目标取价日，绿色边框“源”表示真正读取价格的实际来源日；
- 日历下方展示直接取价数、替代/跳过/待处理数、最终样本数和唯一实际来源日数，并逐条列出“目标取价日 → 实际价格来源日”。

日历的显示顺序必须与执行器一致：生成目标范围 → 按基准日截断 → 执行日期排除 → 识别节假日/无报价日 → 应用处理方式 → 生成最终样本。若 `CARRY_FORWARD` 找到的实际价格来源日位于规则计算区间之前，预览应自动扩展到该月份，不得只在文字中隐藏该来源日。

跨自然月在桌面端并排显示两个月，移动端上下排列；跨自然周只显示覆盖该区间的月份；跨自然年展示起止月份并提示中间月份已折叠。日历只承担预览和复核，不直接修改策略；需要调整时仍通过自然语言重新解析或展开结构化配置。

日历标题中的“试算基准日”可以点击并弹出日期选择器。切换日期后立即重新计算相对锚点、实际区间、自然日数量、节假日/无报价标记以及有效样本说明；当结束锚点晚于新基准日时，按 `futureDatePolicy` 截止并在日历上方明确提示。该选择只用于策略试算，不固化为策略规则；报价单实际执行仍使用自身的 `priceBaseDate` 重新计算。

## 6. 元素级例外如何复用

元素例外不再单独发明一套字段，也不再复制造价窗口下拉框。它复用同一个 `RuleEditor`：

```text
规则作用范围：客户默认 / 指定元素
指定元素：Ag
执行条件：月内日号介于 15～20 日
取价日期：相对区间 · 近 5 天
聚合方式：MAX
系数：1.020000
加价：15.000000 CNY
```

保存时后端要求例外的价格源、日期生成器、聚合方式、系数和加价全部有值；空值不表示继承默认。

- `日期 · 月份`

- `日历匹配`
- `指定日期`

删除：

- `每周周 X`
- `每月 X 号`
- `每年 X 月 Y 日`

- `最新一条`
- `相对区间`

## 8. 推荐结论

采用“**执行条件 = 日期谓词，取价窗口 = 日期集合生成器，聚合方式独立**”的三层设计。

它可以覆盖：

- 今天周几；
- 每月几号区间；
- 每周几到周几；
- 前/近 X 天；
- 前 X 周的周 Y；
- 每周、每月、每年周期采样；
- 指定日期与日期区间；
- 默认规则、元素级例外、多条件组合和优先级。

同时，后端只有一份日期表达式解析器，仅在价格修订首次创建、新元素追加和策略试算时执行。同一报价单的核价侧不再独立解析日期规则或执行 `_GLOBAL_` 策略，而是读取其显式绑定的价格修订；核价换版只有引入新元素时才执行一次新元素取价。

## 9. 自然语言输入与确定性执行边界

自然语言只作为配置入口，不是可执行规则。AI 将用户原文转换为候选 DSL 后，必须依次经过 JSON Schema 校验、业务语义校验、规则冲突检查和本文件定义的日期执行器试算；用户确认最终日历后才能发布策略。价格修订创建与新元素追加只执行已发布 DSL，不调用 AI；核价侧既有元素不重新执行 DSL，只消费显式绑定的价格修订。

解析状态固定为：

- `READY`：结构完整、校验通过，可以由用户确认；
- `NEEDS_CONFIRMATION`：存在自然日/交易日、边界包含、短月或缺价处理等歧义；
- `UNSUPPORTED`：包含工作日序号、多段日期并集、高级聚合、多价格源回退、盘中时刻或非日期业务条件等一期不支持语义；
- `INVALID`：JSON、枚举、日期范围或业务约束不合法。

只有 `READY` 且不存在待确认问题和不支持片段时才允许保存。模型置信度不参与保存判定，不允许删除未识别片段后保存剩余规则。

第一期不需要独立 Skill；后端 Schema、校验器和日期执行器是唯一权威。若后续增加多轮澄清 Skill，它也只能调用查询能力、校验和日历预览，不能保存策略、执行 SQL 或直接取价。

完整的自然语言覆盖边界、AI 请求/响应契约、配置维护、策略版本和确定性抓取规则见 `自然语言AI与策略执行补充设计.md`。
