# fronttask.md —— 前端任务分解

## 结论：本任务前端零改动

**判定依据**（不是「暂时不改」，是「按方案甲不需要改」）：

1. 缺陷位于后端 `ConfigureSnapshotService` 的服务端物化路径，**不经过任何前端代码**。
2. 方案甲只改「从哪里取既有 `row_data`」，**不改数据形态、不改字段、不改接口响应结构** ——
   前端收到的 JSON 与改动前逐位一致（见 `问题说明.md` AC-6）。
3. `POST /quote/create-quotation` 的**请求与响应契约完全不变**（见 `api.md`）。
4. 🔴 **2026-08-25 扩范围复核**：纳入 D-3（`CardSnapshotService`）后，前端仍**零改动** —— D-3 同样只改
   服务端私有方法的调用位置，响应结构一字不变。
5. 🚫 **`api.ts` 的 `timeout: 30000` 本次明确不动** —— 见 `问题说明.md §④ 证据 5`：
   前端 30s 与 Narayana 60s 是两道独立的墙，只放宽前端会撞穿 60s 且数据作废，属无效修法。
   本次靠把物化拉回 60s 预算内来解决。
   ⚠️ **但 AC-1 的秒数判据已按用户裁决改为「先测后定」** —— 评审估算两处全修后总墙钟仍在 ≈32 s 上下，
   **可能仍会撞穿前端 30s**。若实测确认，「是否单独给该调用放宽 timeout」将作为独立决策回到用户面前，
   **不在本次范围内自行决定**。

# 🔴 前端不再是零改动（D-5，2026-08-26 第三次扩范围）

> ⚠️ **本文件此前的「零改动」结论到此为止。** 起因见 `api.md` 的「契约变更」小节。

| 编号 | 服务的 AC | 任务内容 |
|---|---|---|
| **F-6** | AC-13 | 建单调用改为「**发起 → 轮询 → 完成**」三段式。POST 返回后**不再直接进编辑页**，改为进入「正在计算」态并开始轮询 `POST /quotations/{id}/ensure-card-values`（**409=继续轮询，200=完成**）。**范式直接照搬同项目已有的 `basicDataImportV6Service.pollImportResult`**（Step 1 导入用的就是它，含 20 分钟兜底、`onTick` 回调） |
| **F-7** | AC-13 | 进行中要有**用户可感知的状态**（不是干等）。至少「正在计算卡片值…」+ 不可重复提交。⚠️ 后端**不提供**进度百分比（分批埋点只在日志里），别设计成需要百分比的 UI |
| **F-8** | AC-14 | 失败面：轮询拿到非 409 的错误 → **显式提示并停止轮询**，🚫 不许无限转圈；超过兜底时长（建议沿用 20 分钟）→ 提示「后台可能仍在处理，请稍后在报价单列表查看」 |
| **F-9** | AC-13 | 🚫 **仍然不动 `api.ts:5` 的全局 `timeout: 30000`** —— 异步化之后建单 POST 本来就 <5s，轮询是一串独立快 GET/POST，**都不会撞 30s**。改全局超时会掩盖其它接口的真实问题 |

F-1~F-5 原有条目仍然有效，但 **F-1 的判据更新**：不再是「不出现 30s 超时提示」，
而是 **AC-13①「F12 Network 里 `create-quotation` 不再出现『已取消 30.01 秒』」** —— 这是用户实测抓到的原始症状。
