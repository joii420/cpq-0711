## ① 问题描述

**用户原话**（2026-08-25）：

> 「我马上要导入一个大笔订单，可能会超时」
> 「`http://localhost:5174/api/cpq/basic-data-import/v6/quote/create-quotation` 接口直接 30 秒超时」

**客观现象**（三者同时成立，缺一会误判）：

1. 浏览器侧：请求在 **30 秒**整被掐断，前端报超时。
2. 后端侧：**不报 500、不报业务异常**，接口最终返回 `200`，body 里带
   `"cardValuesReady": false, "warnings": ["卡片值物化失败: Error invoking subclass method"]`。
3. 数据侧：报价单与 1845 条明细行**已落库**（不丢单），但
   `quotation_line_item.quote_card_values` **1845 行全部为 NULL**，且**不会自愈** ——
   重试多少次都是同样结果。

> ⚠️ **这个组合极易被误判成「还在后台跑，等等就好」**。实际是跑到 60s 被事务 reaper 强杀、
> 整段计算作废。本次排查一开始也做过这个错误判断，靠 `ARJUNA012117` 日志才纠正。

## ④ 问题原因 / 报告

### 根因：两处独立的 N+1，各自作用于不同的失败面

**这不是一个缺陷，是两个。** 它们叠在同一条链路上，但**只有第二个会导致失败**：

| | **D-1**（初稿唯一认定的） | **D-3**（评审发现的真凶） |
|---|---|---|
| 位置 | `ConfigureSnapshotService.loadRowDataByComp`（`:1144`，SQL 在 `:1152`） | `CardSnapshotService.loadFrozenQuoteTabs`（`:1784`，SQL 在 `:1789`） |
| 循环体 | `snapshotLines` 逐行循环（`:610` → `computeRowDataFromSnap:1181`） | `snapshotNewLinesCardValues` 的 **Pass1 逐行循环**（`:603` → `buildCardValues:1634`） |
| 所在步骤 | ① `snapshotQuotation` | ③ `ensureCardValues` |
| **事务** | 🟢 **无事务** —— `ConfigureSnapshotService` 类 javadoc 原文：<br>「**本协调方法 `snapshotLines` 不带事务**」；`:141`/`:246`/`:1144` 均无 `@Transactional`；`CreateQuotationMaterializer` 类 javadoc 亦明写「**本类不加 @Transactional**」 | 🔴 **`@Transactional`（`CardSnapshotService:1055`），单个事务包住全部 1845 行** |
| 单次往返实测 | 200 次 **2.91 s / 3.19 s**（两次测量） | 200 次 **3.34 s / 3.49 s**（评审与主线各测一次） |
| 1845 行外推 | ≈ **27~29 s** | ≈ **31~32 s** |
| **后果** | 只烧**墙钟**，用户等得久 | **撑爆 60s 事务预算 → reaper 强杀 → 卡片值全量作废** |
| 取数性质 | 按 `lineItemId` 取，**逐行确实不同** | 按 `quotationId` 取，**整单恒定值**，逐行查纯属浪费 |

**一句话根因**：`ensureCardValues` 在一个事务内逐行调用 `loadFrozenQuoteTabs(li.quotationId)` ——
一个**整单恒定**的查询被放进逐行循环，1845 次往返 ≈31 s，叠加逐行 `buildCardValues` /
`buildCostingCardValues` 的 CPU 与树渲染后超出 Narayana 60s 预算，事务被 reaper 强杀
（`ARJUNA012117`），`quote_card_values` 与 `costing_card_values` **两侧同时**全量作废且不自愈。

D-1 是同一族的另一处浪费，**不致命但同样违反 `backend.md` 的 N+1 硬指标**，本次一并修。

> 🔑 **两者是同一个模式的两次发作**：都是**一次正确性修复，把 per-row 读加进（或换掉）一个已经优化过的循环**。
> D-3 尤其典型 —— 它的 diff 是把既有的整单 prefetch **直接替换**成了逐行查库：
> ```diff
> - JsonNode snapshot = (prefetch != null) ? prefetch.templateSnapshotById.get(templateId) : null;
> + JsonNode snapshot = loadFrozenQuoteTabs(li.quotationId);
> ```
> 副作用：`prefetch.templateSnapshotById` 这个整单预取被彻底架空，等于把上一轮的优化白做了。

### 两条调用链

**D-3（真凶，在事务内）**
```
BasicDataImportV6Resource.createQuotation(:152)
  └ CreateQuotationMaterializer.materialize(:43)          ← 本类不加 @Transactional
      └ CardSnapshotService.ensureCardValues(:1056)       🔴 @Transactional(:1055) 单事务包住 1845 行
          └ snapshotNewLinesCardValues(:571)
              └ Pass1 逐行循环(:603)
                  └ buildCardValues(:1634)

                          └ SELECT structure FROM quotation_view_structure
                            WHERE quotation_id=:qid AND view_kind='QUOTE_CARD'   (:1789)
```

**D-1（同族浪费，无事务）**
```
CreateQuotationMaterializer.materialize(:41)
  └ ConfigureSnapshotService.snapshotQuotation(:134 → :145)   🟢 无 @Transactional
      └ snapshotLines(:610)                                    🟢 类 javadoc 明写「不带事务」
          └ computeRowDataFromSnap(:1168)
              └ overlayExistingInputKeys(..., loadRowDataByComp(lineItemId))   ← :1181 循环内查库
                  └ SELECT component_id, row_data FROM quotation_line_component_data
                    WHERE line_item_id=:lid AND row_data IS NOT NULL            (:1152)
```

### 证据链（全部可复跑）

**证据 1 —— DB 监控直接抓到「事务里正在跑 D-3」（本案最硬的一条）**

排查期间挂着的 `pg_stat_activity` 轮询监控，在两次不同的运行里各推出一条：

```
[DB] 事务中空闲 42s pid=2138930 :: SELECT structure FROM quotation_view_structure WHERE quotation_id = $1 AND view_kind = $2
[DB] 事务中空闲 60s pid=2139149 :: SELECT structure FROM quotation_view_structure WHERE quotation_id = $1 AND view_kind = $2
```

该 SQL **逐字就是 `loadFrozenQuoteTabs:1789`**，且出现在一个**已存活 42s / 60s 的事务**里
（`idle in transaction` = 该刻 PG 未在执行，应用正在 Java 侧算值 → 正是逐行 `buildCardValues`）。

**证据 2 —— 事务被砍后的失败刷屏，点名同一个方法**

```
[card-snapshot] loadFrozenQuoteTabs failed q=1ed36b62-...: Unable to acquire JDBC Connection
                [Failing fast as the transaction has rolled back]
```
以 ≈1 ms 间隔连续刷屏（数千条）。这是 reaper 杀掉事务后 Pass1 循环**仍在逐行往下跑**、
每行再撞一次已死事务的直接证据 —— **同时坐实「该调用位于逐行循环内」**。

**证据 3 —— 事务被强杀的日志原文**（`17:46:33`）

```
ARJUNA012117: TransactionReaper::check processing TX 0:ffff7f000101:b36f:6a8e35c1:12b in state RUN
ARJUNA012095: Abort of action ... invoked while multiple threads active within it
ERROR [CreateQuotationMaterializer] [create-quotation] 后置物化失败 quotation=1ed36b62-...（不丢单，前端 warm 兜底）
Caused by: jakarta.transaction.RollbackException: ARJUNA016102: The transaction is not active!
```
堆栈顶帧为 `CardSnapshotService_Subclass.ensureCardValues` → `CreateQuotationMaterializer.materialize(:43)`
—— **抛点在 ③，不在 ①**。

**证据 4 —— A/B 基准实测（同库、同数据、各 200 次）**

| 复刻对象 | 200 次耗时 | 单次 | 1845 行外推 |
|---|---|---|---|
| `loadRowDataByComp:1152`（D-1） | 2.91 s / 3.19 s | ≈14.6 ms | ≈27~29 s |
| `loadFrozenQuoteTabs:1789`（D-3） | 3.34 s / 3.49 s | ≈17 ms | ≈31~32 s |
| 合并成 1 次 `IN`（D-1 对照组） | **0.16 s** | — | ≈1.5 s |

两组由评审与主线**各自独立测过一次**，控制组数字互相校准通过（2.91 vs 2.90）。

**证据 5 —— jstack 采样（⚠️ 附重要限定）**

6 次采样中 5 次落在 `loadRowDataByComp:1152`，阻塞于 `sun.nio.ch.Net.poll`。

🚩 **这只证明 D-1 是采样时刻的墙钟热点，不证明它是失败原因。** 初稿据此把根因单独归给 D-1，
是本次排查最大的方法论失误：**jstack 找的是「时间花在哪」，失败原因要看「哪个事务超了预算」** ——
两者可以落在完全不同的步骤上，本例正是如此（D-1 无事务）。

**证据 6 —— 两侧卡片值同时全空，只能由「③ 整体作废」解释**

实测 `quote_card_values` 与 `costing_card_values` **均为 1845 行全 NULL**。
若瓶颈在 ①，则 ②③④ 会照常执行并写入卡片值；只有 ③ 的事务被整体回滚才会两列同时全空。

**证据 7 —— 30s 与 60s 是两道独立的墙**

- 30s：`cpq-frontend/src/services/api.ts:5` 的 `timeout: 30000`（axios 全局）。Vite proxy 与后端均未设超时。
- 60s：Narayana 默认事务超时（`application.properties` 未显式配置）。

> 🚩 **只放宽前端 30s 是无效修法** —— 60s 那道墙照撞，且撞穿后数据作废。本次不动 `api.ts`。

> ⚠️ **初稿「证据 4」的全称否定已撤销。** 初稿曾以「物化窗口内 `com.cpq` 日志仅 23 行、
> `SqlViewExecutor` 仅 4 次」推出「**除本条外该链路不存在 N+1**」。
> **该推论不成立** —— 这台仪器只看得见带日志的调用，而**裸 `em.createNativeQuery` 完全不打日志**；
> D-1 与 D-3 恰恰都是裸 native query，两者都在它的盲区里。
> 🔑 **教训**：不要用「日志里没看到」证明「不存在」。

### 为什么测试没拦住

1. **等价性测试只守「算得对」，不守「算得快」** —— `OverlayExistingInputKeysTest`、
   `GoldenCardValuesEquivTest`、`CardValuesBatchPersistEquivTest` 全是**值等价**断言；
   N+1 不改变任何返回值，这些测试**必然全绿**。
2. **全工程没有任何「SQL 条数与行数无关」的断言** —— `backend.md` 的 N+1 硬指标目前**纯靠人工 review**。
   本次 AC-3 + T-1 就是来补这个洞的。
3. **测试数据量级不足** —— 既有夹具均为几十行，跑不出 60s 事务超时；且 `mvnw test` 走 `cpq_db`，
   1845 行的单在 `cpq_db_0724`，测试根本看不见它。
4. **本地 DB 若与应用同机则几乎无症状** —— 两处缺陷的严重度都与 DB RTT 线性相关（本环境 15.76 ms）。

### 修复二 · D-1

**做法**：把 `loadRowDataByComp` 的 per-row 读提到 `snapshotLines` 循环外，改为批量预载。

1. **新增**批量加载方法（暂名 `loadRowDataByLineComp(Collection<UUID> lineItemIds)`）：
   ```sql
   SELECT line_item_id, component_id, row_data
   FROM quotation_line_component_data
   WHERE line_item_id IN (:ids) AND row_data IS NOT NULL
   ORDER BY line_item_id, component_id, id
   ```
   **分块 200**（同文件 `writeRowDataBatchAllLines` 的 `CHUNK = 200` 范式）。
2. `computeRowDataFromSnap` 增加入参接收本行预载结果，内部不再调用 `loadRowDataByComp`；
   随后**删除** `loadRowDataByComp`（唯一调用点 `:1181`，已 `codegraph_impact` + `/usr/bin/grep -a` 双向确认无残留引用）。
3. **降级语义保持不变**：原 `try/catch` 记 warn 不中止整份快照的行为必须保留。

**🔒 六条强制落地约束（均来自 2026-08-25 独立评审的实测发现，缺一条即视为未完成）**：

| # | 约束 | 为什么 |
|---|---|---|
| C-1 | **预载集合收窄到 `lineNeedsExpand` 命中的行** | `snapshotLines` 的 `anyNeedsExpand` 段（`:319-332`）已逐行判过；`QuotationResource:154` 的 **saveDraft 增量热路径**下绝大多数行会在 `:447-455` 被 `continue` 掉、**根本走不到** `computeRowDataFromSnap`。不收窄 = 给热路径凭空加一次全量预载（本单 1902 kB）。**逐行懒查时这些行成本为 0，改批量后反而变贵 —— 这是本次改动唯一可能的性能倒退面** |
| C-2 | **IN 列表必须过滤 `null` 元素** | 现状 `:1145` 靠 `lineItemId == null` 提前返空 map 兜住；批量版没有这层保护，含 `null` 的集合绑定行为不确定 |
| C-3 | **SQL 必须带 `ORDER BY line_item_id, component_id, id`** | 表上**没有** `(line_item_id, component_id)` 唯一约束（只有 `pkey(id)` + `idx_qlcd_line`）。评审实测**全库存在 6 组重复键**。两侧都是 `Map.put` 覆盖 =「最后一行赢」，无 `ORDER BY` 时物理返回序不定 → 理论上可取到不同那行。加 `ORDER BY` 成本为零，把这条不确定性钉死 |
| C-4 | **预载只存原始 `String`，循环内对当前行 `readTree` 一次即弃** | 🚩 **撤销初稿「分块 200 后峰值更低」的错误说法** —— 分块只限制单次结果集，累积的 Map 要活到循环结束，**不降驻留峰值**。存 `JsonNode` 全量驻留约 **15~40 MB**（1902 kB 文本 × Jackson 8~20× 膨胀）；存 String 约 **3.8 MB**，降一个数量级 |
| C-5 | **预载结果视为只读，禁止喂给任何会原地改的下游** | 批量预载会让同一 `JsonNode` 实例被预载 Map 与 `freshRowData` **同时引用**（逐行查询天然每次新对象，无此问题）。当前无害（`overlayExistingInputKeys` 只读 `oldRow` 写 `freshRow`，且 INPUT 值是不可变 `ValueNode`），但这是逐行→批量转换最经典的 bug 面。**采纳 C-4 后该问题自动消失** |
| C-6 | **事务注解必须是有意识的选择，并在注释里写明理由** | `test.md T-4` 要求对标 `loadSnapshotRowsByLines`，而那个方法带 `@Transactional(REQUIRES_NEW)` + `self.` 调用。**照抄会把一个原本无事务的读变成开真事务的读**（`snapshotLines` 无事务，见 §④）。此处外层无事务、行为无害，但多借一次连接 + 多一次 begin/commit，**不能是复制粘贴的副产品** |

**实现者可选（不需要重新审批，属「循环前批量预载」范畴内）**：
`snapshotLines` 在进入循环前**已经**对同一张表、同一批 line id 打过整单 IN 查询
（`:308` 增量路径 / `:344` 非增量路径，建单走 `:344`）。可以给 `loadSnapshotRowsByLines`
加一个**姊妹方法**（多带 `row_data` 一列），复用这一次查询而非新增第二条。
- 收益：省 ≈10 次往返 ≈0.17 s —— **在 27 s 面前不值一提，真价值是结构性的**（少一处会与 `:308/:344` 漂移的 id 收集代码）。
- 🚫 **不得修改 `loadSnapshotRowsByLines` 自身的签名** —— `LoadSnapshotRowsByLinesEquivTest` 守着它。

### ⚠️ 移交给分页功能的已知风险（本任务不修，但必须传达）
