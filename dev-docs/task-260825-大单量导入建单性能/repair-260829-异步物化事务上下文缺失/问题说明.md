## ④ 问题原因 / 报告

### 一句话根因

`createQuotation` 把 `materialize()` 改成 fire-and-forget 的后台任务后，HTTP 请求随即结束、其 CDI request context 销毁；
① 步链路上的 `loadComponentsSnapshot()` 标的是 **`@Transactional(TxType.SUPPORTS)`**（不开事务、只借调用方的），
在这个条件下拿不到可用的 `EntityManager` → 抛异常 → **被两层静默 catch 吞掉** → ① 步写 0 行 → ②③④ 在空数据上"成功"跑完 → 埋点全绿。

### 完整因果链

| # | 位置 | 发生什么 |
|---|---|---|
| 1 | `BasicDataImportV6Resource.java:178` | `managedExecutor.runAsync(() -> materializer.materialize(bg))` —— fire-and-forget，HTTP 请求**立即返回**，其 CDI request context 销毁 |
| 2 | `CreateQuotationMaterializer.java:87` | `@ActivateRequestContext` **在这个条件下给不出可用的 EntityManager** |
| 3 | `ConfigureSnapshotService.java:296` | ① 步 `snapshotQuotation` → `snapshotLines` 调 `self.loadComponentsSnapshot(quotationId)` |
| 4 | `ConfigureSnapshotService.java:1068` | 该方法标 **`@Transactional(TxType.SUPPORTS)`** → 不开事务 → `EntityManager` 不可用 → 抛异常 |
| 5 | `loadComponentsSnapshot` 内部 catch | **静默 catch 之一**：warn「取 components_snapshot 失败」→ **返回 null**，流程继续 |
| 6 | `ConfigureSnapshotService.java:146` | **静默 catch 之二**：`snapshotQuotation` 顶层 catch → warn「整单重快照失败(已降级)」→ **不上抛** |
| 7 | — | ① 步写 **0 行** `quotation_line_component_data` |
| 8 | `CreateQuotationMaterializer.java:95-146` | ②③④ 在空数据上依次"成功"，`[create-quotation-timing]` 打出四步全绿 |

**关键鉴别点**：同一调用序列里 `loadCustomerId` / `loadDriverComponents` / `loadCustomerTemplateId` **全部成功** ——
它们都标 `@Transactional(REQUIRES_NEW)`，自己开事务。**只有 `SUPPORTS` 的那一个失效。**

### 🔍 被证伪的三个假设（记录下来，避免后续会话重走）

| 假设 | 谁提的 | 怎么证伪的 |
|---|---|---|
| **`is_current` 被 FLIP 语句翻错** | 用户原始报告 | 44280 行新行 **100%** 带 `pending_quotation_id`，分属 24 张真实 DRAFT 单，每张恰好 1845 料号。pending 模式（`VersionedV6Writer.java:920`）**显式**写 `is_current=false` 且**不 flip、不 delete** 任何现有行 —— 这是 `task-0721 B2` 的他单隔离不变量。<br>另：用户的「健康对照组」`production_energy`/`labor_rate`/`tooling_cost` **一张都不在** `QuotePendingRewriter.WHITELIST_TABLES` 的 8 张表里，而 5 张"异常表"**全部在内** —— 零例外，这是 pending 机制的指纹，不是导入 bug 的指纹 |
