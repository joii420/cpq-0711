## 1. 为什么改

### 1.1 v7 的结构性问题（不是缺陷，是形态问题）

v7 的 §4.3.3 经七轮澄清已相当完备，但它把三件本质不同的知识**揉在同一个「页签配方」里**：

| 知识 | 本质 | v7 存放位置 |
|---|---|---|
| 这张 Sheet 是什么（落表 / 判别式 / 真实导入列 / 附加维度） | **实体定义** | 一半在 `QuoteSheetRegistry`，一半在配方 |
| 这两张表怎么连（键 / 基数 / 兜底优先级） | **关系定义** | 拆成两套机制：§4.3.3.4「码列属性展开」+ §4.3.3.3.4「附加维度」 |
| 这个页签长什么样（主源 / 锚点 / 开关 / 树契约） | **视图定义** | 6 段硬配方 |

三个后果：

1. **加页签 = 加代码**。6 类页签 = 6 段配方；§10 登记的核价侧 17 页签下期要再写 17 段 —— 代码量 O(页签数)。
2. **同一件事有两套机制**。「码列展开」与「附加维度」本质都是「A 表连 B 表」，只因一个是多对一、一个是一对多就分成两套规则，规则之间的边界要靠人记（v7 §4.3.3.3.4 那张三行表就是在描述这个边界）。
3. **关系的正确性无法自动验证**。v7 §9 风险表对「配方与 rule-0724 文档漂移」的应对是「配方注册表用单元测试锁定」—— 但**测什么**没有定义，因为「附加维度填得对不对」是人的判断，没有可断言的客观量。

### 1.2 Cube 评估结论：不引运行时，采用其元模型

| 项 | 结论 | 依据 |
|---|---|---|
| Cube 运行时 | 🚫 **不引入** | ① Cube 自己执行查询，不产出可移植 SQL（`/v1/sql` 只给 parameterized query，issue #4932 未解）；② 其生成的嵌套 SQL 会击穿 `QuotePendingRewriter` 的「顶层 FROM 首个白名单表」假设 → `anchorInjected=false` **静默降级只读**；③ `hf_part_no` / `:total_material_no` / `:versionFilter` / `:pq` 等框架级占位符无处安放；④ 不支持递归 CTE（闭包要塞回手写）；⑤ pre-aggregation 对「per 报价行明细取数」无用 |
| Cube 元模型 | ✅ **采用** | cube / join+relationship / view / segment / access policy 五个概念与本方案一一对应，且其 `relationship` 是**结构事实**而非人的口径，可被真实数据验证 |

### 1.3 PG19 SQL/PGQ 评估结论：否决（已实测）

在 `10.177.152.12:5431`（**PostgreSQL 19beta3**）建 CPQ 同构模型实测，7 条断言全部取证：

| 实测项 | 结果 | 对本方案的影响 |
|---|---|---|
| `MATCH` 的连接语义 | **INNER**，基线 3 行 → 图版 1 行；`OPTIONAL` / `LEFT` 语法均不存在 | 🔴 与必须的 `COALESCE` 双源兜底正面冲突，**静默丢行** |
| 一次查询可连维表数 | **最多 2 张**（路径线性、不能分叉；`multiple path patterns ... not supported`） | 🔴 材质元素页签需 4 张 → 必须拆 4 个 `GRAPH_TABLE` |
| 改写器可识别性 | 用 `QuotePendingRewriter.TABLE_TOKEN` 真实正则扫描：`LEFT JOIN` 版命中 **1**，图版命中 **0** | 🔴 pending 数据看不见 + 锚点注入失效 |
| 等价写法体量 | 基线 693 字符 / 图版 **1010 字符（+46%）**，双向 `EXCEPT` 均 0（逐行等值） | 🟡 收益为负 |
| 执行计划 | 图版 `Hash Join` ≡ 普通 `INNER JOIN`，无优化 | 🟡 零性能收益 |
| 变长路径 | `ERROR: element pattern quantifier is not supported` | 🟡 BOM 闭包/树帮不上 |
| 拓扑写错 | 语法通过、**静默返 0 行** | 🟠 新增静默失败模式 |

> **结论**：`sql_template` 一律保持普通 SQL，**不使用 `GRAPH_TABLE`**。「图」只作为**编译期的元模型**存在于 Java 中，不进入生成的 SQL，也不引入任何数据库 DDL 对象。

## 3. 语义图模型（替代 v7 §4.3.3.4 / §4.3.3.5）

### 3.1 三种声明

```
节点 SheetNode  ── 一张导入 Sheet 或一张查名维表   （≈ Cube 的 cube）
边   Edge       ── 两个节点怎么连 + 基数            （≈ Cube 的 join + relationship）
视图 TabTypeView── 一个页签类型能用哪些节点         （≈ Cube 的 view）
```

### 3.2 节点

```java
SheetNode {
  String   name;              // "物料与元素BOM"（= Excel Sheet 原名，也是血统前缀）
  NodeKind kind;              // FACT(导入 Sheet) | LOOKUP(查名维表)
  String   table;             // element_bom_item
  String   discriminator;     // characteristic='RECIPE' | price_type IN (...) | null
  Scope    scope;             // 收窄策略,由表的实际维度决定（v7 §4.3.3.1 表原样下沉）
  List<ColumnDef> columns;    // 该 Sheet 真实导入列 3~9 个,中文名 = Excel 原表头（v7 §4.3.3.3.1）
  List<String>    grain;      // 附加维度:相对成品料号,这张表的行还按什么展开（v7 §4.3.3.3.4 第一层）
  String   anchorExpr;        // 这张表怎么产出 hf_part_no,LOOKUP 节点为 null
}
```

- `scope` 三档（照抄 v7 §4.3.3.1 实测表，不新增判断）：
  `FULL`（customer_no + is_current + system_type）/ `VERSION_ONLY`（capacity、plating_scheme）/
  `VIA_CUSTOMER_MAP`（material_master，必须 JOIN mcm 收窄）/ `NONE`（纯字典维表）
- **同一张表 + 不同 `discriminator` = 不同节点**。`material_bom_item` 因此天然是 4 个节点（RECIPE / OUTSOURCED / ASSEMBLY / 不过滤），v7 §4.3.3.2.1 的「四种用法」无需另立规则。

### 3.3 边（本次修订的核心）

```java
Edge {
  String from, to;            // 节点名
  String onLeft, onRight;     // 连接键（左侧列 = 右侧列）
  Cardinality cardinality;    // MANY_TO_ONE | ONE_TO_MANY | ONE_TO_ONE   ★
  int    fallbackOrder;       // 多源兜底优先级 → 决定 COALESCE 顺序（0=首选）
  String extraPredicate;      // 仅 material_customer_map 的固定客户谓词
}
```

**关键洞察：v7 的两套机制是同一件事的两个基数分支。**

| v7 里的说法 | v8 里的表达 | 生成的 SQL |
|---|---|---|
| §4.3.3.4「码列的属性展开」（查名） | `MANY_TO_ONE` 边，`to` 是 LOOKUP 节点 | `LEFT JOIN` + 多源按 `fallbackOrder` 生成 `COALESCE` |
| §4.3.3.3.4「附加维度进入页签粒度」 | `ONE_TO_MANY` 边 | `JOIN`，页签行数按 `to.grain` 展开 |
| §4.3.3.2.2「附属源必须标量子查询」 | 目标节点 `grain` ⊊ 页签 grain | **相关标量子查询** |

> ✅ **这不是新概念**：核价侧 `PricingSheetRegistry` 的 `ColumnDef.subDimMaster("operation_no","工序号","process","operation_name")`
> 已经是「码列 → 查名维表」的退化版单跳边。v8 只是把它**一般化**（加基数、加事实表之间的边、允许多跳）。

### 3.4 页签视图

```java
TabTypeView {
  String tabType;             // "材质元素"
  String anchorNode;          // 主源节点 = 图的起点
  List<String> availableNodes;// 该页签可用节点（其余节点的列不出现在字段面板）
  List<Switch> switches;      // 闭包 / 价格策略（模板钩子,见 §6）
  TreeContract tree;          // null 或 BOM 树契约（模板钩子）
}
```

**加一个页签类型 = 加一条 view 声明**，不改编译器一行代码。核价侧 17 页签同理。

### 3.7 谁维护语义模型 · 可配性分级（2026-08-19 补，用户追问「需不需要页面配置」）

#### 3.7.1 结论：语义模型是**开发态资产**，不做成可写配置

继承 v7 §4.3.3.5 已拍板的「**落代码不落 DB** —— 配方内含铁律逻辑，本质是代码而非数据，落 DB 反而无法单测、无法随版本演进」。v8 只是把这份「代码而非数据」从 6 段页签配方换成节点 + 边，**存放方式与维护者都不变**。

#### 3.7.2 依据：这三者都在「不变的一侧」（实测 `cpq_db_0724`，2026-08-19）

| 对象 | 数量 | 随客户增长？ |
|---|---|---|
| **Sheet（节点）** | **17 个** —— sheet 名是 `Q*Handler.sheetName()` 里写死的中文常量 | ❌ |
| **页签类型** | **5 类**（+ BOM 树共 6） | ❌ |
| **查名维表（边的目标）** | **5 张**，现网 40 视图普查 100% 维表查名、0 业务连表 | ❌ |
| **组件** | **157 个 / 13 个客户目录**（约 12 个/客户） | ✅ **持续增长** |

**分界线**：增长的一侧（组件：这个客户的这个页签用哪些列）→ 交给配置器页面；不变的一侧（17 + 6 + 5）→ 留在代码里。

#### 3.7.3 成本瓶颈不在声明

新增一张 Sheet 的实际工作量分布：写 `Q20XxxHandler`（Excel 解析 / 列映射 / 版本化写入 / pending 7 个登记点）+ 建表迁移 = **大头**；加一条节点声明 = **5~10 行**。
为最后 5~10 行做配置页面，省下约 5% 工作量，代价是**边基数断言 / handler 双向断言 / 图连通性断言三类 CI 保护全部失效** —— 把「静默算错钱」的风险交还给不写 SQL 的人，风险方向相反。

### 3.9 🆕 字段名 / 列名分离（2026-08-19 用户裁决，**推翻 v7 的三合一前提**）

#### 3.9.1 变更内容

v7 的核心前提是**三合一**：「列名同时是**视图别名 + 字段名 + 绑定路径**」（§4.3.3.6 原文）—— 这正是「改名牵动 6 处 + 冻结单阻断」的根源。

**v8 拆成两个概念**：

| 概念 | 存放 | 用途 | 改动影响 |
|---|---|---|---|
| **字段名** `fields[].name` | 已有，**不变** | 视图别名 `_字段名` · 绑定路径 `$view._字段名` · 公式 token · `rowKeyFields` / `partNoField` / `sortField` · `cross_tab_ref.match` · 快照 key | **仍同步 6 处 + 冻结单阻断**（§4.3.3.6 不变） |
| 🆕 **列名** `fields[].label` | 键**已存在于前端类型**（`types.ts:180`，V149 遗留），DB 从未填充 | **仅报价单卡片（NORMAL 组件页签）的表头**——编辑页、详情页 | **零影响面**，不进 SQL、不受冻结单限制 |

**默认 `label` 为空 = 跟随字段名**；用户自定义后独立维护；清空即恢复跟随。

#### 3.9.2 为什么这是「根治方案的轻量版」且**零数据迁移**

v7 §4.3.3.6 提过根治方案并判定本期不做：

> 「渲染层改用稳定 `fieldKey` 而非中文名做 key。代价极大 —— 要迁移全部历史 `snapshot_rows` / `row_data` / 公式 token，且触及 AP-44 协议面。」

**本方案不动 key**：`name` 继续承担全部 key 职责，只是多一个显示层。因此**历史数据一行都不用迁**，存量 157 个组件（含手写视图）自动获得该能力（`label` 缺省即跟随，行为与今天逐字一致）。

同时它把最麻烦的机制从高频路径移走了：**用户日常想改的是"表头显示成什么"，那现在零影响；真正高危的"改标识"变成低频操作**，仍受 6 处同步与冻结单阻断保护。

#### 3.9.2b 🔎 作用域澄清：列名**不是** Excel 列名（2026-08-19 用户追问后实测）

三者是**三套独立机制**，不要混：

| 出口 | 表头取自 | 与 `label` 的关系 |
|---|---|---|
| **报价单卡片**（`component_type=NORMAL`，143 个） | `fields[].label \|\| fields[].name` —— **实测 `QuotationStep2.tsx:3278` 已是这个写法** | ✅ **`label` 的唯一作用域** |
| **Excel 视图**（`component_type=EXCEL`，**仅 2 个**） | `excel_columns[].title` —— 每列自带标题，且通过 `tabs[].rowKeyFields` / `field_key` 按**字段名**引用 NORMAL 组件 | ❌ 不受 `label` 影响；改**字段名**才会牵动它 |
| Excel 视图列编辑器 / 公式 `[col_key]` 显示 | V149 `variable_label` 字典表（`variable_path` → `display_name`，全局按视图列注册） | ❌ 另一套字典，与组件字段无关 |

> ⚠️ **v8 初稿把「列名」写成「界面表头 + Excel 导出表头」是错的**，已按上表更正：**Excel 侧不归它管**。
> ⚠️ 连带修正 §4.3.3.6：改**字段名**时第 6 处「模板 Excel 列引用」应明确**包含组件级 `excel_columns[].tabs[].rowKeyFields`**（实测 6 处在用，存的是字段名）。

## 4. 编译器（替代 v7 §4.3.4 的实现方式，铁律一条不减）

### 4.1 算法

```
输入：tabType + builder_config.columns[]
1. 每列按 columnKey 解析到所属节点 → 节点集合 N
2. 对每个 n ∈ N：在图上求 anchorNode → n 的路径
   · 无路径      → err「该列在本页签下无取数路径」
   · 多条路径     → err「路径歧义」+ 列出候选（要求在声明里指定 preferredPath）
3. 页签粒度 = anchorNode.grain ∪ (所有路径上含 ONE_TO_MANY 边的目标节点.grain)
4. 每条边按 cardinality 定形态：
   · MANY_TO_ONE                    → LEFT JOIN（不改行数）
   · ONE_TO_MANY                    → JOIN（展开行数）
   · 目标 grain ⊊ 页签 grain        → 相关标量子查询（v7 §4.3.3.2.2 结论不变）
5. 收窄：按各节点 scope 生成；★ 版本化表的 is_current / system_type 一律落顶层 WHERE
6. 多源查名：同一码列的多条 MANY_TO_ONE 边按 fallbackOrder 生成 COALESCE
7. 模板钩子（见 §6）：闭包 CTE / 价格策略 / BOM 树双分支
8. 输出 SQL → 现有 dry-run → 落库
```

### 4.2 粒度冲突的形式化判据（取代 v7「互不包含即冲突」的口语描述）

设进入页签粒度的各节点 grain 集合为 `G₁…Gₙ`，
**合法 ⟺ 它们按集合包含关系构成一条全序链**（可排成 `G_a ⊆ G_b ⊆ … ⊆ G_z`）。
存在互不包含的一对 → 笛卡尔积 → **err 级阻断**（v7 AC-13 行为不变）。

### 4.3 铁律的实现位置

v7 §4.3.4 铁律表**一条不减**，只标注实现位置：

| 铁律 | v8 实现位置 |
|---|---|
| 业务列 `_` 前缀 / `hf_part_no` 唯一不带 `_` | SQL 生成器（不变） |
| 价格策略必 LEFT JOIN、禁 `COALESCE(...,0)`、别名不带 `_` | **模板钩子** |
| 版本化表禁进带 `is_current` 的 JOIN ON | **算法 step 5 硬编码**（不是可选项） |
| 闭包 `UNION` 去重 + 白名单表顶层 FROM + `COALESCE` 兜底 | **模板钩子** |
| 不生成 ORDER BY，改设 `sort_field` | SQL 生成器（不变） |
| 禁 V44/V76 废弃表（AP-53） | 节点声明只引 V6 表 + `SqlViewValidator` 二次把关（不变） |
| 中文标识符须 ASCII 别名 | SQL 生成器（不变） |

### 4.4 🆕 新增硬约束：生成的 SQL 必须保持改写器可识别的形状

**依据**：本次实测证明 `QuotePendingRewriter` 靠**词法扫描 `FROM|JOIN` 后的白名单表 token** + 「顶层 FROM 首个白名单表」定位主位表工作；形状不对 → `anchorInjected=false` **静默降级只读**。

因此写入编译器的三条生成约束（v7 只在 §4.3.3.3.4 一句带过，v8 提升为显式约束 + 单测）：

1. 顶层 `FROM` 必须是白名单表且以裸表名出现（不得包裹为子查询/CTE/表函数）；
2. 白名单表的 `is_current` / `system_type` 谓词一律在顶层 `WHERE`，不得进 `JOIN ON`；
3. 生成后**自检**：用 `QuotePendingRewriter.TABLE_TOKEN` 正则回扫产物，命中数 ≥ 1，否则编译失败（不是告警）。

## 5. 声明的自动验证（v8 最大增量）

v7 §9「配方与文档漂移」只有「单元测试锁定」这句模糊应对。v8 给出**可执行的断言**。

### 5.1 边的基数验证（每条边一个断言）

```sql
-- 对每条声明为 MANY_TO_ONE 的边：右侧必须唯一，否则声明写错
SELECT <onRight>, count(*) FROM <to.table> [WHERE <to.discriminator>]
GROUP BY 1 HAVING count(*) > 1 LIMIT 5;
-- 期望：0 行。非空 = 该边实际是一对多 → 生成 LEFT JOIN 会让行数翻倍、勾小计即算错钱
```

**这正是 v7 最怕的那类静默故障（§4.3.3.2.2 的「静默算错钱」）第一次有了自动检出手段。**

### 5.2 其余三类断言

| 断言 | 内容 | 覆盖的 v7 风险 |
|---|---|---|
| 节点列 ↔ handler 双向 | 登记列集合 ⇄ handler `put` 列集合（v7 §4.3.3.3.2 原案） | 导入加列而配置器选不到 |
| 图连通性 | 每个 view 的每个 `availableNodes` 成员，从 `anchorNode` 可达且路径唯一 | 配出「无取数路径」的列 |
| 生成形状 | 每个 view × 典型列组合，产物经 `TABLE_TOKEN` 回扫命中 ≥ 1 | §4.4 的静默只读降级 |

### 5.3 血统变成求解副产物

`columnKey = <节点>.<列>` + 求解得到的路径，**共同构成完整血统，无需额外记录**。
v7 §4.3.8「本期只记录不消费」的结论**不变**（跨页签公式引擎本期仍不动），但下期做匹配推荐时可直接用「路径是否指向同一节点同一列」判定，强于现有 `comparable()` 的字符串子集比较。

> 这使 v7 第四轮**遗留待确认 ③**（血统是否拉进本期）不再是取舍题：**血统本期自然产出，消费仍留下期。**

### 10.2 操作形态的裁决（2026-08-18 用户追问「BOM 树 / 价格策略怎么操作」）

**判据：能从结构客观推导的 → 推导；属于业务意图、数据里看不出的 → 用户显式选。**

| 机制 | 操作形态 | 理由 |
|---|---|---|
| **BOM 树** | 页签类型下拉的**第 6 项** | 它替换的是整套契约（不输出 `hf_part_no`、`:total_material_no` 收窄、只读、附带写 `costing_bom_tree_config`），不是在骨架上追加 |
| **元素价格策略** | 🆕 **v8 变更：取消开关** —— 把 `f_material_element_price` 建成节点，**拖「元素单价」列即自动接；但必须先指定「元素列」，否则阻断**（见 §10.4） | 本质是「多一个来源、多两列」，与拖任何其他列同构。v7 做成开关是因为当时没有节点模型可挂。**铁律仍由模板钩子保证**（必 `LEFT JOIN`、禁 `COALESCE(...,0)`、别名不带 `_`、别名固定 `cep`、双 JOIN 条件） |
| **子件闭包** | **保留开关**（唯一剩下的开关） | 它改的是**行的来源**而非列，没有对应的列可拖；若靠「拖了归属料号」推导，用户会遇到「我只想看归属料号，怎么行数变了」——不可解释 |

> **开关从 v7 的 2 个收敛为 1 个**，是语义图模型的直接收益（价格策略从「特例开关」降级为「普通节点」）。
> ⚠️ 连带影响：`builder_config.options` 只剩 `includeChildParts`；`priceStrategy` 字段**移除**，其语义改由 `columns[]` 中是否存在价格策略节点的列推导。

### 10.4 🔴 价格策略规范校正（2026-08-18，用户指出 + 实测取证）

**v7 的价格策略部分整体过期**（v7 写于 2026-07-28；`task-0729` 于 07-29 之后改了函数并加了强制绑定）。v8 稿与原型初版沿用了 v7，一并校正。权威：`rule-260724/AGENT-配置入口.md §3.6/§3.6.1` + `报价侧.md §5.2.2`。

| # | v7 / v8 初稿写的 | 正确写法 | 写错的后果 |
|---|---|---|---|
| 1 | `f_customer_element_price` | **`f_material_element_price`**（V369 起）。旧函数仍在库中、已降级为新函数内部 fallback | 永远吃不到「客户价格调整策略」产出的版本价，**静默按实时价** |
| 2 | `ON cep.element_code = ebi.component_no` 单条件 | **双条件**：追加 `AND cep.material_no = <本视图 hf_part_no 的输出表达式，逐字一致>` | 版本指针只挂父件；闭包形态漏 `COALESCE(cl.root_no, …)` → 子件永远走 fallback，**不报错、不缺行、只是价格不对** |
| 3 | 别名自创（`fce`） | **固定 `cep`**（2026-07-29 定死） | 违反铁律 |

**编译器据此生成两种形态（由「子件数据也要」开关决定，用户无感）**：

```sql
-- 平铺形态
LEFT JOIN f_material_element_price(:customerCode, :priceBaseDate) cep
       ON cep.element_code = ebi.component_no
      AND cep.material_no  = ebi.material_no
-- 闭包形态（hf_part_no = COALESCE(cl.root_no, ebi.material_no)）
      AND cep.material_no  = COALESCE(cl.root_no, ebi.material_no)
```

> ✅ 这条正是配置器的价值证明：手写时「平铺 vs 闭包要不要加 `COALESCE`」是最容易犯且**全静默**的错；编译器由同一个开关同时决定 `hf_part_no` 表达式与 `cep.material_no`，**结构上不可能不一致**。

#### 10.4.1 三项显式绑定（后端硬拒，v7 完全遗漏）

接了取价函数的组件**必须配齐**，否则后端抛 `ComponentElementBindingRequiredException` → **400 `COMPONENT_ELEMENT_BINDING_REQUIRED`**（已核实 `ComponentService:396`；`component` 表实有 `element_code_field` / `element_price_field` / `element_currency_field` 三列）：

| 组件属性 | 含义 | 必填 | v8 配置器如何产出 |
|---|---|---|---|
| `elementCodeField` | 拿哪一列的值匹配元素编码 | ✅ | **原子组自动确定**（见 §10.4.2），不设勾选项 |
| `elementPriceField` | 升版改哪一列 | ✅ | 同上 |
| `elementCurrencyField` | 货币列 | 可空 | 同上，未选货币列则留空 |

**角色仍是 4 个**（`ROW_KEY` / `PART_NO` / `PART_NAME` / `SORT`）—— 2026-08-18 用户裁决：**不为价格策略新增勾选项**。

**元素列的值必须是 `element_code`（`Ag`/`Cu`）**，不是 `element_name`（银/铜）、也不是 `element_no`（`10001`）。三者在 `element` 表并存 —— 该约束改由**编译器保证**（原子组带出的恒是 `ebi.component_no`），不再暴露为用户可勾错的选项。

#### 10.4.2 价格策略 = 原子组（2026-08-18 用户裁决，取代「新增勾选项」方案）

**元素单价基于元素列才能使用** —— JOIN 键 `cep.element_code = <元素列>` 取自元素列，没有它取价函数无从连接。
但**不为此新增勾选项**，改为把这组列做成**原子的**：

| 动作 | 行为 |
|---|---|
| 拖入「元素单价」 | 自动带出**元素列**（`ebi.component_no`，若尚未在输出中）并同时加入输出；「货币」可选 |
| 移除「**元素单价**」（组核心） | **整组移除**（含货币 + 自动带入的元素列） |
| 移除「**元素列**」（JOIN 左键） | **整组移除** —— 没有左键取价函数无从连接，留下单价列会产出无效 SQL |
| 移除「**货币**」（可选成员） | **只移除自己**，组保留、三项绑定仍完整 |
| 用户自己加过的元素列 | **不回收**（只回收「由本组自动带入」的那列） |
| 三项绑定 | 由**组内身份**直接确定，不靠列名匹配 → 用户改列名后绑定仍正确（改名照走 §4.3.3.6 六处同步） |

> ⚠️ **删除方向必须三个都一致**（2026-08-19 原型实测抓到两个缺陷）：只实现「删元素单价时回收」是不够的 ——
> ① 组内还有货币时删单价 → `elementPriceField` 消失但组仍在 → **后端 400**；
> ② 删掉自动带入的元素列 → JOIN 左键落空 → **取价函数静默接不上**。
> 两者都不会在 dry-run 暴露，须由删除语义在源头杜绝。对应 **AC-32**。

**为什么可以不问**（对 `AGENT §3.6.1` 纪律 3「元素列必问用户、禁自己猜」的适用性分析）：
该纪律的立法背景写在同节 —— 原方案是**运行期正则解析视图 SQL 反推**三项绑定，因 `COALESCE(...)`/左右写反/多条件 JOIN 等写法会抓空抓错、**且失败全静默**，故 2026-07-29 推翻改为显式配置。
配置器场景下元素列**不是反推出来的，是配置器自己生成的**：它知道自己把 `ebi.component_no` 输出成了哪一列。这是记账不是猜测，纪律的立法意图（防止静默绑错）已由结构满足。

**保留一个改绑入口（不是勾选项）**：价格策略组头显示「元素键取自：〔元素 ▾〕」，**默认已填好**，仅在下述特殊形态时需要改。

> ⚠️ **实测发现的特殊形态（待确认，见 §10.5）**：现网 `COMP-0049` / `COMP-0233` / `COMP-0242` / `COMP-0302` 四个组件的 `element_code_field = 「元素代码」`，而该字段**没有 `default_source`** —— 即元素键取自**用户手填列**而非视图输出列。原子组默认从主源带出，若要支持这种形态，改绑入口必须允许选中手填字段。

**「元素名称」的定位澄清**（实测：表函数返回列为 `material_no / element_code / unit_price / currency / price_unit`，**不含** `element_name`；现网 **0 个**组件有「元素名称」字段）：
它来自**元素库 `element` 的 LOOKUP 边**（`COALESCE(el.element_name, ebi.component_no)`），是 v7 §4.3.3.4 提出的**新增可选展示列**，**不属于价格策略原子组**，也**不能**用作 `elementCodeField`（其值是「银/铜」而非 `Ag/Cu`）。

#### 10.4.3 🆕 配置器让正则反推变得不必要

后端 `ElementBindingDerivation`（`ComponentService.suggestElementBinding`）是**靠正则解析手写 SQL 反推**这三项的，带 `confidence` / `warnings`，规范注明「推导失败返回空壳，不报错」「失败全是静默的」，2026-07-29 已被推翻为**仅供迁移期推荐**。

配置器是 SQL 的**生产者**，血统直接给出零歧义答案 → **builder 视图的三项绑定由保存事务直接回填，不走 `ElementBindingDerivation`**。存量手写视图继续用反推推荐，行为不变。

> 这使 §4.3.5「一体化保存」多回填三项组件属性，也是 v8 相对 v7 新增的**正确性收益**（v7 即使实现了，保存也会被后端 400 拒绝）。

### 10.5 🔎 实测引出的待确认项（元素键的两种形态）

现网 13 个接了取价函数的组件，绑定高度规律但**存在两种形态**：

| 形态 | 组件 | `element_code_field` | 该字段的 `default_source` | 含义 |
|---|---|---|---|---|
| A · 视图输出 | COMP-0021/0027/0045/0090/0102/0122/0130/0133/0227（9 个） | `元素` | `$mc_view._元素` | 元素符号由 `ebi.component_no` 取出 |
| B · 手填 | COMP-0049/0233/0242/0302（4 个） | `元素代码` | **无** | 元素符号由用户在报价单上手工填/选 |

`element_price_field` **13/13 全叫「元素单价」**；`element_currency_field` 5 个「货币」、8 个空。

**裁决（2026-08-19 用户拍板）：✅ 支持形态 B。**
改绑入口「元素键取自：〔… ▾〕」的候选列表**须包含无 `default_source` 的手填字段**。默认仍按形态 A 自动带出视图输出列；选中手填字段时，编译器不再输出 `_元素` 业务列，JOIN 左键改指该字段在渲染期的值。对应 **AC-33**。
