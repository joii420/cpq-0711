## 2. 需求背景与目标

### 2.1 要解决什么问题

**当前是怎么做的**：组件的取数视图（`component_sql_view.sql_template`）是**裸 SQL 文本**，在「组件管理 → SQL 视图」抽屉里手敲（`SqlViewConfigDrawer.tsx` 的一个 TextArea），保存时跑 dry-run（EXPLAIN）校验。实际上全部由 Agent 按 `dev-docs/rule-260724-组件模板配置/AGENT-配置入口.md` 手写。

**痛点**：

1. **业务/实施人员完全无法自助**。配一个客户模板必须找 Agent 或开发，客户模板一改就要重新排期。
2. **隐性铁律极多，写错不报错只出错数**。已沉淀的规则包括：`hf_part_no` 驱动键别名（写错 → 视图返全表 → UI「首值（共 N 项）」）、业务列 `_` 前缀、tabType→V6 表映射、版本化表禁写进带 `is_current` 的 `LEFT JOIN ON`（§3.6 → 运行期列索引越界，dry-run 查不出）、BOM 闭包三铁律（§3.8.3 → 漏去重则页签小计翻倍且静默）、价格策略必须 `LEFT JOIN` 且禁 `COALESCE(...,0)`、视图 `ORDER BY` 对 DRAFT 无效须改用 `sort_field`。
3. **视图列名 ↔ 字段 `default_source.path` 要逐字对齐**，差一个全半角就取不到值，**后端不强校验**（仅软告警），是当前最高频的静默故障源。
4. **dry-run 只能查语法与禁表**，查不出「语法对但运行期返 0 行」——而这正是页签空白的主要成因。实施人员配完无法自证正确，必须建一张报价单才能验证。

### 2.2 本次要达成的目标

- 实施顾问（**不会写 SQL**）能在界面上通过拖拽，独立配出报价侧 6 类页签（5 类平铺 + BOM 树）的取数，并**当场用真实数据验证**，全程不接触表/JOIN/别名/SQL 概念。
- 用配置器配出的组件，与现网 Agent 手写版**渲染结果逐行等值**（验收标准 §8.7 golden 用例）。
- 铁律由生成器保证：用户**无法**配出违反 §3.6 / §3.8.3 / `_` 前缀 / `hf_part_no` 契约的视图。
- 「视图列 ↔ 组件字段 ↔ 绑定路径」三者永不失配（由同一次保存原子产出）。

### 2.3 不做什么（明确边界）

| 不做 | 说明 |
|---|---|
| ~~BOM 树页签~~ | **第四轮已纳入本期**（用户 2026-07-28 要求），见 §4.3.3.2.3 |
| 年降三张 Sheet | 来料年降 / 组装加工费年降 / 年降系数，本期**不参与配置**（用户确认） |
| 核价侧 | 第二套契约（`:versionFilter` 宏 / `_GLOBAL_` / 禁客户过滤 / spine 树 / `basic_data_path`），本期不做 |
| 自由选表、拉线连 JOIN | 明确不做可视化查询设计器；只做配方式 |
| SQL 反向解析（手写 SQL → 拖拽态） | 现网视图含 `WITH RECURSIVE`/相关标量子查询/多层 `COALESCE`，反解不可靠，一旦解错会静默改坏已上线视图 |
| 跨组件 `GLOBAL` 视图 | 配置器产出的视图一律 `scope=COMPONENT` |
| 公式列 | 仍在「公式」Tab 配置，配置器不产 `FORMULA` 字段 |
| 存量视图迁移 | 20+ 手写视图**原样存活**，不强制迁移、不批量转换 |

## 4. 功能详述

### 4.1 用户场景 / 操作流程

**角色**：实施顾问（懂业务、不写 SQL）。

1. 进入「组件管理」，新建或打开一个组件，切到 **「取数配置」Tab**。
2. 选**页签类型**（主件 / 材质元素 / 零件 / 外购件 / 费用类 / BOM 树）——**只此一个选择**。系统据此自动确定主数据源、判别式（如 `characteristic='OUTSOURCED'`）、取数锚点、客户收窄方式与全部附属源（§4.3.3.2），右侧「可用字段」**按导入 Sheet 分组**列出该页签能取的所有列（带中文业务名）。
3. 勾选**开关**（仅 2 个）：`子件数据也要`（BOM 闭包）、`元素单价接价格策略`（仅材质元素可见）。**客户过滤是固定行为**，不作为开关暴露。
4. 从左侧把需要的列**拖到右侧「已选输出列」**；拖动排序；在每行上勾 `行键`/`料号列`/`名称列`/`排序列`，系统按列名语义自动预填 `字段类型`/`金额`/`小计`（可改）。
5. 常用列不够用 → 展开每组下的**「全部列」**（该表其余物理列，带中文名/类型），拖进来即可，**仍无需知道 JOIN 的存在**（连表规则见 §4.3.3.4）。
6. 点**「真实预览」** → 选一个客户 + 一个料号 → 表格展示真实返回行（行数、各列值、空值高亮）。返 0 行时给出**可操作的诊断**。
7. 点**保存** → 系统跑体检清单 → 通过则原子写入：SQL 视图 + 组件字段 + 绑定路径 + 组件级属性，并刷新引用方模板 snapshot。
8. 任何时候可点**「查看生成的 SQL」**只读查看；点**「转为手写 SQL」**一次性脱钩（不可逆）。

### 4.3 业务规则与技术设计

#### 4.3.1 架构不变量（渲染链路零改动）

```
用户拖拽 → 取数意图 DSL(builder_config JSONB) → [编译器] → sql_template 文本 → 现有 dry-run → 落库
                    ↑ 唯一权威                      ↑ 铁律全在这里            ↑ 下游完全无感
```

`SqlViewExecutor` / `ComponentDriverService` / driver expansion / 快照组装 **一行不改**——它们只读 `sql_template`，不知道 builder 的存在。这是本方案风险可控的根本原因。

#### 4.3.2 数据模型（`component_sql_view` 加 2 列）

| 列 | 类型 | 说明 |
|---|---|---|
| `builder_config` | `JSONB NULL` | 拖拽结果。**NULL = 手写模式**，存量视图不受任何影响 |
| `builder_version` | `INT NULL` | 编译器版本号。铁律升级后可批量重编译全部 builder 视图 |

`builder_config` 结构：

```jsonc
{
  "tabType": "材质元素",                  // 页签类型（业务语义轴）
                                          // 主源/判别式/锚点/附属源全部由 tabType 推导，不入 config
  "options": {                            // 仅 2 个开关；客户过滤固定，不入 config
    "includeChildParts": false,          // → BOM 闭包 CTE（§3.8）
    "priceStrategy": true                // → LEFT JOIN f_customer_element_price(...)
  },
  "columns": [
    {
      "columnKey": "MATERIAL_NAME",      // ★ 只允许后端配方目录里的 key，前端永不传 SQL 片段
      "fieldKey": "f_8a3c…",             // ★ 对应组件 fields[].key（归属关系存这里，不动 fields 结构）
      "label": "材质",                    // → 字段名 + 视图别名 _材质
      "fieldType": "INPUT_TEXT",
      "isAmount": false,
      "isSubtotal": false,
      "roles": ["ROW_KEY"]               // ROW_KEY / PART_NO / PART_NAME / SORT
    }
  ]
}
```

> **安全约束（用户确认）**：`columns[].columnKey` 只能是后端配方目录中已登记的 key，SQL 表达式**全部在后端**。前端无法传入任意 SQL 片段，从结构上杜绝注入。「全部列」同样走后端目录（由 `information_schema` 动态生成后仍在后端拼装）。

> **AP-44 规避（重要）**：BUILDER/MANUAL 的归属关系存在 `builder_config.columns[].fieldKey`，**不在 `fields[]` 上新增任何 JSON 键**。因 CLAUDE.md 明列「给字段加新 config JSON 键」是 AP-44 的触发条件，此设计使 `fields[]` JSON 结构零改动，**不触发 17 检查点协议**。

#### 4.3.3 配方目录：页签类型 × 数据源 × 可选字段

> **2026-07-27 第二轮澄清后重写**。用户指出「费用类还可能计入材质（来料固定加工费即是）」「客户过滤是固定的」「可按导入 sheet 规格约定可选字段」「要能关联材质库/工序库/元素库带出名称」。以下全部内容基于对 `cpq_db_0724` 的实测与 17 个报价侧导入 handler 的核对。

##### 4.3.3.0 两条正交的轴（对第一版方案的结构性修正）

第一版把「取数锚点」和「页签类型」混成了一个「配方」，**这是错的**。一行数据有两个独立属性：

| 轴 | 决定什么 | 由什么定 |
|---|---|---|
| **取数锚点**（视图输出哪一列作 `hf_part_no`） | 这行能否被本报价行取到——框架对报价行隐式注入 `hf_part_no = 本行产品料号` | 数据实际挂在哪个料号上（导入落表决定，客观事实） |
| **页签类型**（`tabType`） | 这行在报价单上的业务身份：料号列/名称列绑哪列、树类型判定、加叶子候选 | 业务语义（人的口径） |

**实测反例**：`unit_price(price_type='INCOMING_MATERIAL_PROCESS')`（来料固定加工费）的 `code` **20/20 全是材质料号**（`00137` 等，存在于 `material_recipe`，且 0 行命中 `material_master`），同时 `finished_material_no` **20/20 有值**。

> 即：**锚点 = 成品（`finished_material_no`），页签类型 = 材质元素（每行是一个材质）**。按第一版「锚点二选一（成品/零件）」的模型，此页签无法配出。

**因此配方模型改为**：页签类型（5 选 1）与数据源（sheet）分别选择，锚点**由数据源自动确定、不由用户选**（下表已逐条固化），用户只回答业务语义层面的「这个页签是什么」。

##### 4.3.3.1 客户 / 版本收窄：按主源表的实际维度决定（第四轮修正）

第三轮写的「客户过滤无条件固定生成」**不准确**。实测各表维度（`cpq_db_0724`，2026-07-28）：

| 表 | `customer_no` | `is_current` | `system_type` | 参与 pending 改写 | 编译器生成的收窄 |
|---|---|---|---|---|---|
| `element_bom_item` / `material_bom_item` / `unit_price` | ✓ | ✓ | ✓ | ✓ | 三者全加（+ 各自判别式） |
| `material_customer_map` | ✓ | ✗ | ✓ | ✓ | `customer_no` + `system_type` |
| `capacity` / `plating_scheme` | ✗ | ✓ | ✓ | ✓ | `is_current` + `system_type`，**无客户过滤** |
| **`material_master`** | ✗ | ✗ | ✗ | ✓ | **无任何过滤列** → 必须 `JOIN material_customer_map` 收窄 |
| `material_recipe` / `process_master` / `element` | ✗ | ✗ | ✗ | ✗ | 纯字典，无过滤（正因如此做查名最安全） |

**准确规则**：主源表有 `customer_no` 就直接加；没有的（`material_master`）**必须靠 `JOIN material_customer_map mcm ON mcm.material_no = mm.material_no AND mcm.customer_no = :customerCode` 收窄，否则返全表**——这正是现网 `cp_view` 的写法。`capacity` / `plating_scheme` 只能加版本过滤。**用户依然无感**，界面不暴露任何过滤开关。

树契约例外：BOM 树页签**禁用** `:customerCode`，按 `:total_material_no` 收窄（见 §4.3.3.2）。

##### 4.3.3.2 六类页签：主数据源 / 锚点 / 行身份料号（第四轮定稿）

用户只选**页签类型**一项；可用字段面板**按导入 Sheet 分组**展示。**行身份料号**是核心概念——既是「这一行代表谁」的标识，也是所有**附属源的关联键**。

| 页签类型 | 主数据源（Sheet → 表 + 判别式） | 取数锚点 | 行身份料号 | 收窄方式 | 开关 |
|---|---|---|---|---|---|
| **主件** | 物料主档/单重 → `material_master` | `mm.material_no` → `hf_part_no` | 成品料号 | **JOIN `material_customer_map`** | — |
| **材质元素** | 物料与元素BOM → `element_bom_item` | `ebi.material_no` → `hf_part_no` | **材质料号** `material_part_no` | 直接三过滤 | 闭包 · 价格策略 |
| **零件** | 自制加工费 → `unit_price(PROCESS)` | `up.finished_material_no` → `hf_part_no` | **零件料号** `up.code` | 直接三过滤 | 闭包 |
| **外购件** | 物料BOM → `material_bom_item(OUTSOURCED)` | `mbi.material_no` → `hf_part_no` | **组成件料号** `component_no` | 直接三过滤 | 闭包 |
| **费用类** | 来料固定加工费 + 来料其他费用 → `unit_price(INCOMING_MATERIAL_*)` | `up.finished_material_no` → `hf_part_no` | **投入料号** `up.code`（**类型不定**） | 直接三过滤 | 闭包 |
| **BOM 树** | 物料BOM → `material_bom_item`（**不过滤 characteristic**） | **不输出 `hf_part_no`**：输出 `material_no`(子)/`parent_no`(父)，按 `component_no = ANY(:total_material_no)` 收窄 | 组成件料号 | `system_type` + `is_current`，**禁用 `:customerCode`** | — |

**费用类的定义（用户第四轮明确）**：= 来料固定加工费 + 来料其他费用两个 sheet。它们的 `code`（投入料号）**既可能是材质、也可能是零件或外购件料号**，无法归入任一 typed 页签，故自成一类。正因归属不定，其查名**必须双源兜底** `COALESCE(mm.material_name, mr.name)`——是材质取材质名，是零件/外购件取物料名。判别式由所选字段推导：只拖一个 sheet 的字段 → 收窄到该 `price_type`；两个都拖 → `IN (...)`，靠「费用要素」列区分行。

> 实测：现网 `INCOMING_MATERIAL_PROCESS` 的 `code`（`00137`/`992`）恰好都是材质料号（在 `material_recipe` 中，且在物料BOM 里以 `characteristic='RECIPE'` 作组成件出现），但**模型不做此假设**。

##### 4.3.3.2.1 物料BOM 的四种用法：由页签类型推导 `characteristic`，用户不选

实测分布（`system_type='QUOTE'`）：`RECIPE 78 / OUTSOURCED 34 / ASSEMBLY 33 / NULL 1`（NULL 疑似脏数据，体检时提示）。

| 用法 | `characteristic` | 角色 |
|---|---|---|
| 外购件页签 | `OUTSOURCED` | **主源**（字段直接可选） |
| 材质元素页签 | `RECIPE` | **附属源**（组成数量/单位/损耗率/毛重/净重…；实测其组成件 1/1 对得上元素BOM 的材质料号） |
| 零件页签 | `ASSEMBLY` | **附属源**（同上一批字段） |
| BOM 树页签 | **不过滤** | **主源**（边式全子件，与现网 `bom_view` 一致） |

**选了页签类型就等于选了 `characteristic`**，用户从不接触这个词。

##### 4.3.3.2.2 🚨 附属源必须编译成相关标量子查询，不能用 LEFT JOIN

**实测粒度差异**（`is_current` 口径）：

```
element_bom_item      : 4 行 / 3 个 (成品,材质) 键   ← 细粒度：一个材质挂多个元素
unit_price(来料加工费) : 2 行 / 2 个 (成品,材质) 键   ← 粗粒度：一个键一行
```

若用 `LEFT JOIN` 接附属源，同一笔费用会在主源的每一行上重复。显示正确，但：

> ⚠️ **一旦该列被勾为 `is_subtotal`，会被累加 N 次 —— 静默算错钱**。与 §3.8.3 铁律 3 的「闭包重复边导致小计翻倍」同类。

**强制规则**：附属源一律编译成**相关标量子查询**，禁用 `LEFT JOIN`。

```sql
(SELECT up.pricing_price FROM unit_price up
  WHERE up.finished_material_no = ebi.material_no
    AND up.code               = ebi.material_part_no
    AND up.price_type = 'INCOMING_MATERIAL_PROCESS'
    AND up.system_type = 'QUOTE' AND up.is_current
    AND up.customer_no = :customerCode
  LIMIT 1) AS _来料加工费
```

**一举两得**：① 结构上不可能让主源行数翻倍；② 天然满足 §3.6 铁律（版本化表禁进带 `is_current` 的 `LEFT JOIN ON`）。

**配套体检**：附属源金额列**默认 `is_subtotal=false`**；手动勾选 → **阻断保存**并说明「该值按主源粒度重复出现，累加将重复计算」。

##### 4.3.3.2.3 🌳 BOM 树页签的树契约（第四轮纳入本期）

与平铺页签是**两套契约**，编译器需额外承担三件事：

| 项 | 平铺页签 | BOM 树 |
|---|---|---|
| 输出 | `hf_part_no` + `_业务列` | **`material_no`(子) / `parent_no`(父)** + `_业务列` |
| 收窄 | `customer_no = :customerCode` | `component_no = ANY(:total_material_no)`，**禁用 `:customerCode`** |
| `characteristic` | 按页签类型过滤 | **不过滤**（边式全子件） |
| 附带产物 | 无 | 一条 `costing_bom_tree_config`（`usage='QUOTE'`） |
| 可编辑性 | 参与 B5 回填 | **只读**（见下） |

**编译器自动生成的两段**（手写时最易错，正是配置器价值所在）：

1. **根分支**：`UNION ALL` 一段取「无父边的成品自身」，列数与类型须与边分支**逐列对齐**（`NULL::text` / `NULL::numeric` / `NULL::varchar` 占位）；
2. **树配置**：建/更新 `costing_bom_tree_config` 记录。

> ⚠️ **BOM 树页签是只读的**：顶层 `UNION ALL` 使框架锚点注入降级（`anchorInjected=false`），该页签**不参与 B5 回填**。这是设计内的安全降级，**界面必须明示**，避免用户以为能在树上编辑。

##### 4.3.3.3.1 🚨 字段清单 = 该 Sheet **真实导入的列**，不是表的物理列（第五轮推翻重写）

**第四轮的「每个 Sheet 分组各自带全部列」是错的，本节整体作废重写。**

**问题**（2026-07-28 用户追问「全部列是什么意思」引出）：我把「全部列」定义成**数据库表的全部业务列**。但 `unit_price` 一张表被 **8 个 sheet 共用**，`element_bom_item` / `material_bom_item` 也各被多个 sheet 写。结果是：某个 sheet 的字段面板里混进了大量**别的 sheet 写的列**，对当前 sheet 永远是空值。

**实测偏差**（handler 实际写入列 vs 表物理业务列）：

| Sheet | 落表 | 表物理业务列 | **该 sheet 真实写入** |
|---|---|---|---|
| 成品其他费用 | `unit_price` | 28 | **5** |
| 自制加工费 | `unit_price` | 28 | **5** |
| 电镀费用 | `unit_price` | 28 | **5** |
| 来料固定加工费 | `unit_price` | 28 | **9** |

| 物料BOM | `material_bom_item` | 22 | **9** |

**正确规则**：

1. **字段清单 = 该 Sheet 的真实导入列**，数量落在 3~9 个 → **「常用列 / 全部列」两段折叠随之取消**，直接全部列出。
2. **中文名 = 用户 Excel 里的原列名**（「值」「比例」「货币」「计价单位」「基准值」「毛用量」），不是我按语义猜的名字。用户在配置器里看到的列名，与他手上那份导入模板**逐字一致**。
3. 键列（`material_no` / `component_no` / `code` / `finished_material_no` / `characteristic` / `price_type`）由页签类型推导，不作普通字段出现——它们以**码列**形态出现（可展开查名）。

##### 4.3.3.3.2 权威来源：新建 `QuoteSheetRegistry` 声明式登记（用户拍板）

报价侧目前**没有**核价侧 `PricingSheetRegistry` 那样的声明式登记，sheet 与列定义散落在 17 个 `Q*Handler` 里。本期新建 **`QuoteSheetRegistry`**：

- **登记内容**：每个 sheet 的 `sheetName` + 落表 + 判别式 + 每列的（DB 列 / **Excel 中文列名** / 类型 / 是否键列）。
- **提取方式**：从 handler 的 `put(DB列, row.get*("Excel列名"))` 配对自动提取初稿，**再逐个 handler 人工核实补全**（部分列用索引式或常量写法设置，正则提取不到，须人工补）。
- **一致性保障**：**单测双向断言**——handler 写入的列集合 ⊆ 登记；登记的非推导列 ⊆ handler 写入。改了 handler 忘记改登记 → 测试挂，避免「导入加了一列而配置器选不到」的静默漂移（核价侧 `PricingSheetRegistry` 已有同类镜像陷阱，见 memory `v6-handler-registry-mirror-trap`）。
- **消费方**：配置器字段目录 + 血统 `columnKey`（= sheet + 列）。

##### 4.3.3.3.3 🚨 实测校正：两张 sheet 的费用值不在 `pricing_price`

配字段时若按「费用 = `pricing_price`」的直觉去绑，**这两张 sheet 会配出一整列 NULL**（实测 `system_type='QUOTE' AND is_current`）：

|---|---|---|---|---|

| `FINISHED_MATERIAL_OTHER`（成品其他费用） | **0/4 全空** | 0 | **4/4 有值** | **比例**（利润/税率/管理费均为比例制，非金额） |

##### 4.3.3.3.4 🔑 关联规则：Sheet 附加维度 → 页签行粒度（第六轮补完，本方案的推导核心）

**关联条件不是逐对手工配的，而是由两层坐标推导的。** 这是「用户只选页签类型」能成立的最后一块拼图。

**第一层：每个 Sheet 登记「附加维度」**（相对于成品料号，这张 sheet 的行还按什么展开）——实测：

| Sheet | 附加维度 | 每成品行数（实测） |
|---|---|---|
| 物料主档/单重、客户料号关系 | 无 | 1 |
| **组装加工费** | +工序号 | **2**（焊接/铆接） |
| **成品其他费用** | +要素 | **4**（利润/外购件管理费/材料管理费/税率） |
| 自制加工费 | +零件料号 | — |
| 电镀费用 | +零件料号 +费用类型 | **2**（电镀加工费/电镀材料费） |
| 物料与元素BOM / 元素回收折扣 | +材质料号 +元素 | — |
| 物料BOM | +组成件料号 | — |
| 来料固定加工费 / 来料其他费用 | +投入料号 | 1 |

**第二层：页签行粒度 = 所选字段涉及各源「附加维度」的并集**，由用户搭配字段**动态决定**（用户 2026-07-28 定：「由用户决定怎么搭配字段」）。

> 主件页签因此是可变的：只选物料主档字段 → 每成品 **1 行**；选了组装加工费字段 → 按工序 **2 行**；选了成品其他费用字段 → 按要素 **4 行**。

**第三层：关联条件与 SQL 形态自动推导**

| 源与页签粒度的关系 | SQL 形态 | 理由 |
|---|---|---|
| **提供粒度**（被选中且附加维度进入页签粒度） | `JOIN <表> <别名> ON <成品级键对齐>`，其 `is_current` / `system_type` / 判别式放**顶层 WHERE** | 必须 JOIN 才能展开多行；**放顶层 WHERE 而非 JOIN ON 是 §3.6 铁律的硬要求**（版本化表进带 `is_current` 的 JOIN ON 会让 pending 改写产出畸形 SQL） |
| **粒度更粗**（附加维度是页签粒度的真子集） | **相关标量子查询** | 唯一取值，且天然规避 §3.6；值会在细粒度行上重复（正确行为，如产品名在每道工序行显示） |
| 同表同行（如元素回收折扣） | 直接取列 | 同一行的另一批列 |

**两条必须阻断的情况**（体检 err 级）：

1. **粒度冲突**：同时选了两个**互不包含**的附加维度（如「按工序展开」＋「按要素展开」）→ **笛卡尔积**，行数虚增、金额全错。
2. **粗粒度列勾小计**：粒度比页签粗的列会在每行重复，累加即**重复计算**（与 §4.3.3.2.2 附属源同类）。

> **这条规则同时解决了第五轮发现的「3 个附属源不唯一」**：成品其他费用（4 行）、电镀费用（2 行）、组装加工费（2 行）——它们不是要 `LIMIT 1` 硬取一行，而是**本来就该让页签变多行**。原设计用标量子查询 `LIMIT 1` 会静默取错值。

##### 4.3.3.4 连表规则：JOIN 降维成「码列的属性展开」（本方案的关键抽象）

**先看事实**。对现网 `cpq_db_0724` 全部 40 个 ACTIVE 视图做 JOIN 形态普查（2026-07-27 实测）：

| 被连表 | 出现次数 / 视图数 | JOIN 条件形态 |
|---|---|---|
| `material_master` | 33 / 21 | `mm.material_no = <某个料号列>` |
| `material_recipe` | 23 / 11 | `mr.code = <同一个料号列>`（总与上者成对做 COALESCE） |
| `process_master` | 15 / 12 | `pm.process_no = <某个工序号列>` |
| `material_customer_map` | 4 / 1 | `mcm.material_no = mm.material_no AND mcm.customer_no = :customerCode` |
| `bom_closure(_d)` / `material_bom_item` / `element_bom_item` | 17 / 4 | 闭包 CTE 内部（§3.8 模板，非用户可配） |
| `f_customer_element_price` | 4 / 1 | 价格策略表函数（固定形态） |

**关键结论**（三条，均为实测而非推断）：

1. **全语料没有一个「业务连表」，100% 是维表查名**——即「拿一个码去查它的名字/属性」。JOIN 条件右侧**恒为该维表的主键**，唯一变化的是左侧用哪个码列。
2. **JOIN ON 带附加谓词的：0 个**（唯一例外是 `material_customer_map` 的固定客户谓词）。§3.6「版本化表禁进 `LEFT JOIN ON`」铁律已被现网彻底遵守。
3. 相关标量子查询只出现在**闭包 CTE** 与 **BOM 树视图**（两者第四轮后均已模板化，由编译器生成）。5 类平铺页签的用户可配部分内为 0。

**因此规则定为**：用户**不配 JOIN，配的是「这个码要显示成什么」**。系统维护一张**查名维表登记表**（含用户点名要的材质库 / 工序库 / 元素库）：

| 库 / 维表 | 表 | 连接键（右侧恒定） | 可展开属性 | 附加谓词 |
|---|---|---|---|---|
| **物料主档** | `material_master` | `material_no` | 品名 `material_name`、标准单位 `standard_unit`、规格 | — |
| **材质库** | `material_recipe` | `code` | 材质名 `name`、符号 `symbol`、规格标签 `spec_label` | — |
| **工序库** | `process_master` | `process_no` | 工序名 `process_name`、工序类别、是否外协、标准单位/币种 | — |
| **元素库** | `element` | `element_code`（= **元素符号**，如 `Ag`/`Cu`） | 元素名称 `element_name`（银/铜/锌）、元素编号 `element_no` | — |
| **客户料号关系** | `material_customer_map` | `material_no` | 客户料号名称、客户产品编号、报价货币、汇率 | `customer_no = :customerCode`（固定注入） |

> **元素库连接键实测**：`element_bom_item.component_no` 存的是**元素符号**（`Ag`/`Cu`/`C`），对应 `element.element_code`；实测 JOIN 命中 83 行。**不是** `element_no`（`10001` 形态）——与 `AGENT §3.6`「JOIN 键 = 元素符号 `component_no`，非元素编号」一致。

配方里每个**码列**声明它可展开到哪些库，**多源时声明 COALESCE 优先级**（与 `AGENT §3.5` 逐字一致）：

| 页签类型 | 码列 | 可展开库（按优先级） | 生成的表达式 |
|---|---|---|---|
| 材质元素 | 材质料号 `ebi.material_part_no` | 材质库 → 物料主档 | `COALESCE(mr.name, mm2.material_name)` |
| 材质元素 | 元素符号 `ebi.component_no` | 元素库 | `COALESCE(el.element_name, ebi.component_no)` |
| 零件 | 零件料号 `up.code` | 物料主档 → 材质库 | `COALESCE(mm.material_name, mr.name)` |
| 零件 | 工序号 `up.operation_no` | 工序库 | `COALESCE(pm.process_name, up.operation_no)` |
| 外购件 | 组成件料号 `mbi.component_no` | 物料主档 → 材质库 | `COALESCE(mm.material_name, mr.name)` |
| 主件 | 销售料号 `mm.material_no` | 客户料号关系 | `mcm.customer_material_name` 等 |
| 费用类·电镀 | 电镀元素 `ps.plating_element` | 元素库 | `COALESCE(el.element_name, ps.plating_element)` |

**界面呈现**：可用字段是两层树，码列下挂它的属性——

```
▾ 常用列
    材质料号                 ← 码列本身（可拖，也可不显示只当 JOIN 键）
      ▸ 材质名称             ← 拖它 → 自动接 材质库 + 物料主档 双源
    元素
      ▸ 元素名称             ← 拖它 → 自动接 元素库（银 / 铜 / 锌）
    工序号
      ▸ 工序名               ← 拖它 → 自动接 工序库
```

用户拖「材质名称」，编译器自动追加所需 `LEFT JOIN`、去重（同一维表被多列展开时只 JOIN 一次并分配独立别名）、生成 COALESCE 表达式。**「JOIN」这个词不出现在界面任何位置。**

> **逃生舱判据（写入界面帮助）**：若某列需要的不是「码 → 单值属性」，而是**真正的业务关联**（返回多行需聚合 / 需条件筛选 / 跨事实表关联），配置器不支持 → 转手写 SQL。现网 6 类页签语料中此类需求为 **0**，属低频长尾。

##### 4.3.3.5 配方注册表的落地形态

不落 DB 表——配方内含铁律逻辑（闭包 CTE 骨架、pending 规避的标量子查询写法），本质是代码而非数据，落 DB 反而无法单测、无法随版本演进。

每条配方声明：数据源（落表 + 判别式）+ 锚点列 + 页签类型 + 固定 WHERE + 常用列清单（key / 中文名 / SQL 表达式 / 推荐 field_type / is_amount / is_subtotal）+ 各码列的可展开库 + 支持的开关。

**「全部列」的构成** = 数据源表全部物理列 ＋ 各码列可展开的库属性（§4.3.3.4），**不是**一个扁平的跨表列池——每一列都能追溯到「它从哪个码展开而来」，这正是编译器能自动接对 JOIN 的前提。

**中文名来源**（不新建需人工长期维护的元数据表）：

1. 配方常用列 —— 配方定义自带（本来就要写）；
2. 其余物理列 —— 优先复用已有登记：`PricingSheetRegistry`（已含 `unit_price` / `element_bom_item` / `material_bom_item` 等表的中文列名 + 类型）、V6 导入 handler 的 Excel 列名映射；
3. 仍缺失 —— 回落显示物理列名 + 数据类型，并允许在配方定义里就地补一条。

#### 4.3.3.6 🚨 列改名的影响面：同步 6 处 + 冻结单阻断（第七轮补，原方案缺口）

「已选输出列」的列名可由用户直接编辑。因「一体化」设计使列名同时是**视图别名 + 字段名 + 绑定路径**，改名影响面远超 SQL 本身。

**实测：全链路没有一处用稳定 ID，全部以中文字段名为 key**（`cpq_db_0724`，2026-07-28）：

| 引用方 | 实际存储形态 |
|---|---|
| 报价单快照 `snapshot_rows.driverRow` | `{"_销售料号": "S-3120014539", "_汇率": 6.9755}` ← 视图别名做 key |
| 报价单快照 `snapshot_rows.basicDataValues` | `{"{$cp_view._销售料号}": "..."}` ← **完整路径字符串**做 key |
| 公式 token | `{"type":"field","value":"单价"}` |
| 组件行键 `row_key_fields` | `["料号","材质","元素"]` |
| `part_no_field` / `part_name_field` / `sort_field` | `"销售料号"` / `"项次"` |
| 跨页签引用 `cross_tab_ref.match` | `[{"a":"料件","b":"料件"}]` |

**规则一：改名时配置器必须在同一事务内同步 6 处**

1. 视图 SELECT 别名 `_旧名` → `_新名`；2. 组件字段 `name`；3. 字段 `default_source.path`；
4. 组件级属性（`rowKeyFields` / `partNoField` / `partNameField` / `sortField`）；
5. **本组件公式** token 的 `value`；6. **其他组件**的 `cross_tab_ref.match` 与模板 Excel 列引用。

> 前 3 处是一体化设计本就保证的；**后 3 处是第一~六轮方案的缺口**，漏了会让公式/跨页签引用静默断裂（求值取不到字段 → 该格空或 `#ERROR`）。

**规则二：已有报价单快照改不了 → 按引用状态分三档**

| 场景 | 处理 |
|---|---|
| 新建视图、尚未保存 | 随便改，零影响 |
| 已保存、无报价单引用 | 自动同步 6 处后保存，安全 |
| 被 **DRAFT** 报价单引用 | 允许改名，保存后自动 `refresh-snapshot` 重刷这些草稿单 |
| 被**冻结单**（`SUBMITTED`/`APPROVED`/`PUBLISHED`）引用 | **阻断改名**。冻结快照是历史凭证，其 key 为旧名且不可重刷；强行改名会让旧单该列渲染成空 |

**界面**：改名输入框失焦时即扫描影响面，在体检区显示「本次改名将同步 N 处引用；影响 M 张草稿单（保存后自动重刷）」；命中冻结单则变 **err 级阻断**并列出单号。

> **根治方案（本期不做）**：渲染层改用稳定 `fieldKey` 而非中文名做 key。代价极大——要迁移全部历史 `snapshot_rows` / `row_data` / 公式 token，且触及 AP-44 协议面。登记 Backlog。

#### 4.3.4 编译器（`SqlViewBuilderCompiler`，后端）

`builder_config` → SQL 文本。**下列铁律由编译器内建，用户无从违反**：

| 铁律 | 来源 | 编译器保证 |
|---|---|---|
| 业务列一律 `_` 前缀 | `3-SQL视图.md §3.2` | 别名统一生成 `_<中文列名>` |
| `hf_part_no` 是唯一不带 `_` 的列 | §3.2 | 驱动键固定别名 `hf_part_no` |
| 价格策略列别名不带 `_`、逐字等于字段名 | `AGENT §3.6` | 价格策略列走独立别名规则 |
| 价格策略必 `LEFT JOIN`、禁 `COALESCE(...,0)` | `AGENT §3.6` | 模板固定，无开关 |
| 版本化表禁进带 `is_current` 的 `LEFT JOIN ON` | §3.6 | 一律生成相关标量子查询 |
| 闭包递归用 `UNION`（非 `UNION ALL`）+ `(root,node)` 二次去重 | §3.8.3 铁律 3 | 闭包 CTE 模板固定 |
| 白名单表必须在顶层 `FROM` | §3.8.3 铁律 1 | 闭包 CTE 只做 `LEFT JOIN`，顶层永远是白名单表 |
| `LEFT JOIN` + `COALESCE(cl.root_no, 本表料号)` 兜底 | §3.8.3 铁律 2 | 模板固定 |
| 不生成 `ORDER BY`（DRAFT 下失效） | §3.6 附带坑 | 改为自动设置组件 `sort_field` |
| 禁 V44/V76 废弃表 | AP-53 | 配方只引 V6 表；仍过 `SqlViewValidator` 二次把关 |
| 中文标识符须 ASCII 别名 | §3.4 | 中文只出现在别名位置，不做标识符 |

`required_variables` 由编译产物反推（复用 `SqlViewValidator.extractNamedParams`），不由用户填。

#### 4.3.5 一体化保存（单事务）

```
编译 SQL → dry-run 校验 → 体检清单 → 写 component_sql_view(sql_template + builder_config)
  → 同步组件 fields[]（按 columns[].fieldKey 增 / 改 / 删）
  → 写 default_source = {type:'BASIC_DATA', path:'$<view>._<列名>'}（逐字对齐，永不失配）
  → 回填 tabType / partNoField / partNameField / rowKeyFields / sortField
  → PUT driver-view（data_driver_path = $<view>）
  → 刷新引用方模板 snapshot（复用 refreshSnapshotsByComponent）
```

**字段权威划分（用户确认）**：

| 字段来源 | 判定 | 「取数配置」Tab | 「字段配置」Tab |
|---|---|---|---|
| BUILDER（key 出现在 `builder_config.columns[].fieldKey`） | 由配置器产出 | 可增删改名、改类型、改取数 | 只能改**展示属性**（列宽 / 顺序 / 小数位 / 公式引用 / Excel 列）；字段名、类型、`default_source` 只读 |
| MANUAL（其余字段：手工加的、公式列） | 不受配置器管辖 | 不显示 | 完全可编辑，**不会被同步删除** |

#### 4.3.6 真实数据预览

- 入参：`customerNo` + `partNo`（料号支持在该客户已导入数据里搜索）。
- 执行：后端用真实 `:customerCode` / `:priceBaseDate` 绑定跑编译产物，**只读连接 + `LIMIT 50` + 5s 超时**，模拟框架的 `hf_part_no` 隐式注入以还原真实收窄效果。
- 返回：行数 + 各列值 + 空值高亮。
- **返 0 行必须给可操作诊断**，而非沉默：
  - 该客户下无此类基础数据 → 提示先导入；
  - 料号在该客户下不存在 → 提示换料号；
  - 该料号数据挂在子件上 → **提示勾选「子件数据也要」**；
  - 价格策略未配 → 提示元素单价将为空（不掉行属预期）。

#### 4.3.7 体检清单（保存前自动跑，可阻断/可告警）

| 检查 | 级别 | 依据 |
|---|---|---|

| 列名在本组件内重复（如「全部列」拖入与常用列同名的列） | 阻断 | 列名同时是字段名与视图别名，重复会导致别名冲突与字段撞名，须改名后才能保存 |

#### 4.3.8 列的「血统」：本期只记录，不改公式引擎（第三轮澄清）

配置器为每一列天然持有**血统**（`builder_config.columns[].columnKey` —— 这列从哪个码列 / 哪个库属性 / 哪个附属源而来）。这为跨页签公式带来一个优化机会，但**本期不实施**。

**现状（已核实）**：

| 环节 | 现状 | 失效模式 |
|---|---|---|
| 匹配对配置 | `cross_tab_ref.match = [{a:'字段名', b:'字段名'}]`，用户在 `CrossTabRefDrawer` 手工一对对配 | 纯人工，易错 |
| 可行性判定 | `formulaSerialize.ts:700` 的 `comparable(rkf_a, rkf_b)`，比较**行键字段名字符串集合**是否互为子集（后端 `RowKeyCompare.java` 为镜像） | ① 同实体不同叫法（「材质」vs「材质名称」）→ 明明可对齐却判不可比；② 异实体同名（两页签都有「名称」）→ 误判可对齐，**静默匹配错行** |

**本期范围（用户拍板）**：**只忠实记录血统，不动跨页签公式的任何代码**。理由：`comparable()` 位于公式校验链路（报价渲染主链路），改它需配套 E2E 回归，风险面超出「取数配置」本身。血统数据一旦积累，下期做优化时直接可用。

**下期可做的优化（已登记 Backlog）**：① 打开跨页签抽屉时按血统**自动推荐匹配对**；② `comparable()` 改为**血统集合**子集判定；③ 不可对齐时给出业务化原因（「本页签行键=材质料号，目标页签行键=零件料号，两者不同源」）；④ 存量手写视图无血统 → 回落字符串匹配，行为逐字不变。

## 8. 验收标准

1. **材质元素基础配方**：拖入 材质 / 元素 / 组成含量 / 损耗率 / 毛重 / 元素单价 6 列，勾「材质」为行键、勾「接价格策略」→ 保存成功。生成的 SQL 含 `AS hf_part_no`、5 个 `_` 前缀别名、元素单价与货币两列**不带** `_`、含 `LEFT JOIN f_customer_element_price(:customerCode, :priceBaseDate)` 且**无** `COALESCE(...,0)`。
2. **三件套一致性**：上条保存后，组件 `fields[]` 恰好 6 项（+ 价格策略带出的货币列），每项 `default_source.path` 与视图输出列名**逐字一致**；`rowKeyFields = ["材质"]`；`data_driver_path = $<view>`。
3. **子件闭包**：勾「子件数据也要」→ 生成 SQL 含 `WITH RECURSIVE` + `UNION`（**不是** `UNION ALL`）+ `(root_no,node_no)` 去重 CTE + `LEFT JOIN` + `COALESCE` 兜底；顶层 `FROM` 是 `element_bom_item`（白名单表）。
4. **码列属性展开（连表）**：在材质元素页签拖入「材质料号 ▸ 材质名称」→ 生成 SQL 自动出现 `LEFT JOIN material_recipe` 与 `LEFT JOIN material_master`，表达式为 `COALESCE(mr.name, mm2.material_name)`；再拖「元素 ▸ 元素名称」→ 自动接 `LEFT JOIN element el ON el.element_code = ebi.component_no`，预览中 `Ag` 显示为「银」。零件页签拖「工序号 ▸ 工序名」→ 自动接 `process_master`。**界面全程未出现 JOIN 字样**；同一维表被两个码列展开时只 JOIN 一次或分配互不冲突的别名，生成 SQL 无重复 JOIN、无别名冲突。
5. **附属源自动关联（★ 第三轮新增，第一版模型配不出的用例）**：页签类型只选「材质元素」，不做任何数据源选择 → 可用字段里同时出现主源列（组成含量、损耗率…）与附属源列（来料加工费）。拖入「来料加工费」→ 生成 SQL 中该列是**相关标量子查询**（`(SELECT up.pricing_price FROM unit_price up WHERE up.finished_material_no = ebi.material_no AND up.code = ebi.material_part_no AND up.price_type='INCOMING_MATERIAL_PROCESS' AND up.is_current LIMIT 1)`），**不得出现 `LEFT JOIN unit_price`**；预览行数与不加该列时**完全一致**（不翻倍）。
6. **附属源小计防呆**：把「来料加工费」勾为小计 → 出现强告警，说明该值按主源粒度重复出现、累加将重复计算。
7. **物料BOM 分流**：页签类型选「外购件」→ 生成 SQL 自动含 `characteristic = 'OUTSOURCED'`；选「BOM 树」→ **不含任何 characteristic 过滤**；界面上没有任何让用户选 characteristic / 选 sheet 的控件。
8. **主件的客户收窄特例**：页签类型选「主件」→ 生成 SQL 含 `JOIN material_customer_map mcm ON mcm.material_no = mm.material_no AND mcm.customer_no = :customerCode`，且**不含** `mm.is_current` / `mm.system_type`（该表无这两列，写了会报错）。
9. **字段清单 = Sheet 真实导入列**：任取 3 个页签，其可用字段面板中的字段数与 `QuoteSheetRegistry` 登记的该 sheet 列数**完全相等**；界面上**不存在**「全部列」之类的二级折叠；字段中文名与导入模板 Excel 表头**逐字一致**（抽查「计价单位」「比例」「值」「毛用量」四列）。
10. **登记一致性单测**：`QuoteSheetRegistry` 与 17 个 `Q*Handler` 的双向断言测试通过；人为在某 handler 加一个 `put` 而不改登记 → 测试**必须失败**。
11. **费用值绑列正确**：费用类页签默认绑「基准值」（非「值」）、主件页签的成品其他费用默认绑「比例」（非「值」）；预览返回非 NULL。人为改绑 `pricing_price` → 预览整列 NULL 且给出「疑似绑错列」诊断。
12. **★ 行粒度动态推导（核心规则）**：主件页签只选物料主档字段 → 预览 **1 行**；加选「组装加工费」的字段 → 顶部粒度提示变为「成品 + 工序号」、预览 **2 行**（焊接/铆接）、生成 SQL 含 `JOIN capacity ca ON ca.material_no = mm.material_no` 且 `ca.is_current` 出现在**顶层 WHERE 而非 JOIN ON**（§3.6 铁律）；改选「成品其他费用」的字段 → 粒度变「成品 + 要素」、预览 **4 行**（利润/外购件管理费/材料管理费/税率）。
13. **粒度冲突阻断**：同时选「组装加工费」与「成品其他费用」的字段 → 体检出现「粒度冲突」**err 级**提示，保存按钮禁用。
14. **粗粒度列小计阻断**：粒度为「成品+工序号」时，把产品级的「单重」勾为金额+小计 → **阻断**，提示该值会在每行重复计算。
15. **费用类双源查名**：页签类型选「费用类」→ 生成 SQL 含 `price_type IN ('INCOMING_MATERIAL_PROCESS','INCOMING_MATERIAL_OTHER')`；拖「投入料号 ▸ 投入料号名称」→ 表达式为 `COALESCE(mm.material_name, mr.name)`（双源兜底），且同时接上 `material_master` 与 `material_recipe` 两条 LEFT JOIN。只拖单个 sheet 的字段时 `price_type` 收窄为单值。
16. **列改名影响面**：改一个已被引用的列名 → 保存后 ① 视图别名、字段名、`default_source.path`、`rowKeyFields`/`partNoField`/`sortField`、本组件公式 token、其他组件 `cross_tab_ref.match` **六处全部同步**；② 被 DRAFT 单引用时自动重刷其快照且该列有值；③ 被冻结单引用时**阻断改名**并列出单号。
17. **BOM 树契约**：页签类型选「BOM 树」→ 生成 SQL ① 输出 `material_no` 与 `parent_no`、**不输出** `hf_part_no`；② 用 `component_no = ANY(:total_material_no)` 收窄、SQL 正文**不含** `:customerCode`（注释中出现不算，§3.7 已屏蔽）；③ 含 `UNION ALL` 根分支且两侧列数相等、类型逐列对齐；④ 保存后 `costing_bom_tree_config` 新增/更新一条 `usage='QUOTE'` 记录；⑤ 界面明示该页签只读（不参与 B5 回填）。
18. **真实预览**：选罗克韦尔 + 料号 `S-3120014539`，不勾闭包返 2 行、勾闭包返 4 行（§3.8.6 实证基准）。
19. **0 行诊断**：换一个无数据的客户 → 预览返 0 行且给出「该客户下无此类基础数据」提示，而非空表格。
20. **体检拦截**：把「元素单价」误勾为小计 → 保存前出现告警（单价类不可累加）；料号列与名称列都不配 → 保存被阻断。
21. **★ Golden 用例**：用配置器从零配出「材料成本」组件，与现网手写版 `COMP-0027` 在同一张报价单上 `refresh-snapshot` 后，`quotation_line_component_data.snapshot_rows` **逐行等值**。
22. **删除影响面**：删除一列 → 二次确认列出受影响模板；确认后字段 / 视图列 / 绑定三者同步消失，模板 snapshot 已刷新。
23. **存量不受影响**：任取 3 个存量手写视图，打开仍是手写编辑器、SQL 逐字不变、渲染结果不变。
24. **脱钩不可逆**：builder 视图点「转为手写 SQL」→ 二次确认 → `builder_config` 清空，此后按手写视图行为；再打开取数配置 Tab 显示引导页而非旧拖拽态。
25. **自检声明**：TS 0 错误；改动的 `.tsx` 经 Vite 200；后端端点非 500；Flyway `success=t`。字段类型枚举未改动 → 不触发 AP-44 E2E 强制项（须在 PR 中显式声明并附 `field_type` 相关 grep 证据）。
