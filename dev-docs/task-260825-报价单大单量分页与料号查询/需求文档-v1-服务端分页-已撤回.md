## ① 背景与目标

**谁的问题**：销售/财务在处理 2000 笔产品级别的大单报价时，系统实质不可用。

**三个客观症状**：

| 症状 | 现状数据 |
|---|---|
| 浏览器吃不消 | 2000 笔产品的报价单，Chrome 堆内存占用 **1.5–2 GB** |
| 首存超时 | 批量导入料号后首次保存，`PUT /quotations/{id}/draft` 整单全量提交 → 撞前端 axios 30s + Narayana 60s 事务 reaper |
| 找不到东西 | 2000 张卡片顺序平铺，没有任何查询手段，找一个料号只能滚 |

**不做会怎样**：大单量客户（现网已有 1845 行实例）无法通过系统报价，只能退回 Excel 线下作业。

**目标**：把「产品卡片」作为分页单元，让**取数、渲染、保存**三条链路都按页进行，并补上料号模糊查询。

## ③ 验收标准（AC）

### A. 服务端分页（读侧）

- **AC-1** 打开 2000 行报价单编辑页，默认只请求并渲染 100 行。断言：响应 `pagination = {page:1, size:100, total:2000, totalPages:20}`；DOM 中产品卡片元素数 **== 100**。
- **AC-2** 页大小切至 200 / 500，立即重取并渲染对应行数。断言：三档各截一图 + 响应 `pagination.size` 逐档匹配，卡片数分别 == 200 / 500。
- **AC-3** **不带** `page` 参数调 `GET /quotations/{id}`，`lineItems` 仍返回全量 2000 行。断言：`lineItems.length == 2000` 且响应体与改动前逐字节一致（老调用方零影响）。
- **AC-4** 核价工作台 `GET /costing-orders/{coid}?page=1&size=100` 分页可用，参数名与响应形态与报价侧**完全一致**。断言：两个端点响应的 `pagination` 对象键名与类型逐一相同。
- **AC-5** 报价单详情页（只读）翻页期间，不得触发任何**修改业务数据**的接口（`saveDraft` / `editCardValue` / `calculateDiscount` / `submit` …）。**唯一允许**的非 GET 请求是按页幂等物化 `POST /{id}/ensure-card-values`，且其作用范围必须 ⊆ 当前页。断言：翻 5 页，非 GET 请求只允许出现 `ensure-card-values`，逐条核对其请求范围。
  > ⚠️ **本条原措辞为「PUT/POST 请求数 == 0」，与 F-H「物化改按页触发」自相矛盾**（翻到未物化的页必然要调 `ensure-card-values`），2026-08-25 由用户提问触发发现并改写。
  > 📌 现状基线：详情页加载 1845 行**实测非 GET 请求 = 0**（见证据文件），故本条护栏的判据是「不许**新增**业务写」，不是「不许有任何 POST」。

### B. 三视图同步

- **AC-6** 编辑页停在第 N 页时，报价侧、核价侧、Excel 视图渲染的**料号集合逐一相同**。断言：三视图各导出当前页料号列表，逐条比对 100/100 命中，无多无少。
- **AC-7** 切页后三视图同步切换，无需手动刷新。断言：切到第 3 页后立即切视图，三处料号集合仍逐一相同。

### C. 料号模糊查询

- **AC-8** 输入料号片段，跨全单匹配 `customer_product_no` / `product_part_no` / `customer_part_name` 三字段（ILIKE `%q%`），命中行再分页。断言：`pagination.total` == 命中行数（**不是 2000**），且用同条件 SQL 直查计数逐一相等。
- **AC-9** 查询命中 0 行时显示空态，不报错、不白屏。断言：截图 + console 无 error。
- **AC-10** 查询状态下翻页正确。断言：第 2 页返回的是命中集合的第 101–200 行（与 SQL `ORDER BY sort_order OFFSET 100 LIMIT 100` 逐行相等）。
- **AC-11** 清空查询回到全量分页。断言：`pagination.total` 回到 2000。

### D. 白名单保存（写侧，本次最高风险）

- 🚨 **AC-12** `partial=true` + `lineItemIds=[本页 100 行]` 保存后，**名单外 1900 行的 `row_data` / `snapshot_rows` / `quote_card_values` / `quote_excel_values` / `sort_order` 逐字节不变**。断言：保存前后对这 1900 行做 SQL 快照，`diff` 输出为空。
- **AC-13** **不传** `scope` 时行为与改动前完全一致。断言：同一份 payload 在改动前后各存一次，两次的库状态 `diff` 为空。
- **AC-14** `partial` 下删除当前页某行，只删该行。断言：`SELECT count(*)` 从 2000 → 1999，且名单外行数不变（1900 == 1900）。
- **AC-15** `partial` 下新增行（无 id），落库并返回新 id，`sort_order` 按**页内相对位置**写入；**名单外行的 `sort_order` 一个都不变**。断言：新增前后对名单外 1900 行的 `(id, sort_order)` 做 diff，输出为空。
- **AC-16**（基线 §4.7 硬约束）`partial` 保存**不得覆盖名单外行的 `quote_excel_values`**。断言：包含在 AC-12 的 diff 中，单独列出该列的比对结果。

### E. 分批提交（首存）

- **AC-17** 批量导入 2000 个料号后首存，前端按下述**批次规则**串行提交。断言：**任一单次请求耗时 < 30s**，且后端日志全程**无 `ARJUNA012117`**（reaper 强杀标记）。

  **批次规则（2026-08-25 补，原 AC 未定义此项）**：

  | 项 | 规则 |
  |---|---|
  | 切分依据 | 前端 `lineItems` 数组**按序切片**（导入顺序 == `sortOrder` 序）：第 k 批 = `slice(k·B, (k+1)·B)` |
  | **批边界固定** | 首存开始时**一次性算定并冻结**；重试**不重新切分**（否则断点续传对不上批号） |
  | 批大小 `B` | 默认 **100**，**与页大小解耦**、可配（用户 2026-08-25 确认沿用默认值） |
  | 串行 | 前一批**响应返回**后才发下一批。🚫 **不许并发** —— 会撞 `savingRef` 在飞守卫（`QuotationWizard.tsx:295`）与后端 OptimisticLock |
  | 每批 payload | `scope.partial=true` + 该批行；**表头字段（客户 / 模板 / 交易条款）只在第 1 批传**，后续批不重复写整单字段 |
  | 幂等键 | 前端 `tempId`（复用 `QuotationWizard.tsx:273` 既有映射表）；重试同批按 `tempId` 匹配已落库行 → upsert，不重复插入 |
  | 失败即停 | 第 k 批失败**立即停止**，不继续发 k+1（否则 `sortOrder` 出洞） |

- **AC-17b** `B` 的取值有实测依据。断言：首存实现完成后，在 1845 行单上对 `B ∈ {50, 100, 200}` 各测一轮，记录单批耗时与事务时长，把选定档位与依据写入 `test-report.md`。
- **AC-18** 首存过程显示进度。断言：截图显示「已存 X / 2000」且 X 单调递增至 2000。
- **AC-19** 人为让第 7 批失败（注入异常），前端提示已存行数，重试**只发未成功批次**。断言：重试请求的 payload 行数 == 未成功批次行数（不是 2000）。
- **AC-20** 断点续传后无重复行。断言：`SELECT count(*), count(DISTINCT id) FROM quotation_line_item WHERE quotation_id=?` 两值相等且 == 2000；且按料号分组无非预期重复。
- **AC-21** 分批完成后 2000 行全部有 id 且卡片值状态一致。断言：`SELECT count(*) FROM quotation_line_item WHERE quotation_id=? AND id IS NULL` == 0。

### F. 总额增量合成

- **AC-22** GET 响应含 `totals{originalAmount, totalAmount}` + 全量 `lineSubtotals:[{id, subtotal}]`。断言：`lineSubtotals.length == 2000`，且 `Σ lineSubtotals[].subtotal == totals.originalAmount`（十进制逐位相等）。
- 🚨 **AC-23** 在当前页改一个影响小计的单元格，**总额立即变化且 delta 精确等于该行小计 delta**。断言：记录改前总额 A、改后总额 B、该行小计改前 a 改后 b，断言 `B - A == b - a`（十进制逐位相等，不是「变了就行」）。
- **AC-24** 跨页编辑正确。断言：改第 1 页某行 + 翻到第 3 页改另一行，总额 == 服务端基数 − 两行旧值 + 两行新值（逐位相等）。
- **AC-25** 保存成功后覆盖表清空，显示值 == 服务端 `totals.originalAmount`。断言：两值逐字节相等。
- **AC-26** **只翻页不编辑时总额全程不变**（防跳数）。断言：连续翻 20 页，每页记录总额显示值，20 个值逐字节相同。
- **AC-27** `handleCalculateDiscount` 不再传前端算的金额，改后端自算。断言：F12 抓包，`calculateDiscount` 请求体**不含** `originalAmount`；且分页模式与全量模式算出的 `finalDiscountRate` 逐位相等。

### G. 按页物化

- **AC-28** `ensureCardValues` 按页触发，只物化当前页未物化行。断言：开 Hibernate `Statistics`，**SQL 条数与页大小成正比、与总行数无关**（100 行页与 500 行页各测一次，条数比 ≈ 1:5；换 2000 行单不改变单页条数）。
- **AC-29** `ensureExcelValues` 同上，单次事务不超时。断言：单次请求 < 30s 且无 reaper 日志。

### H. 比对视图

- **AC-30** 比对视图独立按 partNo 分页。断言：`pagination.total` == 该单去重后料号数（与 `SELECT count(DISTINCT part_no)` 相等）。
- **AC-31** 比对视图翻页不影响编辑页页码。断言：编辑页停在第 3 页 → 切比对视图翻到第 5 页 → 切回编辑页仍在第 3 页。
- 🚨 **AC-31a**（裁决甲）**料号过滤下沉后端**：搜索一个位于**第 1200 位**的料号，必须命中。断言：`pagination.total == 1`，且返回行的 `partNo` 与搜索词匹配。
  > 现状反例：前端 `comparisonMapping.ts:149-153` 的 `filterRowsByPartNo` 只在**已加载行**里 `includes` —— 服务端分页后只在当前 10 行匹配 → 显示「暂无匹配的销售料号」，用户会误判料号不存在。
- 🚨 **AC-31b**（裁决甲）**「差异料号前置」下沉后端**：构造一个差异料号位于**第 900 位**，勾选「差异料号」开关后它必须出现在**第 1 页**。断言：第 1 页返回行中包含该 partNo。
  > 现状反例：`ComparisonBoard.tsx:85-88` + `comparisonMapping.ts:133-146` 的 `sortRowsDiffFirst` 是**全集重排序**；分页后只在当前页 10 行内重排 → 开关等于失效。
  > ⚠️ 兼容既有 AC：task-0717 `test.md:124 (B-SORT-03)` 要求「勾选后总料号数与关闭前**相同**，非差异料号仍可见」→ 后端必须实现为**排序**而非过滤。
- 🚨 **AC-31c**（裁决甲）**料号总数下沉后端**：工具栏「共 N 个销售料号」与分页器 `total` 必须取服务端值。断言：1845 行单上显示「共 1845 个」，分页器页数 == `ceil(1845 / pageSize)`。
  > 现状反例：`ComparisonBoard.tsx:89-90` `totalParts = sortedRows.length` 取本地数组长度 → 服务端分页后显示「共 10 个」，1835 个料号永久不可达。
- **AC-31d** 比对视图分页**排序确定性**：连续翻完全部页，所有页返回行的并集 == 全量料号集合，**无重复、无遗漏**。
  > 依据：`QuotationService.java:2681` 的 `ORDER BY sortOrder ASC` **无 tiebreaker**，且 `sort_order` 上无唯一索引。本单实测 1845 个值全唯一，但 `saveDraft` 重建可能产生同值 → **下沉 SQL 分页必须补 `ORDER BY sort_order, id`**，否则跨页重复 + 丢行且静默。

### I. 分页连带修复

- **AC-32** 提交返回行键冲突时，点击冲突项能**跨页跳转**到目标产品卡片。断言：构造冲突卡片落在第 17 页，点击冲突项后页码自动切到 17 且该卡片高亮可见。

### J. 性能（判据 = 单次请求不撞墙 + 内存上限）

- **AC-33** 2000 行单全流程中，**任一单次请求 < 30s 且后端日志无 `ARJUNA012117`**。断言：打开 / 翻页 / 查询 / 保存 / 首存分批，逐项列出实测耗时。
- **AC-34** 1845 行单在**分页模式**下打开编辑页并进入 Step2 后：`usedJSHeapSize` **< 250 MB** 且 DOM 节点数 **< 10,000**。
  **测量口径必须与基线一致**（否则数字不可比）：headless Chrome + `--enable-precise-memory-info`、测量前强制 GC、同一台机器、页大小 100。

  | | 现状基线（实测） | 分页后要求 | 推算值 |
  |---|---|---|---|
  | `usedJSHeapSize` | **585.3 MB** | **< 250 MB** | ≈ 182 MB |
  | `totalJSHeapSize` | 827.0 MB | —（仅记录） | — |
  | DOM 节点 | **83,319** | **< 10,000** | ≈ 4,500 |
  | `<input>` 数 | 9,230 | —（仅记录） | ≈ 500 |

  > 基线含义：159.3 MB 是**与行数无关的基座**（路由 / antd / 模板结构 / 全局变量），故分页收益只作用于
  > `585.3 − 159.3 = 426 MB` 这部分。阈值 250 MB 在推算值 182 MB 上留了约 37% 余量。
  > ⚠️ 实测为 headless、无 DevTools、强制 GC 后的**下界**；用户报告的 1.5–2 GB 是带 DevTools 的长时交互态。

## ⑧ 方案要点（供 `fronttask.md` / `backtask.md` / `api.md` 展开）

### 读侧契约

```
GET /api/cpq/quotations/{id}?page=&size=&q=
GET /api/cpq/costing-orders/{coid}?page=&size=&q=

响应新增：
  pagination:    { page, size, total, totalPages }
  totals:        { originalAmount, totalAmount }          # 整单，服务端权威
  lineSubtotals: [{ id, subtotal }, ...]                  # 全量、sortOrder 序、约 120 KB
不传 page → 保持现状全量（老调用方零影响）
```

### 写侧契约

```
PUT /api/cpq/quotations/{id}/draft
  body 新增: scope: { partial: true, lineItemIds: [...] }
  partial=true  → 只在「白名单 ∪ 本次新增行」内 upsert/删除，名单外一律不碰
  partial 缺省  → 现状整单语义
  硬约束: partial 下 sortOrder 不许整单重排，只按页内相对位置写回
```

### 增量合成公式

```
显示原价 = totals.originalAmount
         − Σ( lineSubtotals[id] for id ∈ dirty )    # 减掉这些行的服务端旧值
         + Σ( dirty[id] )                            # 加上前端实时值

dirty: Map<lineItemId, 实时小计>，跨页保留；保存成功后按响应清除对应项
```

### 分批提交

批大小与页大小**解耦**（默认 100，可调）；串行调用 `PUT /draft (partial=true)`；每批一个后端事务；幂等去重靠前端 `tempId`（复用 `QuotationWizard.tsx:273` 既有映射表）。
