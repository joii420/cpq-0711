## ① 背景与目标

**用户实拍**：Chrome 标签页提示「**内存用量高：5.2 GB**」（`证据/shot_20260826_230657.png`）。

**实测的规模成本**（1845 行报价单，编辑页 Step2，headless + 强制 GC 后的**下界**）：

| 指标 | 1 行单 | **1845 行单** | 每行成本 |
|---|---|---|---|
| JS 堆 used / total | 57.2 / 132 MB | **601.6 / 853.9 MB** | ≈ 295 KB |
| **DOM 节点** | 584 | **146,231** | ≈ 79 个 |
| **LayoutObjects**（渲染树） | 416 | **138,686** | ≈ 75 个 |
| **JS 事件监听器** | 247 | **24,626** | ≈ 13.2 个 |
| `<table>` / `<input>` | 1 / 11 | **1,845 / 9,230** | 1 / 5 |
| Step2 渲染耗时 | — | **32.0 s** | ≈ 17 ms |

**5.2 GB 与实测 853.9 MB 的差距解释**：`performance.memory` 只统计 JS 堆，而 **DOM 节点 / 渲染树 / 事件监听器的内存在 JS 堆之外**，Chrome 的标签页内存统计包含它们；且实测是「加载完立刻强制 GC、零交互」的下界，用户值是长时间真实编辑后的累积。

**内存构成拆解**（据 1 行单基座 58 MB 反推）：

| 组成 | 大小 | 占比 |
|---|---|---|
| 基座（路由 / antd / 模板结构 / 全局变量） | 58 MB | 10% |
| 数据常驻（1845 行 `lineItems`） | 101 MB | 17% |
| **渲染（1845 张卡片）** | **426 MB** | **73%** |

**目标**：渲染占 73%，前端分页把当页压到 100 行即可砍掉其中 94%。**不改任何服务端契约。**

**不做会怎样**：大单量客户（现网已有 1845 行实例）打开报价单编辑页即占用数 GB 内存，浏览器濒临崩溃，且无任何手段定位单个料号。

### F. 性能（本任务的核心判据）

- 🚨 **AC-19** 1845 行单编辑页 Step2，**分页模式下**：
  **测量口径必须与基线一致**：headless Chrome + `--enable-precise-memory-info`、测量前强制 GC、同机、每页 100。

  | 指标 | 现状基线（实测） | 要求 | 推算值 |

  | **LayoutObjects** | **138,686** | **< 15,000** | ≈ 7,900 |

- 🚨 **AC-20** 泄漏护栏（**本任务最容易被忽略、后果最严重的一条**）：连续翻 20 页后回到第 1 页并强制 GC，JS 堆 / DOM 节点 / 事件监听器**必须回到第 1 页的基线水平**，不得单调上升。

  > ⚠️ 若本条不达标，说明除规模问题外**另有真泄漏**，须停下来报告并另立任务，不得靠分页掩盖。

## ⑤ 用户原话与素材归档

**初始需求**（2026-08-25）：

> 我要给报价单中增加一个分页的功能,考虑到当前的视图有 报价侧,核价侧,比对视图和excel视图. 以及 报价单编辑页,报价单详情页,核价单等查看页面.
> 1. 报价单的产品默认每页数100, 可选100/200/500
> 2. 报价单的卡片式图/excel视图中的报价侧和核价侧展示的料号要统一,根据分页后的实际料号两边渲染一致,同步分页参数
> 3. 评估分页对报价单快照存储的影响,并且2000笔产品的报价单,首次draft的接口超时,负载过重,设计分页可以对这块性能进行优化,并出一个可以分页执行的方案
> 4. 报价单增加料号查询功能,可以根据输入的料号进行模糊匹配
> 5. 分页展示可以分担前端渲染压力,尽量不要全部数据都一次性展示,因为2000笔产品数据的报价单对浏览器内存的占用量达到1.5GB-2GB以上,资源消耗严重

**方案讨论中的关键追问**（2026-08-25 ~ 08-26，逐条都改变了方案）：

> ①「由于后端计算总额,分页后,用户修改产品卡片数据,前端重算卡片后,报价单总额是否不会跟随一起改变」
> —— 暴露 v1 方案漏洞，催生「增量合成」设计（本方案下已不需要）。
>
> ②「分页是以产品卡片为单位进行分页,不是以页签的行为单位,不会进行切割的吧」
> —— **推翻主线关于基线 §4.6 被破坏的误判**。
>
> ③「行键冲突检测…这个不可能,产品卡片为单位的分页不会出现缺行的情况」
> —— 指出主线措辞含糊；澄清为「卡片不在当前页」而非「缺行」。
>
> ④「如果做了分页,报价单的所有产品卡片的数据服务端还是要全部计算出结果,只是减轻了页面端的显示压力,是不是这样」
> —— **成立**。查实 `li.subtotal` 由卡片值 JSON 抽取（`CardSnapshotService.java:723`）、总价 = 全单 Σ（`:820-822`），故建单必须全算。
>
> ⑤「这两个超时无法通过服务端分页解决,反而服务端分页增加了很多功能缺口」
> —— **成立，且是本次范围收敛的直接依据**。读侧分页对两个超时零贡献，却带来 3 个 P0。
>
> ⑥「服务端分页先不做,改动面影响太大. 先只做前端分页,服务端不变」
> —— **最终范围裁决**。
