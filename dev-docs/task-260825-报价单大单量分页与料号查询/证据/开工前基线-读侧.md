## ⚠️ 4. 取证期观察到的异常（**已复现 1 次，根因未定位，不下结论**）

**现象**：对同一张单连续两次 `GET`，卡片值的返回情况不同。

| 次序 | 响应大小 | `quoteCardValues` 非空行数 | 耗时 |
|---|---|---|---|
| 第 1 次 | 5.27 MB | **0 / 1845** | 7.32 s |
| 第 2 次 | 23.04 MB | **1845 / 1845** | 9.98 s |

**已排除**：
- ❌ 连错库 —— API `totalElements` 与 `cpq_db_0724` 一致
- ❌ DTO 未映射 —— `QuotationDTO.java:239` 无条件 `dto.quoteCardValues = li.quoteCardValues`
- ❌ 分支阈值 —— `getByIdBatch`（`QuotationService.java:2769`）是**配置开关**，与行数无关；
  小单（1 行）第一次拉取即正常返回卡片值 23700 字符
- ❌ 数据缺失 —— 两次拉取之间 DB 一直非 NULL（前后各查一次）
- ❌ Hibernate 二级缓存 —— 配置中未启用

**一个尚未验证的可能机制**（🚫 **未取证，不得当结论使用**）：
`saveDraft` 会把被重建行的卡片值**置 NULL**（`QuotationService.java:507 / :2425`，D-1 失效设计），
之后由 lazy `ensureCardValues` 重算。若第 1 次 GET 恰好落在某次「置 NULL → 重算完成」的窗口内，
即可解释。此路径需要有人正在操作该单，取证期未确认是否成立。

**为什么它对本任务重要（无论根因是什么）**：
若上述机制成立，则**一次 autosave 会让整单 1845 行卡片值全部失效并需整单重算** ——
这是大单量下的成本放大器。分页方案中 `partial` 保存**只失效白名单内行**的设计（AC-12）
正好从结构上消除它。

**处置**：登记为开工前待查项，由后端子代理在实现 F-D 时一并取证；若确认为独立缺陷，另立 `repair-`。

## 🔴 实测发现：打开编辑页会触发一次整单 `saveDraft`（已拦截，未落库）

网络层拦截记录：打开 1845 行单编辑页并进入 Step2 的全过程，**捕获到 1 次非 GET 请求**：

```
PUT /api/cpq/quotations/1ed36b62-cb35-4f88-82e8-9456e496544d/draft
```

**没有任何用户编辑动作**，仅「打开 + 切到 Step2」。对照组：详情页 **0 次**。

**意义**：
1. `QuotationWizard.tsx:314` 记录的「打开 → autosave 风暴」问题，在大单上**至少「打开即触发一次整单 saveDraft」这一半仍然成立**（`:317` 的修复未覆盖本次触发路径）。
2. 该 PUT 走的正是 `QuotationService.saveDraft`（`:315` 单 `@Transactional`，1845 行全删全建）——
   **这就是「首次 draft 接口超时」的直接触发点：用户根本没点保存。**
3. 若该 saveDraft 按 D-1 失效逻辑（`:507 / :2425`）把卡片值置 NULL，即可解释本报告 §4 的
   「首拉 null、二拉有值」异常 —— **该假说至此有了直接旁证，但因果链仍未取证，不作结论**。

**处置**：转后端子代理在实现 F-D 前**优先取证**（触发源是哪个 effect、是否每次打开都发）。
若确认为独立缺陷，另立 `repair-`；本任务的 `partial` 语义会把爆炸半径从整单缩到当前页，但**不替代根治**。
