## 一、现象

BOM 页签能看到 6 个节点，材料成本页签只有 2 行——子件 `S-80011` 下的材质 `00002 (AgC3)` **没有出现**。

```
BOM 树（截图1）                     材料成本页签（截图2）
S-3120014539 主料1                  料号    材质        元素
├─ S-80011 投入零件1                 00137   H65         Cu
│   └─ 00002  AgC3      ←────╳       992     AgNi11#-Ⅰ  Ag
├─ W-1001  组成件1                          （无 00002）
├─ 00137   H65
└─ 992     AgNi11#-Ⅰ
```

业务要求（2026-07-26 裁定）：**子件的材质要进材料成本页签；同理，子件的外购件、零件也要进各自对应的页签。**

## 二、根因（已实证）

### 2.1 直接原因：平铺页签按「主件料号」单值收窄

三个平铺页签的 `$view` 驱动键都是主件料号，框架对报价行隐式注入 `hf_part_no = <本行产品料号>`：

| 组件 | 视图 | 驱动键 |
|---|---|---|
| COMP-0027 材料成本 | `mc_view` | `ebi.material_no AS hf_part_no` |
| COMP-0028 外购件成本 | `wg_view` | `mbi.material_no AS hf_part_no` |
| COMP-0029 加工费 | `jg_view` | `up.finished_material_no AS hf_part_no` |

而 `00002` 的 `element_bom_item` 行 `material_no = 'S-80011'`（子件）≠ `S-3120014539`（主件）→ 整体出局。

**数据实证**（本单 pending 域内）：

| 销售料号 | 材质料号 | 元素 |
|---|---|---|
| S-3120014539（主件） | 00137 / 992 | Cu / Ag |
| **S-80011（子件）** | **00002** | **C / Ag** |

**A/B 实证**：同一张单，收窄到主件 = 2 行（与页面逐行一致）；放开到主件+子件 = 额外出现 `00002/Ag`、`00002/C`。

### 2.2 真正原因：报价侧缺「闭包料号集合」接线（架构缺口，非配置疏漏）

**这不是某个视图写错了，是报价侧渲染链路只会按单料号取数。** 能力盘点：

| 能力 | 现状 | 位置 |
|---|---|---|
| 闭包计算 | ✅ 存在，但**只在树渲染里** | `BomTreeRenderService` 跑 `costing_bom_tree_config`(usage=QUOTE) 递归 SQL（task-0725 刚打通，实测 6 节点） |
| 数组注入到视图（树） | ✅ `:total_material_no` | `BomTreeRenderService` |
| 数组注入到视图（平铺） | ✅ `hf_part_no = ANY(:hfPartNos)` | `SqlViewExecutor:278/288`、`:346/363` |
| 多值展开入口 | ✅ `expandMulti` / `expandForPartSet` | `ComponentDriverService:768` |
| **报价侧平铺页签传什么** | ❌ **单料号** `expand(comp.id, customerId, partNo, …)` | `ConfigureSnapshotService:411`（`partNo` 来自 `li.get("productPartNo")`） |
| 核价侧平铺页签传什么 | ❌ 同样是根料号精确匹配 | `CardSnapshotService:809`「非递归组件按 partNo 精确匹配，取代原 BOM 闭包 partSet 超集」 |
| `BomClosureService` | ⚠️ **已退役** | 仅存 `ExcelViewService:278` 一句「不再依赖」 |

> ⚠️ **勿被 javadoc 误导**：`expandForPartSet` 的注释仍写着「`@param partSet` 闭包料号集合（根 + 全部子孙，去环）」，但其唯一调用方 `precomputeCostingDriverUnion` 实际传的是**本单各行根料号**。原 recursive 分支已被判定死代码清理（见 `CardSnapshotService:770-775` 注释）。**注释已过时，不能当作"核价侧已有闭包"的依据。**

**结论：管道齐全（`:hfPartNos` + `expandMulti`），缺的是「把闭包料号集合喂进去」这一步。**

## 三、方案：复用树递归结果当 partSet

```
costing_bom_tree_config(usage=QUOTE) 递归 SQL
        ↓  已有能力，task-0725 验证可出 6 节点
闭包料号集合 partSet = {S-3120014539, S-80011, W-1001, 00137, 992, 00002}
        ↓  作为 partSet 传入
ConfigureSnapshotService → expandMulti → 外层 WHERE hf_part_no = ANY(:hfPartNos)
        ↓
材料成本 / 外购件成本 / 加工费 页签各自按自己的视图语义取到子件数据
```

**视图 SQL 零改动** —— 三个现有视图、以及未来所有客户模板都不用动。

### 3.1 为什么不用「每个视图自己写递归 CTE」（曾评估并否决）

我先做过该方案的 PoC 并跑通（收窄后正确返回 4 行含 `00002`），但**否决**，理由：

1. **转嫁复杂度**：每个客户模板的每个页签都要重写递归 CTE，还必须记住一条隐晦铁律（下条），漏一次是静默失败。
2. **新铁律的存在本身就是反证**：PoC 中 `FROM closure cl JOIN element_bom_item ebi` 直接失败——
   ```
   anchorInjected=true  primaryTable=material_bom_item   ← 选中了递归 CTE base case 里的表
   EXECUTION FAILED: each UNION query must have the same number of columns
   ```
   因顶层 `FROM closure` 是 CTE 不在白名单 → 主位表探测退化为「任意深度第一个 FROM」→ 锚点插进 base case → UNION 两侧列数不等。必须写成 `FROM element_bom_item ebi JOIN closure cl` 才对。**与 task-0725 那个连带 bug 同源。**
3. **性能不可接受**：视图内对**所有根**做全闭包展开再靠外层筛。本地 40 行 BOM 无感，生产几十万行 BOM 时每页签每次渲染全表递归。框架层只需展开本单料号。
4. **口径必然漂移**：BOM 树走 `costing_bom_tree_config` 递归，平铺页签走另一套手写递归 —— 两套实现迟早不一致（如树按 `characteristic` 过滤而平铺没有）。

> 该 PoC 结论仍有价值：**「含递归 CTE 的视图，白名单表必须出现在顶层 FROM」应作为配置铁律补进 `rule-0724/3-SQL视图.md`**（本任务附带产出，与主方案独立）。

## 五、待裁定决策点（**未定不得开工**）

### 决策 1：哪些页签走闭包，怎么声明？

不能全开——「产品」页签是主件属性，闭包会把子件的产品信息串进来。

| 选项 | 做法 | 评价 |
|---|---|---|
| **1-A** | 按 `tab_type` 映射（材质元素 / 外购件 / 零件 → 闭包；主件 → 否） | 零配置改动，但 tab_type 语义被复用为「是否闭包」，耦合；新页签类型要改映射表 |
| **1-B** | 组件新增属性 `bom_closure_scope`（`SELF` / `CLOSURE`），默认 `SELF` | 显式、符合红线 1/2，配置者可控；需加列 + 组件管理 UI + 三个组件配置 |
| **1-C** | 模板级开关 | 粒度太粗，同模板内产品页签和材料成本页签需求不同 → **不推荐** |

> 技术总监倾向 **1-B**：符合配置驱动红线，且「默认 SELF」保证所有存量组件行为不变（零回归）。

### 决策 2：闭包带上来的行，来源如何呈现？

| 选项 | 做法 | 风险 |
|---|---|---|
| **2-A** | 加「归属料号」列，按来源分行 | 同一材质在主件和子件都用到时自然分成两行，成本不被合并掩盖；代价：三个页签各加一个字段，模板列数变化 |
| **2-B** | 不加列，同料号+元素合并为一行 | 列结构不变；**风险：两处的用量/损耗率被合并掉一条，成本可能算少** |
| **2-C** | 不加列，按来源分行 | 列结构不变；但会出现「料号/材质/元素完全相同」的视觉重复行，用户无法分辨，易被当成脏数据 |

> 技术总监倾向 **2-A**：成本正确性优先，且用户在 BOM 树里已经看到层级，页签里给出归属料号才对得上。

### 决策 3：小计变化是否接受？

闭包后行数增加 → 产品小计从 **¥14** 变大（成本更完整）。需业务确认这是期望结果，以及是否影响已提交/已冻结报价单（本方案只影响 DRAFT 重算，冻结单不动）。

## 七、风险与已知坑

### 7.1 cache key 维度（最高风险）

`driverExpansionKey` 6 维含 `partNo` 但不含闭包范围。开启闭包后同一 `(componentId, partNo)` 在不同闭包配置下结果不同 → **必须评估是否加维度**，否则复现 AP-37 串号。**这是 PR 评审的一票否决项。**

### 7.2 样本数据缺口

当前样本单只有材质（`element_bom_item`）能验证闭包。子件的**外购件**和**加工费**在库里没有数据（`W-1001` 挂在主件下、`unit_price` 的 `finished_material_no` 全是主件）。
⇒ **AC-2 无法用现有数据验证**，须先造数据（在 `S-80011` 下挂一个外购件 + 一条子件加工费），否则会重演「无正向数据的遗留掩盖未实现」（记忆 `cpq-unverifiable-feature-masks-gap`）。

### 7.3 重复行与行键

闭包后同一材质可能来自多个料号。若采纳 2-A，`rowKeyFields` 必须包含归属料号列，否则行键撞键 → 编辑串行、末值塌缩（记忆 `cpq-rowkey-uniqueness-disambiguation`）。

### 7.4 测试连库陷阱（本次调查实测踩到）

后端**测试 profile 实际连 `cpq_db`**，而 dev server 连 `cpq_db_0724`（`application.properties` 默认值已改）。PoC 一度返回 0 行让人误判方案不可行，加 `DB_NAME=cpq_db_0724` 才对上。
⇒ 写集成测试时须显式指定库，或用不依赖库内固定数据的夹具（对应 task-0725 验收报告 §六#1 的 P1 待办：审计测试对库内固定数据的硬编码依赖）。

### 7.5 递归深度与环

`costing_bom_tree_config` 递归 SQL 需有深度上限/去环保护。现有报价树配置的行为须确认（PoC 里我用 `lvl < 10`）。
