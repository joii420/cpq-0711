# 任务平台规则（dev-docs 任务根目录 · Agent 入口规则）

> **生效日期**：2026-08-03　**适用对象**：本项目所有 Agent（主线 + 子代理）
> **一句话**：`dev-docs/` 是本项目**唯一的任务根目录**。任何功能需求、BUG 修复、规则整理，都必须先在 `dev-docs/` 下**立项建目录 → 出文档 → 经用户确认**，再开 worktree 进场开发，最后由主线亲验交付。
> **不立项不开工，不确认不进场，不亲验不交付。**

---

## 0. 什么时候必须读本文件

| 触发场景 | 动作 |
|---------|------|
| `superpowers:brainstorming` 头脑风暴结束（用户认可方案） | **不写 superpowers spec、不进 `docs/superpowers/specs/`**，改走本文件 §4 工作流 |
| 用户提出新功能需求 | 走 §1 判定 → 建 `task-` 目录 |
| 用户报 BUG / 自己发现 BUG | 走 §1 判定 → 建 `repair-` 目录（任务内 or 根目录） |
| 用户要求整理规则、沉淀方法论 | 走 §1 判定 → 建 `rule-` 目录 |
| 新会话接手一个已存在的任务目录 | 先读该目录 `需求文档.md` + `test-report.md`，再读 §4 定位当前处在哪一步 |

**优先级**：`CLAUDE.md`（用户全局指令） > 本文件 > superpowers 技能默认流程。三者冲突时按此顺序取舍。

## 1. 目录命名与分类（规则 1~5）

### 1.1 命名格式

```
<类型>-<日期>-<任务标题>
```

- **类型**（三选一，小写英文）
  - `task` —— 新功能 / 新需求 / 较大改造
  - `repair` —— BUG 修复
  - `rule` —— 系统规则、方法论、配置手册
- **日期**：`MMDD` 四位（月日），取**立项当天**。完整年份写在文档头部的日期字段里，不进目录名。
- **任务标题**：中文短语，**不含空格**，一眼能看出做什么。例：`报价侧BOM闭包渲染`、`公式计算精度优化`。

**正例**：`task-0803-BOM页签增加父子取值公式`、`repair-0803-公式计算BUG修复`、`rule-0724-组件模板配置`
**反例**：`task-新功能`（无日期）、`0803-修bug`（无类型）、`task-0803-fix bug`（英文+空格）

### 1.2 放哪里（判定树）

```
是新功能 / 新需求？
├─ 是 → dev-docs/task-MMDD-标题/                        （规则 2）
└─ 否 → 是 BUG？
        ├─ 是 → 这个 BUG 是某个已交付 task 引入的 / 属于该 task 的范围内？
        │       ├─ 是 → dev-docs/task-XXXX-原任务/repair-MMDD-标题/   （规则 3：任务内修复）
        │       └─ 否 → dev-docs/repair-MMDD-标题/                    （规则 4：系统级修复）
        └─ 否 → 是规则 / 方法论整理？
                └─ 是 → dev-docs/rule-MMDD-标题/                      （规则 5）
```

**判不准就问用户，不要猜。** 尤其"这个 BUG 算不算原 task 引入"——归属错了会导致后续追溯断链。

### 1.3 目录结构总览

```
dev-docs/
├── 任务平台规则.md                    ← 本文件（入口，先读这个）
├── main-api.md                        ← 跨任务的 API 总账
│
├── task-0729-客户价格调整策略和价格版本/
│   ├── 需求文档.md                    ← 【必须】交付验收唯一标准
│   ├── fronttask.md                   ← 前端任务文档
│   ├── backtask.md                    ← 后端任务文档
│   ├── api.md                         ← 前后端接口交接文档
│   ├── test.md                        ← 测试用例文档
│   ├── test-report.md                 ← 测试报告
│   ├── 原型-<主题>.html                ← 需要原型的任务才有
│   └── repair-0805-xxx/               ← 该 task 交付后发现的 BUG（任务内修复）
│       └── 需求文档.md（+ 按需补其他）
│
├── repair-0803-公式计算BUG修复/        ← 系统级 BUG（非某 task 引入）
│   └── 需求文档.md（+ 按需补其他）
│
└── rule-0724-组件模板配置/             ← 规则文档集
    ├── AGENT-配置入口.md               ← 规则目录必须有一个 Agent 入口文件
    └── <分册>.md ...
```

## 2. 交付物清单（规则 6、7）

### 2.1 `task` 目录 —— 强制六件套

| 文件 | 谁写 | 何时产出 | 缺了会怎样 |
|------|------|---------|-----------|
| `需求文档.md` | 主线（技术总监） | 立项时，**开工前** | 无验收标准，交付无法判定对错 |
| `fronttask.md` | 主线 | 开工前 | 前端工程师无输入，只能猜 |
| `backtask.md` | 主线 | 开工前 | 后端工程师无输入，只能猜 |
| `api.md` | 主线 | 开工前 | 前后端契约不对齐，联调必炸 |
| `test.md` | 测试工程师（主线审核） | 开发期并行 | 测试无据可依，漏测 |
| `test-report.md` | 测试工程师 | 开发完成后 | 无交付证据，不得合并 |
| `原型-<主题>.html` | 主线 / 前端 | 需求文档确认前 | 仅**需要原型的任务**必须（涉及新页面/新交互/版式变更） |

### 2.2 `repair` 目录 —— 最小集 + 按需扩展

- **必须**：`需求文档.md`（含**根因分析**、复现步骤、修复方案、验收标准）
- **按影响面补**：改前端才要 `fronttask.md`；改后端才要 `backtask.md`；改接口才要 `api.md`；**`test.md` + `test-report.md` 一律要**（回归证据不可省）

### 2.3 `rule` 目录

- 必须有一个 Agent 入口文件（`AGENT-*.md` 或 `README.md`），说明"什么场景读什么分册"
- 内容按主题分册，不写成一个巨型文件

### 2.4 跨任务总账：`main-api.md` 回写（**强制**）

`dev-docs/main-api.md` 是全项目接口契约基线（当前覆盖 87 个 Resource / 约 413 个端点，按 12 大类组织）。**任务里的 `api.md` 只是本次任务的局部契约，必须回写到总账，否则总账会失真。**

| 项 | 规定 |
|----|------|
| **时机** | **任务测试完成后**（`test-report.md` 已产出、缺陷闭环）、**合并 master 之前** —— 让总账随本次任务一起进 master |
| **责任人** | 主线（技术总监）执行，或指派后端工程师执行、**主线必须复核** |
| **粒度** | 以**端点**（HTTP 方法 + 路径）为单位 |
| **方式** | **直接覆盖**：总账里已有同方法+路径的端点 → 用本次 `api.md` 的定义**整段替换**（不保留旧版本、不写变更历史）；总账里没有 → 追加到对应模块的 `###` Resource 小节下；本次**删除**的端点 → 从总账移除 |
| **标注** | 每个被本次覆盖 / 新增的端点小节**末尾加一行来源标记**（只记**最后一次**，不累积）：<br>`> 来源任务：\`task-0729-客户价格调整策略和价格版本\`｜回写日期：2026-08-05` |
| **文件头** | 同步更新 `main-api.md` 头部的日期说明，注明最近一次回写来自哪个任务 |
| **并发冲突** | 两个任务同时改同一端点时，**以合并进 master 的先后为准**：后合并者以自己的 `api.md` 覆盖，并把来源标记改成自己 |
| **不回写的后果** | 总账与实现脱节 → 后续任务照总账设计接口必然踩空。**未回写不得进入合并环节** |

> 只改了实现、没改契约（方法/路径/参数/响应/错误码全未变）的任务可跳过回写，但要在 `test-report.md` 里写明"本次无契约变更，无需回写 main-api.md"。

### 2.5 存量兼容（重要）

历史目录中大量使用 `需求说明.md`（27 处）而非 `需求文档.md`（5 处），另有 `testcase.md`、`测试用例.md` 等变体。

- **新建目录一律用本规则的命名**：`需求文档.md` / `test.md` / `test-report.md`
- **存量文件视为等价，不强制改名**（改名会打断 `CLAUDE.md`、`RECORD.md` 里的既有引用）
- 接手存量任务时：`需求说明.md` 就是它的 `需求文档.md`，按同等效力对待

## 3. 各文档的内容标准

> 骨架是**下限**不是上限。宁可写细，不可留空槽（`TODO` / `待定` / `TBD` 出现在需求文档里 = 该文档未完成，不得进入确认环节）。

### 3.1 `需求文档.md`（**交付验收的唯一标准**，规则 7）

```markdown
# <任务标题>

- 立项日期：YYYY-MM-DD
- 类型：task / repair / rule
- 状态：草拟中 / 待确认 / 已确认待开发 / 开发中 / 测试中 / 已交付 / 已合并
- 关联：worktree 分支名 / 合并 commit / 关联任务目录

## 1. 背景与目标
（为什么做，不做会怎样，做完达到什么状态）

## 2. 范围
### 2.1 本期做
### 2.2 本期明确不做（并说明推迟去向：BACKLOG.md 的哪条）

## 3. 澄清结论与决策记录  ★ 规则 7 核心
| # | 决策项 | 结论 | 理由 | 被否决的方案及原因 |
（与用户对话中拍板的每一条都要落这里。**口头说过但没落文档 = 不存在**，
 后续 Agent 只认文档不认历史对话。）

## 4. 功能需求（逐条编号）
- FR-1 ...
- FR-2 ...

## 5. 数据与规则
（表/字段/视图/公式/状态机/边界值/精度口径；涉及 Flyway 的写清版本号占位）

## 6. 验收标准（逐条编号，必须可判定）  ★ 验收依据
- AC-1 <可观测、可复现、有明确期望值的断言>
- AC-2 ...
（每条 AC 至少对应 test.md 里的一条用例；AC 里禁止出现"体验更好""更合理"这类不可判定表述）

## 7. 影响面与风险
（改动波及的模块/文件/协议检查点；命中 AP-xx 反模式的必须点名；

## 8. 已知坑位
（本任务必须避开的历史教训，引用 docs/反模式.md 条目号）
```

### 3.2 `fronttask.md`

页面/组件清单 → 每个改动点的文件路径 → 交互流程（对齐原型稿）→ 状态管理与缓存 key → 调用哪些接口（引 `api.md` 的编号）→ 边界与空态 → 自检项（`tsc --noEmit` + Vite 200 + 是否触发 E2E）→ 逐项可勾选的 Task 列表。

必须遵守 `CLAUDE.md` 的 UI 交互规范（Drawer 替代 Modal、列表走 SelectableTable + 工具栏动作）。

### 3.3 `backtask.md`

数据模型变更（表/字段/视图/Flyway 版本号）→ 服务与端点清单 → 业务规则与算法 → 事务边界 → 幂等与并发 → 性能要求 → 自检项（Flyway `success=t`、端点返回码、是否需重启 Quarkus）→ 逐项可勾选的 Task 列表。

### 3.4 `api.md`（前后端交接契约）

每个接口一节：编号、方法+路径、鉴权、请求参数（含类型/必填/示例）、响应结构（含示例 JSON）、错误码与含义、与 FR-x 的对应关系。**前后端各自实现前必须以此文件为准，任何一方改契约必须先改本文件并通知另一方。**

⚠️ 本文件的最终形态（联调/测试后的**实际**契约，不是设计初稿）必须在测试完成后**回写 `dev-docs/main-api.md`**，规则见 §2.4。因此写作时按端点分节、方法+路径写在小节标题里，便于回写时按端点定位覆盖。

### 3.5 `test.md`（测试用例）

每条用例：编号、对应 AC-x / FR-x、前置数据、步骤、期望结果、实际结果（留空待填）、优先级。
必须覆盖：正常流、边界值、异常/错误码、权限、并发/重复提交、回归面（历史相关功能）。
**主线审核不通过的用例文档不得进入执行阶段**（审核口径见 §4 第 6 步）。

### 3.6 `test-report.md`（测试报告）

执行环境（分支、库、端口）→ 用例执行汇总（通过/失败/阻塞数）→ 逐条结果 → 缺陷清单（含复现步骤、严重级、修复状态）→ 回归结论 → **AC 逐条达成对照表** → 证据（截图 / curl 输出 / SQL 结果 / E2E 输出）。

## 4. 标准工作流（规则 8）

> 两个硬闸门：**闸门 A = 用户确认文档**，**闸门 B = 主线亲验 + 用户确认交付**。未过闸门不得推进到下一阶段。

| 步 | 阶段 | 执行者 | 动作与产出 |
|----|------|--------|-----------|
| 1 | **澄清立项** | 主线 | 头脑风暴/需求澄清结束 → 按 §1 判定类型与位置 → 建目录 → 写 `需求文档.md`（决策记录 + FR + AC 全部落地） |
| 2 | **原型**（按需） | 主线/前端 | 涉及新页面/新交互/版式变更时产出 `原型-*.html`，与需求文档同批交付 |
| 3 | **开发文档** | 主线 | 写 `fronttask.md` / `backtask.md` / `api.md`，三者互相引用不打架 |
| 4 | 🚦**闸门 A：用户确认** | 用户 | 主线提交文档 → **等待用户确认**。用户提修改意见则回到第 1/3 步。**未确认严禁建分支写代码** |
| 5 | **开 worktree** | 主线 | 用 `superpowers:using-git-worktrees` 建隔离 worktree + 特性分支（分支名建议 `feat/<目录名>` / `fix/<目录名>`）。**必须基于 HEAD 建，不要 fresh**（本地 master 常远领先 origin） |
| 6 | **进场开发（并行）** | 子代理 | ① 前端工程师按 `fronttask.md` 逐项实现　② 后端工程师按 `backtask.md` 逐项实现　③ 测试工程师**同期**编写 `test.md`（不等开发完） |
| 7 | **审核测试用例** | 主线 | 对照 `需求文档.md` 审 `test.md`：AC 是否**逐条**有用例、边界/异常/回归是否覆盖、期望值是否可判定。不达标打回重写 |
| 8 | **测试执行** | 子代理 | 前后端自检通过后测试进场，执行用例 → 产出 `test-report.md` → 缺陷回流给对应工程师修 → 复测直到收敛 |
| 9 | **回写接口总账** | 主线 | 测试通过后，把本次 `api.md` 的**最终契约**按端点覆盖进 `dev-docs/main-api.md`，逐个端点标注来源任务（规则见 §2.4）。无契约变更则在 `test-report.md` 写明并跳过 |
| 10 | **主线亲验** | 主线 | 按 §6 亲自复验（**不采信子代理的"已完成"**），逐条对照 AC 打勾 |
| 11 | 🚦**闸门 B：用户验收** | 用户 | 主线汇报"AC 逐条达成 + 亲验证据" → 用户确认达标 |
| 12 | **收尾** | 主线 | 合并 master → 跑测试确认 → 删 worktree + 分支 → 更新 `需求文档.md` 状态 → 登记 `docs/RECORD.md` → 更新 `BACKLOG.md` |

**并行原则**：第 6 步三条线并行，不要串行等待。前端可先按 `api.md` mock 联调。

**单个开发 Task 内部的推进手法**：仍可用 `superpowers:subagent-driven-development`（每个 Task 派全新子代理 + Task 间两阶段评审）。本规则管**外层流程**，subagent-driven 管**单任务内部执行**，两者不冲突。

## 5. 角色与编排

| 角色 | 由谁承担 | 职责 | 红线 |
|------|---------|------|------|
| **需求方 / 最终验收人** | 用户 | 提需求、拍板决策、过闸门 A/B | —— |
| **技术总监（主线）** | 主线 Claude | 澄清需求、写全部开发文档、建 worktree、编排子代理、审核测试用例、**亲验**、合并收尾 | **默认不亲手写业务代码**（除非用户当次明确要求）；不得自行宣布"完成即合并" |
| 产品经理 | `cpq-pm` | 需求拆解、PRD 对齐、验收标准打磨 | —— |
| 架构师 | `cpq-architect` | 跨模块设计、数据模型、技术选型；破坏三大核心基线的改动**必须**过它 | —— |
| 前端工程师 | `cpq-frontend` | 按 `fronttask.md` 实现 + 前端自检 | 不得改后端契约（要改先回 `api.md`） |
| 后端工程师 | `cpq-backend` | 按 `backtask.md` 实现 + 后端自检 | 同上 |
| 测试工程师 | `cpq-tester` | 写 `test.md`、执行、出 `test-report.md`、复测 | 不得自行放宽验收标准 |

> **子代理编排授权**：用户已在本规则（规则 8）中明确授权主线安排前后端/测试工程师进场，**本流程内派子代理不需要每次再请示**。但派单必须带齐上下文（任务目录路径 + 对应任务文档 + 分支名 + 禁止事项）。

## 6. 亲验纪律（不可省，历史踩过坑）

**子代理会虚报完成**——报"已完成/全绿"而实际未跑、跑错树、或复用了旧 dev server 得到假阳性。主线**必须自己动手**复验，验不出证据就当没做。

亲验清单（按改动类型取用）：

- [ ] **前端**：`cd cpq-frontend && npx tsc --noEmit -p tsconfig.json` → 0 错误；每个改动 `.tsx` 走 `curl -s --noproxy '*' -o /dev/null -w '%{http_code}' http://localhost:5174/src/<路径>` → 200
- [ ] **后端**：`touch` 一个 java 触发重启 → 目标端点 `curl` 返 200/401（不是 500）
- [ ] **Flyway**：`SELECT version, success FROM flyway_schema_history WHERE version='NNN'` → `success=t`；**禁止手工 `psql -f V_xx.sql`**
- [ ] **数据落库**：直接 `psql` 查目标表，用 SQL 断言数据形态（不听子代理转述）
- [ ] **协议级改动**：亲自跑 Playwright E2E（`quotation-flow.spec.ts`，双轨场景加 `composite-product-flow.spec.ts`），看到 `passed` + `'加载中' final count = 0`
- [ ] **后端测试**：必须在 **worktree 内**的 `cpq-backend/` 跑 `./mvnw test`（`mvnw` 不在仓库根；跑到主仓 = 测错树 = 假绿）
- [ ] **子代理提交位置**：`git branch --contains <commit>` 确认提交落在特性分支而非 master

## 7. worktree 纪律

- **建**：`superpowers:using-git-worktrees`，**基于 HEAD**（`git worktree add <path> HEAD` 后切入），不要 fresh
- **共享的东西不要重起**：后端 dev server(8081) / 前端 dev server(5174) / 远程 DB / `node_modules` / `.codegraph/` 全会话共享。worktree 只隔离 git 工作区 + 分支
- **Flyway 特例**：共享 dev server **看不到** worktree 里的新迁移文件。验证时把迁移文件 copy 到主仓跑，**合并前删掉副本**；做 A/B 对比时别把迁移文件 stash 掉
- **提交纪律**：只 `git add` 本次明确改动的文件，**严禁 `git add -A`**（并发会话会互相夹带）；提交后 `git show --stat` 自查
- **并发**：多会话各用各的 worktree，不污染主工作区
