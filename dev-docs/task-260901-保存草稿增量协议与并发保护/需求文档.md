## ① 背景与目标

### 现象

用户在 1845 行的报价单编辑页里**只改了一个产品卡片、一个页签的一个格子**，点保存后端到端耗时 **97.6 秒**（实测，`QT-20260901-0218`）：

| 阶段 | 耗时 | 证据 |
|---|---|---|
| `PUT /draft` | **43.2 s** | `[draft-profile] total=43204ms \| S1.saveDraft=40056ms S2.snapshotRows=2622ms S3.priceReconcile=526ms` |
| 保存后卡片值全量重算 | **54.4 s** | `[ensure-cardvalues] quotation=46e5428f 补算 1845 行（分 7 批，chunk=300，总耗时=54444ms）` |

同一张单**建单时**已经花 97.5 秒算过一遍（`[create-quotation-timing] ①snapshotQuotation=22676ms ②ensureStructure=399ms ③ensureCardValues=27257ms ④ensureExcelValues=47152ms 总计=97484ms`），这 54.4 秒是**第二次算同样的东西**。

### 四条根因（均已查实，证据见 §④）

1. **前端必须全量发**——`QuotationService.java:673` 的语义是「payload 里没出现的行 = 用户删了」，只发改动行会导致其余 1844 行被真删。
2. **后端认不出「没变的行」**——`row_data` 是 jsonb 列 + Java `String` 映射，库里存的是 **PG 规范化后**的文本（键按字节长度重排），与前端 `JSON.stringify` 的串必然不等 ⇒ Hibernate 判脏 ⇒ 9225 条 componentData 全量 UPDATE。
3. **卡片值被无条件清空**——`QuotationService.java:520-521` 对每个 payload 行执行 `li.quoteCardValues = null; li.costingCardValues = null;`，注释理由是「本行 snapshot_rows 被重建」，但该前提在 `repair-260829 B-6`（componentData 改记录级 UPSERT，明确「不 touch snapshotRows」）之后**已不成立**。清空后前端 `shouldWarmCardValues` 必然为真 ⇒ 触发全量重算，形成自制闭环。
4. **回传整单**——`saveDraft` 末尾 `dto.lineItems = loadLineItems(id)` 把 1845 行连同 9.3 MB 组件数据全部回传，而前端只消费其中 **6 个字段**（`syncLineItemsFromResponse`，`QuotationWizard.tsx:794`），那 9.3 MB **一个字节都没读**。

### 另一个必须一并处理的问题：并发覆盖导致数据丢失

`QuotationLineItem.java` 类注释记录了一个 **4/4 复现**的事故：

```
t0  后台 warm 加载 li（此刻 subtotal=37.330516）→ 开始算卡片值（耗时 0.5~1.7s）
t1  saveDraft 写入用户新编辑（subtotal→38.246716、row_data 新值）并 commit
t2  warm commit → 全列 UPDATE 把 t0 的内存快照整行写回 → subtotal 被打回 37.330516
```

> 受害的**不止 `subtotal`**：`annualVolume` / `discount*` / `lineTotalAmount` 等所有列都在同一条语句里被旧值覆盖 —— **用户改的年用量、折扣会被静默冲掉**。

当时用 `@DynamicUpdate` 缓解，注释末尾写明：「两个事务改**同一列**时仍是后写覆盖先写。那需要 `@Version` 乐观锁根治，因写点众多、每处都要处理冲突异常，已记 BACKLOG 独立评估。」

**本任务的 ③ 版本指纹正是该 BACKLOG 项的落地**，且它同时是 ② 三数组 diff 的前置条件（没有版本校验，diff 会基于陈旧基线算出错误结果）。

### 目标

1. 改一个格子的保存端到端 **≤ 10 秒**（现状 97.6 秒）
2. 并发写入不再静默覆盖用户数据
3. 不牺牲任何现有业务能力（见 §③ 反向 AC）

### 不做会怎样

- 现网 22 张 ≥280 行的单，每次编辑都要等 1~2 分钟；1845 行的单已经踩到前端 60 s 超时线（`repair-260829` 记录）
- 并发覆盖的数据丢失是**静默**的，用户改的折扣、年用量被冲掉时没有任何提示

## ② 范围

### 做什么

| 编号 | 内容 |
|---|---|
| **①** | **后端识别未变的行**：`row_data` 用语义比对（JSON 树相等）、`subtotal` 用 `compareTo`；未变的行不 UPDATE、不清空卡片值 |
| **②** | **请求改增量协议**：`PUT /draft` 请求体从「全量 lineItems」改为 `{baseVersion, added[], modified[], removed[]}` |
| **③** | **版本指纹**：`quotation` 加 `user_data_version`，保存时校验，不匹配返回 409；**后端自身写派生数据不改该版本号** |
| **④** | **回传瘦身**：响应只含变化行的 6 个字段 + 单头 + 新版本号；前端回填从「按下标对齐」改为「按 id 认领」 |

### 明确不做什么

| 不做的 | 去向 |
|---|---|
| **`getById` 真分页**（服务端按页返回 lineItems） | 用户 2026-09-01 明确「分页暂时先不讨论」。**它依赖本任务的 ②**（做完 diff 后前端不必持有全量，分页的最大障碍——「保存会删掉未加载的行」——才消除）。登记 BACKLOG，二期 |
| **冲突行级差异比对 + 合并 UI** | 用户裁决「强制刷新」。列出冲突行让用户逐行选的方案工作量约等于本期其余部分之和，登记 BACKLOG |
| **核价侧单元格级即时编辑端点** | 报价侧有 `quote-card-edit`，核价侧无对应端点（grep 全工程确认）。补齐它能减少核价侧对 saveDraft 的依赖频率，但取代不了 saveDraft（增删行/工序/单头它都管不了）。登记 BACKLOG |
| **行级版本号** | 本期用**整单级**版本号。两人同时改**不同行**也会冲突，但报价单通常单人编辑。要支持多人协同再细化，登记 BACKLOG |
| **`ensure-card-values` 端点内部整跑一次 `getById`**（返回 24.6 MB，实测 21.85 s） | 独立缺陷，与本期改动面不重叠，登记 BACKLOG |
| **那条 1.74 MB/s 链路本身** | 环境问题非代码问题（`ping` 32 ms、`COPY BINARY` 实测 1.74 MB/s）。本期所有指标都在该环境下测 |

## ③ 验收标准（AC）

> 统一前置：admin 登录，dev 库 `cpq_db_0724`，基准单 = 1845 行的 DRAFT 报价单（如 `QT-20260901-0218`）。
> 「端到端」= 从点击到页面可继续操作（含保存请求 + 其触发的一切后台重算）。

### A. 增量协议（②）

- **AC-1**（单点）在 Step2 页签**「物料」**第 2 行「材料净重」列把值改为 `3.5` 并失焦，点「保存草稿」。F12 Network 里 `PUT /draft` 的请求体满足：`modified` 数组**长度为 1** 且其 `id` 等于该产品行 id；`added` 与 `removed` 均为空数组；请求体大小 **< 100 KB**。
  > 📌 **修正（2026-09-01）**：原写「材料成本」页签有误 —— SQL 实测该页签**不含**「材料净重」列（其列集为 元素/料件/料号/毛重/项次/净用量/元素单价/…），且最多 6 行。「材料净重」(INPUT_NUMBER) 在**「物料」**页签，该页签恒 2 行，「第 2 行」成立。
- **AC-2**（单点）在 Step2 用「+ 添加产品」加入 1 个产品后点「保存草稿」。**不得走「选配」入口**（`sel_template` 全库 0 行，该入口必然空态，SQL 实测）。请求体 `added` 长度为 1、该元素 `id` 为 null；`modified` 与 `removed` 为空。保存成功后该行在库中存在，且响应回传了它的新 id。
- **AC-3**（单点）删除 1 个产品行后保存。请求体 `removed` 数组为该行 id 的单元素数组；`added`/`modified` 为空。保存后库中该行的 `quotation_line_item` 与 `quotation_line_component_data` 记录均已删除（各 0 行），且**未列入 `removed` 的其它行一行未少**。
  > 📌 **修正（2026-09-01）**：原写「4 张子表各 0 行」在 dev 库上是空跑 —— `quotation_line_process` / `quotation_line_composite_process` / `quotation_line_item_snapshot` **全库都是 0 行**，`0==0` 恒真无分辨力。**这三张表的删除权威判据移到后端自建夹具测试**（B-5a：先插入工序/组合工艺/快照数据，再验删除），E2E 层保留观察但须显式打印「本轮无分辨力」。用户 2026-09-01 裁决采纳此方案。
- **AC-4**（单点）只修改单头「项目名称」为 `AC4-<时间戳>` 后保存。请求体 `added`/`modified`/`removed` **三个数组全为空**，`projectName` 字段为该值。保存后库中 `project_name` 等于该值，且 `quotation_line_item` 表**零行被更新**。
- **AC-5**（边界）什么都不改直接点「保存草稿」。**不发出** `PUT /draft` 请求（承接 `repair-260830` 已交付行为），页面提示「无改动，无需保存」。

### B. 后端只动该动的（①）

- **AC-6** 执行 AC-1 后，`quotation_line_component_data` 表中该报价单的 9225 条记录里，**只有 1 条**的 `row_data` 内容发生变化（比对保存前后的整表 md5 指纹，仅目标行不同）。
- **AC-7** 执行 AC-1 后立即查库：`SELECT count(*) FROM quotation_line_item WHERE quotation_id=? AND quote_card_values IS NULL` 结果为 **1**（只有被改的那一行卡片值被清空），`costing_card_values IS NULL` 同样为 **1**。
- **AC-8** 执行 AC-1 后，保存所触发的卡片值补算**只覆盖 1 行**。判据（DB，可留存）：保存完成后轮询至该单 `quote_card_values IS NULL` 的行数归 0，期间该计数的**峰值为 1**（不是 1845）。后端日志 `[ensure-cardvalues] 补算 N 行` 作为**可选第二路取证**，不作为唯一判据。
  > 📌 **修正（2026-09-01）**：原判据是共享 dev server 的终端日志，按 `test.md §1`「下一轮跑测试会不会把它删掉？」的规则，它不是可留存的验收证据形式。
- **AC-9**（反向）人为构造一行 `row_data` 语义相同但键顺序不同的 payload（模拟 PG 规范化差异），后端判定为「未变」，该行不产生 UPDATE。
- **AC-10**（反向）改动 `row_data` 中任意一个值（哪怕只差最后一位小数）后保存，该行**必须**被判定为「已变」并写入，卡片值被清空重算。

### C. 版本指纹（③）

- **AC-11**（单点）**以「发出保存请求前一刻」的版本号为基准 N**（不是「打开单据时」的版本号）。保存一次成功后，响应里的 `userDataVersion` 为 **N+1**，库中 `quotation.user_data_version` 也为 N+1。
  > 📌 **修正（2026-09-01）**：原写「打开时记 N、保存后 N+1」与 AC-14 自相矛盾 —— 用户改完格子失焦会先触发 `quote-card-edit`（AC-14 要求它也 +1），此时保存后实为 N+2。基准点改为「保存前一刻」后两条 AC 自洽。
- **AC-12**（边界·并发）会话 A 与会话 B 同时打开同一张单（都拿到版本 N）。A 保存成功（版本→N+1）。B 随后保存，收到 HTTP **409**，响应 `reason` 为 `STALE_VERSION`；页面弹出对话框，标题「保存失败」，正文包含「这张报价单已被他人修改」，**只有一个「刷新页面」按钮**（无「强制覆盖」「忽略」等其他按钮）；点击后页面重新加载，数据为 A 保存后的版本。B 的本次编辑丢失属预期行为。
- **AC-13**（反向·关键）打开报价单后**不做任何编辑**，等待后台 `ensure-card-values` 跑完（日志出现 `[ensure-cardvalues]` 完成记录）。此时库中 `user_data_version` **保持不变**。随后正常编辑并保存，**不得**出现 409。
  > 本条防的是最大的设计陷阱：若版本号覆盖后端自算的派生数据，用户什么都没做也会被反复要求刷新。
- **AC-14**（反向）通过 `PUT /line-items/{id}/quote-card-edit` 改一个单元格后，响应中带回**新的** `userDataVersion`，前端更新本地版本号；随后点「保存草稿」不出现 409。

### D. 回传瘦身（④）

- **AC-15** 执行 AC-1 后，`PUT /draft` 的**响应体 < 500 KB**（现状实测 24.6 MB），且响应中 `lineItems` 数组只含被修改的那 1 行。
- **AC-16** 响应中每个 line 元素只含这 6 个键：`id`、`partVersionLocked`、`quoteCardValues`、`costingCardValues`、`quoteExcelValues`、`costingExcelValues`（外加单头字段与 `userDataVersion`），**不含** `componentData`。
- **AC-17**（序列·关键）新增 1 个产品 → 保存（响应回传其新 id）→ 立即再修改这个新产品的一个格子 → 再次保存。第二次保存的 `modified` 数组中该行 `id` 为**第一次保存返回的 DB id**（不是 null），且**该 `line_item id` 在库中唯一存在**（`SELECT count(*) FROM quotation_line_item WHERE id = ?` 恒为 1），未出现重复插入。
  > 📌 **修正（2026-09-01）**：原写「该产品只有 1 行」在本库不可判定 —— `CUST-0004` 映射 1845 个料号、基准单已用满 1845 个，空闲料号为 **0**，任何新增都必然与既有行同料号。改按 line_item id 判定，同样能防住重复插入且不受料号占满影响。用户 2026-09-01 裁决。
  > 本条防的是 ④ 的主要风险：前端回填从「按下标」改「按 id」若没改对，新行拿不到 id，下次保存会重复插入。

### E. 性能（用户裁决目标）

- **AC-18** 在基准单上执行 AC-1 的完整操作，从点击「保存草稿」到**「`PUT /draft` 返回 且 目标行的 `quote_card_values` 由 NULL 回填为非 NULL」**，端到端 **≤ 10 秒**。测 3 次取**最大值**。
  > 📌 **修正（2026-09-01）**：「页面可继续操作」不是可观测断言，采纳测试侧给出的可执行定义（上述双条件）。
  > 🚨 **测量前提**：必须确认无其他大请求在跑（实测 4 个并发大请求会让同一操作从 0.18 s 劣化到 9.8 s，同码同数据能测出 16 s 与 43 s 两种结果）。不满足前提时测得的数字作废，见 `test.md §0`。
  > 现状实测 97.6 秒（43.2 + 54.4）。

  > 📌 **修正（2026-09-01）**：原写「各页签有数据」含形容词且未定范围，改为上述可观测判据（弱化版，但可执行）。
- **AC-20** 保存后，工序与选配-组合工艺的记录数与内容和保存前一致（未改动的行不丢工序）。
  > 📌 **修正（2026-09-01）**：同 AC-3 —— 这两张表在 dev 库**全库 0 行**，E2E 层断言恒真。**权威判据在后端自建夹具测试**（B-5a：先为若干行插入工序/组合工艺数据，保存后逐字节比对未改动行）。E2E 层保留观察并显式打印「本轮无分辨力」。
- **AC-21** 在 Step3 修改年用量为 `100` 后点「下一步」，保存成功且库中 `annual_volume = 100`。
  > 本条防的是 `repair-260830` 已记录的陷阱：Step3 初始物化走**程序化**通道，若增量判定漏掉它，用户在 Step3 的改动永久不落库。
- **AC-22** 走完整提交流程（Step1→…→提交审批），单据状态变为已提交，总价与保存前一致。
- **AC-23**（序列）改 A 行一个格子 → 保存 → 改 B 行一个格子 → 保存 → **刷新页面**。两次改动都在，且 A、B 两行的卡片值都是新值。
- **AC-24**（边界）0 行的空单点保存：不报错，`added`/`modified`/`removed` 全空或不发请求，页面无异常。

### 关键原话（2026-08-31 ~ 2026-09-01 对话）
