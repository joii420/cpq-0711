### 1.1 🚨 「这一轮的绿可不可信」——DB 同一性守卫

本套所有列表总数断言都是**不变量形式**「页面总数 == 同一时刻库中 `count(*)`」。
该形式抗共享库漂移，但**引入了一个新维度：哪个库**。2026-09-04 实测踩到过一次错位
（借用的临时后端连的是**克隆库**，而断言查的是共享库；两库数据一致 ⇒ 数字碰巧相等 ⇒ **断言 PASS 但验证逻辑错位**）。
⚠️ 这类错位**只会假绿不会假红**，且**断言写得越严谨越容易中招**——写死绝对值 17 反而没这个问题。

⇒ 新增 `assertSameDatabase()`（四步），两套 spec 的 `beforeAll` 都先跑它。**本轮实际执行痕迹**：

```
[DB同一性] ①后端 total=45  ②cpq_db_0724 count(*)=45
[DB同一性] ③.5 阳性对照 ✅ 后端能看到 S-1630010773
[DB同一性] ④哨兵=PWDBPROBE-1788505706333-3z8xzx9y  后端读回 HERO={..."productionNo":"PWDBPROBE-..."}
[DB同一性] ✅ 验明正身：后端 http://127.0.0.1:8093 与 PW_DB=cpq_db_0724 是同一个库
```

⇒ **本轮的「页面 == 库」断言确实是同库比较。**

### 4.1 `assertSameDatabase()` 三变体（✅ 3/3）

后端固定连 `cpq_db_0724`，**只变 `PW_DB`**：

| 变体 | `PW_DB` | 期望 | 实测 |
|---|---|---|---|
| `same` | `cpq_db_0724` | 守卫通过 | ✅ `抛错=false`，`④命中=true` |

## 5. 本轮发现

### 发现 1 —— 我方用例缺陷：残留守卫观察面过宽 ⇒ 恒定假红

`snapshotHeroRow()` 原先观察**整行**，而对方 `PUT` 会更新 `updated_at`/`updated_by`（`api.md` C-1 约定），
我们的还原**有意不碰审计列**。⇒ 只要跑过一次写用例，`afterAll` 就报「共享库残留」。
**产品没问题，是我的守卫过严。** 已改为 `to_jsonb(t) - 'updated_at' - 'updated_by'`，并做了证伪（§4.2）。
📌 这个失败模式我在 `FS-1` 的注释里**预见过**，但 `FS-1` 走的是 SQL 还原路径、不经过 `PUT`，所以没触发——
**证伪实验也有覆盖盲区**。

### 发现 2 —— 我方用例缺陷：把断言写死在实现形态上（AC-13）

首轮 `E-12` 报「一条提示都没有」。一次性诊断查明：
`maxlength=null`、输入框收下 129 字符、**前端前置校验拦住、一个保存请求都没发**、库值未变，
**页面上确实写着「生产料号最长 128 字符，当前 129」**——与原型 `边界-过滤空结果与极值.html ②` 逐字一致。

⇒ **产品是对的。** 我只在 `.ant-message-notice` / `.ant-form-item-explain-error` 等四类 antd 类名里找提示，
而实现按原型把它渲染成**单元格内的行内文案**。已改回 AC 的可观测事实（「用户能在页面上看到一条说明长度限制的文案」）。
🚩 这正是 `testing.md §4.1.5`「**必现 ≠ 缺陷**」的实例：确定性复现只证明不是 flaky，不证明是缺陷。
按三问复核（页面与数据是否自洽 / 预期是 AC 写的还是我加的 / 是否本次引入）才没误报。

### 发现 4 —— 我方用例缺陷：`FS-4` 沿用父任务的文案选择器，DOM 变了之后烂掉

`FS-4` 逐字沿用父任务 `FS-1a` 的 `getByText('料号核价', { exact: true }).first().click()`，
本轮 **150s / 300s 两次纯超时**。诊断查明：`/master-data-hub` **渲染完全正常**
（`role=tab` 里就有「料号核价」、无 4xx/5xx、只有 antd 弃用警告），
但该文案在页面上出现多处（页签 + 导航），`.first()` 落到的那个**不可点击** ⇒ click 一直等 actionability。

⇒ **纯超时最容易被误读成「页面坏了」**，而且它出现在「核价侧」——正是主线提醒要警惕
`选配功能` 兼容视图改动的那个区域。**先诊断再归因，避免了一次误报。**
已改为按**角色**定位 `getByRole('tab', { name: '料号核价', exact: true })`。

### 发现 3 —— 并发导入把 `CUST-0004` 从 11 行变 12 行（数据漂移，非缺陷）

`新料号数据规则` 会话导入 `S0001~S0003` 期间实测：


- **本子任务不受影响**：断言全是不变量形式（页面 == 同条件库计数），AC 基线常量只打印不断言。
- **父任务 `E2E-14` 受影响**：它硬编码 `CUST-0004 = 11` ⇒ **将持续假红**，直到基线被更新。
  按「不清、不灌回」的裁决，这个漂移是**永久的** ⇒ 建议把父任务该处改成不变量形式或更新基线。
