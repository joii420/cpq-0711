# repair-0803 公式计算 BUG 修复 —— 修复方案

> 来源：2026-08-02 用户报障「QT-20260802-0049 产品卡片显示『该料号卡片数据待重算』」，
> 技术总监逐层排查，挖出 3 条独立缺陷（[[BL-0097]] / [[BL-0098]] / [[BL-0099]]）。
> 本文是修复方案与实施记录。定稿：2026-08-03

---

## 0. 一句话结论

用户看到的「待重算」**不是公式算错**，而是**某个组件的 `$view` SQL 报错把整个数据库事务毒死了** ——
Java 侧的 `catch` 接住了异常看似已处理，但 PostgreSQL 已把事务置为 aborted，
此后同事务的每条 SQL 都失败，最终整张卡片算不出来，且**报价侧不落错误原文**，故障原因对用户完全不可见。

排查过程中另外发现两条独立缺陷（公式按位置静默绑定、跨组件 token 字段填错），一并修复。

---

## 1. 三个问题的根因（均已实证）

### 1.1 BL-0097（P0）：`$view` 报错毒化整个事务

**故障链**：

```
某组件 $view 查询在 PG 层报错（列名/表结构不匹配等）
  → componentDriverService.expand 抛异常
  → CardSnapshotService:2245 catch 住并置空条目（看似"已处理"）
  → 但 PG 已把当前事务标记为 aborted
  → 此后同事务每条 SQL 均失败（current transaction is aborted）
  → buildCardValues 抛异常 → 返回 null
  → orSentinel() 落 {"tabs":[],"__cardValueFailed":true}
  → 前端显示「该料号卡片数据待重算」，不含任何错误原文
```

**关键代码**（`CardSnapshotService.java`）：

```java
:2239   exp = componentDriverService.expand(...);
:2244   baseRowsByComp.put(cidStr, buildBaseRowsFromRows(rows));
:2245 } catch (Exception e) {
:2246   LOG.warnf("[card-snapshot] expand(flat) comp=%s li=%s: %s", compId, li.id, e.getMessage());
:2247   baseRowsByComp.put(cidStr, MAPPER.createArrayNode());   // ← 吞掉异常，但事务已死
:2248 }
```

**代码里早有记载但未根治**：`:2179-2183` 注释（2026-07-22 真实事故）已写明
"异常会在此处被 catch 且置空条目——但 PostgreSQL 层面该 SQL 错误已把当前事务置于 aborted 状态"。
当时的处置是「树组件跳过平铺展开」，属**点状规避**，未解决"局部 catch 兜不住事务毒化"这个通用问题。

**第二重问题：报价侧错误不可见**。核价侧有 BL-0030 的能力
（`:553` 走 `failedSentinelWithError` 落 `__errorMsg`，前端显示「核价渲染失败: 原文」），
**报价侧走 `:543` 的 `orSentinel` 没有原文**，只能显示通用的「待重算」。

**危害**：
- 爆炸半径不成比例 —— 一个视图写错一个列名，整张卡片 9 个页签全废；
- 排查成本极高 —— 用户与排查者都看不到是哪条 SQL 出错，dev 环境日志还不落文件；
- **"改配置就好了"具有迷惑性** —— 本次用户把公式里的跨组件引用改成常量后故障消失，
  实际只是绕开了那条报错 SQL，**根因视图仍是坏的**，换个公式又会复现。

### 1.2 BL-0098（P1）：FORMULA 字段按「位置」静默绑定公式

`FormulaCalculator.resolveFormula`（`:1476`）解析 FORMULA 字段用哪条公式，有 4 级回退：

```
0. 显式 formula_name                          （最高优先）
1. 模板级 formula_assignments[字段完整下标]
2. 字段名 == 公式名
3. positional fallback ← 按该字段在 FORMULA 字段中的相对位置取 formulas[同位置]
```

**实证（当前生产配置就踩在上面）**：`COMP-0157「物料」`的 `材料成本` 字段是 FORMULA 类型，
`formula_name` 为空、也没有同名公式，于是按位置匹配到 `formulas[2]` = **「银点材料成本公式」**：

| FORMULA 字段（第 N 个） | formulas 数组（第 N 条） |
|---|---|
| 来料回收费 (0) | 来料回收费取值公式 (0) |
| 来料财务费 (1) | 来料财务费取值公式 (1) |
| **材料成本 (2)** | **银点材料成本公式 (2)** ← 隐式绑定 |

用户本人认为"这条公式没有被字段绑定"，实际它正在决定「材料成本」列的算法
（用户改动该公式后故障状态改变，正是此机制的实证）。

**危害**：只要有人在公式列表里插入/删除一条公式、或调整顺序，
所有未显式绑定的 FORMULA 字段都会**静默换成另一条公式** —— 不报错、不提示、UI 上看不出来，只有算出来的钱变了。

### 1.3 BL-0099（P2）：跨组件引用 token 把「列名」写进了 `tab_name`

`formulaSerialize.ts:642-647`：

```js
{ type: 'component_subtotal',
  value: col,            // "税率"
  tab_name: col,         // "税率"  ← 应为页签名（如「产品」），却放了列名
  component_code: td.alias,
  label: `${td.componentName ?? td.alias}·${col}` }
```

后端 `FormulaCalculator.appendToken`（`:133-155`）的 6 级回退中，
第 2 级拼 `tab_name + "#" + colName` = `"税率#税率"` —— **永远命中不了**。

**为什么现在没出事**：第 1 级 `component_code + "#" + colName`（`"产品#税率"`）能命中，
且 `CardSnapshotService` PASS1 同时写入 `cid#col` / `code#col` / `tabName#col` 三种键，兜住了。

**风险**：一旦 `component_code` 缺失或 alias 变化导致第 1 级落空，会连续跌到第 3/4 级
**取整个组件的小计合计**（例如「产品」组件 = 管理费 + 税率之和），静默算错且极难发现。

## 2. 修复方案

### 2.1 BL-0097 的方案选型

| 方案 | 做法 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| **A. Savepoint 隔离** | expand 查询前 `conn.setSavepoint()`，出错 `rollback(sp)` | 同事务内、轻量、PG 原生；**项目已有 `em.unwrap(Session.class).doWork()` 5 处先例** | 需验证异常后 Hibernate session 可用性 | ✅ **选用** |
| B. REQUIRES_NEW 独立事务 | expand 包进 `@Transactional(REQUIRES_NEW)` | 隔离彻底 | **每组件一个独立事务**，连接池压力大；首存性能是本项目历史痛点（见 `cpq-import-firstsave-perf-bottlenecks`） | ❌ 性能风险不可接受 |
| C. 仅让错误可见 | 报价侧也落 `__errorMsg` | 零风险、立即降低排查成本 | 不解决毒化 | ✅ **一并做**（作为 L1） |

**采用 A + C 组合**，分两层：

- **L1（零风险，先做）**：报价侧也走 `failedSentinelWithError`，把首个错误原文落进 `__errorMsg`，
  前端显示具体错误而非通用「待重算」。**即使 L2 有问题，L1 单独就能把排查成本从"翻日志"降到"看界面"。**
- **L2（核心）**：用 Savepoint 隔离每个组件的 expand 查询 —— 单个组件的 `$view` 报错只回滚到该组件的
  savepoint，**事务整体存活，其余 8 个页签照常渲染**。

**为什么不选 B**：本项目首存性能有历史包袱（`saveDraft` 30s 曾是 P0），
一张卡片 9 个组件 × N 行，每个 expand 一个独立事务会显著增加连接获取与提交开销。
Savepoint 是同一连接内的轻量标记，开销可忽略。

### 2.2 BL-0098 的方案选型

| 方案 | 做法 | 结论 |
|---|---|---|
| **A. 保存时固化 `formula_name`** | 组件保存时，对无 `formula_name` 的 FORMULA 字段，把当前解析到的公式名**写死**进字段 | ✅ **选用**（根治，且自动收敛存量） |
| B. 禁用 positional fallback | 直接删掉第 3 级回退 | ❌ 会让所有未显式绑定的存量字段立即失去公式，破坏性 |
| C. 仅 UI 提示 | 前端标注"当前按位置匹配到 XXX" | ⚠️ 治标，作为后续增强（本期不做，登记 BACKLOG） |

**采用 A**：在 `ComponentService.update` 保存路径上，对每个 FORMULA 字段调用与
`FormulaCalculator.resolveFormula` **同口径**的解析逻辑，把解析结果回写 `formula_name`。
这样：
- 用户**保存一次组件**，该组件的隐式绑定就被固化，此后公式顺序变化不再影响它；
- 不破坏存量（未保存过的组件行为不变，仍走 positional fallback）；
- 无需数据迁移脚本（避免 Flyway 里复现复杂的匹配规则）。

### 2.3 BL-0099 的方案

直接修正 token 构造：`tab_name` 填页签名（`td.alias` 或 `td.componentName`）而非列名。
**后端 6 级回退链保持不变**（兼容存量 token）。补前后端共用的 token 形状单测。

### 6.2 B2：Savepoint 方案被证否（重要负面结论）

`SavepointIsolationFeasibilityTest` 两个用例：

1. **对照组通过 —— 完整复现了 BL-0097 的机制**（这是根因分析的决定性实证）：
   ```
   [B2-验证] 无 Savepoint，后续查询异常 =
     ERROR: current transaction is aborted, commands ignored until end of transaction block  [SELECT 1]
   ```
   一条查不存在表的 SQL，就让同事务后续的 `SELECT 1` 全部失败。

2. **实验组证否 —— Quarkus 默认连接池 Agroal 禁止在 JTA 事务内回滚 Savepoint**：
   ```
   java.sql.SQLException: Attempting to rollback while enlisted in a transaction
       at io.agroal.pool.wrapper.ConnectionWrapper.rollback(ConnectionWrapper.java:220)
   ```
   > ⚠️ 迷惑点：`conn.setSavepoint()` **本身不报错**，被拒的只是 `rollback(sp)` ——
   > 「设得上却回滚不了」比完全不支持更容易让人以为方案可行。

**结论**：JTA 事务内用 Savepoint 隔离单条 SQL 错误，在 Quarkus + Agroal 下**走不通**。
真正的隔离只能走独立事务（`REQUIRES_NEW`），但那有连接池与性能代价
（本项目首存性能有历史包袱），**须单独做性能评估**，不在本次范围。

该结论已固化为测试（而非仅写文档），**防止后人再花一轮走同一条死路**；
若将来 Agroal 放开限制，该测试会失败并提示重新评估。

### 6.3 B3：只做了解析口径，未接入保存路径

**已做**：`FormulaCalculator.resolveFormulaNameForField()` —— 把「某 FORMULA 字段最终用哪条公式」
的 4 级回退口径**对外暴露**，供保存期固化调用。配套 `FormulaNameResolutionTest` 5 个用例，
其中两个是 BL-0098 的实证资产：
- `realCase_COMP0157_材料成本_按位置隐式绑到银点公式()` —— 用线上故障单 QT-20260802-0049 的真实配置，
  复现「用户认为公式没被绑定，实际它正决定材料成本算法」；
- `insertingFormulaSilentlyRebinds()` —— 固化危害：**公式列表插入一条，字段配置一个字没动，
  算法却从「银点材料成本公式」变成「乙公式」**。

**未做**：`ComponentService` 保存路径的接入。原因（技术总监判断）：
- 接入点 `:242/:331` 的 `component.fields = fieldsJson` 用的是**预先序列化的 JSON**，
  固化会改动 `fieldList` 从而必须改为 `toJson(fieldList)` —— 需先确认 `fieldsJson` 的来源与额外处理；
- `ComponentService` 在 CLAUDE.md 的 **E2E 强制触发文件清单**内，属核心保存路径，
  而 E2E 当前因 [[BL-0078]] 夹具失效跑不通，验证手段不足；
- 仓促改核心保存路径的风险高于本次收益（B1 已解决可见性这一主要痛点）。

**遗留动作**：BL-0098 保留 TODO，下一轮接入时**必须复用**已暴露的
`resolveFormulaNameForField`，不得另写一套解析（否则口径漂移即 BL-0098 在另一层面重演）。

### 6.5 踩坑记录

**worktree 跑测试反复撞 `FlywayValidateException`**：
```
Detected applied migration not resolved locally: 368 / 369 / 370 / 371
```
根因：并发会话的迁移已应用到**共享 test 库**，但文件在主工作区仍是 untracked，新建 worktree 里没有。
