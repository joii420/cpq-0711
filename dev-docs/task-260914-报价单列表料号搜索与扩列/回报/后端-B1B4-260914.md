### ⚠️ 一处刻意偏离 B-2 字面写法（代理声明：不是偏离 AC）

B-2 写「`partNo` → `EXISTS` 子查询」，实现成 **`id IN (非相关子查询)`**。代理给的理由（原文要点）：

> Panache 的 where 片段拿不到外层根别名，写成 `EXISTS (SELECT 1 FROM QuotationLineItem li WHERE li.quotationId = id ...)` 时，
> Hibernate 6 会把裸 `id` **先解析到子查询根** `QuotationLineItem.id` —— **能编译、能跑、谓词恒 false**，
> 症状是「料号搜索永远 0 条」。`IN` 的左侧在外层，无歧义。代码里写了完整注释。

## 4. 代理规避掉的坑（5 条，原文要点）

1. 🚨 **Panache EXISTS 子查询的裸 `id` 静默解析到子查询根**。按 B-2 字面写会得到「料号搜索恒 0 条」且不报错 —— 代理称这是本次最大的坑。
2. 🚨 **`org.hibernate.SQL` 被 `application.properties:98` 钉死在 WARN**。第一次只加 `-Dquarkus.hibernate-orm.log.sql=true`，**日志 0 条** —— 差一点写成「SQL 条数 = 0，无 N+1」这种**假绿**。必须同时覆盖 category level。
3. `count` 与主查询共用同一份 `params` Map，没为主查询单开一份 —— 正是 AC-16 要验的点。
4. ⚠️ **`pgrep -f "quarkus.http.port=8193" | kill` 会连自己的 bash wrapper 一起杀**（命令字符串含同样文本），**实际发生了两次（exit 144）**。代理称已确认只误杀了自己的 shell，8081 全程 401 未受影响。后续用 `ps -o args=` 二次过滤 `classworlds` 才安全。
5. 全程只读共享库（只跑 SELECT），没建单、没改数据、没跑会写库的测试。

## 5. 🚨 代理报的契约疑点（待主线实查 + 用户裁决）

### AC-15 的基准 SQL Q7 按**模板名**聚合，但 `templateId` 参数按**模板 ID** 过滤 —— 同名模板有多个版本行

代理实查 `cpq_db_0724`（2026-09-14 20:54）：
```
839743b3-…  正泰测试模板1  v1.0  PUBLISHED  → 18 单
6dedb30b-…  正泰测试模板1  v1.1  PUBLISHED  →  9 单
45cc0267-…  正泰测试模板1  v1.2  PUBLISHED  → 32 单
                                              合计 59
```
- 立项文档 §③ 的「正泰测试模板1 **59**」是**按名字**数出来的。
- AC-15 要求「选『正泰测试模板1』→ 命中数 = Q7 = **59**」，而 Q7 是 `WHERE t.name=:tname`，把 3 个版本行合并了。
- B-2 规定 `templateId` 是**单个 UUID 等值过滤** → 前端选中哪一版就只能命中哪一版，**最多 32，永远到不了 59**。

**连带影响 AC-12**：下拉拉 `template_kind='QUOTATION' AND status='PUBLISHED'` 共 21 条，其中「正泰测试模板1」会出现 **3 个完全同名的选项**（D-8 规定不显示版本号 → 用户看到三个一模一样的条目，无法分辨）。代理称实测列表返回里也能看到：前 5 行 4 个不同的 `tplId` 全都叫「正泰测试模板2」。

代理**未自行改契约**，B-1~B-4 完全按文档字面实现。它列的三个方向：① 改按 `template_series_id`/名称过滤；② 下拉带版本号（推翻 D-8）；③ 下拉按名称去重只留最新版（改 AC-12 的「21 条」）。
