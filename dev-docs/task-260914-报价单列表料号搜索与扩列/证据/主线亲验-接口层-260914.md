## 三、AC-18 · N+1 红线（主线独立测量）

```
🔍 手段自检：[Hibernate] 行数 = 15（>0，判据有效）
返回行数=1  → SQL 条数 = 4  ✅
返回行数=5  → SQL 条数 = 4  ✅
返回行数=20 → SQL 条数 = 4  ✅
```
**行数 1→20 翻 20 倍，SQL 条数恒为 4**（1 count + 1 主查询 + `product_category IN` + `template IN`）。

### 🚨 这一条我连踩三个「判据恒给同一答案」的坑，全部记下来

| # | 我做了什么 | 为什么是零证据 | 怎么发现的 |
|---|---|---|---|
| 1 | 用 `pg_stat_user_tables` 的扫描增量代替 SQL 日志 | 共享库有并发（S-API 同时在跑），计数是**全库级**含噪音；多轮取最小值后**两个 size 都得 0**（字典查询被会话缓存吃掉）⇒ **0 和 0 分不出 N+1 和批量** | 自己发现判据无区分力 |
| 2 | `grep 'org.hibernate.SQL'` 数日志 | Quarkus 控制台格式 `%c{3.}` 把 category **缩写成 `org.hib.SQL`** ⇒ 模式恒不命中 ⇒ **恒 0** | 打印日志原文时发现 |
| 3 | 改 `grep 'org.hib.SQL'` | 那 15 行是**启动阶段**的，SQL 语句行的前缀其实是 **`[Hibernate] `** ⇒ 请求增量仍恒 0 | S-API 代理回报里点破 |
| 4 | 用 `trap ... EXIT` 做配置"安全还原" | dev 模式**监听到配置文件被还原 → 热重载 → 日志级别变回 WARN**，于是测量窗口里日志是关的 ⇒ **还原动作本身破坏了测量** | 对比「15 行启动日志存在」与「请求增量为 0」的矛盾推出 |

✅ **每一次都是靠「先证明判据本身有效（`>0`）」这一步挡住的** —— 若跳过该步，四次都会得到「SQL 条数 = 0 ⇒ 没有 N+1」这个彻底的假绿。

**配置改动已干净还原**：`git diff -- application.properties` = **0 行**。
