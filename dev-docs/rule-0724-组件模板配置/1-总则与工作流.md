## 1.2 🚨 每组件配置前必确认 4 项（禁止自己猜）

页签类型 / 料号列 / 料号名称列 / 行键 这 4 项是**猜不准、猜错要返工**的（实证：`来料` 曾被猜零件实为 BOM；`自制加工费` 料号曾绑 `finished_material_no` 实为 `code`），必须由用户明确。两条路：

- **有填好的 `组件模板.xlsx`（推荐）**：4 项已前置到模板列，直接读——`tabType`=Sheet B1；`partNoField`=勾「料号列」的字段；`partNameField`=勾「名称列」；`rowKeyFields`=勾「行键」的字段们；`sort_field`=勾「排序列」；`元素单价接价格策略`=勾「接价格策略」。**模板已填即照配，不再问。**
  - ⚠️ **「料号列」没勾 ≠ 留白待问**：多数客户模板本就不显示料号，这是**明确的「本页签无料号列」**，按 §1.3.1 配（`partNoField` 留空 + 名称列担标识 + 料号只进 SQL JOIN），**不要回头问用户、更不要自己造一列**。
- **没有模板 / 模板留白**：逐个组件用 `AskUserQuestion` 问用户勾选这 4 项（+ 排序列 / 接价格策略）。

> 模板列 ↔ 配置项对照见 `AGENT-配置入口.md §3`。

## 1.3 🔑 料号列铁律

### 1.3.1 模板没有料号列 = 正常，禁凭空造字段（2026-07-24 用户定）

**客户模板里不显示料号是真实业务场景**，不得为了填上 `partNoField` 而新增模板没有的可见字段（历史上曾给材料成本加「材质料号」、给外购件加「组成件料号」，已废止）。

| 情况 | `partNoField` | 标识由谁承担 | 料号去哪了 |
|---|---|---|---|
| 模板**有**料号列 | = 该字段（绑值按 §1.3.2） | `partNoField` | 既是可见列，也是 SQL JOIN 键 |
| 模板**没有**料号列 | **留空** | `partNameField`（名称列） | **只在 SQL 里做 JOIN 键**：`AS hf_part_no` 收窄本行、JOIN 取名称、`ORDER BY` 分组，**不出可见列** |

- 后端支持（`ComponentService.assertPartNoFieldRequirement`，2026-07-23 放宽）：`{材质元素,零件,外购件,主件}` 只要求**料号列或名称列至少一个**，两者皆空才 400。
- 类型判定支持（`QuotationTreeService`）：**优先 `partNoField` 取料号值，为空回落 `partNameField` 取名称值**做匹配标识。
- 代价（配置时心里有数）：无料号列时行键只能用名称等业务列（如 `["销售料号","组成件名称"]`），**同名多行会撞键**（editRows 塌缩）；真出现同名多行再回来跟用户确认要不要把料号列显出来。

### 1.3.2 模板确有料号列时 · 绑定值铁律

`partNoField` 绑的列**必须是该 `tabType` 语义层级的料号，禁绑成品/主件料号**。

| tabType | 料号列语义 | 应绑的列（V6） |
|---|---|---|
| 主件 | 成品/产品料号 | `material_master.material_no` |
| 材质元素 | 材质料号 | `element_bom_item.material_part_no` |
| 零件 | 组成件料号 | `material_bom_item.component_no`；`unit_price` 源取 **`code`**（非 `finished_material_no`=成品） |
| 外购件 | 外购组成件料号 | `material_bom_item.component_no`（OUTSOURCED） |

> 原因：`BomNodeTypeResolver` 把每个有类型页签 `partNoField` 取值收集为该类型候选料号；零件页签绑成成品料号 → 树把成品节点误判零件。
> `unit_price` 列语义：`code`=零件料号、`finished_material_no`=成品料号；常同值但语义不同（零件加工费上卷父成品时分叉）——按语义绑 `code`。

## 1.4 交付方式

- **API**（配置/调试）：`POST /auth/login` → `POST /component-directories` → `POST /components` → `POST /components/{cid}/sql-views` → `PUT /components/{cid}/driver-view`。
- **JSON 导入**（标准交付）：暂存目录建组件 → `GET /component-directories/{id}/export` → 用户建目录 → `POST /component-directories/{新id}/import/commit?conflictPolicy=RENAME`。
  - 🆕 **导出/导入现在会校验公式绑定完整性**（task-0805）：导出带 `bindingReport`（点名但不阻断）、导入 preview 逐字段报绑定去向、commit 默认拒未绑定。完整流程见 §1.6。

## 1.5 🚨 配置改动怎么才生效 —— 模板发布与冻结（2026-08-06 task-0806 起，规则已推翻重来）

> **一句话**：**改组件不再影响任何已发布模板**。配置改动要进报价单，唯一路径是**发模板新版本**。

### 1.5.1 旧规则已作废

~~「`ComponentService.update` 成功后自动调 `TemplateService.refreshSnapshotsByComponent`，改字段后报价单立即生效」~~ —— **H1 自动同步已整体退役**（`ComponentService.java:729/783`）。配套的 `POST /components/{id}/refresh-template-snapshots` **端点已删除**（`ComponentResource.java:130`），别再调。

废掉的原因：它绕过了 `docs/三大核心模块基线.md:178` 的架构基线 —— 改一个组件会静默改写最多 6 张已发布模板 + 在途报价单，无提示无留痕（BL-0133 定性「灾难性」）。

### 1.5.2 现行三态

| 模板状态 | 改组件配置会怎样 | 配置怎么才生效 |
|---|---|---|
| **DRAFT** | 无所谓——发布那一刻才按当时的活配置冻结 | 直接 `publish` |
| **PUBLISHED / ARCHIVED**（已冻结） | **完全不受影响**，快照与活表脱钩 | **`createNewDraft` → 改 → `publish` 出新版本**；老版本永远保持原样 |
| **PUBLISHED / ARCHIVED 但零快照**（过渡态） | — | 管理员调 `POST /templates/{id}/freeze` 就地补冻 |

- 冻结落在 `template_component_snapshot` 表（一行 = 一个模板的一个页签），**18 个渲染配置字段全冻**，含以前从不进快照的 6 个：`rowKeyFields` / `sortField` / `elementCodeField` / `elementPriceField` / `elementCurrencyField` / `columnCount`。
- 读取只经 `PublishedTemplateReader`；**读不到就报错，禁止回落活表**。
- 报价单只能绑 `status=PUBLISHED` 的模板（`QuotationService:255`，否则 400）→ **DRAFT 模板不参与渲染**，「改组件立即在报价单看到效果」这条路已经彻底没有了。

### 1.5.3 ⚠️ 「重新发布」不是一个操作

`publish()` **只收 DRAFT**。已发布模板走 `createNewDraft → publish` 只会产出**新版本**，老版本永远冻不上。所以：

- **过渡期存量补冻** → `POST /templates/{id}/freeze`（`SALES_MANAGER`/`SYSTEM_ADMIN`；只改快照，不动 `version`/`status`/`publishedAt`；**仅对零快照模板可用**，否则 409）。**界面上没有按钮**，需管理员调接口。
- 遇到 **HTTP 409 + `data.code=TEMPLATE_NOT_FROZEN`** → 不是故障，是该模板还没冻过，按上一条补冻。判定**只认 `data.code`，禁按 message 文本匹配**。

### 1.5.4 后门（能用但别当日常手段）

`POST /api/cpq/config-center/refresh-all-snapshots`（`SYSTEM_ADMIN`）仍在，但已降级为 **admin 后门**：带 dryRun 预览 + `operation_log.details` 结构化审计，执行时打日志 `[admin-backdoor] refresh-all-snapshots 已执行：已破坏 N 个模板的不可变性`。**它就是在破坏已发布模板的不可变性**，只在明确知道后果时用。

## 1.6 导出 / 导入的公式绑定校验（task-0805，2026-08-06 交付）

暴露点已从「导入提交」前移到「导出」与「导入预览」，让业务用户在**源环境 UI 里**修，而不是去手改 JSON。

| 环节 | 行为 |
|---|---|
| `GET /component-directories/{id}/export` | 产出 `bindingReport`，逐条标 `BOUND` / `RESOLVED_BY_NAME` / `RESOLVED_BY_POSITION` / `UNRESOLVABLE`（条件公式逐规则出报告）。**只点名，不阻断**；`checksum` 不受它影响 |
| 导入 preview | 逐字段 `formulaBinding{resolvedFormulaId,resolvedFormulaName,status}`；有 `UNRESOLVABLE` → `canCommit=false` + blockers **点名到组件与字段** |
| 导入 commit | 存在未绑定 → **默认 400 整包回滚**；显式传 `ignoreUnboundFormulas=true` 才放行，落库标记待绑定，返 `unboundWarnings` |
| `GET /components/{id}` | 新增 `hasUnboundFormula`（该组件有 `FORMULA` 字段既无 `formula_id` 也无条件公式） |
| `POST /api/cpq/admin/formula-binding/consolidate` | 把按名/按位推导出的隐式绑定**固化成 `formula_id`**；支持 `dryRun`，作用域可传 `directoryId` / `componentIds`，**不传 = 全库** |

> 老 bundle（无 `formula_id`）仍可导入，靠按名称解析回退（18 份真实老 bundle 实测全绿）。
