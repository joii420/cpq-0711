## ① 问题描述

**用户原话**：

> 导入材质库时,提示含量非法, 含量有什么校验规则
>
> 导入材质库,会根据材质进行分组算元素含量总和是否大于1吗? 会出现材质名称相同,材质号不同的情况,材质号不同,含量不同

**客观现象**：

材质库 Excel 中存在**同一个材质名称对应多个材质编号**的情况（业务上是多个独立材质，各自有各自的元素配比）。导入时这些材质被**合并成一组**处理，产生两种后果：

| 情形 | 现象 | 是否有告警 |
|---|---|---|
| **A. 两个编号的元素符号重叠**（如都含 Ag、Ni） | 首个编号落库，但**含量被后一个编号的值覆盖**；后一个编号**完全不入库** | 🚨 **无任何告警**，导入报告全绿 |
| **B. 两个编号的元素符号不重叠** | 含量被累加求和 → Σ 远大于 1 → 报 `含量合计≠1(实际2.00)` → **两个材质都不入库** | 有告警，但**归因误导**：报告指向「含量填错」，实际单看每个编号的含量都正确 |

用户最初感知到的「提示含量非法」即情形 B 的表现 —— 报告说含量合计不对，业务核对 Excel 却发现每个材质编号自己的含量合计都是 1。

## ② 复现 / 发现方式

**环境**：`10.177.152.12:5432/cpq_db_0724`（当前开发库）；后端 `MaterialRecipeImportService`；入口「主数据维护 → 材质 → 导入」。

**出现频率**：**必现**。只要「材质编号」sheet 中同一材质名出现在 ≥2 行且编号不同即触发。

**最小复现**（2026-09-01 以临时探针测试真实调用 `importLibrary` 跑通，探针跑后已删除，DB 无残留）：

「材质编号」sheet：

| 材质 | 材质编号 |
|---|---|
| ZZ名甲 | ZZ001 |
| ZZ名甲 | ZZ002 |

「材质对应元素」sheet：

| 材质 | 材质编号 | 元素名称 | 含量 | 元素编号 |
|---|---|---|---|---|
| ZZ名甲 | ZZ001 | Ag | 0.90 | 10001 |
| ZZ名甲 | ZZ001 | Ni | 0.10 | 10003 |
| ZZ名甲 | ZZ002 | Ag | 0.70 | 10001 |
| ZZ名甲 | ZZ002 | Ni | 0.30 | 10003 |

**实测输出（情形 A，符号重叠）**：

```
totalRows=4  materialsUpserted=1  elementRowsInserted=2  skipped=0     ← 零告警
[ZZ001] symbol=ZZ名甲  元素: Ag=70  Ni=30       ← 期望 Ag=90 Ni=10，被 ZZ002 的值覆盖
[ZZ002] 材质未落库
```

**实测输出（情形 B，符号不重叠，材质名 ZZ名乙 / 编号 ZZ003+ZZ004，各自 Σ=1）**：

```
totalRows=4  materialsUpserted=0  elementRowsInserted=0  skipped=1
skip: sheet=材质对应元素 row=null reason=含量合计≠1(实际2.00) raw=code=ZZ003
[ZZ003] 材质未落库   [ZZ004] 材质未落库
```

**旁证（DB 实查）**：

```sql
SELECT count(*) 材质总数, count(DISTINCT symbol) 不同材质名数, count(DISTINCT code) 不同编号数
FROM material_recipe;
-- 258 | 258 | 258
```

258 条材质、258 个材质名、258 个编号，三者完全相等 —— **库里一条「同名不同号」都没有**。这不是数据天生干净，而是这条路走不通、存不进来。

## ④ 问题原因 / 报告

### 根因（一句话）

**元素行的材质编号不是从它自己那一列读的，而是拿材质名去「材质编号」sheet 反查得到的；该反查表用 `putIfAbsent` 构建（首现优先），于是同名材质的第 2 个及以后的编号被静默丢弃，所有同名行被归进同一个组。**

### 证据链（可复跑）

**1. 反查表构建 —— 首现优先，后来的编号被丢弃**

`cpq-backend/src/main/java/com/cpq/configure/service/MaterialRecipeImportService.java:99-107`

```java
Map<String, String> codeByMaterial = new HashMap<>();   // 材质名 → 编号，单值
for (int r = 1; r <= codeSheet.getLastRowNum(); r++) {
    ...
    codeByMaterial.putIfAbsent(mat, code);              // ← 首现优先，第 2 个编号被丢弃
}
```

**2. 元素行的材质编号列（B 列）从头到尾没被读过**

`MaterialRecipeImportService.java:113-117`

```java
String mat      = cellStr(row.getCell(0));   // A 列 材质名
String elemName = cellStr(row.getCell(2));   // C 列 元素名称
String contentRaw = cellStr(row.getCell(3)); // D 列 含量
String elemNo   = cellStr(row.getCell(4));   // E 列 元素编号
// ← 列 1（B 列 材质编号）从未被读取
```

**3. 分组键是 code，但 code 来自材质名反查**

`MaterialRecipeImportService.java:118` + `:139`

```java
String code = mat.isBlank() ? null : codeByMaterial.get(mat);   // 经材质名中转
...
groups.computeIfAbsent(code, k -> new MatGroup(code, mat)).putElement(elemName, content, elemNo);
```

**4. 组内同符号「末值胜」→ 情形 A 的静默覆盖**

`MaterialRecipeImportService.java:403`

```java
void putElement(String sym, BigDecimal content, String no) {
    elements.put(sym, content);      // ← 同符号末值胜；合并后 Σ 恰好仍为 1，校验通过、零告警
}
```

**5. 材质级 Σ 校验在合并之后才做 → 情形 B 的误导性告警**

`MaterialRecipeImportService.java:147-152`：`sum()` 累加的是**合并后**的组，两个材质的含量被加到一起，Σ=2.00 触发 `含量合计≠1`，但归因指向含量而非合并。

### 引入时间线

| 时间 | 事件 |
|---|---|
| 2026-07-09 | `task-260708` 交付，合 master `1aa7b24`。`backtask.md` 决策 #1 定为「`材质编号` sheet 是材质→材质编号**权威映射**」 |
| 同上 | `backtask.md:140` 明确写：「材质编号以 `codeByMaterial` 为准（**不信该 sheet 内可能是 VLOOKUP 公式的列**）」 |

**这是一个有理由的设计决策**（担心元素 sheet 的 B 列是 VLOOKUP 公式、取不到值），但它隐含了一个**从未被写下、也从未被校验的前提：材质名 → 材质编号是 1:1 映射**。当业务数据出现 1:N 时，代码没有任何位置能发现这个前提已被打破。

> 📌 补充事实：`cellStr()`（`:362-384`）**已经处理 FORMULA 单元格**（读 `getCachedFormulaResultType()`），当初担心的「VLOOKUP 列取不到值」在现有代码下并不成立。

### 影响面

| 维度 | 结论 | 依据 |
|---|---|---|
| **DB schema** | **无需改动**。`material_recipe` 仅 `code` UNIQUE，`symbol` 无唯一约束 | `pg_constraint` 实查：`material_recipe_code_key UNIQUE (code)`、`material_recipe_pkey`，无 symbol 约束 |
| **下游引用** | **无歧义风险**。全部按 `code` 或 `id` 查，**无一处按材质名反查** | `MaterialRecipe.findByCodeOrThrow` / `find("code in ?1")` / `findById`；`ConfigureProductService:328,527`、`ModelConfigService:300`、`MaterialRecipeService` 全部按 code/id |
| **UI 列表** | **无需改动**。列表已有「材质编号」列，同名材质可区分 | `MaterialRecipeManagement.tsx:121-122` |
| **material_master 绑定** | 无影响，当前 `material_recipe_id` 非空行数 = 0 | DB 实查 |
| **协议级改动（AP-44）** | **不触发**。不涉及 `field_type` 变动、不涉及跨端契约、不涉及渲染链路 | 改动限于导入服务内部解析逻辑 |
| **存量数据** | 258 条中可能存在情形 A 的静默错值，**本次不处理**（用户裁定） | 见 ③ 明确不做 |

### 为什么测试没拦住

`MaterialRecipeImportServiceTest` 共 11 个用例，覆盖了含量越界、Σ≠1、×100 归一、Upsert 覆盖、元素主表同步、性能、真实文件基线等，**但没有一个用例构造「同一材质名对应两个编号」的输入** —— 这个输入形态从未进入过测试视野。

三层原因：

1. **前提未被写下来**：`backtask.md` 决策 #1 只写了「材质编号 sheet 是权威映射」，没写「且材质名必须唯一」。没写下来的前提，测试无从覆盖。
2. **真实文件基线恰好不含该形态**：`realFile_R1Import_253Materials_1Skip` 用真实 `材质库.xlsx` 断言 253 落库 / 1 跳过。该文件当时没有同名多号的数据，基线绿得很干净。
3. **原验收标准不可执行**：原 AC「正确导入材质库文档数据」是形容词，没有可观测断言，无法据此推导出「同名多号该怎样」的测试用例。

> ⚠️ 情形 A 尤其危险：它**不产生任何跳过记录**，`skipped=0`、报告全绿。即使有人跑了导入，也无从察觉数据已被覆盖 —— 这类「静默通过」的缺陷不会被任何「看报告有没有报错」式的验收拦住。
