- [ ] **BL-0242 · `ROW_SCOPE` 取值列的别名边界：打了标记却「不生效也不报错」**
  - 来源：`task-260911` 结案（2026-09-11 用户裁决登记）· 由 S-全局片验 `AC-9` 通用性时提出、主线读码查实
  - **现象**：给第二个列打上 `ROW_SCOPE` 后，编译器**会**正确生成 `= ANY(:<列>s)` 集合谓词（这半句已验证通过），
    但运行时该收窄**恒不生效** —— 页签看起来正常（1 行、该列为空），**不报错、无告警**
  - **机制**（实查 `RowScopeSupport.lineItemColumnFor:106`）：
    ```java
    return LINE_ITEM_COLUMN_ALIAS.getOrDefault(dbColumn, dbColumn);   // 映射不到就用原列名
    ```
    `SqlViewExecutor.enrichRowScopeSets` 据此执行 `SELECT DISTINCT <列> FROM quotation_line_item`；
    该列若在明细行表上**没有同名列、也没在别名表登记** ⇒ SQL 报错 → **被 catch 返回空集合**
    ⇒ `= ANY(ARRAY[]::text[])` 恒 FALSE ⇒ JOIN 全不匹配 ⇒ 走 `B-6` 兜底 ⇒ **1 行 + 该列置空**
  - ⚠️ **这正是本项目反复栽的静默失败类型**：`customer_product_no` 能工作，是因为它在 `LINE_ITEM_COLUMN_ALIAS` 里
    登记了 `→ customer_part_no`；**下一个列没有这份运气**
  - **可选方向（未裁决）**：① 打标记时校验取值列可解析，解析不到就**拒绝**而非静默降级
    ② 把别名登记做成语义图上的一个字段（与角色同层），而不是 Java 常量表
    ③ 至少在 `queryRowScopeValues` 的 catch 分支打 `WARN` 并带列名（现在只在失败时记，正常路径无信号）
  - 优先级：**P2**（当前只有 1 个列打了标记且工作正常；风险在"下一个人给第二个列打标记"时兑现）
  - 前置条件：无

### [交互] BL-0215 · dataset 维护页改「项次」提示保存成功、实际未存

| 实验 | 结果 |
|---|---|
| 不改任何值原样回传 | `UNCHANGED` |
| 改 `item_seq`，**保留**旧 `row_fingerprint` | `UNCHANGED` |
| 改 `item_seq`，**删掉** `row_fingerprint` 字段 | `UNCHANGED` |

### [报价与核价 · 价格] BL-0269 · 单据级元素价格表（把散在卡片格子里的单据价收敛成一张按元素码组织的表，两侧共用）

- 📌 **重要前提：这件事不是从零新增。** 系统里已有四层价格权威，本条是把其中「单据层」显式化：

  | 版本指针 | `material_price_version_ref` | (客户, **销售料号**) → 版本，调价任务**按料号逐个推进** |
  | **单据层（冻，已存在但形态是散的）** | `snapshot_rows` / `row_data` / `quote_card_values` / `costing_card_values` | **散在每个卡片格子里** |

- **做了会更好的四点**：① 两侧同源，漂移从**结构上**消失（「读同一行」替代「两条链路碰巧一致」）；② 正好补上 `repair-260910` 方案甲的已知缺口（见下）；③ 价格可审计（「这张单的 Ag 为什么是 11690」从翻 JSON 格子变成读一行 + 来源标记）；④ `PriceReconciler` 600 余行「遍历 `snapshot_rows`/`row_data` 格子改价」的复杂度大部分可退役
