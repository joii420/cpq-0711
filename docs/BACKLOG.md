### [跨任务·既有形态·已取证] BL-0222 · 模板一律按 `id` 取，禁止按 `name` 取 —— 同 series 多版本全部重名，`LIMIT 1`/`findFirst()` 会静默取错且随升版单调漂移

- [ ] 待开发 · 优先级 **P2** · 来源：`task-260907-报价导入建单切ds新表` 开发期，并发会话「核价回填」实际被咬 + 主线全库取证（2026-09-07 用户裁决登记）
- **现象**：`template` 的 `name` 标识的是 **series**，`version` 才区分版本；同一 series 的多个版本**全部同名、且可以同时是 `PUBLISHED`**。
  ⇒ 任何按 `name` 查模板的地方都会返多行。
  ```sql
  WHERE template_id = (SELECT id FROM template WHERE name='报价模板 · ds 原生 v1.0')
  → ERROR: more than one row returned by a subquery used as an expression
  ```
- 🔑 **这是既有约定，不是缺陷，也不是某个任务引入的**（全库取证）：
  ```
  同 series 有多个 PUBLISHED 的 series 数 = 7，且每一个的「不同名字数」都是 1：
    测试客户-4      6 个版本 v1.0~v1.5   全同名
    施耐德BUG2      4 个版本             全同名
    核价模板1 / 罗克韦尔模板3         各 3 个   全同名
    报价模板·ds原生 / 组件模板测试 / 罗克韦尔模板1   各 2 个   全同名
  ```
  🚫 **因此不能靠「把旧版改名或置非 PUBLISHED」来治** —— 旧版是**在役**的
  （`df379593` v1.0 挂着 11 张单 / 20 个报价行），置非 PUBLISHED 会打断它们；
  改名会让该 series 成为全库唯一不守约定的一个。**要治的是查询侧。**
- 🚨 **报错还算好的，静默取错才致命**：用 `LIMIT 1` / `findFirst()` 的地方会取到其中一个而不报任何错。
  **而且「取哪个」是单调漂移不是随机** —— 以 `ORDER BY created_at DESC` 为例：
  它会**先正确一段时间**（写代码时确实取到最新版），然后在**某次升版之后开始取错**，
  ⇒ **升版动作与它的失效之间没有任何因果可见性**，排查的人会去查升版那条线，而不是查这段查询。
- **要做的**：
  1. 全工程审计按 `name` 查 `template` 的位置（Java + SQL 配置 + 测试夹具），一律改按 `id`；
  2. 确实只有名字可用时，必须**显式**写清取哪一版（如 `AND status='PUBLISHED'` + 按 `template_series_id` 取 `max(version)`），
