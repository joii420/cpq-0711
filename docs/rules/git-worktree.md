# 规则分册 · worktree / 分支 / 提交 / 并发

> **何时必读**：建分支或 worktree、提交、合并、多会话并发作业、收尾清理。
> **效力**：与 `CLAUDE.md` 同等，不是参考资料。冲突时以 `CLAUDE.md` 为准。

---

## 1. worktree 共享约束

worktree 只隔离 **git 工作区 + 分支**。以下仍是**共享**的：

- 前后端 dev server
- 远程数据库
- 依赖目录（`node_modules/` 等）与各类构建缓存

**默认不在 worktree 里另起 dev server** —— 复用主工作区已运行的实例。

### 1.0 📁 worktree 一律建在项目内的 `.claude/worktrees/`

```bash
# 建之前先确认 .gitignore 里有这一行（顺序不能反，否则会有一瞬间的脏状态）
grep -qx '.claude/worktrees/' .gitignore || echo '.claude/worktrees/' >> .gitignore

git worktree add .claude/worktrees/<任务名或分支名> -b <分支名>
```

**为什么放项目里而不是同级目录**（`../<项目名>-<任务名>`）：

| | `.claude/worktrees/<名>` | `../<项目名>-<名>` |
|---|---|---|
| 项目同级目录 | ✅ 不变乱 | ❌ N 个 worktree 就是 N 个同级目录 |
| 归属 | ✅ 一眼可见 | ⚠️ 靠前缀猜 |
| 清理 | ✅ 一处看全 | ❌ 散着找 |
| 删项目时 | ✅ 一起消失 | ❌ 残留成孤儿 |
| `git status` | ✅ 干净（靠 gitignore） | ✅ 干净 |

> ⚠️ **`git status` 会不会被污染，取决于 gitignore 有没有那一行，不取决于放在哪。**
> git 允许 worktree 建在主仓库目录内部 —— 实测某项目在 `.claude/worktrees/` 下挂了 **14 个** worktree，`git status` 仍是 0 行。

🚫 **不要建在 `.claude/worktrees/` 之外的项目内路径** —— 那些位置多半没被 gitignore，会立刻污染 `git status`，而本册整套并发纪律都建立在 `git status` 可读这个前提上。
⚠️ 已经建在同级目录的，用 `git worktree move <旧路径> .claude/worktrees/<名>` 迁移，分支和提交不受影响。

### 1.1 🚨 未跟踪 / 未提交的文件**不会**进 worktree

`git worktree add` 是**从某个 commit 检出**的。凡是 git 不认识的文件，新 worktree 里一概没有：

| 典型漏掉的 | 症状 |
|---|---|
| **`.env` / `.env.local`**（通常被 gitignore） | 连接串为空，服务起不来；或更糟——**回落到默认值**，静默连到别的库 |
| 本地库文件（`*.db`） | 同上 |
| 未提交的任务文档 | 子代理进去找不到任务书，然后**自己猜该实现什么**（`subagents.md §1①`） |
| 本地证书 / 密钥 / 缓存 | 构建或调用外部服务时才炸 |

建完 worktree **立刻验一遍**：把主工作区的 `.env` 等未跟踪配置**拷过去**（不是软链，避免一改两边都变），然后确认服务能在 worktree 内起来。

### 1.2 🚨 worktree 必须用**独立的库**，且要验明正身

子代理在 worktree 里跑 `seed` / 迁移 / 集成测试，**如果连的是主工作区那个库，会清掉主线亲验要用的数据**。

两个坑叠在一起，单看任一个都不致命：

1. **相对路径连接串**（如 `file:./dev.db`）在 worktree 里**看起来**是隔离的，实际解析结果取决于进程的工作目录
2. **共享的依赖目录**里，ORM 客户端可能把**主仓的 schema / 库路径烤死**在生成的代码里 —— 于是即使连接串写对了，跑的还是主仓的库

🚫 **不许靠「行数对得上」判断连的是哪个库** —— 两个库内容相同时这个判据完全无效。
✅ **正确做法：写标记再读回来**。往目标库插一条只有它才有的探针记录，再从被测进程读一次；读得到才算连对。（这就是 `testing.md §4.2` 的「验明正身」用在库上。）

配套三条：
- 派工 prompt 里**写死绝对路径**的连接串覆盖，不要依赖相对路径
- 禁止子代理在 worktree 里重新生成 ORM 客户端（会污染共享依赖目录）
- 亲验前确认主工作区的库**没被动过**（比对探针 / 基线行数 + 关键值）

### 1.3 🚨 共享 dev server 是最大的自检陷阱

> **共享 dev server 服务的是主工作区代码，看不到 worktree 里尚未合并的改动。**
> 拿它"验证" worktree 内的改动，得到的是**主仓代码的结果**，是假绿。

worktree 内改动的自检手段，**按此顺序降级使用**：

1. **静态检查**（类型检查 / lint）—— 这类工具按路径读真实文件，可信，**优先用**
2. **确证文件内容**而非只看接口响应（`grep` 改动特征串）
3. 前两步不足以确证时，**才**软链依赖 + 用**另一个临时端口**短暂起服务，**用完即停**（这是「默认不另起」的唯一例外）
4. **数据库迁移**：共享 dev server **不会**执行 worktree 里的迁移文件，需复制到主仓触发，**合并前记得删掉副本**

⚠️ **端口避让**：临时端口给子代理和探索性验证用；**声明端口（`CLAUDE.md` §1 表里那个）保留给主线亲验**，谁都不要占。

### 1.4 依赖按三分支判断，不是一刀切禁止安装

| 情况 | 做法 |
|---|---|
| 主工作区**已有**该子项目的依赖目录 | **软链复用**，不重装 |
| **绿地 / 新建子项目**，主工作区还没有 | **在 worktree 内装**（没有东西可软链，不可避免）；回报里说明装了什么 |
| 依赖清单（`package.json` 等）**有增删** | 在 worktree 内装；**合并后主工作区补装一次** |

⚠️ 无论哪种，**删 worktree 前把装好的依赖目录移到主工作区** —— `git worktree remove` 会连它一起销毁。

## 2. 合并（生命周期步骤 5）

合并看起来只是「切回 master → merge → 跑测试」，**但在多会话并行下这三个动作各藏一个坑**，而它又恰好是全流程唯一**不等用户点头就执行**的高风险动作。按序执行，不要跳步：

### ① 更新 master —— 先拉到最新再 merge

并发会话可能已经推进过 master，甚至改了你依赖的同一批文件。
**基于陈旧 master 合出来的结果，测试再绿也不代表合进去是对的。**

### ② merge —— 冲突分两档，处理方式完全不同

| 冲突类型 | 例子 | 怎么办 |
|---|---|---|
| **技术冲突** | import 顺序、格式、互不相干的相邻行 | 自行解决，但解完必须 `git diff` 复核一遍 |
| **业务冲突** | 同一函数两边都改了逻辑 / 同一 AC 两种实现 / 迁移版本号撞车 / 同一契约字段两边定义不同 | 🚦 **停下来问用户** |

🚫 **业务冲突不许自行裁决"谁的版本对"** —— 那是在替另一个会话做需求取舍，而**你看不到它的上下文**。

### ③ 清构建产物 —— 合并后、跑测试前先清一次

🚨 **worktree 全绿 ≠ 主仓全绿。**
典型：本次删掉了某个源文件，主工作区的构建产物目录里**对应的旧编译结果还在** —— 于是主仓照样能跑（跑的是幽灵），或反过来启动即失败。
**worktree 里看不出来**，它的产物目录是干净的。

### ④ 在主工作区跑全量测试 + 自检

不是"跑一下确认"，是把 `frontend.md` / `backend.md` 的自检项在**主工作区**重跑一遍。

### ⑤ 红了怎么办 —— 必须有出口，不许"边跑边修"

🚫 **禁止在 master 上边跑边修**：master 是其他会话的基线，你修一版跑一版的中间态会被别人拉走。

→ 立刻 `git revert` 掉这个合并提交，把 master 恢复到可用状态，然后回 worktree 修，修完重走步骤 5
→ 在闸门 B 汇报里说明「合并回退过一次，原因是 X」，**不要隐去**

### ⑥ 清理 —— 确认绿了才做

- ⚠️ 删 worktree 前，把装好的依赖目录移到主工作区（见 §1.4）
- 删 worktree 目录 + 删特性分支
- 🧹 确认 `git status` 干净：本次产生的临时脚本 / 中间产物不许留在仓库里（见 §4）
- 🚦 **冷启动验证**（见 `testing.md` §5）—— 合并后的 master 必须能从零跑通
- 回写 `docs/RECORD.md` 与 `dev-docs/INDEX.md`（**此时删掉「未合并分支」那一行**）

## 3. 并发纪律

- 多会话各用自己的 worktree 分支并行，避免污染主工作区
- **提交只 `git add` 本次明确改动的文件，严禁 `git add -A`**（同分支并发提交会交错，会把别人的改动夹带进你的提交）
  > ✅ **唯一例外：空仓库的首次提交**（`bootstrap.md §2.0` 建仓库那次）。此时不存在「别人未提交的改动」可夹带，`git add -A` 是安全且正确的。
  > 例外仅此一次 —— 仓库一旦有了第一个 commit，本条禁令即全面生效。
- ⚠️ **`git commit` 提交的是整个暂存区，不是你刚 add 的那几个路径。** 暂存区若有他人/前序遗留的改动会被一并带走。
  必须用 `git commit -- <paths>` 限定路径，并在提交后 **`git show --stat` 自查有无夹带**
- 🚫 **已应用到共享库的迁移文件，禁止改名、改版本号、删除**（属 `CLAUDE.md` §3.2 红线「契约销毁」）

### 3.1 共享文档的并发写

`docs/RECORD.md`、`dev-docs/INDEX.md`、`docs/BACKLOG.md` 是**多会话同时追加**的高频写点。上面几条只管代码提交范围，管不到它们 —— 而它们才是最容易被静默覆盖的：**内容丢了不报错、不影响构建、不影响测试，只在几周后有人来查历史时才发现那段没了。**

1. **只追加，不重写。** 一律用「在末尾/对应小节追加」的方式，不要整篇重写或大段重排
2. **冲突一律取并集。** 这三个文件的合并冲突**没有"谁的版本对"** —— 两边都对，两边都要留。
   🚫 禁止择一保留，禁止用 `--ours` / `--theirs` 一把梭
3. **写之前先拉最新**，别在陈旧副本上追加

### 3.2 撤销自己的改动时要小心别人的改动

要撤回自己刚写的内容时，**先确认目标文件在你动手前是不是已经是 modified 状态**：

```bash
git diff --stat <file>     # 看有几处改动
git diff <file>            # 逐处确认哪些是你的
```

🚫 **文件若在你动手前就已被别人改过，禁止 `git checkout <file>`** —— 那会连别人未提交的工作一起丢掉（属 §3.2 红线「历史销毁」）。
✅ 正确做法：**用编辑器精准删掉自己加的那几行**。

## 4. 工作区卫生

**临时脚本、中间产物、调试输出、导出的 SQL / JSON —— 一律不落仓库根目录。**

放哪：会话的 scratch 目录（若有），或本任务的 `dev-docs/<任务目录>/`（确实要随任务留存的证据才放这儿）。

- 🧹 **收尾前确认 `git status` 干净**：没有本次产生的未跟踪垃圾文件
- 确实要长期留在仓库里的调试脚本 → 放进 `scripts/` 并写一行用途注释，不要用 `tmp_` / `.tmp_` 这类名字
- 发现仓库里已有历史遗留的临时文件 → **在收尾汇报里列出来问用户要不要清，不要自行删除**（删文件属红线，且你不知道谁还在引用它）

> 为什么单列：这类文件不报错、不影响构建，谁都不会主动清理，于是只增不减。攒到几十个之后，`git status` 就再也无法用来判断「我这次改了什么」——**而本章整套并发纪律都建立在 `git status` 可读的前提上。**

## 5. 本册自检清单

建分支时：
- [ ] **建在 `.claude/worktrees/<名>`**，且 `.gitignore` 里已有 `.claude/worktrees/`（§1.0）
- [ ] 任务文档**已提交**再 `git worktree add`（否则 worktree 里没有它）
- [ ] **建分支那一刻**就在 `dev-docs/INDEX.md` 态势表写下「未合并分支」——不是开发完再写
  > ⚠️ 等开发完再写就晚了：中途会话中断、上下文丢失，那条分支会变成没人知道的孤儿。
  > 删除侧绑在合并后（见「收尾时」最后一项）。

开发中：
- [ ] 没拿共享 dev server 验证 worktree 内的改动
- [ ] 临时端口起的服务用完即停，没占用声明端口
- [ ] 🚨 **主线改了任务文档（AC / 契约 / 原型）后，立刻同步进 worktree 分支并验证**（见下）

### 🚨 开工后改任务文档，必须同步进 worktree 分支（2026-09-03 task-260902 教训晋升）

**主线在主工作区（`master`）改 AC/契约/原型并提交，worktree 分支上的同名文件不会自动更新。**
子代理读的是**它自己 worktree 里的路径**（派工 prompt 就是这么写的），于是它照着**旧版文档**继续干活 —— 而且**不报错**。

真实发生过的一次：主线修订了 AC、补了原型状态、改了 `api.md` 的跳过原因表，全部只提交在 master；
worktree 里的文件还停在几小时前的版本。是**前端工程师发现文件时间戳不对**、自己跑去主工作区读了真原型才做对的。

⚠️ **若无人发现，合并进来的会是一份「代码按新 AC 写、文档还是旧 AC」的交付** —— 验收标准与实现对不上，且事后极难看出来。

**做法（三步，缺一不可）**：

```bash
# 1) 在主工作区提交文档改动（路径限定）
git commit -- <改动的文档路径>
# 2) 立刻同步进分支
cd .claude/worktrees/<名> && git merge master --no-edit
# 3) 验证同步真的到位 —— 不要只看 merge 成功
grep -c "<本次新增的关键词>" dev-docs/<任务目录>/需求文档.md   # 期望 ≥1
git log --oneline master ^HEAD | wc -l                          # 期望 0
```

📌 **更省事的替代做法**：开工后干脆**在 worktree 分支里改任务文档**（反正最终要合回 master），主工作区不碰。
🚫 **无论走哪条，都必须在改完后通知正在跑的子代理重读** —— 它不会自己发现文档变了。

提交时：
- [ ] 没用 `git add -A`
- [ ] 用了 `git commit -- <paths>` 限定路径
- [ ] `git show --stat` 自查过没有夹带

合并时：
- [ ] master 已更新到最新
- [ ] 业务冲突已回问用户，没有自行裁决
- [ ] **清过构建产物**再跑的全量测试
- [ ] 红了的话已 `git revert`，没有在 master 上边跑边修

收尾时：
- [ ] 依赖目录已移回主工作区，再删的 worktree
- [ ] `git status` 干净，无临时文件残留
- [ ] 跑过冷启动验证
- [ ] `INDEX.md` 的「未合并分支」行已删除
