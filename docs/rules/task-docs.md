# 规则分册 · 任务文档与 AC

> **何时必读**：走路径 A 立项、写任务文档、写 AC、BUG 返修立项、闸门 A 自检、闸门 B 归因。
> **效力**：与 `CLAUDE.md` 同等，不是参考资料。冲突时以 `CLAUDE.md` 为准。

---

## 1. 目录约定

`dev-docs/task-YYMMDD-<任务名>/`，子任务与返修任务（`repair-YYMMDD-<任务名>`）挂在主任务目录下。

> 📅 一律用 **6 位 `YYMMDD`**。4 位 `MMDD` 跨年必撞号，而「要不要加年份」不该成为一个需要判断的分支——多两个字符换掉一个决策点。
>
> 🚫 **日期必须实取，不许凭记忆写**：建目录前先跑 `date +%y%m%d`，用它的输出。文档里写「今天」「本周」一律换成绝对日期。
> 理由：模型对当前日期的记忆不可靠，写错了目录名就永久错位——而目录名是索引、跨文档引用、`git log` 三处的共同锚点，事后改名要同步改三处。
>
> ⚠️ **接手既有项目时**：先看现存目录用的是哪种格式，**跟现存惯例走**，不要在半途切换命名风格。要统一另立任务统一改。

🚫 **目录层级上限 = 2 层，禁止第三层。主任务下的所有子任务和返修任务一律平铺**：

```
✅ dev-docs/task-260801-公式精度优化/{task-260810-显示位数调整/, repair-260812-阈值不对称致误报/}
❌ 把 repair- 建在 task-260810- 里面 ← 第三层，禁止
```

即使这次返修修的是某个子任务，也仍然建在**主任务**目录下，只在文档开头注明一行「**返修对象**：`task-260810-显示位数调整`」。

**什么时候建子任务、什么时候另起主任务**（判不准就问用户）：

| 情况 | 放哪 |
|---|---|
| 同一需求的延续、细化、二期 | 该主任务下的**子任务** |
| 修既有任务交付物的缺陷 | 该主任务下的 **`repair-`** |
| 独立需求，与既有任务无共享验收标准 | **新主任务** |
| 跨多个既有主任务 | **新主任务**，在文档里列出关联的主任务 |

> 理由：嵌套超过两层后，索引的反查表和路径引用都会失准，且同一主线的返修散落在不同深度，无法一眼看全。**归属关系靠文档里的「返修对象」字段表达，不靠目录深度。**

## 2. 文档清单

| 文档 | 作用 |
|---|---|
| `需求文档.md` | 该任务的验收标准。**常规任务必写**，格式见 §3 |
| `问题说明.md` | **返修任务专用**，取代 `需求文档.md` 作为立项文档，格式见 §5 |
| `fronttask.md` / `backtask.md` | 前 / 后端任务分解，**每项必须标「服务的 AC」**，格式见 §6 |
| `api.md` | 接口契约 |
| `test.md` | **测试方案 + AC 可追溯矩阵（含「分片」列）**。闸门 A 的**前置产物**，开工前写完。分片依据见 `testing.md §4.5` |
| `test-report.md` | 测试**执行**结果。开工后测试进场执行完才产出 |
| `原型图/*.html` | **页面设计类改动必出**，规范与触发条件见 `frontend.md §1.3`。同为闸门 A 的**前置产物**，定稿后即验收基准 |

**前端或接口零改动的任务也要写 `fronttask.md` / `api.md`**，内容是「为什么不改」的判定依据 + 回归确认清单 + 二期触发条件。
**宁可写细，不可留空槽** —— 留空槽 = 该文档未完成。

**与 PRD 的层级关系**（避免两个「唯一标准」打架）：

- `docs/PRD.md` 是**产品级唯一标准**，跨任务、长期有效
- 任务的立项文档是**该任务的验收切片**，只对本任务有效
- 🚫 **任务文档不得与 PRD 冲突。** 发现冲突时**先更新 PRD，再改任务文档**，不许两边各写各的
- 冲突未消解前，**以 PRD 为准**

## 2.5 跨任务接口总账：`main-api.md` 回写（**强制**）

`dev-docs/main-api.md` 是全项目接口契约基线（当前覆盖 87 个 Resource / 约 413 个端点，按 12 大类组织）。**任务里的 `api.md` 只是本次任务的局部契约，必须回写到总账，否则总账会失真。**

| 项 | 规定 |
|----|------|
| **时机** | **任务测试完成后**（`test-report.md` 已产出、缺陷闭环）、**合并 master 之前** —— 让总账随本次任务一起进 master |
| **责任人** | 主线（技术总监）执行，或指派后端工程师执行、**主线必须复核** |
| **粒度** | 以**端点**（HTTP 方法 + 路径）为单位 |
| **方式** | **直接覆盖**：总账里已有同方法+路径的端点 → 用本次 `api.md` 的定义**整段替换**（不保留旧版本、不写变更历史）；总账里没有 → 追加到对应模块的 `###` Resource 小节下；本次**删除**的端点 → 从总账移除 |
| **标注** | 每个被本次覆盖 / 新增的端点小节**末尾加一行来源标记**（只记**最后一次**，不累积）：<br>`> 来源任务：\`task-260729-客户价格调整策略和价格版本\`｜回写日期：2026-08-05` |
| **文件头** | 同步更新 `main-api.md` 头部的日期说明，注明最近一次回写来自哪个任务 |
| **并发冲突** | 两个任务同时改同一端点时，**以合并进 master 的先后为准**：后合并者以自己的 `api.md` 覆盖，并把来源标记改成自己 |
| **不回写的后果** | 总账与实现脱节 → 后续任务照总账设计接口必然踩空。**未回写不得进入合并环节** |

> 只改了实现、没改契约（方法/路径/参数/响应/错误码全未变）的任务可跳过回写，但要在 `test-report.md` 里写明"本次无契约变更，无需回写 main-api.md"。

## 2.6 存量兼容

历史目录中大量使用 `需求说明.md`（27 处）而非 `需求文档.md`（5 处），另有 `testcase.md`、`测试用例.md` 等变体。

- **新建目录一律用本规则的命名**：`需求文档.md` / `test.md` / `test-report.md`
- **存量文件视为等价，不强制改名**（改名会打断 `CLAUDE.md`、`RECORD.md` 里的既有引用）
- 接手存量任务时：`需求说明.md` 就是它的 `需求文档.md`，按同等效力对待

---

> 🚨 **同一条理由适用于目录名**：改名会打断 `CLAUDE.md` / `RECORD.md` / `INDEX.md` / `git log` 里的既有引用。
> 要改必须**同批全改 + 同步所有引用**，否则宁可不改。

## 3. `需求文档.md` 规范（常规任务）

**五节齐全，缺一节即视为未完成**（与 `问题说明.md` 的六节同等刚性——BUG 流程有硬规范而新功能流程靠自觉，是最容易漏的不对称）：

| 节 | 要求 |
|---|---|
| **① 背景与目标** | 为什么做、解决谁的什么问题、不做会怎样 |
| **② 范围** | **两栏都要写**：<br>**做什么** —— 本次交付的功能点清单<br>🚫 **明确不做什么** —— 讨论中提过但本次不做的、看起来顺手但不在本期的。每条注明去向（进 `BACKLOG.md` / 已否决及理由） |
| **③ 验收标准（AC）** | 按 §4 写，三类覆盖齐全 |
| **④ 依赖与影响面** | 依赖哪些既有模块/接口/数据；会波及哪些现有功能（需回归的清单）；是否触碰 `docs/架构基线.md` 的基线项——**触碰了必须点名是哪一条** |
| **⑤ 用户原话与素材归档** | 用户的需求原话（不要只写你的转述）+ 截图/表格/样例数据**拷进本任务目录**并用相对路径内嵌。不许写「见聊天记录」 |

🚫 **第 ② 节的「不做什么」不是可选项。**
下游规则花了大量篇幅拦「超范围」，但**拦的都是下游** —— 真正的源头是立项时范围边界没写下来。边界只存在于对话里，它就只存在于当次会话里；下一个会话（或子代理）看到一份没有边界的需求文档，"顺手也做了"就成了合理推断。

## 3.5 轻量档：一份 `任务.md` 顶六件套

触发判据在 `CLAUDE.md §4.3`「进了路径 A，再判一次档」。**本节只说产出长什么样。**

🚫 **轻量档不是「少写点」，是「把六件套压进一份文件」** —— 每一节仍要写，只是不再各占一个文件：

| 标准档 | 轻量档 |
|---|---|
| `需求文档.md` 五节 | `任务.md` 的 ①~⑤ 节，**五节一节不少**（含「本期明确不做」和用户原话归档） |
| `fronttask.md` / `backtask.md` | `任务.md` 的「⑥ 任务分解」，**仍按 §6 分条编号并标「服务的 AC」** |
| `api.md` | 并入「⑥」；接口零改动的写一行「为什么不改」 |
| `test.md` | `任务.md` 的「⑦ 测试方案 + AC 可追溯矩阵」，**矩阵的「分片」列照填** |
| `test-report.md` | **仍独立成文件** |
| `原型图/*.html` | **触发条件不变**，页面设计类改动照出 |

> 🚨 **`test-report.md` 为什么不能并进去**：它是**开工后**产出的证据，而 `任务.md` 是**闸门 A 定稿**的立项文档。
> 合成一份，立项文档就会在开工后被反复改写 —— 到闸门 B 时你已经分不清「AC 原文」和「后来对着实现调过的 AC」，追溯链当场作废。

🚫 **压成一份不等于可以省节。** 判据是「**这一节的内容还在不在**」，不是「文件还在不在」——
留空槽仍然是文档未完成（§2）。**宁可在一份文件里写细，不可拿「轻量」当漏写的借口。**

**闸门与验收完全不变**：闸门 A 照过（§7 自检三项照做）、主线亲验四条照走、闸门 B 照报、结案输出照给。

**A0 在轻量档里天然不适用** —— 判据 ③ 已要求「修法唯一」。
⚠️ 一旦发现有第二种合理改法，**当场升回标准档走 A0**，不要在轻量档里私自做方案裁决。

## 4. AC 编写规范

每条 AC 独立编号（`AC-1`、`AC-2`…），且**必须可执行**——三要素缺一不可：

| 要素 | 含义 | 反例 → 正例 |
|---|---|---|
| **前置状态** | 什么数据、什么角色、什么入口 | ~~"打开页面"~~ → "以销售角色打开客户 A 的报价单 QT-001（含 3 个产品）" |
| **操作步骤** | 点哪里、填什么 | ~~"编辑数量"~~ → "在页签「投料」第 2 行数量列填 5，失焦" |
| **可观测断言** | 具体数值 / 具体文案 / 具体行数 | ~~"金额正确"~~ → "该行小计显示 1250.00，页签合计从 3000.00 变为 4250.00" |

🚫 **禁止形容词 AC**：「正确显示」「性能良好」「体验流畅」「符合预期」。
**写不出可观测断言的条目不是 AC，是愿望** —— 打回需求文档重写。

### 🚨 AC 里引用的「事实」必须实查，不许凭记忆写（2026-09-03 task-260902 教训晋升）

AC 的可观测断言里经常要引用**客观事实**：DB 列长、枚举取值、约束（NOT NULL / UNIQUE）、默认值、现网数据分布。
**这些一律要在写 AC 时当场查出来**，🚫 不许按印象写一个"看着差不多"的数字。

| 反例（真实发生） | 后果 |
|---|---|
| AC 写「用户名填 **65** 个字符（超 DB 列长）→ 应跳过」 | 实测 `username` 是 `varchar(100)`，**65 根本不超长** ⇒ 用例照字面写，得到「应跳过却创建成功」的**假红**，工程师要反过来怀疑实现 |
| AC 的跳过原因表**没有一条邮箱规则** | 实测 `email` 是 `NOT NULL + UNIQUE`，不拦就是 INSERT 撞约束 ⇒ **整批 500**，而同一份 AC 里另有一条明写「不许抛 500」，**AC 自相矛盾** |
| 基准查询写 `WHERE status='ACTIVE'`，而契约写「不传即全状态」 | 两个数字永远对不上，验收时分不清是功能坏了还是 AC 错了 |

#### 🚨 实查了 ≠ 查对了：两个方向的补充（2026-09-16 `task-260915` 实证晋升）

上面那条防住了「凭印象写」，**防不住下面两种**，而它们在同一个任务里各发生了一次：

| 形态 | 真实发生 | 后果 |
|---|---|---|
| **查错数据源** | 主线实查 dev 库 `cpq_db_0724` 写 AC（目录组件 10 个、builder 视图 6 份），而测试跑在 **`cpq_db_test`**（实为 9 个、5 份） | 写死字面量的断言**在测试库红，且红得像业务回归** —— 实现根本没问题 |
| **只查了链路的一半** | 主线实查**导出端** `computeChecksum` 后断言「加字段自动纳入，老包 checksum 仍自洽」—— 该句对导出端成立；**没查导入端** `verifyChecksum`，而它拿反序列化后的 DTO 重算，老包必然失配 | 后端 A/B 实测 `23/2` 恶化为 `23/18`；若照文档执行，每份合法老包都会挂「可能被改动或损坏」的假警报 |

**两条纪律**：

1. **查测试实际会跑的那个库**（本项目 `mvnw test` 走 `cpq_db_test`，见决策台账 `DEC-0001`）。
   更稳的做法是 **AC 里一律不写死条数** —— 写成「查源实际值 → 断言目标与源相等」，并**配非空前置**
   （相对断言在源恰好为 0 时会让 `0 == 0` 静默空跑）
2. **跨端契约的事实要查链路两端**（导出 ↔ 导入、写入 ↔ 读取、序列化 ↔ 反序列化）。
   只查一端就下「整条链路成立」的结论，与 `CLAUDE.md §5`「『这段代码存在』≠『用户能走到它』」同族

**怎么做**（成本极低，一条 SQL 的事）：

```sql
-- 列长 / 可空 / 类型
SELECT column_name, data_type, character_maximum_length, is_nullable
  FROM information_schema.columns WHERE table_name='<表>';
-- 唯一约束 / 主键
SELECT conname, pg_get_constraintdef(oid) FROM pg_constraint
 WHERE conrelid='"<表>"'::regclass AND contype IN ('u','p');
-- 现网取值分布（判断某条 AC 会不会因为"现网没这种数据"而空跑）
SELECT <列>, count(*) FROM <表> GROUP BY 1 ORDER BY 2 DESC;
```

⚠️ **最后一条同样重要**：某维度现网若只有单一取值（实测 `recipe_type` 259 条**全是 `locked`**、`process_master` 全是非外协），
那么「筛该维度后断言集合相等」的 AC **会筛出空集、断言空跑、用例照样绿** —— 这类 AC 必须配套要求用例**自造前缀化数据**，否则是又一个假绿。

**AC 集合必须覆盖三类，缺类即视为需求文档未完成**：

1. **单点 AC** —— 单次操作的正确性
2. **序列 AC** —— 用户真实使用是**有状态的连续操作**。至少一条描述「做 A → 做 B → 切走再切回 → 刷新页面」，并断言**中间态与最终态**
3. **边界 AC** —— 空数据 / 超长输入 / 并发编辑 / 权限不足

### 开工后 AC / 契约变更（并行开发下最危险的一件事）

**四步缺一不可**：

1. 🚦 **回用户确认** —— 加 AC = 扩范围。不能主线自己裁完继续走
2. **同步四处**：`需求文档.md` 的 AC → `api.md` → `fronttask.md` / `backtask.md` 的 AC 映射 → `test.md` 的追溯矩阵。**漏一处链就断了**
3. ⚠️ **主动通知所有在跑的子代理** —— 续跑或杀掉重派
   🚨 **已经跑完的片同样要管**（2026-09-16 `task-260915` 实证晋升）：「在跑」两个字会让**已完成**的片从动作清单里消失，
   而它的结论**已经因 AC 变更而失效**。⇒ 逐片过一遍：**这条 AC 变更影响到哪些片的结论？** 受影响的已完成片**必须显式派回去重跑**，
   🚫 不能因为「它已经交了」就当结论仍然成立。
   > 📌 实证：用户裁决改了 `AC-11` 的判定口径（引文按要点算），主线同步了文档、却没让**已跑完**的 S-B 改断言重跑 ——
   > 该 AC 的红一直挂着，直到另一片的测试员顺手看了一眼 surefire 报告文件的时间戳（`19:43 failures="1"`）才发现。
   > 🔑 **「改 AC」与「让受影响的片重跑」是两个动作**，做了前者不等于做了后者。
4. 变更后重跑闸门 A 的三项自检
5. 🚨 **声称「已同步」前，逐处 grep 复核** —— 本任务实测：主线在派工消息里说「任务书已更新」，实际只改了四处里的三处（漏 `backtask.md`），
   是后端子代理 `grep '^## B-'` 才发现的。**「我改过了」的感觉在漏改时与没漏时一样牢固。**

> 🚨 **为什么第 3 步必须显式做**：子代理在派出时读过一次 `api.md`，那份内容就**冻结在它的上下文里**。之后文件改了**它不会知道**，也不会主动重读。
> 典型后果：前端按新契约写完了，后端还在按派出时的旧契约写，联调才发现。

## 5. BUG 返修任务的立项流程

前提：`CLAUDE.md` §4.3 已与用户确认走**路径 A**。

用户提出 BUG 后，**不要直接改代码**，按序走：

1. **定位归属任务** —— 先过 `dev-docs/INDEX.md` 的「按症状反查」和「按代码文件反查」，确认属于哪个**主任务**。查得到就挂过去；确实无归属才新建主任务目录。**判不准就问用户，不要猜。**
2. **建返修目录** —— 在该主任务目录下建 `repair-YYMMDD-<问题简述>/`（**平铺，遵守两层上限**）
3. **只写 ①~④ 四节** —— 问题描述 / 复现方式 / 需求结果 / 问题原因。**写到根因为止就停下，不要往下写修复方案。**
4. 🚦 **闸门 A0：方案裁决（不可跳）** —— 在**对话里**呈报，等裁决：
   - 一句话根因
   - 2~3 个候选方案，每个标注：改动面 / 代价 / 风险 / 是否触发协议级改动
   - **明确推荐哪一个 + 为什么**
   - 🚫 **此时不许把候选方案写进 `问题说明.md`** —— 文档记录裁决结果，不记录提案过程
5. **补写 ⑤⑥** —— ⑤ **只填用户裁决通过的那一个方案**；⑥ 写验收标准
6. **其余文档照写** —— 按 §2 补齐；零改动的也要写「为什么不改」
7. **走闸门 A** —— 完整文档经用户确认后，才建 worktree 动代码

> **为什么拆成 A0 和 A**：根因定位是 Claude 的活，方案选型是用户的活。合在一起写完再给用户看，用户拿到的是**既成事实**而不是**待裁决项** —— 会默认顺着已写好的方案往下走，选择权实际被架空。

### `问题说明.md` 的六节

| 节 | 要求 |
|---|---|
| **① 问题描述** | 用户原话 + 客观现象 / 报错文案。**用户提供了截图必须嵌进 md**：图片拷进本返修目录，用相对路径 `![现象](./图名.png)`，不许只写「见聊天记录」 |
| **② 复现 / 发现方式** | 谁怎么发现的 + 前置数据（哪个单据/客户/记录）+ 可执行操作步骤 + 环境/库 + 出现频率（必现/偶现）。偶现必须写明已知触发条件 |
| **③ 需求结果** | 期望行为逐条列（`E-1`、`E-2`…），注明对照哪条 AC。**必须同时写反向期望**（「该报的仍要报」「该拦的仍要拦」），防止修成「把告警关了」。找不到对应 AC = 需求有缺口，先补 AC |
| **④ 问题原因 / 报告** | 根因 + 证据链（须可复跑）+ 引入时间线（哪个提交引入、之前为什么不犯）+ 影响面 + **为什么测试没拦住**。🚫 **根因未定位前不许进入 A0** —— 拿不出根因就讨论方案，讨论的是猜测。**本节写完必须停下走 A0** |
| **⑤ 修复方案** | ⚠️ **只写 A0 裁决通过的那一个**，不罗列候选、不写「建议采用」。内容：改哪些文件、怎么改、影响面、是否构成协议级改动。<br>末尾可加一行 `已否决备选：<方案> —— <理由>`，防止后续会话重提已被否掉的方案 |
| **⑥ 验收标准** | 按 §4 写，**至少含四类**：阴性（原路径不再复现）、阳性（真问题仍能被抓住）、无副作用（相关值/显示/导出不变）、以及自检证据 |

## 6. `fronttask.md` / `backtask.md` 规范

**前端只按 `fronttask.md` 做，后端只按 `backtask.md` 做**，两份各自独立成篇——因为并行开发的两个子代理**互相看不见**，它们之间唯一的协调物是 `api.md`。

**① 必须分条式，每项独立编号**（前端 `F-1`、后端 `B-1`…）。大段叙述不合格——没法标 AC，也没法逐项验收。

**② 每项必须标「服务的 AC」**：

| 编号 | 服务的 AC | 任务内容 |
|---|---|---|
| F-1 | AC-1, AC-3 | 数量列输入框 + 失焦触发重算 |
| B-2 | AC-1 | 行小计计算接口 |

**③ 只标 AC 编号，不复制 AC 原文。** 单一事实源留在立项文档。复制会双写漂移——改了 AC 忘了改任务文档，比不标更糟。

**④ 双向覆盖，两个方向各拦一种病**（闸门 A 检查）：

| 检查方向 | 拦什么 |
|---|---|
| 每条 AC **至少被一个** `F-x` / `B-x` 覆盖 | **交付缺口** —— 写了 AC 但没人实现 |
| 每个 `F-x` / `B-x` **至少指回一条** AC | **超范围** —— 没人要的功能，Agent 自己加的戏。它不在 AC 里，测试也不会覆盖它，往往是下一个 BUG 的来源 |

> **为什么开发侧也要挂 AC**：开发子代理只读它那份任务文档，**不知道 AC 是什么**。拿到的是「实现一个输入框」这种任务分解，不是「小计应显示 1250.00」这种验收标准。
> 需求 → AC → 任务分解 → 子代理理解，**三次转译，中间两次你都看不见**。

## 6.5 三个确认阶段怎么分工，才不会让用户点三次头

`brainstorming`（步骤 -1）、闸门 A0（步骤 0.5）、闸门 A（步骤 1）都要用户开口，但**问的必须是三件不同的事**。同一件事问三遍，用户第二次就开始不耐烦，第三次就会说「你看着办」——**闸门就是这样被自己作废的**。

| 阶段 | 只问这个 | 🚫 不许在这一步问 |
|---|---|---|
| **-1 brainstorming** | **需求侧**：做什么 / 给谁 / 什么场景 / **边界在哪（明确不做什么）** | 不谈实现方案、不谈技术选型 |
| **0.5 闸门 A0** | **方案侧**：有 2 种以上合理改法时，选哪个 | 不重问需求（那是上一步的产物）；不呈报全套文档 |
| **1 闸门 A** | **确认侧**：照这份已定案的文档干，对吗 | 不再抛开放式问题 —— 用户此时只该做 yes/no |

**四条不重复提问的纪律**：

1. **上一步的产物直接用，不回头再确认一次。** brainstorming 问清的边界直接写进 §3 第②节，不要在闸门 A 再问一遍「这些确实不做吧？」
2. **A0 只呈报候选 + 推荐，不呈报文档。** 用户在 A0 看到的是「2~3 个方案 + 改动面/代价/风险 + 我推荐哪个」，不是完整任务文档
3. **方案唯一时跳过 A0**，但要在闸门 A 明说「本次无岔路，故未走 A0」—— 跳过要留痕，否则下一个会话不知道是漏了还是不需要
4. **一次问完，不要挤牙膏。** 同一阶段的疑问集中成一批问，用 `AskUserQuestion` 一次给全；🚫 不许把「选路径」和「要不要豁免闸门」捆进同一个选项（`CLAUDE.md` §4.3）

> 🚨 用户点头的次数不是越少越好，**是每次点头都要换来一个不同的、不可推导的决定**。
> 问了本可以自己查出来的事、或已经问过的事，就是在消耗闸门的信用额度。

## 6.6 🗣️ 呈报骨架（每次要用户拍板前都按它写）

**适用范围：所有要用户拍板的时刻** —— 路径确认、闸门 A0 / A / B、`CLAUDE.md` §3.2 红线审批、开发中途的**扩范围与改方案**、子代理报上来的越界请求、标准档↔轻量档升降、规则升级提议。不分阶段，一律按本节写。

> **为什么单立一节**：`§6.5` 管的是「**哪一步该问什么**」，本节管的是「**问的时候该怎么写**」。
> 两者缺一不可 —— 问对了阶段但写成一段技术黑话，用户照样做不了决定，只能反问一轮，
> 而反问一轮消耗的正是 §6.5 末尾说的那份闸门信用额度。
>
> ⚠️ 真实教训：闸门 A0 早有「2~3 个候选 + 改动面/代价/风险 + 明确推荐」的要求（§5 第 4 步），
> 但**开发中途的范围变更**只被写了「必须回来问」（`CLAUDE.md` §4.3 决策权归属），没有任何格式要求 ——
> 于是那一类呈报长期是「三段技术结论 + 一个既成方案」，用户无从裁决。本节堵的就是这个口子。

### 结构：正文七段 + 紧接一张选项卡

🚫 **只给选项卡不写正文 = 违规**（选项说明的篇幅装不下背景）。
🚫 **只写正文不给选项卡 = 违规**（用户得自己打字复述你的候选编号）。

| # | 段 | 写什么 | 🚫 反面 |
|---|---|---|---|
| ① | **要你定什么** | 一句话点明决定类型：选方案 / 批扩范围 / 选路径 / 放行 / 批不可逆操作 | 上来就讲技术细节，用户读到第三段还不知道要他干嘛 |
| ② | **起因** | 什么触发的：用户的哪句话、哪条 `AC-x`、计划里的哪一项、哪个子代理的回报 | 光写「我发现……」—— 没有起因，用户判断不了这事该不该现在处理 |
| ③ | **怎么发现的** | 跑了什么命令 / 读了哪个文件的哪一行 / 看到什么输出。**必须可复跑** | 无证据的断言；「经分析」「看起来」「应该是」 |
| ④ | **不处理会怎样** | **用户视角的可观测后果**：哪个页面空白、哪一列变成 NULL、哪个金额算错、哪条校验失灵 | 只说代码层后果（「函数签名不兼容」）—— 用户无法据此估这事值多少钱 |
| ⑤ | **我的把握度** | 上面哪些是**跑过验证的**、哪些是**推测**、推测错了会怎样。逐条标 | 笼统一句「基本确定」，或把推测写成结论。**这一段是给用户的风险折扣率；缺了它，用户会按 100% 可信去批** |
| ⑥ | **候选 2~3 个** | 每个标：怎么改 / 改动面（文件数、碰不碰契约）/ 代价 / 风险 / **代价是实测还是估的** | 只给一个方案 —— 那是通知，不是裁决 |
| ⑦ | **我推荐哪个 + 为什么** | 明确点名一个，给理由 | 「你看着办」「两个都行」—— 给推荐是 Claude 的职责（`CLAUDE.md` §4.3 决策权归属） |

**紧接着用 `AskUserQuestion` 把 ⑥⑦ 做成选项卡**：推荐项排第一并在 label 末尾标「（推荐）」，每个选项的 description 写清代价与风险。
工具自带的 `Other` 就是用户「自己表达」的口子，**不用再另写一个「其他」选项**。

### 两条写法纪律

**1. 🗣️ 先人话后符号名。** ②③④ 三段必须先用**业务语言**说一遍，函数名 / 表名 / 类名 / 文件名只能跟在括号里或后半句。

> 🚫 `f_material_element_price 函数体直读 ds_quote_material_bom / ds_quote_element_bom，没有 _record 分支，11 段视图引用它`
> ✅ 算元素单价的那个数据库函数**只认旧料号**，本单新加的料号在它眼里整体不存在 → **元素单价整列变空**，11 段视图都受影响
> （函数 `f_material_element_price`，直读 `ds_quote_material_bom` / `ds_quote_element_bom`，没走 `_record` 分支）
>
> **判据：用户不读代码也能判断「这事值不值得改」，才算过关。**
> 符号名是给你自己回溯用的，不是给用户做决定用的 —— 它们放在括号里一个都不少，但不许挡在句子前面。

**2. 一次一批。** 同一时刻的多个待决项集中成一次呈报（`§6.5` 纪律 4），一张选项卡最多 4 问。
🚫 不许把互相独立的两个决定捆进同一个选项（`CLAUDE.md` §4.3：捆了用户会连带批准掉他没打算批的那个）。

### 分档：按「这个决定可不可逆」

| 档 | 触发（任一命中即全档） | 写几段 |
|---|---|---|
| **全档 ①~⑦** | 不可逆操作（`CLAUDE.md` §3.2 红线）/ 碰数据契约·DB 迁移·权限·金额与公式·跨端契约·`架构基线.md` / **扩范围或改 AC** / 方案选型（闸门 A0）/ 标准档↔轻量档升降 / 闸门 B 归因 | 七段全写 |
| **短档 ①②⑦** | 以上全不命中，**且决定可逆**：路径 A/B 确认、文档落点、命名、要不要顺带做件小事 | 三段 |

⚠️ **拿不准就走全档。** 代价不对称：全档写长了，用户多读两行；短档写漏了，用户批错一个不可逆的决定。
✅ 短档就是 `CLAUDE.md` §4.3「提问格式……不要罗列长篇选项」的落地形态 —— 那一条管的是短档，不管全档，两者不冲突。

## 7. 闸门 A 前的自检三项

**任一不过就打回重写，不要拿去呈报**：

1. **AC 质量** —— 逐条过，须满足 §4「可执行三要素」且三类覆盖齐全
2. **正向覆盖** —— 每条 AC 至少被一个 `F-x` / `B-x` 认领，且至少被一条测试用例覆盖。没人认领 = 交付缺口。
   ⚠️ **顺带核分片**：每条 AC 在 `test.md` 追溯矩阵的「分片」列**恰好属于一片，不重不漏**。
   重了会有两个测试员同时验它、结论冲突没人裁决；漏了就是交付缺口的另一种形态（`testing.md §4.5`）
3. **反向覆盖** —— 每个 `F-x` / `B-x` 都能指回至少一条 AC。指不回 = 超范围，砍掉或补 AC

**呈报时随文档一并说明「派工计划」**：派哪几类子代理 + **每类认领哪些 `F-x` / `B-x` 编号** + **测试分片计划**（分几片 / 每片认领哪些 `AC-x` / 每片的造数前缀与隔离口径）。
🚫 **分片必须在这里定，不许开工后临时切** —— 分片依据是「这条 AC 会写什么」，那是编排期的判断；开工后再切等于拿并行度赌隔离。
这不是第四项自检，是**呈报内容的一部分** —— 挂在闸门 A 上是为了让用户看清工作怎么分，同时不新增停止点。
🚫 按 `CLAUDE.md` §4.0 分工铁律，**派是默认、主线不写业务实现代码**；不派的唯一理由是「客观做不到」（如无 git 仓库），且要点名说明。

⚠️ **自检通过只是取得「呈报资格」，是否放行仍由用户裁定。**

## 8. 闸门 B 未通过时的归因

出现「测试全绿但用户验收不符」，**先归因再修**，必须归到六类之一并写进 `docs/RECORD.md`：

| 归因 | 判据 | 修法 |
|---|---|---|
| AC 不可执行 | AC 含形容词，双方各自解读 | 重写 AC，补可观测断言 |
| 测试与 AC 不对齐 | 追溯矩阵有缺行，或测试从代码派生 | 按 AC 重写测试 |
| 环境/数据不一致 | 测试库 ≠ dev 库、夹具 ≠ 真实数据、mock 掉了真链路 | 在真实环境重跑 |
| **契约版本不一致** | 并行子代理各自对着**不同版本**的 `api.md` 写 | 对齐契约版本，重派受影响的代理 |
| **测试 harness 不可信** | 「随机挂一条、每次不一样」 | 先修 harness，见 `testing.md` |
| 实现确实错了 | 前五项都排除 | 才是改代码 |

⚠️ 跳过归因直接改代码 = 默认最后一类，而经验上**前五类才是多数**。
⚠️ **联调失败先查契约版本，再查实现质量** —— 两边各自「按自己那份契约」都写对了，也会对不上。

## 9. Backlog 维护规则与条目格式

由 `CLAUDE.md §7` 引用。

**规则一（评审 spec 时）**：① 列出建议推迟的功能点及理由 ② 🚦 **询问用户是否采纳，等待确认，不要自动写入** ③ 确认后立即更新 ④ 每条按下方格式填满 ⑤ 写入后输出摘要与总条目数

**规则二（新会话首个开发指令前）**：① 读取 ② 列出所有 `[ ]` 条目及优先级 ③ 判断本次任务是否与之相关并告知 ④ 相关则询问是否一并处理 ⑤ 不相关则简短提示有 N 条待开发，继续执行
> 会话开局 hook 已注入待开发条目摘要 —— 有摘要就直接用，不必整篇重读。

**规则三（完成开发任务时）**：① 覆盖了的条目更新为 `[x]` 并在变更记录追加一行 ② 满足了某条前置条件的，备注改「✅ 已就绪」 ③ 输出 `CLAUDE.md §4.6` 的结案四行

### 条目格式


由 `CLAUDE.md` §7「Backlog 自动管理规则」引用。写入 `docs/BACKLOG.md` 时严格按此格式：

```markdown
### [模块名称]

- [ ] **功能描述**
  - 来源：spec §X.X / [章节名]
  - 推迟原因：复杂度过高 / 依赖未就绪 / 超出本期范围 / 其他
  - 优先级：P0 必做 / P1 重要 / P2 可选
  - 前置条件：依赖哪个模块或接口完成后才能开始
  - 预估规模：S=1-2天 / M=3-5天 / L=1周以上
```

**状态标记**：`[ ]` 待开发 / `[~]` 进行中 / `[x]` 已完成 / `[-]` 已废弃（**须注明原因**）

⚠️ **「前置条件」不是摆设**：某条前置条件被本次交付满足时，必须回来把它标成「✅ 已就绪」。
不标的后果是，这条 backlog 会一直看起来「还不能做」，然后被无限期跳过。

## 9.5 任务状态与结案

**任务状态**（写进 `dev-docs/INDEX.md`，全项目统一这**七**个值）：

| 状态 | 含义 | 何时改 |
|---|---|---|
| `立项` | 目录已建、文档在写，未过闸门 A | 步骤 0 |
| `开发中` | 闸门 A 已过，worktree 内开发 | 步骤 1→2 |
| `待验收` | 已合并，等用户真机验收 | 步骤 5 |
| `返修中` | **闸门 B 未通过**，返修任务在跑（**须注明返修目录**） | 步骤 7 |
| `挂起` | 卡住推不动（**须注明：卡什么 / 等谁决定 / 挂起日期**） | 任意 |
| `已交付` | 用户验收通过 | 步骤 7 |
| `已废弃` | 需求取消或被取代（**须注明原因和取代者**） | 任意 |

> `返修中` 不能继续挂「待验收」：「等用户来验」和「验过没过、正在返修」在索引上会长得一模一样，而这两件事的下一步动作完全相反。
> `挂起` 没有那三项附注 = 无声僵尸任务，既没人推进也没人敢删。

**结案清单**（四件事，缺任一项即视为未结案；四行输出格式见 `CLAUDE.md §4.6`）：

1. `INDEX.md` 状态改「已交付」，并删掉态势表里对应的进行中/未闭合条目
2. `BACKLOG.md` 对应条目打 `[x]` + 变更记录追加一行
3. `RECORD.md` 追加核心内容与根因；**同一类根因第 2 次出现的，按 `change-protocol.md §6` 提议升级为规则**
4. **拦截点统计** —— 本次每个问题记一句「它是被哪个环节抓住的」，按下表归类后输出第四行

### 拦截点怎么归（归错了统计就没意义）

| 环节 | 归它的判据 |
|---|---|
| **实现期子代理回报** | 子代理在**写实现/写用例的过程中**发现并**只报不改**的问题（契约有歧义、AC 与实际数据对不上、文档前后矛盾、派工指令与 AC 冲突…）。<br>📌 2026-09-14 `task-260914` 新增此类：那一次 **12 个拦截里有 10 个落在这里**（模板同名多版本、`??` 不兜空串、文档三处残留旧契约、1280 的 10px、`AC-19` 前提不成立、凭据缺失…），而原表根本没有这一类 ⇒ 这套流程**最有效的拦截环节一直没被计入统计**，"该不该保留子代理"这个问题因此永远算不清账。|
| **测试执行** | 自动化用例跑出来的失败 |
| **主线审交付（实现）** | 子代理交的**实现代码 / 前端交付**被主线审出来不对，用例还没跑、AC 还没验（线程池没有全局上限、effect 漏依赖、合并后新增 lint…）。<br>📌 2026-09-22 `task-260920` 新增此类：那一次 8 个主线侧拦截里有 **3 个**落在这里，原表只能把它们挤进「主线亲验」⇒ 「亲验」被撑大成「主线做的所有事」，而**它与「审交付」的下一步动作完全不同**（一个是回流子代理返工，一个是改 AC 或记缺陷）。|
| **主线审用例** | 用例**还没跑**就被主线看出来不对（漏 AC / 断言实现细节 / 空夹具 / 片间冲突） |
| **主线亲验** | 测试全绿，但主线逐条对 AC 时发现不符 |
| **冷启动** | 测试与亲验都过，但按文档从零跑不通 |
| **用户验收** | 闸门 B 被用户打回 |
| **上线后** | 交付之后才暴露 |

⚠️ **归「最早发现它的那个环节」，不是「最该发现它的那个环节」。**
后者是判断，前者是事实 —— 统计要的是事实。归成「本该测试抓住的」会让每个环节看起来都很有用，那这份统计就白做了。

> 📌 **本次无问题**是完全正常的结果，写「发现 0 个问题」即可。
> 需要警惕的不是零问题，是**某个环节连续多个任务零命中** —— 那说明它要么没在真正执行，要么真的不必要。

⚠️ **闸门 B 未通过时，先归因再修** —— 必须归到 §8 六类之一并写进 `RECORD.md`。
**跳过归因直接改代码 = 默认「实现确实错了」这一类，而经验上前五类才是多数。**

## 10.5 决策台账登记规范

`docs/决策台账.md` 装的是「**现行**跨任务裁决」——哪些结论**此刻仍然算数**。
字段格式与终态定义的事实源在台账文件与 `.claude/hooks/check-decisions.sh` 文件头，**本节不复述**，只管三件事：**什么该登 / 归谁管 / 何时登与何时归档**。

### 三条硬门槛（必须同时满足）

| # | 门槛 | 不满足时它归谁 |
|---|---|---|
| ① | **跨任务仍然有效** —— 换个任务、换个人接手，这条口径依然管事 | 只在本任务内成立 → `需求文档.md` / `RECORD.md` |
| ② | **`对象:` 写得出符号原名** —— 函数名 / 表名 / 列名 / 文件路径 / 接口路径 / 脚本名 | 写不出 → 它是**流程纪律**，归 `CLAUDE.md` 或 `docs/rules/` 分册 |
| ③ | **至少一条 `前提:` 写得出只读验法** | 全部前提只能写 `无` → 归 `RECORD.md` / `PRD.md`，见下方 🚨 |

🚨 **③ 为什么是门槛而不是建议**：全部前提都不可验 = 这条裁决**没有事实锚点**，脚本永远判不出它失效，只能等人手工标 `[已证伪]` —— 而台账存在的全部理由，恰恰是「人工状态字段必然与事实漂移，且漂移**不报错**」。全不可验的条目登进去 = 一条**永不失效的僵尸裁决**，还占着每个会话的开局注入预算。

⚠️ 但**单条**前提写 `无` 是合法的（台账里的官方样例，第二条前提就是 `无`）。门槛是「**至少一条**可验」，不是「条条可验」。

### 归谁管：台账与五个邻居的分界

🚫 **同一件事不许两处都写全文。** 已经在别处有全文的，台账只在 `出处:` 里指过去，**不复述** —— 复述必然漂移，而漂移不报错。

| 这个问题 | 归谁答 |
|---|---|
| 发生过什么、什么时候做的 | `docs/RECORD.md`（流水） |
| 这事属于哪个历史任务 | `dev-docs/INDEX.md` |
| 这类 bug 长什么样、怎么防 | `docs/反模式.md`（AP-NNN，按症状） |
| 还有什么没做 | `docs/BACKLOG.md` |
| 我该怎么工作 | `CLAUDE.md` / `docs/rules/` |
| **这个对象此刻按哪个口径算** | **`docs/决策台账.md`** |

**一句话判据**：台账回答「**现在还算不算数**」，上面五个**都不回答这个问题**。

### 正反例（取自本项目）

✅ **该登**：

- 对象 `application-test.properties` —— `mvnw test` 到底连哪个库。**这一行被改错过两次**，CLAUDE.md 现行版自己写着「下次动它之前先 grep 实查，不要凭本文件的记载」。三门槛全中：跨任务（每个跑测试的人都撞）／符号原名是文件路径／验法一条 grep 就够。
- 对象 `mat_part` —— 这批表在本库**从未创建**（不是「已废弃」）。2026-09-09 实证**推翻**了 `AP-53` 的原说法，而 AP-53 全文还在。⇒ 正是台账的用武之地：**不改 AP-53 原文**，用一条现行裁决盖住它已过期的那部分。

🚫 **不该登**：

- ❌「实现 agent 会虚报完成，必须主线亲验」—— 写不出符号原名（门槛②）。这是流程纪律，归 `CLAUDE.md §4.5`。
- ❌「本期 AC-22 全库无样本，不造夹具」若只影响本任务 —— 门槛①。留在任务文档里。
- ❌「`AP-31`『加载中…』永久占位族的 4 类共因」—— 反模式库已有全文，台账复述 = 两处漂移。**除非**你要登的是「其中某一类此刻已不成立」—— 那才是裁决。

### 何时登

**触发点唯一：结案时**，并入 §9.5 结案输出契约的「规则升级」那一行一起判。

- ⚠️ **不在 A0 当场登**：任务进行中做的裁决，要到结案才看得出它是「跨任务口径」还是「只在本任务内成立」——当场登会把一批门槛③不达标的东西灌进去。
- ⚠️ **写入前必须问用户是否采纳，不要自动写**（与 §9 Backlog 同）。台账条目会注入**每一个**后续会话的开局，登记权不在你。

编号取当前最大值 +1：

```bash
/usr/bin/grep -aho 'DEC-[0-9]\{4\}' docs/决策台账.md docs/archive/决策台账-归档.md 2>/dev/null | sort -u | tail -1
```

### 何时归档

🚨 **失效不等于当场归档。** 脚本报 `STALE` / `前提失效` **本身就是信号**（这个对象上发生过口径变更）。当场归档会让信号消失 —— 而 `session-brief.sh` 把三类分开计数（被取代 / 前提失效 / 同对象多条）的设计也就白做了。

| 情形 | 当场做 | 结案时做 |
|---|---|---|
| 新裁决顶替旧的 | 新条目写 `取代: DEC-NNNN`，**旧条目留着** | 旧条目全文移入 `docs/archive/决策台账-归档.md`，原处留 `~~DEC-NNNN~~` 指针 |
| 前提被证伪 | 把该 `前提:` 行改标 `[已证伪]`，**条目留着** | 同上 |

🚫 **漏写指针 → 脚本报 `取代指向未知`，追溯链断了。**

### 本节自检

- [ ] 三条硬门槛逐条比对过，不是「感觉挺重要」
- [ ] `对象:` 是符号原名，且与代码里的写法**逐字一致** —— 同对象检查靠**字符串相等**分组，名字不一致会**静默漏报**
- [ ] `出处:` 指得回原文（任务目录 · 原编号 · `RECORD` 日期）
- [ ] 至少一条验法**实跑过**，退出码为 `0`
- [ ] 🚨 验法**不依赖交互 shell 的环境**（函数 / 别名 / shell 选项 / 未导出的变量）——
      判定器用 `bash -c` 起**子进程**执行验法，那些东西在子进程里一律不存在。
      依赖它们的验法会**恒报「前提可疑」**，而那是**验法的假阳性**，不是前提塌了。
      ⇒ 这类前提改写成「验后果、不验机制」，或显式标 `无` 并写明为何不可验。
      （2026-09-12 实证：`DEC-0002` 的 `declare -f grep | grep -q ugrep` 恰好踩中）
- [ ] 该内容在 `RECORD` / 反模式 / `BACKLOG` 里**没有**重复全文
- [ ] 登记前问过用户
