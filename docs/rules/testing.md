# 规则分册 · 测试

> **何时必读**：写测试、跑测试、读测试报告、判断「这个绿可不可信」、闸门 B 之前。
> **效力**：与 `CLAUDE.md` 同等，不是参考资料。冲突时以 `CLAUDE.md` 为准。

---

## 0. 本册在回答什么

**测试报告能当验收证据，前提是测试基础设施本身可信。** 本册管的就是「**怎么知道那个绿是真的**」。

🚫 **测试全绿不构成 AC 达成的证据**，二者不可互相替代：
- 测试证明「代码按**实现者的理解**工作」
- AC 证明「功能符合**需求文档**」

实现者理解错了需求，测试会跟着错，然后**永远全绿**。

---

## 1. 测试不得从实现代码派生

**用例必须从立项文档的 AC 原文派生。**

- 写测试方案时只读 AC 章节，**不读实现代码**
- 派子代理写测试时**只给 AC，不给实现**，并显式禁止它读实现目录（见 `subagents.md` 段 c）
- 信息不足就停下来报告缺什么，**不许翻实现补齐**

⏱ **时点是这条规则能否落地的关键**：闸门 A 之前实现代码还不存在，「不读实现」是天然成立的。一旦拖到开发中期再补测试方案，代码就在眼前，这条规则事实上无法遵守。

> ⚠️ **上下文隔离 ≠ 访问隔离。** 不显式禁止，子代理自己就去把 `src/` 读了，读完又和实现同源。

**例外**：复现已知 bug、定位失败原因时可以读实现 —— 但那是在**用例写完之后**，且不得据此修改断言。

## 2. AC 可追溯矩阵（测试方案必含，缺行即视为文档未完成）

| AC 编号 | 覆盖它的测试 | 层级（单元/接口/E2E/真机） | 验收证据形式 |
|---|---|---|---|
| AC-1 | T1.2 | E2E | 截图 |

三条硬规则：

- **没有任何测试覆盖的 AC = 交付缺口**，必须在闸门 B 汇报时显式列出，**不许沉默**
- **只有单元测试覆盖、没有 E2E 或真机验证的 AC，不算已验收**（单测与实现同源，见 §1）
- 🚨 **矩阵里声明的「验收证据形式」必须真的留得下来**
  **判据：下一轮跑测试会不会把它删掉？会 → 不算证据。**
  测试框架默认会在每轮开跑前清空输出目录，所以声明「截图」却把截图留在那里，等于**没有证据**。
  正确做法：把要当证据的产物**复制到任务目录下的归档位置并随任务提交**。

## 3. 用例质量红线

1. **断言的是 AC 里的可观测断言，不是实现细节**（断言实现细节 = 又变回与实现同源）
2. **三类覆盖齐全**：
   - **单点** —— 单次操作的正确性
   - **序列** —— 「做 A → 做 B → 切走再切回 → 刷新页面」，并断言**中间态与最终态**。只写单点 = 只覆盖 happy path，串起来用必翻车
   - **边界** —— 空数据 / 超长输入 / 并发编辑 / 权限不足
3. 🚨 **断言从未执行 = 假绿**
   数据为空 → 循环 0 次 / 分支没走到 → 断言压根没跑，测试照样报绿。
   对策：**前置数据必须是真实业务数据，不是能让断言空跑的空夹具**；断言前先断言「结果非空」；要求测试打印实际值。

## 4. 出现不稳定失败：先查测试基础设施，再查业务代码

**症状特征：随机挂一条、每次挂的还不一样、数据看着合理但对不上。**

这类症状的高频根因**不在业务代码**，而在：并发、端口分配、临时目录、共享库、全局状态。

⚠️ 它最危险的地方是**两个方向的证据同时失效**：绿可能只是没撞上，红可能是被污染而非真缺陷。
**在 harness 被证明可信之前，测试报告不作为验收证据**，也不要急着修业务代码。

### 4.1 🚫 禁止以「偶发，重跑一下就好」结案

必须定位到根因。宣称修好时要给出**重复次数**，且次数要与**修法的性质**匹配：

| 修法性质 | 含义 | 需要的重复次数 |
|---|---|---|
| **结构性修复** | 失败模式被**构造性消除**（例如探活改成验明正身，撞端口也不会误判） | 少量即可，作用是「确认没引入新问题」 |
| **概率性修复** | 只是把碰撞概率压小，失败模式还在 | 按 `p^n` 算，通常远超直觉 |

量级感（`p` = 修复前每轮通过率）：**p=0.83 时，跑两次全绿有 69% 只是运气**；要把「碰巧」压到 5% 以下需要约 17 轮。
**跑两次全绿证明不了任何事** —— 这是最容易被骗过去的地方。

### 4.2 并行测试的临时资源必须唯一化

端口、库文件、临时目录都要唯一化，且**获取与占用之间不能有「无主窗口」**。

> 典型 TOCTOU：`freePort()` 先 `close()` 拿到端口号，再交给子进程去绑 —— 中间这段时间端口是无主的，OS 会把它分给别人。
> 而且它**不以「启动失败」的形式暴露**：B 的子进程绑不上直接退了，B 的探活却探到 A 那个活得好好的服务，探活成功，然后 B 把全部断言打在 A 的库上。

配套：**探活必须验明正身**（带唯一库路径 / 实例 ID 校验），只看 HTTP 200 挡不住这条路径。

### 4.3 共享库上的测试不得改变全局状态

上一条管的是**临时**资源。真正难查的是另一半：**测试写的是共享 dev 库**，而它改的东西不是临时的。

典型：用例把某个账号置为停用、把某个模板置为已发布、改了系统配置、删了一批"测试数据"，跑完不还原。后果三层，一层比一层难查：

1. 下一轮同一批用例开始**恒定失败**（而不是随机失败）
2. **真人操作也跟着坏** —— 用户来验收，发现登录不上 / 数据不见了
3. 🚨 最坏的一层：这种恒定失败**看起来非常像业务回归**，于是被误归因到刚合并的那次改动上，然后去改一段本来没问题的代码

规则：

- 🚫 **E2E / 集成测试不得改变全局状态**：用户启停用、角色权限、模板/配置的发布态、系统级开关、公共基础数据
- 必须改的，**用例自己在 `finally` 里还原**，并在测试方案里登记「本用例会动哪些全局状态」
- 🚫 **共享库上不许跑会清库的测试**，哪怕清库写在 `beforeAll` / `setup` 里 —— 那属于 `CLAUDE.md` §3.2「环境销毁」红线，停下来报告
- ⚠️ 并发度配置（如 `workers: 1`）**可能是契约不是性能参数**。调大之前先查它旁边有没有注释、`INDEX.md` 里有没有登记

> 与 §4 的分工：§4 管「随机挂一条」，本节管「**恒定挂同几条，而且越跑越多**」。症状不同，根因不同，别拿 §4 的思路查本节的病。

### 4.4 新加的守卫 / 断言必须做一次证伪实验

**首次 PASS 不能证明守卫有效** —— 可能它压根没接上。

- 故意破坏它保护的条件，确认它**硬失败**（例：把身份匹配串改坏，确认探活会失败而不是退回「200 就算数」）
- 断言「某事没发生」时（如「一个请求都没发」），必须配一个**阳性对照**，证明观察手段能抓到该事件
- 🚨 **自己写的验证脚本同样适用**：先确认它「能输出东西」。命令写错导致**全程空输出**，看起来和「全部通过」一模一样

## 5. 冷启动验证（闸门 B 之前必做）

**假装自己是刚 clone 这个仓库的人**，只按文档从零跑一遍：装依赖 → 起服务 → 跑测试 → 打开页面。
**跑不通的每一步，都是文档缺口。**

**为什么这一步不能省**：开发期为了隔离而替换掉的东西，真实值**从头到尾没被验证过** ——

| 开发期的替身 | 从没被验证的真实值 |
|---|---|
| 临时端口 | **契约里声明的端口**（可能压根绑不上） |
| worktree 里的依赖目录 | 主工作区能不能装起来（worktree 一删就没了） |
| 每用例一个临时库 | 真实库上的迁移 |
| mock 掉的外部依赖 | 真实依赖的连通性 |
| 工具默认输出目录里的截图 | 下一轮就被清空，等于没有证据 |

**所有测试全绿，都证明不了「应用能在它自己声称的配置下启动」。**

两条配套：
- **前移一个 5 秒的冒烟**：开发早期就用**声明端口**绑一次，别等亲验才发现绑不上
- 冷启动跑不通的步骤，**补进 README 或任务文档**，不要只在自己会话里记着
