# 规则分册 · 测试

> **何时必读**：写测试、跑测试、读测试报告、判断「这个绿可不可信」、闸门 B 之前。
> **效力**：与 `CLAUDE.md` 同等，不是参考资料。冲突时以 `CLAUDE.md` 为准。

---

## 0. 本册在回答什么

**测试报告能当验收证据，前提是测试基础设施本身可信。** 本册管的就是「**怎么知道那个绿是真的**」。

🚫 **测试全绿不构成 AC 达成的证据**，二者不可互相替代：
- 测试证明「代码按**实现者的理解**工作」
- AC 证明「功能符合**需求文档**」

实现者理解错了需求，测试会跟着错，然后**永远全绿**。

---

## 1. 测试不得从实现代码派生

**用例必须从立项文档的 AC 原文派生。**

- 写测试方案时只读 AC 章节，**不读实现代码**
- 派子代理写测试时**只给 AC，不给实现**，并显式禁止它读实现目录（见 `subagents.md` 段 c）
- 信息不足就停下来报告缺什么，**不许翻实现补齐**

⏱ **时点是这条规则能否落地的关键**：闸门 A 之前实现代码还不存在，「不读实现」是天然成立的。一旦拖到开发中期再补测试方案，代码就在眼前，这条规则事实上无法遵守。

> ⚠️ **上下文隔离 ≠ 访问隔离。** 不显式禁止，子代理自己就去把 `src/` 读了，读完又和实现同源。

**例外**：复现已知 bug、定位失败原因时可以读实现 —— 但那是在**用例写完之后**，且不得据此修改断言。

|---|---|---|---|---|
| AC-1 | T1.2 | E2E | S1（只读） | 截图 |
| AC-5 | T5.1 | E2E | S-全局（改角色权限） | 截图 |

> 📌 **「分片」列在只派一个测试员时填 `S1` 即可**，但**不许留空** —— 留空意味着「这条 AC 会写什么」没人想过，
> 而那正是多测试员并行时第一个炸的地方。分片依据与共库前提见 **§4.5**。

三条硬规则：

- **没有任何测试覆盖的 AC = 交付缺口**，必须在闸门 B 汇报时显式列出，**不许沉默**
- **只有单元测试覆盖、没有 E2E 或真机验证的 AC，不算已验收**（单测与实现同源，见 §1）
- 🚨 **矩阵里声明的「验收证据形式」必须真的留得下来**

  正确做法：把要当证据的产物**复制到任务目录下的归档位置并随任务提交**。

## 3. 用例质量红线

1. **断言的是 AC 里的可观测断言，不是实现细节**（断言实现细节 = 又变回与实现同源）
2. **三类覆盖齐全**：
   - **单点** —— 单次操作的正确性
   - **序列** —— 「做 A → 做 B → 切走再切回 → 刷新页面」，并断言**中间态与最终态**。只写单点 = 只覆盖 happy path，串起来用必翻车
   - **边界** —— 空数据 / 超长输入 / 并发编辑 / 权限不足
3. 🚨 **断言从未执行 = 假绿**
   数据为空 → 循环 0 次 / 分支没走到 → 断言压根没跑，测试照样报绿。
   对策：**前置数据必须是真实业务数据，不是能让断言空跑的空夹具**；断言前先断言「结果非空」；要求测试打印实际值。

4. ⏱️ **计时类断言：有后台负载时，单样本不作数**（2026-09-22 `task-260920` 晋升，用户裁决采纳）
   同一条 AC，一个样本 4.03 s「通过」、另一个 7.6 s「不通过」，两个都是真的 —— 差异来自**点击时刻落在后台周期的哪一点**（排队等锁 + 轮询颗粒）。
   🚫 不许拿单次测量判定门槛，也不许两人各测一次后争论谁对。**至少 5 个样本看分布**（记最小 / 中位 / 最大），门槛按分布定，并写明测时后台在跑什么。
   ⚠️ 与「偶发重跑一下就好」（§4.1）不同：这里不是不稳定，是**被测对象本来就有分布**，取一个点当结论才是错的。

## 4. 并行执行与不稳定失败：先查测试基础设施，再查业务代码

> 🧭 **本节两半，别走错门**：§4.1~§4.4 管**并行出了问题怎么归因**；§4.5 管**怎么并行才不出问题**。
> 要开多测试员分片，直接看 **§4.5**。

**症状特征：随机挂一条、每次挂的还不一样、数据看着合理但对不上。**

这类症状的高频根因**不在业务代码**，而在：并发、端口分配、临时目录、共享库、全局状态。

⚠️ 它最危险的地方是**两个方向的证据同时失效**：绿可能只是没撞上，红可能是被污染而非真缺陷。
**在 harness 被证明可信之前，测试报告不作为验收证据**，也不要急着修业务代码。

### 4.1 🚫 禁止以「偶发，重跑一下就好」结案

必须定位到根因。宣称修好时要给出**重复次数**，且次数要与**修法的性质**匹配：

| 修法性质 | 含义 | 需要的重复次数 |
|---|---|---|
| **结构性修复** | 失败模式被**构造性消除**（例如探活改成验明正身，撞端口也不会误判） | 少量即可，作用是「确认没引入新问题」 |
| **概率性修复** | 只是把碰撞概率压小，失败模式还在 | 按 `p^n` 算，通常远超直觉 |

量级感（`p` = 修复前每轮通过率）：**p=0.83 时，跑两次全绿有 69% 只是运气**；要把「碰巧」压到 5% 以下需要约 17 轮。
**跑两次全绿证明不了任何事** —— 这是最容易被骗过去的地方。

### 4.1.5 🚨 「必现」≠「缺陷」（2026-09-03 task-260902 教训晋升）

§4.1 拦的是「偶发就重跑」。**本条拦的是它的反面：确定性复现之后直接判缺陷。**

> **「确定性复现」只证明「不是 flaky」，不证明「是缺陷」。这是两个独立判断，不许合并。**

真实发生过的一次：测试报告「材质页筛「停用」→ 切页签往返 → 再导出变成全量，**必现 7/7，跨 3 个时段、跨 2 轮选择器重构**」，
结论写的是「🔴 真缺陷 · 用户以为在导筛选结果，实际拿到全量」。

主线复验时补了**一个它没测的维度** —— 切回后**筛选框显示的是什么**：

| 时点 | 筛选框 | 列表共 | 导出行数 |
|---|---|---|---|
| 筛「停用」 | 状态：停用 | 1 | 1 |
| 切走再切回 | **状态：全部** | **263** | **630** |

⇒ **筛选框、列表、导出三者自洽**：切回后用户看到的本来就是全量，导出全量正是「所见即所得」。
根因是壳页 `destroyInactiveTabPane`（既有架构，切走即销毁组件）—— **是 AC 假设了架构不支持的行为，不是产品缺陷**。
最终处置是**改 AC 不改代码**。

**报缺陷前必须回答的三个问题**（任一答不上就不能定性为缺陷）：

1. **页面呈现与底层数据是否自洽？** —— 只测「导出了什么」不够，还要测「页面此刻显示什么」。
   两者一致 = 功能正确（哪怕结果不合你预期）；两者矛盾 = 才是缺陷。
2. **这个预期是 AC 写的，还是既有架构本来就不支持的？** —— 去看一眼相关组件/壳页的关键 prop 再下结论。
3. **是本次改动引入的吗？** —— 用 A/B（干净 master vs 本分支）对照，不要凭"它在我这红了"就归因给本次。

⚠️ **报错的代价不对称**：把「AC 写错」报成「产品缺陷」，会让人去改本来是对的代码 —— 比漏报更贵。

### 4.2 并行测试的临时资源必须唯一化

端口、库文件、临时目录都要唯一化，且**获取与占用之间不能有「无主窗口」**。

> 典型 TOCTOU：`freePort()` 先 `close()` 拿到端口号，再交给子进程去绑 —— 中间这段时间端口是无主的，OS 会把它分给别人。
> 而且它**不以「启动失败」的形式暴露**：B 的子进程绑不上直接退了，B 的探活却探到 A 那个活得好好的服务，探活成功，然后 B 把全部断言打在 A 的库上。

配套：**探活必须验明正身**（带唯一库路径 / 实例 ID 校验），只看 HTTP 200 挡不住这条路径。

### 4.2.5 🚨 同一 worktree 内不要与实现代理并发跑构建（2026-09-10 `repair-260910` 教训晋升）

测试代理与实现代理共用一个 worktree 的 `target/` 时，**并发构建会互删 class**：
实测测试代理读到「48 tests / 0 failures」，而它自己的那次运行其实**编译失败**
（`NoSuchFileException: target/classes/...`），**maven 的非 0 退出码被 `tail` 淹没**，报告是上一次的残留。

**两条动作**：
1. 跑测试前先确认 `target/` 没有其他 maven 在写（`quarkus:dev` 的热重载**同样会改写 `target/classes`**，不只是 `mvn test`）
2. 🚨 **按 mtime / 自有日志确权**，断言「点名的测试类缺失即硬失败」+ 与基线计数比对
   —— 🚫 **不要用 `-Dsurefire.reportsDirectory` 做隔离**：实测在 surefire **3.5.4** 下**被静默忽略**，
   报告仍落默认目录，**而且不报错**。用它等于没隔离，还以为隔离了。

### 4.2.6 🕒 新起的前端临时栈，开跑前先预热一次页面（2026-09-22 `task-260922` 同一根因 2 次后晋升，用户裁决采纳）

新起的 Vite dev server 在**第一次**打开页面时要按需转换全部模块，耗时可超过 60 s
（`VITE ready in 194 ms` 只说明服务起来了，不说明页面能在用例超时内渲染出来）。
不预热就开跑，第一批用例会成批卡在「等关键元素可见」上超时 —— **同一轮、不同用例、同一步骤**失败，第二轮零复现。

📌 **实证**（同一任务内独立两次）：S-UI 片 run1 的旧 spec T-5 / T-17 与新 spec T-1 三条都卡在等 `.ant-table-thead th`，run1 总耗时 6.8 min、run2 同代码同栈 4.1 min 全过；
主线亲验首跑同样 60 s 等不到表头，后端日志**只有登录、没有列表请求**（前端还没加载完），第二次立即 11/11 通过。

**动作**：临时栈（任何新端口上新起的 Vite）起来后，**先用浏览器打开一次目标页，等关键元素渲染出来**，再开始跑用例 / 计时。
主线派 E2E 片时把这一步写进执行步骤（`subagents.md §2 f`）。

⚠️ 撞上这种「一轮成批超时、下一轮全好」时，先按本条排除冷加载，**再**按 §4.1 归因 —— 🚫 不许直接记成「偶发」。

### 4.3 共享库上的测试不得改变全局状态

上一条管的是**临时**资源。真正难查的是另一半：**测试写的是共享 dev 库**，而它改的东西不是临时的。

典型：用例把某个账号置为停用、把某个模板置为已发布、改了系统配置、删了一批"测试数据"，跑完不还原。后果三层，一层比一层难查：

1. 下一轮同一批用例开始**恒定失败**（而不是随机失败）
2. **真人操作也跟着坏** —— 用户来验收，发现登录不上 / 数据不见了
3. 🚨 最坏的一层：这种恒定失败**看起来非常像业务回归**，于是被误归因到刚合并的那次改动上，然后去改一段本来没问题的代码

规则：

- 🚫 **E2E / 集成测试不得改变全局状态**：用户启停用、角色权限、模板/配置的发布态、系统级开关、公共基础数据
- 必须改的，**用例自己在 `finally` 里还原**，并在测试方案里登记「本用例会动哪些全局状态」
- 🚫 **共享库上不许跑会清库的测试**，哪怕清库写在 `beforeAll` / `setup` 里 —— 那属于 `CLAUDE.md` §3.2「环境销毁」红线，停下来报告
  > 📖 那**本次运行自己建的一次性库**怎么回收？→ **§4.5 末节**。答案不是「申请放行 `DROP`」，是让回收动作根本不需要 `DROP`。
- ⚠️ 并发度配置（如 `workers: 1`）**可能是契约不是性能参数**。调大之前先查它旁边有没有注释、`INDEX.md` 里有没有登记
- 🚦 **未合并分支的数据库迁移，不许未经主线同意就落进共享测试库**（2026-09-17 `repair-260916` 实证晋升）
  迁移一旦写进共享库的迁移历史，**所有不含该迁移文件的分支**在这个库上跑测试都会启动失败
  （本项目开了 `quarkus.flyway.out-of-order=true`，报 `FlywayValidateException: Detected applied migration not resolved locally`）——
  这是**全局状态改动**，且在本分支合并前一直存在。
  ⇒ 子代理要在共享测试库上跑含新迁移的测试前，**先报主线**；主线三选一：
  ① 改用一次性库（克隆后跑，回收走 §4.5 末节）；② 同意落共享库，并**当即通知同机其他会话**（附临时绕开：`QUARKUS_FLYWAY_VALIDATE_ON_MIGRATE=false`），同时尽快合并；
  ③ 🆕 **把迁移文件单独先并入 `master`**（2026-09-17 `task-260916` 实证，用户裁决 D-10）——
  用临时暂存区只提交那一个迁移文件（`GIT_INDEX_FILE=… git read-tree HEAD` + `update-index --cacheinfo`，避开他人未提交改动），
  再 `touch` 主仓一个 java 文件触发 8081 热重载把它应用到开发库。**它把「孤儿迁移」变回「master 上的普通新迁移」**，
  其他分支合一次 master 即恢复；代价是该迁移的效果提前生效（须先向用户呈报并获批）。
  ⚠️ 选 ② / ③ 时的通知**只发同一仓库的会话** —— `ListAgents` 不显示对方工作目录，**发之前先核实**
  （问一句、或从会话名与既有上下文判断）。实证：2026-09-17 主线逐个广播，其中一个是别的仓库（IOT）的会话，对方回信指出发错。
  📌 实证：后端按派工在 `cpq_db_test` 跑出 `V444 success=t`，此后 master 副本在该库跑测试即启动失败，直到本分支合并

> 与 §4 的分工：§4 管「随机挂一条」，本节管「**恒定挂同几条，而且越跑越多**」。症状不同，根因不同，别拿 §4 的思路查本节的病。

### 4.4 新加的守卫 / 断言必须做一次证伪实验

**首次 PASS 不能证明守卫有效** —— 可能它压根没接上。

- 故意破坏它保护的条件，确认它**硬失败**（例：把身份匹配串改坏，确认探活会失败而不是退回「200 就算数」）
- 断言「某事没发生」时（如「一个请求都没发」），必须配一个**阳性对照**，证明观察手段能抓到该事件
- 🚨 **自己写的验证脚本同样适用**：先确认它「能输出东西」。命令写错导致**全程空输出**，看起来和「全部通过」一模一样

### 4.5 多测试员分片并行：能不能共库，看用例写什么

**分片依据是「写入面」，不是 AC 编号。**
按编号均分（`AC-1~4` 给 S1、`AC-5~8` 给 S2）看着均衡，却会把两条都动同一个全局开关的 AC 切到两片 —— **必然打架，且症状是 §4 那种随机失败**，排查成本远超省下的时间。

按写入面分三档，能不能共用一份库由档位决定：

| 片的写入面 | 共库？ | 约束 |
|---|---|---|
| **只读片** —— 列表 / 详情 / 权限可见性 / 文案与布局断言 | ✅ 共用 | 无。这类往往占 E2E 的大头，**是并行收益的主要来源** |
| **私有写片** —— 只写自己造的业务数据（新建一张单、改自己刚建的那张） | ✅ 共用 | 三条缺一不可：① 造数带**分片专属前缀 / 专属账号**；② 只断言自己造的那批；③ `finally` 清理自己那批 |
| **`S-全局` 片** —— 用户启停用、角色权限、模板/配置发布态、系统开关、公共基础数据 | 🚫 不共用 | **串行殿后**，见下。§4.3 的全局状态纪律原样适用 |

🚨 **拿不准归哪档，一律归 `S-全局`。** 误判代价严重不对称：
只读用例误放进 `S-全局`，只损失一点并行度；**全局写用例误放进共库片，损失的是整轮测试的可信度** —— 而且它伪装成业务回归（§4.3 第 3 层），会把人引去改一段本来没问题的代码。

#### `S-全局` 为什么是串行殿后，而不是各给一个独立库

给它独立库当然更快，但那等于把「**项目必须支持快速克隆库**」写成模板的硬依赖 ——
SQLite 是 `cp` 一个文件，Postgres 有 `CREATE DATABASE ... TEMPLATE`，而要跑全量迁移 + seed 的重库，**克隆开销直接吃掉并行收益**。

**默认做法（零基础设施要求，任何项目都能落地）**：

- `S-全局` 不参与并行，等其余片全部跑完，在共享库上**单独跑**
- 用例自己在 `finally` 里还原动过的每一项全局状态，并在 `test.md` 登记「本片会动哪些全局状态」（§4.3 既有要求）
- 🚫 仍然不许清库 —— 那是 `CLAUDE.md` §3.2「环境销毁」红线，**换成独立库也不豁免**

✅ **项目具备秒级克隆库能力时，可升级为「各片独立库、`S-全局` 也并行」** —— 这是优化，不是默认。
升级前两件事缺一不可：① 按 §4.4 做一次**证伪实验**（故意让两片写同一个全局开关，确认它们**真的互不可见**，而不是碰巧没撞上）；
② **先想清楚这些库谁来回收**（见本节末），别等跑完才发现唯一的回收手段是 `DROP` —— 那是红线，当场卡住。

#### 共库并行真正的杀手：全局计数断言

两个测试员各造各的单、互不干扰 —— 但只要有一条断言写成「列表共 8 条」，另一个人造一张单就把它打红了，**而且红得像业务回归**。

🚫 **共库片的断言必须是存在性 / 针对性的，不许是全局计数**：

| ❌ 会被别片打红 | ✅ 分片安全 |
|---|---|
| 「列表共 8 条」 | 「列表里能找到 `EXP-S2-001`，其状态列显示『已审批』」 |
| 「删除后列表少 1 条」 | 「删除后按 `EXP-S2-001` 搜索，返回空」 |
| 「合计金额为 12500.00」 | 「筛选申请人 = `s2-tester` 后，合计金额为 12500.00」 |

⚠️ 这条与 §3 的「断言前先断言结果非空」是同族但**方向相反**：
那条防**空跑**（断言从未执行 → 假绿），这条防**串扰**（断言被别人的数据打红 → 假红）。**两条都要，缺一条就换一种骗法。**

#### 分片计划是编排期产物，不是执行期临时切的

分几片、每片认领哪些 AC、每片的造数前缀 —— **在闸门 A 的派工计划里就定好**（编排纪律见 `subagents.md §1 ②`），落在 §2 追溯矩阵的「分片」列里。

两条硬规则：

- **每条 AC 恰好属于一片，不重不漏。** 重了会有两个测试员同时验它，结论冲突时没人裁决；漏了就是交付缺口
- **片间不得有共享的可写对象。** 列不出「本片会写什么」的片，说明用例还没想清楚，**不许开跑**

⚠️ **不要为了并行而分片。** 只有一两条 AC 的任务分两片，编排开销（N 路审用例 + N 份回报 + 片间冲突裁决）超过收益。
**片数由写入面决定，不由并行欲望决定** —— 全部只读就一片跑完，也完全正当。

#### 写库片在跑的时候，主线自己也是一个并发源（2026-09-22 `task-260920` 晋升，用户裁决采纳）

分片纪律管的是**测试员之间**，但**主线**同样会起浏览器、连同一个库、占同一批端口 ——
而写库片开跑前的「没有别的 Playwright 在跑」采样，**会把主线起的那个也算进去**，于是它按纪律停下不写库，一轮报批作废。

两条，任选其一写进派工：

- **主线侧**：放行写库片之后、到它回报之前，主线不起 Playwright（只读查库、读日志不受限）；
- **派工侧**：在该片的采样口径里**点名排除主线的配置文件**（如 `-c e2e/mainline*.config.ts` 的进程），并写明主线只连自己的临时前端。

🚫 不写清楚的后果不是「撞一次」，是**写库片在报批通过后被自己的安全检查挡住**，而报批窗口（数据状态、实时数字）已经过期。

#### 一次性库怎么回收：让它根本不产生 `DROP`

一升级成「各片独立库」，下一个问题立刻来：**每跑一轮泄漏一批克隆库**。

但 `DROP` 是 `CLAUDE.md §3.2` 的 **deny 档**红线，hook 直接拒**且没有豁免开关**。而红线拦的是「命令文本长什么样」——
`DROP DATABASE app_test_run_a1b2` 和 `DROP DATABASE app_test` 在它眼里**一模一样**，它没有任何办法判断你 drop 的是自己建的还是别人在用的。

所以回收的方向不是「想办法让 `DROP` 被放行」，是**让回收动作根本不需要 `DROP`**：

| 库的形态 | 回收方式 | 撞红线吗 |
|---|---|---|
| **文件型**（SQLite 等） | 库文件就建在本次运行的临时目录里，**连目录一起回收** | 不会 —— 删自己建的临时目录不属于 §3.2 任何一类 |
| **容器型** | 一次性库跑在一次性容器里，**停容器即回收** | 不会 |
| **单库够用时** | 压根不建库：**每个用例一个事务，跑完回滚** | 不会 |
| **必须真 `DROP` 才能回收**（Postgres / MySQL 克隆） | 🚦 **收尾不执行，只产出「待回收清单」**，见下 | 走 §3.2 三步前置，由用户批准 |

**待回收清单**写进 `test-report.md`，主线随**闸门 B 汇报**一次性报给用户批准：

| 库名 | 创建时间 | 归属片 | 状态 | 回收命令 |
|---|---|---|---|---|
| `app_test_run_a1b2c3` | 2026-09-07 14:02 | S1 | 已跑绿，可回收 | `DROP DATABASE app_test_run_a1b2c3;` |
| `app_test_run_d4e5f6` | 2026-09-07 14:02 | S2 | **失败待定位，保留** | —— |

⚠️ **失败的片，它的库不进回收清单** —— 保留到缺陷定位完成。
drop 掉的正是**唯一能复现的现场**，而不稳定失败往往复现不出第二次（§4.1）。
这与 §2「证据必须留得下来」同源，只是方向相反：那条防证据被**下一轮**清空，这条防证据被**本轮自己**清掉。

🚫 **三条底线**：

- **项目固有的测试库不许 drop**，哪怕它叫 `xxx_test`、哪怕写在 `afterAll` / teardown 里。
  它登记在 `CLAUDE.md §1` 的 profile 表里，和 dev 库一样是**别人也在用的环境**（§4.3）
- **子代理没有批准权**：撞到红线停下来报主线，🚫 **不许换个写法再试** —— 换工具、包成脚本、改成 ORM 调用**都算绕路**
- 🚫 **不许为了「能自动回收」去申请豁免或给 hook 加库名白名单**。
  白名单一旦存在，下一步就是把库名凑成白名单的形状 —— 红线等于没有。**宁可每轮多一次用户批准。**

## 5. 冷启动验证（按触发条件跑，不是每任务必做）

**假装自己是刚 clone 这个仓库的人**，只按文档从零跑一遍：装依赖 → 起服务 → 跑测试 → 打开页面。
**跑不通的每一步，都是文档缺口。**

**为什么这一步不能省**：开发期为了隔离而替换掉的东西，真实值**从头到尾没被验证过** ——

| 开发期的替身 | 从没被验证的真实值 |
|---|---|
| 临时端口 | **契约里声明的端口**（可能压根绑不上） |
| worktree 里的依赖目录 | 主工作区能不能装起来（worktree 一删就没了） |
| 每用例一个临时库 | 真实库上的迁移 |
| mock 掉的外部依赖 | 真实依赖的连通性 |
| 工具默认输出目录里的截图 | 下一轮就被清空，等于没有证据 |

**所有测试全绿，都证明不了「应用能在它自己声称的配置下启动」。**

两条配套：
- **前移一个 5 秒的冒烟**：开发早期就用**声明端口**绑一次，别等亲验才发现绑不上
- 冷启动跑不通的步骤，**补进 README 或任务文档**，不要只在自己会话里记着

### 5.1 触发条件：命中任一即必跑

上面说的是它**为什么有价值**，但那价值不是每个任务都重新产生一次 —— 不碰依赖、不碰配置的任务，
第 N 次冷启动验的是和第 N-1 次**完全相同的东西**。所以改成条件触发：

| 必跑 | 为什么 |
|---|---|
| **依赖清单有改动**（`package.json` / `pom.xml` / `requirements.txt` / lockfile） | 装得起来这件事本身变了 |
| **启动配置 / 端口 / 连库串有改动** | 「声明的配置」变了，而全绿的测试用的是开发期替身 |
| **有新增迁移** | 真实库上的迁移从没在测试里跑过 |
| **本任务在 worktree 里装过依赖** | worktree 一删依赖就没了，**主工作区能不能装起来从头到尾没被验证过** |
| **改动了 README 或启动文档本身** | 改了说明书，就要按说明书走一遍 |
| **距上次冷启动 ≥ 5 个已交付任务** | 防长期漂移 —— 没有任何一次改动"负责"打破它，但它就是会坏 |

全不命中 → **可跳过**。

### 5.2 跳过必须留痕，否则「跳过」和「忘了」长得一样

🚫 **不许凭印象说「上次跑过」。说不出是哪个任务跑的，就当没跑过。**

两件事绑死：

1. **闸门 B 汇报里必须有这一行**（写「已跑」或写理由，二选一，不写就是漏项）：
   ```
   冷启动：已跑 ✅
   冷启动：未触发（不碰依赖/配置/端口/迁移；上次验证 task-260901-xxx）
   ```
2. **跑过冷启动的 `RECORD.md` 条目必须带 `[冷启动✓]` 标记** —— 这样查上次只要一条命令：
   ```bash
   /usr/bin/grep -a '\[冷启动✓\]' docs/RECORD.md | tail -1
   ```
   > 没有这个标记，「距上次 ≥ 5 个任务」这条触发条件就**无法判定**，于是会退化成永远不跑。
   > 一条规则如果它的触发条件查不了，它等于不存在。

## 5.5 🔑 判据本身可能是零证据 —— 三种形态，观测结果都不红

**这是本项目 2026-09-07 一天内被四个会话互相纠出至少 8 次的同一族问题。**
共性是：**当事人都查了，而且查的都属实** —— 但**属实 ≠ 是证据**。

| 形态 | 长什么样 | 为什么骗得过复核 |
|---|---|---|
| **① 只验了契约的一侧** | 绿 | 「后端要求 `customerNo`」验了、「前端提供 `customerNo`」没验 ⇒ 合并后按钮必然 400 |
| **② 验了一个恒真的东西** | 绿 | 「89 段 SQL 的编译产物是否逐字节相同」—— 它们按**视图名**文本引用，改视图体不改 SQL 文本 ⇒ **结构上必然相同** |
| **③ 验了一个恒为空的样本** | **既不绿也不红** | 拿三个「同形态」的存量组件当「既有缺陷」的证据，而它们**渲染行数 = 0** ⇒ 既没成功也没失败，**却极容易被读成「和我一样坏」** |

| **④ 验了一个回滚不到位的对照** | **绿，且看起来像"白测"** | 改动落在**配置驱动**的链路上时，**回滚代码 ≠ 回滚行为** —— 见下 |

#### 形态④ 详解（2026-09-10 `repair-260910` 教训晋升，由测试代理拒绝执行主线指令而暴露）

主线在 `test.md` 里写的还原实验是「把编译器改动改回去重跑，应重新出现 4 行」。**这在本案是零证据**：

> 实测：视图重生成**之前**，跑着**全部** Java 改动的实例，产品页签**仍是 4/7/4 行**，与 master 逐字节相同；
> 重生成之后，同样的代码、同样的库变成 1 行。
> ⇒ **决定渲染行为的是已落库的 `sql_template`（编译产物），不是编译器的实时产出。**

所以回滚编译器而不重新编译视图，结果**必然不变**，按「不变红 = 白测」的字面判据会得出**完全错误的结论**。
而真正意义上的回滚 = 改共享库的编译产物 = **全局配置写入**，测试片没有批准权。

🔑 **判据**：**改动是否经过一层"落库的产物"？** 经过了，就要问「我回滚的是**源**还是**产物**」——
只回滚源而产物还是新的，实验测的是产物，跟你的回滚没关系。

✅ **可替代的三种做法**（本次实际采用，全部在私有写入面内）：
**两版产物对跑**（同时刻同夹具，拿旧产物与新产物各跑一次 ⇒ 证明绿不是恒真）·
**正向控制**（改输入值，看输出是否跟着变 ⇒ 证明绑定是活的，不是常量）·
**判别性反例**（构造一个能区分"修对了"和"修错了"的输入 —— 本次是填一个表中不存在的客编：
**1 行且该列空** = 谓词在 `ON`；**0 行** = 误入 `WHERE`；**4 行** = 谓词没生效）。

还有一个高频变体：**判据落在一个恒为 1 的维度上**。
现网「每个料号只对一个客户」时，任何「跨客户是否串号」的等价性验证**都必然通过** ——
它证明的是「**单客户下**等价」，不是「多客户下等价」。⚠️ **这类前提还要限定维度**：
同一句话在 A 表上成立、在 B 视图上可能不成立，混用会导出错误结论。

### 🚨 形态⑤：**验收库 ≠ 生产库时，代价可能在验收库里根本不可见**

**2026-09-11 跨会话实测晋升。**

一个会话的方案有个已知代价（丢冻结版本价），它向用户呈报时写的是
「**该代价在本库不触发**（关键表 0 行）」—— 用户据此批准。

**实测**：那个"本库"是它的**验收库**（`cpq_db_0910`，关键表 **0 行**）；
而**生产开发库** `cpq_db_0724` 上同一张表有 **4 行** ⇒ **代价真实触发**，
某客户元素合计从 `43872.854` 掉到 `856.84`。

🔑 **判据**：**凡是「本库不触发 / 现网没有这种数据 / 影响面为零」这类论断，
必须点名是在哪个库、哪个环境实测的，并在生产库上复核一次。**

⚠️ 这一条与 `subagents.md §5.5` 咬合：**批准的有效性取决于批准时他掌握的信息**。
"代价不触发"是批准的前提，前提在另一个库才成立 ⇒ **批准本身失效，必须重新呈报**。

📌 它是被**另一个会话的通知**逼出来的 —— 对方发现这个改动被兑现到了生产库，
它才去查三个库的对照。**跨会话互相通知的价值正在这里**：
一个会话看不见自己验收环境的盲区，另一个会话在别的环境里一眼就撞上了。

### ⇒ 一条判据在使用前，先回答

> 🔑 **先证明这个判据在【已知答案】上给得出正确结果，再拿它下结论。**

- 有没有**阳性对照**？（把修复改回去 / 让老逻辑跑一遍 / 在改动前的版本上打同一条判据）
- 样本**非空**吗？0 行的样本证不出任何事
- 判据落的那个维度，**取值集合大于 1** 吗？
- 契约的**另一侧**验了吗？

📌 **实证**：AC-2「两个客户的行并存」在「整组删除根本没执行」时**同样成立** ——
必须补一条「同客户改一格再导 ⇒ 旧行被删+归档+升版」的阳性对照，才能同时证明
「删除路径确实执行了」+「删除按复合轴收窄」两件互相独立的事。

## 5.6 守卫改动：**「该拦的拦住」和「不该拦的别拦」都要验**

**假阳性比漏放更容易让守卫被整个废弃。** 同一条守卫 2026-09-07 一天内被证伪三次，**两次是假阳性**：

| 形态 | 后果 |
|---|---|
| 漏放（左边只看已提交内容） | 未跟踪的迁移文件从守卫底下溜过去 |
| **假阳性 · 恒拦**（`git ls-tree` 少了尾斜杠 ⇒ 右边恒空 ⇒ 全部判成差集） | **每次都拦 ⇒ 第二天就会被人直接注释掉** |
| **假阳性 · 诱导破坏**（按命令行子串匹配进程） | **诱导你去「按端口停掉」别人的进程** —— 诱导的动作本身是破坏性的 |

⚠️ **证伪实验只能证明它抓得住你想到的那一类**：用「已提交的迁移」做的 4/4 实验，
**结构上不可能暴露「未跟踪文件」这个洞**。

> 🔑 **守卫比纪律值钱的地方**：**守卫不依赖你当时想不想得起来。**
> 实证：某会话上午刚亲手把一个维度加进守卫、还做了证伪实验，**四小时后排查自己的事故时却没去问它**。
> **知道一条规则，和在正确的时刻想起用它，是两回事。**

## 5.7 🔁 证伪实验的三条硬纪律（2026-09-13 一夜之内同型失手两次后晋升）

**证伪实验（把修复改回去、看是否变红）是本册最锋利的工具，也是最容易产出假证据的工具。**
本节三条各对应一次真实事故，都不是假想。

### ① 还原动作必须带「还原后复验」，且路径用**绝对路径**

🚫 **只在注释或 TODO 里写「实验结束必须还原」是不够的** —— 两次实证：

| 失手 | 经过 | 后果 |
|---|---|---|
| **人没了** | 前端代理把修复短路成 `if (false && …)` 跑对照，**会话进程异常退出**，代理连同还原一起消失 | 开关留在 `false`；**另一个测试代理在这段时间跑同一条 AC，产出一份「修复无效」的假红**，两份证据打架，主线险些据此推翻正确的修法 |
| **脚本写错** | 主线把还原写进 `trap EXIT`，但 `git checkout -- cpq-frontend/src/…` 是**相对路径**，trap 触发时 cwd 已被切到 `cpq-frontend/` ⇒ 路径不匹配、**静默什么也没做** | 工作区留在实验态。**是脚本里多写的那句「还原后再探测一次」把它喊了出来**（`命中=1 应 0`） |

⇒ **规范**：
- 还原后**必须再探测一次**并把结果写进日志（`命中=N（应 0）`），🚫 不许只执行不复验；
- 还原命令一律用**绝对路径**，或在同一条命令里显式 `cd` 到仓库根；
- 实验**开始前先提交**一次（哪怕是 WIP），给还原留 git 安全网。

### ② 干预必须**先证明生效**才允许跑测试

🚫 **「我改了文件」不等于「跑的是改后的代码」。** 实证：vite 在 WSL + git worktree 下**没触发 HMR**，
连探 6 次（含缓存穿透参数）服务的都还是旧代码 —— 此时跑出来的红是**空验证**，与被测对象无关。

⇒ **规范**：干预后先向运行时**索取模块正文 / 打印实际值**，确认干预标记在场；
**探不到就中止实验、直接还原**，🚫 不许「先跑了再说」。前端确定性做法是**编辑后重启 dev server**，不依赖 HMR。

### ③ 判「代码是否生效」看**运行时正文**，不看**符号存在**

实证：环境探针写的是 `f3_x1: /componentData/.test(src) && /rowData/i.test(src)` ——
修复被 `false &&` 短路时，**这两个符号仍然在文件里**，探针照样返 `true`。
那次假红的日志开头明晃晃印着 `f3_x1:true`，**没有任何人识破**。

⇒ **规范**：判据要落在**会随开关变化的特征**上（短路标记、实际返回值、实际请求数），
🚫 不许用「某个标识符/函数名是否出现」当「功能是否启用」的判据 —— 那是 §5.5「判据恒绿」的又一形态。

### ④ 判据所在的**环境**，可能正在替被测对象打补丁

前三条讲的是**判据本身过期**（静态信息）；这一条不一样 —— **判据没错、执行也没错，是环境在偷偷补齐缺失的东西。**

> 📌 **实证（2026-09-13，并发会话提供）**：它给共享库落了迁移、也改了 Registry 声明，但**四个文件都没提交进 git**。
> 它本地 `8081` 一直 `401` 正常 —— 因为 **Quarkus dev 读的是工作区文件**，而工作区恰好留着那几个未提交的副本。
> ⇒ 「本地能跑」把「git 里缺了什么」这个事实**完全遮住**；任何人从 master 起后端都会被启动自检拦死，而它自己看不见。

⇒ **轻量判据（不必真换环境就能自查）**：问一句 ——
**「我的判据和被测对象，是不是同一个进程 / 同一棵树 / 同一份缓存喂出来的？」** 是，就不独立。

| 本次三个实例 | 判据 | 被测对象 | 共用的那层 |
|---|---|---|---|
| 探针假绿 | 源码里符号在不在 | 开关开没开 | 同一份文件文本 |
| 注释误导 | 一句 javadoc | 后端统计口径 | 同一个文件（但不会一起更新） |
| **环境代偿** | 本地服务能不能起 | git 里有没有那几个文件 | **同一棵工作树** |

⇒ **重判据必须换环境**：干净 `checkout` / 另一台机器 / CI。这是唯一能把「代偿」拆开的办法。

### ⑤ 复跑与证伪实验**不得覆盖已留档的证据**（2026-09-18 `repair-260916` 同一根因 2 次后晋升，用户裁决采纳）

前四条管的是「实验结论对不对」；这一条管「**实验跑完，之前那份对的证据还在不在**」。

| 失手 | 经过 | 后果 |
|---|---|---|
| **复跑别人的脚本** | S-C 按派工复跑 S-B 的浏览器 spec，而该 spec 把截图 / JSON **写死**到 `证据/测试/S-B/` | S-B 那一轮的 **57 个证据文件被覆盖**；主线靠开跑前的检查点提交才恢复 |
| **证伪实验** | 后端把修复临时改回旧写法、重跑两个测试类证明「会变红」，**surefire 报告写在同一个 `target/`** | 磁盘上只剩**报错那一版**，「修复后通过」的报告没了；主线在还原后的代码上重跑 20 条才补回证据 |

⇒ **规范**：
- 测试脚本的**证据输出目录必须可由环境变量改写**，🚫 不许写死到某一片 / 某一轮的目录；
- 复跑他片脚本、做证伪实验，**一律写到独立目录**（如 `…/<本片>/复跑-<栈>/`、`…/证伪-<时间>/`）；
- 做不到隔离时：**开跑前先提交检查点**（哪怕是 WIP），**跑完在正常代码上再跑一次**，留最终证据；
- 回报里写明「实验产物放在哪、是否覆盖过既有证据」—— 🚫 不写，主线就会拿被覆盖后的文件当证据。

### ⑥ 多目标验证：断言前先校验**条数**，否则「少查了一个」会静默变成「全部通过」（2026-09-20 `repair-260918` 闸门 B 晋升，用户裁决采纳）

前五条管「实验本身可信吗」；这一条管「**我以为验了 N 个，实际只验了 N−1 个**」。

📌 **实证**：主线亲验脚本取 3 个对照料号查它们在升版前后是否被改动，断言「每条都没变」通过 ✅。
实际上其中一个料号 `PERF600-B00999` 在那张报价单里**根本不存在** —— SQL 静默返回 2 行，
`every()` 在 2 行上成立，断言照过。**缺的那一个不会报错，只会消失。**

⇒ **规范**（多目标 / 多料号 / 多文件 / 多环境的批量验证一律适用）：

1. **先断言条数**：`返回条数 == 预期条数`，对不上**直接判失败**，🚫 不许只断言「每条都满足」；
2. **再断言值互异**（值本该不同时）：全部相同往往说明取错了同一个对象，或夹具同构到分辨不出串值；
3. 目标集合**先证明非空且成员齐全**，再进入比较逻辑 —— 与 `CLAUDE.md §5`「grep 空结果 ≠ 不存在」同源：
   **少返回不是「验过了」，是「没查到」。**
