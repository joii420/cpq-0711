# 规则分册 · 首次进入项目（初始化）

> **何时必读**：新会话开始时发现 `CLAUDE.md` §1 仍带「待探测」字样，或 `docs/` / `dev-docs/` 下缺少 §2.1 表中的文件。
> **一次性**：本册只在项目初始化时执行一遍。做完之后它就不再被触发 —— 这也是它不放在常驻层的原因（每个会话、每个子代理都加载一段只用一次的内容，是纯浪费）。
> **效力**：与 `CLAUDE.md` 同等。**必须先做完本册，再执行用户的任务。**

> 目录分工：**`docs/` = 项目文档目录**（长期知识）；**`dev-docs/` = 项目任务目录**（每任务一子目录 + 任务索引）。

---

## 0. 🌱 先判断：这是不是一个还没有代码的绿地项目

**本册整个 §1 做的是「探测」。空项目上无从探起 —— 必须先分流，不能埋头往下走。**

```bash
# 排除模板/文档/依赖目录后，找任何源码或依赖清单
find . -maxdepth 3 \
  \( -name node_modules -o -name .git -o -name claude-template -o -name .claude \
     -o -name docs -o -name dev-docs -o -name dist -o -name build \) -prune -o \
  -type f \( -name 'package.json' -o -name 'pom.xml' -o -name 'build.gradle*' -o -name 'go.mod' \
     -o -name 'pyproject.toml' -o -name 'requirements.txt' -o -name 'Cargo.toml' -o -name '*.csproj' \
     -o -name '*.ts' -o -name '*.tsx' -o -name '*.js' -o -name '*.vue' -o -name '*.py' \
     -o -name '*.java' -o -name '*.go' -o -name '*.rb' -o -name '*.php' -o -name '*.cs' -o -name '*.rs' \) -print -quit
```

**有输出** → 既有项目，正常往 §1 走。

**无输出** → 🚦 **停下来问用户，不要继续。** 报这三句，等回话：

1. 「探测到本项目还没有任何应用代码（列出你查了什么、结果为空）」
2. 「所以现在**探不出**技术栈 / 端口 / 数据库 profile —— 强行初始化会把 `CLAUDE.md` §1 填成空的」
3. 「要怎么走？**A. 你先告诉我技术栈和端口，我搭出骨架再初始化**；**B. 把『搭骨架』当第一个正式任务走完整流程**（立项 / AC / 原型图 / 闸门）」

🚫 **不许把 §1 按空项目填完然后往下走。** §1 的端口表是后面所有自检项的取值来源 ——
前端「每个改动文件的模块地址 200」、后端「endpoint 返 200/401」、`CLAUDE.md` §1 的存活自检，全都从那张表里读端口。
§1 是空的，这些自检就全部失去判据，而且**不报错**：它们会被悄悄换成「我看了一下代码，应该没问题」。

> 实测教训：这一条是被三轮实测反复撞出来的。用户照 `README` 走「拷贝 → install → 说『按 CLAUDE.md 走首次初始化』」，
> 在空项目上跑完初始化，§1 全空，后续整套规则失准。**这不是用户操作失误，是本册当时缺了这个分支。**

## 1. 探测并回写 `CLAUDE.md` §1

自行探测，**不要问用户能自己查到的东西**：

| 要探测的 | 从哪查 |
|---|---|
| 语言 / 框架 / 版本 | `README*`、`package.json`、`pom.xml`、`build.gradle`、`go.mod`、`pyproject.toml`、`*.csproj` |
| 前后端子项目目录 | 仓库根下含独立构建文件的子目录 |
| dev server 端口 | `vite.config.*`、`webpack.config.*`、`application*.properties`、`*.yml`、`.env*` |
| 数据库连接 / profile 列表 | 同上；`application-<profile>.*` 的文件名即 profile 名 |
| 已在跑的服务 | `ss -ltnp 2>/dev/null \| grep -E 'node\|java\|python'` |
| 核心模块与数据流 | 顶层目录结构 + 路由/控制器清单 + README |

探测完把结论**直接改写进 `CLAUDE.md` §1**，删掉「待探测」标记。

### 1.1 🔒 凭据一律脱敏回写

口令、API Key、Token **不许原样写进 `CLAUDE.md`** —— 它要提交进仓库。
写成环境变量名 + 占位符（`${DB_PASSWORD}`），主机与库名可以写。

发现仓库里已有明文凭据 → 在 §3 汇报里点名，**不要自己改动或删除**（可能有别处引用）。

### 1.2 profile 表的「可写？」列必须填满

`✅ 可写`（本地/个人库）/ `⚠️ 共享可写`（多人共用，写之前想想别人）/ `🚫 只读`。

探测到**生产 profile** 时，`CLAUDE.md` §1 的生产库红线三条必须落地，不能留空。

### 1.3 顺带裁剪 `CLAUDE.md` 与各分册

凡写着「按项目替换 / 视情况选择」的地方，一律在此步定下来，**不留悬空条件句**。
典型：前端不是组件化 SPA → 把 `docs/rules/frontend.md` 的 UI 规范整册替换为等效约定。

🚫 **但裁剪权有边界——被约束方不能删自己的约束**：

| 范围 | Claude 能做什么 |
|---|---|
| `CLAUDE.md` §1 速览、§2 文档表的**探测结果** | ✅ 直接回写 |
| `CLAUDE.md` §3~§7 与 `docs/rules/*` 的**规则条款** | ⚠️ 只能**替换为等效约定**（保留「规则 + 理由 + 例外 + 自检项」骨架），且在 §3 汇报里**逐条列出改了什么** |
| 规则条款的**删除** | 🚫 **必须用户点头**。判不准就保留原文 + 标「适用性待确认」 |

> 理由：初始化发生在会话最开头，用户还没读过内容。此刻允许删条款，等于规则在用户视线外消失且不留痕。

### 1.4 探测不到的

典型：业务定位、模块职责的业务含义。
→ 向用户提**一个**集中的问题问清，**不要臆造**。

## 2. 创建缺失的文档骨架

### 2.0 🚨 先确认这是个 git 仓库（不是就建）

```bash
git rev-parse --is-inside-work-tree 2>/dev/null || {
  git init -q
  printf 'node_modules/\ndist/\nbuild/\n*.db\n.claude/hooks.log\n.claude/worktrees/\n' >> .gitignore
  # ✅ 空仓库首次提交是 `git add -A` 的唯一合法场景（见 git-worktree.md §3 例外）：
  #    此刻不存在「别人未提交的改动」可夹带。仓库有了第一个 commit 之后禁令即生效。
  git add -A && git commit -qm "chore: 接入 claude-template 规则包与项目文档骨架"
}
git log --oneline | head -3     # 必须有输出
```

**没有 git 仓库，下面这些规则会整片失效，而且是静默失效**：

| 失效的 | 因为 |
|---|---|
| 闸门 A 之后的分支隔离、worktree（`git-worktree.md` 整册） | 没有分支可开 |
| **派子代理**（`subagents.md`） | 派工六段的第一段是「worktree 绝对路径 + 分支名」，填不出来就派不了 |
| 提交纪律、并发纪律、`git show --stat` 自查夹带 | 没有提交这个动作 |
| §3.2 红线里的「历史销毁」整类 | 没有历史 |
| 合并六步、`git revert` 出口 | 没有合并 |

⚠️ 已有仓库但**工作区脏**（`git status` 一堆未提交改动）→ 在 §3 汇报里列出来问用户要不要先提交，**不要自行提交别人的改动**。

### 2.05 🔌 外部依赖自检（缺了不报错，只会静默降级 —— 所以必须点名）

本规则包引用了两个外部能力。**它们不会自动安装、也不会自动初始化**，而缺失时的表现是「悄悄换个做法继续走」，用户看不见。

```bash
command -v jq         >/dev/null && echo "jq ok"        || echo "缺 jq"
command -v codegraph  >/dev/null && echo "codegraph ok" || echo "缺 codegraph"
ls -d .codegraph 2>/dev/null     && echo "索引已建"      || echo "索引未建"
```

| 依赖 | 缺了会怎样 | 处置 |
|---|---|---|
| **`jq`** | 六个 hook 全部静默失效（红线不拦、分册不注入、自检不检查） | 报给用户装，**这是最严重的一个** |
| **代码索引**（`codegraph` + 本项目 `.codegraph/`） | `CLAUDE.md §5`、`change-protocol.md §2 步骤1`、`frontend.md §4` 要求的「影响面用索引算，不要靠 grep 估」**永远无法满足** | 见下 |
| **需求澄清技能**（`brainstorming` 等） | `§4.5` 步骤 -1 降级成随口问几句，**AC 全是猜的**，要到闸门 B 才显形 | 探不到就在 §3 汇报里点名，并说明本项目的步骤 -1 将由你自己按 `task-docs.md §6.5` 的提问框架承担 |

**代码索引的处置 —— 🚦 只提醒，由用户决定，你不许自行执行**

🚫 **不要自己跑 `codegraph init`。** 它会扫描整个仓库、可能耗时几分钟、写入上百 MB 到工作区 ——
这是**用户的决定**，不是初始化的既定动作（§4.3 决策权归属）。

在 §3 汇报里报**三件事**，然后等回话：

1. 「本项目**未建代码索引**」
2. 「不建的后果：`CLAUDE.md §5`、`change-protocol.md §2 步骤1`、`frontend.md §4` 要求的『影响面用索引算、不要靠 grep 估』**无法满足**，只能退回 grep」
3. 「要建的话是这两条命令，我可以代跑，也可以你自己跑」：
   ```bash
   codegraph init .                   # 扫全仓库，大项目可能几分钟
   echo '.codegraph/' >> .gitignore   # 🚨 必做，索引可能上百 MB
   ```

✅ **用户说不建，是完全合法的答复** —— 照常往下走，只是把降级记在汇报和 `RECORD.md` 里。
⏱ 顺带说明时机：**现在这一步是最合适的**（老项目代码已齐、绿地项目骨架刚搭完）。用户若说「以后再说」，之后任何时候补建都行，不阻塞任务。

🚫 **未建索引时，不许在自检里写「已跑影响面分析」** —— 退回 grep 是合法降级，
但要写明「**未建代码索引，影响面由 grep 估算**」，并按 §5 用 `/usr/bin/grep -a` 复核。

### 2.1 文档骨架

只建骨架，不编内容：

```bash
mkdir -p docs dev-docs docs/rules
[ -f docs/PRD.md ]      || printf '# PRD\n\n> 功能交付的唯一标准。需求变更必须同步本文件。\n\n## 1. 产品定位\n\n## 2. 功能需求\n\n## 9. 演进史\n\n| 日期 | 变更 | 原因 |\n|---|---|---|\n' > docs/PRD.md
[ -f docs/RECORD.md ]   || printf '# 开发记录（多 Agent 共享记忆）\n\n> 开始工作前必读；完成工作后必须追加。\n> 格式：[日期] 模块 - 描述 | 涉及文件 | 关键决策\n\n' > docs/RECORD.md
[ -f dev-docs/INDEX.md ]|| printf '# 任务索引\n\n## 0. 当前项目态势\n\n- 进行中的任务：\n- 未闭合缺陷：\n- 未合并分支：\n- Backlog 概况：\n\n## 0.1 按症状反查\n\n| 症状 | 归属任务 | 根因 |\n|---|---|---|\n\n## 0.2 按代码文件反查\n\n| 文件 | 被哪些任务动过 | 压着的契约 |\n|---|---|---|\n\n## 1. 任务清单\n\n| 目录 | 状态 | 一句话 |\n|---|---|---|\n' > dev-docs/INDEX.md
[ -f docs/BACKLOG.md ]  || printf '# Project Backlog\n\n> 自动维护文件，spec 评审后写入，开发完成后更新。\n\n## 状态说明\n- [ ] 待开发\n- [~] 进行中\n- [x] 已完成\n- [-] 已废弃（需注明原因）\n\n---\n\n## 待开发条目\n\n---\n\n## 变更记录\n\n| 日期 | 操作 | 条目 | 备注 |\n|---|---|---|---|\n' > docs/BACKLOG.md

[ -f docs/架构基线.md ] || printf '# 架构基线（核心约定，破坏前必须评估）\n\n> 不轻易改动的核心结构与契约。破坏基线前：评估 + 用户裁决。\n> 与 CLAUDE.md §4.3 配套——判「算不算涉及数据契约」时查这里，不要临场靠感觉。\n\n## 1. 核心模块与边界\n\n## 2. 数据契约\n\n## 3. 不变量\n\n## 4. 破坏性改动清单\n\n| 基线项 | 谁依赖它 | 破坏的后果 | 改动前必须做什么 |\n|---|---|---|---|\n' > docs/架构基线.md
```

⚠️ `docs/rules/` 下的分册**随模板一起分发**，不由脚本生成。缺了要从模板包补齐，**不要现编** —— 现编出来的是你以为的规则，不是这套规则。
