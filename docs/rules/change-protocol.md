# 规则分册 · 强联动改动与规则演进

> **何时必读**：改字段类型 / 枚举 / DTO 结构 / 跨前后端契约；改任何「一处改了、多处会静默失效」的东西；发现新的踩坑要沉淀时。
> **效力**：与 `CLAUDE.md` 同等，不是参考资料。冲突时以 `CLAUDE.md` 为准。

---

## 1. 什么算「协议级改动」

四类，命中任一即是：

1. **跨前后端的数据契约** —— 字段类型、枚举值、DTO 结构、接口返回形状
2. **渲染主链路文件** —— 列表 / 编辑 / 详情共用的取数、缓存、展开逻辑
3. **数据库迁移**
4. **任何「改一处、多处静默失效」的强联动改动**

协议级改动的共同特征：**漏一处不报编译错、不报运行时错，只是行为不对。**
这是最贵的一类 bug —— 因为所有自动化防线（编译、类型检查、单测）**全部看不到它**。

## 2. 强联动改动 SOP（四步，不可跳）

### 步骤 1：写代码前 —— 列出全部检查点清单

- 全工程 `grep` + 跑影响面分析（`codegraph_impact` 或等效工具）
- ⚠️ **影响面分析优先于 grep**：它按真实调用边遍历，不漏别名 / 间接引用 / 动态分发；grep 只能当补充
- ⚠️ **grep 结果为空 ≠ 不存在** —— 某些环境的 `grep` 是别名（如 `ugrep -I`），会把含大量非 ASCII 的源文件**静默判为二进制并返空**。下"影响面为零"的结论前，必须用 `/usr/bin/grep -a` 复核
- **清单写进任务文档**，不要只放在脑子里

> 🚨 **列清单之前，先确认你对每个符号的理解来自函数体，不是来自签名**（2026-09-10 `repair-260910` 教训晋升）
>
> 实证：主线把 `rowFingerprint(rowKeyFields, driverRow)` 的**签名**当成了**语义**，据此断定
> 「指纹只取行键字段 ⇒ 多行会撞」，并把整个方案建在这个前提上、派了 5 个子代理。
> 打开函数体才发现它是**两段拼接**（行键段 + **全量键升序段**）＝ 整行内容指纹，结论完全相反。
>
> **三条证伪材料，任意一条都能在 30 秒内拦下**：① 函数体本身 ② 该函数所属类的 javadoc
> （明写「effKey 保留仅为签名兼容、不参与匹配」）③ **库里一条真实数据**（墓碑里的 fp 各不相同）。
> 🔑 **动作**：下结论前至少做到「**打开函数体** + **看一眼真实数据**」。
> 名字像、签名像、形态像，都不是语义。

> 🚨 **跨层数据契约的单测，夹具必须从真实数据取材，🚫 不许手搓**（2026-09-11 `task-260911` 教训晋升，同类第 2 次）
>
> **实证**：真实 `basicDataValues` 的键**带花括号** `{$builder_xxx._客户料号_客户产品编号}`，
> 而手搓夹具写成了**不带花括号**的形态。旧代码 `key.endsWith("." + 列名)` 对夹具**为真**、对真实数据**恒假**。
> ⇒ **证伪实验真的跑了、也真的变红了，但它证伪的是一个真实世界不存在的输入形态。**
> 手搓夹具在简化结构时，**顺手把唯一能抓住这个 bug 的那个特征也简化掉了**。
>
> 更讽刺的是：该响应类的 javadoc **本来就写着**「key = 字段原始路径**(含花括号)**」—— **契约一直在那儿**。
>
> ✅ **做法**：`ObjectMapper.readValue` 真实响应 / 真实落库 JSON，**逐字照抄**，键名、嵌套、类型一个不改。
> 🚫 `Map.put("简化过的键", 值)`。

### 步骤 2：写代码中 —— 对照清单逐项勾掉

一个检查点一个勾。**没勾完不算写完。**

### 步骤 3：写代码后 —— 跑 E2E，并在所有受影响视图分别验证

- 跑 E2E（不是可选，见 §3）
- **列表 / 编辑 / 详情**三处**分别**验证 —— 只验一处是最常见的漏法
  > 典型：编辑页正常、详情页显示僵尸数据，因为详情页的只读渲染组件缺了对应分支

### 步骤 4：交付必含

- 清单的 grep / 影响面分析**命中输出**（原始输出，不是"我查过了"）
- E2E 通过证据
- 各视图截图（**修复前 vs 修复后**）

---

## 3. 为什么协议级改动必须跑 E2E

**跳过 E2E 等于跳过自检。** 协议类 bug 的表现是「渲染不对但不报错」——类型是对的值不对、单测跟着实现者一起错、接口返的数据没问题是消费端解析错了。**三道自动化防线全部看不到它，只有把整条链路跑一遍才暴露。**

---

## 4. 新增枚举值 / 新字段类型：协议传播点清单

新增一个枚举值或字段类型时，它要在**很多地方**被认识。典型传播点（按项目实际补全）：

| # | 传播点 | 漏了的症状 |
|---|---|---|
| 1 | 后端校验白名单 | 存不进去 / 报"非法值" |
| 2 | 数据库约束 / 枚举定义 | 写库失败 |
| 3 | 前端类型定义 | 类型报错或被 `any` 吞掉 |
| 4 | 数据规范化 / 映射函数 | 值被静默丢弃 |
| 5 | 缓存 key 的维度 | **串号**：不同实例拿到同一份缓存 |
| 6 | 渲染分支（列表 / 编辑 / **详情**） | 显示空白 / "—" / 僵尸旧值 |
| 7 | 计算/公式引擎的字段值循环 | 参与不了计算，静默算漏 |
| 8 | 路径采集 / 依赖收集 | 数据不预取，出现"加载中"永久占位 |
| 9 | 导出（Excel / PDF）分支 | 导出列为空 |
| 10 | 已存快照 / 历史数据的兼容 | **老数据显示错**，新数据正常 |

🚨 **第 5、10 两条最容易漏**：
- **缓存 key 少一个维度** → 同一个组件在不同上下文被复用时互相污染，而且只在特定顺序下复现
- **老快照没迁移** → 新建的一切正常，打开历史单据就错。测试用的都是新建数据，**测不出来**

> 📌 **cpq 项目版的传播点清单在 `docs/方案制定前必读.md`** —— 那里有 7 类改动决策树、
> AP-44 的 17 个协议检查点、以及连环 bug 案例。**本册是通用 SOP，那份是本项目的实际清单，动手前两份都要过。**

> **这张表要随项目长**。每发现一个新的传播点就加一行，并在 `dev-docs/INDEX.md` 的「按代码文件反查」表登记「这些文件压着什么契约」。

## 4.5 新增「运行时占位符 / 上下文变量」：传播点不在 §4 那张表里

§4 的清单管的是**枚举值 / 字段类型**。**新增一个运行时占位符**（SQL 模板里的 `:xxx`、由后端在执行期绑值）
是另一族，传播点完全不同 —— 2026-09-10 `repair-260910` 实测，漏掉其中任一条都**不报错、只是值恒空**：

| # | 传播点 | 漏了的症状 |
|---|---|---|
| 1 | 执行期绑值（从上下文取值补进 namedParams） | 占位符未绑定 → 按既有降级规则变成字面量 `NULL` |
| 2 | **所有不经主绑定管线的旁路** | 预览 / 校验 / dry-run 各有各的字面量替换，逐条补 |
| 3 | 🚨 **批量合并（"合桶"）的准入闸门** | **最隐蔽**：合桶路径为了复用结果**根本不传行级上下文**，闸门若不认识新占位符，它会继续把该视图判为「无行维度」⇒ 走合桶 ⇒ 取不到值 ⇒ **页签行数看着对了、新列却恒空，且不报错** |
| 4 | 编译产物的重新生成 | 编译器改了口径，**存量视图的 SQL 文本是当年落库的快照**，不重放就永远是旧口径 |
| 5 | 谓词的**摆放位置** | 挂 `LEFT JOIN … ON` 还是 `WHERE`，在"值为空"时行为相反：`ON` 保住左表行、`WHERE` 让整页签 **0 行且不报错** |

🔑 **一句话判据**：**这个占位符的值来自哪一级上下文？**
单据级（全单一个值）不影响批量合并；**行级**（每行不同）会让"按某个键合并查询"的等价性**在定义上失效** ——
那不是性能退化，是**结果会错**，必须同时处理合并策略。

## 4.6 「改了配置但暂不生效」不是可控中间态 —— 是定时兑现

**2026-09-11 `task-260911` 实测晋升。**

本项目的取数视图有两层：**语义图**（配置，`semantic_node` / `semantic_node_column`）
和 **编译产物**（`component_sql_view.sql_template`，落库）。改了前者、没重编译后者，就形成 **stale**。

🚨 **视图重编译是全量的**：`POST /config-center/refresh-all-snapshots` with `recompile:true`
实测 `recompileViews=98`，而 `templateIds` **只能定向「快照推送」那一层，挡不住 `sql_template` 被全量重写**。

⇒ **任何人跑一次重编译，所有处于 stale 的语义图改动都会被一起兑现** ——
包括别人的、还没验完的、甚至还在等用户裁决的。

**两条动作**：

1. **改了语义图就要么当场重编译、要么明确记录"它处于 stale 且会被下一次重编译兑现"** ——
   🚫 不要把它当成"我先改着，等验完再生效"的可控状态。
2. 🚦 **执行重编译前，逐个查清 `recompileChanged` 里每一个的 diff 内容** ——
   🚫 **不接受「与本任务无关」这个说法就放行**。

> 📌 **实证（主线自己的疏漏）**：后端预览时报 `recompileChanged=6`，其中 3 个标注为"与本任务无关的既有 stale"，
> **主线接受了这个判断、没追问 diff 内容就执行了**。事后由测试片查出：那 3 个的改动是
> `f_material_element_price` → `f_customer_element_price`（价格函数换客户级），实测**非等价**
> （某客户合计 `43872.854 → 856.84`，机制是 `versioned` 整支被摘掉），
> 且其中一个是 **ACTIVE 组件、被三个 PUBLISHED 模板引用**。
> ⇒ 「与本任务无关」只说明**责任归属**，不说明**影响为零**。

## 4.7 配置类迁移上线后，必须确认长驻实例重载了配置

**2026-09-11 `task-260911` 实测晋升。**

改配置表（如给语义图的列打角色）的迁移，**对已经启动的长驻实例不生效** —— 它们持有内存快照。

📌 **实证**：在启动早于 `UPDATE` 的实例上打完标记后重新编译，产物**毫无变化**；
同一时刻、同一份配置、同一个库，**全新 JVM 编出来就带新谓词**。
⇒ 验证时差点把"机制不通用"判成失败（**假红**）。

⚠️ **最危险的是纯迁移场景**：本次侥幸没踩到，是因为迁移随代码一起合并 ⇒ 热重启 ⇒ 新 JVM。
**只跑迁移、不动代码时没有这个副作用**，配置改了但行为不变，**且没有任何报错**。

**动作**：这类迁移的交付说明里必须写明「**上线后需重启/重载配置**」，并在验收时**用新进程**验。

## 5. 沉淀：发现新的强联动关系时

三件事一起做，缺一件这条经验就白踩了：

1. **检查点清单**留在该任务目录下
2. **`dev-docs/INDEX.md`「按代码文件反查」表**登记「这些文件压着什么契约」
3. **`docs/RECORD.md`** 追加一条根因记录

### 5.1 风险警告的放置原则

**警告要放在会触发它的人的必经之路上，不是放在报告里。**

判据：**谁最可能破坏这条约束？他动手前会打开哪个文件？警告就该在那儿。**
→ 写进「按代码文件反查」表 + **该文件的行内注释**。

> 反例：把「`workers: 1` 不能调大，否则并行测试会互相清库」只写进测试报告。报告会被归档，而**下一个想让测试跑快点的人只会打开配置文件** —— 他在那里看不到任何警告，那行 `workers: 1` 看起来就只是个性能参数。
>
> 这正是「按代码文件反查」表的真正价值：**它不是索引，是把契约压在文件上。**

## 6. 教训 → 规则的晋升通道

上一节说了教训往哪儿沉淀，但**沉淀不等于生效**：`RECORD.md` 按时间组织、`INDEX.md` 按任务/文件组织，两者都要求下一个人**恰好去查**才起作用。
**同一个坑在 `RECORD.md` 里躺三次，也不会自己变成规则。**

所以晋升要有明确触发条件，不能靠"觉得这条挺重要"：

| 触发条件 | 动作 |
|---|---|
| **同一类根因第 2 次出现** | 🚦 **必须**在收尾汇报里提议「是否升级为规则」，交用户裁决 |
| 症状可归纳（不同表象、同一成因） | 写进 `docs/反模式.md`（按症状反查） |
| 是某些文件压着的隐性契约 | 写进 `INDEX.md`「按代码文件反查」+ **该文件的行内注释** |
| 是全局工作方式问题（流程、纪律、自检口径） | 提议写进 `CLAUDE.md` 或对应分册，**由用户裁决，Claude 不自行改规则条款** |

**提议格式**（三行，写进收尾汇报，不要长篇）：

```
规则升级提议：<一句话规则>
  依据：本次 + <上次出现的任务/日期>，同一根因第 N 次
  建议落点：CLAUDE.md §X / docs/rules/<分册> / docs/反模式.md AP-NNN / INDEX 按文件反查表
```

⚠️ **收尾四行里的「规则升级：本次提议 N 条 / 无」就是这条的强制输出**（`CLAUDE.md §4.6`）。
写「无」是合法的，**不写才是漏项** —— 强制输出的作用是逼你想一遍，不是逼你每次都提。

### 6.1 规则也要能退役

只有晋升没有退役，规则集只会单调增长到没人读得完。根因已不可能再发生的（依赖移除、架构重构、工具换代）→ 在收尾汇报里**提议退役**，由用户裁决；退役走**归档**不走删除（移入 `docs/archive/` 并注明「已退役，原因 X」），防止后来人翻到历史引用时撞空。
